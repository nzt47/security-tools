## 0. 一句话结论

三个桶现在混装的是**四种东西**：运行时观测（只读）、治理分析（只读）、人工处置（可写）、系统配置（可写且危险）。
按「看 / 改」重新切是合理的，但**不能只切一刀**：只读页有 17 个，一个桶装不下（三个桶合计 29 叶，侧栏全树 38 项），
所以正确做法是 **桶＝能力轴（看/做/配）、小节＝域轴（运行/治理/账号/资源）**，再用页面合并把同源入口收掉。

## 2. 为什么现在"难管理"（不是分类不好看，是四个具体缺陷）

1. **同源双入口**：`admin/dashboard` 与健康仪表盘的「管理概览」Tab 读同一个 `/api/dashboard/summary`，
   两个导航项、两份壳。这正是本仓自己明令避免的"双入口"（`docs/handoff/口径.md` 的单一入口纪律）。
2. **桶名是历史产物**：全景看板里有「引擎（定时任务 CRUD）」「开关中心（改配置）」——
   它们不是"看板"，是**改系统**；治理与运营里有 6 个纯只读分析；系统管理里 4 个纯只读页。
   ⇒ 用户打开某个桶时**无法预判"我能不能动东西"**。
3. **同类页面被桶切开**：审计类有 4 处 —— 日志查看（运行日志）、操作审计（UI 审计中间件）、
   系统日志（应用日志）、审计链导出（不可篡改链）；导出类有 2 处（审计 CSV / 数据分片）。
   想知道"谁动了什么"要在三个桶之间跳。
4. **缺"待办"横切**：审批单、待处理反馈、未处置事故分散在 3 个叶子；
   而审批是 P0 操作面（历史上曾因藏太深"没人能批"）。

## 3. 目标架构

### 3.1 推荐：桶＝能力轴，小节＝域轴（保留 4 个桶 key，只换语义）

**桶 key 一个都不新增/删除**（`workspace/panorama/governance/admin` 不变 ⇒ 顶层深链全稳），只改三件事：
桶的标题、桶内内容、桶内小节。

| 桶（key 不变） | 新标题 | 小节 | 叶子 |
|---|---|---|---|
| `workspace` | 会话与配置 | —（不变） | 会话任务 / 分身 / 提示词 / 能力获取 / 技能中心 / 工作流 / 工具与接入 / 记忆管理 / 资产管理（9） |
| `panorama` | **观测（只看）** | 运行 / 治理 / 留档 | health, sensors, monitor, logs, platform ｜ pipeline, capabilities, roi, incidents, route-coverage, business ｜ audit, replay（13） |
| `governance` | **操作（可改）** | 处置 / 调度 | approvals, feedback, ui-guard ｜ engine, settings（5） |
| `admin` | **配置（低频·危险）** | 账号 / 系统与资源 | users, roles, menus ｜ instances, notifications, local, security（7） |
| （从 admin 迁入观测） | — | — | dashboard → 观测·运行；audit/logs/export → 观测·留档 |

要点：
- **只读全部进 `panorama`**，写操作全部进 `governance`/`admin`；
- 但**域轴用小节保留**（观测里再分运行/治理/留档），这样"看"和"改"分开、又不丢"这块是治理还是系统"；
- 叶子 key 全不动 ⇒ 旧深链零迁移（这是本方案最大的便宜）；
- 侧栏变成「4 桶 + 小节 + 叶子」，小节可折叠，默认展开运行/处置/账号三节。

### 3.2 备选：真·二分（不推荐）

「观测（17 项）」「操作（12 项）」两桶。最贴"看/改分开"的字面，但：
17 项必须再分小节（等于回到 3.1），且"治理"与"系统"这两个域感会彻底消失；
审批和用户管理并排，操作风险等级不同却同级。⇒ 长期看更难管。

## 4. 已批准的三处合并（细化到实现）

### 4.1 系统管理·仪表盘 → 健康仪表盘「管理概览」Tab

- **证据**：health.tsx 已有 `TABS` 含 `admin`（标签「管理概览」，`/api/dashboard/summary`，切到才拉一次）；
  `pages/Dashboard/index.tsx` 读的是同一个端点（6429 行 → 卡片化）。
- **做法**（关键细节：**不删页面组件，只删壳**）：
  1. 删叶子 `admin/dashboard`，`LEGACY_NAV_KEY_MAP['admin/dashboard'] = 'panorama/health'`，
     health 启动时识别 `?panel=admin/dashboard`（或 `&tab=admin`）直接落在「管理概览」；
  2. 删**壳** `pages/hub/admin/dashboard.tsx`（16 行，只做 AdminGuard + 包一层）；
  3. `pages/Dashboard/index.tsx` **保留**并改成 health「管理概览」Tab 的内容 —— 一处实现、两处入口收敛成一处；
     依据：`router/index.tsx` 顶部明写「pages/system/*、pages/Dashboard、pages/Export 保留不删」，
     而且它只被这个壳引用（实测全仓仅 1 处 import），不搬进 health 就会变成不可达模块。
  4. 顺带：health 现在那份简版「管理概览」渲染（adminSummary 卡片）与 `pages/Dashboard` 重复，
     合并后删掉简版，只留 `pages/Dashboard`。
- **净效果**：叶子 −1、壳文件 −1、**同源实现 2 → 1**；`ui_reachability` 的 page_files 少 1（壳），需重派生。
- **代价**：收益直接（少一个同源入口），风险低（health 已有该 Tab，改的是"打开时选哪个 Tab"）。

### 4.2 数据导出 → 审计导出页第 2 个 Tab

- **证据**：`governance/audit` = AuditExportPanel（审计链导出 + CSV 下载）；`admin/export` = `pages/Export`（数据分片导出）。
  两者都是"导出数据"，只是对象不同（链 / 业务表）。
- **做法**：在 AuditExportPanel 内加 Tab「审计链 / 数据导出」，把 `pages/Export` 作为第二个 Tab 的内容
  （`pages/Export` 保留、`pages/hub/admin/export.tsx` 壳删）；删叶子 `admin/export`，
  `LEGACY_NAV_KEY_MAP['admin/export'] = 'governance/audit'`（`&tab=export`）。
- **代价**：审计导出页变长（两 Tab），但"导出"从此只有一个入口；净效果同 4.1（叶子 −1、壳 −1）。

### 4.3 消息中心 → 页内 Tab「通知 / 通道」

- **证据**：`HubAdminNotifications` 直接上下堆了 `NotificationCenter`（通知列表，只读）+ `HubChannelsPanel`（通道配置/扩展启停，可写，980 行）。
- **做法**：同一叶子内改成 `PageTabsHeader` + 两 Tab（通知 / 通道），与全站页头一致；**不新增叶子**。
- 顺带：把"当前无发送调用方（未接线）"的提示留在通道 Tab 顶部（已有文案）。

三处合并合计：**29 → 27 个叶子**（dashboard、export 各少 1），且消除 2 处同源/同类多入口。

## 5. 搬迁与契约机制

| 机制 | 用法 | 风险 |
|---|---|---|
| 叶子 key 不变 | S1 只改分组，不动 key | 无（深链、测试、文档全部照旧） |
| `LEGACY_NAV_KEY_MAP` | S2/S3 删叶子时登记旧 key → 新 key | 已有成熟机制；`resolveNavKey` 三态语义不变 |
| `&tab=` 深链 | 合并页用 `?panel=<新key>&tab=<tab>`；旧 `?panel=<旧key>` 由 LEGACY 落到新 key 并打开对应 Tab | 需在合并页读一次 URL（已有先例：instances 的 `initialTab`、tools 的 panel→Tab） |
| 桶 key 不变 | 桶标题改了但 `panorama/governance/admin` 保留 | 顶层 `#/workbench?panel=panorama` 等链接仍有效 |

## 8. 风险与回滚

| 风险 | 说明 | 处置 |
|---|---|---|
| 深链断裂 | 删叶子后旧链接落到默认页 | 全部走 `LEGACY_NAV_KEY_MAP`；加一条测试：旧 key 必须能解析到新 key |

| 一次改太多 | S3 五个合并同批上 | 一批一个合并，逐批三档截图 + 部署验收 |

## 9. 建议

1. **S1 现在做**：收益最大（"能不能改"一眼可分）、风险最低（零 key 变更、零派生）。
2. **S2 紧接着做**：三处合并是 Owner 已点头的，且消除了同源双入口。
3. **S3 按批做**，每批独立可回滚；不建议一次推倒。

> 需要 Owner 拍板的只有一件事：**S1 的桶名**——是叫「观测 / 操作 / 配置」，
