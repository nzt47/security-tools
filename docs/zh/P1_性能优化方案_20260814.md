# P1 性能优化方案（Windows 冷启动卡死 + 锁竞争）

**日期**: 2026-08-14
**依据**: v1.2.0-rc2 全量回归实测暴露的两类性能问题 + 并发安全系列锁纪律沉淀
**前置**: P0 测试可信度修复收口（剩余基线遗留项见 `剩余基线遗留项待办清单_20260814.md`）

---

## 一、问题陈述（实测数据）

### 1.1 Windows 冷启动卡死（本轮回归实证）

`python scripts/run_full_pytest.py 4 4`（4 chunk × 4 worker）与 `4 2` 均出现 chunk 卡死：

| 卡点 | 证据 | 性质 |
|---|---|---|
| `import sentence_transformers`（收集期） | chunk 日志 mtime 7 分钟无写入，卡在 `importlib._bootstrap_external._path_stat` | 冷启动重型依赖真实 import |
| `import pyarrow` | chunk_0 栈：`pyarrow/__init__.py` → `create_module` | 冷启动 C 扩展加载 |
| `importlib.metadata` 扫描 | chunk_1 栈：`path.locate().exists()` → `os.stat` 循环 | 慢文件系统扫描 |
| `weekly_report`/`task_scheduler` | `inspect.getframeinfo` → `os.path.realpath` 慢路径 | 真实功能慢 + 并行资源竞争放大 |

**根因链条**：
1. Windows 上重型 C 扩展（torch/pyarrow/pandas）冷启动加载本身慢（分钟级）
2. 4 个 worker 并发冷启动 → 资源竞争 + Defender 实时扫描 → import 时间暴涨
3. `pytest.ini --timeout=60 --timeout-method=thread`：thread 模式**只能 dump 栈 + 标记失败，无法中断阻塞在系统调用（os.stat/import）的测试** → 超时后测试仍继续执行 → chunk 永久卡住
4. 分块并行下 `weekly_report` 类慢测试被放大到 >60s → Timeout → 卡死

**结论**：本地 Windows 分块并行不可用（只能 4×1 串行 ≈ 50 分钟）；CI Linux 无此问题（signal 超时可中断）。

### 1.2 锁竞争（并发安全系列遗留）

并发安全系列已规范锁纪律（持锁禁 I/O/回调、锁内仅内存状态变更、RetryPolicy 统一重试），但**无量化数据**支撑"Top 锁竞争"判断：
- 无锁等待/持锁时长采样
- 无锁竞争热点报告
- 无法回答"哪把锁在高并发下是瓶颈"

## 二、方案 A：Windows 冷启动卡死治理

### A1 子进程 import 预热机制（核心）

**目标**：消除分块并行子进程的"首个文件收集期冷 import"慢路径。

**实现**：
- 新增 `scripts/warmup_imports.py`：按模块依赖拓扑顺序预加载重型依赖（`torch`→`transformers`→`sentence_transformers`、`pyarrow`→`pandas`、`chromadb`→`pydantic_settings`），仅 import 不推理，输出耗时报告
- `run_full_pytest.py` 每个 chunk 子进程的 pytest 命令前置 `python -c "import warmup"` 预热（或 pytest 插件 `pytest_sessionstart` 钩子）
- 预热失败不阻断（记录 WARN 继续，冷 import 慢但最终完成）

**验收**：4×4 并行下无 chunk 收集期卡死；单 chunk 首个文件收集 < 30s。

### A2 timeout 策略治理

**现状缺陷**：`--timeout-method=thread` 超时不中断阻塞调用。

**方案**：
- **本地 Windows**：调大 `--timeout=120~300`（慢 import 测试留余量），并接受"超时仅标记、测试继续跑完"的语义——配合 A1 预热后超时频率应大幅下降
- **CI Linux**：维持 `--timeout=60 --timeout-method=signal`（SIGALRM 可中断 join/C 扩展，xdist worker 下降级 thread 属已知限制）
- 将 timeout 值收敛到单一配置（`pytest.ini` 注释 + CI 命令行同步，避免漂移）

**验收**：本地串行全量 Timeout 数 ≤ 3 且均为已知慢测试。

### A3 慢测试分流（slow 标记）

**现状**：`weekly_report`/`task_scheduler` 相关测试在分块进程下稳定 >60s。

**方案**：
- `--durations=20` 全量跑一次，列出 Top 慢用例
- 慢用例（>30s）加 `@pytest.mark.slow`，本地全量排除、CI 分块矩阵单独跑（`-m "slow"`）
- 与 ci.yml 现有 `-m "not slow and not skip_ci"` 对齐（CI 已排除 slow）

**验收**：慢用例清单明确；默认回归路径不撞 Timeout。

### A4 分块策略优化

- 当前 `files[i::4]` round-robin：重型依赖文件分散在各块 → 每块都冷加载一次
- 改为**依赖分组**：把共享重型依赖的测试文件聚到同一块（仅一块承担冷加载），其余块轻量快速
- 预热 + 分组后可回退 `4 2` 并行（约 25 分钟）

## 三、方案 B：锁竞争量化与优化

### B1 锁等待采样（先量化）

**目标**：回答"哪把锁是瓶颈"，不盲改。

**实现**：
- 复用并发安全系列 6 个并发测试场景，增加锁等待时长采样：
  - 轻量 hook：`threading.Lock.acquire` 包装或 `sys.setprofile`（生产环境可关）
  - 采集指标：`lock_name / wait_count / wait_total_ms / hold_total_ms / max_hold_ms`
- 输出：`scripts/analyze_lock_hotspots.py --log <采集日志>` → Top N 锁竞争报告（Markdown/JSON）
- 采样仅在压测/诊断模式开启（`LOCK_PROFILE=1`），默认零开销

**验收**：产出锁竞争热点报告；明确 Top 3 锁。

### B2 热点优化手段（按 B1 报告选择）

| 手段 | 适用场景 | 先例 |
|---|---|---|
| 读写锁（`threading.RLock`/`RWLock`） | 读多写少的全局状态 | `routes_logging._ALERT_RULES_CACHE` |
| 分段锁（shard locks） | 单一全局锁串行化热路径 | `lock_free_ring_buffer` |
| 无锁化（CAS/队列） | 计数器/状态标志 | perf_monitor `_CountingFilter` 线程安全计数 |
| I/O 移出锁外（已有纪律） | 存储/日志路径 | storage/replay_storage 已异步化 |

**验收**：Top 锁等待时间降低 ≥50%（以 B1 基线为准）。

### B3 日志/存储路径异步化（B2 延续）

- 采样/统计路径：队列 + 批量 flush + 背压（现有 `log_dict`/perf_monitor 过滤链）
- 对齐 HPA/Prometheus 基线：P99 ≤ 40ms（warning）/ 80ms（critical）
- 约束：【不易】异步写入必须有重试机制保证最终一致性（对齐 memories_fts 事务性写入约定）

## 四、验收标准总表

| 指标 | 当前 | 目标 |
|---|---|---|
| 本地全量回归耗时（4×4 并行） | 不可用（卡死） | ≤ 25 分钟 |
| 本地全量回归耗时（4×1 串行） | ~50 分钟 | ≤ 35 分钟（预热后） |
| chunk 收集期卡死 | 复现 | 0 次 |
| Timeout 失败数（全量） | 3+（weekly_report 等） | ≤ 3 且均为 slow 标记 |
| 锁竞争热点报告 | 无 | 可复现产出 |
| Top 锁等待时间 | 无基线 | 降低 ≥50% |
| 日志路径 P99 | — | ≤40ms（warning）/ ≤80ms（critical） |
