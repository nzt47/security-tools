# 灰度执行隔离设计（TASK-S8-03 / v7.2 §5.1 · §5.2）

> 版本：s8-03.1｜落地模块：`agent/digestion/isolation.py`、`isolation_worker.py`、`takeover.py`
> 实测脚本：`scripts/verify_isolation.py`（机器可读证据）｜演示：`scripts/demo_s8_03_isolation.py`
> 本文回答三件事：**等级怎么定**、**每一档到底保证了什么**、**哪些边界我们明确不保证**。

---

## 一、为什么需要它

S3-02 的回放沙箱是**进程内确定性执行模型**：它跑的是 `ReplayEnv` 内存虚拟文件系统，
`commit()` 恒抛，出界即 `SandboxEscapeError`。用来判"行为是否等价"它是对的
（同输入同结果、无墙钟无随机），但用来**跑真实生成代码**它不够——因为它根本没有
"边界"可言，候选与宿主在同一个进程里。

于是 S3-03 的 shadow 灰度只能"**记录选中**"（`gray.routed`）而不能"**真实接管**"，
`real_takeover=false`、`container_isolated=false` 是当时**如实**的声明。本任务补齐
执行隔离，从而**解锁**真实接管——并且保持"默认关闭"。

## 二、三档隔离等级

```
IsolationLevel ∈ { in_process , subprocess_hardened , container }
```

| 等级 | 何时生效 | 边界性质 | `kernel_isolation` | `container_isolated` |
|---|---|---|---|---|
| `in_process` | 显式要求；或容器与子进程能力**都**不可用 | 无执行隔离（沿用 S3-02 回放模型） | ✗ | ✗ |
| `subprocess_hardened` | 有 Python 子进程能力但**无** Docker（Windows 开发机 / 无 Docker 的 CI） | **进程级 + 环境级**，无内核级 | ✗ | ✗ |
| `container` | Docker CLI **与** daemon 均可用 | **内核级**（namespace + cgroup + 只读挂载 + 非 root） | ✓ | ✓ |

> **强序只是"边界更强"，不是"可互相冒充"。** `ISOLATION_RANK` 仅用于展示排序与降级方向，
> 任何地方都不得用"等级更高"掩盖"这次其实是另一档在跑"——`isolation_declaration()`
> 为此把**本次实际等级**与**环境最高等级**分成两个字段。

## 三、选择与降级策略

```
requested = 调用方参数  >  CP_DIGESTION_ISOLATION_LEVEL  >  auto
auto      : Docker 可用 → container
            否则子进程可用 → subprocess_hardened
            否则 → in_process（并**拒绝** real_takeover）
```

四条硬规则：

1. **探测分两步**：`docker --version`（CLI 是否存在）与 `docker info`（daemon 是否在跑）。
   **必须分开**——"装了 CLI 但 daemon 没起"是开发机最常见状态，把它当成"容器可用"
   正是"冒充容器"。实测这台机器上就出现过：CLI 29.4.3 在，daemon 起初没起。
2. **显式请求 container 但 Docker 不可用 ⇒ 如实降级到 `subprocess_hardened`**，
   `downgraded=True`，降级理由进 `reasons` 与报告。**绝不冒称容器。**
3. **显式 `in_process`/`subprocess_hardened` 不做 Docker 探测**（与结果无关），
   并如实标注 `docker.probed=false`——不伪造一个"不可用"的探测结论。
4. **非法取值回退 `auto`** 并说明（不猜、不静默）。探测结果带 TTL 缓存；
   daemon 忙导致的探测超时方向是**保守的**（判不可用 ⇒ 退到更弱的档或直接拒绝）。
5. **`in_process` ⇒ 拒绝 `real_takeover`**：策略层（`resolve_takeover_policy`）
   在解析阶段就返回 `enabled=False`、`source=refused_no_isolation`，且**优先级高于**
   能力级配置——**没有隔离就不接管，这条不可由配置绕过**。

## 四、容器路径（Linux/Docker）

启动参数逐条显式（`ContainerExecutor.build_argv()`，用例断言每个参数都在）：

| 维度 | 参数 | 为什么 |
|---|---|---|
| 网络 | `--network none`（默认） | 出域在**内核/网络命名空间**层面被拒，不是靠自觉 |
| 内存 | `--memory {m}m --memory-swap {m}m` | cgroup 硬限；超限被 OOM kill（退出码 137） |
| CPU | `--cpus {n}` | cgroup 配额 |
| 进程数 | `--pids-limit {n}` | 挡住 fork 炸弹 |
| 文件系统 | `--read-only` + `--tmpfs /work:…,mode=1777` + `--tmpfs /tmp:…` | 根只读；**唯一可写根是 tmpfs 临时目录** |
| 源码 | `--mount type=bind,source=<repo>,target=/src,readonly` | 源码树只读；**唯一挂载**（不挂 `$HOME`/`.ssh`/凭据目录） |
| 权限 | `--user 65534:65534 --cap-drop ALL --security-opt no-new-privileges` | 非 root、无 capability、禁止提权 |
| 环境 | `-e HOME= -e USERPROFILE= -e SSH_AUTH_SOCK= …` | 「存在但为空」比「不存在」更能挡住 `getenv(k, default)` 的默认值回退（S4-04 同款做法） |

**禁止出现**的参数（用例断言）：`--privileged`、`--pid=host`、`--network=host`、
`--userns=host`、`--cap-add`、`-v/--volume`（挂载一律走 `--mount` 且只读源码）。

### 实测踩到的两个坑（如实记录，不粉饰）

1. **`-e HOME=` 挡不住 Docker**：Docker/runc 会按容器用户的 passwd 条目覆写 `HOME`
   （`--user 65534:65534` ⇒ `/nonexistent`；root ⇒ `/root`），而 `-e CP_TEST=` 这类
   普通变量是生效的。故**平台原始值另存 `env_raw`**，再由执行体在启动时统一清空为
   空串——两件事分开记，报告里不会出现"已清空"掩盖"平台本来给了什么"。
2. **tmpfs 默认 root 属主**：非 root 用户写不进去（`PermissionError: /work/a`）。
   故 tmpfs 显式给 `mode=1777`。

## 五、强隔离子进程路径（Windows 无 Docker）

复用 S4-04 已验证的环境清空范式（`agent/subagent/sandbox.apply_isolation_env`，
`env_mode=replace` 语义，函数体内懒加载）：

| 维度 | 做法 | 手段性质 |
|---|---|---|
| 环境 | **整体替换**：`HOME`/`USERPROFILE`/`SSH_AUTH_SOCK`/`SSH_AGENT_PID`/`GIT_SSH_COMMAND` 置空；`AWS_*`/`AZURE_*`/`GOOGLE_*`/`KUBECONFIG`/`GH_TOKEN`/`GITHUB_TOKEN`/`NPM_TOKEN`/`OPENAI_*`/`ANTHROPIC_*` 等**前缀命中即删除**；全部代理出口清空 | 环境级（可靠） |
| 工作目录 | 一次性临时目录（`tempfile.mkdtemp`），cwd 指向它，用后即删 | 进程级 |
| 文件 | **协作式路径守卫**：唯一可写根是临时目录；源码树只读（越界即 `escape_blocked`） | **协作式（可被不守规矩的二进制绕过）** |
| 资源 | 墙钟超时 kill + stdout/stderr 截断；POSIX 另有 `RLIMIT_AS/CPU/NPROC/FSIZE`（`preexec_fn`） | 超时=宿主强制；rlimit=内核；**Windows 无 rlimit** |
| 网络 | 代理出口清空 + 应用层策略（`network=none` 时协作式拒绝）；外部调用**只记账不外发** | **非内核级** |
| 用户 | 与宿主同用户 | 无隔离 |

**一句话**：这一档买到的是"**环境与工作目录的干净**"，买不到"**内核级边界**"。
详见第六节实测对比表里标着「差距」的那几格。

## 六、等级实测对比表（机器可读证据的**摘要**；原始输出见验收报告）

由 `scripts/verify_isolation.py` 在目标等级内**实测**产出（每个等级单独跑，
跑不了的等级如实写「未运行（原因）」，**不以后验推断补写**）：

| 边界 | in_process | subprocess_hardened | container |
|---|---|---|---|
| HOME 为空 | 未运行（refused） | `''` | `''` |
| USERPROFILE 为空 | 未运行（refused） | `''` | `''` |
| SSH_AUTH_SOCK 为空 | 未运行（refused） | `''` | `''` |
| HOME 平台原始值 | 未运行（refused） | `''` | `/nonexistent`（非宿主 HOME） |
| 宿主凭据（**env 推导**路径）不可见 | 未运行（refused） | 不可见 | 不可见 |
| 宿主凭据（**绝对**路径）不可见 | 未运行（refused） | **可见（差距）** | 不可见 |
| 临时目录可写 | 未运行（refused） | 可写 | 可写 |
| 源码树只读 | 未运行（refused） | **写入成功（差距）** | 写入被拒 |
| 宿主目录不可写 | 未运行（refused） | **越界写入成功（差距）** | 写入被拒 |
| 出域被策略拒绝 | 未运行（refused） | 拒绝 | 拒绝 |
| 出域被**内核**拒绝（直连探针） | 未运行（refused） | **可达（无内核级网络隔离）** | 拒绝（内核级） |
| 内存超限被终止 | 未运行（refused） | **未终止（分配 512MB 仍存活）** | 被终止（硬限） |
| CPU/时间超限被终止 | 未运行（refused） | 被终止 | 被终止 |
| 进程数超限被拒 | 未运行（refused） | **未拒（同时存活 80/80）** | 被拒 |
| 非 root 运行 | 未运行（refused） | 非 root（Windows 无 uid 概念） | `uid=65534`（非 root） |

> 「未运行（refused）」是 `in_process` 的**正确**结论：该档没有执行隔离环境，
> 执行器**拒绝**在边界外执行候选（fail-closed），而不是"跑一下看看"。
> 「差距」是 `subprocess_hardened` 的**真实弱点**，不掩饰也不因此废掉这一档。

## 七、不保证的边界（诚实清单）

### 7.1 所有等级共同不保证

- 不保证候选**逻辑正确**：隔离只保证"跑得安全"，不保证"跑得对"（等价性由三层比对判）。
- 不保证抵抗**拒绝服务**：候选可以耗尽自己的配额（被终止），但配额内的抖动仍会影响耗时观测。
- 不保证**跨等级行为一致**：`in_process` 用模型时钟、隔离执行用真实墙钟，两者不做量纲换算。

### 7.2 `subprocess_hardened` 明确**不**提供

- ❌ **内核级隔离**：无 mount/net/pid namespace，无 cgroup。
- ❌ 宿主文件系统的**绝对路径**保护：路径守卫是协作式的，一个不理会守卫的二进制可以越界。
- ❌ **内核级网络拒绝**：只有代理清空 + 应用层策略，直连 socket 仍可能成功（实测可达）。
- ❌ Windows 上的内存/CPU/进程数**硬上限**：无 `resource` 模块等价物，只有墙钟超时兜底。
- ❌ 与宿主**不同用户**：同用户、同会话。
- ❌ 系统调用过滤（无 seccomp/AppArmor 等价物）。
- ➡️ 因此**不得**用于执行来源不可信的第三方二进制；只用于云枢自己生成、已被判定集约束的候选实现。
- ⚠️ POSIX 上 `os.path.expanduser("~")` 在 `HOME=""` 时会回退到 passwd 条目（实测返回 `/`），
  故探针**不使用** `expanduser` 推导凭据路径，而是显式用 `HOME`/`USERPROFILE` 推导并
  另记 `home_expand` 原始值——避免用一次"看起来不可达"掩盖"其实可达"。

### 7.3 `container` 明确**不**提供

- ❌ **不是虚拟机**：与宿主共享内核，内核漏洞可逃逸（本任务不做 VM 级隔离）。
- ❌ **镜像供应链**：按 tag 固定（`python:3.12-slim`），未按 digest 锁定。
- ❌ 自定义 seccomp/AppArmor：沿用 Docker 默认档。
- ❌ `network=whitelist` 下白名单是**应用层**协作策略，**非**内核级拒绝（只有 `--network none` 是内核级）。
- ❌ 侧信道（计时/缓存）与 DoS 类攻击不在本任务范围。
- ❌ Docker daemon 自身被攻陷时全部约束失效（信任边界在 daemon 之外）。

### 7.4 「等级如实标注」的落点

`ShadowReport.isolation` 把三件事**分开**报告，任何一件都不得由另一件代偿：

| 字段 | 含义 |
|---|---|
| `mode` | **本次实际**用的执行模型（`in_process_deterministic_model` / `isolated_execution`） |
| `real_takeover` | **本次是否真的接管了**（= 开关开 **且** 实际执行了） |
| `real_takeover_enabled` | 开关是否开着（开着但预算为 0 ⇒ `real_takeover=false` 且此字段 `true`） |
| `level` / `container_isolated` | 本次**生效**等级（容器不可用时这里绝不会是 `container`） |
| `available_level` | 环境**具备**的最高等级 |
| `guarantees` / `not_guaranteed` | 该等级**保证**什么、**不保证**什么（本文第七节的机器可读形态） |

## 八、与灰度链路的接线

```
ShadowRunner.run()
  ├─ ① 开关（默认关闭）        ② 通行证（PassportStore，无证不放行）      ③ 判定集
  ├─ ④ 抽样计划（预算/确定性抽样/灰度路由）
  ├─ ⑤ 10% 人工抽检清单
  ├─ ⑥ 逐样本**回放**双跑（S3-02 沙箱；副作用只记录 —— 语义**未改**）
  ├─ ⑥.5 **真实接管**（本任务新增；默认关闭）
  │     策略：默认关 + 显式比例 + 无隔离即拒绝 + 每日预算
  │     执行：IsolationExecutor（container / subprocess_hardened）
  │     比对：与**同一候选的回放观测**比硬性两层（结构 / 副作用）
  │     失败：连续 N 次 ⇒ 回落 sandbox_replay_only + 事故卡（L2）
  └─ ⑦ 人工抽检入队  ⑧ 劣化信号/开销/质量补丁  ⑨ 台账 + 事件 + 审计 + 声明定稿
```

### 8.1 `ReplaySandbox.isolation_level`（S3-02 语义**不变**）

- 新增构造参数 `isolation_level`（默认 `in_process`），不可识别取值**回退** `in_process`；
- 新增 `isolation_plan()` / `isolation_executor()` / `execute_isolated(job)` / `verify_isolation()`；
- **`replay_case()` 一行未改**：仍然全程 `ReplayEnv` 内存模型、`commit()` 仍恒抛。
  用例断言：换等级不改变回放的 `status`/`steps`/副作用集合/canonical 文本/判定结论。
- 两条通道的分工是刻意的：**判定等价性**（回放，确定性）与**安全执行真实代码**（隔离）
  是两件事；混在一起会让"等价"这个结论失去确定性。

### 8.2 真实接管的四条契约

1. **默认关闭**：需 `CP_DIGESTION_REAL_TAKEOVER=true` **且**显式比例
   （`CP_DIGESTION_REAL_TAKEOVER_RATIO` 或能力级 `shadow_config.real_takeover_ratio`）。
   只开开关不给比例 ⇒ 不开；非法比例 ⇒ 回退关闭。
2. **无隔离即拒绝**（见 §三规则 5）。
3. **有每日预算上限**：沿用 S3-03 的 `min(日均 × 比例, 上限)`（含低流量保底与
   S5-03 成本刹车系数）；预算 0 ⇒ **一次都不跑**（不是"跑一点"）。
4. **连续失败自动回落**：连续 `N`（默认 3）轮"跑了但失败" ⇒ 本能力自动回落
   `sandbox_replay_only` + 开事故卡（`self_healing.levels.raise_incident`，L2）
   + 审计。回落态写在**台账**里（不是内存计数），跨进程重启仍然成立；
   恢复需有成功一轮（或人工处理事故卡）。

> 「失败」= 隔离执行未成功 **或** 与回放观测硬性两层不一致。
> 「没跑」（预算 0 / 未抽样）**不计**为失败——否则"因为没预算所以没跑"会被读成"一直失败"。

### 8.3 比对口径（为什么只有硬性两层）

| 层 | 是否执行 | 口径 |
|---|---|---|
| `structure` | **硬性** | 终态归一后相等 **且** 步骤标签序列逐字相等 |
| `side_effects` | **硬性** | 三类副作用的形态归一集合相等（沿用 `normalize_param_value`） |
| `judge` | **如实 `not_run`** | 两条通道输出形态不同（回放=虚拟工具结果，隔离=真实进程输出），拿相似度去抹平这个差异只会制造"看起来等价"的假象 |

**为什么接管不自动合入**：任务书 §五明确"自动合入候选产物"属 L2 白名单决策，
不在本任务。故 `TakeoverReport.adopted` **恒为 `False`**，产物只作为证据留在
报告与台账里。

### 8.4 留痕

| 载体 | 内容 |
|---|---|
| 审计 | `digest.shadow.takeover`（正常轮）、`digest.shadow.takeover_fallback`（回落轮），actor=`<runner.actor>.takeover` |
| 事件 | **复用既有 `digest.stage`**（不新增事件类型），`scope=shadow_takeover`，reasons 带 `isolation_level`/`transport`/`budget`/`executed`/`failed`/`fallback`/`adopted` |
| Trace | 能力级 `digestion.takeover.<capability_id>`，**actor=`digestion.takeover`**；`side_effects.notes` 标注等级/传输/是否合入 |
| 台账 | `takeover_ledger.jsonl`（能力级、每轮一行：attempted/succeeded/failed/level/fallback/incident_id） |
| 事故卡 | `data/healing_incidents/inc_*.json`（L2；detail 带 `capability_id`/`level`/`fallback_transport`） |

> **已知的诚实限制**：接管的 Trace 在没有任务上下文（`TraceContext.current()` 为空）时，
> 会按统一台账的既有不变量"缺 `workspace_id` ⇒ 显式降级"记录（日志可见该告警）。
> 这是既有的 P7.1-19 行为，本任务不绕过它，也不把它说成"完整 Trace"。

## 九、record-and-replay 语义不变（副作用只记录不双写）

四道闸同时成立：

1. **回放通道**：`ReplayEnv.commit()` 恒抛；
2. **隔离通道**：唯一可写根是一次性临时目录（容器内是 tmpfs，宿主上是 `mkdtemp`，用后即删）；
   源码树对容器是只读挂载、对子进程是协作式守卫；
3. **外部调用**：一律只记 `external_calls` 副作用，**永不真实外发**；
4. **实测比对**：`snapshot_paths()` / `diff_snapshot()` 对真实目录做前后指纹比对
   （`changed`/`created`/`removed` 三态分开——把"被改写"说成"删了又建"是把严重的事说轻）。

演示与用例都断言：一次完整接管跑完后，真实环境见证目录的指纹**逐字未变**。
