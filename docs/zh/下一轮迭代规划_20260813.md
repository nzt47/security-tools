# 下一轮迭代规划（v1.2.0-rc1 之后）

**日期**: 2026-08-13
**依据**: v1.2.0-rc1 并发安全修复系列收口 + 全量回归 98 失败甄别结论 + planning 记账修复（TD-4）状态

---

## 背景

v1.2.0-rc1 已完成并发安全系列闭环（高 3 / 中 12 / 低 7），但全量回归暴露三类非本系列问题，且运行时性能仍存在可量化优化空间。下一轮按"先修可信度 → 再提性能 → 后做功能"排序。

---

## A. 测试可信度修复（P0，短期）— 全量回归稳定全绿

> 目标：`pytest tests/` 无环境性/顺序性失败，全量结果可信，为后续迭代提供稳定基线。

| 项 | 现象 | 根因/方向 | 验收 |
|---|---|---|---|
| A1 测试顺序污染治理 | ~53 用例单跑通过、全量失败（dialog_state / response_workflows / knowledge_observability / log_dict / mcp_executor / perf_monitor / skill_manager / few_shot_injector / security_utils） | `--randomly-seed` 下模块 reload 导致类身份错位、全局单例/状态跨用例泄漏；方向：按模块收敛全局状态（fixture 重置）、固定 seed 基线或引入测试隔离；`test_few_shot_injector.py::test_select_examples_by_intent` 最后变动于 `1d6a22d5`（其他会话），需先确认是否已提交 | 固定 seed 全量 0 失败，多 seed 抽样稳定 |
| A2 环境依赖修复 | `tests/unit/test_vector_store_sqlite_vec.py` 4 用例 `ModuleNotFoundError: transformers.configuration_utils`；另有 10 个 pytest errors 待归因 | 环境依赖损坏（模块非 package）；方向：版本 pin / 重装 / 降级路径（sqlite-vec 不可用时纯 FTS5+BM25 已有）；10 errors 需逐一确认归属（collect 错误 vs setup 错误） | 环境健康检查脚本通过；errors 归零 |
| A3 工作区纪律 | orchestrator `_interaction_lock`（18 用例）+ parent_selection `EvolutionRecord params`（8 用例）失败 | 其他会话未提交/未跟踪改动污染回归判定；方向：并行会话及时提交、回归前 `git status` 核查 | 回归前工作区干净或差异已知 |

## B. 性能优化（P1，中期）

> 目标：在锁纪律已规范的基础上，量化并削减锁竞争与 I/O 延迟。

| 项 | 方向 | 收益 | 验收 |
|---|---|---|---|
| B1 锁竞争热点分析 | 在 6 个并发测试基础上引入锁等待时间采样（profiling hook / 计数），定位高竞争锁；评估读写锁 / 分段锁 / 无锁化（`lock_free_ring_buffer` 已有先例） | 高并发下吞吐与 P99 延迟 | 热点报告产出，Top 锁竞争降低 |
| B2 日志/存储路径异步化 | storage / replay_storage 已把 I/O 移出锁外，进一步评估异步批量落盘（队列 + 批量 flush + 背压），降低采样与统计路径延迟 | 日志路径不阻塞业务线程 | 压测 P99 达标（对齐 HPA/Prometheus 基线） |
| B3 测试套件提速 | 全量 52 分钟：`pytest --durations` 定位慢用例、`-x` 并行分发（xdist）或拆分 CI 矩阵 | 全量回归缩短，CI 反馈加速 | 全量 < 30 分钟 |

## C. 新功能迭代（P2，长期）

> 目标：把并发安全从"修复"升级为"预防"，并继续推进进化机制重构。

| 项 | 方向 | 说明 |
|---|---|---|
| C1 进化机制重构收尾 | TD-4 记账修复已闭环，阶段 5 灰度发布操作手册已就绪 → 按手册执行灰度发布，继续剩余阶段 | 规划模块闭环可观测 |
| C2 运行时锁看门狗 | 引入持锁超时看护（锁等待/持锁时长告警），接入 Prometheus 告警规则（P99 >40/80ms 已有基线） | 锁纪律违规运行时即暴露，而非等崩溃 |
| C3 锁纪律静态扫描 | 将"锁内禁止 I/O/回调"固化为 CI 静态扫描（沿用 kwarg-scanner 容器化先例），新代码进库即拦截 | 从源头防止锁纪律回潮 |

---

## 优先级建议

1. **A 先行**：A1/A2/A3 是全部后续工作的可信度前提（当前全量 98 失败中 83 个非本系列，必须归零）。
2. **B1+B2 可并行**：均依赖 A 的稳定基线；B3 独立可随时启动。
3. **C 依赖前两者**：C2/C3 是对本系列修复的机制化沉淀，建议在 B 阶段同步设计。
