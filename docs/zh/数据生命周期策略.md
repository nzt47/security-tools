## 一、定位与三条不可越界原则

云枢已有 **12 类只有追加、没有清理**的运行时数据。短期无害，长期会让"跑得久"变成风险：
磁盘膨胀、查询变慢、归档不可控、**没人说得清哪一类可以删**。

本策略把每一类数据的三件事写成可机械判定的规则：**留多久 / 怎么归档 / 能不能删**。

三条不可越界原则（批次总表 §二，本策略的宪法）：

| # | 原则 | 代码落点 |
|---|---|---|
| ① | **审计链永久保留**，只归档不删除 | `policy.REDLINE_CLASS_IDS` + `guard.PurgeGuard`（`CODE_REDLINE`） |
| ② | **默认保守**：首跑 dry-run、只归档不删除、调度默认关闭 | `policy.delete_source=False`（默认）+ `scheduler` 首跑强制 dry-run + `CP_RETENTION_ENABLED` 默认关 |
| ③ | **不改变既有统计口径**（历史指标须仍可复算） | `metrics.py` 归档前后复算对照；温层只对**读端分片感知**的类开启 |

## 二、分层模型

| 层 | 含义 | 实现 | 是否改变文件布局 |
|---|---|---|---|
| **热** | 近期可查，仍在活动文件里 | 不动 | 否 |
| **温** | 活动文件里的历史行按日分片，仍可查（不压缩） | **复用既有** `agent/skills_mgmt/log_archiver.archive_daily_file` | **是**（故仅读端分片感知的类可开） |
| **冷** | 整文件打成**自描述压缩包**，离线可还原 | `agent/retention/archiver.py` → `data/archive/<class>/<period>.<ext>.gz` | 默认**只复制不搬走** |
| **删** | 仅显式标"可删"的类，且必须先过 `PurgeGuard` | `agent/retention/guard.py` | 默认**关闭** |

### 温层为什么不是每类都开

温层会**改变文件布局**（行从活动文件移到分片文件）。只有读端已被证实"分片感知"的类才能开，
否则读端只认活动文件 ⇒ 归档后指标变小 ⇒ 等于篡改历史。实测结论：

| 数据类 | 读端是否分片感知 | 证据 | 温层 |
|---|---|---|---|
| `events` | ✅ | `agent/observability/events.py::event_files()` 收 `events-*.jsonl`；跨分片按 `event_id` 去重 | 开（`warm_days=0`） |
| `policy_decisions` | ✅ | `agent/policy/decisions.py::_candidate_files()` 收 `<stem>.<any>.jsonl` | 开（`warm_days=0`） |
| `shadow_ledger` | ❌ | `ShadowLedger.rows()` / `ManualReviewQueue.rows()` 只读 `self.path` 单文件 | **关** |
| `skills_audit` | ❌ | 读端为各技能模块自行拼路径，无分片约定 | **关** |
| 其余 | ❌ | 非行式数据（SQLite / 文件树） | **关** |

`warm_days=0` 的语义是"**活动文件只保留当日**"，与既有 `log_archiver` 的判定（`ts[:10] >= today` 留、其余为历史行）
**逐字一致**。其它正值无法由既有实现表达，`scan.warm_plan()` 会显式报告"温层不可表达"而**不自造第二套分片语义**。

### 3.1 红线类（**禁止删除**）

以下三类在策略表与代码里都显式标注 **禁止删除**，`PurgeGuard` 一律拦截（包括"误把审计类当普通类传进来"）：

| 红线类 | 为什么禁止删除 |
|---|---|
| `audit_chain` | **审计链 + 每日 Merkle 根**是全部动作的证据本体。删除即无法验签、无法自证历史。归档只做**一致性备份副本**，源库与链序（`seq`）永不改动 |
| `skills_audit` | **纯审计轨**（S2-02 已 chmod 0444 置只读）；冻结后仍要求"不删除、不追溯" |
| `legacy_audit_archive` | 存量审计的只读归档镜像，本身就被定义为"不删除" |

> **签名私钥不进归档**：`data/audit/audit_signing_key.pem` **刻意不在** `audit_chain` 的 globs 内 ——
> 把私钥复制进归档目录会扩大暴露面，签名私钥由既有 `AUDIT_SIGNING_KEY` 管理。

### 3.2 记忆类：删记忆不删证据（S5-01 路径）

`memory_entries` / `memory_snapshots` 在策略表里标为"可删"，但**本模块没有删除权**：
`PurgeGuard` 会以 `CODE_FORGETTING_PATH` 拒绝，并把调用方**转给**
`agent.memory.forgetting.ForgettingEngine`。那条路径的语义由 S5-01 定义，本任务只做接线与拦截：

```
ForgettingEngine.forget(candidates) / erase_subject(subject_id)
  ① 先快照      MemorySnapshotStore.capture(...)      ← 删除前的回滚凭据
  ② 再删除      物理删除记忆条目
  ③ 盐销毁      SubjectPseudonymizer.shred(sid)       ← 密码学粉碎（链上只有假名）
  ④ 链保留      写 memory.erase（subject 用假名）+ verify_chain + 残留标识扫描
```

即：**链上永远留有"发生过删除"的证据，但没有被删的内容**。

## 四、归档件格式（自描述）

每个冷归档件 = 一个压缩包 + 一份清单（落地 `data/archive/<class>/`）：

```
data/archive/events/2026-09-10.jsonl.gz
data/archive/events/2026-09-10.manifest.json
data/archive/audit_chain/2026-09-13.db.gz
data/archive/audit_chain/2026-09-13.manifest.json
```

清单字段（`agent/retention/manifest.py::ArchiveManifest`）：

| 字段 | 含义 |
|---|---|
| `schema` / `schema_version` | 归档格式版本（`retention.archive.v1`；非法版本**一律拒读**，不做"尽力兼容"） |
| `class_id` / `period` / `period_kind` | 数据类 + 归属周期（`day` 分片日 / `snapshot` 快照日） |
| `created_at` | 归档时间（UTC） |
| `time_range`（`first_ts`/`last_ts`） | 归档内容的**真实时间范围**（取不到则为空，不猜） |
| `record_count` / `file_count` | 记录数（JSONL=行数；SQLite=表行数；树=文件数）/ 文件数 |
| `payload_bytes` / `payload_sha256` | 解压后载荷的字节数与校验和 |
| `archive_bytes` / `archive_sha256` | 压缩件本身的字节数与校验和（**防归档件被改**） |
| `files[*]` | 每个源文件的**字节切片**（`offset`/`bytes`）+ 自身 `sha256`（SQLite 另有 `row_count`/`row_digest`） |
| `codec` | 压缩编解码器（还原端按此解，不靠猜扩展名） |

**载荷 = 各源文件原始字节按顺序拼接**（不重排、不解析、不规范化），因此
"往返一致"是**逐字节**判定而不是"看起来差不多"。压缩用 stdlib `gzip`（`mtime=0`，确定性）：
`zstandard` 虽在本机可用但**未进 `requirements`**，硬依赖会让 CI 在干净环境上失败。

### 4.1 SQLite 为什么用一致性备份

`unified_traces` / `audit_chain` 是**活动 SQLite 库**（开着 WAL、后台有写线程）。
文件级复制会得到"页撕裂"副本（能打开、行数不对）。故走 `sqlite3.Connection.backup()`
（官方在线备份 API）→ 副本入包。副本字节的 sha256 ≠ 活动库的 sha256，
所以还原一致性用**行级摘要**（`row_digest`）判定，而不是字节比对。

## 五、删除闸门（PurgeGuard）

删除是唯一不可逆的动作，故设一道**必经闸门**：**本治理层**的删除动作在真正 `os.remove`
之前都必须过 `agent/retention/guard.py::PurgeGuard.check()`（`Archiver._do_purge` 删前
会**再判一次**，含"必须先有归档件"）。六条拒绝理由，任一命中即拒：

| 拒绝码 | 触发条件 | 说明 |
|---|---|---|
| `redline` | 类为红线（审计链/每日根/纯审计轨/只读镜像） | **含"误把审计类当普通类传进来"** |
| `forgetting_path` | 类为记忆类 | 转 `agent.memory.forgetting.ForgettingEngine`（S5-01） |
| `not_deletable` | 策略表未标"可删" | 默认策略 = 只归档不删除 |
| `metric_dependency` | 有既有指标依赖本类明细复算 | 删了就"篡改历史" |
| `out_of_scope` | 待删路径不在本类 globs 展开结果内 | 越界删除防护（用白名单，不用目录前缀） |
| `not_frozen` | 该路径尚无校验通过的归档件 | **先归档、验签、再删除** |

补充：`no_paths`（空清单）与 `unknown_class`（未知类）同样拒绝。

### 5.1 管辖边界（**不在本治理层管辖内的既有删除路径**）

本闸门管辖 **`agent/retention` 自己发起的删除**。仓库里还有**各模块自带的既有清理路径
（不在本治理层管辖内）**，它们**不经过**本闸门 —— 本任务**不接管**它们
（接管属重构而非治理，会变更既有语义）：

| 既有清理路径 | 清理对象 |
|---|---|
| `agent/monitoring/replay_storage.py::cleanup_old_records(days=30)` | 回放记录（含 `DELETE` + `os.remove`） |
| `agent/p6/snapshot.py::cleanup_snapshots(keep_count=5)` / `agent/p6_snapshot.py::cleanup_snapshots` | 旧快照文件 |
| `agent/memory/forgetting.py::prune()` | 记忆快照库到期件（**S5-01 自有口径**） |
| `agent/policy/inbox.py::prune_recent()` | 策略收件箱近期项 |
| `agent/tool_fewshot_store.py::cleanup_expired()` | 过期 few-shot 样本 |
| `agent/task_scheduler.py::cleanup_old_logs()` | 调度器日志 |
| `agent/skills_mgmt/cleanup.py::cleanup_orphans` / `cleanup_unused` | 技能资产孤儿/未用 |
| `agent/monitoring/resource_monitor.py::cleanup_persisted_history()` | 资源监控历史 |

**因此本闸门提供的是「销毁类动作在 `agent/retention` 内不可绕过」，不是「全仓库只有一条删除路径」。**
把这条边界写明，是为了避免后来者把"闸门存在"误读成"所有删除都被守卫"——
那会让人对未受守卫的路径放松警惕。

### 5.2 已知落点风险（如实登记）

* `agent/policy/decisions.py::DEFAULT_DECISION_LOG = "data/policies/decisions.jsonl"` 是
  **相对进程 CWD** 的路径（不是从 `__file__` 推出、也未被绝对化）。若进程 CWD 不是仓库根，
  决策日志会落到别处，本策略的 globs（相对仓库根）就会**扫不到它**。
  本任务不改该模块语义；运营期若以非仓库根为 CWD 启动，请用 `CP_POLICY_DECISION_LOG`
  显式指定绝对路径。
* `agent/skills_mgmt/log_archiver.archive_daily_file` 的**实际**分片后缀是 `-YYYY-MM-DD`
  （如 `events-2026-09-10.jsonl`），而该模块 docstring 写的是 `-YYYYMMDD`。
  本策略的归属日解析**两种形态都认**（`scan._DAY_RE` / `scan._DAY_COMPACT_RE`），
  以免依赖单一口径。

## 六、调度与开关（默认关闭 + 首跑 dry-run）

`agent/retention/scheduler.py::register_retention_job()`

* **默认关闭**：只有 `CP_RETENTION_ENABLED=true`（或 `config.yaml retention.enabled: true`）才注册任务。
* **默认每周日 03:00**（`day_of_week=6`，Python weekday 语义），可配。
* **首跑强制 dry-run**：即使运维已把 `CP_RETENTION_DRY_RUN` 设为 `false`，
  **本进程内的第一次运行仍是 dry-run**（先列出将归档哪些类、多少文件、多少字节），第二次才真正落盘。
* **每次执行入链式审计**：`action="retention.run"`，payload 只放**计数与体积**
  （归档包数/文件数/记录数/字节数、温层移出行数、删除文件数/字节数、清单路径），不放内容。
* **同时发事件**：`retention.run`（`agent/observability/events.py::EV_RETENTION_RUN`，新增分组
  `GOVERNANCE_EVENT_TYPES`，**不改动** §3.6/P7.1-18/§6.6 三组冻结清单）。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `CP_RETENTION_ENABLED` | `false` | 是否注册调度任务 |
| `CP_RETENTION_DRY_RUN` | `true` | 非首跑是否只做 dry-run |
| `CP_RETENTION_DELETE_SOURCE` | `false` | **是否允许归档后删除源**（默认只归档不删除） |
| `CP_RETENTION_ARCHIVE_DIR` | `data/archive` | 归档根目录 |
| `CP_RETENTION_CLASSES` | 空（=全部） | 逗号分隔的类过滤 |
| `CP_RETENTION_DAY_OF_WEEK` / `_HOUR` / `_MINUTE` | `6` / `3` / `0` | 调度时刻 |

非法值一律**回退默认并 warn**（与 S7 各调度器同一口径），越界值夹紧。

## 七、指标口径可复算（防"篡改历史"）

归档若把读端看不见的数据搬走，指标就会变小 —— 那等于篡改历史。故本任务把
"**归档前后既有指标一致**"作为**归档方式是否合格的判据**：

| 受守护指标 | 事实源（**调用既有函数，不自建口径**） | 归档后是否可复算 |
|---|---|---|

**判据的机械形式**：任一类若"归档后指标无法复算"，则该类归档方式不合格，
必须改为「**保留聚合摘要 + 明细归档**」双轨。本任务实测三类指标归档前后**逐字段一致**
（对照表见 `TASK-S8-01_验收报告.md`）。
