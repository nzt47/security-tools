## 3. 裁定 #4：并发用例按意图修正

### 3.1 先查清：原用例"实测 5"的**真实机制**（不是产品丢数据）

读 `tests/unit/test_concurrency_multi_writer.py::_crash_worker`（L74-91）得到三件事：

1. **它通过 `out` 报告的是"已写完 5 条并显式 `chain._journal.flush()`"**（即只报了"进了预留日志"），
   随后死循环等父进程 kill；
2. **第 5 条落盘的时机**：`append()` 只把整条记录写进**预留日志**（`append_row` 内 `handle.flush()`，
   **非 fsync**）并入队，真正进 DB 由后台 writer 线程批量完成（`WRITER_POLL_INTERVAL=0.5s`）；
   原用例**没有任何 flush-to-DB 的确认点**；
3. **`entry.seq == 6` 的语义**：新进程构造时取 `max(DB 行, 预留日志末行)` 作链头
   （`chain.py:1254-1269`），日志末行是 5 ⇒ `_next_seq=6` ⇒ 续写从 6 开始。

隔离探针（`s1105_probe2.py` / `s1105_probe3.py`，进程外复刻该时序，**累计 58 轮**：
v2 的 10 轮 + v3 的 12/24/12 轮）得到一个**反直觉但决定性**的结论：

```
[A4] FAIL {"entry_seq": 6, "snap": {"flush_ok": true, "com": 5, "enq": 1, "inflight": [6],
          "db": [1,2,3,4,5], "db_head": 5}, "entries1": [1,2,3,4,5],
          "entries2_after_0.5s": [1,2,3,4,5,6], "db_after_0.5s": [1,2,3,4,5,6]}
[A6] FAIL {"entry_seq": 6, "snap": {"flush_ok": true, "com": 5, "enq": 1, "inflight": [6],
          "db": [1,2,3,4,5], "db_head": 5}, "entries1": [1,2,3,4,5], ...}
[A9] FAIL （同形态）
```

分批实测（**样本 <20 只披露不考核**，故按批列出）：v2 `N=10 → 1 FAIL`；v3 `N=12 → 2 FAIL`；
v3 `N=24 → 1 FAIL`；v3 `N=12 → 0 FAIL`。**合计 N=58，4 FAIL（6.9%）**，批次间波动 0–17% ⇒
这就是"冷跑才失败"的来源。失败时的不变量：

- 失败时**丢的那条是"幸存者自己"刚 append 的 seq 6**（`inflight=[6]`），**被杀进程的 5 条一条没丢**
  （`db` 恒含 1..5）；
- `flush()` 明明返回 `True` 却仍有在途：`flush` 的屏障是
  `_commit_count >= _enqueue_count`（`chain.py:2109-2118`），而
  **日志重放的 5 条提交把 `_commit_count` 顶到了 5，早于目标 1** ⇒ 屏障**被外来提交提前满足**；
- `entries()` 的"DB 查询"与"待入库合并（`_buffered_extra` → `_db_head()`）"是**两次不原子查询**
  （`chain.py:2262-2266` + `2268-2292`），writer 恰在两次之间提交时，该条就**漏在读快照外**；
- 0.5s 后 DB 收敛为 1..6 ⇒ **没有任何记录丢失**。

结论：原用例的 `len(rows) == 6` **实际要求了 `flush()` 的强屏障语义**，而它 docstring 只承诺
"持锁进程被杀不死锁 / 能续写"。这与裁定 #4 的定性一致（**断言比意图更严**），但**失败机理**与
"硬杀丢掉在途 1 条"**不同**——这一点必须写清，避免后人照着一个错误的因果去改产品。

### 3.2 修正后的用例（方案一：落盘确认 + 持锁）

`test_killed_process_does_not_deadlock_next_writer` 现在：

- 新增 worker `_crash_worker_committed_then_holds_lock`：写 5 条 → `flush(30s)` →
  **`_db_head() == 5` 复核已落盘** → `with chain._cp_lock.locked(...)` **持锁** → 才发信号 → 等硬杀；
- 父进程断言：`tag == "lock-held"`、`allocated == [1,2,3,4,5]`、`proc.exitcode != 0`、
  `entry.seq == 6`、**`seqs_in_db == [1,2,3,4,5,6]`（1..6 连续无空洞）**、
  `journal_replay_count == 0`（前提：5 条确已落盘）、
  **`seq_degraded_count == 0`（正向收紧：新写者真取到锁）**、`elapsed < 30s`。

**为什么选方案一而不是两段式**：裁定给的两段式是"无法在不改产品的前提下确认落盘"时的退路；
而 `AuditChain.flush()` + `_db_head()` **都已在产品里**（无新接口、无产品改动）⇒ 能确认落盘，
于是"在途不确定性"被彻底移除，断言可名正言顺要求总数 6（**且没有放宽任何断言**）。

**为什么额外让 worker 持锁**：docstring 承诺的是"**持锁**进程被杀不得死锁"，而 `append()` 返回时
锁早已释放；若只是"写+落盘后被杀"，用例只能证明"能续写"，**证明不了"锁随进程消亡自动释放"**。

### 3.3 新增的"已知语义"用例（记录"硬杀会丢在途"）

`test_hard_kill_loses_in_flight_records_that_never_reached_storage`：
worker 用 `auto_start_writer=False` + `journal_enabled=False` 造出**纯在途**（只在进程内队列，
既不在 DB 也不在日志）的 5 条 → 硬杀 → 新写者从 `seq=1` 起、库里只剩幸存者 1 条、`journal_replay_count == 0`。

把语义写成**可复核的两侧口径**：

| 情形 | 硬杀后是否丢 | 覆盖 |
|---|---|---|
| 已 `append()` 且**预留日志启用**（默认） | **不丢**：下次启动重放补齐（58 轮探针实测 1..5 恒在；0.5s 内收敛 1..6） | 本用例 docstring ① + 兄弟用例 `test_killed_process_records_recovered_from_journal` |
| **未落预留日志**的在途（日志未启用/写失败） | **丢**（永久） | **本用例（确定性）** |
| **整机掉电**（`fsync=False`，`chain.py:1565-1569`） | 最后若干条可能丢 | 无法确定性复现，**仅文档化** |

**为什么既不用 `xfail` 也不用"断言可能 < 6"**（任务允许二选一，此处给出选第三种的理由）：

1. `xfail` 的语义是"**应当被修掉的失败**"；而本语义已被 Owner 裁定为**可接受**，
   长期挂 xfail 会把正常语义留成"待修红灯"，反而**掩盖真回归**；
2. "断言可能 < 6" 是**不确定性断言**：在本用例口径下"丢"是**必然**，
   而一旦将来有人给队列加同步落盘，它会静默退化成"看运气通过" ⇒ 正是纪律禁止的**假绿**；
3. 故改为**确定性断言"丢"本身**（`rows == [1]`）+ 兄弟用例断言"已落日志的不丢"，
   两侧都是正向断言、口径可复核。
