## 1. 背景

v7.2（`CloudPivot_v7.2_final_合并归档(智谱审核版).md`，V7.0 基线 + 45 处补丁的冻结归档）是一份
**"目标系统级"理想架构图纸**：以"IDE 伴侣智能体"为宿主形态书写（§11.5 VS Code 扩展、
§11.1 node≥20/pnpm≥9/VSIX 生态、§0/§1.7 "云枢 = IDE 伴侣"、"不做独立 Web App"），
其护城河公式为 `ToolDescriptor × 消化状态机 × SkillFactory × Watchdog+Policy`。

云枢（Yunshu）现状是**数字生命体形态**：Python 3.12 服务（Flask/waitress，单机 Windows 开发 +
Linux Docker 生产）+ Web/Electron 工作台（yunshu-ui），并以 `skills_mgmt / workflow_learning /
process_distill / evolution(EVO) / self_healing / memory / knowledge` 等模块承载了 v7.2 多数机制的
**已落地或半落地实现**（证据见 01 号审计报告 §2.4 证据表）。

审计（01 号报告 §4 P1）确认：若把 v7.2 当作整包施工图纸直接照搬，将触发与自身 §13.4
"禁止整版重写"纪律相悖的**重写冲动**，且其宿主环境假设（node/pnpm/VSIX、独立 Web App 禁令）
与云枢形态直接冲突 → 产生"系统二象性 + 双维护 + 工程失控"风险。

本 RFC 是 S0-01 的第一交付物：裁定 **v7.2 与云枢的宿主/范围关系**，产出可追溯的架构决策，
使后续 S1–S6 的每个任务都有明确的"落地/降级"边界。

## 2. 目标（解决什么 / 不解决什么）

**解决：**

1. 明确 v7.2 在云枢重构中的身份：**机制/契约清单**（可吸收的规范化描述），而非独立产品图纸。
2. 逐章裁定 v7.2 的落地范围：哪些章节作为契约/机制吸收进云枢既有模块，哪些作为"参考形态"
   降级（暂不落地/入 Backlog），为 S1–S6 提供"照做清单"。
3. 给出裁决与审计结论（P1/P9/P3/T8）一致的落位：复用 skills_mgmt/workflow_learning/
   process_distill/EVO/self_healing 资产，只补契约与缺口。

**不解决（在后续任务解决）：**

- 具体契约字段设计（S1 ToolDescriptor v2.1）与消化对象三层映射（S0-02）。
- 数据/可观测基座（S2）、消化流水线统一（S3）、治理安全（S4）、记忆评测（S5）、UI 面板（S6）。
- digest 术语更名本身的**实施**（本 RFC 只确认更名方向，实施见 TASK-S0-01 步骤 4 与术语映射表）。

## 3. 方案对比

| 方案 | 说明 | 优势 | 劣势 | 成本 |
|---|---|---|---|---|
| **A. v7.2 作为机制/契约清单吸收进云枢（推荐）** | 云枢维持"Python 服务 + Web/Electron 工作台"宿主；把 v7.2 章节按"契约/机制"逐章映射到既有模块（skills_mgmt/process_distill/workflow_learning/EVO/self_healing），只补缺口；宿主相关章节（§11.5/§11.1/§1.7）降级为参考 | 与 01 号审计结论一致；复用既有资产避免系统二象性；术语/契约可追溯；符合 v7.2 §13.4 纪律；工作量最小、风险可控 | 需要显式的章节裁决清单（本 RFC）与术语纪律（术语映射表）防"消化/内化"语义漂移；部分机制（node 生态描述）需翻译为云枢等价物 | 低–中：裁决 + 映射 + 缺口补齐，增量演进 |
| **B. v7.2 作为独立 IDE 伴侣产品另起工程** | 按 v7.2 §11 起 node/pnpm/VSIX 工程，与云枢并行 | 文档"按图施工"最省翻译成本 | 重复造轮子（P9）：云枢已有同构实现；双代码库双维护；许可/数据不出域冲突（§10 合规与云枢 Local-First 冲突）；违背 v7.2 自身不变量#1"不搬代码只接协议"；直接违反审计结论 | 高：新工程 + 与云枢能力割裂 |
| **C. 渐进双形态：工作台为主、VS Code 插件入 P5 Backlog** | 云枢工作台为唯一宿主；保留"VS Code 扩展"作为远期（P5）评估项，不投入当前重构 | 为未来 IDE 触点留口子；避免过早承诺 | 当前无 IDE 触点真实需求（云枢用户经 Web/Electron 工作台）；VS Code 插件若提前做会分散 S0–S6 资源 | 中：插件需与 Python 服务定义清晰 IPC/契约 |

## 4. 推荐方案及理由

**推荐方案 A：v7.2 作为机制/契约清单吸收进云枢，宿主维持云枢工作台。**

理由（四条）：

1. **审计实证**（01 号报告 §2.4/§4/§6）：v7.2 的机制层与云枢已落地资产高度同构
   （SkillFactory↔skills_mgmt 评审评估、轨迹→Skill↔workflow_learning/process_distill、
   谱系↔EVO lineage、自愈↔self_healing、审批↔approval 等）；差距是**契约与量化门**而非**从零实现**。
   方案 B 将把差距重建成第二套系统（系统二象性），正是云枢历次审计反复禁止的。
2. **宿主一致性**：云枢的价值主张（记忆命中、更少打断、透明可控）与 v7.2 §1.2 同源，
   但承载宿主是"数字生命体 + 工作台"；v7.2 的 IDE 伴侣形态是其**目标产品的历史语境**，
   机制（契约/状态机/流水线/治理）可跨宿主迁移，工程章节（§11.5 VS Code 扩展）不可照搬。
3. **成本与风险**：方案 A 走"映射 + 补齐缺口"的增量路径，每一阶段只接线已建未用能力 +
   补一个契约缺口，可独立验收；方案 B/C 均引入新的双轨成本与维护面。
4. **纪律一致性**：方案 A 尊重 v7.2 §13.4（禁止整版重写）与其不变量#1（归一化优先、
   不搬代码只接协议）——云枢不在 node/VSIX 生态重新"搬"一套实现，而是把 v7.2 契约
   **接**到既有 Python 实现上。

## 8. 架构四问（v7.2 §13.1 必答）

1. **第一性身份？** v7.2 的第一性身份是"个人智能体的记忆/成本/治理护城河协议"，
   云枢的第一性身份是"数字生命体工作台"；两者同价值主张、异宿主。身份裁决：云枢是宿主，
   v7.2 是协议清单。
2. **是否触碰 §5.2 只读区？** 否——本 RFC 只裁定文档映射与术语，不触碰云枢 core/auth/
   audit/watchdog 只读区；S2/S4 涉及审计/治理时另行评估。
3. **commodity 还是差异化？** IDE 伴侣宿主（VS Code 扩展/node 生态）对云枢当前用户是
   commodity 触点（可永久借用社区 IDE 能力，不内化）；机制契约（ToolDescriptor/状态机/评测）
   是差异化（值得内化）→ 与"借来的必须变成自己的"不变量一致。
4. **上游是工具还是同事？** v7.2 文档是把"Claude/Trae/DSH 等上游"当**工具**（探针/契约/黑盒
   萃取）；云枢同样把外部 IDE/Agent 当工具层接协议，集中式语义（云枢为唯一宿主决策中枢）成立。
