### 1.3 为什么必须补"装配点"（对交接清单的必要偏离，已声明）

**交接文档 §2.2 的期待是**："纯倒置后给出'服务/测试运行期该层确已被导入'的证据"。
**实测否证**：全仓 `grep config_observability` 只有 3 处命中——模块自身 docstring、
`observability_config.py:668`（被删的那行）、以及 `tests/unit/test_tracing_config_delegation.py:75`
（monkeypatch 字符串目标）。**`config_observability` 在 production 代码里唯一的 importer 就是被删掉的那一行。**

⇒ 纯倒置的后果**不是"留痕时机变化"，而是"配置变更可观测性整条链变成死代码"**
（Loki 推送 / `config_changes_total` 指标 / 高风险告警都不会再触发）。

故补一个装配点，并选择**能给出结构性保证**的位置：`agent/monitoring/__init__.py` 末尾。
理由：任何使用 `ObservabilityConfig` 的代码都必须先 `import agent.monitoring.observability_config`，
而导入任何子模块都**必然先执行包 `__init__`** ⇒ 注册必定早于第一次 `set()`（是机制保证，不是"恰好也被导入"）。

- 图模拟先验证装配边不成环：`sim_wiring.txt`（对 8 个候选装配点逐一模拟，全部 `OK 无环`）。
- 位置必须在 `__getattr__`/`__all__` **之后**，否则加载链中任何
  `from agent.monitoring import X` 都会命中尚未定义 `__getattr__` 的半初始化包（已写入代码注释）。
- 装配点必须用**绝对子模块导入**：写成 `from agent.monitoring import config_observability` 时，
  解析器按 `node.module` 记为 **self 边** `agent.monitoring → agent.monitoring`，DFS 判为 1 节点自环
  （实测错写即得 `total=1 / active=1`，`arch_step1.json`）。

### 1.7 行为影响面（逐条显式声明，不隐藏）

### 2.3 根因 B：`SystemRoot` 是**仅 Windows 存在**的环境变量（Shard 1 的 1 个 ERROR + Shard 2 的 6 个 ERROR）

同一根因、两种症状：

**修法**：抽公共实现 `tests/unit/repair_fixtures.py::outside_repo_tempdir()`（消掉重复实现，
符合本仓"夹具集中一处"的既有约定）：

> 候选基址（系统临时目录——**先临时摘掉 pytest 对 `tempfile.tempdir` 的改写**以恢复
> `TMPDIR`/系统默认裁决 → `SystemRoot\Temp` → `/tmp` → `TMPDIR/TEMP/TMP`）
> → 逐个用**被测代码自己的** `gitio.is_git_repo` 校验确不在 git 仓库内
> → `mkdtemp` → 对结果复核 → **统一返回绝对路径**；
> 无可用基址时显式 `AssertionError`（**不**退化成"仓库内目录"让用例静默测错路径）。

用"被测代码自己的判据"是为了避免"夹具认为不在仓库内、被测代码认为在"的口径漂移。

**本地对照臂**：`SKILLS_OFFLINE` 无关；该缺陷需要 Linux。故用 **WSL(Ubuntu-24.04 / Python 3.12.3，
与 CI 同为 Linux + 3.12)** 在**真实 Linux** 上跑新实现（`verify_fixture_linux.py`）：

```
platform            : linux
SystemRoot (应为空) : None
OLD dir=None 落到     : <repo>/.pytest_tmp/cp-repair-outside-g31ej5g0     ← 旧写法落到仓库内
NEW helper 返回      : /tmp/cp-repair-outside-12jyojzq                   ← 绝对路径、不在仓库内
VERDICT: FIXED-ON-LINUX
```

> **诚实标注**：WSL 里 `is_git_repo` 对任何 `/mnt/c` 路径都返回 `False`
> （WSL 下 git 对 Windows 挂载点报 dubious ownership），故探针中"旧写法 `is_git_repo` 结果"
> 一列**不具判定力**；"旧写法在 Linux 上确实落到仓库内"这一条**以 CI 原始日志为准**
> （见上）。新写法的判定依据是"返回绝对路径且路径不在仓库树下"，不依赖 git 可用性。

#### 2.7.1 Shard 4 根因与修法（**已修并经真实 CI 验证**）：扫描成本 × 全局 `--timeout=60` → 级联超时

- `tests/unit/test_date_shift_blindspots_guard.py` 的守卫要对 `tests/` 全树做 AST 扫描
  （`scan_all()`，按 root 缓存，代码注释自述"首版无缓存时 `--scan` 120s 都跑不完"）。
- **本机实测**（`guard_timing_local.txt`，`--durations=8`）：**首个用例
  `test_no_import_time_clock_constants` 耗时 16.77s**（整次全量扫描的成本全压在这一个用例上），
  其余用例命中缓存后为亚秒级；整个文件 20 passed / 30.00s。
- CI 的 pytest 参数为 `-n 2 --dist=loadscope --timeout=60`（见 `ci.yml`），
  4 核 runner 上同 shard 还有 ~3100 个用例 ⇒ 该 CPU 密集扫描**突破 60s**。
  一旦首次扫描超时，**扫描结果没能写进缓存**；`--dist=loadscope` 使同模块用例同处一个 worker，
  worker 被超时终结重启后下一条守卫用例又成为"首个"、再次全量扫描、再次超时
  ⇒ **7 条级联超时**，并波及同 worker 的 `TestServiceMerge::test_service_auto_merge_duplicates`。
  这也解释了"时红时绿"：载轻时首次扫描 <60s，其余全部命中缓存 ⇒ 绿。

**修法（`319a25e7`，不是放宽超时）**：在模块导入期（pytest **收集期**）调用一次 `scan_all()` ——
收集不在 `--timeout=60` 的计时窗口内，级联的触发条件随之消失。
`git diff` = **24 行纯新增注释 + 1 行 `scan_all()`**；**断言、检测器、扫描范围、授权清单一字未改**。
