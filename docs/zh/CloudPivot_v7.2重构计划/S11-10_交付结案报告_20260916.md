### 1.3 为什么必须补"装配点"（对交接清单的必要偏离，已声明）

**交接文档 §2.2 的期待是**："纯倒置后给出'服务/测试运行期该层确已被导入'的证据"。
**实测否证**：全仓 `grep config_observability` 只有 3 处命中——模块自身 docstring、
`observability_config.py:668`（被删的那行）、以及 `tests/unit/test_tracing_config_delegation.py:75`
（monkeypatch 字符串目标）。**`config_observability` 在 production 代码里唯一的 importer 就是被删掉的那一行。**

⇒ 纯倒置的后果**不是"留痕时机变化"，而是"配置变更可观测性整条链变成死代码"**
（Loki 推送 / `config_changes_total` 指标 / 高风险告警都不会再触发）。

故补一个装配点，并选择**能给出结构性保证**的位置：`agent/monitoring/__init__.py` 末尾。
理由：任何使用 `ObservabilityConfig` 的代码都必须先 `import agent.monitoring.observability_config`，
而导入任何子模块都**必然先执行包 `__init__`** ⇒ 注册必定早于第一次 `set()`（是机制保证，不是"恰好也被导入"）。

- 图模拟先验证装配边不成环：`sim_wiring.txt`（对 8 个候选装配点逐一模拟，全部 `OK 无环`）。
- 位置必须在 `__getattr__`/`__all__` **之后**，否则加载链中任何
  `from agent.monitoring import X` 都会命中尚未定义 `__getattr__` 的半初始化包（已写入代码注释）。
- 装配点必须用**绝对子模块导入**：写成 `from agent.monitoring import config_observability` 时，
  解析器按 `node.module` 记为 **self 边** `agent.monitoring → agent.monitoring`，DFS 判为 1 节点自环
  （实测错写即得 `total=1 / active=1`，`arch_step1.json`）。

#### Shard 4 根因（已量化）：全仓 AST 扫描成本 × 全局 `--timeout=60`，超时后级联

- `tests/unit/test_date_shift_blindspots_guard.py` 的守卫要对 `tests/` 全树做 AST 扫描
  （`scan_all()`，按 root 缓存，代码注释自述"首版无缓存时 `--scan` 120s 都跑不完"）。
- **本机实测**（`guard_timing_local.txt`，`--durations=8`）：**首个用例
  `test_no_import_time_clock_constants` 耗时 16.77s**（它承担整次全量扫描），
  其余用例命中缓存后为亚秒级；整个文件 20 passed / 30.00s。
- 在 4 核 CI runner 上以 `-n 2` 跑同一 shard（该 shard 还有 ~3100 个用例），
  这 16.77s 的 CPU 密集扫描**很容易突破 pytest 全局 `--timeout=60`**。
- 一旦首次扫描超时，**扫描结果没能写进缓存**；xdist 在 worker 被超时终结后重启 worker，
  下一个守卫用例又成为"首个"、再次全量扫描、再次超时 ⇒ **7 条守卫用例级联超时**，
  并波及同一 worker 的 `TestServiceMerge::test_service_auto_merge_duplicates`。
  这与"7 条全是守卫 + 1 条同 worker 用例超时"的形态完全吻合，也解释了"时红时绿"
  （载轻时首次扫描 <60s，全部命中缓存 ⇒ 绿）。

**建议（未实施，需一次 CI 迭代验证）**：把全量扫描**预热到收集期**（模块级
`scan_all()` 或等价机制）——收集期不在 `--timeout=60` 的计时窗口内，超时级联即消失，
且**断言、扫描范围、覆盖率一字不改**。替代方案（降级）是给该文件单独放宽超时，
但那会弱化这条守卫，不建议。

#### Shard 5 根因（已定位）：断言强于模块自身文档化的降级契约

- `agent/utils/native_preimport.py` 的 `NATIVE_IMPORT_ORDER = ("numpy","pyarrow","pandas","sklearn")`，
  其存在意义是规避 **Windows** 上 pyarrow 原生初始化过晚导致的 `0xC0000005` 崩溃。
- 该模块**明确把"环境缺件"当作合法降级路径**：`except Exception as _e:  # pragma: no cover - 仅环境缺件时走到`
  → 记 `failed:<原因>` 并 `logger.warning("…（降级，不阻断启动/收集）")`。
- `tests/unit/test_native_preimport.py` 的两条用例把它当**硬契约**：
  · `test_protection_already_applied_in_this_process`：对**每个**模块断言
    `not recorded[name].startswith("failed")` —— 而该用例**自己的 docstring 写的是**
    "**不得全部为 failed**（那说明环境缺件，属另一类问题）"⇒ **实现比其自述口径更严**；
  · `test_default_is_enabled_and_imports_the_stack`：子进程探测断言 `pyarrow_loaded == "True"`。
- 而 **pyarrow 在本仓任何依赖清单里都没有声明**（已对全部 `requirements*.txt` /
  `pyproject.toml` / `setup.py` / `setup.cfg` / `constraints*.txt` 递归 grep，**0 命中**），
  CI 只做 `pip install -e .` + pytest 插件 ⇒ **CI 上必然没有 pyarrow**（本机恰好装了 24.0.0，
  所以本地全绿）。Linux 上 pyarrow 既不参与该 Windows 崩溃路径、pandas/sklearn 也不要求它。

**建议（未实施，属语义决策，留给 Owner）**，二选一：
1. **声明/安装 pyarrow**（进依赖清单或 CI 安装步骤）——若认为该原生栈契约必须成立，这是"补齐环境"；
   代价：所有 shard 多装一个较重的 wheel。
2. **把断言对齐到它自己文档化的口径**（"不得全部 failed"）——承认 Linux 上 pyarrow 缺失属合法降级；
   代价：这是一次**断言放宽**，必须由 Owner 明确批准，本会话**不擅自实施**。

> **为什么这两条不在本会话硬改**：按本任务红线"改不到就如实上报并保持红，宁可留真实红灯，
> 不留假绿灯"——①Shard 5 的修法涉及"放宽断言"或"改 CI 依赖"两类需要 Owner 决策的变更；
> ②Shard 4 的修法需要在真实 CI 上迭代验证（本机无法复现 4 核 `-n 2` 的负载），
> 单次盲改有引入新 churn 的风险。两者均**已证为存量**（失败集合与会话前逐字相同），
> 不影响本批次"不得引入新失败"的判据。
