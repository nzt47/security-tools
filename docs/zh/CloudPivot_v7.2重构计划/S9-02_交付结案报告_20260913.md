### 1.4 为让它真跑通而修掉的 4 个缺陷（代码行级）

#### 缺陷 A：工厂不认 `deepseek` ⇒ 真实 judge 永远"未构造出适配器"

* 位置：`agent/model_router/adapters.py::ModelAdapterFactory.create`
* 现象：`judge_runtime.PROVIDER_CREDENTIAL_ENVS` 早已把 `deepseek` 当**一等 provider**
  （`PROVIDER_CREDENTIAL_ENVS["deepseek"] = ("DEEPSEEK_API_KEY",)`），但工厂只认
  `openai|claude|gemini|zhipu|qwen` ⇒ 返回 `None` ⇒ `LLMJudge._resolve_invoke` 抛
  `JudgeUnavailable("未能构造模型适配器")`。**"有凭证即用"是纸面承诺。**
* 修复：新增 `OPENAI_COMPATIBLE_BASE_URLS`（OpenAI 兼容端点表）+ 一个 `elif` 分支，
  复刻 `openai` 分支行为；`deepseek` 缺省端点 `https://api.deepseek.com/v1`，
  显式 `base_url` 优先。**既有分支行为零变更**。
* 影响面核实：全仓 `ModelAdapterFactory` 的**生产调用点只有 `LLMJudge` 一处**
  （其余为测试），故新增分支不改变任何既有路径。

#### 缺陷 B：`_adapter_kwargs()` 丢掉了端点 ⇒ 兼容端点会打错主机

* 位置：`agent/digestion/shadow.py::LLMJudge._adapter_kwargs`
* 现象：此前只透传 `api_key`。端点解析出来了却不传下去，请求会落到 SDK 缺省
  （`api.openai.com`）——那不是"回落"，是**打错地方**。
* 修复：`LLMJudge` 增加 `base_url`（构造参数 + 私有字段 + `_adapter_kwargs` 透传）；
  `judge_runtime.JudgeConfig` 增加 `base_url`，来源**复用部署级 `LLM_BASE_URL`**
  （`shadow.JUDGE_BASE_URL_ENV`，**未新造同名开关**，故 `settings/registry.py` **无需新增登记**；
  该键早已登记为 `_c` 只读脱敏）；`JudgeAvailability`/自检输出新增 `base_url`（非密钥，可复盘）。
  旧路径 `shadow.resolve_judge` 也一并对齐。

#### 缺陷 C：`success=True` + 空 `content` 被判成 **0.95 → 通过**（假绿门）

* 位置：`agent/digestion/shadow.py::_extract_reply`
* 现象（**实测复现**）：`deepseek-v4-flash` 是推理型模型，token 预算先花在
  `reasoning_content` 上；`finish_reason="length"` 时可见 `content` 为**空串**而
  `success` 仍为 `True`。旧代码走过文本键循环后落到 `json.dumps(out)`，
  而那份 JSON 里第一个数字是 `"prompt_tokens": 95` ⇒ `_ANY_SCORE` 读成 **95 → 0.95**
  ⇒ **`verdict=pass`，`kind=llm_judge`**。
* 这是 S8-04 堵过的那个洞（`success=False` 时 429 → 1.0）的**另一扇门**：
  通道截断被伪装成"语义等价"，**负例消失**。
* 修复前实测（stash 回原代码后跑的原始输出，用作反证）：

```
PRE-FIX result: {"score": 0.95, "verdict": "pass", "confidence": 0.95, "kind": "llm_judge"}
threshold: 0.85 => pass? True
```

* 修复：文本键**存在但为空** ⇒ 抛 `JudgeUnavailable`（如实回落，不猜分数），
  与既有"失败回复不算回复"同一口径。同时让 `OpenAIAdapter.generate/chat` 透出
  `finish_reason`，使"成功但无内容"在生产日志里**可诊断**（否则只看到一句"模型没回复"）。

#### 缺陷 D：预算护栏**读写两本不同的账** ⇒ 护栏永久失聪

* 位置：`agent/digestion/judge_runtime.py::JudgeBudgetGuard.record / _writer_store`
* 现象：`spent()` 按参数 `events_dir` 读当日 judge 栏，而 `record()` 把
  `store=self._store`（默认 `None`）交给 `utc.record_cost` ⇒ 落到**全局默认**事件目录
  （`CP_EVENTS_DIR`/`data/events`）。只给 `events_dir` 而不给 `store` 时，
  **读写指向两本不同的账** ⇒ `spent_cents` 恒为 0 ⇒ **每日预算永远不会触发**
  （"超预算即回落"沦为纸面条款），同时花销被记到另一个目录。
* 修复：新增 `_writer_store()` —— 显式 `store` 最优先（不夺走注入权）；
  否则若给了 `events_dir`，写侧用 `EventStore(path=active_events_path(events_dir))`
  **显式绑到同目录**（惰性一次 + 缓存）；两者都没有时同走全局默认（天然一致）。
* 反证：把 `store=self._writer_store()` 还原成 `store=self._store` 后，新增回归用例
  **2 failed**（`spent=0`）；改回后 **4 passed** ⇒ 修复是**承重**的，不是装饰。

> 说明：W1 首轮实跑得到 `utc_delta_cents=0.0`。**首要原因是我的验证脚本绕过了
> `JudgeGuard.__call__` 直接调 `runtime.judge.score()`**，而 `_on_call()`
> （⇒ `budget.record()` ⇒ `record_cost`）是挂在 Guard 上的。这是**测法错误**，
> 已修正为走真实集成路径 `runtime.guard(...)`。排查过程中才发现了缺陷 D。

### 1.5 新发现缺陷（**未修改，按纪律留档立项**）：`verdict` 口径在"different + 高置信"下反向

见 §1.3 表第 2 行。原始模型输出：

```
reason: "上游是读取文件并写报告，候选是删除生产数据库并群发邮件，步骤和副作用完全不同。"
model_verdict = fail        ← 模型明确说"不同"
confidence    = 1.0
verdict       = pass        ← 但代码判成"通过"
```

**根因（代码行级）**：`shadow.parse_judge_verdict` 按 §4.5 逐字口径
`confidence >= 0.85 ⇒ pass`，把 `confidence` 当作**相似度**用；但 `_JUDGE_STRUCTURED_PROMPT`
问的是"结论与**置信度**"——即对该结论的把握。`verdict=different` + `confidence=1.0`
（"我 100% 确定它们不同"）因此被映射成 `pass`，**语义反了**。
后果：层③ 会把"完全不同的执行"记成"无回归"，**负例消失** —— 与该功能
（检测行为漂移）的目的直接冲突。

**为何本次不擅自修**：该口径是 §4.5 的**逐字规格**，且代码已**如实披露**
（`model_verdict=fail`、`conflict=True`，未静默改写模型结论），属于
"已披露的规格选择"而非静默 bug。改它会变更 S3-03/S8-04 多处的阈值语义与断言，
超出"收尾批次"范围。**建议单独立项**（建议口径：以 `model_verdict` 为主判据，
`confidence` 仅在其缺失时兜底；或明确区分 `similarity` 与 `confidence` 两个字段）。

**可能的缓解**：下游消费 `verdict` 时应同时检查 `conflict`；本次已确认
`conflict`/`model_verdict` **确实**被透出（未被吞掉）。

### 2.3 `tests/e2e`：8 个 setup ERROR 是环境，且**测试代码**本身健全

**无服务时**（首轮）：30 passed + **8 ERROR**，8 条全是 setup 期的

**根因（代码行级 + 实测）**：`tests/e2e/conftest.py` 在没有现成服务时会自己拉起

本环境**访问不了 huggingface.co**，5 次指数退避重试累计 >2 分钟 ⇒ 必然超过 conftest 的 120s 预算。
**决定性验证**：模型其实**已在本地 HF 缓存**（`~/.cache/huggingface/hub/models--sentence-transformers--paraphrase-multilingual-MiniLM-L12-v2`），

```

======================= 38 passed in 128.07s (0:02:08) =======================
```

**归类：③ 依赖外部环境（网络 / 真实 HEAD）**。结论：**e2e 用例 38/38 全过**，
那 8 个 ERROR 是"环境缺服务 + 启动依赖外网"导致，**不是用例缺陷**。

> `stdout/stderr` 接进 PIPE 却**从不读取**，超时时也不 dump ⇒ 服务为什么起不来
> （上述 HF 超时）在报错里**完全看不见**。这正是本次排查一开始拿不到根因的原因。

### 2.5 顺带修掉的 1 个真失败：`tests/integration/test_audit_trace.py` 的 teardown

**现象（每次运行必现 2 个 ERROR，隔离复跑同样出现 ⇒ 不是抖动）**：

```
2 passed, 2 errors
ERROR at teardown of ...: PermissionError: [WinError 32] 另一个程序正在使用此文件...: './test_audit_integration\\audit_chain.db'
```

**根因（代码行级）**：原文件 `setup_method` 用**仓库根相对路径** `./test_audit_integration`
（`test_audit_trace.py:16`），`teardown_method` 直接 `shutil.rmtree`（`:52`），
**没有先释放** `AuditLogger` 持有的链式轨写者。两个后果：
① 每次跑完都在工作区留下 `audit_chain.db` / `.lock` / `.seqjournal`
（**且未被 .gitignore 覆盖** ⇒ 进入 `git status` 的"产物漂移"）；
② Windows 下 sqlite 仍被占用 ⇒ 每条用例多报一个 teardown ERROR（断言其实是通过的，
于是极易被当成"抖动"忽略 —— 这正是本次差点误判的地方）。

**修法**：改用系统临时目录；teardown 先 `flush()` + `close()` 再删。
**验证**：`2 passed`（0 error），且删除目录后重跑**不再重新生成** `test_audit_integration/`。

**未彻底修掉、如实留档**：`AuditChain.close()` 会 flush + 停 writer + 释放单写者登记，
但**不释放** `<db>.lock` 的跨进程锁文件句柄 ⇒ close 之后该文件仍删不掉。
故 teardown **精确地只容忍 `*.lock`**：其它任何文件删不掉都继续抛错
（真正的句柄泄漏**不许**被这处掩盖），并对残留锁文件打 `warning` 留痕。
产品侧缺口另立遗留项（§2.6）。
