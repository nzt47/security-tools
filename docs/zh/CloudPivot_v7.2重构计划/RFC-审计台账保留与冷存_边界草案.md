## 零、P0 前置：现存台账**未通过验签**（实测，阻断本任务开工）

在撰写本草案前的现状核验中，对**主工作区**默认台账做了只读诊断，结论如下。

### 0.1 实测事实

| 项 | 实测值 |
|---|---|
| 库 | `data/audit/audit_chain.db`，12,500,992 bytes |
| 记录数 | 15,895（`seq` 1..15895） |
| 结构性完整性 | `seq` **连续**（无缺口）、**重复 seq 0**、**不同 self_hash 15,895**（无重复） |
| 验签结论 | `python scripts/verify_audit_chain.py --stats` → **TAMPERED**，首个异常 `seq=17`，`reason=prev_hash_mismatch`，异常条数 9980（前向传播所致） |
| 断链处数 | **20**（18 个 seq 区间：`[17,17] [29,30] [45,46] [54,54] [56,56] [72,72] [612,612] [7692,7692] … [11418,11418]`） |
| 断链形态 | **悬空前驱 20 / 回跳 0 / 其他 0** —— 即 20 条的 `prev_hash` 指向的 `self_hash` **在整个库中不存在** |
| 悬空前驱是否在旧 JSONL 轨 | **均不存在**（5 个样本逐个检索 `data/audit/audit_2026091{0,1}.jsonl`；旧轨不携带 `self_hash` 字段） |
| 时间分布 | 2026-09-10（12,393）/ 2026-09-11（3,502）；**无 2026-09-12 记录** |
| 每日根封存 | `data/audit/daily_roots.jsonl` **不存在**；`--stats` 报 `每日根=0 封存=False`，签章方案 `sha256-self` |
| 时间戳倒置 | `seq=29` ts 12:21:08.246 而 `seq=30` ts 12:21:05.843；`seq=45` 12:21:10.127 而 `seq=46` 12:21:08.677 |

复现命令（**只读**，以 `mode=ro` 打开 SQLite，不 import `agent.audit`、不建库、不启写者线程）：

```powershell
python scripts/audit_chain_link_diag.py            # 形态学诊断（本次新增）
python scripts/verify_audit_chain.py --stats       # 汇总验签（S2-02 既有）
```

### 0.2 形态学结论（据上表事实，非定论）

- **不是"记录被事后篡改"**：若有插/删/改，必留下 `seq` 缺口或重复、或 `self_hash` 重复；实测三者皆无。
- **是"前驱记录缺失"**：20 条记录的 `prev_hash` 指向的自 hash 在链库与旧轨中**都不存在**。
- 结合 `seq` 连续 + 时间戳与 seq 序倒置，**最可能的成因是跨进程并发写者交错**
  （每条记录的时间戳由调用方在**进入写锁之前**生成，故 seq 分配序与 ts 序可以不一致）。
  关键缺口：S2-02 的「单写者纪律」(`SingleWriterViolationError`) 由**进程内**登记表
  `_WRITER_REGISTRY` 保证 —— **不覆盖跨进程**；而 `data/audit/audit_chain.db` 是多个进程
  （常驻服务 + 并行会话 + 测试运行）默认共享的路径。
- 上述含"最可能"的判断属推断；**需 S2-02 owner 复核当时是否存在并发进程/演练脚本写入**。

### 0.3 为什么它阻断本任务

分层/冷存的前提是「链可验签」。在一条**当前不通过验签**的链上设计保留策略，等于把不确定
性固化进新结构，并使"冷存后仍可验签"这一核心验收项失去意义。

### 0.4 三条处置候选（**不得就地改写**；本草案不单方决策）

> 为什么"不得就地改写"：`actor` / `subject` 同时参与 `payload_hash`（覆盖整条规范化记录）与
> `self_hash`；改写任一条会破坏其后**全部**记录、已封存日根与 ed25519 签名，且
> `agent/audit/migration.py` 已将该纪律固化为常量（`deleted = 0  # 恒为 0：不删除（显式留证）`、
> `retraced = 0  # 恒为 0：不追溯（不导入链）`）。

| 候选 | 做法 | 代价 | 建议 |
|---|---|---|---|
| **A. 现场固化留证** | 现库 + 诊断报告整体**只读归档**（复用 `migration` 的只读归档机制），不修不改；新台账显式记录一条"前序链存在 20 处已知悬空前驱"的审计事件 | 历史区间**永久不可验签**（如实声明） | **推荐**：与项目"不删除不追溯、显式留证"纪律一致 |
| B. 已知断点白名单 | 把 20 处登记为既有断点，验签工具支持 `--known-breaks`，使**新增**记录可独立验签 | 需接受"历史不可验证"且白名单本身成为可被滥用的口子 | 可作 A 的补充，不宜单独使用 |
| C. 重建链 | 以现链内容重建一条自洽链 | **与 append-only / 不追溯纪律直接冲突**；"重建"无法证明重建前的内容 | **不推荐**（除非 Owner 判定历史价值低于一致性成本，且必须留证） |

**建议下一步（低成本）**：由 S2-02 owner 用 §0.1 命令复核形态；同时排查**跨进程单写者缺口**
（是否有第二进程写同一默认路径），再在 A/B 间裁定。

## 一、问题陈述

1. **只增不减**：链式台账无 TTL、无冷存、无容量治理。实测 2 天重度测试流量即产生 15,895 条 / 12.5 MB
   （≈786 B/条）；长期运行的增速需真实流量基线，本草案不臆测。
2. **契约要求**：§8 要求 **D4 审计 RPO≈0 / RTO≤5min**、**审计永久（365 天转冷 + 匿名化）**，
   §3.5 要求「每日 Merkle 根 → 外部只追加存储」，P7.2-24 要求 Ledger 三级查询预算
   （聚合 <200ms / 明细分页 <1s / 单条详情 <500ms）。
3. **当前真空**：每日根**从未封存**（`daily_roots.jsonl` 不存在），签章停留在 `sha256-self` 降级态 ——
   即 §11.10「验签每月」目前**无物可验**。
4. **风险登记**：R12「审计日志被篡改（高，对策=链式哈希 + Merkle + 外部追加）」的"外部追加"一环未落地。

## 二、硬约束（不可越线）

1. **append-only 与两级哈希**：禁止就地改写既有记录（见 §0.4 引文）。
2. **单写者纪律**：保持 `SingleWriterViolationError` / `ReadOnlyChainError` 语义；
   **若本任务顺带补齐跨进程单写者**（§0.2 缺口），须作为独立子项并单独验证。
3. **任一历史区间可独立验签**：不得引入"必须从创世读起才能验"的设计。
4. **审计平权（P7.2-24）**：冷存不得造成"UI 操作在查询面消失"。
5. **删除权语义（S5-01 §8）**：删的是**记忆**不是证据。冷存**不得**成为"绕过遗忘"的后门 ——
   审计链内本就不存记忆内容（只存 `content_hash`），但冷存设计须保持这一性质。
6. **项目树卫生（P7.2-18）**：冷存/归档目录不得位于项目树或 `.cp/` 内。
7. **best-effort 不阻断主路径**：冷存失败不得让审计写入失败（现状 `AuditFacade.record` 已是 best-effort，须保持）。

## 三、边界

**做（in-scope）**
- 热→冷**分层**与搬迁；冷段**只读封存**（复用既有 `_set_readonly` / `is_readonly`）。
- **每日 Merkle 根**的实际封存与 ed25519 签章（当前 `RootsSigner` 已具备能力，仅未启用/未封存）。
- 跨层**验签锚点**（局部锚点重算）与逐条**包含证明**。
- 容量/延迟**预算与回归**；每月验签 + 断链诊断的**演练流程**。
- §3.5「外部只追加存储」的**最小形态**。

**不做（out-of-scope）**
- 篡改检测机制本身（S2-02 已交付：两级哈希 + Merkle + `verify_chain`）。
- 哈希/Merkle/签名**算法变更**（会破坏既有链）。
- 审计面板/UI（属 S6-01）。
- **记忆**删除与遗忘（属 S5-01，已完成）。
- 轨迹 90 天过期（属 S2-01/Trace 轨，与台账不同库不同生命周期）。
- **修复 §0 的断链**（属独立裁定，见 §0.4）。

**反目标（明确放弃）**
- "更聪明的压缩"（无损压缩收益有限，且引入解压依赖）。
- 把冷数据搬回热库的"自动回暖"（徒增写路径与风险）。
- 以删除换容量 —— **审计永久的契约优先于磁盘**。

## 四、候选设计

| | A. 分段 SQLite | B. 按日 JSONL + 只读封存 | C. 仅就地只读 + 容量告警 |
|---|---|---|---|
| 形态 | 热库保留最近 N 天；更早按段落 `audit_chain_seg_<start>_<end>.db`（只读） | 冷段导出为按日 JSONL（复用 `migration` 归档机制） | 不搬迁，只把旧库只读 + 超阈值告警 |
| 验签 | **最佳**：直接复用 `verify_chain(anchor_seq=段首, anchor_prev_hash=段首前驱)` 局部锚点重算 | 需把 JSONL 重新装配为 `AuditEntry` 再锚定验签 | 无变化（但容量问题不解决） |
| 查询 | 热库变小 ⇒ 四类查询更优；冷点需"哪段"路由 | 冷点只能顺序扫（明细分页/单条详情可能超预算） | 与现状同 |
| 实现成本 | 中（段切分 + 路由 + 只读封存） | 中低（复用归档件多） | **低** |
| 主要风险 | 段边界断链若处理不当 ⇒ 新的"悬空前驱" | 装配/编码往返丢字段；大文件内存压力 | 只把风险推后 |
| 可回滚 | 高（段文件即原库副本） | 中（JSONL→库需再迁移） | 高 |
| 建议 | **主方案** | 冷点的检索辅助格式（与 A 并存，非替代） | 仅作过渡/降级路径 |

> 两者可组合：**A 为主（保验签与检索）**，B 作为冷段的**人读/长期保存副本**。

## 五、验收标准（草案，可测）

1. **冷段独立验签**：`verify_chain(seg_entries, anchor_seq=段首 seq, anchor_prev_hash=段首 prev_hash)` → `ok=True`。
2. **整链仍可验签**：热+冷串联（跨段 `prev_hash` 连续）后，全链验签 `ok=True`。
3. **包含证明**：任一冷记录可经 `merkle_proof` 对其所属**已封存日根**出证明，`verify_merkle_proof` 通过。
4. **每日根封存生效**：`daily_merkle_root()` 产出且 `verify_daily_root()` 通过；`daily_roots.jsonl` 存在且链式自洽（`roots` 自身外层哈希链连续）。
5. **查询预算不退化**：聚合 <200ms / 明细分页 <1s / 单条详情 <500ms（P7.2-24），冷存前后**实测对比**。
6. **目录合规**：冷存根在项目树外且 `is_readonly()` 为真。
7. **失败注入不阻断**：冷存写失败时主路径审计写入仍成功，且失败计数/告警可见（best-effort 证据）。
8. **演练可复现**：月度验签 + §11.10 篡改演练（人为改一条冷记录）能被 `verify_chain` 定位，且
   `scripts/audit_chain_link_diag.py` 给出正确形态（悬空前驱/回跳/结构性损坏三类可区分）。
9. **§八 裁定路径的实施证据**（取决于 §九 R1 的选择）。

- `AuditFacade.record` 仍是**唯一**写入口；`audit` 单例与 `reset_audit_facade()` 语义不变。
- `AuditChain`：`append` / `entries` / `iter_entries` / `get` / `count` / `chain_head` / `stats` /
  `verify_chain` / `verify_daily_root` / `daily_merkle_root` / `verify_daily_roots_all` / `clear`（测试专用）。
- `verify_chain(entries, *, anchor_seq, anchor_prev_hash, expect_first_seq)` 的**锚点语义**不变。
- `scripts/verify_audit_chain.py` 退出码 **0 完整 / 1 检出篡改 / 2 用法或 IO 错误**（CI 依赖）。

## 八、§8「365 天转冷 + 匿名化」的口径风险（**需 Owner 裁定**）

**结构性事实**：`self_hash = sha256(seq|ts|actor|action|subject|payload_hash|prev_hash)`，且
`payload_hash` 覆盖**整条**规范化记录（含 `actor` / `subject` / `payload`）。因此
**"到 365 天就把既有记录匿名化"在结构上不可能**——任何就地改写都会破坏该条及其后全部
`self_hash`，并连带使已封存日根与 ed25519 签名失配（此即 §0.4 引文所固化的纪律）。

三条合规路径：

| 路径 | 做法 | 代价 / 边界 |
|---|---|---|
| **(i) 写入即伪名 + 到期销毁密钥** | 所有审计写入方在**写时**只落伪名（S5-01 的 `SubjectPseudonymizer` 模式），到期 `shred` 盐即达成不可关联 | **推荐**；对**既有** 15,895 条无效（其 `actor` 多为 `agent`/`system` 等非自然人标识，如实声明） |
| (ii) 冷存层有损投影 | 冷介质只保留 `seq/ts/action/payload_hash/self_hash/prev_hash`，去掉 `actor`/`subject`/`payload` 原文；链本身不动，冷点匿名性由**访问面**保证 | 冷点 `actor`/`subject` **永久不可再查**（审计可用性下降）；需 Owner 认可 |
| (iii) 只转冷、不声称匿名化 | 如实标注 §8 该条**当前未实现**并列入遗留 | 最诚实、成本最低；但不满足 §8 字面 |

**建议**：(i) + (iii) 组合 —— 写入侧一次性收敛到伪名（未来记录天然匿名友好），对**既有**
记录如实声明"未匿名化且不可追溯匿名化"。路径 (ii) 是否采纳取决于审计可用性与合规要求的权衡。
