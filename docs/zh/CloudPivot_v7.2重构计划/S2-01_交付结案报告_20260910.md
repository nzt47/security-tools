## 4. 遇到的问题与解决方案

### 4.1 问题 1：gitleaks 密钥扫描误报（CI 阻断，已修复）

| 项 | 内容 |
|---|---|
| 现象 | 首轮 push（`b9f17236`）「硬编码密码扫描（全分支）」job failure（19s），报 1 处 `openai-api-key` |
| 定位 | `scripts/demo_s2_01_trace.py` 的**演示占位密钥** `sk-demo-SHOULD-BE-REDACTED`（本意是"假密钥，验证脱敏不可恢复"）命中 `.github/gitleaks-config.toml` 规则 8 `\b(sk\|sk-ant)-[A-Za-z0-9_\-]{20,}\b` |
| 根因 | 占位符命名未复用仓库既有白名单约定（配置内已为同类占位符设立 `^sk-(test\|secret\|real\|instance)[-A-Za-z0-9_]*$`） |
| 解决 | 演示脚本与单测占位密钥统一改用 `sk-test-` 前缀（`sk-test-DEMO-SHOULD-BE-REDACTED` / `sk-test-SUPERSECRET-0123456789abcdef`），命中既有白名单；**语义与验证强度不变**（脱敏按字段名 `api_key` 生效，与值前缀无关） |
| 验证 | ① 本地等价模拟（复刻规则+白名单，仅扫 git 跟踪文件）→ 0 发现；② CI 重推后 gitleaks job **success**（run `34465395154`） |
| 经验 | 新增任何"假密钥/假凭据"字面量，必须复用 `.github/gitleaks-config.toml` 的占位符白名单前缀（`sk-test-` 等），或改为运行时拼接；**"假密钥"同样会阻断 P0 安全门禁** |

### 4.2 问题 2：跨平台测试用例失败（CI 阻断，已修复）

| 项 | 内容 |
|---|---|
| 现象 | 最终提交前一轮（`9b581962`）「云枢系统测试流程」失败：单元测试 Shard 4 = **1 failed / 2110 passed**，其余 5 shard 全绿 |
| 定位 | 失败点 `tests/unit/test_trace_v2.py::TestWorkspaceId::test_normalized_case_and_separators`，`AssertionError: assert 'ws_53762e7a3125a2c6' == 'ws_e45f7ad1b90faf6e'` |
| 根因 | 用例断言 `derive_workspace_id("C:/Repo/Demo") == derive_workspace_id("c:\\repo\\demo")`——该等式**仅在 ntpath 语义下成立**。Linux（CI ubuntu-latest）上 `os.path.normcase` 为恒等、`\` 非分隔符、`C:` 被当作普通目录名，两串本就是**不同路径**，故哈希必然不同（本地 posixpath/ntpath 双向模拟已复现：posixpath 下不等、ntpath 下相等） |
| 触发条件 | 本地（Windows）测试通过、CI（Linux）失败——典型"平台语义差异"漏检 |
| 解决 | ① 改为**平台规范化恒等**断言：`derive_workspace_id(p) == derive_workspace_id(os.path.normcase(p))`（两平台均成立）；② 新增**分隔符变体恒等**断言（按 `os.sep` 构造）；③ 大小写不敏感语义单独由 `test_windows_case_insensitive_paths` 覆盖并加 `@pytest.mark.skipif(os.name != "nt")` |
| 验证 | ① 本地 posixpath/ntpath 双向模拟：新断言两平台恒成立，旧断言 posixpath 下复现失败；② 重推后「云枢系统测试流程」**21/21 job success**（Shard 4 转绿） |
| 经验 | ① 断言"同一路径的不同写法等价"必须限定平台语义，否则 Windows 绿 / Linux 红；② 涉及 `os.path` 语义的用例应在本地做 **posixpath/ntpath 双向模拟**再提交；③ 纯本地跑绿不等于 CI 绿——**路径语义类断言是最易漏检的一类** |

### 4.3 问题 3：源码文本断言受 linecache 行号漂移影响（自测脆弱，已加固）

| 项 | 内容 |
|---|---|
| 现象 | 全量 `tests/unit` 扫描中 `TestAppendOnly::test_writer_statement_is_insert_only` 偶发失败（单跑通过） |
| 定位 | 该用例用 `inspect.getsource()` 断言 `_write_to_db` 仅含 INSERT；**扫描运行期间修改了 `trace_v2.py`**，linecache 以新文件内容配旧 `co_firstlineno` 切片 → 取到错误函数体 |
| 根因 | 本仓库 K13/F1/F2 已记录的同类问题（`inspect.getsource` 行号漂移） |
| 解决 | 改为**直读源文件文本**（`pathlib.Path(trace_v2.__file__).read_text()` + 按文本定位函数体），与内存行号解耦；并在验收/结案流程中固化"CI 扫描期间不改源码文件"纪律 |
| 验证 | 加固后全量 `tests/unit` 复跑 **12524 passed / 0 failed** |

### 4.4 问题 4：双远端 rebase 后历史分歧（已解决）

| 项 | 内容 |
