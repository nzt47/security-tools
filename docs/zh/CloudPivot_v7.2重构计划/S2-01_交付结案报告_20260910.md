## 4. 遇到的问题与解决方案

### 4.1 问题 1：gitleaks 密钥扫描误报（CI 阻断，已修复）

| 项 | 内容 |
|---|---|
| 现象 | 首轮 push（`b9f17236`）「硬编码密码扫描（全分支）」job failure（19s），报 1 处 `openai-api-key` |
| 定位 | `scripts/demo_s2_01_trace.py` 的**演示占位密钥** `sk-demo-SHOULD-BE-REDACTED`（本意是"假密钥，验证脱敏不可恢复"）命中 `.github/gitleaks-config.toml` 规则 8 `\b(sk\|sk-ant)-[A-Za-z0-9_\-]{20,}\b` |
| 根因 | 占位符命名未复用仓库既有白名单约定（配置内已为同类占位符设立 `^sk-(test\|secret\|real\|instance)[-A-Za-z0-9_]*$`） |
| 解决 | 演示脚本与单测占位密钥统一改用 `sk-test-` 前缀（`sk-test-DEMO-SHOULD-BE-REDACTED` / `sk-test-SUPERSECRET-0123456789abcdef`），命中既有白名单；**语义与验证强度不变**（脱敏按字段名 `api_key` 生效，与值前缀无关） |
| 验证 | ① 本地等价模拟（复刻规则+白名单，仅扫 git 跟踪文件）→ 0 发现；② CI 重推后 gitleaks job **success**（run `34465395154`） |
| 经验 | 新增任何"假密钥/假凭据"字面量，必须复用 `.github/gitleaks-config.toml` 的占位符白名单前缀（`sk-test-` 等），或改为运行时拼接；**"假密钥"同样会阻断 P0 安全门禁** |

### 4.2 问题 2：源码文本断言受 linecache 行号漂移影响（自测脆弱，已加固）

| 项 | 内容 |
|---|---|
| 现象 | 全量 `tests/unit` 扫描中 `TestAppendOnly::test_writer_statement_is_insert_only` 偶发失败（单跑通过） |
| 定位 | 该用例用 `inspect.getsource()` 断言 `_write_to_db` 仅含 INSERT；**扫描运行期间修改了 `trace_v2.py`**，linecache 以新文件内容配旧 `co_firstlineno` 切片 → 取到错误函数体 |
| 根因 | 本仓库 K13/F1/F2 已记录的同类问题（`inspect.getsource` 行号漂移） |
| 解决 | 改为**直读源文件文本**（`pathlib.Path(trace_v2.__file__).read_text()` + 按文本定位函数体），与内存行号解耦；并在验收/结案流程中固化"CI 扫描期间不改源码文件"纪律 |
| 验证 | 加固后全量 `tests/unit` 复跑 **12524 passed / 0 failed** |

### 4.3 问题 3：双远端 rebase 后历史分歧（已解决）

| 项 | 内容 |
|---|---|
| 现象 | origin push 被拒（远端已有 CI 自动提交的依赖图 `9f43b9dd`）；rebase 后 gitee push 被拒（gitee 存有 rebase 前的 `8b70649a`） |
| 解决 | ① `git pull --rebase origin master` 后推 origin；② `git fetch gitee && git merge gitee/master` 生成合并提交 `88f0acba`（两侧内容等价，`git diff` 为空）后推送**两端**，恢复 origin/gitee 同点 |
| 经验 | 仓库存在 CI 自动提交（依赖图 `[skip ci]`）→ push 前先 `fetch`；**不要对 master 强推**，用合并提交对齐双远端 |

### 4.4 问题 4：CI 覆盖缺口（并发取消，已补跑）

见 §3.2 说明：`cancel-in-progress` 使连续 push 取消旧 run，且合并提交 diff 为空不触发 `paths:` 过滤工作流。已用 `gh run rerun` 对 tree-identical 提交补跑 `ci.yml` / 日志性能守护 / Error Reporting。
