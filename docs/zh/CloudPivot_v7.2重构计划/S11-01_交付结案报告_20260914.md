## 3. 根因（代码行级）

| # | 位置 | 事实 |
|---|---|---|
| 1 | `agent/orchestrator/lifecycle_manager.py:118` | **唯一**在业务代码里"定序预导入"原生栈的地方 —— 但它发生在 **`DigitalLife` 构造时**，此时进程早已加载 torch/onnxruntime/sklearn 等重型原生库，pyarrow 的"干净窗口"已经错过 |
| 2 | `app_server.py`（修复前 1–49 行） | 生产进程（长寿命）**完全没有**这道保护；`.env` 加载在第 45–49 行，`plugins.plugin_api`（会连带导入 memory/admin/skills/chat 等重模块）在第 32 行就已执行 |
| 3 | `tests/integration/conftest.py::_pin_native_import_order()`（修复前 53–71 行） | 该实现在**修复前只被 tests/integration 引用**；`tests/unit` 走不到 ⇒ unit 处于**无保护**状态（S10-05 遗留 #6） |
| 4 | 结论 | 保护**位置太深 + 覆盖面太窄**：产品侧（app_server）没有，测试侧只覆盖 integration |

**为什么"顺序"能免于崩溃**：pyarrow 的原生初始化只需**在进程干净时**发生一次。
一旦 `numpy → pyarrow → pandas → sklearn` 在入口按序导入完，后续
`sklearn.utils.fixes:19 → pandas → pyarrow` 命中 `sys.modules`，原生初始化不再发生，崩溃路径不可达。

## 4. 交付内容

### 4.1 新增共用实现 `agent/utils/native_preimport.py`（唯一实现）

- 把 S10-05 在 `tests/integration/conftest.py` 内联的 `_NATIVE_IMPORT_ORDER` +
  `_pin_native_import_order()` **提升**为一个模块（**同一份实现，不是第二份**），
  并把现象/根因/顺序依据/失败姿态的完整记述集中到该模块 docstring。
- 对外 API：`NATIVE_IMPORT_ORDER`、`is_enabled()`、`pin_native_import_order(extra=())`、
  `report_line()`、`PREIMPORT_RESULTS`、`STATUS_KEY/STATUS_ENABLED/STATUS_DISABLED`。
- **幂等**：重复调用只补做"尚未记录过"的模块，**已记录项不重跑、不覆写**
  （否则第二个调用点会把真实耗时覆写成 `cached`，报告就再也看不出保护是否真装上 —— 假绿灯）。
- **失败姿态**：任何一步导入失败只记 WARNING 并继续，绝不抛异常、绝不阻断启动/收集。

### 4.2 `app_server.py`：进程入口最前

```
（修复后顺序）
1. stdlib 导入
2. Windows stdout UTF-8 reconfigure        ← 上移：保证 [S11-01] 记录行不乱码
3. .env 装载（agent.env_config_manager）    ← 上移：让开关可写在 .env（守「配置走 .env」）
4. ★ agent.utils.native_preimport.pin_native_import_order() + print(report_line())
5. import requests / plugins.plugin_api / flask / 其余 agent.*
```

- **位置纪律**：第 4 步必须早于 `plugins.*`（`plugins/__init__.py` 会连带导入
  memory/admin/skills/chat 等重模块）与一切其它 `agent.*`。允许早于它的**只有**
  `.env` 装载器 —— 因为开关本身要能从 `.env` 读到。
- **未引入任何副作用模块**：只 import 标准库 + `agent.env_config_manager` +
  `agent.utils.native_preimport`（两者顶层依赖均为纯标准库，已核对：
  `env_config_manager` → `agent.logging_utils` / `agent.utils.cross_process_lock` 均为 stdlib-only）。
  没有起服务、没有连库。

### 4.3 `tests/conftest.py`：unit / integration 共用同一道保护

- 在 `sys.path.insert(0, PROJECT_ROOT)` 之后立即调用 `pin_native_import_order()`
  —— 这是 pytest 在 `tests/**` 下"能 import 到 agent 的最早时机"（rootdir→子目录逐级加载 conftest）。
- `pytest_report_header` 从 `tests/integration/conftest.py` **上移**到 `tests/conftest.py`
  （只定义一处）：若两处都定义，pytest 会拼接两个 hook 结果 ⇒ integration 打印两遍、unit 一遍也没有。
- `tests/integration/conftest.py` 改为**只 import 共用模块**，删除内联实现
  （用 AST 守卫锁死"不得再长出第二份"，见 §5.2）。
- 装载失败只降级告警，并提供同名降级函数，不阻断收集。
- **顺带修掉一处由本改动"暴露"的裁剪入口回归**（如实记录，非任务要求）：
  S10-05 时 `tests/integration/conftest.py` 在模块级不 import 任何 agent 模块，
  所以"裸 `pytest` + `--confcutdir=tests/integration`"（此时 `tests/conftest.py` 不加载、
  它那句 `sys.path.insert(0, PROJECT_ROOT)` 也就没执行）能勉强跑；改成 import 共用模块后
  该组合会 **conftest 装载即 `ModuleNotFoundError`**（实测 rc=4），比基线**更糟**。
  故在 `tests/integration/conftest.py` 加了一句幂等 `sys.path` 兜底：

  | 命令 | 基线（main 工作区） | 修复后（worktree） |
  |---|---|---|
  | `pytest tests/integration --confcutdir=tests/integration --collect-only -q` | 129 collected / **48 errors**，rc=1 | **2106 collected / 0 errors**，rc=0 |
  | `pytest tests/integration --confcutdir=tests/integration ...`（中间态，仅改 import 未加兜底） | — | rc=**4**（`ModuleNotFoundError: No module named 'agent.utils'`） |

  即该兜底让这个入口**严格优于基线**，并已用守卫用例锁死
  （`test_integration_conftest_bootstraps_repo_root_for_cropped_entry`：
  要求 `sys.path` 兜底存在且早于共用模块的 import）。

### 4.4 开关 `CP_NATIVE_PREIMPORT_ENABLED`（可关闭 + 已登记注册表）

| 项 | 值 | 取自哪里 |
|---|---|---|
| 读取点 | `agent/utils/native_preimport.py::is_enabled()` → `os.environ.get(_ENV_KEY)` | 真实代码行 |
| 语义 | `0/false/no/off/空` = 关闭；**未设置 = 开启** | 真实代码行 |
| 注册表默认值 | `True`（bool） | 与读取点"未设置 ⇒ 开启"逐条一致 |
| 风险级 | **B（需二次认证 + 双人确认）** | 见下 |
| 生效方式 | `needs_restart=True`（进程入口读取） | 真实行为 |
| owner | `agent/utils/native_preimport.py`（真实文件，守卫会校验存在性） | — |

**风险级裁定依据（拿不准取更严，依据写进注册表注释）**：

- 支撑 B：关闭后**长寿命进程**可能在已加载 torch/onnxruntime 之后被 `arrow.dll` 原生初始化
  打成 `0xC0000005`，**进程被系统直接终止、没有 traceback** —— 与同表
  `CP_ARCHIVE_LOCK_ENABLED` / `CP_EVENTS_LOCK_ENABLED` / `CP_TRACE_LOCK_ENABLED`
  的「关掉即失去完整性/存活强保护」**同型**，而那些条目按本表既有「风险级裁定口径（保守优先）」定为 B。
- 反例（已考虑、未采纳）：同表 `CP_MODEL_FALLBACK_ENABLED` 定为 A —— 但关掉它只让调用
  **显式失败**、进程照常存活，不产生静默崩溃，故不同型。
- 结论：A 降 B 只多一次确认成本；B 降 A 则可能让"关掉崩溃防护"变成随手可切。

|---|---|---|---|
| 预导入自身成本（干净进程，3 次样本） | — | — | **2.23s / 2.45s / 2.83s** |
| `pytest tests/unit --collect-only -q` 进程总耗时（3 轮交替，中位数） | **19.3s** | **17.0s** | **+2.3s（+13.5%）** |
| 同上，pytest 自报 "collected in"（中位数） | 13.15s | 13.36s | −0.2s（**无变化**） |

逐轮原始数字（ON/OFF 交替，消除顺序效应）：

```
round=1 mode=ON  collect= 19.6s   collected in 13.32s
round=1 mode=OFF collect= 17.7s   collected in 13.99s
round=2 mode=ON  collect= 19.3s   collected in 13.15s
round=2 mode=OFF collect= 17.0s   collected in 13.36s
round=3 mode=ON  collect= 18.8s   collected in 12.86s
round=3 mode=OFF collect= 16.1s   collected in 12.64s
```

**如实结论（不是"应该更快"，是实测）**：

1. 对 `tests/unit`，保护给**收集阶段**带来约 **+2.3s**（约 +13.5%）。
   原因经直接证据确认：unit 的测试模块在收集期**本身并不导入** numpy/pandas/sklearn
   —— 关掉保护后用 `python -X importtime` 观察整个 `--collect-only`，
   **没有任何** `numpy / pyarrow / pandas / sklearn` 的导入行：

   ```powershell
   $env:CP_NATIVE_PREIMPORT_ENABLED='0'
   python -X importtime -m pytest tests/unit --collect-only -q -p no:randomly 2>&1 |
       Select-String -Pattern "\| (numpy|pyarrow|pandas|sklearn)(\.|$)"
   # → 输出为空（命中 0 行）
   ```

   所以这 2.3s 是**净新增**，不是"把将来的开销提前"。
   （对 `pytest tests/unit` **全量**则不同：全量过程中本来就会导入这批库，理论上成本被摊掉。
   但"全量 ON/OFF 对照"需要跑两次 60+ 分钟的全量 ⇒ **超出本任务预算，未做，故此处不作数字断言**。
   §6.5 只报告**一次**全量的实测值，并声明它与 57m30s 基线**口径不同**
   —— 不同 worktree、不同日期、不同机器负载，**只披露不考核**。）
2. pytest 自报的 `collected in` **不变**（13.15 vs 13.36）—— 因为它的计时器在 conftest 加载**之后**
   才起跳，差额全部落在 conftest 阶段。这也说明"看 pytest 自己那行会看不到这个成本"，
   必须看**进程总耗时**。
3. **首跑冷缓存会给出严重误导**：第一次未交替测量得到 `ON 58.5s / OFF 17.0s`（差 41.5s），
   交替复测后真实差值是 2.3s ⇒ **41.5s 是冷缓存伪影**，已按纪律"先怀疑自己的测量"排除，不作为结论。
4. 对 `tests/integration` **耗时不变**：该套件的预导入在 S10-05 就存在且无条件执行，
   本任务只是换了实现位置（等价 + 幂等），不新增开销。

**判断**：+2.3s 是保护本身的代价（导入同一批原生栈在任何进程里都要付），
unit 套件全量 57 分钟量级下占比 <0.1%；**若某环境认为不划算，用 `CP_NATIVE_PREIMPORT_ENABLED=0` 一键回到旧行为**（该开关即为此而设）。

**#2 的代码行级根因**（值得单列，属产品/测试两侧的口径问题）：

`tests/unit/test_decision_log_rotation.py:1186-1198` 把"今日"**硬编码成字面量**：

```python
lines = [
    _raw_line("2026-09-10T10:00:00+00:00", "deny",  "d10"),
    _raw_line("2026-09-11T10:00:00+00:00", "allow", "d11"),
    _raw_line("2026-09-13T10:00:00+00:00", "ask",   "d13"),   # ← 写作当日 = "今日"
]
...
result = archive_daily_file(path)
assert result["archived"] == 2, result     # 两条历史日被移入分片
```

`archive_daily_file` 的语义是"归档除**当前日**以外的全部日"。
作者在 **2026-09-13** 写该用例时 `2026-09-13` 恰为今日 ⇒ 归档 2 天、`today=1`；
到 **2026-09-14**，`2026-09-13` 也成了历史日 ⇒ 归档 3 天、`today=0`，断言必然失败。
**即：该用例会在写作次日自动变红**，与 S11-01 无关。已列入 §8 遗留 #3。
