## 3. 遇到的问题与解决方案

| # | 问题 | 解决方案 |
|---|---|---|
| 1 | §3.2 无 risk/data_class 的 unknown 取值；存量资产 trust 全缺，默认低风险/低敏感会造成"假安全" | 沿用 S1-01 裁定 None=未评估；本任务确定性回填：auto 带仅 public/internal；confidential/secret **只出 candidate** 进 NEEDS_REVIEW（人工复核确认后才写入），destructive **永不自动写入**（三件套校验器强制，不静默放行） |
| 2 | 真实存量 29 条资产中 5 个中文名 persona 技能在 Registry 登记时被**误合并**进同一 descriptor（`name_similarity` 对纯 CJK 名称清洗为空 → 不同名也相似度 1.0，违背 P7.2-05 宁冗余勿误合） | registry 修正：`normalize_name` 对纯 CJK 名称保留原串，`name_similarity` 走字符级 SequenceMatcher（CJK 路径）；ASCII 行为零变化；回归单测锁定（`TestCjkNameSimilarityRegression`） |
| 3 | 护栏技能（safety_guard 等）正文"提及"删除/格式化等危险操作（实为拦截语义）——朴素关键词扫描会误升风险 | 句级护栏判定：破坏性短语所在句命中禁止/拦截/二次确认/审批后/正向可回滚恢复 → 视为被护栏（不升）；"无需弹窗确认"类**免确认指令**才触发 RK-5 高风险人工复核 |
| 4 | 实跑暴露默认 registry 台账被隔离 store 的测试写入污染（install 接线落全局 data/descriptors.json） | Descriptor 台账与技能主轨**同目录隔离**（默认 store → 全局台账；tmp store → 同目录台账）；复跑技能中心受影响套件验证零污染 |
| 5 | 批量回填的原子性：registry 写 API 默认每次 autosave，单条失败会残留半批 | `run_backfill` 以 `autosave=False` 运行，ok 批显式 `save()` 提交、批失败 `reg.load()` 回滚至上一已提交批次；单测注入 `update_trust` 故障验证整批回滚不残留 |
| 6 | 干跑/实跑须确定性可复现（验收项） | 计划为纯函数（无时钟/无随机），资产按 id 排序、规则确定性输出；dry-run 两次结果逐字节一致（单测 + 实跑 CLI 双验证） |
| 7 | 人工复核结果（reviewer 提升 verified/confidential/high）不得被回填降级覆盖 | 保守合并：provenance 仅单调提升/同级补证据；risk/data_class 现状为空或计划更严才写；requires_approval 只 False→True；undo/补偿文本只在现状为空时补（单测 `test_conservative_preserves_human_upgrade`） |
| 8 | 演示/冒烟环境耦合：`demo_pipeline` 读取共享台账（S1-02 起台账被回填/安装常态化写入） | demo 改用一次性临时台账路径（autosave=False 永不落盘），演示与真实台账彻底隔离 |
| 9 | **CI 架构规则校验失败（head 740d042f，no_circular_dependency 点名 store.py:592）**：service 侧新增 skills_mgmt→descriptors.backfill 懒加载，与 backfill→skills_mgmt.store/file_store 懒加载构成 `store→registry→service→backfill→store` 环 | **修复（commit `d3fa0a7b`）**：backfill.sync_skill_descriptor 移除 skills_mgmt 读库回退（payload 必由调用方传入，缺失返回 advisory 错误）；service._sync_descriptor_advisory 在服务侧组装 payload（skill 对象→主轨→文件轨）；descriptors 保持纯依赖叶子。本地复现失败→修复→回归绿（0 未豁免违规）+ 新增单测（缺 payload 契约）；依赖图同步更新 |
