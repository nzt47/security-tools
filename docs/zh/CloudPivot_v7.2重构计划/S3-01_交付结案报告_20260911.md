## 4. 遇到的问题与解决方案

### 4.1 问题 1：轨迹步骤顺序不确定（实现期实测，已修复）

| 项 | 内容 |
|---|---|
| 现象 | 端到端演示中 LCS 骨架退化为**单步**（应 3 步），`eligible=False`，无法产出模式 |
| 定位 | `capability.collect_rows()` 对同一任务的行按 `(started_at, trace_id)` 排序，而 `trace_id` 是**随机 16 位 hex** |
| 根因 | 合成/真实台账中同一任务的多个能力调用可能落在**同一 `time.time()` 刻度**（Windows 时钟粒度 + 连续调用），此时 `started_at` 相同；用随机 `trace_id` 作兜底键会把步骤**打乱**，使"读→测→写"变成"写→读→测"，公共子序列自然退化为 1 |
| 修复 | 统一台账的 `started_at ASC` 排序**本身已含写入序**（稳定序）⇒ 直接**保留输入顺序**，删去随机兜底键；`group_rows_by_task()` 同步改为保留输入序 |
| 验证 | 演示骨架恢复 3 步、`eligible=True`；用例 `test_step_order_follows_ledger_order` 固化；测试数据一律显式传递增 `started_at`，不再依赖时钟 |
| 经验 | **等值排序键上的随机兜底会静默破坏语义**；"看起来更确定"的 tie-break 反而引入不确定性 |

### 4.2 问题 2：决策树分支提取的盲点（实现期实测，已修复）
