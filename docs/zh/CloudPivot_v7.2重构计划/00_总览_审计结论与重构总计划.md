## 3. 重构总计划

### 3.1 是否需要分阶段拆分：**需要**

论证（四条）：

1. **范围大、耦合深**：v7.2 覆盖契约层（ToolDescriptor/状态机）→ 数据层（Trace/审计/事件）→ 流水线（SkillFactory/内化）→ 治理安全（审批/策略/熔断）→ 记忆评测（ACR/UTC/L0-L3）→ UI（六面板），且 §13.3 联动表证明 schema/状态机/事件/策略/熔炉五处硬耦合——一次交付必然失控。
2. **依赖链天然分层**：契约层是所有下游的前提（S1 → S2 → S3 → S4/S5），数据/埋点又是上层机制（断食、审批衰减率、评测）的地基；存在严格的前置顺序。
3. **与云枢现状承接**：大部分机制云枢已有半落地实现（skills_mgmt/workflow_learning/process_distill/EVO/self_healing），重构 = 映射+补齐缺口而非从零新建；分阶段便于每阶段"只接线已建未用能力 + 补一个契约缺口"，风险可控、可独立验收。
4. **团队既有工作流即分任务并行**：docs/zh 各轮重构计划（规划/知识/学习/进化/自愈）均以"总览 + 编号任务提示词"形式分发执行——延续该模式成本最低。

### 3.4 执行策略与里程碑

- **并行可行组**：S3 与 S4 部分并行（S4 仅依赖 S2 + 部分 S1）；S5-02（评测锚）可在 S2 完成后尽早启动，作为后续阶段验收的标尺。
- **里程碑**：M1（S0+S1 契约冻结）→ M2（S2 数据/审计/埋点基座）→ M3（S3 消化流水线闭环）→ M4（S4 治理安全收口）→ M5（S5+S6 记忆评测与面板）→ M6（全量回归 + 混沌 + 结案）。
- **撤退/验收门**（对齐 v7.2 §1.4 与云枢各轮惯例）：每阶段 DoD 清单化（参照 §11.4 Walking Skeleton DoD 风格），任一项不达标不进下一阶段；委派成功率/消化吞吐等量化指标进入 M3 后逐周披露。

### 3.5 通用约束（所有阶段共享，沿用云枢既有轮次纪律）

1. **守不易**：不破坏既有公开接口与行为；新增机制失败绝不阻断主流程（评审 advisory 语义）。
2. **配置**：可调参数走 `.env`（`CLOUDPIVOT_*` / 既有 `SKILLS_*` / `EVOLUTION_*`），非法值回退默认。
3. **测试**：新功能必加单测，覆盖率 ≥80%；既有全量回归不降级。
4. **留痕**：所有状态机/审批/审计事件写入既有审计与事件存储（对齐 §2-02 之后为链式审计）。
5. **安全底线**：自动化调度/自动合并/自动回滚默认关闭或需显式阈值；destructive 必审批。
6. **术语纪律**：消化(digest)两义必须在 S0 更名收敛后使用，正文与 UI 一致。
