## 4. 遇到的问题与解决方案

### 4.1 问题 1：敏感键**子串**匹配吞掉度量字段 → UTC 归零（自测暴露，已修复）

- **现象**：首轮联调发现 `cost` 事件的 `tokens_in` / `billable_tokens_in` 被替换为
  `"[已丢弃:敏感键]"`，下游 `int()` 解析失败 → **当日 UTC 与成本全为 0**。
- **根因**：`sanitize_payload()` 以**子串**匹配敏感键黑名单，而黑名单含 `token`，
  `tokens_in` 命中子串 → 被当作密钥丢弃。
- **修复**：改为「**精确命中 + 非字母数字分段命中 + 末段命中**」（`api_key`/`access_token`/
  `token` 拦截，`tokens_in`/`token_count`/`token_usage` 放行），并增设**度量字段白名单**
  （18 个键永不被启发式误伤），保护 §6.6 cost schema。
- **回归**：`test_metric_fields_never_mangled` + `test_secret_keys_dropped` 等 6 例。
- **暴露的深层问题**：这与 S2-02 的 D6（脱敏误伤 24 位 hex 关联键）**同源**——启发式脱敏对
  「内部生成的结构化标识/计量字段」天然不友好。本任务的处置是把事件流建成
  **「载荷纪律」（只放标识/标签/计数）+ 显式白名单**，而不是继续加启发式规则。

### 4.2 问题 2：`task.closed` 丢失 `workspace_id`（P7.1-19 不变量静默失效，已修复）

- **现象**：演示输出中 `task.closed.payload.workspace_id` 为空，而该任务明明绑定了
  `ws_demo_s203`（工具级/成本级事件都有值）。
- **根因**：收口顺序为 `TraceFacade.finish()`（**清空 ContextVar**）→ `record_task_closed()`，
  后者再读 `trace_fields()` 时上下文已为空。工具级 Trace 在收口前落账故不受影响，
  **只有任务级事件受影响**——即 P7.1-19「workspace_id 不变量」在任务级静默降级。
- **修复**：`record_task_closed()` 增 `workspace_id` / `subject_id` 显式形参，
  由 `_record_task_closed_metrics()` 从 `ctx` 携带过来（不依赖收口后的上下文）。
- **回归**：`test_success_path_emits_task_closed` 断言二者非空；演示快照可见
  `"workspace_id": "ws_demo_s203"`。

### 4.3 问题 3：CI 架构门禁失败——新增循环依赖（首轮本地复现即拦截，已修复）

- **现象**：`arch_rules --check` 报 **未豁免违规 1 项**：
  `agent.skills_mgmt.service → agent.observability.acr`（规则 `no_circular_dependency`）。
- **根因**：既有链路 `acr → events → trace_v2 → descriptors.bridge → skills_mgmt.store →
  registry → service` 已存在，本任务在 `service.list_pending_approvals()` 里新增
  `service → acr` 刚好闭合为环。
- **修复**：把 view 埋点**下沉到审批域** `ApprovalFlow.record_view()`（审批域不在该链路上），
  服务层经注入的 `self._approval` 调用，**服务层不再导入 observability**。修复后
  `arch_rules --check` → ✅ 通过（0 未豁免违规）、`lint-imports` → 2 kept / 0 broken。
- **附带收益**：语义更内聚（审批域拥有自己的指标 API），且与 S2-02 的依赖倒置取向一致。

### 4.4 问题 4：`approval.required` 审计镜像破坏 S2-02「一动作一记录」不变量（回归暴露，已修复）

- **现象**：S2-02 既有单测 `test_audit_integration.py::test_approval_lifecycle_recorded`
  失败——链上动作序列多出 `approval.required`，与其断言的
  `[approval.submit, approval.approved, approval.submit, approval.rejected]` 不符。
- **根因**：事件流的「治理类事件审计镜像」把 `approval.required` 也镜像入链，
  但审批状态机**已**把 `approval.submit/approved/rejected/merged/archived` 直接写链，
  造成语义重复留痕。
- **修复**：`AUDIT_MIRROR_TYPES` 收敛为真正**无其他写入方**的四类：
  `escape` / `model.degraded` / `policy.denied` / `healing.triggered`；
  并加断言 `test_audit_mirror_set_is_governance_only` 固化该不变量。

### 4.5 问题 5：测试互扰——全局 `os.makedirs` patch 致全量扫描 1 failed（全量回归暴露，已修复）

- **现象**：全量 `tests/unit` 首次扫描 **13032 passed / 1 failed**：
  `test_system_tools_core.py::TestSystemToolsLoadSaveTasks::test_save_tasks_creates_directory`
  断言 `os.makedirs` 恰好被调用 1 次，实际 2 次（多出的一次来自事件出口建目录）。
- **根因**：该用例以 `patch('agent.tools.task_tools.os.makedirs')` 打桩——`os.makedirs` 是
  **进程级全局函数**，patch 后影响全进程；本任务在 `task_tools` 的受控写登记链路上新增了
  目录创建调用，被该断言计入。
- **修复**：事件出口与逃逸台账改用 `pathlib.Path.mkdir(parents=True, exist_ok=True)`

  全量扫描 **13033 passed / 0 failed**。
- **说明**：该失败**不是**功能缺陷，而是「测试以全局副作用计数作断言」的脆弱性被新调用点触发；
  处置取向是不改动既有测试的断言意图，而是让新代码使用更局部的原语。
