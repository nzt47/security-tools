### 3.4 与既有规避的关系（为什么产品侧没事、测试侧必崩）

## 5. 「能修的」与「环境限制」的分界

| 类别 | 判定 | 处置 |
|---|---|---|
| pyarrow 原生初始化崩溃本身 | ③ **环境 / 平台受限**（Windows 原生 DLL 加载状态；同版本 pandas/pyarrow 在新鲜进程 100% 正常，CI（Ubuntu）不复现） | 不改产品语义；在测试基础设施层固化导入顺序规避 |
| 「单进程长跑必然崩」导致 80% 用例无法验证 | ① **测试隔离/加载顺序问题**（可修，且已验证） | ✅ 已修：`tests/integration/conftest.py` 的 `_pin_native_import_order()` |
| 崩溃时没有 pytest 汇总行 ⇒ 结论被吞 | ① 可观测性问题 | 本次全部运行落文件 + 崩溃前探针快照（`s1005_probe.py`） |
| 105 条 skip | 既有设计（`@pytest.mark.slow` 门控） | 用 `--runslow` 单独覆盖（§8.3） |

**修的是**：进程内原生栈的导入时机（让 `pyarrow` 在进程最干净时完成原生初始化），
与产品侧 `lifecycle_manager.py:118` 既有处置同源同法。
**没改的是**：任何被测功能、断言、产品代码。

## 6. 修复与验证

### 6.1 修复内容

`tests/integration/conftest.py`（**仅测试基础设施**）新增：

```python
_NATIVE_IMPORT_ORDER = ("numpy", "pyarrow", "pandas", "sklearn")   # 与 sklearn.utils.fixes 真实依赖链一致

def _pin_native_import_order() -> None:
    for _name in _NATIVE_IMPORT_ORDER:
        if _name in sys.modules: continue
        try: importlib.import_module(_name)
        except Exception as _e: logging.getLogger(__name__).warning(...)   # 降级，不阻断收集

_pin_native_import_order()
```

并在 `pytest_report_header` 把每步实际结果写进报告头（**防空转/假绿灯**）：

```
[S10-05] 原生扩展导入顺序固化: numpy=ok:108.9ms, pyarrow=ok:7.9ms, pandas=ok:418.8ms, sklearn=ok:1149.7ms
```

**为什么这对「随机顺序」也成立**：规避发生在**收集阶段**（任何用例执行之前），
`pyarrow` 的 `sys.modules` 条目在第一个测试跑之前就已存在，因此
`pytest-randomly` 无论把 `test_digital_life_integration.py` 排到第几位，
都走不到 `pyarrow/__init__.py:71` 的原生初始化路径 —— 这是**结构性**规避，
不是「把文件顺序摆好」的偶然规避（故本次无需禁用 `randomly` 才能跑通）。

        Tee-Object -Append perfile.log
