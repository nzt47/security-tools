## 1. 文档定位与总体评价（一句话结论）

**v7.2 是一份"目标系统级"的理想架构图纸（SSOT），其价值主张、治理原则与大部分机制设计是高质量、可采纳的；但它是按"独立 IDE 伴侣产品 + Node/VS Code 宿主"的形态书写的，与云枢"数字生命体 + Python 服务 + Web/Electron 工作台"的现状存在形态与术语错位，且若干机制的样本门槛、判定集维护、低流量策略在个人开发者负载下不可直接照搬。因此它应被当作"机制清单 + 参考架构"逐层吸收，而不是当作云枢的整包施工图纸。**

核心判断依据：

1. v7.2 的护城河公式 `ToolDescriptor × 消化状态机 × SkillFactory × Watchdog+Policy` 与云枢近四个月的重构轮次（技能中心消化体系、workflow_learning、过程蒸馏、EVO 进化机制、自我修复机制）**在机制层面高度同构**——v7.2 不是天外飞来的新系统，而是把这些已落地/半落地的能力提升到"契约层 + 状态机 + 量化门槛"的规范化描述。
2. v7.2 的绝大多数"能力点"在云枢已有真实模块承载或雏形（详见 §2.4 与 §6 差距矩阵），说明设计不是空中楼阁；反过来也意味着**施工风险主要是"映射与取舍"而不是"从零建设"**。
3. 文档自称"冻结版施工图纸"，但它的宿主形态（§11.5 VS Code 扩展、§1.7 不做独立 Web App）与云枢实际形态矛盾，且对云枢已有的同名机制（如 "digest/消化"）语义不同——**直接照章施工将触发整版重写冲动并产生术语污染**（详见 §4）。

## 2. 设计思路合理性评估（认可项）

### 2.1 战略定位与价值声明——诚实、清醒（认可）

| 条目 | 评价 |
|---|---|
| §1.2 "生成质量不超上游，赢的是记忆、成本、治理，不是智力" | 对个人 IDE 伴侣类产品是**正确的差异化声明**，避免与 Cursor/Cline 拼模型智力；护城河锁定在"工具契约 + 消化 + 治理"上，与云枢的差异化方向一致（记忆命中、更少打断、透明可控）。 |
| §1.4 战略撤退点（委派成功率 <60% 持续 2 周 / 否决率 >70% / 维护成本超承受） | 量化止损是**成熟的产品元认知**，且云枢 EVO 轮次已有"撤退点/自主权分级"先例，可直接对齐。 |
| §1.6 认知三修正（闭源不可内省→行为级萃取；无跨架构迁移只有等价替换→shadow；协议以实测为准→探针先行） | 三条都是真实工程约束的正确抽象，**尤其"shadow 等价替换"与"探针先行"**，直接指导 MCP/闭源 Agent 的接入策略。 |
| §1.7 非目标清单 | 明确不 fork、不 native 替代闭源、不做分布式追踪等——**有效防范围过大的工程失控**（对应云枢教训"过度工程化拖死 P0"）。 |

### 2.3 机制设计——大部分正确、部分为云枢已有思想的规范化

**认可的机制（含出处）：**

1. **八条不变量（§1.5）**：回滚第一公民（无 undo_hint 不得入库）、权限跟随能力禁止信任继承、自动化不可做不可见之事、数据不出域、黑盒承认黑盒——这些是治理层最常被忽略、实际事故率最高的原则。
2. **消化状态机七态 + 转移条件（§3.3）**：borrowed→mirrored→shadow→internalized→native 及 permanent_borrowed/deprecated 旁路，比云枢现有"草稿→审核→发布→弃用"多出"shadow 灰度"这一层，是**增量最值得借鉴的部分**。
3. **ToolDescriptor v2.1 契约（§3.2）**：把 meta/tenancy/trust/runtime/evolution/quality/governance 结构化，且"risk=destructive ⇒ requires_approval ∧ undo_hint ∧ compensating_action 全必填"——**把安全前置到了契约层**，方向正确。
4. **内化触发六条件 + ROI 自动 PR（§4.5.1）**："消化不是口号，而是会自动产生 PR 的流水线"——与云枢 process_distill/workflow_learning"自动固化"思想一致，但增加了 **ROI 量化和质量/性能/隐私硬闸门**，是升级点。
5. **评测分层 L0-L3 + L0 锚 20 条人工冻结用例（§6.5）**：打破"自验收循环"，是云枢历来强调的"外部评测锚"思想的延续。
6. **安全细节**：提示注入防御六机制 + 审批面安全（§5.7）、审计平权（UI 操作与 Agent 同表）、子智能体临时凭据 TTL 销毁、egress guard 与 OPA 职责分离——**覆盖面超过云枢现状，是最值得吸收的安全增量**。
7. **整包回滚原子单位（§4.4 P7.2-15）**：code+skills+weights+data-baseline 耦合回滚，防止"只回技能不回代码"的不一致——对应云枢"四套版本空间耦合"真实教训。
8. **分裂脑防护 + 单机 lockfile（§4.4 P7.2-16）**：与云枢 SingletonManager/lockfile 实践同构。
9. **名片懒加载（§4.5.2）**：SKILL.md 只读 frontmatter、正文按需流式——直接解决技能库增长后的"上下文爆炸"，云枢 RRF 5000 技能压测报告印证了该问题的真实性。
10. **UI 五坑 / 永不自动化五类 / 断食与双层成本刹车**：产品化程度高，可直接作为云枢 UI 验收红线。

## 3. 理论缺陷（设计思路本身的问题）

| # | 缺陷 | 出处 | 问题说明 | 建议 |
|---|---|---|---|---|
| T1 | **消化状态机的"判定集维护成本"未建模** | §3.3 / §3.1 EquivalenceCase(30-100) | mirrored→shadow 需要 30–100 组等价判定用例；用例由谁写、LLM 生成后谁抽检、上游漂移后判定集失效重生成的成本全部未计。判定集本身会成为新的维护负担，可能使内化停滞。 | 增加"判定集资产"概念：Seed Pack（§11.4 12 技能×≥3 组）起步 + LLM 生成+人工抽检 + 判定集漂移重探纳入 30 天周期；将判定集构建成本计入 ROI 公式。 |
| T2 | **内化六条件的样本门槛与个人负载矛盾** | §4.5.1（digest_count≥50 / 月 samples≥200） | 个人 IDE 场景下，单个原子工具月调用 200 次很可能达不到 → 六条件永不满足 → 消化空转，护城河公式失效。 | 增加**低流量替代通道**：月 samples<200 时支持"手动 promote + 人工评审"，或按能力类型（高频原子 vs 低频社区）分档门槛。 |
| T3 | **模式挖掘对噪声轨迹的鲁棒性未定义** | §4.5（LCS + 决策树，输入≥20 条） | 真实编码轨迹含失败重试/探索噪声，LCS 对噪声敏感；文档只提脱敏，未定义轨迹归一化/清洗/同任务判定标准。 | 定义"同类轨迹"的判定键（任务意图 + capability 集合 + 结果状态），增加轨迹清洗步骤与最低相似度阈值。 |
| T4 | **native 后的持续保障缺失** | §3.3（native = 30 天零回退 + 每周探活） | native 后不再双跑 diff，"探活"内容未定义（是否含与上游等价性 diff）；native 自身也会随环境漂移退化，缺 native 期持续质量闸。 | 定义 native 期"探活 = 判定集子集每周重放 + 成本/成功率监控"，退化触发 shadow 回退弧（文档已有 native→borrowed 降级动作，需落成自动规则）。 |
| T5 | **ACR 介入计分的启发式本质** | §6.1-6.4（Approve=1/条件=0.5/超时 Deny=2…） | 赋值无理论推导且难度等权；文档自认 P1 起数据拟合，但早期（W1-W9）ACR 不可比，撤退点（§1.4）若引用早期 ACR 会有噪声风险。 | 早期只披露不考核（§6.3 已如此），撤退判定优先用"委派成功率/否决率"等客观信号而非 ACR。 |
| T6 | **UTC 计量的口径一致性问题** | §6.2 / §4.1 P7.1-18 缓存命中不计 token | 不同模型计价/缓存/重试/shadow 开销的归一化口径未给公式；跨模型比较成本可能失真。 | 定义成本归一基准（以主力模型价格为锚 + 换算系数表），shadow_overhead 计入成本埋点（§6.6 已有该字段，需公式化）。 |
| T7 | **"成功率"的判定主体可靠性** | §3.9 回收三件套中"上游自评+云枢复评" | 复评若由 LLM judge 承担，其本身可能误判；撤退点"委派成功率<60%"建立在待校准的判定上。 | 成功率优先用可机械验证信号（schema 校验/测试通过/副作用核对），LLM judge 只做兜底并抽样人工校准。 |
| T8 | **"消化对象"分层不清** | §3.3 状态机主语为 Tool/Capability，§3.7 SKILL.md 又独立成章 | 原子工具（MCP tool）内化与 SKILL.md 编排的内化是两跳还是一条流水线？文档未给出 Tool→Skill 的聚合规则（类似云枢 workflow→skill_converter 的关系）。 | 明确消化对象三层：原子工具（capability）→ 工作流序列 → SKILL.md 编排；定义各层的状态机适用范围与转换器。 |

## 7. 审计结论汇总

### 7.1 总体结论
- **合理骨架（认可）**：价值定位、八条不变量、消化状态机+内化六条件、评测分层、安全治理细节、文档纪律——方向全部正确，且大部分与云枢近四个月重构方向同构。
- **采纳方式**：v7.2 作为**机制/契约清单**吸收进云枢，宿主形态维持云枢工作台（形态决策见总计划 S0）。

### 7.2 三项最高优先缺口（重构必须先处理的）
1. **G1 形态与术语对齐**（P1+P2+P3）：先定 v7.2↔云枢映射与宿主形态，否则一切施工都会错位或重复造轮子。
2. **G2 审计与埋点基座**（P5+P6）：链式审计 + events + ACR/UTC 埋点是"记"与"控"的地基，也是多数上层机制（断食/审批衰减率/评测）的依赖。
3. **G3 消化流水线统一与量化门**（T1+T2+T3+T4）：把云枢已有三轨固化（digest/process_distill/workflow_learning）统一到七态 + 判定集 + 内化六条件，并解决个人负载下门槛不可达的问题。

### 7.3 理论缺陷 8 项 + 实践缺陷 10 项 + 补充缺口 12 项
- 详见 §3/§4/§5；每一处均给出处置方向，可直接转写为重构任务验收标准（见总计划）。
