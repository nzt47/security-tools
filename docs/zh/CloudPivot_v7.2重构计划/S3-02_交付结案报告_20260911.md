## 4. 遇到的问题与解决方案

### 4.1 问题 1：轨迹派生用例的**参数错位**（实现期实测，已修复）

| 项 | 内容 |
|---|---|
| 现象 | 从同类轨迹生成的用例，`input` 拿到的是**探索前缀行**（`list_dir`）的参数，而非目标能力种子步的参数 |
| 根因 | 清洗会削掉前导噪声/合并相邻重复 ⇒ 清洗后步骤与台账原始行**不同长**，按下标硬对必然错位 |
| 修复 | 改为 `align_concrete_args()`：按**标签贪心对齐**（清洗保留合并重复的首个，与贪心取首个一致） |
| 验证 | `test_alignment_skips_noise_prefix_rows`、`test_concrete_args_are_copied` |

### 4.2 问题 2：同名键被形态归一压成**同一个占位符** ⇒ 两处都绑到第一个值（已修复）

| 项 | 内容 |
|---|---|
| 现象 | 端到端演示中"上游臂把报告写到**被读的文件**上"（`env_files` 1 项 vs 候选 2 项） |
| 根因 | 清洗期把每个具体路径都压成 `${path}`（形态占位符**不编码位次**），而读的 path 与写的 path 恰好同名 ⇒ 只按键名绑定必然张冠李戴 |
| 修复 | ① 用例程序把形态占位符**提升为位次槽**（`${path}` / `${path_2}`，方言仍是 S3-01 的 `${name}`）；② 接口补齐按**位次**取槽（`positional_slot_names`）；③ 该位次记的是**字面量**时直接用字面量、绝不回退裸键 |
| 验证 | `test_complete_params_prefers_positional_slot_over_bare_key`、`test_complete_params_uses_literal_over_bare_key_fallback`；演示复跑 36/36 全过 |

### 4.3 问题 3：S3-01 骨架**只带差异参数** ⇒ 单独不足以构成可执行实现（已修复，含口径披露）

| 项 | 内容 |
|---|---|
| 现象 | 用 `PatternImplementation` 直接回放，候选在 `write_file` 步骤因缺 `path` 触发 `escape_blocked` |
| 根因 | `generalize.infer_parameter_slots` 只对"跨轨迹取值有差异"的键建槽 ⇒ 跨轨迹恒定的字面量/形态参数（如写的 `path=${path}`）**不进骨架** |
| 修复 | `sandbox.complete_params()`：执行前按"**位次对齐 → 同标签 → 用例输入**"补齐工具契约要求的必需参数，补齐来源逐条进 `Observation.filled`（**显式可审**，不是把候选偷偷换成上游程序） |
| 披露 | 这是 S3-01 交付契约的**已知边界**（骨架是"结构 + 差异参数"，不是完整实现）；补齐规则与来源已写入模块文档、通行证与演示输出 |

### 4.4 问题 4：`PatternStep.params` 的**键名是槽名**而非原键名（已修复）

| 项 | 内容 |
|---|---|
| 现象 | 候选的写步骤参数变成 `{cmd_2: "${cmd_2}"}`，工具契约认的是 `cmd` ⇒ 内容被写成空串 |
| 根因 | `service.mine()` 用 `pstep.params[slot.name] = slot.placeholder`，而 `slot.name` 在同名键多次出现时带位次后缀 |
| 修复 | `sandbox.restore_param_key(s)`：按命名规则反向还原，且**仅还原已知参数名**（`my_index_2` 这类业务键保持原样） |
| 验证 | `test_pattern_slot_keys_are_restored`、`test_restore_param_key_keeps_unknown_suffix`、`test_restore_param_keys_keeps_first_on_collision` |

### 4.5 问题 5：把 S3-01 的**描述性**分支条件当执行守卫 ⇒ 条件恒假、该步被永久跳过（已修复）

| 项 | 内容 |
|---|---|
| 现象 | 若把 `PatternStep.condition`（如 ``步骤 `write_file` 缺失``）当条件步守卫，该步在骨架里恒被跳过 ⇒ 候选行为与上游**系统性**不一致 |
| 根因 | 该字段是"**该位次的历史分支条件**"这一**描述性标注**（渲染进 SKILL.md 供人工核对），不是可执行守卫 |
| 修复 | `PatternImplementation(use_conditions=False)` 默认**不当守卫**；需要条件执行须在编译期显式给出 `ProgramStep.condition`（Seed Pack 的 `native_template` 即该通道） |
| 验证 | `test_pattern_description_conditions_are_not_execution_guards`、`test_pattern_use_conditions_is_opt_in`；Seed Pack 的 TDD 用例同时覆盖"执行/跳过"两态 |

### 4.6 问题 6：层②最初按**形态**比对 + 台账基线**量纲不符**（两处方法学缺陷，已修正）

| 项 | 内容 |
|---|---|
| 现象 A | "写对了形态、写错了具体位置"能穿过硬性层（因为路径被归一到 `${path}`） |
| 现象 B | 台账基线（`read_file` 单次调用 **3ms** 墙钟）被直接当作整链 p99 上限 ⇒ 回放实测 **14ms** 被判"p99 倒退"，门**错误拒绝** |
| 根因 A | 形态归一（S2 载荷纪律）掩盖了具体目标差异；且内容层一度只带"路径+摘要" |
| 根因 B | 台账 `duration_ms` = **单次能力调用墙钟**；回放 = **整条任务链模型时钟** ⇒ 量纲与粒度都不同 |
| 修复 A | 层②改为三条硬性检查：两臂**具体目标**逐一相同 + **内容指纹**相同 + 用例契约（**具体值优先、形态容忍**）；形态视图保留在 `detail` 供报告与人工核对 |
| 修复 B | **阈值**统一取同一回放系统内的**上游臂**（双跑同环境 ⇒ 天然可比，也正是 §4.5「p99 ≤ 上游」的本义）；S2-01 台账统计按任务书要求**照实披露**在 `baseline["ledger"]`，并显式标注 `baseline_source` |
| 验证 | `test_side_effect_layer_catches_target_drift`、`..._catches_content_drift`、`test_default_baseline_is_upstream_arm_not_ledger` |
