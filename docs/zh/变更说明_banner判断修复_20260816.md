# 变更说明：Banner 判断修复 + Substring 越界修复（diagnose_ssh）

**日期**: 2026-08-16
**影响文件**:
- `scripts/dev/diagnose_ssh.sh`
- `scripts/dev/diagnose_ssh.ps1`
- `scripts/dev/mock_ssh_server.py`（新增，验证载体）

---

## 1. 背景

在构造 Mock SSH 服务器（`mock_ssh_server.py`）以本地完整演练诊断认证层时发现：即使 Mock 正确返回标准 SSH banner（`SSH-2.0-OpenSSH_mock_9.5`），诊断脚本第 4 层（SSH 服务响应）仍判定 FAIL。追查确认 banner 判断条件本身有误，属历史遗留 bug，导致**任何正常 sshd 都会被误判**，且无法到达第 5 层认证。

## 2. 问题一：Banner 判断前缀错误（220 → SSH-）

### 现象

```
[4/5] SSH 服务响应
  [FAIL] 未收到 SSH banner（22 上非 SSH 服务 / sshd 未运行）
```

### 根因

| 版本 | 修复前 | 问题 |
|---|---|---|
| `diagnose_ssh.sh` | `[[ "$BANNER" == 220* ]]` | `220` 是 **SMTP** 协议响应前缀（RFC 5321），并非 SSH |
| `diagnose_ssh.ps1` | `$banner -match '^220'` | 同上 |

SSH 协议 banner 规范见 **RFC 4253 §4.2**：服务器必须先发送形如 `SSH-2.0-<软件名> <注释>` 的版本标识，前缀固定为 `SSH-1.99-` 或 `SSH-2.0-`。用 `220` 判断必然失配。

### 修复

```bash
# diagnose_ssh.sh（bash 通配模式）
[[ "$BANNER" == SSH-* ]]
```

```powershell
# diagnose_ssh.ps1（正则）
$banner -match '^SSH-'
```

### 影响范围

- 修复前：所有真实 sshd 在第 4 层被误判 FAIL，第 5 层认证逻辑永远无法执行（诊断止步于网络/服务层）。
- 修复后：banner 层正常判定，诊断可继续进入认证层。

## 3. 问题二：PS 版 Substring 越界（ArgumentOutOfRangeException）

### 现象

修复 banner 判断后首次运行，banner 层虽然 PASS，但伴随异常：

```
[PASS] sshd responds: 使用“2”个参数调用“Substring”时发生异常:“索引和长度必须引用该字符串内的位置。
参数名: length”
```

### 根因

```powershell
# 修复前（L95 附近）
($banner -split "`r?`n")[0].Substring(0, [Math]::Min(60, $banner.Length))
```

`$banner` 为完整响应（含行尾 `\r\n`），长度 29；split 后的首行（仅 `SSH-2.0-OpenSSH_mock_9.5`）长度 27。`Substring` 的 `length` 用了 **整段 banner 的长度**而非首行长度 → 27 字符的字符串请求截取 29 位，越界抛异常。

### 修复

```powershell
$first = ($banner -split "`r?`n")[0]
$shown = $first.Substring(0, [Math]::Min(60, $first.Length))
Write-Host "  [PASS] sshd responds: $shown"
```

先取首行，`length` 用首行自身长度，避免与行尾换行符长度不一致导致的越界。

## 4. 附带增强：TCP / Banner 步骤前日志打印

两版脚本在第 3 层（TCP 端口）与第 4 层（SSH 服务响应）判定前输出 `[log]` 行，便于定位具体卡在哪一层：

```
[3/5] TCP 端口 2222
  [log] 目标 127.0.0.1:2222；方法 /dev/tcp 探测；超时 5s
  [log] 探测命令: timeout 5 bash -c "echo >/dev/tcp/127.0.0.1/2222"
  [log] 若此层卡住：主机不可达 / 防火墙拦截 / 端口未监听
```

PS 版对应输出：目标/方法（`TcpClient.ConnectAsync`）/超时 3s/卡住原因。

## 5. 验证结果

用 `mock_ssh_server.py` 三模式在沙盒 `127.0.0.1:2222` 实测（PS 版，TcpClient 不受沙盒 bash 网络隔离影响）：

| Mock 模式 | 层 3 TCP | 层 4 Banner | 层 5 认证 |
|---|---|---|---|
| 默认（banner + 断开） | PASS | **PASS**（SSH-2.0-OpenSSH_mock_9.5，无 Substring 报错） | 走到并归类异常（exit=255，Mock 主动断握手，预期） |
| `--no-banner`（非 SSH 服务） | PASS | **FAIL**（no SSH banner） | 仍走到（kex_exchange_identification） |
| `--auth-deny` | PASS | PASS | 同默认（见下"边界"） |

### 边界说明

- `--auth-deny` 纯文本无法命中 ssh 的 `Permission denied` 分支：SSH 协议在 KEX 阶段只认二进制协议消息，纯文本被 ssh 归类为协议错误（`ssh_dispatch_run_fatal`）。完整模拟认证拒绝需真实 sshd 或 paramiko 类库。
- 沙盒隔离 bash 子进程 `/dev/tcp`（sh 版第 3/4 层连本机 Mock 端口报 FAIL，但 `ssh.exe` / `python socket` 正常），真实 Git Bash/真机无此限制；速查表已补充对应排查条目。

## 6. 回归影响

- `diagnose_ssh.sh` / `diagnose_ssh.ps1` 参数接口（`--host/--port/--user/--key`）未变，`local_ops.ps1 diag` 入口不受影响。
- banner 层从"永远 FAIL"修正为"按 SSH-2.0 前缀判定"，是行为修正，非接口变更。
