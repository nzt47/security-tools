# 技能索引缓存 L3 TTL 行为边界与规避方案

- **日期**: 2026-08-06
- **模块**: `agent/skills_mgmt/index_cache.py`（SkillIndexCache，构造参数 `validate_interval`）
- **关联文档**: [技能索引缓存失效策略与并发排查指南_20260806.md](./技能索引缓存失效策略与并发排查指南_20260806.md)
- **压测基线**: `data/bench_skill_cache_result.json`（`--ttl 60`，1000 技能）

---

## 1. 背景

L3 TTL（Time-To-Live 校验窗口）在 [get_all_metadata](../../agent/skills_mgmt/index_cache.py) 上增加**快路径**：
窗口内（自上次全量校验/重建起 `validate_interval` 秒内）跳过全量增量校验，直接返回内存缓存。

实测收益（1000 技能，`validate_interval=60`）：

| 场景 | L1+L2 后 | L3 开启 | 变化 |
|---|---|---|---|
| 窗口内重复 `get_all_metadata` | 236.7ms | **0.002ms** | 12 万倍 |
| 增量变更场景（改 10 / 删 5） | 253.8 / 233.4ms | **4.8 / 3.7ms** | **-98%** |

代价是**"外部直接修改文件"在窗口内不可见**（可见延迟 = 窗口长度）。
本文档说明该边界的具体行为与规避方案。

---

## 2. 行为边界（谁可见 / 谁不可见）

### 2.1 不可见：窗口内**外部直接修改**技能文件

绕过 `SkillFileStore` 写操作、直接在 `skills_repo/<id>/skill.md` 上改文件的场景：

```text
t0         t0+10s（窗口）          t0+10s 之后
├──────────┤                      │
│ 修改1 修改2 修改3               │  首次 get_all_metadata
│ （全部走快路径，不可见）        │  → 全量校验，吸收全部累积修改
└────────────────────────────────┘
```

- 窗口内多次修改**累积**，过期后**一次校验全部吸收**（只解析最终状态，不追溯历史）
- 缓存返回的 `meta` 是**窗口起始时的快照**（最后校验时刻），不是实时值

### 2.2 可见：`file_store` 写操作（不受 TTL 影响）

`fs.create / update_meta / delete` 之后调用 `cache.invalidate(skill_id)`：
- **单技能即时失效**：窗口内 `get_metadata(skill_id)` 仍走 stat+hash 校验回源，`get_all_metadata` 返回的 dict 中该技能已被移除
- 这是【不易】不变量：**TTL 只遮蔽"外部直接改文件"，不遮蔽业务写入路径**

### 2.3 可见：单技能 `get_metadata`（不受 TTL 影响）

`get_metadata` 每次做 `mtime + size + hash` 校验，命中才返回缓存——**与 TTL 无关**，始终反映磁盘最新状态（该技能存在时）。

### 2.4 不受 TTL 影响的路径（汇总）

| 调用 | TTL 影响 | 说明 |
|---|---|---|
| `get_metadata(id)` 单技能 | **无** | 每次 stat+size+hash 校验回源 |
| `file_store` create/update/delete | **无** | invalidate 即时失效 |
| `get_all_metadata(refresh=True)` | **无** | 强制全量重建，绕过窗口 |
| 首次 `get_all_metadata`（冷启动） | **无** | 基线未建立（`_last_validate_ts=0`），必校验一次 |
| 窗口内重复 `get_all_metadata` | **有** | 快路径，外部修改不可见 |

### 2.5 基线刷新时机

`_last_validate_ts` 仅在两类时刻刷新：
1. **全量重建**（`_rebuild_locked` 末尾：冷启动懒加载 / refresh=True）
2. **窗口外校验完成**（`_validate_all` 返回后）

窗口内的快路径**不刷新**基线——这正是"窗口内修改不可见"的机制：
修改在窗口内被跳过，过期后一次校验吸收，基线前移，形成新的窗口。

## 3. 规避方案

按推荐优先级排序：

### 方案 A：业务写入走 `file_store`（推荐）

所有技能变更（创建/更新/删除）通过 `SkillFileStore` 的写接口完成：
`invalidate` 保证即时失效，**TTL 完全无感**。适用于"应用内管理技能"的主流程。

```python
fs = SkillFileStore(repo_path=...)
cache = SkillIndexCache(fs, validate_interval=60.0)  # 放心开启
fs.update_meta("alpha", {"name": "new"})   # 立即生效，不受窗口影响
```

### 方案 B：需要立即可见时 `refresh=True`

外部修改后需要马上读最新全量索引，显式强制重建（成本 = 全量解析，1000 技能 ~1s）：

```python
index = cache.get_all_metadata(refresh=True)
```

### 方案 C：调小 `validate_interval`

缩短窗口 = 缩短可见延迟，但增加校验频率（L1 成本 ~250ms/1000 技能）：

```python
cache = SkillIndexCache(fs, validate_interval=2.0)  # 可见延迟 ≤ 2s
```

### 方案 D：关闭 TTL

`validate_interval=0`（默认值）即回到 L1+L2 行为——每次调用都校验。一致性最强，性能最差。

### 方案 E：事件驱动（L4，未来）

Watchdog 监听技能目录，变更事件精确失效 O(k)，在"实时可见 + 无全量校验"间兼得。
技能上万且外部修改频繁时启用（参考 `agent/memory/file_watcher.py`）。

---

## 4. 决策建议

| 场景 | 建议 |
|---|---|
| 技能由应用内 `file_store` 管理 | 开 TTL（A），窗口可设较大（如 60s） |
| 技能被外部脚本/部署直接写文件 | 不开 TTL（D）或窗口调小（C）；必要时 B |
| 混合（应用写 + 外部写） | 开 TTL + 外部写后手动 `refresh=True`（A+B） |
| 实时性要求极高 | 关闭 TTL，评估 L4 事件驱动 |

**铁律**：【不易】TTL 遮蔽的是"外部直接改文件的可见性"，**绝不遮蔽 `file_store` 写路径与单技能 `get_metadata` 的失效语义**。引入任何绕过 TTL 的新路径时，须先确认这两个不变量不被破坏。
