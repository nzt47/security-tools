# 云枢 · 外部智能体集成与原生工具能力对齐方案

> 记录日期：2026-09-16　｜　状态：部分已落地（见 §6）

## 1. 适用范围与三种集成方向

评估对象是**本仓的云枢**（`DigitalLife` 智能体系统），不是同名的低代码平台。

"把 Trae / Claude Code / DSH 集成进云枢"必须拆成三个方向，混谈会得出错误结论：

| 方向 | 含义 | 前提 |
|---|---|---|
| **A. 云枢 → 外部工具** | 云枢编排它们干活 | 对方有程序化入口（CLI/HTTP/SDK） |
| **B. 外部工具 → 云枢** | 它们干活时调用云枢能力 | 云枢必须暴露 **MCP server** 或受控 HTTP API |
| **C. 作为模型后端** | 只借模型，不借 Agent | OpenAI 兼容协议 + `base_url` |

### 兼容性速评（★ 越多越省事）

| 工具 | A | B | C | 关键事实 |
|---|---|---|---|---|
| **DSH** | ★★★★ | ★★ | — | `dsh --profile headless "<任务>"` 一次一答、stdout 纯文本、exit 0/1（**实测可用**）；另有 `127.0.0.1:3080` 的 HTTP RPC（约 50 端点）做长会话 |
| **Claude** | ★★ | ★★ | ★★★★ | 技能侧**已通**（见 §3.5）；CLI 需修复安装或改走 Agent SDK |
| **Trae** | ★ | ★★★ | ★ | GUI 产品，无 CLI/无程序化入口；官方支持 MCP 客户端 + Rules ⇒ 只能"它来消费云枢" |

## 3. 三条接入通则（血泪总结，违反必踩坑）

### 3.1 新增一个"能被模型调用"的工具，必须同时做三件事

1. **Python 注册**：`agent/tools/<mod>.py` 里 `@_tools.register(...)` + 在 `lifecycle_manager._register_builtin_tools()` 挂上；
2. **分类表 YAML**：`data/tool_definitions/<tool>.yaml`（`category` 必须是既有 11 个分类之一）。

   **为什么必需**：`agent/tool_router.py:163-229` 的 `TOOL_CATEGORIES` **从该目录派生**（YAML 才是数据源，代码内默认值只是兜底）；`get_tools_for_input()`（`tool_router.py:430`）**只返回命中分类里列出的工具**。
3. **关键词**：`data/tool_router_keywords.json` 对应分类里加**高精度**词。

   **为什么必需（反直觉）**：`classify_user_input()` 以 `matched = {"core"}` **起步**（`tool_router.py:413`，"core 始终包含"），而 core 恒有 5 个工具 ⇒ **路由结果永不为空** ⇒ `orchestrator.py:3399-3401` 的"路由非空才收窄白名单"**永远会收窄**。所以"没命中分类时白名单保持全量、工具仍可见"这条兜底**根本不存在**——关键词是**可见性开关**，不是加分项。

> 只做第 1 步的后果：工具**注册成功、日志正常、但模型永远不调用**——零报错的静默失败。

### 3.2 新增工具后必须同步的硬编码基线

- `tests/unit/test_tool_definitions_yaml.py`：YAML 数 == Python `@register` 数（写死在断言里）、`_build_category_map` 计数（写死）；该文件还断言"迁移脚本幂等"（跑一遍所有 YAML 的 sha256 必须不变）。
- **YAML 必须由 `python scripts/migrate_tools_to_yaml.py` 生成，不要手写**——手写与脚本产出的任何字节差异都会让幂等测试失败。
- 之后跑 `python scripts/sync_tool_index.py` 刷新 `data/tool_index.json`。
- ⚠️ `scripts/migrate_tools_to_yaml.py` 的 `_build_category_map()` 已改为"默认表兜底 + YAML 覆盖"：否则新工具**此刻还没有 YAML**，会被写成 `uncategorized` ⇒ 永远进不了路由（先有鸡先有蛋）。

### 3.3 强制点必须落在**唯一汇聚点**

`agent/tools/__init__.py` 的 `call()` 是所有工具调用的唯一汇聚点。只把闸门插在 `agent/tool_calling.py::_execute_safe` 会漏掉 **orchestrator 的两条直连** `tools.call(...)`（`orchestrator.py:3519`、`:3557`）——闸门会装在半扇门上。

另注：`_execute_safe` 的重试是**异常驱动**的（`tool_calling.py:877-889` 的 `return result` 在 try 体内无条件执行，只有 `except` 才 `continue`），所以"闸门拒绝是返回 dict"不会被重试 3 次，无需额外短路。

## 4. 各工具的具体接入路径

### 4.1 DSH（最短路径）

- **一次性任务**：`dsh --profile headless "<任务文本>"` → stdout 纯文本 + exit 0/1。**限制**：无 `--output-format json`、无 stdin 管道、无多轮、每次冷启动。
- **长会话/多轮**：`127.0.0.1:3080` 的 HTTP RPC。信封 `{"type":"client-request","rpcId":…,"method":…,"payload":{…}}`，`POST /api/<method>`；`session.prompt` **只回 `{accepted:true}`，不含答案**，需轮询 `session.history` 或订阅 WebSocket `/api/events.mux`（无 SSE 兜底）。
- **两个入口属于不同 profile**：`dsh-host-apiproxy` **不挂载**在 headless profile ⇒ 一次性和长会话是两条路，不能混用。
- **无鉴权**：只有 Host 头信任围栏；`~/.dsh/settings.yaml` 里 `permission.defaultPreset: danger-full-access` ⇒ 它内部无审批，**云枢侧审批是唯一闸门**。
- **反向（B 方向）**：DSH 是纯 MCP **客户端**（`@deepseek-ai/dsh-mcp-client`），要在 `$DSH_HOME/cordis.patch.yml`（机器级跨 profile 补丁层）加一行才能消费云枢的 MCP server。
- 轨迹归档可用 `GET /api/session.export?sessionId=…` 取 ZIP（比解析 zstd JSONL 省事）。

### 4.2 Claude

- **技能面已通、零开发**：`agent/extensions/skills_installer.py:41` 直指 `~/.claude/skills`；`file_store.py:236 from_agentskills_io` 做双向映射。**能写成技能的，就不要写成工具。**
- 注意：技能走的是 front matter **白名单 18 字段**（`file_store.py:74-81`），**不含** `risk_level/data_class/requires_approval` ⇒ 技能不受 ToolDescriptor 治理不变量约束。**低风险提示词类能力走技能；高危执行类必须走工具 + descriptor。**
- Agent 能力（自主改代码）需 CLI headless 或 Agent SDK；本机 `claude` 命令的目标二进制缺失，属环境问题。

### 4.3 Trae

无程序化入口，**不要尝试驱动它**。正确做法是**新建云枢 MCP server**，由 Trae 作为 MCP 客户端接入；Trae 的 Rules/自定义 Agent 描述走 `/api/workflow-learning/convert-external-skill` 转成云枢技能。

### 4.4 云枢 MCP server（stdio，B 方向的落点，**已落地**）

**启动命令**（零第三方依赖，不用官方 `mcp` SDK；手写口径与 `mcp_services/multi_search_engine.py` 一致）：

```powershell
python mcp_services/yunshu_mcp_server.py
```

stdin 逐行读 JSON-RPC、stdout 逐行写 JSON-RPC（一行一帧 + 立即 flush）；**日志全部走 stderr**，且导入期与运行期把 `sys.stdout` 临时替换为 `sys.stderr` ⇒ 除协议帧外任何内容都不会落到 stdout（stdio MCP 最易翻车的地方）。实现方法：`initialize` / `tools/list` / `tools/call` / `ping`，未知方法返回 `-32601`；`resources` / `prompts` **未实现，故 `capabilities` 里不声明**（声明了却拒绝会让客户端误判能力）。

**默认暴露的工具（只读五件套）**：`read_file`、`list_directory`、`get_file_info`、`search_files`、`grep`。
写入类与执行类（`write_file` / `edit` / `shell_execute` / `run_program` / `software_install` / `delegate` / `todo_write`）**默认不暴露、不出现在 `tools/list` 里**——MCP 客户端是外部进程，默认授权它改宿主文件或执行命令是不可接受的默认值。所有调用都经 `agent.tools.call()`，因而自动受 `agent/tool_gate.py` 的集中式闸门约束。

**放宽方式与风险**：环境变量 `CP_MCP_SERVER_TOOLS`（逗号分隔的**真实注册名**）覆盖默认清单：

```powershell
$env:CP_MCP_SERVER_TOOLS = "read_file,grep,write_file"   # 名字必须真实存在
python mcp_services/yunshu_mcp_server.py
```

> ⚠️ **放开写入/执行类 = 允许外部 MCP 客户端改动/执行宿主**（无二次确认、无人在回路）。
> 含未注册的名字 ⇒ **启动即拒绝**（stderr 报错 + 退出码 2），绝不静默忽略。
> 该 server **不做鉴权**（stdio 由客户端进程自己拉起，信任边界在客户端侧）⇒ **不要把它的 stdio 暴露到网络**
> （如 socat / 端口转发到 TCP），stdio 之外没有任何保护；要远程暴露请另建带鉴权的 HTTP 入口。

**DSH 侧**（`$DSH_HOME/cordis.patch.yml` 的机器级补丁层；`serverName` 需匹配 `[A-Za-z0-9_-]{1,32}`）：

```yaml
- id: mcp-yunshu
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: yunshu
    transport: stdio
    command: python
    args: ['C:\Users\Administrator\agent\mcp_services\yunshu_mcp_server.py']
    cwd: 'C:\Users\Administrator\agent'
    failOnStartupError: true   # 缺省 false：连接失败只记日志，模型会静默少掉这些工具
```

模型看到的工具名是 `mcp__yunshu__read_file`（`mcp__<serverName>__<rawName>`）。**实测**：DSH 内置的 `@modelcontextprotocol/sdk` 1.30.0 stdio 客户端可完成 initialize → tools/list（恰好五件套）→ tools/call。

**Trae 侧**（其 MCP 配置里的 `mcpServers` 条目，字段名与 Claude Code 同形）：

```json
{
  "mcpServers": {
    "yunshu": {
      "command": "python",
      "args": ["C:\\Users\\Administrator\\agent\\mcp_services\\yunshu_mcp_server.py"],
      "cwd": "C:\\Users\\Administrator\\agent"
    }
  }
}
```

两侧共用**同一个 stdio 入口**：调整暴露清单只改环境变量，不必改客户端配置。

## 5. 与外部智能体相关的安全强制点

### 5.1 已核实的三层权限架构

`PermissionGateway.check()`（`agent/permission_system.py:620`）＝ 层0 策略即代码（默认关闭）→ RBAC → ABAC → 正则兜底。

**⚠️ 不能把 RBAC 白名单裸接进工具主链路**：`_check_rbac`（`:832-876`）是**严格白名单**语义（不在 `allowed_tools` 即拒绝；角色无策略也拒绝），而 `default_role` 是 `guest`、其白名单只有 `["web_search", "read_file"]` ⇒ 实测**74 个工具只放行 2 个（封杀 97.3%）**。（数据修复前策略里的工具名写错，当时是 72 个里只放行 1 个 ≈ 98.6%，连 `read_file` 都不放过；修复只是把"几乎全封"改善成"绝大多数被封"，性质没变。）这是"接入权限"变成"系统瘫痪"的根因，不是保守与否的取舍。

**当前口径**：`agent/tool_gate.py` 采 **fail-open + 显式拒绝**——只强制"显式列入 `roles[*].denied_tools`"与"descriptor 声明 `trust.requires_approval=true`"两类，其余放行；闸门自身故障一律放行（绝不断工具执行）。

**RBAC 严格模式：已做成默认关闭的开关**（`agent/tool_gate.py`，开关 `CP_TOOL_GATE_STRICT`，**不设即零行为变化**）：

- **开启命令**（PowerShell）：`$env:CP_TOOL_GATE_STRICT=1`；可选 `$env:CP_PERMISSION_DEFAULT_ROLE="owner"`（缺省即 `owner`，非法值告警后回退 `owner`）、`$env:CP_PERMISSION_SESSION_SOURCE="cli"`（缺省即 `cli`）。开关只认 `1/true/yes/on`（大小写与两侧空白不敏感），其它取值一律保持 fail-open。
- **开启前必须先确认**：① `default_role` / `CP_PERMISSION_DEFAULT_ROLE` 指向的角色**不是 `guest`**——为此仓库新增了 `owner` 角色（`allowed_tools: ["*"]`、`denied_tools: []`，ABAC 仍生效；`default_role` **仍是 `guest`**，故不开开关时该角色无影响）；② 该角色确实在 `data/permission_policies.json` 的 `roles` 里（角色不存在 ⇒ 直接全量拒绝）；③ 清楚 `session_source` 该报什么——报 `scheduled` 会命中 `scheduled-no-write` / `scheduled-no-edit`。
- **会话来源现在可按调用上下文上报（本次新增，未加任何环境变量）**：`agent/tool_gate.py` 新增 `set_session_source(source)`（返回可 `with` / `reset()` 的句柄）、`current_session_source()`、`reset_session_source(...)`，底层是 `contextvars.ContextVar`、**默认空**。取值优先级（高 → 低）：**调用方显式传入** `check_tool_call(..., session_source=...)` → **上下文变量** → 环境变量 `CP_PERMISSION_SESSION_SOURCE` → 缺省 `cli`（＝改动前的唯一口径）。`agent/task_scheduler.py::run_task` 已在**执行线程内**把来源标为 `scheduled`，并用 `try/finally` 在任何退出路径（成功/异常）还原——**必须写在执行线程内**：`contextvars` **不跨线程继承**，`tick()` 由 daemon 线程 `_run_loop` 调用，在调度线程里设置对执行线程无效；若不还原，后续人机对话的工具调用会被继续当成定时任务来源。
- **⚠️ 行为后果：这两条 ABAC 规则从"摆设"变成"真拦截"**：`scheduled-no-write`（`write_file`）/ `scheduled-no-edit`（`edit`）此前**没有任何生产链路**报 `scheduled`（来源只来自进程级环境变量、默认 `cli`）⇒ 永不触发。接通后，**开启 `CP_TOOL_GATE_STRICT` 时定时任务将无法写文件、无法编辑文件**，拒绝结构为 `blocked=True` / `error_code="PERMISSION_DENIED"`（`read_file` 等读取类工具不受影响）。**不开启严格模式时该上报不产生任何行为变化**（闸门仍是 fail-open，根本不构造 ABAC 上下文）；`_guard_scheduled_command` 走的是 `check_action` 正则层、判定口径**未改动**。守门测试：`tests/unit/test_scheduled_session_source.py`。
- **两个已知副作用**：① `guest` 严格白名单封杀面极大——只放行 74 个真实工具中的 2 个（97.3%）；② ABAC 的 `time_outside` 会让某工具**在一天中的某些时段失效** ⇒ **时段相关的偶发失败**（同一份代码白天全绿、夜里变红）。**当前数据下 ② 已不再发生**：原先唯一的时段规则 `off-hours-shell-restriction`（`shell_execute` + `time_outside ["09:00","18:00"]`）因与所有者作息（**18:00 开始工作**）直接冲突，已从 `abac_rules` **移除**并留档于同文件顶层 `_policy_notes`（含可照抄的恢复片段）；实测修复后严格模式 + `owner` 下 `shell_execute` 放行。**但机制仍在**——任何人把 `time_outside` 规则加回 `abac_rules`，② 立刻回来。配套修复：`_time_in_window` 原先用字符串比较（`start <= now <= end`），`start > end` 时**恒为假**，连"18:00–06:00 这种跨午夜作息"都表达不出来；现已支持跨午夜窗口（`start > end` ⇒ `now >= start or now <= end`），把窗口改成自己的作息即可。
- **回滚方式**：去掉 `CP_TOOL_GATE_STRICT` 环境变量（或置 `0`）。本层不改任何数据文件、不改任何默认值，回滚无残留。

### 5.2 数据侧的坑（已修，并用测试钉死）

`data/permission_policies.json` 曾把工具名写成 `file_read`/`file_write`/`code_runner`/`browser_navigate`/`system_format`/`system_shutdown`，**这些名字在注册表里都不存在** ⇒ ①严格白名单下的静默误杀；②「格式化/关机仅限内网」两条 ABAC 规则**永不触发**（安全约束静默失效）。

现由 `tests/unit/test_permission_policies_consistency.py` 守护（13 用例：工具名必须存在于 `data/tool_definitions/*.yaml`、角色键必须是 `Role` 合法取值、`default_role` 必须已定义、备忘区目标必须未注册且必须写明理由）。

### 5.3 子代理委派的八要素契约

`goal`(①，≥8 字符) / `constraints`(②) / `prior_artifacts`(③) / `prohibitions`(④) / `artifact_format`(⑤) / `budget_tokens`(⑥) / `timeout_seconds`(⑦) / `callback_url`(⑧)。**缺任一即拒，且不得默认补齐**。

CLI 通道契约：`<agent_cli> -p <task_file.json> --output-format json --max-turns N`（`channel.py:254`），输出按 JSONL 解析，四级降级 `jsonl → jsonl_retry → text_extract → E_UPSTREAM_FORMAT`。配置项 `CP_SUBAGENT_AGENT_CLI`（本机未配置 ⇒ 走 `_UnconfiguredExecutor` 优雅报错，不会意外拉起进程）。

**注意**：该 argv 契约是云枢自己定义的（`-p` 收的是 **task file 路径**），Claude Code 的 `-p` 收的是 prompt 文本 ⇒ **任何外部 agent 都要一个薄 shim 做翻译**，这是接 CLI 智能体的统一成本。

### 5.4 三个"现成的高危旁路"（接外部 CLI 前必须处理）

1. `agent/tools/shell_tools.py` 的底层 `execute_shell` 自身无安全检查 —— 但**注册的 `shell_execute` 工具是有防护的**（`agent/tools/system_tools.py:110-136`：critical 拦截、warning 走 `check_action`、检查故障时 **fail-closed**）。**不要绕过工具直接调底层函数。**
2. ~~`agent/task_scheduler.py` 的 `system_command` 分支用 `shell=True` 且**完全无校验**~~ → **已修**：现由 `_guard_scheduled_command` 在 `Popen` **之前**按与 `shell_execute` 相同的口径把关（critical 拦、warning 走 `check_action`、检查不可用时 **fail-closed**）。权限对象优先取注入的 `_yunshu_ref._permission`；**未注入时回退到模块级惰性 `PermissionSystem()`**——不回退就等于留一条无防护的无人值守命令通道。`shell=True` 保留（命令可能含管道/重定向），理由已就地注释。
3. 出域闸门只有一个物理出口 `HttpClient._egress_block`（`agent/web/http_client.py:100-174`）——**外部 CLI 子进程天然不经此路**，只能靠沙箱的 `validate_network` + 剥离代理/凭据环境变量兜底。

### 四个原语的分工

`grep` 找到内容 → `edit` 改对片段 → `delegate` 把子任务交出去 → `todo_write` 让模型看得见"做到哪一步了"。
四者都是"单步做对"之外的**可靠性**原语：长任务真正高频的失败模式不是单步做错，而是**中途跑偏**（忘了前面定下的约束、重做已完成的事、收尾漏项）。

`todo_write` 的两条语义选择（都有理由，改前请先读模块 docstring）：
- **整体替换**而非增量追加：增量语义要求模型精确记住上一版清单才能算差量，记错就发生状态漂移且无法自愈；
- **内存态、按会话隔离、不落盘**：`clean-runtime-noise` 钩子会还原运行时数据噪声，新增数据文件另有维护成本；计划是短期草稿，重启失效可接受。


`apply_config_and_test.py` 防呆的实际意义超出预期：其模板会删掉 `file` 类 17 词 + `memory` 整类 15 词 + `lifetrace` 整类 16 词（**-40 词**）⇒ 修复前跑一次就会**打掉记忆检索路由**且不报错。

### `delegate` 的两条使用须知（实测，非推测）

1. **默认只授予只读工具子集**（`read_file`/`search_files`/`list_directory`/`get_file_info`/`grep`）。
   原因：`SubAgentToolset.build(requested, authorized_capabilities)` 是「申请 ∩ 授权 − 矩阵拒绝」的三重交集，两者皆空 ⇒ 裁剪集为空 ⇒ 子代理**只要声称调用任何工具**，本次委派就整体失败（`agent/subagent/executor.py:555-562`，`E_TOOL_NOT_AUTHORIZED`），工具会退化成"只能纯推理"。写入与 Shell **刻意不在默认内**：子代理声称写文件或执行命令仍会让委派失败。放宽/收紧用环境变量 `CP_SUBAGENT_DEFAULT_TOOLS`（逗号分隔；空串 = 不授予任何工具）。
2. **复合请求下曾被截断掉 → 已修（「关注名单」定向修复）**：`get_tools_for_input` 按分类 priority 升序截断到 `max_tools=25`，而 `async` 的 priority 是 8（`core`0/`web`1/`file`2/`code`3/`system`4/`extension`5/`pdf`6/`software`7/`async`8/`schedule`9）。修复前实测：

   | 输入 | 命中分类 | 截断后 `delegate` 是否可见 |
   |---|---|---|
   | 「把这个调研任务委派给一个子代理去做」 | async, core | ✅（12 个工具） |
   | 「读取文件、搜索内容、执行命令…然后委派子代理汇总」 | async, code, core, file, web | ❌（被截到 25 个） |

   **修法**：`agent/tool_router.py` 新增模块常量 `PINNED_TOOLS = ("delegate",)` + `_restore_pinned_tools()`——截断之后，把**"类别已被关键词命中"却被数量上限丢掉的** pinned 工具**补回结果末尾**；**补回后允许总数略超 `max_tools`**（宁可多一个工具，也不让"委派"这种跨步骤能力在复合请求里凭空消失）。未命中类别的 pinned 工具**不会**被加入（补回不是绕过路由），白名单剔除的也不会复活。实测修复后：同一复合输入 → 26 个（25 + 补回的 `delegate`），并已确认 `delegate` 真的出现在 `get_tools_for_input(...) → get_tool_defs(whitelist=...)` 下发的 `function.name` 集合里。

   **为什么不做全局调优**（两个杠杆都被刻意放弃）：① 把 `async` 的 priority 提到 ≤3 会**挤掉 `code` 的工具**（每一次命中 code 的请求都受影响），且实测**不可靠**——复合输入下 25 的截断点落在 `code` 组内部，`async` 仍可能被丢；② 把 `delegate` 放进 `core` 等于**每轮常驻**约 500–800 token，与输入是否真的需要委派无关。两者都改变**每一轮**请求的 schema 与 token 成本，而关注名单只影响"本来就被类别命中、却又被挤掉"的那部分输入。守门测试：`tests/unit/test_tool_router_pinned.py`。
