# 云枢 · 外部智能体集成与原生工具能力对齐方案

> 记录日期：2026-09-16　｜　状态：部分已落地（见 §6）

## 1. 适用范围与三种集成方向

评估对象是**本仓的云枢**（`DigitalLife` 智能体系统），不是同名的低代码平台。

"把 Trae / Claude Code / DSH 集成进云枢"必须拆成三个方向，混谈会得出错误结论：

| 方向 | 含义 | 前提 |
|---|---|---|
| **A. 云枢 → 外部工具** | 云枢编排它们干活 | 对方有程序化入口（CLI/HTTP/SDK） |
| **B. 外部工具 → 云枢** | 它们干活时调用云枢能力 | 云枢必须暴露 **MCP server** 或受控 HTTP API |
| **C. 作为模型后端** | 只借模型，不借 Agent | OpenAI 兼容协议 + `base_url` |

### 兼容性速评（★ 越多越省事）

| 工具 | A | B | C | 关键事实 |
|---|---|---|---|---|
| **DSH** | ★★★★ | ★★ | — | `dsh --profile headless "<任务>"` 一次一答、stdout 纯文本、exit 0/1（**实测可用**）；另有 `127.0.0.1:3080` 的 HTTP RPC（约 50 端点）做长会话 |
| **Claude** | ★★ | ★★ | ★★★★ | 技能侧**已通**（见 §3.5）；CLI 需修复安装或改走 Agent SDK |
| **Trae** | ★ | ★★★ | ★ | GUI 产品，无 CLI/无程序化入口；官方支持 MCP 客户端 + Rules ⇒ 只能"它来消费云枢" |

## 3. 三条接入通则（血泪总结，违反必踩坑）

### 3.1 新增一个"能被模型调用"的工具，必须同时做三件事

1. **Python 注册**：`agent/tools/<mod>.py` 里 `@_tools.register(...)` + 在 `lifecycle_manager._register_builtin_tools()` 挂上；
2. **分类表 YAML**：`data/tool_definitions/<tool>.yaml`（`category` 必须是既有 11 个分类之一）。

   **为什么必需**：`agent/tool_router.py:162-228` 的 `TOOL_CATEGORIES` **从该目录派生**（YAML 才是数据源，代码内默认值只是兜底）；`get_tools_for_input()`（`tool_router.py:405`）**只返回命中分类里列出的工具**。
3. **关键词**：`data/tool_router_keywords.json` 对应分类里加**高精度**词。

   **为什么必需（反直觉）**：`classify_user_input()` 以 `matched = {"core"}` **起步**（`tool_router.py:392`，"core 始终包含"），而 core 恒有 5 个工具 ⇒ **路由结果永不为空** ⇒ `orchestrator.py:3399-3401` 的"路由非空才收窄白名单"**永远会收窄**。所以"没命中分类时白名单保持全量、工具仍可见"这条兜底**根本不存在**——关键词是**可见性开关**，不是加分项。

> 只做第 1 步的后果：工具**注册成功、日志正常、但模型永远不调用**——零报错的静默失败。

### 3.2 新增工具后必须同步的硬编码基线

- `tests/unit/test_tool_definitions_yaml.py`：YAML 数 == Python `@register` 数（写死在断言里）、`_build_category_map` 计数（写死）；该文件还断言"迁移脚本幂等"（跑一遍所有 YAML 的 sha256 必须不变）。
- **YAML 必须由 `python scripts/migrate_tools_to_yaml.py` 生成，不要手写**——手写与脚本产出的任何字节差异都会让幂等测试失败。
- 之后跑 `python scripts/sync_tool_index.py` 刷新 `data/tool_index.json`。
- ⚠️ `scripts/migrate_tools_to_yaml.py` 的 `_build_category_map()` 已改为"默认表兜底 + YAML 覆盖"：否则新工具**此刻还没有 YAML**，会被写成 `uncategorized` ⇒ 永远进不了路由（先有鸡先有蛋）。

### 3.3 强制点必须落在**唯一汇聚点**

`agent/tools/__init__.py` 的 `call()` 是所有工具调用的唯一汇聚点。只把闸门插在 `agent/tool_calling.py::_execute_safe` 会漏掉 **orchestrator 的两条直连** `tools.call(...)`（`orchestrator.py:3519`、`:3557`）——闸门会装在半扇门上。

另注：`_execute_safe` 的重试是**异常驱动**的（`tool_calling.py:877-889` 的 `return result` 在 try 体内无条件执行，只有 `except` 才 `continue`），所以"闸门拒绝是返回 dict"不会被重试 3 次，无需额外短路。

## 4. 各工具的具体接入路径

### 4.1 DSH（最短路径）

- **一次性任务**：`dsh --profile headless "<任务文本>"` → stdout 纯文本 + exit 0/1。**限制**：无 `--output-format json`、无 stdin 管道、无多轮、每次冷启动。
- **长会话/多轮**：`127.0.0.1:3080` 的 HTTP RPC。信封 `{"type":"client-request","rpcId":…,"method":…,"payload":{…}}`，`POST /api/<method>`；`session.prompt` **只回 `{accepted:true}`，不含答案**，需轮询 `session.history` 或订阅 WebSocket `/api/events.mux`（无 SSE 兜底）。
- **两个入口属于不同 profile**：`dsh-host-apiproxy` **不挂载**在 headless profile ⇒ 一次性和长会话是两条路，不能混用。
- **无鉴权**：只有 Host 头信任围栏；`~/.dsh/settings.yaml` 里 `permission.defaultPreset: danger-full-access` ⇒ 它内部无审批，**云枢侧审批是唯一闸门**。
- **反向（B 方向）**：DSH 是纯 MCP **客户端**（`@deepseek-ai/dsh-mcp-client`），要在 `$DSH_HOME/cordis.patch.yml`（机器级跨 profile 补丁层）加一行才能消费云枢的 MCP server。
- 轨迹归档可用 `GET /api/session.export?sessionId=…` 取 ZIP（比解析 zstd JSONL 省事）。

### 4.2 Claude

- **技能面已通、零开发**：`agent/extensions/skills_installer.py:41` 直指 `~/.claude/skills`；`file_store.py:236 from_agentskills_io` 做双向映射。**能写成技能的，就不要写成工具。**
- 注意：技能走的是 front matter **白名单 18 字段**（`file_store.py:74-81`），**不含** `risk_level/data_class/requires_approval` ⇒ 技能不受 ToolDescriptor 治理不变量约束。**低风险提示词类能力走技能；高危执行类必须走工具 + descriptor。**
- Agent 能力（自主改代码）需 CLI headless 或 Agent SDK；本机 `claude` 命令的目标二进制缺失，属环境问题。

### 4.3 Trae

无程序化入口，**不要尝试驱动它**。正确做法是**新建云枢 MCP server**，由 Trae 作为 MCP 客户端接入；Trae 的 Rules/自定义 Agent 描述走 `/api/workflow-learning/convert-external-skill` 转成云枢技能。

## 5. 与外部智能体相关的安全强制点

### 5.1 已核实的三层权限架构

`PermissionGateway.check()`（`agent/permission_system.py:611`）＝ 层0 策略即代码（默认关闭）→ RBAC → ABAC → 正则兜底。

**⚠️ 不能把 RBAC 白名单裸接进工具主链路**：`_check_rbac`（`:823-867`）是**严格白名单**语义（不在 `allowed_tools` 即拒绝；角色无策略也拒绝），而 `default_role` 是 `guest`、其白名单只写了不存在的名字 ⇒ 实测**会封杀 72 个工具中的 71 个（98.6%）**，连 `read_file` 都不放过。这是"接入权限"变成"系统瘫痪"的根因，不是保守与否的取舍。

**当前口径**：`agent/tool_gate.py` 采 **fail-open + 显式拒绝**——只强制"显式列入 `roles[*].denied_tools`"与"descriptor 声明 `trust.requires_approval=true`"两类，其余放行；闸门自身故障一律放行（绝不断工具执行）。

### 5.2 数据侧的坑（已修，并用测试钉死）

`data/permission_policies.json` 曾把工具名写成 `file_read`/`file_write`/`code_runner`/`browser_navigate`/`system_format`/`system_shutdown`，**这些名字在注册表里都不存在** ⇒ ①严格白名单下的静默误杀；②「格式化/关机仅限内网」两条 ABAC 规则**永不触发**（安全约束静默失效）。

现由 `tests/unit/test_permission_policies_consistency.py` 守护（13 用例：工具名必须存在于 `data/tool_definitions/*.yaml`、角色键必须是 `Role` 合法取值、`default_role` 必须已定义、备忘区目标必须未注册且必须写明理由）。

### 5.3 子代理委派的八要素契约

`goal`(①，≥8 字符) / `constraints`(②) / `prior_artifacts`(③) / `prohibitions`(④) / `artifact_format`(⑤) / `budget_tokens`(⑥) / `timeout_seconds`(⑦) / `callback_url`(⑧)。**缺任一即拒，且不得默认补齐**。

CLI 通道契约：`<agent_cli> -p <task_file.json> --output-format json --max-turns N`（`channel.py:254`），输出按 JSONL 解析，四级降级 `jsonl → jsonl_retry → text_extract → E_UPSTREAM_FORMAT`。配置项 `CP_SUBAGENT_AGENT_CLI`（本机未配置 ⇒ 走 `_UnconfiguredExecutor` 优雅报错，不会意外拉起进程）。

**注意**：该 argv 契约是云枢自己定义的（`-p` 收的是 **task file 路径**），Claude Code 的 `-p` 收的是 prompt 文本 ⇒ **任何外部 agent 都要一个薄 shim 做翻译**，这是接 CLI 智能体的统一成本。

### 5.4 三个"现成的高危旁路"（接外部 CLI 前必须处理）

1. `agent/tools/shell_tools.py` 的底层 `execute_shell` 自身无安全检查 —— 但**注册的 `shell_execute` 工具是有防护的**（`agent/tools/system_tools.py:110-136`：critical 拦截、warning 走 `check_action`、检查故障时 **fail-closed**）。**不要绕过工具直接调底层函数。**
2. ~~`agent/task_scheduler.py` 的 `system_command` 分支用 `shell=True` 且**完全无校验**~~ → **已修**：现由 `_guard_scheduled_command` 在 `Popen` **之前**按与 `shell_execute` 相同的口径把关（critical 拦、warning 走 `check_action`、检查不可用时 **fail-closed**）。权限对象优先取注入的 `_yunshu_ref._permission`；**未注入时回退到模块级惰性 `PermissionSystem()`**——不回退就等于留一条无防护的无人值守命令通道。`shell=True` 保留（命令可能含管道/重定向），理由已就地注释。
3. 出域闸门只有一个物理出口 `HttpClient._egress_block`（`agent/web/http_client.py:100-174`）——**外部 CLI 子进程天然不经此路**，只能靠沙箱的 `validate_network` + 剥离代理/凭据环境变量兜底。

### `delegate` 的两条使用须知（实测，非推测）

1. **默认只授予只读工具子集**（`read_file`/`search_files`/`list_directory`/`get_file_info`/`grep`）。
   原因：`SubAgentToolset.build(requested, authorized_capabilities)` 是「申请 ∩ 授权 − 矩阵拒绝」的三重交集，两者皆空 ⇒ 裁剪集为空 ⇒ 子代理**只要声称调用任何工具**，本次委派就整体失败（`agent/subagent/executor.py:555-562`，`E_TOOL_NOT_AUTHORIZED`），工具会退化成"只能纯推理"。写入与 Shell **刻意不在默认内**：子代理声称写文件或执行命令仍会让委派失败。放宽/收紧用环境变量 `CP_SUBAGENT_DEFAULT_TOOLS`（逗号分隔；空串 = 不授予任何工具）。
2. **复合请求下可能被截断掉**（实测）：`get_tools_for_input` 按分类 priority 升序截断到 `max_tools=25`，而 `async` 的 priority 是 8（`core`0/`web`1/`file`2/`code`3/`system`4/`extension`5/`pdf`6/`software`7/`async`8/`schedule`9）。

   | 输入 | 命中分类 | 截断后 `delegate` 是否可见 |
   |---|---|---|
   | 「把这个调研任务委派给一个子代理去做」 | async, core | ✅（11 个工具） |
   | 「读取文件、搜索内容、执行命令…然后委派子代理汇总」 | async, code, core, file, web | ❌（被截到 25 个） |

   即：**单一委派意图没问题，复合请求会被挤出**。两个可选杠杆（都属全局调优，未擅自采用）：把 `async` 的 priority 提到 ≤3（会挤掉 `code` 的工具、影响每轮 schema），或把 `delegate` 放进 `core`（`always=True`，每轮常驻约 500–800 token）。
