# 云枢系统前端可视化与干预方案（2026-08-16）

> 前置依赖：《云枢系统功能模块审计报告_20260816.md》（已确认模块清单、层级关系、现有状态/指标/干预 API 盘点）。
> 本方案设计目标：在**不改动既有模块内部实现**的前提下，新增「统一拓扑聚合 API + 前端拓扑视图 + 干预操作面板」，实现云枢功能模块的结构关系、运行状态、关键指标可视化展示与实时干预。

---

## 一、设计目标与原则

### 1.1 目标
1. **结构可视化**：以拓扑图直观展示 6 大功能域 → 子模块 → 核心组件的层级关系与依赖关联。
2. **状态可视化**：每个节点实时呈现运行状态（健康/警告/故障/离线/未启用）与关键指标（健康分、在线数、调用量等）。
3. **实时干预**：在节点上提供上下文操作入口（启停/切换/重载/执行/紧急），危险操作二次确认 + 操作审计留痕。

### 1.2 设计原则（三易对齐）
- **【不易】** 不修改任何既有模块实现；复用现有 50+ 状态/干预 API；安全边界（权限系统、紧急停止）只做前置包装，不绕过。
- **【变易】** 拓扑结构由**模块注册表**（JSON 数据驱动）描述，新增模块只需注册即可自动上图；状态采集器按需扩展。
- **【简易】** 前端零新依赖（原生 JS + CSS，遵循现有主控台模式）；聚合层薄适配，不做过度抽象。

## 二、总体架构（数据流）

```
┌──────────┐   GET /api/modules/topology（聚合）    ┌─────────────────┐
│ 前端拓扑  │ ◄─────────────────────────────────── │ 模块聚合服务      │
│ 视图      │                                      │ modules_api.py   │
│ (index   │   POST /api/modules/<id>/actions      │ (新增, 薄适配层) │
│  .html)  │ ────────────────────────────────────► │                  │
└──────────┘                                      └────────┬────────┘
                                                           │ 读: 复用现有状态源
                                                           ▼
                  ┌─────────────────────────────────────────────────┐
                  │ 状态源(只读)                                       │
                  │ /api/health/*  /api/sensors  /api/status        │
                  │ /api/panorama  /api/heartbeat  /api/tools/health│
                  │ /api/scheduler/tasks  /api/permission/status    │
                  │ /api/memory/overview  /api/llm/instances  ...    │
                  └─────────────────────────────────────────────────┘
                                                           │ 写: 调用既有干预 API
                                                           ▼
                  ┌─────────────────────────────────────────────────┐
                  │ 干预适配(动作映射表)                               │
                  │ toggle/restart/execute/emergency → 既有 API      │
                  │ + 危险分级 + 二次确认 + 操作审计(log_system)       │
                  └─────────────────────────────────────────────────┘
```

**核心思想**：聚合服务是"只读状态采集 + 写操作适配"两层，全部落在 `app_server.py` 内部新增 Blueprint，**不动既有路由与模块**。

## 三、模块拓扑可视化设计

### 3.1 拓扑结构数据模型（模块注册表）

采用 JSON 清单（`agent/modules_registry.py` 内常量或 `configs/modules.json`），描述层级与节点元数据：

```json
{
  "domains": [
    {
      "domain_id": "perception",
      "domain_name": "感知层",
      "icon": "👁",
      "children": [
        {
          "module_id": "sensor.registry",
          "name": "传感器注册表",
          "path": "sensor/registry.py",
          "type": "service",
          "status_source": "api:/api/sensors",
          "metrics": ["sensor_on", "sensor_total"],
          "actions": ["reload", "disable"]
        }
      ]
    }
  ]
}
```

字段说明：
- `domain_id`：域标识（perception/cognitive/memory/action/service/ops）。
- `module_id`：模块唯一 ID（域.子域.名称），供状态聚合与干预路由定位。
- `status_source`：该模块状态从哪个现有 API 获取（聚合器按声明采集）。
- `metrics`：该节点要展示的关键指标键。
- `actions`：该节点允许的干预操作类型。

### 3.2 拓扑图呈现

- **形态**：分层树状拓扑（六域横向分组，域内纵向层级），支持折叠/展开；或力导向图（依赖关系可视化），默认采用**树状**（简单清晰，符合简易原则）。
- **节点卡片**：
  - 图标 + 模块名 + 状态色标圆点；
  - 状态色标：`绿=健康`、`黄=警告`、`红=故障`、`灰=离线/未启动`、`蓝=未启用`；
  - 关键指标徽标（如 `3/5 在线`、`健康 0.92`、`CPU 41%`）。
- **边**：仅显示域内强关联（感知→认知→记忆→行动主链路以箭头示意，复用全景仪表盘"四阶段流水线"语义）。
- **联动**：点击节点 → 右侧详情面板（状态明细 + 指标趋势 + 干预按钮）。

### 3.3 状态聚合规则

| 节点状态 | 判定来源 | 优先级 |
|---|---|---|
| 健康(green) | 健康探针 score ≥ 0.8 且无 issues | 高 |
| 警告(yellow) | 0.5 ≤ score < 0.8 或有告警 | 高 |
| 故障(red) | score < 0.5 或心跳丢失 / 进程异常 | 高 |
| 离线(gray) | 无数据源（available=false） | 中 |
| 未启用(blue) | 配置开关关闭（如 learning.*.enabled=false） | 中 |

聚合器缓存 5s 内结果（防重复采集拖垮后端），前端轮询 5s 刷新。

## 四、关键指标面板设计

### 4.1 全局指标条（顶部）
复用全景数据源，一屏总览：
- 整体健康分（`/api/health/dashboard`）
- 传感器在线数（`/api/sensors`）
- CPU / 内存 / 电池（`/api/panorama`）
- 会话数 / 交互次数 / 运行时长（`/api/panorama`）
- 定时任务运行中数（`/api/scheduler/tasks`）

### 4.2 节点级指标（详情面板）
点击节点后展示该模块声明的 `metrics`，按 `status_source` 拉取实时值 + 最近趋势：
- 感知节点：传感器在线/严重度分布
- LLM/工具节点：P99 延迟、错误率、成功率（`/api/tools/health`、monitoring metrics）
- 记忆节点：消息数、摘要版本、Token 占用（`/api/memory/overview`）
- 任务节点：下次执行时间、历史成功率（`/api/scheduler/history`）
- 安全节点：告警数、紧急状态（`/api/permission/status`、`/api/safety/alerts`）

### 4.3 实时性
- 默认：前端 5s 轮询聚合 API（简易、可靠）；
- 可选增强：SSE 推送（复用 `yunshu-ui` 已验证的 SSE 客户端模式），仅在需要秒级干预反馈时启用。

## 五、干预操作接口设计

### 5.1 统一干预入口

```
POST /api/modules/<module_id>/actions
Body: { "action": "toggle|restart|execute|emergency", "params": {...}, "reason": "操作原因" }
```

聚合层按 **动作映射表** 转发到既有 API，**不新建业务逻辑**：

| 动作 | 目标模块 | 转发到（既有接口） | 风险等级 |
|---|---|---|---|
| `toggle` | 工具 | `POST /api/tools/toggle` | 中 |
| `toggle` | 技能 | `POST /api/skills/toggle` | 中 |
| `toggle` | 扩展 | `POST /api/extensions/toggle` | 中 |
| `toggle` | 定时任务 | `POST /api/scheduler/toggle` | 中 |
| `execute` | 定时任务 | `POST /api/scheduler/execute-now` | 中 |
| `reload` | 感知/配置 | `POST /api/network-config` / `POST /api/config`（按模块映射） | 低 |
| `compress` | 记忆/上下文 | `POST /api/memory/compress`、`/api/context/compress` | 低 |
| `switch_mode` | 行为模式 | **需新增**（现状 `/api/mode` 仅 GET 读取，无 POST 写接口） | 中 |
| `emergency_stop` | 全局 | `POST /api/permission/emergency`（stop） | **高** |
| `emergency_pause` | 全局 | `POST /api/permission/emergency`（pause） | **高** |
| `block_network` | 全局 | `POST /api/permission/emergency`（network_block） | **高** |

### 5.2 安全与审计（守【不易】安全边界）
1. **危险分级**：动作映射表标注风险等级；前端对高危动作（emergency_*）展示**红色二次确认弹窗**并强制输入 `reason`。
2. **操作审计**：聚合层每次干预调用 `agent.log_system` 的 `log_operation()` 记录 `module_id/action/reason/结果/IP`，可在日志看板回溯。
3. **只包装不绕过**：紧急停止仍走 PermissionSystem 既有实现，聚合层不新增并行安全逻辑。
4. **幂等与限流**：干预接口复用既有 `RateLimiter`，防止高频误操作。

## 六、前端实现方案

### 6.1 载体选型
| 方案 | 说明 | 结论 |
|---|---|---|
| **A. 主控台新增「系统拓扑」视图** | 在 `templates/index.html` 现有 11 视图模式上新增 `#view-topology`，复用 `static/js/app.js` 导航框架与样式体系 | **推荐**：改动最小、零新依赖、与全景仪表盘风格一致 |
| B. yunshu-ui 新增面板 | Electron 工作台加 Mosaic 面板 | 可选二期：适合桌面工作流集成 |

### 6.2 页面布局

```
┌──────────────────────────────────────────────────────────┐
│  全局指标条（健康分|传感器|CPU|内存|会话|任务）              │
├──────────────────────────────┬───────────────────────────┤
│  六域分层拓扑树               │  节点详情面板               │
│  ┌ 感知层 ▼ (3/5 在线)      │  ┌ 模块信息               │
│  │  ● 传感器注册表 0.92     │  │  ● 状态: 健康            │
│  │  ● CPU 41% · 内存 63%   │  │  ● 路径: sensor/*.py     │
│  ├ 认知层 ▼                 │  │  指标趋势(迷你图)        │
│  ├ 记忆层 ▼                 │  ├ 干预操作 ────────────  │
│  ├ 行动层 ▼                 │  │  [切换] [重载] [执行]   │
│  ├ 服务层 ▼                 │  │  [紧急停止]              │
│  └ 运维层 ▼                 │  └ 最近操作审计记录        │
│                              │                           │
└──────────────────────────────┴───────────────────────────┘
```

### 6.3 组件与文件规划
| 文件 | 内容 |
|---|---|
| `static/js/topology.js` | 拓扑渲染（树状）、状态轮询、节点点击、干预调用、二次确认弹窗 |
| `static/css/topology.css` | 节点卡片、状态色标、详情面板样式（复用 `panorama.css` 色彩体系） |
| `templates/index.html` | 新增导航按钮 `🗺 拓扑` 与 `#view-topology` 容器 |
| `agent/modules_registry.py` | 模块注册表（六域节点 + status_source + actions） |
| `agent/modules_api.py` | Blueprint：`GET /api/modules/topology`、`POST /api/modules/<id>/actions`、操作审计 |

### 6.4 关键交互
- 折叠/展开域与子树；节点状态色 + 指标徽标随轮询实时刷新；
- 点击节点 → 详情面板（状态明细/指标趋势/操作按钮）；
- 高危操作 → 红色确认弹窗（展示操作后果 + 必填原因）；
- 干预后 2s 自动刷新该节点状态，操作结果 toast 提示；
- 全屏适配（复用 `responsive.css`）。

## 七、后端支撑 API 契约

### 7.1 `GET /api/modules/topology`
返回拓扑全量（注册表结构 + 实时状态 + 指标）：
```json
{
  "generated_at": "2026-08-16T10:00:00",
  "overall_health": 0.92,
  "domains": [
    {
      "domain_id": "perception",
      "domain_name": "感知层",
      "nodes": [
        {
          "module_id": "sensor.cpu",
          "name": "CPU 传感器",
          "status": "healthy",
          "status_detail": "cpu=41.2%",
          "metrics": {"sensor_on": 18, "sensor_total": 22},
          "actions": ["reload", "disable"]
        }
      ]
    }
  ]
}
```

### 7.2 `POST /api/modules/<module_id>/actions`
```json
{ "action": "toggle", "params": {}, "reason": "联调测试" }
```
响应：`{ "ok": true, "forwarded": "POST /api/tools/toggle", "result": {...}, "audit_id": "..." }`

### 7.3 `GET /api/modules/<module_id>/detail`
节点详情（状态明细 + 指标趋势历史 + 近期操作审计），供详情面板使用。

## 八、实施步骤与验收标准

### 8.1 实施步骤（可回滚小步）
| 步骤 | 内容 | 产物 |
|---|---|---|
| S1 | 新增 `agent/modules_registry.py` 模块注册表（六域节点 + status_source + actions 映射） | 注册表常量 |
| S2 | 新增 `agent/modules_api.py` 聚合 Blueprint（topology/detail/actions + 审计 + 限流），注册到 `app_server.py` | 3 个 API |
| S3 | 主控台新增「拓扑」视图：导航按钮 + 容器 + `topology.js` + `topology.css` | 前端拓扑页 |
| S4 | 联调验证：拓扑加载/状态刷新/节点干预/高危确认/审计落盘 | 测试记录 |
| S5 | （可选）`yunshu-ui` 面板接入 + SSE 秒级刷新 | 二期 |

### 8.2 验收标准
1. `/api/modules/topology` 返回六域全量节点，状态与现有 `/api/health/dashboard`、`/api/sensors` 一致；
2. 前端拓扑图正常渲染/折叠/刷新，节点状态色标准确；
3. 对工具/技能/任务节点执行 toggle/execute，对应既有 API 被调用且状态更新；
4. 紧急停止操作触发红色二次确认，`reason` 必填，操作写入日志审计可查；
5. 全流程零改动既有模块代码，回归现有 316 项测试通过。

## 九、方案风险与规避

| 风险 | 规避 |
|---|---|
| 聚合 API 高频采集拖垮后端 | 5s 缓存 + 前端轮询节流；状态源只读复用 |
| 干预误操作 | 高危二次确认 + reason 必填 + 操作审计 + 限流 |
| 新增模块未自动上图 | 注册表数据驱动，新增模块补注册即可；注册表加 CI 结构校验（可选） |
| 与既有全景视图重复 | 全景=指标总览，拓扑=结构与干预，二者互为补充，入口并列不冲突 |
