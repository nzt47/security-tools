## 二、已修复：39 个 env 未登记（master 硬守卫变红）

### 现象

`tests/unit/test_settings_registry.py::TestMechanicalZeroGap` 在 master 上：

```
extracted = 370 / registered = 331 ⇒ missing = 39
```

### 根因

三个 S8 任务各自新增 env 读取点，但都没登记进 `agent/settings/registry.py`：

| 来源 | 条数 | 键 |
|---|---|---|
| S8-02 并发与运维加固 | 17 | `CP_ARCHIVE_LOCK_*`、`CP_EVENTS_LOCK_*`、`CP_EVENTS_PENDING_MAX`、`CP_EVENTS_CORRUPT_LOG_EVERY`、`CP_TRACE_*`、`CP_POLICY_DECISION_LOG_*` |
| S8-03 灰度容器隔离 | 11 | `CP_DIGESTION_ISOLATION_*`、`CP_DIGESTION_REAL_TAKEOVER*`、`CP_DIGESTION_TAKEOVER_DIR` |
| S8-04 LLM-judge | 9 | `CP_DIGESTION_JUDGE_*` |

（同一守卫此前已被补过一次，但只补了 S8-05 的一条 ⇒ **守卫红了却没红到能推动全量补登的程度**。）

### 修法（机械补登，零行为变更）

类型 / 默认值 / 语义**逐条取自真实读取点**（`os.getenv`、`_env_flag/_env_int/_env_float`
的 default 实参与对应模块常量）；`owner_module` 取自扫描器的来源信息（测试要求指向真实文件）。

**风险级裁定（保守优先，已写进代码注释）**：

| 判据 | 级别 | 例 |
|---|---|---|
| 关掉**完整性强保护**（跨进程锁）会让写入交错/损坏 | **B** | `CP_ARCHIVE_LOCK_ENABLED`、`CP_EVENTS_LOCK_ENABLED`、`CP_TRACE_LOCK_ENABLED` |
| 打开/放宽**成本护栏** | **B** | `CP_DIGESTION_JUDGE_DAILY_BUDGET_CENTS`、`..._FOLLOW_FASTING`、`REAL_TAKEOVER_BUDGET_CAP/MIN_BUDGET/FAIL_THRESHOLD` |
| 打开**真实流量接管**（本系统最高危动作） | **B** | `CP_DIGESTION_REAL_TAKEOVER` |
| **路径 / 密钥文件位置** | **C**（只读脱敏） | `CP_DIGESTION_TAKEOVER_DIR`、`..._JUDGE_SECRET_FILE`、`..._JUDGE_DOTENV` |
| 其余纯数值上限 / 超时 / 非安全开关 | **A** | 各 `*_TIMEOUT_SEC`、`*_MAX`、`ISOLATION_*` 限额 |

> ⚠️ 注释中写明：**若后续复核认为某条应升降级，请连依据一起改，不要只改级别。**

## 三、仍未修：`unregistered_dynamic = ['<unresolved>']`（如实披露）

### 根因（S8-03 引入）

| 位置 | 代码 | 语义 |
|---|---|---|
| `agent/digestion/isolation.py:981` | `for name in self.HOST_ENV_ALLOWLIST: value = os.environ.get(name)` | 把宿主环境白名单**原样转发**给隔离子进程 |
| `agent/digestion/isolation_worker.py:351` | `values = {n: str(os.environ.get(n, "")) for n in names}` | `ISOLATION_ENV_WATCH` 的**可见性快照**（诊断用） |

两者语义上都属"转发/诊断"，**不是可切换开关**，应当与既有
`agent/skills_mgmt/executor.py::_ENV_WHITELIST` 一样走 `PASS_THROUGH_SITES` **显式声明 + 写明理由**。
扫描器解析不出它们，是因为原实现只认 `for x in NAME`（`ast.For` + `iter` 是 `Name`），
而这两处分别是 **`self.CONST`（类常量）** 与 **推导式**。

### 我尝试过、并**已回退**的修法（重要：一次假绿灯）

我扩展了 `scripts/scan_settings.py::collect_loop_literals`，让它同时识别
`self.CONST` 与推导式两种写法。改完后守卫确实 `ok=True`、`unregistered_dynamic=[]` ——
**但这是假的**：实测这两处读取**从报告里彻底消失**
（既不进 `managed`，也不进 `dynamic`，也不进 `passthrough`；`managed` 名数仍是 370）。

也就是说，我用一个自己无法完全解释的守卫改动，**把一条真实红灯换成了假绿灯** ——
正是该脚本注释里警告的"用声明/catch-all 掩盖真实缺口"。故
`git checkout -- scripts/scan_settings.py` **回退**，宁可留一条真实红灯。

> **纪律记录**：本次审计出现两次"自己的错误"——D4 的误读（真用前置）与本次的假绿灯。
> 两次都是**在复验环节被抓出来**的。这不是浪费：**假绿灯比红灯危险得多**。

### 建议的修法（独立小任务）

方向二选一，**都不动扫描器的判定口径**：

1. **改代码让来源可解析**：这两处改为迭代**模块级常量**
   （`isolation.py` 的 `HOST_ENV_ALLOWLIST`、`isolation_worker.py` 的 `ISOLATION_ENV_WATCH`），
   再在 `PASS_THROUGH_SITES` 增加两条声明并写明理由；
   ⚠️ 注意：若常量被解析成字面量，扫描器会按 `loop_literal` **逐条记录**那些 OS 环境名
   （`SystemRoot`/`WINDIR`/`COMSPEC`/`PATHEXT`/`NUMBER_OF_PROCESSORS`/`PROCESSOR_ARCHITECTURE`…），
   它们需要进 `PROCESS_ENV_DENYLIST`（该表有"恰好等于观测集"的断言，须一起改）。
2. **让扫描器把它们如实归类为"未声明的透传点"**（而不是 `<unresolved>` 动态家族），
   使红灯的**提示更准确**，再按 (1) 声明。
   这需要在 `_record`/`scan_paths` 里补一条明确分支 + 单测，**属守卫工具改动，须单独评审**。

**判据**：无论选哪条，都必须保证"未声明的来源照样进 `undeclared_passthrough`"
（不得放宽），并补一条回归用例锁死"读取点不得从报告中消失"。

### 两个真失败的细节

**（一）自伤回归**：`test_disabled_by_default_does_not_register` 依赖**仓库 config.yaml 的当前取值**
（当时 `slo_report.enabled: false`）。当天 Owner 要求把周报真正挂上调度，该值改为 `true`
⇒ 用例变成"断言部署取值"而失败。
⇒ **用例设计问题**（把"机制"与"部署选择"混在一起），不是功能回归。
修法：显式注入配置段，两向确定性验证；部署取值由 config.yaml 与文档负责，**不由单测锁死**；
并补上原先缺的"配置开启 ⇒ 注册"与"env 优先于配置"两条。

**（二）跨任务接缝**：S8-05 的 D3 给归组键加了**结构版本前缀**
（`agent/digestion/cleaning.py:191` `v2|cap=<集合>|steps=<档位>|out=<结果>`），
`v2` 自身含数字，而 S7-05 的断言是"键里一个数字都不许有"
⇒ 按**字面**失效，但**意图未失效**（真正要守的是"不得把目标里的 `0000` 编进键"）。
修法：按**意图**改断言并**补正向断言钉住新结构**（必须存在 `v2|` 前缀）——
**收紧而非放宽**，同时把"断言写得比意图更严"这个隐患消掉。

> 这两个真失败正好各代表一类接缝：**"我改了配置却忘了我自己的测试假设了它"**
> 与 **"我改了数据结构却没跑依赖它的旧测试"**。与 §一 的模式一致。
