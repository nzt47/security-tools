---

## 1. 背景与问题

第二批性能对比报告实测：入链索引的全量扫描路径峰值内存 **5.6 MB / 3000 卡**（O(N) 线性、测完即释放），外推：

| 库规模 | 全扫峰值内存（外推） |
|---|---|
| 3 千卡 | ≈5.6 MB |
| 1 万卡 | ≈18 MB |
| **10 万卡** | **≈180 MB** |

**根因**：三条全量扫描路径（`rebuild_links_index`、`_has_incoming_links` 索引缺失回退、`delete_many` 索引缺失回退）均调用 `self.list()`，一次性解析**全库 Card 对象**驻留内存（每张卡的 frontmatter + 正文 content 字符串），随后才聚合入链映射。

**触发条件**：仅索引缺失 / 解析失败 / 全量重建时。正常读路径查表 O(1) 无此开销。当前规模（几千 ~ 1 万卡）可控，但知识库规模增长至 10 万卡量级时，回退/重建路径的 180 MB 峰值将不可忽略。

---

## 2. 目标与收益估算

**目标**：全量扫描峰值内存从 O(N)（全库卡片对象驻留）降为 **O(U)**（U = 被引用 slug 数，即索引表本体大小），且**行为、语义、时间复杂度均不变**。

**收益估算（10 万卡、每卡 2 links、slug 平均 10 字符）**：

| 内存项 | 现状（list() 驻留） | 流式方案 |
|---|---|---|
| 全库 Card 对象 + content | ≈180 MB | ≈0（逐张 yield 即释放） |
| 入链映射 refs dict | ≈15–30 MB | ≈15–30 MB（输出本身，无法避免） |
| 单张卡驻留 | — | ≈2–5 KB |
| **峰值合计** | **≈180–210 MB** | **≈15–35 MB（约 6–12x 降低）** |

时间：仍为 O(N) 一次全库解析（与原 list() 相同，无额外开销）。

---

## 3. 方案设计

### 3.1 新增 `CardStore.iter_cards()` 流式生成器

在 [card.py](file:///c:/Users/Administrator/agent/agent/knowledge/card.py#L430) 的 `list()` 旁新增生成器，语义与 `list()` 对齐：

```python
def iter_cards(
    self, status: Optional[str] = None, type: Optional[str] = None
) -> Iterator[Card]:
    """流式枚举卡片（生成器）：逐文件解析、yield 后即释放，不驻留全库。

    与 list() 语义一致：按 slug 字典序、损坏卡跳过、可选 status/type 过滤；
    差异仅在内存形态——调用方为纯聚合/判定场景时无需全量驻留（O(1) 单卡）。
    """
    with self._rwlock.read():
        for t in _TYPE_DIRS:
            if type is not None and t != type:
                continue
            d = self._wiki_root / t
            if not d.exists():
                continue
            for p in sorted(d.glob("*.md")):
                try:
                    card = self._md_to_card(p)
                except (ValueError, TypeError):
                    continue  # 跳过损坏卡片，不阻断全库列举
                if status is not None and card.status != status:
                    continue
                yield card
```

> 设计点：`iter_cards` 放在写锁上下文内（与 `list()` 一致），保证枚举期间不被多步写打断；生成器在消费者遍历完成后释放读锁。

### 3.2 三处全量扫描路径改为消费生成器

| 路径 | 现状 | 改造 |
|---|---|---|
| `rebuild_links_index` | `for card in store.list()` | `for card in store.iter_cards()` |
| `_has_incoming_links` 回退 | `any(slug in c.links for c in self.list() ...)` | `any(slug in c.links for c in self.iter_cards() ...)`（短路保留） |
| `delete_many` 回退 | `for card in self.list()` | `for card in self.iter_cards()` |

聚合逻辑（refs / incoming dict）不变；`archives/` 前缀过滤、损坏卡跳过、判定语义全部不变。

## 4. 复杂度与内存分析

- **时间**：O(N)（与现状相同，单次全库解析）。
- **内存**：峰值 = 入链映射 dict（O(U)）+ 单张 Card（O(1)）。`refs`/`incoming` 是输出必须驻留的；卡片对象不再全量驻留。
- **边界**：若引用密度极高（每卡引用上百目标），refs dict 仍可能大（O(N·L)）；当前契约每卡 links 数量级很小，可接受。极端场景可进一步拆分为「分片聚合 + 合并」，本方案不引入（避免过度设计）。

---

## 5. 不变量与测试

【不易】不变量全部保留（由现有测试锁定）：

1. `rebuild_links_index` 结果 == 全库扫描逐卡 links 聚合结果（集合相等）；
2. 增量叠加 == 全量重建（CRUD 挂接一致性）；
3. 幂等：重复 add / remove 不存在无变更；空段清理；
4. `archives/` 前缀不入表；
5. 索引缺失回退语义与索引存在时一致。

**新增测试**：

- `test_iter_cards_equivalent_to_list`：`iter_cards()` 结果（slug 集合、links）与 `list()` 一致（含损坏卡跳过、过滤参数）。
- `test_rebuild_matches_stream_scan`：`rebuild_links_index` 改造后结果与流式直接聚合一致（现有 `test_rebuild_matches_full_scan` 已覆盖等价断言，此测试显式锁定「list 版 vs 流式版」输出逐字节一致，防实现漂移）。
- 回归：现有 9 项 `test_links_index.py` + 367 项知识模块全量。

## 7. 回滚

- `iter_cards()` 为纯新增方法；三处调用点各一行改动。
- 回滚 = 恢复 `list()` 调用（删除生成器），无行为残留，不触碰索引文件格式与不变式。

---

## 8. 决策点（待评审确认）

1. **是否落地**：当前规模（≤1 万卡）内存可控（≈18 MB），本方案为**前瞻性优化**；建议与库规模增长计划对齐决定优先级。
2. **排序保持**：`iter_cards` 保持 `sorted(glob)` 与 `list()` 逐字节对齐（本方案默认）；若接受不排序，可省去文件名列表排序的 O(N) 小内存，但语义需文档化。
3. **`iter_cards` 放置位置**：本方案放 `CardStore`（card.py）；如团队倾向职责分离，可放独立模块并回调 `_md_to_card`（会侵入私有实现，不推荐）。
