## 裁定 #1 · 记忆压缩阈值：取校验器允许的最大值 32768，并显式写入配置

**裁定**：`config.yaml` 的 `memory.token_limit` **显式设为 32768**（原为"未配置 ⇒ 代码硬编码默认 4096"）。

**事实（主线查证）**
- 语义：`memory/memory_manager.py:286,428` + `memory/summarizer.py::should_compress` —
  **最近 200 条消息**的 token 合计 ≥ `token_limit × 0.8` 即触发压缩。
- 默认 4096 ⇒ 触发点仅 **≈3276**；而一次大工具输出（`list_directory` 返回 195 项）≈ **14k tokens**
  ⇒ **每次大工具输出必然触发一次压缩**（额外 LLM 摘要调用 + 把刚拿到的上下文压掉）。
  实测"真机一次会话压缩 5 次"即源于此；这也**很可能是早期"答非所问"的推手之一**。
- 三处上限并非同一概念：压缩阈值 4096（记忆层）/ 编排窗口 131072（`lifecycle_manager.py:288`，
  决定往 prompt 塞多少历史）/ `plugins/chat.py` 4096（纯显示公式）。
- `config.py` 校验器把本键限制在 **512..32768**（超限会被"修正为 4096"）。
- `deepseek-v4-flash` 的**真实上下文窗口从未验证**，131072 只是通用默认值。

**为什么不直接对齐 131072**：需先改校验器上限（schema 变更）+ 未验证模型真实窗口，有提示词超窗风险。

**实施**
- ✅ `config.yaml` 增加 `memory.token_limit: 32768`（含完整依据注释）。
- ✅ 验证：配置解析正常；校验器无 `token_limit` 相关错误；
  实测 `MemoryManager._token_limit = 32768` ⇒ **压缩触发点 3276 → 26214（8×）**。
- ⏭ 后续（已立项）：先**实测模型真实窗口**，再建立"窗口 → 压缩阈值"的推导关系，
  让压缩阈值与 `get_context(token_limit=...)` **同源**；并考虑把**工具结果**从压缩触发口径里
  **单独计量**（否则"一次大工具输出 = 一次压缩"的行为不变）。

## 裁定 #2 · BM25-only 召回：暂不标定，保持现状

**裁定**：**不为 BM25 单独标定归一化映射与阈值**，维持 S10-03 的"质量门只认有界相似度"口径。

**事实**
- `agent/skills_mgmt/loader.py`：`_RRF_QUALITY_MIN = 0.3` 的语义是「**有界相似度**阈值」，
  只认 `_BOUNDED_QUALITY_KEYS = (tfidf_score, vector_score, rerank_score)`，
  与编排层 `orchestrator._BOUNDED_RELEVANCE_KEYS` **逐字对齐**。
- 修复前根因：`max()` 把 `bm25_score=3.5184`（**无界**）拿去与有界阈值 0.3 比较 ⇒ 噪声候选过闸。
- S10-03 实测边界：同一批 **11 条** query 中，**没有一条真命中的 top1 是 BM25-only**
  （真命中的有界分为 0.4444 / 0.5 / 0.5455）；BM25-only 只出现在噪声 query 的 top1 与正样本的 #2 之后。

**理由**：①编排层早已按同一口径拒绝 BM25-only ⇒ 检索层与之一致**不产生新分叉**；
②为 BM25 发明归一化需要**真标签**，现仅 11 条 —— 按本项目纪律"**样本 <20 只披露不考核**"，
不足以标定；③真用期一旦出现"专有名词/代码标识符搜不到"，**带真实漏召回样本再标定**才有依据。

**触发复评的条件**：运营期出现可复现的"纯 BM25 真命中被拒"样本 ≥20 条。

## 裁定 #4 · 被硬杀时丢掉在途 1 条：判定可接受，**按意图改用例**

**裁定**：**可接受**（异步刷盘的固有语义）；修改用例使其回到原意，并补一条用例**显式记录该语义**。

**事实**
- 用例 `test_killed_process_does_not_deadlock_next_writer`：spawn worker 写 5 条 → 收到信号后
  **立刻 `proc.terminate()`（硬杀）** → 新写者接管续写 → 断言 `entry.seq == 6` 与 `len(rows) == 6`，
  实测 **5**。隔离复跑：第 1 次（冷）35.19s **失败**，第 2、3 次 3.95s / 2.56s **通过**。
- 该用例 docstring 承诺的是「**持锁进程被杀不得死锁**：OS 文件锁随进程消亡自动释放；
  预留日志让新进程能接着原链头续写」—— **只承诺锁恢复 + 能续写，未承诺"硬杀的在途数据不丢"**。
- ⇒ 与 `v2|` 那次同型：**断言（不丢数据）比意图（不死锁）更严**。

**理由**：SIGKILL/terminate 下在途未 flush 的数据丢失是**异步刷盘的固有语义**；
要"不丢"就得每条 fsync（性能代价），那是**产品耐久性口径变更**，不应由一个测试顺带要求。

**实施要求（留给实施者，务必按此做）**
1. 用例改为「**先等 worker 确认第 5 条已落盘（flush 完成）再杀**」，
   然后断言"锁已释放 + 新写者能续写 + 总数 = 6" ⇒ 回到**原意（测恢复能力）**。
2. **另补一条独立用例**，显式记录"硬杀会丢在途数据"这一**已知语义**（避免后人误以为它保证不丢）。
3. ⚠️ **不要**把断言放宽成 `>=5` —— 那是**放宽而非按意图修正**，会顺带掩盖"锁没恢复"。

**若 Owner 后续认为"审计记录一条都不能丢"**：应作为**独立耐久性需求**单列
（含每条 fsync 的吞吐/延迟影响评估），**不要**塞回这个用例。
