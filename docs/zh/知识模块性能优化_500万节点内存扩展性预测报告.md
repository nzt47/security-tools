## 2. 500 万节点基线预估（每卡 2 links）

| 内存项 | 现状（list() 驻留） | 流式扫描（方案） |
|---|---|---|
| 全库 Card 对象 + content（500 万 × 1.73 KB） | ≈8.65 GB | ≈0（逐张 yield 即释放） |
| refs 入链映射（12.8 MB × 50） | ≈640 MB | ≈640 MB（索引本体，必须驻留） |
| 单张卡驻留 | — | ≈2–5 KB |
| **峰值合计** | **≈9.3 GB** | **≈640 MB** |

**结论**：500 万节点 = **单机架构的终点**。现状 9.3 GB 必然 OOM；流式 640 MB 虽可控，但已是常态内存的高水位（且随密度上升更快）。

## 4. 扩展性结论与建议

| 决策维度 | 500 万节点评估 |
|---|---|
| 内存（现状） | ≈9.3 GB：**必然 OOM，单机不可行** |
| 内存（流式） | ≈640 MB（基线）～ 3.2 GB（高密度）：流式也偏高 |
| 耗时（全扫） | ≈18.75 分钟：**单机串行全扫失去工程意义** |
| 索引本体 | refs 640 MB 成为新主导成本，卡片驻留已非主项 |

**建议**：

1. **500 万节点 = 架构重构线（非流式可解）**：流式方案收益（9.3 GB → 640 MB）仍显著，但已不足以支撑该规模，需同步引入：
   - **分片存储**：refs 按 slug 前缀/哈希分片，增量写只触达单片，单文件 `index_links.md` 的整文件读改写在此规模不可行；
   - **并行扫描**：全扫 18.75 分钟 → 按分片并行（预期线性加速，N 片 ≈ 时间/N + 合并开销）。
2. **流式落地仍前置**：即便做架构重构，`iter_cards()` 流式扫描是分片扫描的基础形态（逐文件处理、无驻留），应先落地。
3. **业务预案**：该规模下回退全扫/全量重建应改为**后台任务 + 状态提示**，禁止同步阻塞主流程。
4. **阈值建议**：以本报告曲线为参照——≤200 万卡流式即可；≥500 万卡启动分片重构评估。
