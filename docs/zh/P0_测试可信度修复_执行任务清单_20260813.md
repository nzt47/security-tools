### A1 测试顺序污染治理（T-1 ~ T-4）

**T-1 单文件复跑定位**
- [ ] 对 `failures_baseline.txt` 中每个失败模块执行 `python -m pytest <模块> -q -p no:randomly --no-header`
- [ ] 标注"单独跑通过"的模块 → 候选顺序污染（预期：dialog_state / response_workflows / knowledge_observability / log_dict / mcp_executor / perf_monitor / skill_manager / few_shot_injector / security_utils 等）
- 产出：候选顺序污染模块清单（含用例数）
- 验收：清单完整覆盖 ~53 个失败用例

**T-2 根因分类**
- [ ] 按失败现象分类：类身份错位（模块 reload 后 `isinstance`/type 比较失败）、全局单例/缓存跨用例泄漏、fixture 顺序依赖、文件/端口/环境变量污染
- [ ] 每个分类给出 1~2 个代表性失败用例的 traceback 关键帧
- 验收：每个失败用例可归入一个根因类别

**T-3 修复**
- [ ] 对全局单例/缓存泄漏：为相关模块增加 autouse fixture（scope=function/module）重置全局状态（如 `routes_logging._ALERT_RULES_CACHE` 已有先例）
- [ ] 对类身份错位：消除测试中隐式模块 reload（检查 `importlib.reload`、`monkeypatch` 后未恢复），或改用 `importlib` 稳定路径
- [ ] 对 fixture 顺序依赖：将隐式依赖改为显式 fixture 声明
- 验收：所有候选污染用例修复落地，不破坏原用例意图

**T-4 顺序稳定性验证**
- [ ] 固定 seed 全量：`python -m pytest tests/ -q --randomly-seed=<固定值>` → 0 failed / 0 errors
- [ ] 另取 3 个不同 seed 抽样（`--randomly-seed=1/2/3`）→ 均稳定
- 验收：任意 seed 全量通过
