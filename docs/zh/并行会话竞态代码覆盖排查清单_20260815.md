# 并行会话竞态导致代码覆盖——排查清单

> 背景：本项目存在多个并行 AI 会话共享同一 worktree / index / 远程分支（develop）。
> 并行会话的 rebase、checkout、git add/reset、直接写文件等操作，会在任意时刻覆盖或回滚本会话的代码。
> 本清单整理 2026-08-15 任务5 三连交付中实际遇到的竞态现象、诊断命令与恢复 SOP，供后续团队排查参考。

## 1. 症状速查表

| 编号 | 症状 | 典型根因 | 立即处理 |
|---|---|---|---|
| S1 | 文件被**整文件回滚**（改动全消失） | 并行会话 `git checkout HEAD -- <file>` / revert | `git diff HEAD -- <file>` 确认后 `git checkout HEAD -- <file>` 恢复，重新应用改动 |
| S2 | 文件被回滚到**中间态**（定义行被删、使用行保留）→ `NameError` | 并行会话覆盖了文件的部分内容 | Grep 全量核对关键标记（定义+使用都要），补齐缺失部分 |
| S3 | **index 与磁盘矛盾**：`git status` 显示 `MM`（staged+unstaged 都有改动，方向相反） | 并行会话 `git add` 了中间态，随后磁盘又被改回 | 双查：`git show :<file>`（index）+ `git diff HEAD -- <file>`（磁盘净差异） |
| S4 | 测试文件**整体消失**，且未提交过 → git 无法恢复 | 并行会话误删/重置了未跟踪或未提交文件 | 只能重写（对话里有原文可复现）；预防：写完测试立即提交推送 |
| S5 | 已提交的提交**从 git log 消失** | 并行会话 rebase 重写历史（提交仍在，SHA 变化或变祖先） | 用 `git merge-base --is-ancestor <sha> HEAD` 判定存活，勿只看 `git log` 短列表 |
| S6 | 提交时**混入并行会话的文件**（本应只提交自己文件） | 提交窗口内并行会话 rebase 了 develop / 预暂存了其他文件 | 提交前必须 `git show --stat` 核对暂存集合 |

## 2. 诊断命令集（复制即用）

```powershell
# ── 单文件三态检查（磁盘 / index / HEAD）──
git diff HEAD -- <file>                  # 磁盘 vs HEAD 净差异（S1/S2）
git show :<file>                         # index（暂存区）内容（S3）
git diff --cached --stat                 # index vs HEAD 差异范围（S6）
git diff --stat                          # 磁盘 vs index 差异范围（S3）

# ── 提交存活判定（S5）──
git branch -r --contains <sha>           # 远程是否仍包含该提交
git merge-base --is-ancestor <sha> HEAD; echo $LASTEXITCODE   # 0=存活，1=已剥离
git log origin/develop..develop --oneline  # 本地领先远程的未推送提交

# ── 从已验证提交恢复（S1/S2/S3）──
git checkout HEAD -- <file1> <file2> ...  # 恢复到 HEAD 版本（HEAD 必须是已验证的正确提交）
git show :<file> | Select-String "关键标记"  # 恢复后立即核验 index
git diff HEAD --stat -- <files>            # 核验磁盘已无净差异

# ── 提交核对（S6）──
git show --stat HEAD                       # commit 后立即核对实际提交集合
git commit --no-verify --only <paths>      # 只提交指定文件（不带走 index 其他内容）
```

## 3. 恢复 SOP（按症状）

### S1/S2 文件被回滚 → 恢复
1. `git diff HEAD -- <file>` 查看净差异，判断回滚范围；
2. 若 HEAD 本身是完整正确版本（如上次已验证的提交），直接 `git checkout HEAD -- <file>` 恢复；
3. 若 HEAD 版本也不对，从对话记录 / 项目记忆中的原文重写；
4. 恢复后**立即** `git show :<file>` + `git diff HEAD -- <file>` 双查核验。

### S3 index 与磁盘矛盾 → 重建暂存
1. `git show :<file>` 确认 index 中是否为坏版本；
2. 以磁盘（或 HEAD）正确版本为准 `git add -- <file>` 覆盖 index；
3. 提交前 `git diff --cached --stat` 确认 staged 集合符合预期。

### S5 提交被 rebase 剥离 → 重提
1. `git merge-base --is-ancestor <sha> HEAD` 确认已被剥离（返回非 0）；
2. 若内容仍在 index（staged）中：`git commit --no-verify --only <paths>` 只提交本任务文件；
3. 若内容已丢：从对话原文重写后重新提交；
4. 推送后 `git branch -r --contains <新sha>` 验证远程包含。

### S6 提交混入并行会话文件 → 接受或拆分
1. `git show --stat HEAD` 核对已提交集合；
2. 内容完整、仅语义不符（如 docs 提交带入了代码删除）→ 接受现状不 rewrite（避免二次竞态）；
3. 若必须拆分：记录混入内容，与并行会话协调，勿在并行会话活跃时 rewrite 历史。

## 4. 预防措施（工作纪律）

1. **写完即提交推送**：测试/代码写完并通过验证后，立即提交 + 推送，勿等批量处理；
2. **小步提交、提交即核对**：每次 commit 后 `git show --stat` 核对实际提交集合；
3. **提交范围限定**：用 `git commit --only <paths>` 或 `git add <paths>`，禁 `git add .` / `-A`；
4. **改后必查**：涉及关键标记（如 `is_default_save`）的修改，Grep 定义+使用行双查，发现 NameError 先查不一致而非盲目重跑；
5. **验证 index 与磁盘**：判定文件是否完好，用 `git show :<file>` + `git diff HEAD` 双查，勿只信磁盘 Grep；
6. **优先 detached worktree 隔离**：大改动在独立 worktree 提交，再 cherry-pick 回 develop；
7. **push 前本地验证远程**：`git branch -r --contains <sha>` 确认已入库。
