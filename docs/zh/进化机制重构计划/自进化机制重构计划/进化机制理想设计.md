## 三、设计合理性评估（元审计结论）

### 3.1 合理骨架（认可，继续作为方向）

1. **L1/L2/L3 三层翻译框架正确且务实**：把"递归自进化"从"让系统改写自身代码"翻译为"在护栏内更新外部策略工件"，与云枢约束 C1-C5、与 EVO-T1~T6 已落地的能力（真实评估 `agent/skills_mgmt/evaluator.py`、谱系 `lineage.py`、受控编辑 `meta_editor.py`、审批/回滚 `approval.py`/`rollback.py`）完全同构。该框架可作为后续一切自进化工作的总纲。
2. **云枢化降级思路（MAE→角色化评估、MIA→TTPU、课程→难度分级、世界模型→回归+回放）方向正确**：全部复用现有资产、零新增训练基建，符合【简易】最小充分解原则，且与主文档《智能体学习机制理想设计.md》§3.2 D2-D9 无冲突（§8 自检结论成立）。
3. **护栏 G1-G5 主张正确且有实现锚点**：G2（`value_guard.py` 价值观红线 + `reviewer` 三重审核）、G3（`EvolutionArchive` 谱系）、G4（`rollback_version` + `learning.budget` + dry-run 默认）、G5 第一层（`StagedEvaluator` 分阶段评估）均已存在。
4. **"触发条件必须可度量"的原则正确**，且报告 §8 诚实披露了 KPI#4 口径错配与 LearningMetrics 无持久化两个问题（后续已补 SQLite 持久化，commit `3f37612d`）。

### 3.3 实践缺陷（与云枢现状的错位）

1. **时效性错位（最突出）**：报告成文 2026-08-14 时主线 TASK-01~07 尚在执行中，故结论"近期只做接线与度量、零自进化"。**截至 2026-08-21，主线已全部收口**（`变更说明/TASK-01~07_*.md` 齐备）：规划接线（`planning.wire_enabled=false` 灰度）、反思持久化（`reflection_persist=true`）、预算护栏（`budget.mode=warn_only`）、沉淀管道（`precipitate_enabled=false`）、进化/反馈/生命周期调度（`learning.evolver/feedback_agent/lifecycle` 均 `enabled=true, dry_run=true`）、新颖性管线（`sensor_learning.enabled=false`）、自主权分级（`agent/autonomy.py`，默认 L3）均已在代码中。**重构计划的正确前提是"构件已就绪、等待受控放行"，而非"从零接线"**。
2. **"最小自进化闭环已存在雏形"的表述需要更新为"闭环构件已齐备但整体休眠"**：`offline_evolver` 已接真实评估 + 谱系 + 父代选择 + 调度（EVO-T1~T6 结案，1310 关联用例 + 全量 14730 通过），`learning_scheduler.py` 已统一注册四类调度——报告写作时点之后的状态已远超其描述。
3. **"绝不伪造指标"与"评估集样本不足"之间存在未处理的张力**：EVO-T2 的 `no_samples → score=0.0` 语义正确，但样本池只有 15 条，意味着当前"真实评估"对大多数 Skill 返回 0 分或直接跳过——G5 门禁在样本不足时形同虚设，报告未给出评估集扩充路径。
4. **配置与实现不一致处未披露**：`evolution_scheduler.py` 文档字符串声明 `LEARNING_EVOLVER_ENABLED` 默认 false，而 `config.yaml` 已置 `enabled: true`（配合 dry_run=true）——语义靠 dry_run 兜底，但"调度已注册、只是预演"这一状态报告未描述。

### 3.4 需要补充完善的内容清单（报告缺什么）

1. **技能评估集工程**：样本规模目标、类别/难度覆盖规范、扩充管道（反思产物/失败案例/feedback 回流/人工标注）、可执行回归门禁 CLI（替代"1.2 万回归"的错位引用）。

3. **Judge 双假设判别实验设计**：对照通道、分歧率指标、判别结论模板。
4. **POC-A 成本模型更新**：按真实评估器口径重估（子进程执行 + 自一致性倍数 + 预算熔断），替换蒙特卡洛数字。
5. **G1 元规则版本化实现方案**：参数清单、版本化存储 schema、门控与回滚命令。
6. **沙箱回放安全前提**：进程级隔离/白名单/资源限制设计，软隔离问题的处置。
7. **多租户维度**：进化工件租户作用域、跨租户禁止、KPI 分租户聚合的设计原则。
8. **触发监控运维落地**：持久化启用、周级滚动统计、监控面板/告警、L3 决策评估框架（谁批准/何时评估/评估什么）。

## 五、重构计划：分阶段论证

### 5.1 是否需要分阶段？——需要

论证依据：

1. **范围横跨 7 个独立领域**（评估资产、度量数据源、进化调度放行、元规则治理、角色化评估、回放安全、路由自适应），各有独立测试面与验收标准，无法一次性提交。
2. **存在明确依赖链**：评估集（任务1）→ 闭环放行门禁（任务3）→ Judge 验证（任务5）；度量（任务2）→ 闭环放行判据（任务3）与触发监控（任务2 自身）；复杂度判定源统一（任务7）依赖评估集与 KPI 基线。
3. **守【不易】安全底线**：所有进化动作必须保持"dry-run → 观察 → 人工确认 → 小流量"的渐进放行，任何一步都不允许一次性大改动直接生效。
4. **守"不易"原则（大变更拆解为可回滚小步）**：每阶段可独立灰度、独立回滚、独立验收；既有 1.5 万+ 测试与 pre-commit 守卫使"接线型重构"可被安全验证。
