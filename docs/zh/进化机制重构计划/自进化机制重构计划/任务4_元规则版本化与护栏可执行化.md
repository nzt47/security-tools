## 1. 背景（为什么做）

TASK-08 报告护栏 G1 要求：**"更新规则本身（变异策略、评估阈值、进化权重、触发条件）必须进入版本管理，任何变更走 bump_version + 门控；禁止运行时无版本修改"**——即"更新规则本身也是被管制的对象"。

但审计发现进化参数当前散落三层且**无版本化**：

| 层 | 示例 | 现状 |
|---|---|---|
| `.env` | `EVOLUTION_*`、`EVAL_*`、`LEARNING_*`、`EVOLUTION_MAX_TOKENS_PER_ROUND` 等 | 环境变量，无版本历史、无门控 |
| `config.yaml` | `learning.evolver/feedback_agent/lifecycle/budget` 等 | git 版本化（整体文件），无逐项 bump/回滚语义 |
| 代码默认值 | `evolution_scheduler.py` 的 `DEFAULT_INTERVAL_DAYS`、`offline_evolver.py` 的阈值 | 硬编码，改动走 git 但无运行时门控 |

同时，G2-G5 的构件（`value_guard.py`、`EvolutionArchive`、`approval.py`、`rollback.py`、`StagedEvaluator`）均已存在但**分散**，缺少一个可查询的"护栏状态服务"，决策层无法随时回答"当前护栏是否全就绪、最近一次元规则变更是什么、如何回滚"。

本任务建立**元规则（meta-rule）版本化存储 + 变更门控 + 回滚**，并收口 G1-G5 为统一护栏状态服务。

## 2. 目标描述（做什么）

1. **盘点元规则清单**：进化策略参数（变异策略、父代选择权重、评估阈值、预算、调度间隔、触发条件阈值）逐项登记 schema（名称/类型/默认值/合法范围/生效读取点）。
2. **元规则版本化存储**：`data/learning/meta_policy/`（JSON 文件 + 版本快照），提供 CLI：`meta-policy list / show / bump / rollback / diff`；schema 校验非法值回退默认（沿用 .env 非法值回退既有约定）。
3. **变更门控**：元规则变更走审批链（复用 `approval.py`）→ 生效前校验 → 审计（G3 全链路）；"运行时无版本修改"零容忍（代码审计可证所有读取点都经过版本化层或回退默认）。
4. **护栏状态服务**：聚合 G1-G5 可查询状态（G1 元规则版本/最近变更、G2 value_guard 启用与红线条数、G3 谱系完整性、G4 回滚能力与预算模式、G5 回归门禁与观察期配置），暴露只读端点（如 `/api/learning/guards`）。
5. 默认**只读/不接管**：本任务不改变任何进化参数的实际值，只建立管控载体；参数迁移到新存储为灰度可选。

## 3. 不变式约束（不易——禁止触碰）

- 禁止修改既有模块的**参数读取语义**：环境变量 > config.yaml > 硬编码默认值的优先级保持不变；元规则层只做"登记 + 快照 + 门控 + 查询"，不改变最终生效值来源（除非显式迁移）。
- 禁止修改 `approval.py`/`rollback.py`/`value_guard.py`/`lineage.py` 既有接口（复用，不改造）。
- 非法值回退默认（沿用 EVO 总览 §六.2 约定）；变更失败绝不阻断主流程。
- 元规则存储为只读默认；任何变更必须过审批链，无审批零生效。

## 4. 执行步骤

### Step 1：元规则清单盘点
- 从 `.env.example`、`config.yaml`、`evolution_scheduler.py`/`offline_evolver.py`/`evaluator.py`/`learning_budget.py`/`evolution_scheduler.py` 代码默认值中提取进化参数清单，登记为 `data/learning/meta_policy/schema.json`（名称/类型/默认值/合法范围/读取点/所属护栏）。

### Step 2：版本化存储与 CLI
- 新增 `agent/learning/meta_policy.py`：`MetaPolicyStore`（JSON + 版本快照目录 `data/learning/meta_policy/versions/`）+ CLI 命令（list/show/bump/rollback/diff/validate）。
- `bump`：快照当前生效值 → 写入新版本 → 标记 pending；`rollback`：恢复上一版本快照。

### Step 3：变更门控
- `bump` 后的新版本进入审批队列（`approval.py`），批准后生效；拒绝则保持当前版本。
- 生效前 schema 校验（非法值拒绝并告警）；每次 bump/rollback 写审计（G3 字段：change_id/param/old/new/approver/rollback_command）。

### Step 4：护栏状态服务
- 新增 `agent/learning/guard_status.py`：聚合 G1-G5 状态（数据来源：meta_policy 版本、value_guard 配置、EvolutionArchive 统计、learning.budget 模式、任务1 回归门禁配置与最近结果、任务3 放行模式）。
- 暴露只读端点 `/api/learning/guards`（JSON：每项护栏 enabled/status/最近变更/回滚命令）。

### Step 5：灰度迁移（可选）
- 提供 `meta-policy migrate --dry-run` 预演把指定参数从 .env/config 迁移到 meta_policy 存储的读取路径；默认不迁移，仅报告差异。

### Step 6：测试与文档
- 新增单测：schema 校验、bump/rollback 快照恢复、非法值回退、审批门控（未批准零生效）、护栏状态聚合与真实配置一致。
- 产出变更说明 + 元规则清单文档。

## 5. 预期成果（交付物）

1. `data/learning/meta_policy/schema.json` 元规则清单（覆盖进化/评估/调度/预算/触发条件参数）。
2. `agent/learning/meta_policy.py` 版本化存储 + CLI（bump/rollback/diff/validate/migrate）。
3. 变更门控（审批链 + 校验 + 审计）接线。
4. `agent/learning/guard_status.py` + `/api/learning/guards` 护栏状态服务。
5. 变更说明 + 新增单测全部通过。
