## 1. 背景（为什么做）

TASK-08 报告的"中期"结论：开启**策略工件级自进化（L2）**——`feedback` 执行体 + evolver 调度 + lifecycle，全部 dry-run → 观察 → 人工确认。审计确认该目标的大部分构件**已存在**：

- `agent/skills_mgmt/evolution_scheduler.py`（周级进化，`config.yaml learning.evolver` 已 `enabled=true, dry_run=true`）；
- `agent/skills_mgmt/feedback_agent.py`（每日反馈建议执行体，`dry_run=true`）；
- `agent/skills_mgmt/lifecycle.py`（每日零使用淘汰判定，`dry_run=true`）；
- EVO-T1~T6：真实评估、谱系（`lineage.py`）、审批（`approval.py`）、回滚（`rollback.py`）齐备。

缺的是**受控放行机制**：当前只有"dry-run（零副作用）"与"关闭"两态，没有"观察（执行真实评估但零提交）、人工确认（审批后提交）、小流量（按比例命中 + KPI 无劣化自动回退）"的渐进台阶，也没有统一的放行判据与一键总开关。

本任务建立 **dry-run → observe → confirm → rollout 四态放行框架**，把三类进化动作（feedback 晋升/淘汰、evolver 提交、lifecycle 迁移）纳入统一管控，接任务1 回归门禁（G5 第一层）与任务2 监控（在线保守观察期判据，G5 第二层）。

## 2. 目标描述（做什么）

1. 定义并实现**放行状态机**：每类进化动作四个模式 `dry_run / observe / confirm / rollout`（配置 `learning.rollout.<action>.mode`，环境变量覆盖）。
2. **observe 态**：执行真实评估与建议生成，但零提交；结果写 `EvolutionArchive`（decision=preview）+ 审计；用于积累"若放行会怎样"的数据。
3. **confirm 态**：产物进入审批队列（复用 `approval.py`），人工批准后提交；提交前自动快照（`bump_version`）+ 回归门禁（任务1）。
4. **rollout 态**：新版本按配置比例命中流量；KPI 无劣化（任务2 监控，判据如任一 KPI 连续 2 个评估周期恶化）自动回退上一版本并告警。
5. **全链路审计 + 一键总开关**：所有放行动作（预览/审批/提交/回滚）写谱系与审计；总开关关闭后全部动作回到 dry_run。
6. 默认态 = 当前配置不变（dry_run），**本任务不改变任何生产行为**，仅提供放行能力。

## 3. 不变式约束（不易——禁止触碰）

- 不修改 `offline_evolver.py` 进化算法与 `BatchEvolutionReport` 结构、不修改 `feedback_agent.py`/`lifecycle.py` 的建议生成逻辑——放行框架只在其**调度出口**叠加模式控制。
- 提交门槛保持既有逻辑（`improvement>=0.05`、`usage>=min_usage` 等）；新增回归门禁（任务1）为可开关的附加门槛。
- 默认态安全底线：任何放行动作默认 `dry_run`；`rollout` 必须同时满足"回归门禁 PASS + 人工/规则审批通过"。
- 越级拦截：未经审批的提交、脱离框架的直接写操作一律禁止（代码审计可证零绕过路径）。
- 所有动作可回滚（`rollback_version` / 工作流快照 / 文件级快照），回滚后行为与旧版本一致（快照比对）。

## 4. 执行步骤

### Step 1：放行状态机设计
- 定义 `learning.rollout` 配置 schema：`<action>.mode`（dry_run/observe/confirm/rollout）、`<action>.rollout_ratio`（0-1，默认 0.1）、`<action>.kpi_rollback_window_weeks`（默认 2）。
- 新增 `agent/learning/rollout_controller.py`：统一读配置、判定当前模式、暴露 `can_commit(action)` / `preview(action)` / `approve(action)` / `rollback(action)`。

### Step 2：observe 态实现
- 三类执行体在 observe 态：跑完整流程（含真实评估、候选生成），结果仅写 `EvolutionArchive`（decision=preview）+ `data/learning/rollout_audit.jsonl`，零提交/零 KPI/零版本变更。
- observe 数据同时喂给任务2 监控（"预演采纳率"指标，与真实采纳率区分）。

### Step 3：confirm 态实现
- 复用 `approval.py` 审批链：产物 → 审批队列 → 人工批准 → 提交（`bump_version` 快照）→ 写谱系 decision=approved。
- 提交前强制回归门禁（任务1）：PASS 才可提交；FAIL/NO_SAMPLES 记录并跳过（或按配置进入人工复核）。

### Step 4：rollout 态实现
- 按 `rollout_ratio` 比例命中新版本；命中失败自动回退上一版本并告警（复用 `rollback_version`）。
- 在线保守观察期（G5 第二层）：任务2 监控连续 2 个评估周期任一 KPI 恶化 → 自动回退 + 告警（判据可配置）。

### Step 5：总开关与审计
- 一键总开关 `LEARNING_ROLLOUT_MASTER_ENABLED`（默认 false）：false 时所有动作强制 dry_run。
- 审计字段统一：`action / mode / candidate_id / parent_record_id / decision(preview|approved|rejected|rolled_back) / before_version / after_version / regression_result / kpi_snapshot / rollback_command`。

### Step 6：测试与文档
- 新增单测：四态行为（observe 零提交、confirm 未审批零提交、rollout 比例命中与自动回退、总开关强制 dry_run）、越级拦截、审计完备。
- 产出变更说明 + 放行操作手册（人工确认流程）。

## 5. 预期成果（交付物）

1. `agent/learning/rollout_controller.py` 四态放行框架 + `learning.rollout` 配置段。
2. 三类进化动作接入放行框架（observe/confirm/rollout 三态可逐级启用，默认 dry_run）。
3. 回归门禁（任务1）与 KPI 监控（任务2）在 confirm/rollout 路径的接线。
4. 全链路审计 + 一键总开关 + 放行操作手册。
5. 变更说明 + 新增单测全部通过。
