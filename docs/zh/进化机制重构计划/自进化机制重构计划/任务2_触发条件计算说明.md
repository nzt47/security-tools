## 一、总则

报告 §5.2 承诺"所有触发条件均使用 T03 已定义 KPI 或可直接从审计日志计算的统计量，
无主观判断型门槛"。本说明把每条触发条件翻译为**可执行判定规则**，并披露口径、边界与
示例数据。判定由查询层（`evaluate_trigger_conditions`）完成，"连续 4 周"不依赖人工判断。

**KPI 编号约定**（TASK-08 §3.3）：
KPI#1 token 复用率；KPI#2 Skill 命中率；KPI#3 工作流命中率；KPI#4 分类型失败率；
KPI#5 反馈均分趋势；KPI#6 沉淀增量；KPI#7 进化采纳率。

## 二、公共口径

### 2.1 周桶定义

- 以 **ISO 周**（周一起始、周日结束）为统计桶；周标签形如 `2026-W34`。
- 判定窗口 = 最近 N 个**有数据** ISO 周（含当前进行周；N 默认 4，
  `config.yaml learning.metrics.trigger_monitoring.window_weeks`）。
- 周内某 KPI 无数据（无交互/无任务/无候选等）→ 该周对该 KPI **不可度量**。

### 2.2 连续 N 周判定规则

对窗口内每一周逐项判定；**任一不可度量周 → 整条件 `insufficient_data`**（绝不判命中）：

```
hit  = 窗口内每周均满足阈值 且 每周均可度量
insufficient_data = 窗口内存在不可度量周（或系统运行不足一个窗口）
not_hit = 窗口内存在可度量周但不满足阈值
unknown = 依赖的外部输入缺失（如沙箱回放统计未接入）
```

> 设计取舍：不可度量周不按"假设满足"处理，宁缺毋滥——避免把数据缺失误判为触发。

### 2.3 环比口径

- **KPI#1 环比无提升** = 最新周 token 复用率 ≤ 前一周复用率
  （双方均需有 token 数据：`total > 0`；否则不可度量）。
- **KPI#5 均分下降** = 最新周反馈均分 < 前一周反馈均分
  （双方均需有反馈数据：`count > 0`；否则不可度量）。

### 2.4 KPI 周值口径（与 TASK-03 快照一致）

| KPI | 周值口径 |
|---|---|
| KPI#1 token 复用率 | 周节省 / (周消耗 + 周节省) |
| KPI#2 Skill 命中率 | 周语义命中 / 周语义查询（观察埋点默认关，不污染分母） |
| KPI#3 工作流命中率 | 周 workflow 命中 / 周交互总数 |
| KPI#4 分类型失败率 | 周 failed / 周 total（按 task_type；阈值用原始值比较） |
| KPI#5 反馈均分 | 周反馈评分均值（0-5） |
| KPI#6 沉淀增量 | 周新增 Skill/工作流/经验/知识卡片/反思 数 |
| KPI#7 进化采纳率 | 周采纳候选 / 周候选（候选数 < N → 该周 `insufficient_data`） |

## 三、五条触发条件（§3.3 + §5.2）

### TC-1 引入 LLM-as-Judge（评估角色化）

- **报告原文**：KPI#7 进化采纳率连续 4 周 <5% 且 KPI#1 token 复用率环比无提升。
- **判定规则**：
  1. 窗口内每周：候选数 ≥ `min_candidates`（默认 5）且 采纳率 < 5%；否则该周不可度量；
  2. KPI#1 环比：最新周复用率 ≤ 前一周复用率。
- **边界**：候选基数不足的周不参与统计（dry-run 期候选为 0 → 全 `insufficient_data`，
  不误触发）；KPI#1 无 token 数据时环比不可度量。
- **示例**（`test_kpi7_4week_streak_tc1_hit`）：4 周每周候选 10、采纳 0（0%<5%）；
  前一周复用率 0.333、最新周 0.2（无提升）→ **命中**。
  任一候选周 <5 → `insufficient_data`（`test_kpi7_insufficient_data_blocks_4week_streak`）。

### TC-2 Solver 路径增强

- **报告原文**：KPI#3 工作流命中率连续 4 周 <10%。
- **判定规则**：窗口内每周 交互数 > 0 且 命中率 < 10%。
- **边界**：周交互数为 0 → 不可度量（无流量无意义）。
- **示例**（`test_tc2_solver_enhancement_hit`）：4 周每周 100 交互、3 命中（3%<10%）→ **命中**。

### TC-3 启用课程难度自适应

- **报告原文**：KPI#4 分类型失败率（task_type 维度）连续 4 周 >30% 且 KPI#5 反馈均分下降。
- **判定规则**：
  1. 窗口内每周存在任务数据（total>0）且**任一分类型**失败率 >30%；
  2. KPI#5 环比：最新周均分 < 前一周均分。
- **边界**：复杂度维度（COMPLEX）为任务7 接线后的扩展项（本任务已预留扩展键，
  默认无数据）；无任务数据周不可度量。
- **示例**（`test_tc3_course_adaptation_hit`）：4 周每周 llm 类 10 任务 5 失败（50%>30%），
  前周均分 4、最新周 3（下降）→ **命中**。

### TC-4 启用沙箱回放

- **报告原文**：沙箱回放覆盖率 <50% 且 KPI#6 沉淀增量停滞。
- **判定规则**：
  1. 回放覆盖率 < `replay_coverage_threshold`（默认 0.5）——**外部输入**
     （`/api/learning/metrics/trigger?replay_coverage=0.4` 或运维统计源），未接入 → `unknown`；
  2. 窗口内每周沉淀产物数 == 0（停滞，默认阈值 0）。
- **边界**：回放统计为"T03 + 回放统计"双来源中非 KPI 部分，本任务以参数注入；
  任务5/6 事件管线开启后接真实数据源。
- **示例**（`test_tc4_sandbox_replay_hit_and_unknown`）：4 周无沉淀 + 覆盖率 0.4 → **命中**；
  未传覆盖率 → **unknown**（不触发）。

### TC-5 启动元规则级递归自进化（L3 研究）

- **报告原文**：上述三项全部触发 + 审计通过率连续 3 个月 100% + 零安全事故 +
  G1-G5 全部实现 + 决策层书面批准。
- **判定规则**：
  1. 可计算部分：TC-1 ∧ TC-3 ∧ TC-4 全部命中；
  2. 外部前置：`audit_ok` / `g1_g5_ready` / `decision_approval`（参数注入，
     由任务4 护栏状态服务与决策流程提供）——任一缺失 → `unknown`（不判命中）。
- **边界**：L3 为远期研究红线，本条件命中仅表示"可进入 L3 研究评估"，
  任何实现仍须走任务4 元规则版本化 + 审批链。
- **示例**（`test_tc5_l3_research_hit`）：TC-1/3/4 全命中 + 三外部前置全 True → **命中**；
  外部前置缺失 → **unknown**（`test_tc5_l3_unknown_when_externals_missing`）。

## 五、持久化与跨重启（"连续 4 周"统计前提）

- 默认**关闭**（`learning.metrics.persistence.enabled: false`）：进程内内存聚合，
  周级统计在内存镜像（`_daily_events`）上工作，跨重启不保留。
- 灰度开启（`enabled: true`，环境变量 `LEARNING_METRICS_PERSIST_*` 可覆盖）：
  事件经 `lm_daily_agg` 落库（I/O 不进锁、DB 失败自动降级内存聚合 + warning）；
  重启后新实例从 DB 回填内存镜像，"连续 4 周"窗口可累计。
- 验证：`tests/unit/test_learning_metrics_triggers.py::test_persistence_restart_weekly_window_accumulates`
  （写 4 周数据 → flush → 新实例同路径加载 → 周序列与触发判定一致）。
- 灰度步骤：先在灰度环境置 `enabled: true` 运行 ≥4 周观察周序列完整 → 再评估
  `insufficient_data` 收敛 → 触发条件才具备判定意义（与任务3 放行联动）。

## 六、数据可用性看护

`insufficient_data` 本身是运维信号（告警 `LearningTriggerDataInsufficient`）：
- KPI#4 长期无数据 → 检查 `record_task_result` 生产调用方是否被禁用/短路；
- KPI#7 长期 `insufficient_data` → evolver 仍处 dry-run（任务3 放行后产生真实候选）；
- 跨重启丢失 → 检查持久化是否启用。
