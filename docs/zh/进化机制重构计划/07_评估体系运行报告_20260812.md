## 2. 全量评估各阶段耗时分布（真实沙盒）

样本池：`data/evals/`（search/code/chat 各 5 条，共 15 条），沙盒脚本为每技能临时仓库 `scripts/main.py`。

| 类别 | 判定路径 | stage1_ms | stage2_ms | total_ms | 执行次数 | 每样本执行 | used_tokens |
|------|----------|-----------|-----------|----------|----------|------------|-------------|
| search | contains / json[found]（有 expected_output） | 63 | 422 | **485** | 1+5=6 | 1 | 215 |
| code | validator 精确判定（有 expected_output） | 62 | 328 | **390** | 1+5=6 | 1 | 215 |

关键日志（`staged.stage2.done`）：

## 3. chat 类 stage2 瓶颈定位（自一致性路径拆解）

对 chat 单样本（`chat-001`）逐环节计时（真实沙盒 runner）：

| 环节 | 耗时 | 说明 |
|------|------|------|
| ① 首次沙盒执行 | 62.0 ms | `subprocess.run` 冷启动 + 脚本执行 |
| ② 第 2 次沙盒执行 | 78.0 ms | 自一致性重复 |
| ③ 第 3 次沙盒执行 | 63.0 ms | 自一致性重复 |
| ④ Jaccard 相似度计算 | **0.0 ms** | 计算本身可忽略 |
| 自一致性路径合计 | **203.0 ms** | 沙盒执行 203 + 相似度 0 |
| ⑤ 反馈信号查询 | 15.0 ms | 首查；后续缓存命中 ~1ms |

**对照实验（dry runner，无子进程）**：

```
chat 全样本（5 条 × 3 次 = 15 次执行）dry runner 总耗时 = 0.0 ms
```

**瓶颈判定**：

- 自一致性评分的**计算逻辑不是瓶颈**（Jaccard ≈ 0ms，dry runner 15 次执行 ≈ 0ms）；
- **瓶颈是「3 次重复执行 × 每次独立子进程冷启动」**。每次 `SkillExecutor.execute` 都启动一个全新 Python 解释器（~60-98ms），chat 全量 15 次子进程 ≈ 15 × 60ms ≈ 900ms，与实测 stage2_ms=921ms 完全吻合；
- 反馈查询（每样本 1 次，~1ms 缓存后）与相似度计算均可忽略。

**优化方向（待评估，不改变评估正确性前提）**：

1. **降执行次数**：`EVAL_CONSISTENCY_RUNS=3 → 2`（每样本 2 次执行，仍可计算一致性），stage2 预期 ~921 → ~620ms；
2. **并行执行**：同一样本的多次重复执行互不依赖，可用 `concurrent.futures.ThreadPoolExecutor` 并行启动子进程（注意 I/O 密集可并行，CPU 密集需进程池）；
3. **子进程复用**：改造沙盒为长驻 worker（stdin/stdout 协议），避免每次冷启动；代价是安全边界收紧，需按「不可信代码执行必须 multiprocessing 隔离」约束审慎评估；
4. **类别差异化**：对 chat 类单独调参（更少 runs + 更强反馈权重），而非全局统一。

## 4. 预算熔断统计

### 4.1 触发方式（场景3：强制熔断）

`stage1_budget_tokens=1`（极小预算），3 条 search 样本。

### 4.2 熔断链路日志证据

```
stage1.start  sample_ids=b-001 budget_tokens=1
budget.break  stage=stage1 sample=b-001 input_estimate=10 used=10 budget=1 executed=0 skipped_remaining=1
eval.budget_exceeded  used=10 budget=1 executed=0 sample_total=1
stage1.abort  status=budget_exceeded samples=0 used_tokens=10 budget=1
```

### 4.3 统计口径

| 指标 | 值 |
|------|-----|
| 熔断类型 | 输入侧预算耗尽（输入估计 10 tokens > 预算 1） |
| 已执行样本 | 0（首样本即熔断） |
| 跳过剩余 | 1（样本池共 3 条，本轮初筛仅取 1 条） |
| 状态传播 | `budget_exceeded` → `stage1.abort`（未进入 stage2） |
| 降级策略 | 绝不伪造指标：仅返回已执行的真实结果，`score` 为已执行样本均值 |

> 说明：`budget.break` 区分输入/输出两侧超限（`input_estimate` / `output_estimate`），
> 便于区分是「任务文本过大」还是「脚本输出过大」导致的成本失控。

## 5. 样本不足分支（no_samples）

空样本池场景：

```
staged.no_samples  category=search pool_dir=... available_categories=(无) → 返回 no_samples
eval.no_samples    category=search（绝不伪造指标）
结果: status=no_samples score=0.0000 samples=0
```

**统计**：样本池为空或目标类别无样本时，评估器返回 `no_samples`，`score=0.0`、`sample_count=0`，
不执行、不评分、不进入后续阶段——满足「绝不伪造指标」的不变约束。

## 7. 结论

1. **评估正确性**：三类真实样本全量通过（success_rate=1.000，score≈0.996），分阶段判定（淘汰/熔断/无样本）均按契约工作，日志证据完整；
2. **性能**：单次真实执行成本 ~60-98ms（子进程冷启动主导），chat 自一致性 ×3 后 stage2 达 921ms，是当前最显著的优化点；
3. **预算保护**：熔断机制正常，成本失控会显式标记 `budget_exceeded` 并仅返回真实结果；
4. **下一步**：按 §3 优化方向降低 chat stage2 耗时（优先 `EVAL_CONSISTENCY_RUNS` 调参与并行化）。
