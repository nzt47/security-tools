# 知识模块性能优化建议

> 生成时间：2026-08-07
> 基线：知识模块回归测试 **339 passed / 0 失败**（见《知识模块回归测试报告》）
> 依据：agent/knowledge/ 源码静态分析 + 已埋点的耗时统计日志（distill/discuss/tools/card 全链路）

## 一、现状与性能观测能力

知识模块已完成耗时统计埋点（`agent/knowledge/observability.py` 统一出口），可观测到：
- 工具入口：`kb_distill.done` / `kb_card.ok|failed`（总耗时）
- LLM 调用点：`distill.llm_ok|llm_failed` / `discuss.llm_ok|llm_failed` / `extract.llm_ok|llm_failed`
- 引擎写操作：`create / update / delete / transition / import` 单次耗时

这些埋点形成「工具入口 → LLM 调用点 → 引擎写操作」的性能排查链路，可通过 Promtail/Loki 的
`quantile_over_time(0.99, [1h])` 观察 P99 变化，作为优化前后的量化依据。

## 二、热点分析（按影响分级）

| 级别 | 热点 | 位置 | 复杂度 | 触发场景 |
|---|---|---|---|---|
| P0 | log.md 全文件读改写 + 跨进程文件锁 | ingest.py `_append_log_line` L277 / `_FileLock` L189 / `_line_exists` L256 | O(L)* | 每次 ingest/discuss/promote/transition 写操作 |
| P0 | card.list() 全库扫描 + 全量 YAML 解析 | card.py L254-L273 | O(N·M)** | delete 入链检查 / rebuild_index / audit / list |
| P1 | _has_incoming_links 每次 delete 全扫全库 | card.py L171-L175 | O(N) | 每次 delete |
| P1 | update_index_delta 每次全量读改写 index.md | index.py L113-L198 | O(index 大小) | 每次 create/update/delete/transition |
| P1 | yaml.safe_load 每次读卡全量解析 frontmatter | card.py `_md_to_card` L82-L95 | O(frontmatter) | get/list/update 高频路径 |
| P2 | LLM 调用为主瓶颈（串行依赖） | distill.py / discuss.py（已埋点） | 外部延迟 | distill → discuss → extract 串行 |
| P2 | KnowledgeSearch 每次实例化全量重建 BM25 索引 | search.py `_build_index` L359-L368 | O(N·词) | 每次 KnowledgeSearch() 构造 |
| P2 | 敏感检测 | ingest.py `detect_sensitive` L165（已有 1MB 采样） | O(采样) | 每次入库 |

*L = log.md 行数；**N = 卡片数，M = 单卡 frontmatter 解析成本。

## 三、详细建议

### P0-1 log.md 全文件读改写（最高优先）

**现状**：`_append_log_line` 每次持锁后读整个 log.md → 全量逐行判重（`_line_exists`）→ 组装 → 全量写回。文件随知识库增长，每次操作成本线性上升；高频写操作（批量入库）时锁竞争叠加放大。

**建议（分步，可回滚）**：
1. **判重前置短路**：以 `(action, slug, date)` 组合为键维护进程内最近写入的 LRU 集合（如 100 条），命中则跳过读文件判重（覆盖同进程内重复入库主场景）。
2. **分片日志**（规模 > 1 万条时）：log.md 按 `log-YYYYMM.md` 分片，当前月文件保持小体积；`_append_log_line` 只读改写当月文件。
3. **批量入库合并写**：`ingest_file` 批量场景合并为单次追加（一次锁 + 一次写）。

**收益**：O(L) → O(1)（命中短路）/ O(月度行数)。**取舍**：分片需同步调整 logbook.append_log 与 AGENTS.md 日志契约；先做 1 低成本高收益。

### P0-2 card.list() 全库扫描

**现状**：每次 `list()` 都 glob 全部 `*.md` 并 `yaml.safe_load` 完整 frontmatter。`delete` 的入链检查、`rebuild_index`、audit 均触发，卡片量级增大后成为主要 CPU/IO 热点。

**建议**：
1. **入链索引**：维护 `knowledge/index_links.md`（slug → 入链列表，增量维护，与 index.md 同机制），`_has_incoming_links` 改为查表，O(1)；`delete` 不再全扫。
2. **mtime 缓存**：进程内按 `(path, mtime, size)` 缓存解析结果，未变更的卡片跳过 YAML 解析；配合 `list()` 全量列举场景显著降 IO。
3. `rebuild_index` 复用 list 结果时避免二次扫描。

**收益**：delete 从 O(N) → O(1)；list 从全量解析 → 仅解析变更卡。**取舍**：入链索引是新的可持久化产物，需与 index.md 保持一致性测试（对齐 update_index_delta 模式）。

### P1-1 _has_incoming_links 每次 delete 全扫

**现状**：`delete` 每删一张卡就对全库 `list()` 一次检查入链，批量删除为 O(N²)。

**建议**：并入 P0-2 的入链索引后自然消除；在索引落地前，可先做**批量删除接口**（一次扫描维护引用计数，多个待删 slug 并行校验），避免 N 次全扫。

### P1-2 index.md 全量读改写

**现状**：`update_index_delta` 每次写卡都 `read_text` 整个 index.md → 修改 → 原子写。已是增量语义（不重扫全库，好），但单次成本仍随 index 体积线性增长。

**建议**：
1. **追加 + 定期重整**：条目追加到 section 末尾（保持幂等判定），每 100 次写或每日 `rebuild_index` 重整一次排序，把 O(index) 摊薄为 O(1) 追加。
2. index.md 超过阈值（如 5000 行）时强制走分片或按类型拆分（concepts/entities/insights 三个文件）。

**收益**：高频写路径 O(index) → O(1)。**取舍**：追加模式需保证「增量叠加 = 全量重建」不变式（现有测试已锁定）。

### P1-3 yaml.safe_load 全量 frontmatter 解析

**现状**：`_md_to_card` 每次读卡都完整 `yaml.safe_load` frontmatter 并构造 Card；`get` 在 `create` 冲突检查、`update`、`list` 中高频触发。

**建议**：
1. **lazy 解析**：`get`/冲突检查只需 slug 存在性（文件路径命中即可），避免 YAML 解析；仅在真正需要 Card 字段时解析。
2. frontmatter 字段裁剪：metadata 为空时不解析（`_card_to_md` 已不写空 metadata）。

### P2-1 LLM 调用链（外部延迟主瓶颈）

**现状**：distill → discuss → extract 为串行 LLM 调用，单次 50ms~秒级；已埋点可观测。降级铁律保证异常不中断，但正常路径的延迟直接决定闭环总耗时。

**建议**：
1. **结果缓存**：以 `(source_hash, system_prompt)` 为键缓存提炼结果（幂等命中已有 source_hash 基础，可扩展为产物级缓存），重复入库零 LLM 开销。
2. **讨论并行化**：多素材讨论场景改为并发（ThreadPoolExecutor 上限 3），提取与讨论解耦并行。
3. **超时收敛**：`kb_*` 工具侧对 LLM 设置有界超时（如 10s），避免极端场景拖长链路（超时降级已由测试锁定）。

### P2-2 KnowledgeSearch 每次实例化全量重建 BM25

**现状**：`__init__` 即 `_build_index` 全量构建 BM25（遍历全部卡片分词），高频构造（工具每次调用）成本重复。

**建议**：
1. **模块级缓存**：以 `(wiki_root, 卡片集合签名)` 为键缓存 BM25Index，实例化复用。
2. 卡片增量时惰性重建（变更计数触发）。

## 四、落地优先级

| 批次 | 事项 | 理由 |
|---|---|---|
| 第一批（低成本高收益） | P0-1.1 判重短路 / P1-3 lazy 解析 / P2-2 索引缓存 | 改动局部、不触碰持久化契约、回归风险低 |
| 第二批（需一致性测试） | P0-2 入链索引 / P1-1 批量删除 / P1-2 index 追加+重整 | 引入新的可持久化产物或格式变更，须补一致性测试 |
| 第三批（外部依赖治理） | P2-1 LLM 缓存 / 并行 / 超时收敛 | 涉及 LLM 行为与并发，须以耗时埋点量化后再动 |

## 五、验证方式

- **回归**：每批改动后运行知识模块 339 项测试（`test_knowledge_*.py`），重点盯
  `test_knowledge_card.py`（41 项）与 `test_knowledge_workflow.py`（12 项）的一致性断言。
- **量化**：优化前后对比 `distill.llm_ok / promote.card_ok / kb_distill.done` 的
  `duration_ms` P99（Loki `quantile_over_time`），预期 log.md/index.md 相关写路径降幅最大。
- **不变量守护**：幂等（零副作用）、只读素材（sha256 校验）、降级铁律（不抛异常）
  三类不变量测试不得因优化被破坏。

## 六、结论

知识模块当前性能瓶颈集中在**文件读改写型热点**（log.md / index.md / 全库 list），
而非计算密集；优化核心是「减少全量读改写与重复解析」，第一批即可释放主要收益，
且不触碰降级铁律、幂等、只读素材等核心不变量。
