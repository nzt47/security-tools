## 2. 判据（按优先级）

1. **硬证据**：工具自我声明不可用 / 空实现 / 实现与声明不符（如 `schedule_task`）；
2. **重复或近义**：同一动作两个入口（要写明差异，否则合并）；
3. **schema 过宽**：≥10 个参数或 10+ 个 action（模型容易选错，也是拆分信号）；
4. **零调用**：只作参考，**不作删除依据**（"没调用"常是描述差/选不到，不是没用）。

## 5. 拆分试点：`byted_bp_cdn_pagesdeploy`

现状：1 个工具 13 个参数、`action` 有 15 个取值（deploy/list/get/deployments/serve/domain-*/offline/
delete/subscribe-cdn/save-credentials/setup/detect），模型要一次记全才能正确调用。

目标形态（一个动词一个工具 + 兼容壳）：

| 新工具 | 覆盖的 action | 说明 |
|---|---|---|
| `pages_list` | list / get / deployments | 只读查询 |
| `pages_deploy` | deploy / serve | 需要 `name+dir`（含 index.html 校验） |
| `pages_domain` | domain-add / domain-verify / domain-del / domain-list | 域名绑定 |
| `cdn_subscribe` | subscribe-cdn | 走 `subscribe_cdn.py` |
| `pages_admin`（壳，保留） | offline / delete / setup / save-credentials / detect | 危险动作与引导，保留 `action` 派发 |

验收（有环境时）：先只读 `list` 跑通 → 用临时目录验证 `pages_deploy` → 最后验证旧壳转发。
拆分会让工具数 +4，要在主线档案里看模型选择率是否变好，而不是只看"能不能调"。

## 6. 新工具怎么进工具集（现状）

1. **只从吞噬进**（tool 形态草稿：manifest + 骨架 + YAML + 来源脚本）；
2. **AI 实现 + 静态校验**（`POST …/implement`：语法 / 顶层语句 / TOOL_SCHEMA / 危险调用 / 硬编码密钥）；
3. **登记**（`POST …/register-tool` → `ToolGenEngine.generate_persistent` + `persist_dynamic_tool`）：
   AST + 子进程校验、写 `custom/`、台账、治理 YAML，**风险默认 critical**（调用要审批）；
4. **启动加载**进注册表（#1322 起不再依赖"恰好调用过扩展工具"）；
5. 界面「工具调用」可见、可停用；说明与可调用性徽章见 #1322。

**已知缺口**：可调用性清单是提交产物，运行期登记的工具不在里面 ⇒ #1322 用 `scope=runtime`
在请求期补算；若要成为"一等公民"，需把登记产物入库并重派生清单（需人工评审 AI 代码）。
