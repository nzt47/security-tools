## 一、设计文件审计摘要

### 1.1 合理性评估

设计文件《最好的个人知识库》提出的 **LLM-Wiki 理念**（从"囤积信息"到"经营认知"、三层内容 + 一层宪法、目录表达状态、人机协同工作流、AI 簿记/人思考）整体成立，可作为云枢知识层演进方向。

### 1.2 设计文件存在的理论/实践缺陷

| # | 缺陷 | 影响 | 重构应对 |
|---|------|------|----------|
| 1 | 无检索质量设计（纯双向链接导航，无向量检索/重排） | 知识库规模增长后检索必然失效 | 任务 4 复用云枢存量混合检索 + reranker |
| 2 | "AI 维护成本接近零"过度乐观（每次全量扫 wiki 更新 index） | token 成本与漂移风险随规模线性增长 | 任务 5 增量索引（文件监听） |
| 3 | 知识生命周期与"目录表达状态"矛盾（移动文件破坏链接） | 状态迁移需移动文件 → 全量重链 | 任务 2 用 frontmatter 状态字段 + 仅 Archive 移动 |
| 4 | 冲突标记无闭环（标记后谁决策） | 矛盾无限累积 | 任务 5 冲突裁决协议（状态机） |
| 5 | 无隐私/权限/多租户 | 敏感信息泄漏面 | 任务 1/7 复用 SensitiveDataFilter + 边界护栏 |
| 6 | 无自动化审计调度（靠人记得体检） | 知识库腐烂 | 任务 5 定时任务（复用 task_scheduler） |

### 1.3 云枢现状差距矩阵

| 设计层 | 云枢现状 | 差距 |
|---|---|---|
| 素材层 | sensor 感知、文件监听、无收集入口 | 无显式收集箱与入库通道 |
| 中间层 | 对话摘要（summarizer），非知识提炼 | 无"原文→结构化笔记"提炼管线 |
| 知识层 | KnowledgeBase 仅 add_document/query 薄封装 | 无知识卡片 schema、双向链接、矛盾标记、交叉引用 |
| 规则层 | .superpowers/CLAUDE.md 是贡献指南 | 无知识库宪法；无 index.md/log.md 概念 |
| 生命周期 | MemoryReviewer 有 stale/duplicate | 无 draft/current/archive/unknown 状态机 |
| 检索 | **已有**混合检索 + rerank（优势） | 未面向知识库语义，需接线 |
| 前端 | yunshu-ui 会话/技能管理 | 无知识卡片/关系视图 |

## 二、重构计划总览

**结论：必须分阶段。** 现有记忆系统接口（`MemoryInterface`、`HolographicAdapter`、`VectorStore`、`MemoryManager`）是【不易】硬约束，不可破坏；知识层是全新子系统，渐进叠加。

7 个阶段按"契约 → 管道 → 核心 → 提炼 → 检索 → 治理 → 前端 → 闭环"推进，每阶段可独立交付、可回滚。

### 2.3 执行顺序建议

1. 先并行启动 **任务0、任务1、任务2**（任务0 是全部契约来源，先产出 1-2 天供后续引用）。
2. 任务1 完成后再启动任务3；任务2 完成后再启动任务4。
3. 任务5、6 可并行（分别依赖任务2/4）。
4. 最后任务7 打通闭环。

### 2.4 通用验收底线（所有任务适用）

- 本任务新增测试全绿，覆盖率 ≥ 80%（任务0 要求 ≥ 85%）。
- 既有测试全量回归通过（不破坏现有接口）。
- 新增模块不反向依赖现有记忆模块（`memory/`、`agent/memory/`），如需使用只能通过已定义接口。
- 所有对外 API 遵循云枢 `log_dict` 结构化日志规范。
