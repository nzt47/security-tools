# 双链扩展性能压测报告（内存链接缓存前后对比）

- **日期**：2026-08-07
- **关联模块**：`agent/knowledge/search.py`、`agent/knowledge/link_cache.py`、`agent/utils/periodic_sampler.py`
- **关联任务**：任务4 知识检索整合（验证加固轮 · 双链扩展性能优化）
- **压测脚本**：`scripts/dev/benchmark_knowledge_search.py`、`scripts/dev/stress_knowledge_search.py`

## 1. 背景与目标

知识检索热路径（双链扩展 `_link_recall`）此前每次 search 都逐条执行
`resolve_link → CardStore.get`（文件 I/O + 读锁等待），上一轮链路内分段计时
实测该阶段占总耗时 **99%+**（读写混跑下 avg≈75.7ms / p95≈107.9ms）。

本轮实施「构造期预计算链接缓存」（`LinkCache`，与 `_cards`/`_bm25` 索引同
快照语义，写后重建 searcher 即刷新），目标：验证优化前后 QPS 与 P99 延迟变化。

## 2. 压测方法

| 项 | 说明 |
|---|---|
| 数据集 | 复杂双链关系库 10 卡（含链式/环形/互引/断链/归档/反向链接，`verify_knowledge_search.py --complex` 数据集）|
| 向量路 | 关键词伪向量路（content 命中「调参/数据/特征」即召回）|
| 查询负载 | 混合 7 查询（命中/部分命中/未命中），固定随机种子保证两模式负载一致 |
| legacy 模式 | 模拟优化前：双链扩展逐条 `resolve_link→CardStore.get`（文件 I/O + 读锁）|
| cache 模式 | 优化后：双链扩展走预计算内存缓存（零文件 I/O、零读锁）|
| 度量 | QPS（请求/秒）+ p50/p95/p99/max 延迟（每调用 `perf_counter` 计时）|
| 并发 | 8 线程 ThreadPoolExecutor 并发，n=100（预热 3 次后计时）|
| 硬件 | 本地 Windows（Asia/Shanghai 时区），同一进程内 A/B 对比，消除硬件差异 |

## 3. QPS / P99 对比（8 线程并发，实测）

| 指标 | legacy（优化前） | cache（优化后） | 提升 |
|---|---|---|---|
| **QPS** | 213.3 | 5811.0 | **27.2x** |
| **P99 延迟** | 51.14 ms | 0.489 ms | **105x 提速** |
| P95 延迟 | 49.04 ms | 0.278 ms | 176x |
| P50 延迟 | 37.71 ms | 0.132 ms | 286x |
| mean 延迟 | 35.73 ms | 0.153 ms | 234x |
| max 延迟 | 51.14 ms | 0.489 ms | 105x |

> 首轮基准（重构前）测得 legacy QPS 207.6 / P99 49.9ms → cache QPS 6876.3 /
> P99 0.256ms（QPS 33.1x、P99 195x）。工具类封装重构后性能无回归
> （QPS 27.2x、P99 105x，波动属正常环境噪音）。

## 4. 链路内分段耗时对比（642 样本，含读写混跑，stress 脚本实测）

| 阶段 | 优化前 avg | 优化后 avg | 说明 |
|---|---|---|---|
| bm25 | 0.021 ms | 0.020 ms | 纯内存倒排 |
| vector | 0.048 ms | 0.045 ms | fake 向量路 |
| **link（双链扩展）** | **75.657 ms** | **0.032 ms** | **约 2360x 提速，瓶颈消除** |
| rrf | 0.098 ms | 0.083 ms | 纯内存融合 |
| rerank | 0.022 ms | 0.020 ms | 未启用（降级原序）|
| assemble | 0.021 ms | 0.017 ms | 组装 hits |
| **total** | **75.97 ms** | **0.303 ms** | **约 250x 提速** |

关键观察：优化前 link 阶段占总耗时 99%+，且读写混跑时被 CardStore 写锁等待
放大（max 128.98ms）；优化后热路径零文件 I/O、零读锁等待，max 仅 0.24ms。

## 5. 优化方案（已落地）

1. **`LinkCache` 预计算缓存**（`agent/knowledge/link_cache.py`）：构造期用
   `resolve_link + 内存 store 鸭子类型`一次性把每卡 links 解析为内存 slug，
   热路径 `_link_recall` 纯内存查缓存。语义与实时解析完全等价（断链/归档/
   损坏/快照外新增卡一律跳过，46 项既有测试全绿确认）。
2. **耗时日志采样率**（`agent/utils/periodic_sampler.py`）：`PeriodicSampler`
   按调用次数周期确定性抽样（`KNOWLEDGE_TIMING_SAMPLE_RATE`，默认 0.1，
   每 10 次 search 输出 1 条 `search_stage_timing`），生产降噪，实测 rate=0.1
   → 30 次调用输出 3 条。
3. **并发稳定性**：读写锁（`_RWLock`）写串行化 + 读并发，压测双场景
   （纯读 320 次 + 读写混跑 80 组 CRUD）全部通过，库最终一致。

## 6. 结论

- 内存链接缓存将检索 P99 延迟从 **51ms 降至 0.49ms**，QPS 从 **213 提升至 5811**
  （约 27 倍），双链扩展阶段耗时占比从 99%+ 降至可忽略水平。
- 缓存为快照式语义，写路径刷新方式与 BM25 索引一致（重建 searcher），
  无缓存一致性维护成本。
- CI 已纳入性能回归（`tests/unit/test_knowledge_search.py::TestLinkCachePerfRegression`）：
  结构断言（热路径不读 CardStore）+ 耗时断言（link < 20ms），确保缓存策略不退化为文件 I/O。
