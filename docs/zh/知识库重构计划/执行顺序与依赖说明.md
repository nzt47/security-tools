## 三、逐任务依赖说明

### T0 · 知识库宪法与目录/卡片 Schema 定义
- **前置依赖**: 无
- **为什么最先**: 全部后续任务依赖其产物——目录结构（`knowledge/`）、`AGENTS.md` 规则、Card Schema（`agent/knowledge/schema.py`）、生命周期状态机（`agent/knowledge/lifecycle.py`）。此契约是"单一事实源"，后续任务只引用不改。
- **启动建议**: 先启动 T0，定稿契约后并行启动 T1/T2。

### T1 · 素材层 Ingest 管道
- **前置依赖**: T0（目录结构 + `slugify`）
- **消费产物**: `knowledge/raw|inbox/`、`agent/knowledge/logbook.py`（log.md 追加）
- **为谁提供输入**: T3 提炼管线消费 inbox 素材。

### T2 · 知识层卡片引擎（核心）
- **前置依赖**: T0（Card schema + 状态机）
- **消费产物**: CardStore（`agent/knowledge/card.py`）、链接解析（`links.py`）、index 维护（`index.py`）
- **为谁提供输入**: T4/T5/T6 均依赖 CardStore。

### T3 · 中间层提炼管线
- **前置依赖**: T0、T1
- **消费产物**: T1 的 inbox 素材；`logbook.append_log`
- **注意**: 依赖 T1 必须先完成（提炼需消费 ingest 产物）。

### T4 · 知识检索整合
- **前置依赖**: T2
- **消费产物**: CardStore、links；复用现有 hybrid + reranker（不修改它们）
- **为谁提供输入**: T5（矛盾检测可选）、T6（`/api/knowledge/query`）。

### T5 · 治理巡检与冲突裁决
- **前置依赖**: T2、T4
- **消费产物**: CardStore、links、index、`KnowledgeSearch`（可选）
- **与 T6 可并行**: 二者互不依赖，仅共同依赖 T2/T4。

### T6 · 前端知识库视图与 API
- **前置依赖**: T2、T4
- **消费产物**: CardStore CRUD、融合检索 API。
- **与 T5 可并行**: 是。

### T7 · 人机协同闭环工作流
- **前置依赖**: T2、T4、T5
- **消费产物**: T2 CardStore、T4 KnowledgeSearch、T5 lint/resolve_conflict。
- **为什么最后**: 编排全部下游能力（capture→distill→discuss→card→audit），任一前置缺失都会断链。

## 四、并行调度建议

```
T0 ────────► 定稿契约
  │
  ├─► T1 ──► T3
  │              ──► T5 ──┐
  └─► T2 ──► T4           ├─► T7
                  ──► T6 ──┘
```

1. **首批**: T0（契约先行，其余任务等待其 schema 定稿）。
2. **第二批（并行）**: T1 + T2。
3. **第三批**: T3（依赖 T1）+ T4（依赖 T2）。
4. **第四批（并行）**: T5 + T6（均依赖 T2/T4）。
5. **末批**: T7（依赖 T2/T4/T5）。

## 五、执行要点

- 每批任务独立验收（测试全绿 + 覆盖率门槛 + 回归通过），完成后才进入下一批。
- T0 的 `AGENTS.md` 与 `schema.py`/`lifecycle.py` 命名必须一致（单一事实源），后续任务不得擅自改动契约。
- 【不易】约束贯穿全程：不修改现有 `MemoryInterface`、`VectorStore`、`tool_router_hybrid.py`、`tool_router_reranker.py`。
- 若契约需变更，先更新 T0 文档再通知下游，禁止任务内自行偏离。
