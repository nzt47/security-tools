# CI 修复与单测脚本总结（2026-08-11）

> 本文记录知识库重构流水线（`.github/workflows/knowledge-tasks.yml`）接入 CI 时踩到的
> **两个真实坑点**与解决方案，以及配套本地单测脚本的定位。用于后续维护同类守卫流水线时避免重蹈覆辙。

## 一、坑点 1：CI 环境没有 pytest

### 现象
手动触发流水线 `run_knowledge_tasks.py` 时，在「交付物验证 + 全量任务测试」步骤直接失败：

```
/opt/hostedtoolcache/Python/3.10.20/x64/bin/python: No module named pytest
```

### 根因
workflow 的「安装依赖」步骤只执行了 `pip install -e .`。测试依赖（pytest 全家桶）**不会**随
`-e .` 安装——主 CI（`.github/workflows/ci.yml`）的测试作业是**显式**安装 pytest 全家桶的，
新 workflow 未对齐该惯例。

### 解决方案
「安装依赖」步骤对齐主 CI 惯例，显式安装与 ci.yml 完全一致的测试依赖：

```yaml
- name: 安装依赖
  run: |
    python -m pip install --upgrade pip
    pip install pytest pytest-cov pytest-xdist pytest-mock pytest-timeout pytest-asyncio pytest-randomly
    pip install -e .
```

同时在 push / pull_request 的 `paths` 中纳入 `.github/workflows/knowledge-tasks.yml` 自身，
使 workflow 配置改动也能自动触发自检（配置即测试对象）。

### 教训
**新 workflow 的依赖安装必须对齐仓库主 CI 的既有惯例**，不能假设 `pip install -e .` 覆盖测试环境。
配套把「安装依赖」清单当作可复用的基线。

## 二、坑点 2：共享 concurrency 组导致 workflow 被取消

### 现象
修复坑点 1 后重新 push，自动触发的流水线 run **1 秒即被取消**（status: cancelled），日志无任何错误。

### 根因
仓库「排队治理」（P2-4）让全部高频 push workflow 共享 concurrency 组 `ci-${{ github.ref }}`
（`cancel-in-progress: true`）。其语义是：**同 ref 下多 workflow 并发触发时，只有最新注册的一个
run 存活，其余全部取消**。一次 push 同时触发 5 个 workflow（ci.yml、核心不变量监控、知识库重构检查等），
我的 workflow 成为被取消的一方（幸存的是「日志性能守护」），因此守卫类流水线形同虚设。

### 解决方案
守卫类流水线**独立成组**，不参与主 CI 的共享排队池：

```yaml
# 独立分组：保证 knowledge 变更必跑、不被主 CI 批次挤掉；
# 仍保留「连续 push 只留最新」语义（同组内 cancel-in-progress: true）
concurrency:
  group: knowledge-tasks-${{ github.ref }}
  cancel-in-progress: true
```

### 教训
- 共享 concurrency 组的设计意图是**合并高频 push 的排队**，适用于主 CI 这种重型流水线；
  但**守卫/门禁类流水线共享该组 = 不可靠**（大概率被同批其他 workflow 取消）。
- 判断「是否独立成组」看流水线职责：主 CI（可容忍被下一批替代）→ 共享组；
  守卫/发布（必须可靠执行）→ 独立组，且发布类还应 `cancel-in-progress: false`（防半发布态）。

## 三、本地一键单测脚本：`scripts/run_all_unit_tests.ps1`

用于**快速验证 watcher/ingest 改动是否影响其他模块**，两级流程：

| 阶段 | 内容 | 耗时量级 | 失败行为 |
|------|------|---------|---------|
| ① 快速回归 | `tests/unit/test_knowledge*.py` + `test_routes_knowledge.py`（21 个文件） | 秒级 | 立即退出（快速定位受影响模块） |
| ② 全量回归 | 复用 `scripts/run_unit_tests.ps1 -Parallel`（pytest-xdist 并行，排除本地原生崩溃的 test_reranker） | 分钟级 | 透传退出码 |

用法：`.\scripts\run_all_unit_tests.ps1`（两级全跑）/ `-OnlyQuick` / `-OnlyFull`。

**注意**：Windows 下个别用例偶发 `WinError 5`（文件占用，如 `index.md.tmp → index.md` 的
`os.replace`）属瞬态抖动，单独重跑即通过，非代码回归；疑似杀软/句柄竞争，建议失败用例先重跑复验。

## 四、watcher.py 单测（`tests/unit/test_knowledge_watcher.py`）

T1 补全交付物 `agent/knowledge/watcher.py`（薄封装 `ingest.KnowledgeWatcher`，进程内单例）配套
**8 个用例**：

- 再导出一致：`watcher.KnowledgeWatcher is ingest.KnowledgeWatcher`（【不易】单一事实源）
- 单例语义（FakeWatcher 隔离，不依赖 watchdog 时序）：给定根目录单次实例化 / 重复 start 幂等 /
  stop 后重启新实例 / 无活动实例时 stop 空操作 / **单例存在但未运行的残留态会被替换**（覆盖
  `_ACTIVE is not None and _ACTIVE.is_running` 的 is_running=False 短路径分支）
- 真实 watchdog 端到端：文件落入 inbox → 自动登记 meta + log.md

该测试已挂入 `run_knowledge_tasks.py` 的 T1 测试清单，本地一键脚本与 CI 流水线均会执行。
