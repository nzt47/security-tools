# 双链保护机制 · 专项技术文档

> 生成时间：2026-08-08
> 适用范围：知识库「双链引用 → 入链索引 → 删除保护（409）」全链路
> 关联代码：[card.py](../../../agent/knowledge/card.py)、[routes_knowledge.py](../../../agent/server_routes/routes_knowledge.py)、[apiClient.ts](../../../yunshu-ui/src/lib/apiClient.ts)、[Knowledge.tsx](../../../yunshu-ui/src/pages/Knowledge.tsx)

## 1. 机制概述

知识库卡片支持 `[[双链]]` 引用。当卡片 A 的正文/links 引用卡片 B 时，B 拥有"入链"。**被引用的卡片不允许被删除**，删除时后端返回 HTTP 409 并携带引用方列表，前端弹出保护提示。

```
┌──────────┐  引用 [[B]]  ┌──────────┐
│ 卡片 A    │ ──────────► │ 卡片 B    │  ← 入链目标
└──────────┘             └──────────┘
  引用方 / 入链来源         删除 B → 409
```

## 2. 后端链路（三层）

### 2.1 双链解析（链接事实源）

- `parse_links(content)` 解析正文 `[[目标]]` / `[[目标|别名]]` → 目标列表（别名剥离、去重）。
- `CardStore.create`（[card.py](../../../agent/knowledge/card.py#L301-L321)）：`links` 显式传入优先保留；**为空则从正文解析**（与 `update` 语义对齐）。
- `CardStore.update`：每次以正文双链结果**同步覆盖** `links` 字段。

> ⚠️ 历史 Bug（已修复）：`create` 原不解析正文双链 → 新建卡 `links` 为空 → 入链索引未登记 → 删除被引用卡不触发 409。修复即上述"为空则从正文解析"。

### 2.2 入链索引（index_links.md）

| 操作 | 索引维护 |
|------|----------|
| create/update | `_sync_links_index_add`：对每个 links 目标登记 `目标 ← 本卡`（`update_links_delta(add=True)`） |
| update | 先移除旧引用（读旧卡 links），再登记新引用 |
| delete | `_sync_links_index_remove`：移除被删卡产生的引用关系 |

- 索引是**可重建的辅助文件**：写失败仅告警（`logger.warning`）不阻断卡片主操作。
- `_has_incoming_links` 优先查索引（O(1)）；索引缺失/解析失败时**回退全库扫描**（容错降级）。

### 2.3 删除保护（路由 409）

- `CardStore.delete`（[card.py](../../../agent/knowledge/card.py#L385-L400)）：写锁内先 `_has_incoming_links(slug)`，有入链 → 拒绝删除返回 `False`（不产生任何副作用）。
- 路由 [routes_knowledge.py](../../../agent/server_routes/routes_knowledge.py) DELETE：`delete` 返回 `False` → HTTP 409：

```json
{
  "error": "卡片存在入链，删除被拒: <slug>",
  "incoming_links": ["引用方1", "引用方2"],
  "ok": false
}
```

## 3. 前端提示链路

1. [Knowledge.tsx](../../../yunshu-ui/src/pages/Knowledge.tsx#L171-L187) `handleDelete`：`window.confirm` 确认 → `deleteCard(slug)`。
2. 409 响应 → `apiClient` 抛 `ApiError(status=409)`，**details 携带完整错误 body**（含顶层 `incoming_links`）。
3. 前端读取 `e.details.incoming_links`，`window.alert` 展示引用方列表：

```
删除被拒：该卡片存在入链，引用方需先解除引用。引用方: <列表>
```

> ⚠️ 历史 Bug（已修复）：`ApiError.details` 原取 `p.details`（undefined），而 `incoming_links` 是顶层字段 → 提示显示"引用方: 未知"。修复为将完整错误 body 作为 `details`。

## 6. 排查日志指引

`agent.knowledge.card` logger 输出 `[入链追踪]` 系列日志，按关键字过滤：

| 关键字 | 含义 |
|--------|------|
| `创建卡片[入链追踪]` | create 的 links 来源（显式/正文解析）与解析结果 |
| `创建卡片[入链追踪] 入链索引登记完成` | 引用目标清单 |
| `删除被拒[入链追踪]` | 409 触发点 + 引用方明细 |
| `删除卡片[入链追踪]` | 入链检查通过 + 被删卡 links + 索引移除 |
| `入链索引登记失败` / `入链索引移除失败` | 索引写失败（已降级，不影响卡片主操作） |

## 7. 边界与不可变约束

- 【不易】同 slug 已存在绝不静默覆盖（CardConflictError）。
- 【不易】有入链的卡片删除绝不产生部分副作用（写锁内先检查后操作）。
- 【不易】索引写失败容错降级：主操作（写卡/index/log）不被辅助索引阻断。
- `archive` 态迁移（`transition`）同样执行入链改写（`[[archives/<slug>|旧名]]`），保证 `parse_links` 无死链。
