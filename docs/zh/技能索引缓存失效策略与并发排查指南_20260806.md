# 技能索引缓存失效策略与并发排查指南

- **日期**: 2026-08-06
- **模块**: `agent/skills_mgmt/index_cache.py`（SkillIndexCache）
- **配套压测**: `scripts/bench_skill_index_cache.py`
- **压测基线**: `data/bench_skill_cache_result.json`（1000 技能）

---

## 1. 设计原则（三义）

- **【不易】** SkillFileStore 对外接口不变；索引失效必须能回源重新解析；只缓存 front matter（不缓存 skill.md body）；返回值是同一 dict 对象（守 loader 倒排索引 `id()` 契约）。
- **【变易】** mtime + hash 双重失效；持久化格式版本化（cache_version）；挂载方式可选。
- **【简易】** 一次解析、多次命中；增量校验只重解析变化的文件。

---

## 2. 失效策略总览

缓存项 = `{ skill_id: metadata, skill_id: {mtime, hash} }`，`skill_id` 即技能目录名。

| 维度 | 校验 | 触发动作 |
|---|---|---|
| 文件修改 | `st_mtime` 变化 | 失效 → 回源重解析 |
| 内容篡改 | 内容 hash 变化（即使 mtime 未变） | 失效 → 回源重解析 |
| 文件删除 | `skill.md` 不存在 | 清理缓存项，返回 `None` |
| 缓存文件损坏 | JSON 解析失败 | 全量重建 |
| 版本不匹配 | `cache_version != "1.0"` | 全量重建 |
| 结构非法 | skills/meta 非 dict | 全量重建 |

命中判定（`_entry_valid`）顺序：

```text
skill.md 存在
  └→ mtime 与缓存一致？
        ├─ 否 → 失效回源
        └─ 是 → 内容 hash 与缓存一致？
                  ├─ 否 → 失效回源（防文件被覆盖回去）
                  └─ 是 → 命中缓存（返回内存 dict，不读磁盘内容）
```

> **【不易】hash 必须与校验同源**：缓存 hash 用 `read_bytes()` 原始字节计算，校验也用 `read_bytes()`。若用 `read_text()` 计算，Windows 上 universal newline 转换（`\r\n→\n`）会导致 hash 永不相等 → 缓存永失效。

## 3. 文件被覆盖时的具体行为

### 3.1 正常覆盖（内容变化，mtime 也变化）

写文件必然更新 mtime → `mtime 变化` → 失效回源，重新解析并更新 hash。**每次覆盖后首次访问是回源，后续命中新缓存**。

### 3.2 内容变化但 mtime 被恢复（"覆盖回去"场景）

例如部署脚本把旧文件写回并恢复原始 mtime。此时 mtime 校验通过，但 **hash 变化触发失效回源**——这是 hash 校验存在的原因（守【不易】：防文件被覆盖回去导致缓存与磁盘不一致）。

### 3.3 内容不变但 mtime 变化（touch）

`touch` 更新 mtime → 失效回源。解析后 hash 与旧值相同，重新缓存。结果是**一次无害的重解析**（不做任何特殊优化，保证一致性优先）。

### 3.4 覆盖时 front matter 的 id 与目录名不一致

缓存 key 始终是**目录名**（`entry.name`），`meta["id"]` 仅在 front matter 缺 id 时回填目录名。若覆盖后 front matter 的 `id` 与目录名不同，缓存内 `key=目录名` 而 `meta["id"]=front matter 值`。**调用方应保证两者一致**（`create`/`update_meta` 走 `file_store` 时由 `_invalidate_index_cache` 同步失效，不会读到旧值）。

---

## 4. 文件被重命名时的具体行为

### 4.1 技能目录重命名（`skills_repo/a/` → `skills_repo/b/`）

| 操作 | 行为 |
|---|---|
| `get_metadata("a")` | `a/skill.md` 不存在 → 清理缓存项，返回 `None` |
| `get_metadata("b")` | 缓存无此 key → 回源解析加入缓存 |
| `get_all_metadata()` | 增量校验：`a` 被清理、`b` 被解析（`changed=True` → 触发 `persist`） |

> **注意**：若 `b/skill.md` 的 front matter `id` 仍为 `a`，缓存 `key=b` 但 `meta["id"]=a`。建议重命名时同步修改 front matter 的 `id`，或走 `file_store` 的迁移接口（会同步失效旧缓存）。

### 4.2 skill.md 本身重命名（`skill.md` → `other.md`）

目录仍在但 `skill.md` 缺失 → 目录被视作"无技能"：
- `get_metadata` → `None` 并清理缓存
- `get_all_metadata` → 该目录被跳过，缓存清理

### 4.3 目录名以 `_` 或 `.` 开头

`_rebuild_locked` / `_validate_all_locked` 会跳过（与 `load_metadata_index` 原逻辑一致），缓存不收录此类目录。

---

## 5. 文件被删除时的具体行为

- **外部删除目录**：`get_metadata` → 清理缓存返回 `None`；`get_all_metadata` → 增量校验清理。
- **file_store 删除**（`fs.delete`）：挂载时自动调 `cache.invalidate(skill_id)` 同步失效（锁外调用，见 §6）。

---

## 6. 并发一致性保障

### 6.1 锁模型

- `RLock` 保护 `_cache` / `_cache_meta` 的全部读写（get/put/validate/persist 快照）。
- **持锁不 I/O**：`invalidate` 锁内仅内存状态变更；日志在锁外输出（守项目硬约束"持锁操作严禁包含 I/O 或外部回调"）。`persist` 锁内仅构建 payload 快照，文件写操作全部在锁外。

### 6.2 invalidate 触发时机（file_store 挂载时）

`create` / `update_meta` / `delete` 之后由 `_invalidate_index_cache` 调用 → 写后立即失效，下次访问回源，不会读到旧缓存。

### 6.3 已知边界（排查时注意）

- **同进程多线程**：RLock 保证一致，压测 `concurrent` 场景 hit_rate=1.000（无死锁）。
- **跨进程/多实例**（如并行会话 worktree）：各自独立缓存实例，**以磁盘文件为最终事实**——任一实例写入后，其他实例靠 mtime/hash 校验自然失效回源，无需跨进程同步。
- **get_metadata 锁内含文件 I/O**：命中校验需 stat + read + md5（既有实现），1000 技能并发下锁竞争明显（见压测 §8 `concurrent` p99）。

## 7. 排查日志字段表（新增）

结构化 JSON 日志，`module_name="index_cache"`，按 `action` 区分。

| action | 关键字段 | 排查用途 |
|---|---|---|
| `invalidate.ok` | `skill_id` / `had_cache_entry` / `cache_size_after` / `duration_ms` | 确认谁失效了哪个技能；`had_cache_entry=false` 说明失效不存在的条目（正常，幂等） |
| `persist.ok` | `skill_count` / `cache_file_size` / `cache_path` / `duration_ms` | 持久化规模与耗时；`cache_file_size` 突变提示缓存内容异常 |
| `persist.failed` | `skill_count` / `error` / `fallback=runtime_parsing` | 写盘失败但不影响内存缓存 |
| `load_on_startup.ok` | `skill_count` / `duration_ms` | 热启动加载耗时 |
| `load_on_startup.cache_corrupt` | `error` / `fallback=rebuild_from_source` | 缓存文件损坏 → 全量重建 |
| `load_on_startup.cache_missing` | `fallback=lazy_build_on_first_access` | 首次部署，懒加载 |
| `load_on_startup.version_mismatch` | `cached_version` / `expected_version` | 升级缓存格式 |
| `rebuild.ok` | `skill_count` / `duration_ms` | 全量重建 |

**并发不一致排查套路**：
1. 用 `invalidate.ok` 的 `had_cache_entry` + `cache_size_after` 判断"谁把缓存清空/缩减了"；
2. 用 `persist.ok` 的 `cache_file_size` 判断落盘内容是否符合预期规模；
3. 对照 `load_on_startup.*` 与 `rebuild.ok` 的 `skill_count`，确认重启后缓存是否按预期恢复。

## 8. 压测基线（1000 技能，2026-08-06）

运行：`python scripts/bench_skill_index_cache.py --count 1000`

| 场景 | 指标 | 结果 |
|---|---|---|
| generate | 1000 技能 mock 数据生成 | 602ms |
| cold_start | 首次全量解析（懒加载） | 1024ms |
| hot_start | load_on_startup 4.4ms + 增量校验 294.9ms | **相对冷启动提速 71.2%** |
| hit | 单技能命中 5000 次 | avg 0.90ms / p99 1.44ms |
| match(loader) | 倒排索引冷热 | 345.6ms → 325.5ms |
| incremental | 改 10 个 404ms / 删 5 个 311ms | 含 O(n) stat+hash 校验 |
| concurrent | 8 线程 4000 次 | hit_rate=1.000，avg 7.3ms / p99 82.5ms |
| invalidate | 20 次 | avg 0.015ms / p99 0.08ms |
| persist | 1000 技能原子写入 | 11.1ms（文件 355KB） |

**结论**：缓存加载/查询的极限瓶颈在**增量校验的 O(n) stat+hash**（`get_all_metadata` 每次全量遍历），而非解析或单次命中。1000 技能规模下约 295ms，属可接受；若技能数上万，需考虑校验策略优化（超出本次范围）。
