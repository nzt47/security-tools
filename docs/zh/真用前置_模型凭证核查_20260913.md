## 二、影响（为什么这是「真用」的硬前置）

设计与运营清单的共同前提是「**让它真实执行工具**」，只有工具调用才会落成 Trace：

| 挂着的事项 | 是否被本问题阻塞 |
|---|---|
| 消化吞吐 / 内化转化率 / ACR / UTC | **是** —— 无 Trace 则无数据，永远是 0 |
| LLM-judge 真实评分（S8-04） | **是** —— judge 走的就是同一套模型适配器 |
| 灰度真实接管（S8-03） | 否（容器隔离是独立工程） |
| L0 锚 / 周报 / 审计链 | 否（这些不需要模型） |

> ⚠️ 特别注意：**不要**因为"周报能生成、L0 锚全过、面板能打开"就认为系统可用 ——
> 那些链路都不经过模型。**模型不通 ≠ 系统坏了，但 = 学不到任何东西。**

## 三、顺带发现的真缺陷：自检是**假绿灯**（建议立项）

`agent/orchestrator/lifecycle_manager.py::get_config()`：

```python
"api_key_set": bool(self._llm.api_key),      # ← 只看"有没有填"，不看"能不能用"
```

于是 `/api/chat` 的 `llm_state` 报 `configured: true / api_key_set: true`，
而**实际每一次调用都 401 失败**。运营清单 §九 把"面板数字不对"归因于开关默认关闭，
但没有覆盖这一类「**填了但无效**」的假绿灯 —— 看面板会以为模型是好的。

**建议修法**（与 v7.2 的"不谎报"纪律一致，可并入 S8 批次或单列小项）：
1. `llm_state` 增加**可区分**字段：`configured`（已填）与 `verified`（最近一次真实调用是否成功）；
2. 启动自检或健康检查做**一次极小的真实探针**（`max_tokens=1`），失败即如实标注原因，
   与 S8-04 的 judge 三态（`available` / `no_credentials` / `disabled`）**同款口径**；
3. 降级话术（"我暂时无法给出令人满意的回答"）**必须带上真实原因**，否则用户只知道"它变笨了"，
   不知道"是 key 失效"。

## 八、复验暴露的新缺陷簇（**「真用」的真正卡点现在在这里**）

> 判据纪律：以下每条都有可复现证据，**不是推测**。四条都清掉之前不要开始「真用」，
> 否则要么白用（学了错东西），要么污染轨迹（假阴性/假阳性都会进台账）。

### D1 · 输出护栏误拦正常回复（critical，**最阻塞**）

- **现象**：回复 "（输出校验未通过，已拦截）"，用户看不到任何答案。
- **证据**（`logs` 与启动日志）：
  ```
  [OutputGuard] validate_llm_output 出口 | severity=critical | passed=True | findings=1
    [hallucination/critical] LLM 提到未加载的技能: coverage_report @coverage_report
  → [护栏] 校验完成 | severity=critical | findings=1 | has_sanitized=False
  ```
- **根因**（`agent/skills_mgmt/output_guard.py:61`）：
  ```python
  _SKILL_BACKTICK_RE = re.compile(r'`([a-z0-9][a-z0-9_\-]*[_\-][a-z0-9_\-]+)`')
  ```
  它把**任何反引号包裹的 snake_case / kebab-case 标识符**当成"技能 ID 引用"。
  本次触发的是**目录名** `coverage_report`（来自 `list_directory` 的真实结果）。
  `_check_hallucination()` 拿它跟 `loaded_skills` 一比 → 不在集合里 → 判 `critical` → 整条回复被拦。
- **影响面（严重）**：云枢的日常用途就是"读代码 / 改文件 / 跑测试 / 写文档"，
  而这些回复**必然**会提到 `` `list_directory` ``、`` `unified_traces` ``、`` `tool_trace.py` `` 这类标识符。
  **即：正常干活越专业，越容易被自己的护栏拦死。**
- **候选修法**（需 Owner 裁定，因为它动的是护栏，按项目纪律不宜单方面放宽）：
  1. 收紧正则：只有出现在**显式技能语境**下才算引用（如前面有 `skill` / `@` / `技能` 前缀），
     或要求标识符命中**技能 ID 命名约定**；
  2. 白话降级：`_SKILL_BACKTICK_RE` 命中但未命中"技能语境"时降为 `warn`，不拦回复；
  3. 用**已加载技能清单反查**：只有当标识符与某个"看起来像技能名"的模式相似时才报，否则忽略。
  4. 无论选哪种，都须补**回归用例**：目录名/文件名/函数名出现在反引号里 → **不得**判 critical。

### D2 · 对话编排层返回与提问无关的内容（critical）

- **现象**：问「2 加 3 等于多少？只回答数字」，返回的 `response` 是一整篇
  `# self_reflection` **技能文档**；`reasoning` 却是上一轮"列文件被截断"的思考。
- **证据**：`tool_steps` / `reasoning` 与上一条**完全不同的问题**返回得**逐字相同** ⇒ 是全局残留，不是本轮结果。
- **根因（已定位到两处）**：
  1. `agent/server_routes/routes_chat.py:428,429`：
     ```python
     "tool_steps": getattr(Yunshu, '_last_tool_steps', []),
     "reasoning":  getattr(Yunshu, '_last_reasoning', None),
     ```
     二者取自**全局单例 `Yunshu` 的实例属性**（last-write-wins），**不是按会话隔离**的 ⇒
     本轮没写就返回上一轮的值（会话串扰）。注意同文件 342-344 行注释声称已"根治会话串扰"，
     但只覆盖了 `session_id`，未覆盖这两个属性。
  2. `response` 来自 `Yunshu.chat(...)`（`routes_chat.py:345`）—— 返回技能文档而非答案，
     定位在编排/上下文装配层（**尚未定位到具体位置，需专项排查**）。
- **影响**：这是「云枢能不能用」的核心 —— **答非所问 + 上一轮内容串台**。
- **补充证据（2026-09-13 02:0x，D1 修完后复测）**：再问同一句「帮我列出当前工作目录下的文件」，
  护栏已不拦（✅ D1 已修），但 `response` 变成**原始工具结果 JSON**：
  `{'ok': True, 'path': '.', 'abs_path': 'C:\\Users\\Administrator\\agent', 'type': 'dir', 'items': [...], 'total': 195}`
  —— **工具结果被当作最终答案直接回吐**，模型没有基于它组织回答。
  同时这一轮 `tool_steps=0`（工具确实执行了，却没记上步骤）⇒
  与"`_last_*` 是全局 last-write-wins"互为印证。
  **给 S9-01 的提示**：`response` 这条支路有两个可分辨的坏形态 ——
  ①回吐原始工具 JSON（本次）；②回吐技能文档正文（前次）。两者都不该出现，
  都指向"装配中间态被当成最终答案返回"。
- **【2026-09-13 02:2x 方法学校正 + 复验】先排除"是不是我探测姿势不对"**：
  我最初的探测在请求体里传的是 `session`，而**线上 handler 只认 `session_id`**
  （`plugins/chat.py:148-149`；`session` 只在**查询参数**位置被接受）
  ⇒ 我那些探测其实全部落在**同一个全局会话**里。为排除这个干扰，已用
  **正确的 `session_id` + 每次全新会话**重测，**D2 依然复现**：
  | 提问（全新 session_id） | 实际 response |
  |---|---|
  | 「2 加 3 等于多少？只回答数字」 | **一整篇 `# self_reflection` 技能文档**（383 tokens） |
  | 「帮我列出当前工作目录下的文件」 | **原始工具结果 JSON**（14128 tokens） |
  ⇒ D2 是**真实缺陷**，不是探测姿势造成的假象。但请 S9-01 复验时**务必用 `session_id`**。
- **【关键】线上 `/api/chat` 是 `plugins/chat.py`，不是 `routes_chat.py`**：
  两者都有 handler 且都读 `getattr(Yunshu, '_last_tool_steps')`。实测响应字段含
  `context` / `voice_result` 且**不含** `thinking_mode` ⇒ 命中的是 `plugins/chat.py:306-329`
  （`routes_chat.py` 的返回里有 `thinking_mode`）。
  **改错文件会白干** —— 本任务以 `plugins/chat.py` 为准，`routes_chat.py` 若已不生效请一并说明。

### D4 · `context.percentage` 是**误导性显示**（中）—— ⚠️ 本节结论已修正

> **【2026-09-13 02:2x 修正】我最初的解读是错的。**
> 我先前写"上下文预算被撑爆（454.7% 超限）"——**这个解读不成立**。
> 数字是真的（确实来自接口），但它的**含义**是"会话累计 token ÷ 一个没配过的硬编码 4096"，
> **不是**上下文窗口溢出告警。下面是把两处代码读透后的结论。

- **现象**：`context = {"input_tokens":16, "output_tokens":383, "session_total_tokens":18623, "token_limit":4096, "percentage":454.7}`。
- **`percentage` 的真实算法**（`plugins/chat.py:304,327`）：
  ```python
  _token_limit = _cfg.get("memory", "token_limit", default=4096)   # ← 硬编码默认
  "percentage": round(_session_total / _token_limit * 100, 1)
  ```
  而 `config.yaml` 的 `memory` 段 **根本没有 `token_limit` 这个键**
  （实际只有 `max_tokens: 8000 / enable_long_term / summary_threshold / retention_days`）
  ⇒ 分母恒为**代码里的 4096**。
  同时 `_session_total`（`plugins/chat.py:298-303`）是**整个会话所有消息 content 的累计和**，
  不是"本次请求的上下文占用"。**累计值 ÷ 固定小分母 ⇒ 用几轮必然 >100%**，这是构造性的，不是异常。
- **真实上限在哪**：编排器用的是 `lifecycle_manager.py:273`
  `self._memory_token_limit = memory_cfg.get("token_limit", 131072)`
  ⇒ 同样是**默认值**（config 没配），但它是 **131072**。以 18623 计约占 14%，并不紧张。
- **真正的问题（两条，都是"读数骗人"而不是"系统炸了"）**：
  1. **`session_total_tokens` / `percentage` 算的是全局会话，不是请求指定的会话**：
     `plugins/chat.py:298` 用的是 `_get_current_session_id()`，而同一个 handler 在
     `:149` 是**按请求**解析 `session_id` 的 ⇒ 你在 A 会话聊天，`context` 块报的可能是
     全局当前会话（B）的数字。实测：全新 session_id 首次提问，
     `session_total_tokens` 直接是 14551（in=16/out=383）—— 显然不属于这个新会话。
  2. **字段名歧义导致"看起来没有会话隔离"**：该 handler 只认请求体里的 **`session_id`**；
     传 `session`（查询参数名才是 `session`）时**静默回落到全局会话**。
     我最初的探测正是踩了这个坑（详见 §八 D2 的修正说明）。
- **影响**：`percentage` 会被读成"上下文要爆了"，从而误判系统状态；
  真实上限（131072）从未被披露，读数的人无从判断余量。
- **建议**（改动小、收益直接，也不动策略）：
  1. `context` 块改用**请求指定的会话**计算，并额外披露**真实上限**
     （`self._memory_token_limit`）与"本次请求占用"两个数，别只给一个累计比值；
  2. 字段名歧义要么接受 `session` 作为别名，要么在响应里回显**实际使用的 session_id**，
     让调用方能自查（本次就是靠日志才发现自己传错了字段）；
  3. 单次 `list_directory` 返回 195 项 ≈ 14k tokens 且未见预算内截断 ——
     这仍是一个**真实的效率问题**（挤占上下文、抬高成本），但与"percentage 报警"是两件事。
- **归口**：D4 由「上下文预算」改归为「**读数可信性**」；与 S9-03 的关系见 §九。
