# 并发与写入路径盘点（TASK-S8-02 步骤 1）

> 所属：S8 生产化加固批次 / TASK-S8-02 并发与运维加固｜基线：`master`
> 生成：2026-09-13｜方法：逐模块通读源码 + 实测复现（进程数/条数/重复 seq 均为**实测值**，非估算）
> 结论一句话：**全部落盘点原先都建立在"进程内单写者 + `busy_timeout` 兜底"的假设上；
> 生产 waitress 单进程时成立，一旦出现多进程（开发脚本与服务同跑、多 worker、离线批处理）
> 就有重复 seq、写丢失、文件损坏三类风险。本任务把该假设升级为可证明的多进程安全。**

## 二、逐条失效模式（含复现依据）

### 1. `AuditChain` —— 唯一有"重复 seq"风险的路径（P0）

**并发模型**：`append()` 在**进程内** `_append_lock` 内分配 `seq`（`self._next_seq`），
两级 sha256 后入**无界** `queue.Queue`；后台线程 `audit-chain-writer` 每 0.5s 或满 100 条
批量 `INSERT`（WAL + `synchronous=FULL`）。`_next_seq` 只在**构造时**从
`SELECT seq, self_hash FROM audit_chain ORDER BY seq DESC LIMIT 1` 恢复一次。

**已有保护**：`seq INTEGER NOT NULL UNIQUE`、`busy_timeout=5000`、进程内单写者登记
`_WRITER_REGISTRY`。

**多进程失效链（实测）**：

1. 进程 A、B 同启，都读到 `max(seq)=0` ⇒ 都从 `seq=1` 开始分配；
2. B 先入库成功，A 的批次撞 `UNIQUE` ⇒ 现有代码把**整批**塞进 `_failed_buffer`
   （`deque(maxlen=2000)`，**进程内**）并 `_resync_seq()`；
3. `_failed_buffer` 到上限后 `append` **静默丢弃最旧一条**（无计数、无告警）；
4. 进程退出 ⇒ ring buffer 消失 ⇒ **审计记录永久丢失，且链上留空洞**。

> 根因不是"性能"，是**审计断链**：链式哈希要求 `seq` 连续，空洞会被
> `verify_chain` 判为 `seq_not_monotonic`（"记录被删除或插入"），与**篡改不可区分**。

**另一个静默点**：`close()` 在 `_degraded=True` 时直接丢弃 residual 与 ring buffer。

### 2. `UnifiedTraceStore` —— 静默丢失 + 降级不可逆（P0）

- `queue.Queue()` **无 maxsize** ⇒ `put_nowait` 永不抛 `queue.Full`，`except Exception`
  兜底是**死代码**；真实容量上限是 `deque(maxlen=1000)`。
- `deque` 溢出**静默丢最旧**：`_workspace_degraded_count` 等计数器都不覆盖它。
- `_degraded` **粘滞**：一次 SQLite 错误 → 本进程后续写入**永久**改走内存。
- `flush()` 返回 True 的判据是 `_commit_count >= _enqueue_count`，而 `_mark_committed`
  在**ring buffer 路径**同样被调用 ⇒ `flush() is True` **不证明已落盘**。
- 未设 `journal_mode`（无 WAL）：多进程写争用回滚日志，`busy_timeout` 到期即失败。

### 3/4/5. JSONL 追加族（P1）

三者共享同一形态：`open(path, "a")` + `write` + （可选 `flush`）。

- **POSIX**：`O_APPEND` 下小于 `PIPE_BUF` 的写入近似原子；
- **Windows**：**不保证** ⇒ 交错/半行；读侧 `except json.JSONDecodeError: continue`
  **静默跳过** ⇒ 损坏不可见（这是最坏的一类：数据没丢，但没人知道它坏了）。

`DecisionLog` 额外两个问题：

- **无轮转**：单文件无限增长（S4-02 L9/L10 的原始缺口）；
- `iter_records()` 的 `except OSError: continue` 会**静默跳过整个不可读分片**
  ⇒ 决策统计被静默污染（分母变小而无人知晓）。

`log_archiver.archive_daily_file` 是全量读→全量重写，**无锁且非原子**：
两个进程（或"一个在追加、一个在归档"）会互相覆盖。其进程内 `_ARCHIVED` 记忆
只防"本进程重复归档"，**给出的是假安全**。

## 三、统一加固方案（本任务的落点）

### 3.1 唯一锁实现（验收项「不新建第二套锁」）

改造前**同一套 OS 文件锁原语被手抄了三份**（`env_config_manager` /
`knowledge.ingest` / `self_healing.watchdog_singleton`），语义各不相同且各自带坑：

| 位置 | 锁语义 | 已知坑 |
|---|---|---|
| `env_config_manager._acquire_process_lock` | `LK_LOCK` 阻塞 | **无超时**（进程互等可不返回）；`open('a+')` 下 `seek` 对写无效 |
| `knowledge.ingest._FileLock` | `LK_LOCK` + 50ms 轮询 | 自带超时但靠模块级全局 `_THREAD_LOCK` 兜线程 |
| `watchdog_singleton._try_lock` | `LK_NBLCK` 非阻塞 | 只有"被拒"语义，与上面两者**不可互换** |

**处置**：提取唯一共享工具 `agent/utils/cross_process_lock.py`，并把上面三处
**改写为调用它**（代码级证据：`agent/` 下 `msvcrt.locking` / `fcntl.flock`
只出现在该文件；该断言已固化为回归用例
`test_only_one_lock_implementation_in_agent`）。

该工具提供任务书要求的两种语义与显式降级：

- `try_lock()` 非阻塞（失败立刻返回 False，**不排队**）；
- `locked(timeout)` / `acquire(timeout)` 有限等待（超时抛 `LockTimeout`）；
- `locked(on_timeout="degrade")` 由调用方自己走降级；
- 计数：`acquire/conflict/timeout/degraded/waits/wait_ms_*`（`lock_metrics()` 快照）；
- 留痕：超时**逐条**留痕，冲突按 `(路径, 进程)` 冷却去重（避免退避循环冲垮审计链）。

**实现期实测修正（写入代码注释）**：

1. **锁文件布局**：`HOLDER_SLOT`（诊断）+ `HEAD_SLOT`（协作槽）；截断点只保留
   "已有深度"，否则会削掉协作槽（或因硬截断破坏既有 `1+512` 布局约定，
   实测 `test_watchdog_singleton` 3 条断言失败）。
2. **重入语义**：只认**同一实例**重入；同线程的**不同实例**必须冲突
   （否则"单写者/单例"守卫在进程内被静默绕过）。
3. **配对释放**：按实例计深度，避免"内层释放把外层标记为未持有"导致
   **OS 锁永不释放**（实测锁泄漏）。
4. **句柄复用**：开/关句柄实测 0.26ms，而纯 `msvcrt.locking` 仅 0.012ms
   （差 20 倍），故复用句柄并做 LRU 有界回收。
5. **静态诊断载荷**：定长槽 + 按字段降级压缩，保证截断后**仍是合法 JSON**
   （否则长 Windows 路径会让 `read_holder()` 恒返回 `{}`）。
6. **热路径不调 metrics 采集器**：`increment_counter` 内部无条件执行
   `logger.debug(f"...")`，f-string 先求值再丢弃，实测占单条延迟约 0.4ms；
   改为进程内整数计数 + 显式 `publish_lock_metrics()`。

### 3.2 `AuditChain`：跨进程 seq = 锁内分配 + **预留日志**

三条候选路线（任务书允许任选，须说明崩溃语义）与取舍：

| 路线 | 崩溃语义 | 实测代价 | 结论 |
|---|---|---|---|
| 锁内同步 SQLite 提交 | 事务回滚 ⇒ 无空洞、无重复 | 一次 `synchronous=FULL` 提交 **17–22ms**（append 基线 p99 0.14ms，约 150×） | **否**（违反"p99 不退化"） |
| 预留区间 | 未用尽的区间 ⇒ **空洞** | 低 | **否**（链式校验要求 seq 连续，空洞会被判 `seq_not_monotonic`） |
| **锁内分配 + 预留日志** | 日志 `flush` 后即跨进程可见；进程被杀 ⇒ 启动**重放**补写 ⇒ **无空洞**、链仍连续 | 实测见下 | **采用** |

**预留日志（`agent/audit/seq_journal.py`）**：每行是**整条记录**（不是只留一个号），
故"崩溃后区间空洞"这一语义在本方案下**不会发生**——这正是任务书
"链式哈希校验必须仍能通过"的达成方式。

**写路径顺序（不可颠倒）**：取跨进程锁 → 解析权威链头 → 分配 seq + 两级哈希 →
**写预留日志并 flush** → 发布链头到锁槽 → 释放锁 → 交接后台批量入库。
（若先发布链头再写日志，别人会从槽取到"日志里根本没有"的链头 ⇒ 空洞。）

**降级（不静默）**：取锁超时 ⇒ 回落 **DB 事务分配**（`BEGIN IMMEDIATE` +
读链头 + 直接入库）：正确但慢，显式计数 + 留痕。**双故障**（锁与 DB 同时不可用）
才退回"按内存链头分配"，此时 `seq_alloc_reliable=False` 如实暴露。

**实现期实测修正**：

| 缺陷 | 现象 | 修正 |
|---|---|---|
| 队列路径与日志收敛**重复插入**同一条 | `UNIQUE constraint failed: audit_chain.seq` | 记录"在途 seq"集合，收敛时排除 |
| 收敛水位用 `MAX(seq)` | 崩溃后先写新 seq ⇒ 落后的旧 seq **永不补**（实测恢复后只剩 1/25 条） | 改为**连续水位** + 精确"不在库里"判定 |
| 锁内做 DB I/O | 临界区被 `synchronous=FULL` 拖到数秒 ⇒ 其它进程取锁超时 ⇒ 降级分配 ⇒ **重复 seq**（实测 `duplicates=[80]`） | DB I/O 只归 writer 线程；`append()` 临界区只有内存计算 + 一次无 fsync 日志写 |
| 压缩在每轮都跑 | 每次 append 都重写 512 行 | 行数闸 + 时间闸 |
| `entries()` 短路条件只看 ring buffer | DB 转不可用后"刚写的"读不到（用例**偶发绿灯**） | 条件纳入预留日志 |
| 内核文本模式追加 | Windows `\n`→`\r\n` 使字节账目失真 ⇒ 每次 append 重读尾部 256KB | 预留日志改用二进制追加 |

**性能对照（clock 口径：`time.perf_counter`，Windows，N=3000，同机同进程）**：

| 阶段 | p50 | p95 | p99 | mean |
|---|---|---|---|---|
| 基线（改造前，纯内存分配） | 0.035 ms | 0.046 ms | 0.140 ms | 0.037 ms |
| 首版（每 append 开/关锁句柄 + 每次查 DB + 每轮压缩） | 2.40 ms | 5.78 ms | 14.65 ms | 3.35 ms |
| **终版（句柄复用 + 锁槽快路径 + 压缩节流 + 二进制日志）** | **0.18 ms** | **0.33 ms** | **0.64 ms** | **0.20 ms** |

> **如实说明**：终版相对**纯内存基线**仍有约 5×（p50）的上升——这是"跨进程临界区 +
> 一次持久化写"的固有成本，不可能为零。它仍远在项目既有预算内
> （`test_append_mean_latency_under_5ms` 断言 mean < 5ms，实测 0.20ms，余量约 25×），
> 且相对"真正决定端到端开销"的一次 `synchronous=FULL` 提交（17–22ms）可忽略。

### 3.3 其余落盘点

- `EventStore` / 成本：跨进程锁 + **单次 `os.write` 整行**追加（连降级路径也不可能撕行）；
  锁不可得时**排队重试**，缓冲满则**显式失败**（三种行为都有用例）。
- 技能审计分片 / `log_archiver`：归档全流程持锁；**先写分片、后替换活动文件**，
  故失败只会造成**重复**（可去重）而非**丢失**；活动文件替换用 `os.replace` 原子完成。
- `DecisionLog`：跨进程锁 + 轮转（大小/按日，**默认关闭**）+ 旧分片只归档不删 +
  统计口径不变式（`read()` 记录多重集在轮转前后恒等）+ `read(limit=N)` 时间序修正 +
  不可读分片计数。

### 4.1 S8-01 对决策日志的实际处置

`agent/retention/policy.py` 的 `policy_decisions` 类声明：

| 字段 | 值 | 含义 |
|---|---|---|

### 4.2 ⚠️ 缝合处实测缺陷：S8-01 温层归档会让本模块**静默丢统计**

**两处对"分片名"的理解不一致**：

- 本模块轮转产出**点号**形态 `decisions.<YYYYMMDD>.jsonl`；
- S8-01 温层复用的 `log_archiver.archive_daily_file` 产出**连字符**形态，
  且实际是 **ISO 日期**（`day = ts[:10]`）⇒ `decisions-2026-09-10.jsonl`；
- 本模块读侧门槛一度是 `name.startswith(stem + ".")`（只认点号）。

**实测后果（已复现并留用例）**：3 天决策（2 条历史日 + 1 条今日）经
`archive_daily_file` 之后，`read()` 由 **3 条跌到 1 条**——归档"成功"、
统计凭空少 2/3、**且无任何报错**。`_candidate_files()` 只返回活动文件。
S8-01 侧的口径复算校验 `utc.weekly` / `digestion.throughput` / `audit.chain`，
**不覆盖** `policy.decision_audit`，故那条路查不出来。

**处置（本任务修）**：`DecisionLog._candidate_files()` 同时识别两种命名——
点号形态任意后缀；连字符形态只认 `<stem>-YYYY-MM-DD<ext>`（ISO）与
`<stem>-YYYYMMDD<ext>`（紧凑），**反例**（`decisions-backup.jsonl` /
`decisions-old.jsonl` / `decisions-2026.jsonl` / `decisions-2026-09.jsonl`）不收
（宽进会**多**读数据，同样是口径漂移）。修复后实测恢复为 **3 → 3 条**。

**顺带勘误**：`log_archiver.archive_daily_file` 的 docstring 写的是
`<stem>-YYYYMMDD<ext>`，**与实际产物不符**（实际为 `<stem>-<YYYY-MM-DD><ext>`）。
该笔误正是上述匹配写成"只认紧凑 8 位"死代码的成因，已一并更正。

**回归用例**（`tests/unit/test_decision_log_rotation.py`）：
① 调用**真实的** `archive_daily_file` 后 `read()` 多重集恒等（跨任务回归守卫）；
② 点号与连字符分片**共存**时都可读；
③ 形近文件（人工副本等）不被误当分片。

### 4.3 其余联动

1. **只归档不删除**：本任务任何路径都不得 `unlink` 审计/决策数据；
2. **默认保守**：轮转/自动归档**默认关闭**，开启后首次可 dry-run；
3. **口径不变**：轮转前后统计多重集恒等（有不变式用例），历史指标可复算；
4. **登记点已就绪**：轮转产出物（分片路径 + 时间范围 + 条数）在 `stats()` 中可查，
   与 S8-01 的 `globs` 口径一致（点号形态），无需改本任务代码。

> **给 S8-01 的建议（不阻塞）**：`policy_decisions.globs` 目前只列点号形态。
> 若温层开启后产生连字符分片，`scan` 侧的文件枚举可能同样漏掉它们；
> 建议把 globs 扩为同时覆盖 `<stem>-*.jsonl`，或统一温层分片命名。
> 本任务已使**读端**对两种形态都安全，故该问题当前不造成数据不可读。
