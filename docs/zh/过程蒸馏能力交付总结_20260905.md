# 过程蒸馏能力交付总结（知识库 → 子代理蒸馏 → workflow/Skill 固化）

日期：2026-09-05
模块：`agent/process_distill/`（新增）
测试：`tests/unit/test_process_distill.py`（23 项，全部通过）
回归：`test_workflow_to_skill.py` / `test_workflow_learning.py` 全绿（59 passed）

## 一、需求背景

用户希望云枢**本身**具备一项元能力：自动派出子代理从知识库/素材中阅读
"其他 agent 的编程过程"，总结出**可复现的步骤序列**，并固化为可复用资产：

- **workflow**（一次性/可执行）：被主循环"工作流学习层" 0-Token 命中执行；
- **Skill**（长期复用）：落文件轨 `skills_repo/<id>/skill.md`，被语义层
  SkillLoader 召回。

调研确认：云枢已有底层设施（`subagent/` 骨架、`workflow_learning/`、
`skills_mgmt/`、`knowledge/`），但**没有**"知识库/外部素材 → 步骤序列 →
固化"的编排链路；`subagent/` 容器是占位实现（不调 LLM、无并行编排），
`skills_mgmt` JSON 轨与 `skills_repo` 文件轨无自动同步——这些是本次设计的
输入约束。

## 二、设计

新模块 `agent/process_distill/`，编排 `素材 → 蒸馏 → 合并 → 固化`：

```
sources.py    素材收集：wiki 检索（KnowledgeSearch）/ 路径文件（.md/.txt 目录递归）
              ↓
distiller.py  并行子代理蒸馏：每条素材 = 一个隔离 LLM worker（ThreadPoolExecutor），
              输出结构化步骤 JSON；LLM 缺失/失败 → 规则提取骨架（不抛异常）
              ↓
merge.py      合并归一：多路步骤保序拼接 + 相邻近似去重 + 任务签名/触发词
              ↓
solidify.py   固化：
              ├─ workflow：映射到已注册工具的步骤 → LearnedWorkflow →
              │   WorkflowGenerator.generate_and_store（data/learned_workflows.json）
              └─ skill：编译 skill.md（front matter + 步骤正文）→ 双写
                  JSON 轨（create_manual）+ 文件轨（file_store.create）
service.py    门面 ProcessDistillService.distill(query/paths, artifacts)
tools.py      工具注册 distill_process_from_knowledge（agent.tools 全局注册表）
```

### 关键设计决策

1. **子代理 = 隔离 LLM worker**。项目 `subagent/` 容器是占位骨架，不真正调
   LLM，因此本模块实现"真执行"版的子代理语义：每条素材派一个独立
   `distill_one` 调用（独立上下文、只读素材快照），线程池并行
   （`max_workers`，上限 16），主代理只消费合并结果——与 subagent 隔离思想
   一致但不依赖其占位实现。后续若 `subagent/` 补齐执行引擎，可平滑迁移。

2. **降级铁律**（与 knowledge/distill 对齐）：无 LLM / 超时 / JSON 解析失败
   → 该素材退回规则提取（编号/条目行 → 骨架步骤），绝不抛异常；仅"素材
   不存在 / 参数错误"抛 ValueError。

3. **固化边界显性化**：
   - workflow 只收**映射到云枢已注册工具**的步骤（工具白名单默认取
     `agent.tools` 实时注册表，也可显式注入）；纯指令步骤进不了执行轨，
     `solidify_to_workflow` 返回 `action=skipped` + 原因，提示改固化为 skill；
   - skill 双写：只调 `create_manual`（JSON 轨）不会被主循环召回——调研
     确认语义层只扫 `skills_repo` 文件轨，故同时 `file_store.create` 落
     `skill.md`，两条轨都要写才"可管理 + 可召回"。

4. **幂等**：`workflow_id/skill_id` 由步骤内容哈希派生（`pd-<name>-<hash>-wf/skill`），
   同一素材组合重复蒸馏返回已有 id（`action=exists`），不重复创建。

5. **LLM 获取**：`ProcessDistillService` 默认从 `.env`
   （`LLM_PROVIDER/LLM_API_KEY/LLM_MODEL/LLM_BASE_URL`）构建 `LLMService`
   （与 plugins/chat.py 同源）；可注入 llm（duck-typing：
   `chat(messages, system_prompt=...)`），测试注入 FakeLLM 不触网。

6. **接入主循环**：`lifecycle_manager._register_builtin_tools()` 中追加一行
   注册（try/except 包裹，失败仅日志，不影响其余内置工具）；云枢在对话中
   即可自主调用 `distill_process_from_knowledge` 工具。

## 五、使用示例

```python
from agent.process_distill import ProcessDistillService

svc = ProcessDistillService()                       # 默认走 .env LLM

# A. 从知识库 wiki 检索蒸馏并固化（workflow + skill）
r = svc.distill(query="git gc 维护复盘", artifacts=["workflow", "skill"])

# B. 蒸馏外部 SKILL.md 目录（如 .superpowers/skills/**）固化为 skill
r = svc.distill(paths=[".superpowers/skills/subagent-driven-development"],
                artifacts=["skill"])

# C. 云枢对话内自主调用（工具已注册进主循环）
#    用户说："把 .superpowers/skills 里的方法论蒸馏成我的技能"
#    云枢调 distill_process_from_knowledge(paths=[...], artifacts=["skill"])
```

## 七、二轮增强（HTTP 路由 / 异步化 / 批量导入 / LLM 稳定性）

### 7.1 HTTP REST 路由

新增 `agent/server_routes/routes_process_distill.py`（`app_server.py` 中
`/api/workflow-learning/*` 注册块之后挂载，try/except 包裹）：

```
GET  /api/process-distill/health   → {ok, llm_configured, artifacts}
POST /api/process-distill/distill  → {ok, query, paths, llm_used,
       materials:[{id,title,source_ref}], process, artifacts:{workflow?,skill?}}
```

- 与对话工具共用 `ProcessDistillService` 进程级单例（懒加载，复用 .env LLM）；
- 响应素材瘦身（只回 id/title/source_ref，全文不进 HTTP 响应）；
- 校验：query 与 paths 全空 → 400 `VALIDATION_ERROR`。

### 7.2 异步化（长管线不阻塞对话）

`process_distill/tools.py` 现注册 **3 个工具**：

| 工具 | 语义 |
|---|---|
| `distill_process_from_knowledge` | 同步执行（短任务） |
| `distill_process_async` | 提交 `AsyncExecutor` 后台跑，立即返回 `task_id`，用既有 `get_task_status` / `get_task_result` 轮询 |
| `process_distill_run` | 内部执行体（供 async submit 调用；也可被其它工具复用） |

异步任务的真实服务在后台线程惰性构建（.env LLM）；结果瘦身后存入
`data/async_tasks.jsonl`，1 小时 TTL。

### 7.4 LLM 稳定性防御（真实端点发现）

换有效 key 后实测发现：**deepseek 端点对部分内容段存在间歇性空响应**
（同素材 5 次调用约 1-2 次返回空；与内容长度/prompt 结构无单调关系，
短内容与长内容都可能空）。代码侧已加防御：

- `distill_one` 内部重试 `_LLM_RETRIES=3`（指数退避 1s/2s），空响应或坏 JSON
  重试，把单素材空率从 ~25-40% 降到 <2%；
- 全败才规则降级（不抛异常，降级铁律不变）；
- 模型未服从 JSON 但给出编号文本时，用 `extract_text_steps` 兜底提取
  （保留 LLM 提炼质量），仍无则规则降级。

服务门面新增 `use_default_llm` 参数：默认 `True`（生产自动用 .env LLM）；
测试/离线显式 `use_default_llm=False` 强制规则降级（修复了此前
`llm=None` 被误当作"自动构建"的语义 bug）。

### 7.7 评审-消化闭环与"没内容"修复（用户反馈驱动）

用户反馈：技能面板点击"查看内容"提示"该技能没有可查看的指令正文（仅
运行时元数据）"（例：`pd-skill-8627a82f-skill`）。

**根因（两类）**：
1. **legacy 轨孤儿残留**：早期测试/多轮批量产生的 `pd-*` 项在
   `agent/data/skills.json`（legacy 轨）中累积 21 个孤儿——`skills_mgmt`
   的 `sync_to_legacy_skills_json` 只追加不删除，主轨删除后 legacy 残留；
   其项结构是 `{id, name, enabled, description, params}`（无 content，
   legacy 只存启停占位），对应文件轨已删 → UI 显示"仅运行时元数据"。
   已全部清除（21 个孤儿 + 历史 digest 事件/分类残留）。
2. **文件轨状态悬空**：固化时 `file_store.create` 的 meta 未传
   `status`/`enabled` → 文件轨技能状态未声明。

**修复 A/B/C（代码层）**：
- **A. 双轨一致**：`solidify_to_skill` 固化文件轨 meta 显式带
  `status: draft`、`enabled: True`、`version`；review 后把权威状态同步
  到文件轨 front matter。
- **B. 正式评审-消化**：`solidify_to_skill(run_review=True)`（默认）固化后
  调 `SkillsMgmtService.review()` 走正式三审——PASSED→approved、
  WARN→pending_review、FAILED→rejected；仍不自动 publish（发布留人工，
  符合云枢"AI 只产草稿、审核放行"）。结果含 `review: {status, verdict,
  score, summary}`。
- **C. 固化前质量门槛**：`_quality_check()`——规则降级产物步骤 <3 拒识、
  LLM 产物无步骤拒识、全空步骤拒识；返回 `action=skipped` + 原因。

**已入库 15 个产物补齐**：文件轨补 status/enabled + 全部跑正式评审——
**15/15 `review=passed / verdict=ok / score=94`，状态 draft → approved**，
双轨一致（json=approved / fs=approved / enabled=True，0 mismatch）；
legacy 轨重建为 15 项全 enabled=True。召回验证正常（如 "review code
changes" → receiving/requesting-code-review 0.667、"debugging" →
systematic-debugging 1.0）。

**遗留（skills_mgmt 既有缺陷，非本模块）**：`sync_to_legacy_skills_json`
只追加不更新——技能 review 升 approved 后 legacy 的 enabled 不自动刷新。
本模块固化路径已规避（见 A）；如需根治应在 skills_mgmt service 层补
"review/状态变更后同步 legacy"。

### 7.8 免 LLM 工具链 workflow 的冷启动死锁修复（用户反馈驱动）

用户反馈："我要的是工作流技能（免 LLM 的工具链 workflow），不是 LLM
技能（方法论 skill）。这 15 个没 LLM 能用吗？"

**澄清**：云枢两类资产不同——skill = 方法论文本（语义层命中后作指令返回/给
LLM 参考，不执行）；workflow = 工具调用链（DAG 模式由 `WorkflowExecutor`
直接调工具，**免 LLM 0-Token**）。15 个 `.superpowers` 蒸馏产物是方法论
（步骤是认知动作，映射不到工具）→ 只能固化为 skill，符合预期。真正能产
免 LLM workflow 的来源是**云枢自己的成功工具调用序列**（自动学习钩子）。

**根因（workflow_learning 冷启动三重死锁）**：
1. learner 初值 confidence=0.3 < matcher.min_confidence=0.4 → 刚学的工作流
   永远匹配不到（原始相似度 0.807 也被门槛误杀）；
2. record_execution 用对数公式重算，首次成功把 confidence 从 0.4 砸回
   ~0.18 → 再次跌破门槛（二次死锁）；
3. combined = sim×conf×priority 中 conf(0.4)×priority(50→0.75) 压低分数，
   冷启动 sim 0.35 时 combined≈0.11 < executor min_score 0.25 → 无法首跑；
   另 matcher 索引不含 steps 工具名/原始请求 → 复现请求相似度低。

**修复（三处，均带专项测试）**：
- `learner.py`：新学 workflow confidence 初值 0.3 → **0.4**（= 匹配门槛，
  冷启动立即可匹配）；
- `models.py record_execution`：对数重算 → **相对演进**（成功 +0.1×e^衰减、
  失败 ×0.9、下限 0.05），首次成功 confidence 单调上升不再跌回门槛下；
- `matcher.py`：① 索引文本补 **steps 工具名 + source_user_input**（复现
  请求 sim 0.3→0.8+）；② combined 计分对**从未执行过**（success_count=0）
  的 workflow 豁免 conf 因子（按文本相似度首跑，执行后恢复 conf 演化）。

**验证**：
- 全链路：learn → 原样/相似请求命中 → DAG 模式 3 工具**免 LLM 执行成功**
  → confidence 0.4→0.5 演化 → 再命中（闭环成立）；
- 演示沉淀：`scripts/seed_demo_workflows.py` 往生产仓库写入 3 条真实工具链
  （python 行数统计、代码打包 zip、json→yaml），"把代码打包 zip" 等请求

### 7.9 工作流技能 vs 工作流 分层（资产类型声明 + 步骤级 LLM 混合 + Agent 接主循环）

用户设计诉求："必须将工作流技能和工作流分开——**工作流技能免 LLM 0-Token，

**设计落地（三部分，替代旧的纯按结构自动分类）**：

**A. 资产类型声明**（`LearnedWorkflow.workflow_type`）：
- `"toolchain"`（**工作流技能**）：纯工具链，免 LLM 0-Token；模型级校验
  禁止 `need_llm` 步骤；
- `"hybrid"`（**工作流**）：可含 `need_llm` 步骤（步骤级 LLM 混合），或
  超过 DAG 上限（>10 步/复杂分支）时整条走 Agent 模式；
- 默认 `"toolchain"`（向后兼容：既有 workflow 全为纯工具链）。

**B. 步骤级 LLM 混合**（`WorkflowStep.need_llm` + `prompt_template`）：
DAG 执行器中 `need_llm=True` 的步骤改由注入的 `llm_step_runner`
（(prompt_text, ctx) → str）执行，其余步骤仍走本地工具——**"本地能解的
先本地做，某一步需要 LLM 决策/生成时才调 LLM"**。数据经 prev_output/
黑板正常流转。`skipped_llm` 语义修正：纯工具链成功 → True；含 LLM 步骤
→ False（如实报告）。纯 need_llm 步骤的 hybrid 无需 tool_executor。

**C. Agent/LLM 接主循环**：`WorkflowExecutor`/`WorkflowLearningService`
新增 `set_llm_step_runner`/`set_agent_executor`；orchestrator 工作流层
懒注入步骤级 LLM runner（复用主代理 `_llm.chat`，无 LLM 时跳过并日志，
hybrid need_llm 步骤执行时报错不静默）。

**验证**：
- hybrid 混合执行：LLM 决策(输出路径) → 本地 read_file(免 LLM) → LLM 总结，
  3 步成功、工具/LLM 调用各就各位、数据流转正确（`skipped_llm=False`）；
- 纯工具链：免 LLM 0-Token（`skipped_llm=True`）；
- 校验：toolchain 禁 need_llm 步骤、hybrid 放行、非法类型拒绝、默认兼容；
- runner 缺失：hybrid need_llm 未配 runner → 执行失败（不静默）；纯 LLM
  workflow 无需 tool_executor；
- 回归：workflow 全量 **291 项全过**（新增 `tests/unit/test_workflow_hybrid.py`
  11 项）。

**改动文件**：`agent/workflow_learning/models.py`（workflow_type/need_llm/
prompt_template + 校验）、`executor.py`（步骤级 LLM 分支、skipped_llm 语义、
