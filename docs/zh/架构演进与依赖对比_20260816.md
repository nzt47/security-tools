# 云枢架构演进总结：API 服务依赖对比（2026-08-16）

> 本文档记录本次 API 审计收口的架构演进：从"三服务 + 大量未挂载代码"收敛为"双服务 + 网关适配层"，附清理前后依赖图与量化对比。

## 一、演进背景

审计发现四类架构问题：

1. **死服务**：sensor_server.py 与 app_server.py 同端口 5678 冲突、零运行时引用、接口无消费者
2. **未挂载代码**：`agent/server_routes/` 下 16 个模块 188 个路由定义从未注册（与 app_server 内联实现重复）
3. **前端 404**：`/api/replay/upload`、`/api/vector/*`、`/api/knowledge/add` 前端在调用但后端未注册
4. **孤岛组件**：`agent/api_gateway.py` 完整实现（API Key/限流/配额/Swagger）但零引用

**关键设计**：`before_request` 仅拦截网关显式注册的端点；内部 API 走 Flask 原生路由 + `require_token`，开放 API 走网关——双轨并存、互不干扰。

## 六、演进收益与建议

**收益**：
- 消除同端口服务冲突与 188 个死代码定义（可维护性）
- 修复前端真实 404（replay/vector 闭环）
- 网关从孤岛变为可运行组件（限流/配额已验证 + 每日 CI 守护）

**后续建议**：
1. `register_all_routes`（server_routes/__init__.py）已无生产调用，可考虑删除
2. A 类剩余待接线模块（routes_feedback、routes_business_dashboard、routes_health、routes_dashboard、semantic-config、handoff）有真实依赖，按需接线
3. 若需开放多租户 API，可在网关上逐批迁移内部端点（认证迁移为远期项）
