## 二、设计思路文件内容摘要

该文件为一次对话记录，提出理想智能体自主学习机制的完整框架，可归纳为**四个维度 + 一个前沿方向**：

| 维度 | 核心主张 |
|---|---|
| 一、总体架构 | 分层模块化（感知/记忆/规划/执行/反思）；**非参数记忆**（经验库/Skill库）与**参数记忆**（模型权重）双向转换 |
| 二、学习引擎 | ① 经验蒸馏→Skill沉淀（离线自蒸馏 + 在线检索应用，肖仰华判据：相似任务 token 消耗显著下降）；② **测试时学习**(TTL，推理过程实时更新规划师参数)；③ 新颖性检测触发学习管线；④ 课程学习 + 生成式世界模型合成边缘案例 |
| 三、反馈体系 | ① **过程奖励**而非仅结果奖励；② **MAE 三角色对抗**（Proposer/Solver/Judge）；③ 双轨数据飞轮（仿真小飞轮 + 在线大飞轮）；④ 因果推理驱动进化方向 |
| 四、安全保障 | ① 验证门控（功能/安全/泛化三维）；② 层级化目标对齐 + 目标疲劳抑制；③ Skill 生命周期管理（压缩/聚类/淘汰）；④ **自主权 L1-L5 分级** |
| 五、前沿方向 | **递归自进化**（哥德尔智能体：`π_{t+1}, I_{t+1} = I_t(π_t, I_t, r_t, g)`，更新规则本身也进化） |

> 总结公式：**专家能力 = （基础模型 × 高保真环境）^强化学习**；核心原则：闭环性、层次性、安全性、可持续性。

## 三、设计思路合理性评估

### 3.1 合理之处（方向正确，值得采纳）

1. **分层模块化架构与云枢现状吻合**：云枢已有感知层(`sensor/`)、记忆层(`memory/`+`lifetrace/`)、规划层(`planning/`)、执行层(`agent/orchestrator/`)、知识层(`agent/knowledge/`)，设计思路的五层框架可作为目标架构蓝图而非全新系统。
2. **"执行→反思→沉淀→复用→优化"闭环提法正确**：云枢已有一处真实落地的自动闭环——`workflow_learning`（成功交互→学习工具序列→下次 0-Token 命中→`skill_converter` 质量门控自动升格为 Skill，`config.yaml workflow_learning.auto_upgrade.enabled=true`）。设计思路与已有雏形同构，应围绕它扩圈而非另起炉灶。
3. **经验蒸馏→Skill 沉淀与现状可对接**：`agent/knowledge/distill.py` 已实现素材→结构化 Note 的五步闭环；`skills_mgmt` 已实现三层检索（TF-IDF+向量+BM25 RRF 融合+reranker+质量门禁）。缺的只是"知识→技能"连接器与调度（见 §4.3 差距表）。
4. **验证门控思想与现状一致**：`reviewer.py` 三重审核（重复/安全/质量）、`workflow_learning` 质量门控（success_count≥5 且 confidence≥0.7）、`output_schema` 后置验证设计意图均已存在。
5. **Skill 生命周期管理与现状一致**：`models.py` 全状态机（DRAFT→PENDING_REVIEW→APPROVED→PUBLISHED→DEPRECATED→ARCHIVED）、`merge_skills` 聚类合并、`bump_version/rollback` 版本管理均已存在。
6. **新颖性检测触发学习是正确方向**：`sensor/change_detector.py` 已做快照 diff 并持久化变更日志，但纯"日志器"无学习钩子——设计思路恰好指出了该能力的正确归宿。
7. **肖仰华判据（相似任务 token 下降）可量化**，可作为学习有效性的核心验收指标之一。

### 3.2 理论缺陷（设计思路本身的问题）

| # | 缺陷 | 说明与替代 |
|---|---|---|
| D1 | **"专家能力=(基础模型×高保真环境)^强化学习"是伪数学** | 幂次符号仅为修辞，无维度/无单位/无法实证。更严谨表述：`能力 = f(基础模型, 环境保真度, 反馈信号质量, 更新机制)`。评审采用时应降格为"定性口号"。 |
| D2 | **参数记忆↔非参数记忆"双向转换"对 API 型智能体不现实** | 云枢通过 API 调用外部 LLM，参数记忆（微调权重）成本不可承受且无训练基建。应明确：参数记忆是"模型提供方"职责，云枢只做**上下文工程级记忆**（提示注入+外部检索+策略/模板更新）。设计思路混淆了"智能体可学习"与"基础模型可训练"两个层面。 |
| D3 | **测试时学习(TTL)与"LLM 不可变"冲突** | MIA 框架的 TTL 依赖可更新的自研规划师；云枢规划/认知全部依赖外部 LLM。替代：**测试时更新外部策略**（工作流模板、规则、Skill 参数、反思经验）——这正是 `workflow_learning` 已验证可行的路径。 |
| D4 | **过程奖励(PRM)需要奖励模型训练管线** | 云枢无训练基建。替代：先用启发式规则 + LLM-as-Judge 做"伪过程奖励"，积累标注数据后再评估是否值得训练。云枢现有评估器全部是零 Token 规则（`agent/cognitive/reflection.py` 等），可作为第一阶段基底。 |
| D5 | **MAE 三角色对抗成本失控风险** | 每轮学习 3 次 LLM 调用。云枢 `configs/models.yaml` 声明了 `cost_limits` 但**无强制钩子**。引入前必须先建"学习动作 token 预算"护栏（见 TASK-03）。 |
| D6 | **课程学习/生成式世界模型对个人数字生命体不现实** | 无仿真器、数据量低。降级为轻量课程：复用 `enhanced_planner` 的任务复杂度分级（TRIVIAL→COMPLEX）做难度自适应；"世界模型合成边缘案例"用**评估集回归 + 沙箱回放**替代。 |
| D7 | **递归自进化（哥德尔智能体）实践风险极高** | 自我改写决策逻辑可致目标漂移、不可审计、不可回滚，违反云枢"配置驱动、可回滚"工程约束。应定位为**远期探索**，且必须守住"更新规则本身也必须版本化+门控"底线（见 TASK-08）。 |
| D8 | **因果推理驱动进化方向过重** | 完整因果推理链成本高、收益不确定。用 `agent/cognitive/failure_analysis.py`（已有失败分类）+ 轻量对照实验替代。 |
| D9 | **双轨数据飞轮中"仿真环境"对云枢不现实** | 无仿真器。降级为"**离线小飞轮=评估集回归+沙箱回放**；**在线大飞轮=workflow_learning+反馈闭环**"——后者云枢已实现主体。 |

> **替代方案设计文档**：D2/D3 的完整落地设计见 [D2D3_API架构替代方案设计.md](D2D3_API架构替代方案设计.md)——提出"上下文工程学习（CEL）"框架：D2 用三层记忆模型+沉积/实例化双管线替代参数记忆；D3 用测试时策略更新（TTPU，四类可更新外部策略工件+PolicyUpdateBroker）替代规划师参数更新。

### 3.3 实践缺陷（与云枢现状的错位）

1. **从零设计视角，未盘点现有资产**：`workflow_learning`（在线小飞轮已落地）、knowledge 五步闭环、skills_mgmt 审核/版本/合并、`feedback.py` SQLite 闭环均未被设计文档引用。若照设计文档"全新建"将造成系统二象性（平行实现）。
2. **无成本/性能约束**：每步反思、多角色评估的 token 开销无预算概念；云枢有 `LLMMonitor`（环形缓冲）与 `GracefulDegrade`，但无"学习动作预算"。
3. **无数据隐私边界**：学习样本（对话、感知数据）需脱敏；云枢 `memory/black_box.py` 已有 AES-256-GCM 加密可复用，设计文档未提。
4. **无人机边界**："自动沉淀"与云枢现有边界冲突（`distill.py` 强制 `draft→approved` 人工审批后才可 `promote_to_card`）。需定义**分级自动沉淀策略**：自动进 DRAFT，经门控/人工后才晋升。
5. **无度量体系**：只给 token 判据，缺完整 KPI 集（复用率/命中率/失败率/反馈分/采纳率）。

### 3.4 需要补充完善的内容清单

1. **学习有效性 KPI 体系**（见 TASK-03）：token 复用率、Skill/工作流命中率、分类型失败率、反馈均分趋势、沉淀增量、进化采纳率。
2. **学习动作成本预算与熔断**：单次学习动作 token 上限、日预算，超限熔断（复用 `rate_limiter`/`circuit_breaker`）。
3. **数据脱敏与隐私边界**：复用 `black_box.py` 加密与脱敏管道，学习样本入库前脱敏。
4. **回滚机制**：Skill 版本快照已具备（`bump_version/rollback_version`），策略/规则/工作流更新必须同步支持回滚。
5. **人机边界分级**：`自动产 DRAFT + 门控/人工晋升` 的分级策略（TASK-04 落地）。
6. **与现有系统的衔接矩阵**：设计维度 × 现有模块映射（见 §4.3）。
7. **渐进路线**：从"接线已建未用能力"开始，而非新建系统（见 §5）。

### 4.4 核心缺陷汇总（重构必须解决的 8 个断点）

1. **规划引擎"已建未用"**：`planning.enabled=true` 但 orchestrator 主链路从未调用 `PlanningCore.chat()`。
2. **认知评估整体休眠**：Reflection/ActorCritic/Debate/KnowledgePrecipitate 生产代码零调用。
3. **反思产物不闭环**：反思结果只进黑匣子日志，不进向量检索面；`learn_from_experience` 经验库恒空。
4. **知识→Skill 断链**：knowledge 与 skills_mgmt 两系统相互独立。
5. **沉淀管道未调度**：`memory_abstractor` / `offline_evolver` / feedback 淘汰建议均无触发执行体。
6. **感知→学习断链**：ChangeDetector 不触发任何学习/记忆流程。
7. **自主权分级缺失**：无 L1-L5 行为分级，与"阻断-熔断-降级"三套机制不对应。
8. **输出验证门控缺位**：LLM 输出内容/质量无运行时把关；健康评估只采样不拦截。

## 五、重构计划：分阶段论证

### 5.1 是否需要分阶段？——需要

论证依据：

1. **范围横跨 5 个独立子系统**（规划、认知、技能、感知、安全），各有独立测试面与验收标准，无法一次性提交。
2. **存在明确依赖链**：沉淀管道（T04/T05）依赖反思产物（T02），反思依赖规划接线（T01）；度量体系（T03）需先于沉淀管道上线以便验收。
3. **守"不易"原则（大变更拆解为可回滚小步）**：每阶段可独立灰度、独立回滚、独立验收，避免一次性大重构的失控风险。
4. **既有工程护栏**：1.2 万+ 回归测试、架构规则检查、pre-commit 守卫使"接线型重构"可被安全验证。

### 5.2 阶段划分与依赖关系

```
主线（闭环贯通）：
  TASK-01 规划引擎接入主链路 ──► TASK-02 反思沉淀与认知评估上线 ──► TASK-04 知识→技能沉淀管道 ──► TASK-05 反馈进化与生命周期自动化
                                                   │
                                              度量基建先行：TASK-03 学习有效性度量体系（T04/T05 验收依赖其 KPI）
并行轨道：
  TASK-06 新颖性感知学习管线（依赖 T02 的记忆回写能力，可与 T03/T04 并行）
  TASK-07 自主权分级与输出验证门控（完全独立，可与任意任务并行）
远期：
  TASK-08 远期自进化探索研究（研究型，任意时间启动）
```

### 5.3 工作量与风险评估

| 任务 | 规模 | 风险 | 灰度策略 |
