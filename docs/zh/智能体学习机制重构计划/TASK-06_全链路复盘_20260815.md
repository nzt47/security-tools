## 二、并行会话竞争提交事故复盘（重点）

### 2.1 事故事件链（2026-08-15 提交结案总结时）

1. 我 `git add` 结案总结文档（仅 1 个新文件），准备提交
2. 提交时使用**普通 `git commit`（未加路径限定）**——这是事故的触发点
3. 并行会话此前已 staged 的 33 个文件（agent/human_in_the_loop/takeover_queue.py、agent/monitoring/*、data/evolution_lineage_export.csv 等）**仍留在共享 index 中**
4. 普通 commit 将 index 中**全部已 staged 内容**（我的 1 + 并行 33 = 34 个文件）一并提交
5. 提交标题却是我的（"docs(learning): TASK-06 结案总结入库"），33 个并行文件被"偷渡"进入该提交

**为什么 index 里会有并行会话的 staged 内容？** 此前轮次（d45b0c2b 转正提交前）并行会话持续在共享 index 上 add 其文件；我上轮的路径限定 commit 只提交我的文件，**并行会话的 staged 内容一直保留在 index 中未被清理**——共享 index 是并发写入的单一事实源，任何一方的普通 commit 都会带走全部 staged。

### 2.2 根因分析

- **共享 index 无隔离**：并行会话全部共用 `.git/index`，staged 集合是全局状态
- **普通 commit 的语义**：`git commit`（无 pathspec）提交 index 全部内容；`git commit -- <path>` 才只提交指定路径
- **残留 staged 未被察觉**：提交前未做 `git diff --cached --stat` 核对暂存集合（规范要求：提交后必须核对 staged 集合完整，同样适用于提交前）

### 2.3 处置流程（成功恢复）

```
1. 判定：git status -sb → "ahead 3, behind 1"（未推送）→ 可改写历史
2. 撤销：git reset --soft HEAD~1
   → 34 个文件全部退回 index（我的 + 并行 33），工作区无损失
3. 重提：git commit -- <我的文档路径>（路径限定）
   → 撞上并行会话持锁（其 commit --only 带 pre-commit 已跑 290s）
4. 等锁：后台轮询 200 次 × 3s，捕获锁释放窗口
   → 117 次尝试后提交成功（5775b2b7，仅 1 个文件）
5. 验证：git show --stat HEAD（仅我的文档）+ staged 残留 33 行（并行文件无损）
```

**关键判定标准：**
- `git status -sb` 未推送（无 ahead/behind）→ `reset --soft` 可安全修正
- 已推送 → **禁止 reset 改写历史**，核验内容完整性后接受现状
- 锁非 stale（git 进程活跃）→ **严禁删除 index.lock**，轮询等锁

## 三、可复用 CheckList（沉淀入项目规范）

> 已整理为 CheckList 更新至 `docs/wiki/git_detached_commit_ops_manual.md`

**提交前（每次必做）：**
- [ ] `git diff --cached --stat` 核对暂存集合：确认只含本任务文件

**提交后（必做）：**
- [ ] `git log --oneline -1` + `git show --stat HEAD` 核对提交内容集合

**遇锁：**
- [ ] 先 `Get-Process git` 判定锁是否 stale；进程活跃 → 禁删锁，轮询等锁
- [ ] 未推送 → `reset --soft` 可修正；已推送 → 禁改写历史，接受现状
