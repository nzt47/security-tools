# 并发串行瓶颈排查技术备忘录（memory 层锁审计 + 压测证据链）

> 日期：2026-08-15
> 场景：waitress threads 8→16 后高并发压测（12 并发中文请求，客户端 timeout=120s）
> 结论先行：**memory 层不存在导致请求严格串行的全局锁**；"串行"是 LLM 外呼延迟 + CPU 饱和（调度器子进程风暴）+ GIL 争抢的复合结果。但 memory 层存在一个需修复的同步压缩隐患。

## 2. memory 层锁审计（逐文件结论）

### 2.1 `memory/storage.py`
- `_write_lock`（`threading.Lock`）：仅保护**写**路径（`save_message` / `save_summary` / `clear_summary` / `clear_messages`），每次持锁仅为一次文件写入，毫秒级。
- `load_summary` / `load_recent_messages`：**读路径无锁**，纯文件读取。
- **结论**：不构成串行点。✅

### 2.2 `memory/memory_manager.py`
- `AsyncCompressor._lock`：仅控制后台压缩任务启停/待处理标记，**不在请求路径**。
- `get_context` 读路径：**无锁**。但存在**同步压缩分支**（潜在串行隐患）：
  ```python
  if self._need_compress:
      if not self._async_compressor.is_running():
          self._execute_compression()   # ← 请求线程内执行！
      self._need_compress = False
  ```
  `_execute_compression()` 内部含 **2 次 LLM 外呼**（`summarizer.compress` + `merge_summaries`）与 `save_summary` 写锁。若后台压缩器未运行，首个请求将阻塞在 2 次 LLM 上（数秒~数十秒）。
- `_message_window`（`deque`）：多线程 `append` / `list()` 无锁 → 读改写竞态（CPython 下 append 近似原子，但迭代与修改并发存在竞态风险）。
- `_need_compress`：无锁读改写（`get_context` 与 `add_message` 并发）→ 竞态。
- **结论**：无全局串行锁，但同步压缩分支是**每个请求可能触发的隐藏慢路径**。⚠️

### 2.3 `memory/vector_store/vector_store.py`
- `_shared_encoder_lock`（**模块级全局锁**）：仅在 `_get_shared_encoder` 单例**懒加载**时持有（双检锁，加载 SentenceTransformer ~20s 一次）；编码调用路径**不持锁**。
- `InvertedIndex._lock`（实例 `RLock`）：仅 BM25 打分/增删文档，毫秒级。
- **chat 请求路径不经过 VectorStore**（仅 skills/knowledge/周报使用）。✅

### 2.4 `memory/vector_store/sqlite_vec_backend.py`
- `_lock`：串行化 SQLite 写入（写安全），读路径同样持锁。不在 chat 请求路径。✅

### 2.5 `agent/context/assembler.py` + `agent/skills_mgmt/bm25_searcher.py`
- 无任何线程锁；`_pull_long_term` 实际仅读 `data/reflection/*.json`（轻量文件 IO）。
- **结论**：请求路径检索无锁。✅

## 3. 真正串行成因（证据权重排序）

1. **LLM 外呼延迟 6–13s/次**：DeepSeek 服务端排队/生成长文本。即使 16 线程并行，单请求耗时主因仍是 LLM。
2. **CPU 饱和 89.3% → GIL 争抢**：`task_scheduler` 在压测期间高频 spawn 子进程（`echo hello`/`python test.py`，会话内累计 16,070 次），fork + 子进程 CPU 占用使 waitress 线程调度出现明显延迟 → 请求间隔 13–33s 的"假串行"。
3. **行为模式切换 safe 14 次**：CPU 过高的症状而非原因；safe 模式仅拒绝高耗能任务，不直接串行化对话。
4. **看门狗线程池饱和风险（设计隐患）**：`_LLM_CALL_POOL`（max_workers=16）满员时，新请求在池内排队，`result(timeout=60)` 的计时包含排队等待 → 池饱和时请求被"排队式串行化"并 60s 降级。

## 4. 排查步骤回顾（可复现）

1. **日志窗口切片**：`server_semantic_fix9.log` 压测时段（11:56–12:01）按时间线回放，确认空档期实际执行模块。
2. **锁清单枚举**：对 memory 包全量 grep `threading.Lock|RLock|Semaphore|acquire`，逐条判断作用域（初始化 vs 请求路径）。
3. **请求路径还原**：`_call_llm_v2` → `_get_lifetrace_context` / `_get_user_context` / `_context_assembler_extra` / `memory.get_context`，确认各段是否触锁、是否 LLM 外呼。
4. **排除向量库**：确认 chat 路径不经过 VectorStore / sqlite_vec / `_shared_encoder_lock`。
5. **交叉验证**：`decision_basis.llm_duration_ms`（6–13s）+ `TaskScheduler` 计数（16,070）+ `行为模式变更`（14 次）三者互证。

---

## 5. 修复建议（按优先级）

1. **[P0] 修 `get_context` 同步压缩分支**：`_need_compress` 时禁止在请求线程内执行 `_execute_compression`，改为仅 `request()` 交给后台；或给同步压缩加独立线程 + 超时。
2. **[P1] 看门狗线程池去排队化**：`_run_llm_bounded` 在池满时应立即降级而非排队等 worker（或显著提高 `max_workers` / 改用信号量限流 + 直接调用）。
3. **[P1] 收敛调度器子进程**：`task_scheduler` 高频任务（测试用 `echo hello`/`python test.py`）应限频/禁用，避免 CPU 风暴挤压主链路。
4. **[P2] 竞态加固**：`_message_window` 与 `_need_compress` 加锁或改用原子操作（`deque` 并发 append 与 `list()` 竞争）。
5. **[P2] 压测环境隔离**：压测前确认无后台定时任务/子进程风暴，避免环境污染结论。

- 0/12 全部 120s 超时但组装证据 +10：部分请求已完成 LLM+组装却未在客户端超时前返回，**响应后置路径（输出护栏 / 会话保存 / lifetrace 保存）耗时未单独埋点**，需补耗时埋点定位。
- 看门狗启用后（本次压测运行中已生效 60s 上限），请求应于 ~60s 降级返回，客户端仍 120s 超时 → 说明存在 **60s 看门狗覆盖不到的卡点**（疑似 memory 同步压缩的 LLM 或响应保存路径），待埋点确认。
