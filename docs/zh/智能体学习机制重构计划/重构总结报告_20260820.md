## 3. 性能数据（本机实测，2026-08-20）

### 3.1 批量写入 vs 逐条提交（SQLite，10k 行）

| 方式 | 耗时 | 说明 |
|---|---|---|
| 单事务批量（本实现 `flush()`） | **21.4 ms** | 一次 `BEGIN` + N 行 `UPSERT` + 一次 `COMMIT` |
| 逐条提交（10k 次 commit） | 60304.5 ms | 每条独立事务，fsync 开销累积 |
| **加速比** | **≈ 2815×** | 批量事务消除了逐条 fsync 开销 |

### 3.2 持久化对埋点路径的开销（10k 次 `record_interaction`）

| 配置 | 耗时 | 说明 |
|---|---|---|
| 默认关闭（纯内存，`persistence=None`） | 151.4 ms | 与重构前行为完全一致（零改动路径） |
| 持久化开启（仅 pending 累积，未 flush） | 161.8 ms | 内存 dict 累积开销 **+6.88%** |
| `flush()` 落库 10k pending 行 | 6.6 ms | 批量单事务，可忽略 |

### 3.3 结论

- **默认关闭零感知**：未启用持久化时埋点路径无任何新增开销（生产默认不感知）
- **启用后开销可控**：pending 累积为纯内存操作（+6.88%），落库为批量事务（10k 行仅 6.6ms），且 I/O 全在锁外不影响并发埋点
- 持久化核心收益：**重启不丢数据 + 支持"连续 4 周"跨重启触发统计**（TASK-08 §5.2 触发条件的前置）

## 4. 关键设计决策（三义对齐）

| 决策 | 依据 |
|---|---|
| 持久化默认关闭 | 【不易】TASK-03"纯埋点+只读聚合、不改变业务行为"不变式；显式开启才生效 |
| 内存聚合为主 + 阈值批量 flush | 【简易】get_snapshot 走内存结构不变，落库为旁路；I/O 不进锁（持锁禁令） |
| 每日聚合表（`lm_daily_agg`）替代事件流水 | 【简易】最小充分；feedback 以均值近似回填，KPI 只消费均值，精度满足 |
| `__init__` 持久化启用块后置 | 【不易】回填依赖内存字段先初始化（本次修复的 AttributeError 根因） |
| DB 失败自动降级 + warning | 【不变式】埋点异常零影响主链路 |

## 5. 遗留与建议

- 生产启用持久化需显式配置（`persistence` 参数或 `LEARNING_METRICS_PERSIST_*` 环境变量）；`config.yaml` 配置段可后续补充
- KPI#4 复杂度维度（COMPLEX）依赖 TASK-01 `planning.wire_*` 接线后扩展（报告 §8 已披露）
- pytest 在并行会话活跃时耗时异常（环境问题，非代码缺陷），CI 为可靠验证通道
- 后续触发条件监控（"连续 4 周 <5%"等）可基于持久化数据建立周级滚动统计
