## 描述（Description）

waitress threads 8→16 后高并发压测（12 并发中文请求，客户端 timeout=120s）：
排队确实缓解（Task queue 176→6），但成功率反降至 **0/12**，请求间隔 13–33s 呈"严格串行"。

排查结论：**memory 层不存在导致串行的全局锁**，串行由以下复合因素造成：
1. LLM 外呼延迟 6–13s/次（DeepSeek 服务端排队/生成）
2. CPU 89.3% 饱和：`task_scheduler` 压测期间执行 16,070 次子进程（`echo hello` / `python test.py`），GIL 争抢使 waitress 线程调度延迟
3. 行为模式因 CPU 过高切换 safe 14 次（症状非原因）

同时发现 memory 层 **P0 隐患**（已修复）：`MemoryManager.get_context` 在 `_need_compress=True` 且后台压缩器未运行时，会在**请求线程内同步执行 `_execute_compression()`**（含 2 次 LLM 外呼），成为隐藏的每请求慢路径。

## 根因分析（Root Cause）

| 项 | 说明 |
|---|---|
| memory 层锁审计 | `storage.py` 写锁仅保护写路径；`memory_manager.py` 读路径无锁；vector_store `_shared_encoder_lock` 仅编码器懒加载；chat 请求路径不经过向量库 |
| 串行主因 | LLM 6–13s 延迟 + 调度器子进程风暴致 CPU 饱和/GIL 争抢（证据：`llm_duration_ms` 6332~12907ms；TaskScheduler 16070 次；行为模式切换 14 次） |
| P0 隐患 | `get_context` 同步压缩分支：请求线程内执行 `_execute_compression`（2 次 LLM 外呼 + 写锁） |
| 次生问题 | `_need_compress` 在 get_context 内无条件清除 → 后台未运行时压缩需求被丢弃 |

## 修复方案（已应用）

**P0：`memory/memory_manager.py`（commit `7a8a798f`）**
- `get_context` 不再同步执行压缩：改为 `_async_compressor.request()` 通知后台，未运行时幂等 `start_sync()` 启动
- `_need_compress` 改由 `_execute_compression()` 成功后清除；失败保留供后台重试
- 请求线程零 LLM 阻塞

**待跟进（P1/P2，未应用）**
- P1 看门狗线程池去排队化：`_LLM_CALL_POOL`（max_workers=16）满员时新请求排队，`result(timeout=60)` 计时含排队 → 池饱和即"排队式串行化"
- P1 收敛调度器子进程：高频测试任务限频/禁用，避免 CPU 风暴
- P2 竞态加固：`_message_window`（deque）与 `_need_compress` 无锁读改写

## 验收标准（Acceptance Criteria）

- [ ] 单请求 E2E：`get_context` 调用时后台压缩器未运行，请求线程不阻塞（观察日志无 `执行同步压缩`）
- [ ] 压测复跑：threads=16 场景下至少 1 轮 12 并发，成功率较 0/12 有提升（需先关闭调度器子进程风暴）
- [ ] 压缩功能不回归：消息超阈值后后台压缩仍能完成，`summary_version.txt` 版本递增，`_need_compress` 压缩成功后自动清除
