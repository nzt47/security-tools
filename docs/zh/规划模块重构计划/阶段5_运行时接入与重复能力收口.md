# 任务提示词 · 阶段 5：运行时接入与重复能力收口

> **关联文档**：`docs/zh/规划模块重构计划/规划模块理想设计.md`（缺陷 D6/D7/D8 详见第四节）
> **前置阶段**：阶段 0–4 全部完成且各自验收通过。

---

## 目标描述

将规划引擎**真正接入聊天主链路**（D7），启用生产配置，收敛与 `agent/task_planner/` 的重复能力（D8），完成端到端验收与灰度发布。这是重构的收官阶段，风险最高，必须灰度。

## 前置依赖

- 阶段 0–4 全部完成且各自验收通过。

## 执行步骤

1. **路由决策与接入**：
   - 明确接入位置：规划引擎作为 orchestrator **LLM 层之上的策略增强**（复用现有 模板→语义→LLM→拒识 路由的判定结果），即：语义层判定为"复杂任务"（或显式 `planning_mode=True`）时，调用 `_planner.chat()`（内部走统一执行模型），其响应进入现有 OutputGuard/记忆/反思/追踪链路，**不新增独立路由**，避免与现有四层路由冲突。
   - 修改 `orchestrator.py`：移除"追加规划引擎工具列表文本"的占位逻辑，替换为真实调用（保留 `get_stats()` 用于状态面板）。
   - 保留逃生通道：规划调用失败/超时/预算超限时回退到原 LLM 直答路径（调用前保存原 LLM 响应候选）。
2. **配置启用与参数化**：
   - `config.yaml` 将 `planning.enabled` 改为 `true`（灰度期通过环境变量 `PLANNING_ENABLED` 覆盖），`complexity_threshold` 参数化生效（修复 D6：`_needs_planning` 改为"关键词命中数 × 加权"或调用语义层判定的可配置规则，阈值从配置读取）。
   - 新增配置汇总：`planning.{enabled, complexity_threshold, budget.*, storage.*, metrics.enabled, ask_user_timeout_seconds, replan_on_failure}`。
3. **重复能力收口（D8）**：
   - 将 `agent/task_planner/planner.py` 的 4 类硬编码模式（代码/文章/分析/项目）迁移为 `planning/decomposer.py` 的"规则分解策略"（`RuleStrategy`），实现 `agent/task_planner` 的调用方改走 `planning` 统一入口。
   - `agent/task_planner` 保留兼容薄壳（转发调用），不再演进；评估后更新依赖关系图（`agent/data/skills.json`/架构检查需同步）。
4. **端到端验收与灰度**：
   - 用 `tests/eval/` 评测集在接入后复跑，与阶段 4 基线对比（成功率不下降、成本在预算内）。
   - 灰度步骤：`PLANNING_ENABLED=false→true`（先 5% 流量）→ 观察指标与错误率 → 全量。提供回滚开关文档（环境变量切换）。
   - 产出《规划引擎接入验收报告》：真实任务示例、指标前后对比、回滚步骤。

- [ ] **P1 · 接入 token 计费，回填成本口径**
  - 背景：`cost_total` 恒 0.0 的根因是 Plan 路径 `planning/executor.py` 只
    `record_step`、从不 `record_text`/`record_tokens`，budget 快照 `cost=0.0`
    （ReAct 路径 `react.py:_think` 已有记账）。评测集恰好全部走 Plan 路径，
    故聚合成本为 0。
  - 输入：预演数据 `cost_pilot_forecast.json`（由 `scripts/pilot_cost_forecast.py`
    生成，估算口径：token=字符数/3，单价 0.002 USD/1k）。13 用例全量预演成本
    ≈ **$0.0032**，其中 parallel 类主导（$0.003162，占 ~98%，6 次 LLM 调用）；
    multi_step 与 failure_injection 走规则分解 0 调用，接入计费后仍为 0。
  - 动作：executor 任务执行处（LLM 调用/工具结果聚合点）调用
    `budget_manager.record_text` 记账；`token_price_per_1k` 从配置透传
    （`config.yaml planning.token_price_per_1k`，默认 0.002 与 budget.py 一致）。
  - 验收：`scripts/eval_planning.py` 复跑后 `cost_total` 非 0 且与预演量级
    （13 用例 $0.001~0.01）吻合；评测基线表成本行回填；成本超限
    `EXCEEDED_COST` 降级路径有单测覆盖；`token_price_per_1k` 配置透传生效
    （改 `config.yaml planning.token_price_per_1k` 后 budget 快照/埋点 cost
    按新单价变化）；ReAct 与 Plan 两路径计价口径一致（同一 price 与同一
    token 估算方式，防双轨漂移）；executor 新增记账后既有规划单测全绿
    （无行为回归）。

- [ ] **P3 · 规则分解检索经验（默认不实施，可选增强）**
  - 背景：经验命中率仅统计 LLM 分解路径，规则分解不查询经验库（不改变行为）。
  - **默认决策：阶段 5 不实施**。理由：规则分解输出确定性高、行为可预期，
    不受 LLM 幻觉影响，注入经验收益低且会改变既有确定性行为（违【不易】）；
    命中率口径保持"仅 LLM 分解路径"并在 `规划评测基线.md` 固化。
  - **触发条件**（满足其一再启用）：① 线上出现规则分解类任务的系统性失败
    模式可被历史教训覆盖；② 业务方明确要求规则分解输出受经验引导。
  - **启用步骤**（若触发）：在 `RuleStrategy.decompose` 分解后追加
    `get_advice_for_task` 注入点并计入命中率埋点；重跑评测集核对成功率
    不下降；同步更新命中率口径文档。
  - 验收：默认不实施时，决策与理由记录在案、口径固化——`规划评测基线.md`
    命中率定义注明"仅 LLM 分解路径"（可直接检索验证）；启用时按上述步骤
    全量验证并更新基线，且命中率埋点 `record_experience_lookup` 的 task_type
    标签计数与检索实际次数一致。

## 预期成果

- 复杂任务真实走规划链路；失败/超时自动降级到直答；指标与日志贯通。
- 配置全部参数化生效；双规划器收敛为单一入口。
- 端到端验收通过，可安全灰度。

## 评估标准

1. E2E 测试：构造复杂任务（多步+并行+失败注入），断言响应来自规划链路（`used_planning=True` 或响应含 `plan_summary`）、失败时回退直答、链路耗时 ≤ 配置 `timeout_seconds`。
2. 评测集 KPI 对比阶段 4 基线：成功率 ≥ 基线，平均成本 ≤ 预算上限。
3. `planning.enabled=true` 且 `PLANNING_ENABLED=false` 时可回退为旧行为（逃生通道测试）。
4. 架构检查/依赖图更新后 CI 通过；既有规划测试与全量回归全绿。
5. `agent/task_planner` 兼容薄壳转发测试通过，其原调用方无感知。

## 回滚方式

环境变量 `PLANNING_ENABLED=false` 一键回退；orchestrator 改动可单独 revert；`agent/task_planner` 薄壳保留原始实现，回滚即恢复旧规划器。
