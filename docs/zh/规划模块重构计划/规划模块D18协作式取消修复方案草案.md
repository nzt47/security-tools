## 一、根因分析

`PlanExecutor.execute_plan` 循环在 `_do_execute_task` 处 `await` 工具协程，此 await 点是唯一可中断机会。当前 `cancel_plan` 仅直接赋值 `plan.state = CANCELLED`（[executor.py L473-478](../../../planning/executor.py#L473-L478)）：

- 正在 `await` 的工具协程**不感知取消**，继续执行直到自然结束；
- `execute_plan` 循环在工具完成后才检查状态，取消无法"立即生效"；
- 同步工具（非协程）在独立线程/进程阻塞时，事件循环内完全无法中断。

边界 #2/#3/#6 已修复（收尾不覆盖取消、断言容忍、恢复路径统一），但**取消本身不传播**——D18 复现测试 `test_cancel_interrupts_running_tool` 仍按预期失败。

## 二、三义分析

- **【不易】** 取消语义是业务内核：`cancel_plan(plan_id)` 后，进行中的工具调用必须尽快中断（协作式取消），计划最终状态必须为 `CANCELLED`。
- **【变易】** 工具形态多样（异步协程可协作取消；同步阻塞工具无法协作取消）；多个 plan 可能并发执行于同一 executor 实例（取消标志必须 per-plan 隔离）。
- **【简易】** 最小充分解：per-plan 取消标志 + `asyncio.Task.cancel()` 传播 + 工具调用前检查 + 同步工具降级（执行完当前调用即退出）。不引入线程/进程级强杀（超出范围）。

## 三、修复方案（推荐方案 A：协作式取消）

### 1. per-plan 取消标志

`plan.metadata["_cancelled"] = True` 作为取消标志（**不用** executor 实例级 `asyncio.Event`，避免并发多计划互相干扰）：

- `_do_execute_task` 在**每次工具调用前**检查：若已取消 → 抛 `asyncio.CancelledError`；
- `execute_plan` 循环任务完成后检查：若已取消 → 退出循环不再调度后续任务。

### 2. 取消传播（`PlanExecutor.cancel_plan`）

```python
async def cancel_plan(self, plan: Plan) -> Plan:
    plan.metadata["_cancelled"] = True
    plan.state = PlanState.CANCELLED        # 兼容现状：直接赋值（终态校验由 core 断言兜底）
    task = self._running_tasks.get(plan.id)  # 新增：记录当前正在执行的 execute_plan 任务
    if task is not None and not task.done():
        task.cancel()                        # 传播 CancelledError 到 await 点
    return plan
```

### 3. 运行任务引用管理

`execute_plan` 入口登记 `self._running_tasks[plan.id] = asyncio.current_task()`，`finally` 清理（`pop`）。

### 4. await 点取消处理

`_do_execute_task` 的 `await` 处 `CancelledError` 自然传播到 `task.cancel()`；循环外层捕获 `CancelledError` → 标记取消收尾（不当作异常错误），`_finalize_state(plan, CANCELLED, ...)`（边界 #2 已保证保留取消状态）。

### 5. 同步工具降级

`asyncio.iscoroutinefunction(tool)` 为 False 时：无法协作取消 → **执行完当前工具调用后检查标志退出**，不再调度后续任务（取消语义降级为"尽快停止"而非"立即中断"）。

## 四、方案对比（备选）

| 方案 | 说明 | 取舍 |
|------|------|------|
| **A（推荐）** | per-plan 标志 + `task.cancel()` + 调用前检查 + 同步降级 | 最小改动，覆盖全部已知竞态；同步工具无法即时中断（可接受降级） |
| B | 工具调用包裹 `asyncio.wait_for(..., timeout)` 强制超时取消 | 需配置超时；对正常长任务误伤；不解决同步工具 |
| C | 线程/进程级工具隔离 + 强杀 | 架构改动大，超出阶段 3 范围，风险高 |

## 七、风险与回滚

- **风险 1**：工具内部 `try/except BaseException` 吞掉 `CancelledError` → 取消失效。兜底：循环内标志检查仍会在工具返回后退出，语义不丢失。
- **风险 2**：`task.cancel()` 在错误线程/时序调用（task 已完成）→ 幂等（`not task.done()` 守卫）。
- **风险 3**：`ReActLoop` 路径（`ReActResult`）的取消不在本方案范围，留阶段 3 内单独评估。
- **回滚**：改动集中在 `planning/executor.py` 单文件，可单独 revert；取消标志为 metadata 新增字段，向后兼容。
