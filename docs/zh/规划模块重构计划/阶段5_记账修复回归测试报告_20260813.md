## 二、2 个真实回归的修复验证过程（重点）

本次提交在验证过程中暴露并修复了 **2 个由 orchestrator.py 日志增强引入的真实回归**，均通过失败的既有测试第一时间捕获，未流入线上。

### 回归 1：基类 `Orchestrator` 无 `_config` 属性

- **触发用例**：`test_digital_life_comprehensive.py::TestChatMethodComplete::test_chat_planning_mode_enabled`
- **引入原因**：规划入口日志新增 `self._config.get("planning")`。基类 [Orchestrator](../../../agent/orchestrator/orchestrator.py#L180) 本身无 `_config`（该属性由宿主类 LifecycleManager.__init__ 提供），测试经 `Orchestrator.__new__` 构造故缺失；模拟脚本走真实 `DigitalLife`（混入 LifecycleManager）未暴露此问题。
- **失败现象**：`AttributeError: 'Orchestrator' object has no attribute '_config'`（-k planning 全量跑 330/331 时捕获）
- **修复**：`getattr(self, "_config", None) or getattr(self, "config", None) or {}`（最小兜底，不改生产路径）
- **验证**：`TestChatMethodComplete` 3/3 通过；规划子集 331/331 通过

### 回归 2：timeout 配置读取丢 `planning` 子段，恒取默认 30s

- **触发用例**：`test_planning_stage5_e2e.py::TestPlanningFallback::test_planning_timeout_falls_back_within_budget`
- **引入原因**：日志重构把改动前 `(self._config.get("planning") or {}).get("timeout_seconds", 30)` 改写为 `self._config.get("timeout_seconds", 30)`——在**顶层 dict** 上取键，`planning` 子段的 `timeout_seconds=0.1` 永远读不到，恒回退默认 30s。
- **定位过程**：
  1. 入口日志直接暴露 `timeout_seconds: 30.0`（测试注入 0.1 失效）；
  2. Python 复现：`orch._config = {'planning': {'timeout_seconds': 0.1}}` 时顶层 `.get('timeout_seconds', 30)` 仍返回 30；
  3. 与改动前 git diff 逐行比对，确认丢失 `.get("planning")` 一层。
- **修复**：`_planning_cfg = _planning_cfg.get("planning") or {}`（恢复与改动前一致的取值语义，同时保留 getattr 兜底）
- **验证**：`test_planning_timeout_falls_back_within_budget` 单独跑通过（超时 0.1s 中断，链路 <1.5s）；stage5_e2e 10/10、17 组合、331 规划子集全绿

### 教训（守【不易】）

1. **日志增强不得改变业务取值路径**——本次两处回归均为"为打日志重排取值逻辑"引入；正确做法是先取好值再打日志（`_planning_cfg` 收敛后复用）。
2. 新增日志字段必须在所有构造形态下可读（基类直构 vs 混入宿主），统一用 `getattr` 兜底。
