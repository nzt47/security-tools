## 一、缺陷定位

### 1.1 现象（复现测试）

`tests/unit/test_planning_defect_d1.py::test_final_transition_goes_through_state_machine`：
在 `core.execute_plan()` 执行全成功计划后，断言 `(EXECUTING, COMPLETED)` 状态机钩子被触发
→ **当前不触发**（复现成功）。

### 1.2 代码位置

| 位置 | 代码 | 问题 |
|------|------|------|
| `planning/executor.py` L178 | `plan.state = PlanState.EXECUTING` | 绕过状态机（幂等冗余，影响小） |
| `planning/executor.py` L214–222 | `plan.state = PlanState.COMPLETED/FAILED` | **绕过状态机**：钩子、转换历史、合法性校验全部失效 |
| `planning/core.py` L202–211 | `if plan.state == PlanState.EXECUTING:` … | **死代码短路**：executor 返回后 state 必为 COMPLETED/FAILED，分支永不成立 |

---

## 二、根因分析

1. **状态变更权责分散**：`plan.state` 被三处直接赋值（executor 起始、executor 收尾、core 收尾），
   而 `PlanStateMachine` 的 `transition()`（含合法性校验、`_transition_history`、`_trigger_hooks`）仅被 core 调用一次（INIT→EXECUTING）。
2. **core 步骤 4 与 executor 收尾逻辑重复且互斥**：executor 先收尾改状态 → core 步骤 4 的 `EXECUTING` 判断成为不可达死代码。
3. **设计意图**：core 步骤 4 本意是"最终状态判断走状态机"，但因 executor 抢先直接赋值而失效。

---

## 三、三义分析（不易 / 变易 / 简易）

### 不易（Invariance，锁定的业务内核）
- **计划状态变更必须经状态机**：合法性校验、转换历史、钩子回调是状态机的不变量能力，不能被直接赋值旁路。
- 状态机合法转换表 `VALID_TRANSITIONS` 为契约，不可改动。

### 变易（Adaptability，需权衡的部分）
- `PlanExecutor` 可**独立使用**（现有单元测试 `test_planning_executor.py`、D1/D14 复现测试均直接构造 executor 不传状态机）。
  → 修复必须兼容"无状态机的独立使用"路径，否则破坏既有契约。
- 未来阶段 2 引入统一执行模型时，状态机注入方式需可演进。

### 简易（Simplicity，最简方案）
- 最小改动：**给 executor 增加可选状态机引用，收尾时若存在则走 `transition()`，否则保持直接赋值**（向后兼容）。
- 不引入新抽象、不重构 executor 接口签名、不改状态机契约。

## 四、方案对比

| 方案 | 做法 | 改动面 | 兼容性 | 评价 |
|------|------|--------|--------|------|
| **A1（推荐）** | executor 构造注入可选 `state_machine`；收尾用 `_finalize_state()` 走状态机，无状态机时降级直接赋值 | executor.py 2 处、core.py 1 处 | ✅ 独立使用完全兼容 | 最小充分解，符合三义 |
| B | core 删除步骤 4 死代码，最终状态完全由 executor 负责（不传状态机） | core.py 1 处 | 需 executor 自身能触发钩子（否则 C1 未修） | 不解决根因，钩子仍不触发 ❌ |
| C | executor 完全剥离状态变更，只返回执行结果，由 core 统一判断并 transition | executor.py、core.py 多处 | ❌ 破坏 executor 独立使用契约，改动大 | 违反"最小改动" ❌ |

**结论：采用方案 A1。**

## 五、推荐方案（A1）变更清单

> 以下为设计描述，**本草案阶段不落地代码**；实施时按此清单修改。

### 变更 1：`planning/executor.py`

1. `PlanExecutor.__init__(self, tool_registry, llm_service=None, max_retries=3, config=None, state_machine=None)`
   - 新增可选参数 `state_machine: PlanStateMachine = None`，保存到 `self.state_machine`。
   - 保持既有位置参数顺序不变（向后兼容，仅追加可选参）。
2. 新增私有方法：

```python
def _finalize_state(self, plan: Plan, target: PlanState, *, reason: str) -> None:
    """收尾状态变更：优先走状态机（触发钩子/记录历史），无状态机时降级直接赋值"""
    if self.state_machine is not None:
        self.state_machine.transition(plan, target, reason)
    else:
        plan.state = target
```

3. `execute_plan()` 收尾 L214–222 改为：

```python
if plan.is_success():
    self._finalize_state(plan, PlanState.COMPLETED, reason="所有任务执行成功")
    plan.result = "所有任务执行成功"
elif plan.is_complete():
    self._finalize_state(plan, PlanState.COMPLETED, reason="部分任务失败但计划完成")
    plan.result = "计划执行完成,但部分任务失败"
else:
    self._finalize_state(plan, PlanState.FAILED, reason="计划执行超时或异常终止")
    plan.error = "计划执行超时或异常终止"
```

4. L178 `plan.state = PlanState.EXECUTING` **保持不变**（幂等冗余；core 已先行 transition，独立使用场景仍需此赋值，不引入状态机自环问题）。

### 变更 2：`planning/core.py`

1. `PlanningCore.__init__` 中，executor 创建之后注入状态机（当前顺序 executor 先于 state_machine 创建）：

```python
self.executor = PlanExecutor(...)          # 现有
self.state_machine = PlanStateMachine()     # 现有
self.executor.state_machine = self.state_machine   # 新增：收尾状态变更走状态机
```

2. 步骤 4（L202–211）由死代码改为**兜底断言 + 日志**，明确"executor 已通过状态机完成收尾"：

```python
# 最终状态已由 executor 通过状态机完成（EXECUTING -> COMPLETED/FAILED）
assert plan.state in (PlanState.COMPLETED, PlanState.FAILED), \
    f"计划执行后状态异常: {plan.state}"
```

> 若后续阶段 2 统一执行模型，可整体移除步骤 4 冗余逻辑。

## 七、风险与回滚

- **风险 1**：executor 收尾调用 `transition()` 时若当前状态不允许（例如独立使用时 plan.state 被外部改为非 EXECUTING），会抛 `InvalidStateTransitionError`。
  - 缓解：`_finalize_state` 对 `InvalidStateTransitionError` 捕获并降级为直接赋值（打印告警），保证独立使用健壮性。
- **风险 2**：`asyncio.create_task` 风格的异步钩子在 transition 中 fire-and-forget，异常不会被等待（既有行为，不在本方案范围）。
- **回滚**：本方案仅改 2 个文件（executor.py、core.py），撤销 2 处变更即可；或经 git 还原。测试文件不随方案回滚（C1 测试作为回归护城河保留）。
