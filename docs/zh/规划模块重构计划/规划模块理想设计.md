## 二、现状审计：云枢规划模块实际运行状况

### 2.1 模块结构（`planning/`）

| 文件 | 职责 | 现状评价 |
|------|------|----------|
| `planning/core.py` | `PlanningCore` 主控：协调分解/执行/反思/状态机/ReAct | 双入口并存：`plan()+execute_plan()` 与 `chat()→ReActLoop` |
| `planning/decomposer.py` | `TaskDecomposer`：LLM 或规则分解 | `refine()` 已实现但**从未被调用** |
| `planning/executor.py` | `PlanExecutor` + `ToolRegistry` | 仅串行执行 `next_tasks[0]`；`parallel_groups` 被丢弃；中文工具匹配靠脆弱关键词表 |
| `planning/reflector.py` | `Reflector`：步骤/计划反思 + 经验教训持久化 | `learn_from_experience` 重复定义（死代码）；经验只存不用；ReAct 路径调用参数错误 |
| `planning/state_machine.py` | `PlanStateMachine` | 状态转换正确，但无持久化、无取消信号的协作式语义 |
| `planning/react.py` | `ReActLoop`：思考-行动-观察循环 | 反思结果只打日志不应用；`ask_user` 伪实现；循环检测过于粗糙（仅判断连续相同动作） |
| `planning/models/` | Plan/Task/Action/Record/ReAct 数据模型 | 结构基本合理；`Plan.is_success()` 存在逻辑短路缺陷 |

### 2.2 运行时接入情况

- **初始化**：`agent/orchestrator/lifecycle_manager.py::_initialize_planning_engine()` 在 `_PLANNING_AVAILABLE` 时实例化 `PlanningCore` + `ReActLoop`，注册 5 个规划工具（check_health / get_status / search_memory / get_sensor_summary / llm_chat）。
- **聊天主链路**：`agent/orchestrator/orchestrator.py` 的 chat 流程（模板层→语义层→LLM 层→拒识兜底→OutputGuard→记忆）中，规划模块**仅**在 LLM 响应尾部追加一行"（规划引擎已就绪，可用工具: ...）"文字（`self._planner.get_stats()`），**从未调用 `_planner.chat()` / `_react_loop.run()`**。
- **配置**：`config.yaml` 中 `planning.enabled: false`，`max_depth: 5`，`timeout_seconds: 30`（`timeout_seconds` 实际未被代码使用）。
- **结论**：规划引擎是"已建未用"的可选组件，与运行中的聊天链路完全解耦。

### 2.3 与其他组件的重复

`agent/task_planner/`（`planner.py` / `enhanced_planner.py` / `dag.py` / `enhanced_dag.py`）是另一套**规则硬编码**的任务规划器（4 类关键词模式：代码/文章/分析/项目），用于上下文工程的 DAG 生成。系统存在**两套规划器**，职责边界不清、能力不一致，需收敛。

### 2.4 现有测试

- `tests/integration/test_planning_core.py`（30 个用例，含端到端工作流）
- `tests/unit/test_planning_react.py`、`tests/unit/test_planning_state_machine.py`
- 覆盖了初始化、分解、执行、取消、状态查询等基础路径，但**未覆盖**：并行执行、验证机制、持久化恢复、预算超限、降级链、反思闭环应用。

## 三、设计思路合理性评估

### 3.1 合理且应采纳的部分（【不易】应固化为不变契约）

| 设计观点 | 评估 | 落地建议 |
|----------|------|----------|
| 目标层 / 策略层 / 执行层三层解耦 | **正确且正是当前缺口**：当前 Plan 直接是一串任务，无策略层与目标层，遇到阻碍只能失败或整体重做 | 在 Plan 模型中引入 `goal`（目标）+ `strategy`（策略）+ `tasks`（执行），重构时的核心不可变量 |
| 动态反馈与闭环（监控→偏差检测→重规划） | 正确。闭环是 agent 规划的命门，当前闭环断裂 | 修复反思→调整→重规划链路（阶段 1、2） |
| 硬约束 / 软约束 / 资源调度 | **必须补充**。LLM agent 的成本、token、时限是不可回避的硬约束 | 阶段 3 BudgetManager |
| Plan B / 降级 / 优雅降级 | 正确，agent 容错的最低要求 | 阶段 3 降级链 |
| 可解释性与人机协同 | 方向正确，但"人机协同"必须是**真正的异步暂停/恢复**而非标志位 | 阶段 1 修复 ask_user；阶段 4 输出结构化计划摘要 |
| 模块化 / 插件化（分解策略、调度算法、数据源可替换） | 正确 | 在抽象层预留策略接口（阶段 2） |
| 规划验证机制（执行前校验逻辑合理性与资源可用性） | **关键补缺项**，当前完全没有 | 阶段 2 计划验证器 |
| 混合规划（few-shot CoT + 确定性算法，固定流程用工作流引擎） | 与系统现有 orchestrator 分层思想一致 | 阶段 5 接入时决策路由位置 |
| 统一状态表示 | 正确，当前 Plan 与 ReAct 各说各话 | 阶段 2 统一执行记录模型 |
| ADPS 双轴框架（认知功能轴 × 执行拓扑轴） | 框架性指导，适合作为演进坐标系，不宜直接落地 | 作为阶段 4/5 演进参考 |

### 3.2 存在理论缺陷或需要修正的部分

1. **"最理想"缺成本模型**：理想规划模块必须"现实"，但对 LLM agent 而言最重要的现实是 **token/成本预算**，设计文档未提及。理论层面：无限规划 + 无预算 = 不可控成本风险。
2. **"容错"缺进程级语义**：agent 的容错不止于任务失败重试，还包括**进程崩溃/重启后的计划恢复**。设计文档未覆盖持久化与检查点。
3. **"多尺度支持"超出当前业务必要性**：年度→分钟级多尺度规划对当前云枢业务是过度设计，违背【简易】原则。应先做单尺度深度。
4. **"What-if 影响评估"在 v1 属于过度设计**：需要完整模拟器支撑，工程代价高、收益不确定。应降级为"计划摘要 + 关键参数可调 + 重规划"。
5. **人机协同语义未定义**：何时暂停？超时怎么办？恢复后状态如何合并？必须定义 暂停/恢复/继续/超时策略 协议。
6. **未提 LLM 输出鲁棒性**：分解/思考结果依赖 `json.loads` 直接解析，无 schema 校验、无重试。这是实践层面的最大脆弱点，设计文档反而遗漏了最关键的工程细节。

### 3.3 与云枢系统现状的适配性

| 设计主张 | 与现状的冲突/契合 |
|----------|-------------------|
| 双轴框架 | 契合：云枢已有 模板/语义/LLM/拒识 四层路由（执行拓扑轴），规划应作为其中"LLM 层的策略增强"而非新的独立路由，避免与现有多层路由打架 |
| 插件化评估标准 | 契合：云枢已有 `core/registry.py` 统一注册表，可直接复用 |
| 分层任务分解 | 部分重复：与 `agent/task_planner/` 规则规划器重复，重构时须收敛（阶段 5） |

## 四、识别出的理论/实践缺陷

按严重度分级（P0 阻塞性正确性缺陷 → P1 设计/架构缺陷 → P2 缺失能力）：

### P0 正确性缺陷（必须最先修复）

| # | 缺陷 | 位置 | 影响 |
|---|------|------|------|
| D1 | `Plan.is_success()` 要求 `state == COMPLETED`，但 `executor.execute_plan()` 在仍处于 `EXECUTING` 时调用它，导致"全部成功"分支永远不触发，全成功计划被标记为 `result="计划执行完成,但部分任务失败"` | `planning/models/plan.py` + `planning/executor.py` | 成功/失败判定错误，污染执行记录与统计 |
| D2 | ReAct 路径调用 `reflector.step_reflect(task, ...)` 传入**字符串** task，而签名期望 Task 对象并访问 `task.description` → `AttributeError` 被 try/except 静默吞掉 | `planning/react.py` + `planning/reflector.py` | **ReAct 路径的反思永远失效**，闭环完全断裂 |
| D3 | `ask_user` 行动类型是伪实现：直接返回成功"等待用户输入"，不真正暂停等待用户，循环继续执行 | `planning/react.py::_act` | 人机协同名存实亡，用户无法在关键节点介入 |

### P1 设计/架构缺陷

| # | 缺陷 | 说明 |
|---|------|------|
| D4 | 双路径割裂 | `plan()`+`execute_plan()` 与 `chat()`→ReAct 互不共享状态与记录；`decomposer.refine()`、`plan_reflect` 结果从不回灌计划 |
| D5 | 并行执行未实现 | 分解器输出 `parallel_groups` 后被丢弃；执行器只取 `next_tasks[0]` 串行执行；`TaskType.PARALLEL` 从未生效 |
| D6 | 复杂度判定粗糙且配置悬空 | `_needs_planning` 靠关键词计数；`complexity_threshold`（0.5）配置**从未被使用**；误判率高 |
| D7 | 规划引擎未接入主链路 | orchestrator 仅追加工具列表文本；`planning.enabled: false`；"已建未用" |
| D8 | 双规划器并存 | 与 `agent/task_planner/` 功能重复，职责边界不清 |
| D9 | 无计划持久化 | `_active_plans` 纯内存，重启即失；无检查点/恢复；反思经验库（`./data/reflection`）与系统记忆/知识库无关联 |
| D10 | 工具匹配与参数抽取脆弱 | `ToolRegistry.find_tool` 中文关键词表极小且过宽（`"将"`、`"写入"`）；`_extract_params` 硬编码中文句式正则，鲁棒性差 |
| D11 | 无规划验证机制 | 依赖图不校验（悬空依赖→任务永不可执行→计划卡死）；工具可用性不预检；循环依赖不检测 |
| D12 | 反思调整不应用 | `reflection.adjustments` 只打日志，不更新 context / plan / 后续思考提示词 |

## 五、需要补充完善的内容

在采纳理想设计的同时，须补充以下内容（对应任务阶段）：

1. **成本与预算体系**（阶段 3）：token/cost/时间三层预算，超限时触发降级或征求用户。
2. **持久化与崩溃恢复**（阶段 2）：计划/任务/执行记录落库（SQLite，复用系统已有 `agent/data/orchestrator_config.db` 的 SQLite 先例），启动时恢复未完成计划。
3. **规划验证机制**（阶段 2）：执行前校验依赖完整性、环检测、工具可用性、LLM 输出 schema 校验+重试。
4. **规划质量评测体系**（阶段 0 + 阶段 4）：定义 KPI（成功率、平均迭代数、平均成本、失败原因分布），建立回归基准集。
5. **真正的异步人机协同协议**（阶段 1/3）：`ask_user` 需返回"等待用户"语义并暂停循环，支持恢复/放弃/超时。
6. **规划前经验检索**（阶段 4）：decompose/think 前调用 `reflector.get_advice_for_task()`，让历史经验进入规划输入。
7. **LLM 输出鲁棒性**（阶段 2）：统一 JSON 提取 + schema 校验 + 失败重试 + 规则兜底（现有 `_extract_json_from_response` 的健壮性升级）。
8. **规划摘要与可观测输出**（阶段 4）：结构化 `PlanSummary`（目标、策略、任务、依赖、风险、预算），供 UI/日志/追踪使用。
9. **单规划器收口**（阶段 5）：将 `agent/task_planner/` 的规则模式并入规划引擎的"规则分解策略"，消除重复。

## 六、重构原则与总体路线

### 6.1 三义原则（【不易/变易/简易】）

- **【不易】**：公开 API 契约（`PlanningCore.plan/execute_plan/chat/cancel_plan/get_plan_status`、`ToolRegistry.register/get/list_tools`、`ReActLoop.run`、`Plan/Task/Action` 模型字段）保持不变；现有测试通过；日志/埋点格式不破坏现有观测体系。
- **【变易】**：分解策略、执行拓扑、约束检查、降级策略以策略对象注入，不写死 if-else；保留插件式扩展点。
- **【简易】**：不做 what-if 模拟、不做多尺度规划、不引入新重型依赖；每个阶段最小充分，可回滚。

### 6.2 阶段依赖关系

```
阶段 0（基线）→ 阶段 1（正确性）→ 阶段 2（统一模型+闭环+持久化）→ 阶段 3（预算+容错）
                                                              → 阶段 4（经验回灌+观测）→ 阶段 5（接入+收口）
```

- 阶段 0/1 必须串行先行（修复正确性前不得叠加新功能）。
- 阶段 2 与 3 可在阶段 1 完成后并行（2 偏数据模型与执行，3 偏策略与资源）。
- 阶段 4 依赖阶段 2（需统一执行记录）。
- 阶段 5 依赖全部前置阶段，且涉及运行时风险，须灰度启用。

### 6.3 每阶段固定交付模板

每个阶段任务提示词统一包含：`目标描述`、`前置依赖`、`执行步骤`、`预期成果`、`评估标准（验收门禁）`、`回滚方式`。
