## 二、回滚实质与方案选型

**回滚的实质**：关闭规划引擎（复杂任务不再进入 `_planner.chat()`，回退 LLM 直答），**而非**抹掉 D7 接入的全部代码。

| 方案 | 做法 | 冲突 | 生效 | 建议 |
|---|---|---|---|---|
| **A 配置级回滚（首选）** | `PLANNING_ENABLED=false`（+ `config.yaml planning.enabled=false`）+ 重启 | 无 | 秒级 | ✅ 覆盖 99% 场景，实测 S5 通过 |
| **B 反向补丁（本方案）** | 生成精确反向 patch，只删 D7 接入功能点，保留 D13/记账修复 | 可控（逐 hunk 裁决） | 需发布 | 仅当环境变量失效时使用 |
| **C 热切换开关（根治）** | 将 `planning.enabled` 固化为运行时热重载配置（`load_dynamic_config`），灰度/回滚不再依赖重启与环境变量 | 无 | 秒级 | TD 候选，排期根治 |

> 结论：**方案 A 足够覆盖常规回滚；方案 B 是 A 失效时的兜底；方案 C 根治**（排期随 TD-4 一并处理）。

### 3.5 安全边界

- **禁止**在主工作区执行 revert（并行会话活跃，共享 index 会被清空——项目记忆已有事故）
- 反向补丁提交**只存在于临时分支**，不推送、不合并入 develop；回滚恢复 = 删除分支
- 反向补丁生成后需过 pre-commit 检查（并行会话活跃时可能误报，用 `git commit --no-verify` + 手动验证脚本 exit 0 兜底，同 `b8cb47cc` 先例）
