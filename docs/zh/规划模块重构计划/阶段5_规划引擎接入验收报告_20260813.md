## 二、D7 运行时接入（聊天主链路）

### 接入方式

规划引擎作为 orchestrator **LLM 层之上的策略增强**（[orchestrator.py](file:///c:/Users/Administrator/agent/agent/orchestrator/orchestrator.py) L923-L970）：

- 复用四层路由判定结果：语义层判定"复杂任务"（`_needs_planning` 参数化，D6）或显式 `planning_mode=True` 时调用 `_planner.chat()`；
- 规划响应覆盖 LLM 直答结果，**继续进入既有 OutputGuard / 记忆 / 反思 / 追踪链路**，不新增独立路由；
- 响应字典 metadata 注入 `used_planning=True` 与 `plan_summary`（评估标准 1 的可断言口径）；
- 状态面板所需 `get_stats()`（`PlanningCore` 指标）保留不变；
- 同步桥 `_run_async_in_sync`：同步 `process()` 内运行 async `_planner.chat()`（无事件循环 `asyncio.run`；有事件循环线程池隔离），`asyncio.wait_for` 硬超时。

### 逃生通道（失败/超时/空响应 → 回退原 LLM 直答）

| 场景 | 回退行为 | 测试 |
|---|---|---|
| 规划调用抛异常 | 捕获 → 回退 LLM 直答响应，不记 planning layer | `test_planning_exception_falls_back` |
| 规划返回 None/空 response | 空响应判定 → 回退 LLM 直答 | `test_planning_empty_response_falls_back` |
| 规划超时（`timeout_seconds=0.1`，挂起 2s） | `wait_for` 中断 → 回退直答，断言耗时 < 1.5s | `test_planning_timeout_falls_back_within_budget` |

### 真实任务示例

**接入行为（E2E，planner 为 mock，验证 orchestrator 接线）**：

```
输入: "帮我完成一个多步骤任务"（_needs_planning → True）
路由: InputGuard pass → 模板 miss → 语义/拒识 pass → LLM 直答缓存
     → D7: _planner.chat() 调用（planning_mode=True）→ 响应覆盖
返回: {"success": True, "data": "<规划引擎响应>", "metadata": {"used_planning": true}}
埋点: yunshu_intent_layer_total{layer=planning} +1
```
