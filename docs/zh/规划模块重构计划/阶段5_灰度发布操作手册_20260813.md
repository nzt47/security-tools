## 三、环境变量切换步骤

### 3.1 方式 A：systemd / Docker 部署（生产）

```bash
# 灰度：5% 实例（仅给目标实例追加环境变量）
systemctl set-environment PLANNING_ENABLED=true     # 或写入 docker-compose 对应服务 environment
systemctl restart yunshu-app

# 全量
# 对所有实例执行上述命令

# 回滚（一键）：清空环境变量 → 回落 config.yaml（enabled=true）或显式 false
systemctl set-environment PLANNING_ENABLED=false
systemctl restart yunshu-app
```

### 3.2 方式 B：Windows 服务 / 计划任务

```powershell
# 设置进程环境变量（一次性，当前会话）
$env:PLANNING_ENABLED = "true"
# 持久化到用户/系统环境变量
[Environment]::SetEnvironmentVariable("PLANNING_ENABLED", "true", "User")
# 重启应用进程使配置生效

# 回滚
[Environment]::SetEnvironmentVariable("PLANNING_ENABLED", "false", "User")
```

### 3.3 方式 C：本地开发验证

```powershell
$env:PLANNING_ENABLED = "true"   # 或 $env:PLANNING_ENABLED = "false"
python -c "from agent.orchestrator.lifecycle_manager import LifecycleManager; print('skip')"  # 占位，实际通过应用入口验证
# 清除：Remove-Item Env:PLANNING_ENABLED
```

> 取值语义（[lifecycle_manager.py](../../../agent/orchestrator/lifecycle_manager.py)）：`false`/`0`/`no` 禁用；`true`/`1`/`yes` 启用；其他值视为非法并回退 `config.yaml`。
> 模块不可用（`planning` 导入失败）时强制禁用，不受环境变量影响——这是第三重保险。

### 3.4 回滚 SOP（任一步骤异常即执行）

```bash

## 四、监控指标看板配置

### 4.1 指标清单

| 指标 | 含义 | 来源/通道 | 灰度观察点 |
|---|---|---|---|
| `yunshu_intent_layer_total{layer="planning"}` | 规划引擎命中的意图分层计数（D7 埋点） | Prometheus 原生（yunshu-app `/metrics`） | **主指标**：规划流量是否按预期增长 |
| `yunshu_intent_layer_ratio{layer="planning"}` | 各层占比（恒 = 1.0） | Prometheus 原生 | 规划占比爬坡曲线 |
| `planning.plans.total/success/failed` | 计划执行成功/失败计数 | BusinessMetricsCollector 内存字典（`planning_metrics.get_metrics()`） | 成功率（failed/total） |
| `planning.cost_total` | 规划 token 计费累计（USD） | 同上 | 成本随流量线性，不失控 |
| `planning.iterations_avg` / `planning.duration_ms` | 平均迭代数 / 单计划耗时 | 同上 | 规划质量与延迟 |
| `planning.experience_queries_total/hits_total` | 经验检索次数/命中（仅 LLM 分解路径） | 同上 | 经验库积累效果 |
| `llm_error` / `llm` | LLM 调用失败率（TD-1） | Prometheus 原生 | 规划回退路径不抬升 LLM 错误率 |

> 【不易】`planning.plans.*`、`planning.cost_total` 等目前经 `BusinessMetricsCollector` 自管理字典记账，**尚未注册进 `BUSINESS_METRICS_DEFINITIONS`，不直接出现在 Prometheus `/metrics` 文本**。看板查询通道：
> 1. 应用侧接口/日志读取 `planning_metrics.get_metrics()`（推荐，零部署成本）；
> 2. 若需原生 Prometheus 可见，在 `agent/monitoring/business_metrics.py` 的 `BUSINESS_METRICS_DEFINITIONS` 补注册 `planning.plans.*` 等指标（另立小任务，不影响灰度本身）。
>
> 【2026-08-13 记账修复生效后】`planning.cost_total` **已真实计费**（`87856021`：executor `_execute_llm_reasoning` 补 `record_text(prompt/response)` 与 react.py 同口径 + `execute_plan` finally 统一回填 budget 快照）。灰度期间 **`cost_total` 应为非 0 且随流量线性增长**——修复前 Plan 路径成本恒 0（记账缺陷），若灰度后观察到恒 0，说明部署版本未含 `87856021` 或收尾快照未触发（见 §六排查）。

### 4.2 Grafana 面板 PromQL 查询

数据源：`yunshu-app`（抓取目标 `host.docker.internal:5678`）。

**Panel 1：规划流量与占比（折线/时间序列）**

```
# 规划引擎每分钟命中次数（应随灰度阶梯上升）

**Panel 2：规划成功/失败（按计划数，来自接口指标）**

```
# 成功后链路观测：成功率 = success / total（接口字段计算，非 PromQL）
planning.plans.success / planning.plans.total * 100
```

**Panel 3：规划成本（USD，累计）**

```
planning.cost_total
```

**Panel 4：LLM 错误率（回退护栏）**

```
sum(rate(yunshu_intent_layer_total{layer="llm_error"}[5m]))
  / sum(rate(yunshu_intent_layer_total{layer="llm"}[5m]))
```

### 4.3 告警规则建议（追加到 `deploy/monitoring/prometheus/planning_alerts.yml`）

```yaml
groups:
  - name: planning_alerts
    interval: 30s
    rules:
      # 规划命中突降 = 灰度/回滚动作异常（无请求时天然告警，先跑基线再启用）
      - alert: PlanningTrafficDrop
        expr: sum(rate(yunshu_intent_layer_total{layer="planning"}[10m])) < 0.1
        for: 30m
        labels: {severity: warning, category: planning, layer: traffic}
        annotations:
          summary: "规划引擎流量消失（10 分钟窗口 < 0.1 次/秒）"
          description: "灰度开启后规划命中消失。可能：PLANNING_ENABLED 未生效、进程未重启、orchestrator 判定未触发。"
      # 规划失败率异常（> 10%，护栏）
      - alert: PlanningFailureRateHigh
        expr: planning.plans.failed / planning.plans.total > 0.1
        for: 10m
        labels: {severity: warning, category: planning, layer: execution}
        annotations:
          summary: "规划执行失败率超过 10%"
          description: "超过阈值请检查逃生通道是否频繁回退（LLM 直答成功率应保持 100%）。"
```

## 五、灰度判定标准（达标门槛）

| 观察指标 | 阈值 | 说明 |
|---|---|---|
| 用例成功率（评测集 13 例） | = 100%（基线值） | 灰度前复跑 `scripts/eval_planning.py` 对照 |
| 单计划成本 | ≤ $0.01/用例（预演量级） | `planning.cost_total` 随流量线性，无异常突刺；**非 0 且线性**（`87856021` 修复后真实计费） |
| 规划平均耗时 | ≤ `timeout_seconds`（默认 30s） | 超时用例由逃生通道兜底，不应抬升用户感知延迟 |
| LLM 错误率 | 不高于灰度前 | 回退路径不引入新错误 |
| 用户可感知错误率 | 0 增长 | 看板 + 告警规则综合 |

## 六、常见问题

| 现象 | 排查 |
|---|---|
| `layer="planning"` 计数为 0 | ① 环境变量/config 是否生效（进程是否重启）；② 请求是否触发 `_needs_planning`（复杂任务才有，简单问候走模板/直答）；③ 显式 `planning_mode=True` 可强制验证 |
| 全量后偶发回退 | 属设计内逃生通道（超时/预算超限），观察 `planning.plans.failed` 与 LLM 直答成功率，确认不放大即可 |
| 成本指标不涨（恒 0） | 修复后应**非 0**（`87856021`）。若仍恒 0：① 部署版本未含记账修复（未重启/镜像未更新）；② 计划未走 `execute_plan` finally 快照回填（全部被逃生通道拦截或空计划）；③ 接口指标通道未接入（§4.1）；④ `token_price_per_1k` 缺失（默认 0.002 兜底，通常不是主因） |
