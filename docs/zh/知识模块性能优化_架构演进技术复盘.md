> 复盘范围：从第二批性能优化落地 → 流式方案设计 → 容量预估系列（12 份报告）→ 容量模型闭合的完整过程
> 日期：2026-08-08 ｜ 分支：develop / release/v1.2.0
> 关联：对比报告 / 变更说明 / 架构演进总结（Wiki）/ 架构委员会汇报摘要邮件

## 1. 背景与目标

知识模块（CardStore）入链判定原为全库扫描（每删除一次 O(N)），写入链路（create/update/delete/delete_many）与 index.md 维护均存在性能瓶颈。本阶段目标：

1. **落地第二批优化**：批量删除（2.2）、入链索引（2.1）、index.md 高频追加（2.3）；
2. **一致性先行**：TDD 锁定「增量叠加 == 全量重建」不变量；
3. **容错降级**：索引读失败回退全扫、写失败不阻断主操作；
4. **容量评估**：从实测锚点外推至极限，形成架构演进路线图。

---

## 2. 演进过程全景

```
第二批优化落地（查表 O(1)）
   → 流式扫描方案（内存 O(N)→O(U)）
   → 容量预估系列（50万 → 100万 → 200万 → 500万 → 1000万 → 2000万 → 5000万 → 1亿 → 10亿 → 100亿 → 1万亿 → 1京 → 1垓[系列总终结]）
   → 架构演进判定（流式 → 单机分片 → 分布式 → 集群化 → 区域级多集群 → 联邦式 → 去中心化[理论] → 系列终止）
```

每阶段均有**实测基准锚定**（3000 卡实测 + refs 合成实验），外推口径可追溯、可复核。

## 3. 关键决策与权衡（复盘要点）

### 3.1 入链索引：一致性不变量先行（TDD）

| 决策 | 内容 | 权衡 |
|---|---|---|
| 测试先行 | 7 项一致性测试先于实现（红）→ 实现后全绿 | 不变量锁定在代码之前，杜绝「实现自证」 |
| 增量 == 重建 | 「增量叠加 == 全量重建」为【不易】核心不变量 | 保证索引可随时用重建修复 |
| archives 不入表 | 与 find_orphans 语义对齐（纯 slug 入链） | 边界一致，无二义 |

### 3.2 容错降级机制（架构委员会关注点）

| 层 | 失败场景 | 降级行为 | 原则 |
|---|---|---|---|
| 读路径 | 索引缺失/损坏（非法 UTF-8） | 回退全库扫描 | **行为不退化**（判定正确性优先） |
| 写路径 | 索引登记/移除失败（磁盘故障/损坏） | warning + 不阻断卡片主操作 | **索引是可重建辅助文件**，主操作优先 |
| 验证 | 7 项降级单测 + 3 项 `--log-cli` 实证 | 告警文案逐条核对 | 测试真实触发，非空转 |

### 3.3 容量模型：外推方法论与边界

- **锚点**：3000 卡实测 5.6 MB（含 refs）、全扫 0.225 ms/卡、refs 12.8 MB/10 万卡；
- **模型**：线性外推 + 敏感性分析（引用密度/正文长度）+ 分片并行理想下界；
- **收敛点**：2^20 片后「继续加片」的边际收益被路由/对账成本吞没 → **分片不是万能解**；
- **边界**：工程现实极限 10^8–10^9，架构理论极限 10^12–10^14，1 京/1 垓为纯数学外推 → **模型闭合声明**。

### 3.4 分支策略与发布

- 全部提交 develop，容量报告逐份 cherry-pick 到 release/v1.2.0，两分支保持对齐；
- 教训：**提交前确认当前分支**（邮件+PDF 曾误落 release，已 soft-reset 转移至 develop）；
- 工作区存在其他任务未提交改动（agent/*.py），全程未触碰、未混入本次提交。

## 5. 经验教训（What went well / What went wrong）

### What went well

1. **TDD 一致性先行**：先锁定不变量再实现，杜绝「测试迁就实现」；
2. **降级铁律闭环**：读回退 + 写不阻断 + 实证单测，容错行为可审计；
3. **外推可追溯**：每份报告标注数据来源与口径，敏感性分析覆盖关键维度；
4. **每次变更独立提交 + 小步验证**：70+ 测试全绿才提交，可回滚。

### What went wrong / 待改进

1. **误提交分支**：未确认当前分支即 commit（邮件+PDF 落入 release），已 soft-reset 修正——**提交前检查 `git branch --show-current`**；
2. **外推系列未设止损点**：50 万外推逐步加码至 1 垓，过程消耗大量文档篇幅；虽最终以「模型闭合」收束，但**下次外推系列应在设计阶段设定上限**（如 ≤10^12）；
3. **图表为线性轴**：跨越 20 个数量级的数据用线性图表达不佳（1 京/1 垓处曲线贴底），应早期切换对数轴；
4. **容量监控阈值未落地代码**：refs > 512 MB 阈值目前停留在文档层面，需在 `_has_incoming_links`/`rebuild_links_index` 加监控埋点。
