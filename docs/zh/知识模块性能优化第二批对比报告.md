## 3. 各优化项对比明细

### 3.1 2.1 入链判定（本轮最大单项收益）

`_has_incoming_links` 由「每次全库扫描解析 + 遍历 links」改为「查 `index_links.md`」：

| 判定方式 | 耗时（1 万卡） |
|---|---|
| 全扫回退（优化前） | 2249.3 ms |
| 查表（优化后） | 1.07 ms |
| **加速** | **≈2094x** |

> 收益直接作用于 `delete` / `archive` / 断链检测等每次判定。查询成本已从 O(N) 降到接近 O(1)（索引文件解析，随库线性但远低于全扫）。

### 3.2 2.2 批量删除 `delete_many`

| 场景 | `delete_many(50)` 修复前 | `delete_many(50)` 修复后 | 50 次 `delete` | 提升 |
|---|---|---|---|---|
| 索引缺失（回退全扫） | 2235.1 ms | 2716.9 ms | 106689.3 ms | **≈47.7x** |
| 索引存在（查表） | 2342.9 ms | **134.1 ms** | 173.5 ms | **≈17.5x** |

- 索引缺失回退场景：`delete_many` 一次全扫构建入链映射 + O(K) 删除，vs 逐次 delete 每次 O(N) 全扫，**数量级提升**。
- 索引存在场景（修复后）：`delete_many` 优先**一次解析入链索引**（O(M)）构建入链映射，比逐次 delete（每次各解析一次索引）更快；修复前该场景每次 `self.list()` 全扫，反而慢 13.5x（详见 §4）。

### 3.3 2.3 index.md 高频追加

| 写入方式 | 耗时（1 万行 index） |
|---|---|
| 序插 `append=False` | 4.9 ms |
| 追加 `append=True` | 4.8 ms |

- 单次写加速 ≈1.0x：两种模式均需 `_atomic_write` 全文件读改写（O(index) 文件 I/O 为主成本），定位差异（1 万行字符串比较 vs 直接定位 section 末尾）相对文件 I/O 可忽略。
- **真实价值**：CPU 定位成本从 O(index) 降到 O(1)，高频路径（create/update 每次触发）不再逐行比较排序；配合定期 `rebuild_index` 重整收敛（不变式见变更说明 §4），在 index 行数继续增长（如 10 万行）或定位比较成为瓶颈时差异将显性化。
- 诚实结论：本轮 2.3 的收益是**定位复杂度降阶 + 不变式重构**，而非单次写耗时数量级下降；其意义在于解除「每次写都扫描 index」的持续成本。

## 4. 基准发现与修复（delete_many 复用入链索引）

**问题（基准暴露）**：初版 `delete_many` 未复用入链索引，索引存在场景每次 `self.list()` 全扫（O(N)，3000 卡 ≈2.3 s），比逐次 `delete` 查表慢 13.5x，违背实施方案 §0「2.1 的索引表复用于 2.2 的入链判定」依赖设计。

**修复（本轮已落地）**：`delete_many` 优先 `read_links_index` **一次**解析入链索引构建 `incoming`（O(M)），索引缺失/解析失败时回退全库扫描（降级铁律，与 `_has_incoming_links` 一致）。集合内互引放行判定语义不变（`refs = [r for r in table.get(slug, []) if r not in pending]`）。

**复验数据（3000 卡，删 50 张）**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 索引存在 | 2342.9 ms | **134.1 ms（17.5x）** |
| 索引缺失回退 | 2235.1 ms | 2716.9 ms（全扫波动，数量级不变） |

回归：新增 `test_delete_many_index_missing_fallback`（索引缺失回退语义与索引存在时一致），完整回归 **367 passed**。
