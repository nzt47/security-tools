## 2. 2000 万节点分片策略

### 2.1 片数权衡

| 片数 | 单片 refs 驻留 | 并行全扫（理想） | 文件数 | 元数据/合并开销 | 判定 |
|---|---|---|---|---|---|
| 16 | ≈160 MB | ≈4.7 分钟 | 16+ | 低 | 偏少，单片内存仍高 |
| **64** | **≈40 MB** | **≈1.2 分钟** | 64+ | 中 | **推荐** |
| 256 | ≈10 MB | ≈18.75 秒 | 256+ | 高（小片 IO、合并成本） | 过度分片 |

**推荐 64 片**（1000 万–2000 万规模带）：单片 40 MB 回到常态内存区间，并行全扫理想 ≈1.2 分钟，文件数可控（每片 = 哈希桶文件 + 可选备份）。

### 2.2 分片路由设计（示意）

```
ref_slug_hash = hash(ref_slug) % 64
shard_file = index_links/<shard_id>.md
```

- 增量写：add/remove 只触达 `ref_slug` 对应单片（写成本 ∝ 1/64）；
- 全量重建：每片独立扫描聚合 → 并行（进程/线程池）→ 结果合并；
- 读侧查表：`_has_incoming_links(slug)` 需读全部 64 片合并（内存 ≈40 MB），或在单片内再按目标前缀索引（二级索引）降读成本。

### 2.3 降级逻辑在分片下的映射（本报告基于已验证的降级机制）

| 现有降级机制 | 单机（现状） | 分片后 |
|---|---|---|
| 索引缺失/损坏 → 回退全扫 | 全库 75 分钟 | **只回退该片**（秒级） |
| 写失败 → 不阻断卡片主操作 | warning 降级 | 不变（片级隔离后影响面更小） |
| 污染行检测 → warning | 全文件扫描 | 逐片检测，定位到片 |
| 回退/重建耗时 | 同步阻塞 75 分钟 | 后台化 + 并行（≈1.2 分钟） |

一致性不变量改写：「各片增量叠加 == 对应片全量重建」（原「全局增量 == 全局重建」分解到片级，逐片可验证）。

## 5. 结论与建议

| 决策维度 | 2000 万节点评估 |
|---|---|
| 内存（现状） | ≈37.2 GB：完全不可行 |
| 内存（流式单机） | ≈2.5 GB：越过单机合理水位 |
| 内存（分片 64 片） | ≈40 MB/片：回到常态区间 |
| 耗时（全扫） | 流式 75 分钟 vs 分片并行理想 1.2 分钟 |
| 架构判定 | **分片架构执行线（64 片推荐）** |

**建议**：

1. **64 片分片为 2000 万规模推荐基线**：单片 40 MB、并行全扫 1.2 分钟、文件数可控；256 片过度分片收益不再显著（合并/IO 成本上升）。
2. **降级机制分片化改造**：现有「索引缺失回退全扫、写失败不阻断、污染检测」三件套在分片下天然收敛——回退影响面从全库缩至单片，改造重点是路由层与片级一致性校验。
3. **一致性验证自动化**：将现有「增量叠加 == 全量重建」不变量测试按片改写（`test_delta_accumulation_matches_rebuild` 等 9 项 links_index 测试为分片版基线）。
4. **监控阈值**：refs 总量 > 512 MB（≈400 万卡）启动分片评估；> 1 GB（≈800 万卡）必须分片。
