## 一、背景与目标

并发安全系列已规范锁纪律（持锁禁 I/O/回调、锁内仅内存状态变更、RetryPolicy 统一重试），
agent 代码 25+ 处锁纪律注释（api_gateway / multi_tenant / knowledge/search / workflow_learning/matcher /
llm_response_cache / holographic_adapter / markdown_syncer 等），但存在三处机制化缺口：

| 缺口 | 现状 | 目标 |
|---|---|---|
| 无量化数据 | 无锁等待/持锁时长采样，无法回答"哪把锁是瓶颈" | B1：产出锁竞争热点报告，明确 Top 3 锁 |
| 违规运行时不可见 | 锁纪律违规（持锁超时/死锁）只能等崩溃暴露 | C2：运行时锁看门狗，持锁超时接入 Prometheus 告警 |
| 新代码可能回潮 | 锁纪律靠人工 review，无 CI 拦截 | C3：锁纪律静态扫描，新代码进库即拦截 |

## 二、B1 锁竞争热点分析

### 2.1 采样机制（零开销默认关闭）

**新增 `agent/monitoring/lock_profiler.py`**：

```python
class SampledLock:
    """LOCK_PROFILE=1 时替换 threading.Lock/RLock 的采样包装

    采集: lock_name / wait_count / wait_total_ms / hold_total_ms / max_hold_ms / contended_count
    语义: wait 从 acquire 进入(阻塞)到获得锁; hold 从获得锁到 release
    开销: 默认关闭(环境变量未设置时 threading.Lock 原样), 开启后每 acquire/release 仅 2 次时间戳
    """
```

- 启用方式：`LOCK_PROFILE=1` + `LOCK_PROFILE_LOG=<path>.jsonl`（模块导入时 patch `threading.Lock/RLock`）
- 记录格式：JSONL 每行 `{lock_name, thread_id, ts, wait_us, hold_us}`
- 采样场景（复用并发安全 6 并发测试 + 热点业务）：
  1. `tests/unit/test_permission_system_concurrency.py`（30 线程）
  2. `tests/unit/test_task_scheduler.py` 并发块
  3. 热点模块高并发脚本：api_gateway 配额、multi_tenant、knowledge/search 检索、workflow_learning/matcher、llm_response_cache、holographic_adapter

### 2.2 报告生成器

**新增 `scripts/analyze_lock_hotspots.py --log <jsonl> [--top N=10] [--out report.md|json]`**：

- 聚合：按 `lock_name` 分组 → `wait_total_ms` 降序 → `wait_count` / `avg_wait_ms` / `hold_total_ms` / `max_hold_ms`
- 输出 Markdown 报告：
  ```
  | rank | lock_name | wait_count | wait_total_ms | avg_wait | max_hold_ms | 建议 |
  | Top 3 锁 | ... | 建议手段(读锁/分段锁/无锁化/I/O 移出) |
  ```

### 2.3 优化落地（P1 方案 B2 表，按报告选择）

| 手段 | 适用场景 | 先例 |
|---|---|---|
| 读写锁（RLock/RWLock） | 读多写少全局状态 | `routes_logging._ALERT_RULES_CACHE` |
| 分段锁（shard locks） | 单一全局锁串行化热路径 | `lock_free_ring_buffer` |
| 无锁化（CAS/队列） | 计数器/状态标志 | perf_monitor `_CountingFilter` |
| I/O 移出锁外 | 存储/日志路径 | storage/replay_storage 已异步化 |

### 2.4 验收

1. `scripts/analyze_lock_hotspots.py` 对采样日志产出报告（明确 Top 3 锁）✅
2. Top 锁优化后：`wait_total_ms` 相对基线降低 ≥50%（以首次采样为基线）✅
3. 采样/分析脚本与生产路径零耦合（LOCK_PROFILE 未设置时零开销）✅

## 三、C2 运行时锁看门狗

### 3.1 核心实现

**新增 `agent/monitoring/lock_watchdog.py`**：

- `LockWatchdog` 单例（默认关闭，`LOCK_WATCHDOG_ENABLED=1` 开启）：
  - 持锁超时：包装 acquire/release，`hold_time > LOCK_WATCHDOG_HOLD_MS(默认 2000)` → 记违规（含调用栈、锁名、线程）
  - 锁等待超时：`wait_time > LOCK_WATCHDOG_WAIT_MS(默认 5000)` → 记潜在死锁/饥饿告警
  - 守护线程 30s 周期扫描持锁线程表，兜底检测"异常长时间持锁"（即使 release 路径被绕过）
- 零开销：未启用时包装直通（函数指针替换，无分支热路径开销）

### 3.2 Prometheus 接入

- 指标注册进 `agent/monitoring/business_metrics.py` 的 `BUSINESS_METRICS_DEFINITIONS`（对齐 planning 指标注册先例）：
  - `lock_hold_timeouts_total`（counter，持锁超时次数）
  - `lock_wait_timeouts_total`（counter，锁等待超时次数）
  - `lock_hold_duration_ms`（histogram，持锁时长分布）
- 告警规则追加 `deploy/monitoring/prometheus/lock_watchdog_alerts.yml`：
  ```yaml
  - alert: LockHoldTimeout
    expr: increase(lock_hold_timeouts_total[10m]) > 0
    for: 5m
    labels: {severity: critical, category: concurrency}
  - alert: LockWaitTimeout
    expr: increase(lock_wait_timeouts_total[10m]) > 0
    for: 5m
    labels: {severity: warning, category: concurrency}
  ```

### 3.3 配置（.env，全部带默认值）

```
LOCK_WATCHDOG_ENABLED=0        # 默认关闭（生产零开销）
LOCK_WATCHDOG_HOLD_MS=2000     # 持锁超时阈值
LOCK_WATCHDOG_WAIT_MS=5000     # 锁等待超时阈值
```

### 3.4 验收

1. `tests/unit/test_lock_watchdog.py`：持锁 3s 触发 hold 告警、正常持锁不误报、wait 超时触发、指标注册可查、未启用零开销（基准对比）✅
2. 手工验证：`LOCK_WATCHDOG_ENABLED=1` 下故意持锁 3s → `/metrics` 出现 `lock_hold_timeouts_total` 增量 ✅

## 四、C3 锁纪律静态扫描 CI

### 4.1 扫描器

**新增 `packages/lock_scanner/`**（纯 Python ast 扫描，无重型依赖，直接 setup-python 运行，无需 Docker 镜像）：

- 规则 1（HIGH，阻断）：`with lock:` / `lock.acquire()` 代码块内出现 I/O 或外部调用：
  `open(` `write(` `read(` `socket` `requests.` `urllib` `subprocess` `os.system` `os.remove` `os.rename` `logging` `logger.` `print(` `sleep(` `time.sleep` `input(` `join(` `queue.get(timeout` 等
- 规则 2（MEDIUM，提醒）：锁内调用非 `# lock-safe` 标注的外部函数（启发式：非内建、非本项目内存操作函数的调用）
- 豁免机制：行注释 `# lock-safe` 显式声明（白名单，审计留痕）
- 报告：JSON + 控制台 `::error::`/`::warning::`（对齐 kwarg-scanner 输出约定）

### 4.2 CI 接入

**新增 `.github/workflows/lock-discipline-scan.yml`**（沿用 kwarg-docker-scan 模式）：

```yaml
name: 锁纪律静态扫描
on: [push, pull_request]   # 分支: master/main/develop/release/**
jobs:
  high-risk-scan:    # HIGH 阻断（新代码含锁内 I/O → CI 失败）
  medium-risk-scan:  # MEDIUM 提醒（不阻断）
```

- 基线机制（对齐 `.guard_baseline.json` 先例）：首跑对现有 25+ 处锁纪律注释代码生成 `baseline.json`（允许现有模式），仅**新增**违规阻断——避免历史存量阻塞流水线
- 可选：pre-commit local hook（提交前本地拦截，防进库才暴露）

### 4.3 验收

1. 注入锁内 `open()` 样例 → CI HIGH 阻断 ✅
2. 合法代码（锁内仅内存 dict/list 变更、含 `# lock-safe` 标注）→ 通过 ✅
3. baseline 机制：存量锁纪律代码不产生新告警，新增违规必拦截 ✅
