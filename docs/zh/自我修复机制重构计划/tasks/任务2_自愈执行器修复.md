# 任务 2：自愈执行器修复（验证真实化 + 动作补全 + 危险动作保护）

> 所属阶段：阶段二（恢复层修复） ｜ 依赖：任务 1（健康评估真实化） ｜ 工作量：中
> 对应设计文档章节：第二层「即时恢复策略」+ 第五层「安全护栏」
> 关联缺陷：D7、D9、D11、M4 ｜ 关联既有代码：`agent/monitoring/self_healer.py`、`agent/monitoring/alert_manager.py`

---

## 一、目标描述

修复自愈执行器的三个"假成功/半成品"问题，让自愈闭环的"执行→验证"名副其实：

1. **验证真实化（修 D7）**：`verify_heal()` 不再依赖无参 `assess()`（已由任务 1 修复为返回 None），改为读取真实健康分，并支持按动作类型定义验证指标（如重启后进程存活 + 健康分回升）；
2. **动作补全（修 D9）**：`restart_service` 在 Windows 下不再"假成功"——未验证到进程重启/端口恢复一律 FAILED；补全 `restart_component` 动作（进程内模块热重启）；
3. **危险动作保护（守安全红线）**：`clear_cache` 默认不再允许 `*` 全清，纳入白名单 + 冷却 + 频率三重校验；删除 `~/.cache` 等越权路径；
4. **恢复路径规范化（修 D11）**：`recover_circuit_breaker` 改为调用公开 API（`force_close`/`reset`），禁止直改私有字段；
5. **恢复动作映射表（补 M4）**：建立"故障域 → 恢复动作"配置映射（LLM 超时 → 重试/降级；工具失败 → 熔断恢复；记忆故障 → 重索引等）。

**【不易】约束**：`execute_action`/`verify_heal`/`get_records`/`get_stats` 公开方法签名不变；`HealAction` 枚举值不全删，未实现的动作返回 `SKIPPED`（原因明确）而非 `FAILED`。

## 二、执行步骤

### 步骤 1：验证机制真实化

修改 `agent/monitoring/self_healer.py` 的 `verify_heal`：

- 增加 `verify_action(action) -> bool` 内部分发，按动作定义验证器：
  - `restart_service`：验证进程 PID 变更 或 目标端口恢复可连接（端口列表从 context 传入）；
  - `clear_cache`：验证缓存目录大小下降且主流程无异常；
  - `recover_circuit_breaker`：验证目标熔断器状态已非 OPEN（读公开 `get_status()`）；
  - `gc_collect`/`clear_memory`：验证 RSS 下降 > 阈值（默认 1MB）或对象数下降；
- 验证数据源统一走 `agent.health.assessor` 的最新持久化评分（任务 1 产物），评分 `None` 或低于阈值（默认 0.7）时验证失败；
- 轮询间隔与超时走既有 `_verify_timeout` 配置，超时返回 `(False, 原因)`。

### 步骤 2：修复 restart_service

- Windows 分支：不再直接 `Restart-Service 'yunshu'`（大概率无此服务），改为：
  1. 通过 context 传入重启方式（`restart_command`）；未传且无可用服务管理工具时返回 `SKIPPED("未提供可执行的重启方式")`；
  2. 执行后必须经步骤 1 的验证器确认，验证失败返回 `FAILED` 并携带证据；
- Linux 分支保持 systemctl/service 探测，但同样以验证结果为准。

### 步骤 3：危险动作保护（clear_cache / clear_memory）

- 新增 `_cache_whitelist` 配置（默认只允许显式列出的缓存路径，空列表 = 禁用通配清理）；
- `clear_cache` 校验：路径必须在白名单内，且 pattern 非 `*`；越权路径返回 `SKIPPED("路径不在白名单")`；
- `clear_memory` 中 Linux 的 `/proc/sys/vm/drop_caches` 写入默认禁用（配置开启才允许），Windows 分支保持纯 GC。

### 步骤 4：恢复熔断器规范化

- `_recover_circuit_breaker` 改为：
  1. 通过 `get_all_circuit_breaker_status()` 定位 OPEN 的熔断器；
  2. 调用公开 API `register_circuit_breaker(name).reset()`（或 `force_close()`）恢复；
  3. 记录恢复前/后状态到日志与自愈记录；
- 若目标是任务 3 合并后的统一熔断体系，则调用其统一接口（任务 3 与 2 可并行，本任务先实现"走公开 API"原则即可）。

### 步骤 5：恢复动作映射表

- 新建 `agent/self_healing/policy.py`（或复用 `agent/health` 配置），声明式配置：

```yaml
self_healing:
  restore_map:
    llm_timeout:            # 故障域
      detect: error_handler.category == NETWORK_TIMEOUT
      actions: [retry_limited, degrade_llm_router]
    tool_failure:
      detect: error_handler.category == EXTERNAL_API
      actions: [recover_circuit_breaker, clear_cache]
    memory_failure:
      detect: module == memory && error_rate >= 0.4
      actions: [rebuild_index]   # 预留，未实现则 SKIPPED
    decision_loop:
      detect: state_hash_repeat >= 3   # 任务 5 提供检测信号
      actions: [terminate_loop]
```

- 每个动作映射到 `execute_action` 或明确标注"未实现 → SKIPPED + 原因"；
- `alert_manager._check_heal_action` 默认动作从写死的 `["restart_service"]` 改为读取该映射表。

### 步骤 6：测试

- 单元测试：verify_heal 对"假健康分 None"返回失败；restart_service 无重启方式返回 SKIPPED；clear_cache 越权路径被拒；recover_circuit_breaker 走公开 API（mock breaker）；
- 集成测试：mock alert 触发 → 动作执行 → 验证失败的完整链路日志可读。

## 三、预期成果

1. `verify_heal` 基于真实健康分与动作专属验证器，不再假成功；
2. `restart_service`/`clear_cache`/`clear_memory` 均具备明确的失败/跳过语义与安全校验；
3. `recover_circuit_breaker` 通过公开 API 操作熔断器；
4. `agent/self_healing/policy.py` 恢复动作映射表 + alert 接线；
5. 全部测试通过，旧测试中"验证永远成功"的用例被改写为真实断言。
