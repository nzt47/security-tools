# 任务 6：轻量自我进化机制（失败案例回流 + 修复策略库 + 参数联动）

> 所属阶段：阶段四（进化与运营） ｜ 依赖：任务 1（健康评估）+ 任务 4（失败反思） ｜ 工作量：高
> 对应设计文档章节：第四层「从失败中自我进化（FATE 框架）」——**裁剪替代版**
> 关联缺陷：D1（FATE 不可落地）、M2 ｜ 关联既有代码：`agent/quality/defect_tracker.py`、`agent/auto_tuner.py`、`agent/feedback.py`、`planning/reflector.py`

---

## 一、目标描述

将设计文档的 FATE（监督微调 + 强化学习）裁剪为云枢可落地的**提示词/策略级进化闭环**：

```
失败发生 → 结构化失败案例（四维评分）→ 修复策略库（候选生成+筛选）
    → 运行时注入（提示词/参数/路由）→ 新一轮验证 → 策略权重更新
```

1. **失败案例结构化（替代 FATE 打分）**：按云枢四个维度对失败案例评分——**安全性、实用性、过度拒绝、轨迹效率**（对应 FATE 四维，但用规则+LLM 评估而非训练）；
2. **修复策略库（替代"8 候选生成 + 帕累托筛选"）**：失败案例 → 生成候选修复策略 → 按"安全优先 + 综合分"筛选出 1-3 条入库，带使用计数与成功率；
3. **运行时注入**：ReAct 思考、Critic 提示词、工具路由选择时查询策略库，命中则注入（对应 FATE"策略更新"的提示词层实现）；
4. **参数联动**：与 `auto_tuner` 打通——策略库统计可作为自动调参的输入信号（如某工具失败率高 → 建议降低并发/调整超时）。

**【不易】约束**：**禁止任何形式的模型微调/训练管线**（违【简易】）；策略库只追加不删除（可标记 `deprecated`）；注入的策略必须可追溯（携带策略 ID 入日志与 trace）。

## 二、执行步骤

### 步骤 1：失败案例模型与采集

在 `agent/quality/defect_tracker.py` 基础上扩展（或新建 `agent/evolution/` 包）：

```python
@dataclass
class FailureCase:
    case_id: str
    task_type: str
    trace_id: str
    failure_type: str            # error_handler 分类
    diagnosis: dict              # 任务 4 的 FailureDiagnosis 摘要
    scores: dict                 # {"safety": 0-1, "utility": 0-1,
                                 #  "over_rejection": 0-1, "trajectory_efficiency": 0-1}
    candidate_strategies: list   # 修复策略候选
    selected_strategies: list    # 筛选后入库的策略 ID
    created_at: float
```

- 采集点：任务 4 的失败反思出口 + `defect_tracker` 既有记录 + `feedback.py` 负面反馈；
- 四维评分：safety 由操作是否触达危险域规则判定；utility 由任务是否最终完成；over_rejection 由失败原因是否"过度拒绝"（如权限误判）；trajectory_efficiency 由步数/重试次数统计；LLM 可参与语义部分，规则保证下限。

### 步骤 2：候选生成与筛选

- 候选生成：对每个失败案例，从三类来源生成修复候选——a) 任务 4 的 `repair_hints`；b) 策略库相似案例复用；c) 可选 LLM 生成（`evolution_llm_generate: true` 配置开关，默认开、可关）；
- 筛选：先淘汰 safety < 0.6 的候选（安全红线），再按综合分 `0.4*safety + 0.3*utility + 0.2*trajectory + 0.1*(1-over_rejection)` 排序取 top3（近似帕累托：不引入帕累托前沿算法，保持【简易】）；
- 入库策略结构：`{strategy_id, case_id, prompt_patch, param_patch, scope(global/task_type/tool), success_count, attempt_count, status}`。

### 步骤 3：运行时注入

- 新增 `agent/evolution/injector.py`，提供 `get_strategies(scope_key) -> list` 与 `record_strategy_result(strategy_id, success)`；
- 接线点（三个，均由配置开关控制，默认开启）：
  1. `ReActLoop._think`：按 task_type 查询策略，命中则拼入"历史经验"段落（与 reflector 经验并列，注明 `[策略 #id]`）；
  2. `CriticEvaluator.evaluate`：提示词注入相关策略（如"避免过度拒绝"类策略）；
  3. 工具路由（`tool_router.py`）：某工具失败率高的策略建议切换备用路径时，路由层执行；
- 所有注入在 trace/log 中携带 `strategy_id`，保证可追溯与回滚（策略可一键全局 disable）。

### 步骤 4：策略统计与参数联动

- `injector` 维护 `success_count/attempt_count`，定期（每日）更新策略 `status`（成功率 < 30% 且次数 ≥ 5 自动 `deprecated`）；
- 联动 `auto_tuner`：新增信号源 `get_strategy_stats()`，`auto_tuner` 生成建议时可将高失败率策略关联到参数建议（如某工具策略失败率高 → 建议 `tool_max_concurrency` 下调），走既有 HITL 审批流程；
- 产出周报（复用 auto_tuner 报告机制）：本周失败案例数、策略命中数、策略成功率、deprecated 数。

### 步骤 5：测试

- 单元测试：四维评分规则路径正确；筛选安全红线生效（safety<0.6 必淘汰）；`record_strategy_result` 更新统计；
- 集成测试：注入器命中策略时 prompt 含 `[策略 #id]`；策略 deprecated 判定逻辑；与 auto_tuner 信号源打通（mock 数据）；
- 安全测试：策略注入内容有长度上限与敏感词过滤，防止策略库自身被投毒。
