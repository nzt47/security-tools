# 任务 4：失败路径反思闭环（Reflexion on Failure + 结构化诊断）

> 所属阶段：阶段三（认知层补强） ｜ 依赖：无 ｜ 工作量：高
> 对应设计文档章节：第三层「语义级自我修正（ReAct + Reflexion）」+ 反思循环 Prompt 工程
> 关联缺陷：D6、D12、M3 ｜ 关联既有代码：`planning/react.py`、`planning/reflector.py`、`agent/error_handler.py`

---

## 一、目标描述

让"反思"真正触达失败——这是设计文档最核心的主张"从错误中学习"的落地点：

1. **失败触发反思（修 D12）**：`ReActLoop` 中行动失败时不再跳过反思，进入专门失败反思分支：根因分析 → 动作重构建议 → 注入下一轮；
2. **结构化诊断注入**：将工具/LLM 失败输出转化为结构化诊断报告（错误类型/分类/上下文/历史修复记录），而非把原始报错丢给 LLM（采纳文档"诊断引擎"思想）；
3. **修复历史注入**：第 2 轮起注入"此前尝试过什么、为何未成功"，强制换思路（修 D6 的一半：配合任务 5 的状态哈希做终止保障）；
4. **失败经验沉淀**：失败反思结果进入 reflector 的 `lessons_db`，供后续任务与 `get_advice_for_task` 复用。

**【不易】约束**：`ReActLoop.run` 的公开行为不变（成功路径不因本任务改变）；`Reflector` 既有方法签名不变；反思为 LLM 可用时增强、不可用时规则兜底，禁止反思本身阻断主循环。

---

## 二、执行步骤

### 步骤 1：失败反思触发点

修改 `planning/react.py`：

- 在行动失败分支（当前 `if self.reflector and action_result.success:` 处）新增 `else` 分支调用 `failure_reflect`；
- 失败反思在 `max_iterations` 兜底之外增加**独立反思轮数上限**（配置 `reflection_retries`，默认 2），防止反思自身循环放大成本（对应 D6 收敛保证）；
- 反思结果 `adjustments` 注入下一轮思考的 context（复用现有 `next_hint` 机制，保持最小改动）。

### 步骤 2：结构化诊断生成

新建 `planning/diagnostics.py`：

```python
@dataclass
class FailureDiagnosis:
    error_type: str          # 由 error_handler.ErrorCategory 映射
    error_message: str       # 截断至 300 字符
    tool_name: str | None
    attempt: int             # 第几次尝试
    history: list[dict]      # 前几轮失败摘要（action + 错误 + 猜测根因）
    project_context: dict    # 可用工具/配置摘要（裁剪至 token 预算）
    repair_hints: list[str]  # 按 error_type 映射的约束/建议（表格驱动）
```

- `build_diagnosis(action_result, attempts, history) -> FailureDiagnosis`：从 `ActionResult.error` 解析错误类型（复用 `error_handler.YunshuError.category` 或字符串特征匹配）；
- 修复提示表（参照文档"错误类型 → 注入的约束"思想，映射到云枢场景）：

| error_type | 注入的修复约束 |
|-----------|----------------|
| network_timeout | 建议重试/换备用路径，禁止无限重试 |
| permission_denied | 检查权限声明与工具白名单，勿重复尝试 |
| external_api | 校验参数/凭证，勿原样重发 |
| tool_not_found | 校验工具名与注册表，勿虚构工具 |

### 步骤 3：失败反思 Prompt 与解析

在 `planning/reflector.py` 新增：

- `FAILURE_REFLECTION_PROMPT`：输入 = 原始任务 + 失败动作 + 结构化诊断报告 + 修复历史；输出 JSON = `{"root_cause": str, "confidence": float, "repair_actions": [str], "avoid": [str]}`；
- `async failure_reflect(task, result, diagnosis, attempts) -> FailureDiagnosis | None`：LLM 可用则调用解析，不可用则走规则兜底（基于 `repair_hints` 表 + 历史重复检测）；
- 失败反思结果写入 `lessons_db`（复用 `learn_from_experience` 的失败分支，确保持久化）；
- 历史记录：`reflection_history` 增加 `type="failure"` 条目，携带 diagnosis 摘要。

### 步骤 4：注入与收敛

- `ReActLoop._think` 组装 prompt 时，若存在 failure diagnosis，拼入"上次失败诊断 + 修复历史"段落（增量传递，不重传全量历史，省 token——文档要点 5）；
- 第 2 次失败时在 prompt 中显式声明"前 N 次修复尝试及失败原因"，强制 LLM 换思路；
- 反思轮数超限或 LLM 连续 2 轮输出相同 `root_cause` 时终止反思并升级（提示调用方降级/人工），对应文档"仍失败→降级→人工兜底"。

### 步骤 5：测试

- 单元测试：`build_diagnosis` 错误类型映射正确；失败反思 LLM 故障时走规则兜底且不抛异常；修复历史注入内容包含前轮失败摘要；
- 集成测试：mock reflector 返回修复建议，验证下一轮 context 含该建议；失败 3 轮后反思终止路径触发；
- 回归测试：既有 ReAct/Reflector 测试零回归。
