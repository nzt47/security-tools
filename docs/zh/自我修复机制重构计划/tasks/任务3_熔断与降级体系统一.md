# 任务 3：熔断与降级体系统一（单熔断 + 降级诚实化 + 恢复路径规范）

> 所属阶段：阶段二（恢复层修复） ｜ 依赖：无（可与任务 2 并行） ｜ 工作量：中
> 对应设计文档章节：第二层「即时恢复策略」（重试/降级/备用路由）
> 关联缺陷：D8、D10、D11、M6 ｜ 关联既有代码：`agent/error_handler.py`、`agent/circuit_breaker.py`、`agent/graceful_degrade.py`

---

## 一、目标描述

消除"两套熔断体系并存 + 降级伪造成功"两大问题，建立单一、诚实、可观测的即时恢复层：

1. **双熔断统一（修 D10）**：`error_handler.py` 内部的熔断注册表与 `circuit_breaker.py` 全局注册表合并为单一事实源，状态互相同步；
2. **降级诚实化（修 D8）**：`graceful_degrade` 的模块降级方法不再伪造成功——降级路径返回的结果必须携带 `degraded=True` 标记且**不计入 success 指标**；
3. **恢复路径规范（修 D11）**：所有熔断恢复统一走公开 API，禁止私有字段直改；
4. **降级收益可量化（补 M6）**：降级埋点补充"挽回损失"口径（如跳过评估节省的调用次数/延迟），支撑降级策略有效性评估。

**【不易】约束**：`GracefulDegrade`/`CircuitBreaker`/`error_handler` 全部公开 API 签名不变（仅内部实现与新增接口）；`DegradeModule` 枚举值不删；向后兼容别名（`RETRY`/`RELAXED`/`FALLBACK`/`DISABLED`）保留。

---

## 二、执行步骤

### 步骤 1：熔断统一（单一事实源）

- 分析 `error_handler.py` 中 `_circuit_breakers` 的写入点与读取点（`get_circuit_breaker_status` 等）；
- 方案：将 error_handler 的熔断器改为**委托** `circuit_breaker.py` 的 `get_circuit_breaker(name)` 注册表：
  - error_handler 内保留兼容字段与方法，内部调用委托函数；
  - 状态查询（`get_circuit_breaker_status`）改为读 `get_all_circuit_breaker_status()`；
  - 提供 `migrate_breakers()` 一次性迁移：把 error_handler 已有的 OPEN 状态迁移进统一注册表（测试环境用，避免生产状态丢失）；
- 运行 `tests/contract/` 契约测试确认 error_handler 既有调用方零破坏。

### 步骤 2：降级诚实化

修改 `agent/graceful_degrade.py`：

- `critic_evaluate_with_degrade`：删除硬编码 `overall_score=7`；降级时返回 `{"degraded": True, "reason": "Critic 服务不可用...", "overall_score": None}`，且**不调用 `_record_module_result(module, success=True)`**（降级不是成功）；
- `memory_query_with_degrade`：降级返回 `[]` 时仍标记 degraded，不计 success；
- `schema_validate_with_degrade`：对 dict 直接 `valid=True` 改为真正调用可注入的验证器；验证器缺失时返回 `valid=False + degraded=True`；
- 新增 `_record_degrade` 统计口径：`degraded_fallbacks_used`（实际用到 fallback 的次数）与 `degraded_calls_avoided`（短路避免的调用数），区分"降级决定"与"降级真发生"；
- 所有降级返回对象统一带 `degraded: bool` 字段（保持 `default_fallbacks` 兼容）。

### 步骤 3：恢复路径统一

- 检索全库 `_state = "half_open"` / `\._state\s*=` 等私有字段直改点，全部替换为公开 API：
  - 半开试探：`register_circuit_breaker(name)` 后由冷却期自然转半开，或调用新增的 `force_half_open(name)`（在 `circuit_breaker.py` 新增，经锁保护）；
- `self_healer._recover_circuit_breaker` 与任务 2 保持同一原则，此处从体系层兜底保证无第二套状态。

### 步骤 4：降级收益可观测

- `_log_action` 的 degrade 事件增加字段：`avoided_calls`、`saved_latency_ms`（fallback 相对主路径的耗时差）、`fallback_type`（cache/stub/default）；
- `get_status()`/`get_metrics()` 输出上述统计，供 Dashboard 展示"降级经济性"。

### 步骤 5：测试

- 单元测试：降级路径返回带 `degraded=True` 且不计 success（断言 `_module_states` 计数）；熔断委托后两套查询结果一致；`force_half_open` 状态转换正确；
- 契约测试：`tests/contract/` 新增"error_handler 熔断与 circuit_breaker 全局注册表同源"用例；
- 回归测试：既有 255+ 测试（尤其 graceful_degrade/circuit_breaker/error_handler 相关）零回归。

## 三、预期成果

1. 全库仅一套熔断状态源，`get_circuit_breaker_status()` 与 `get_all_circuit_breaker_status()` 返回一致；
2. 降级动作诚实：无伪造 SUCCESS，`degraded` 标记贯穿降级返回对象，指标不被污染；
3. 无私有字段直改残留（grep 校验通过）；
4. 降级埋点含 `avoided_calls`/`saved_latency_ms` 收益字段；
5. 契约测试新增并通过，全量回归零失败。
