## 一、背景

设计文档的核心主张是"从错误中学习"，但原实现存在两个断点：

1. **T2（自愈层）**：`verify_heal` 调 `assess()` 无参返回默认满分 1.0 → 验证永远通过（D7）；`restart_service` 无命令时仍返回 SUCCESS（D9）；`clear_cache` 无白名单可任意清除（D9）；`recover_circuit_breaker` 直改私有字段 `._state`（D11）；恢复动作分散无映射表（M4）。
2. **T4（认知层）**：`ReActLoop` 中反思只在 `action_result.success` 时触发（D12）→ 失败路径完全绕开反思，"从失败中学习"落空；失败信息以原始报错直接丢给 LLM（M3 缺诊断引擎）；反思无轮数上限，存在循环放大成本风险（D6 一半）。

两条线共同目标：**让自愈与反思真正诚实触达失败**，且不引入超出裁剪红线的复杂度（不引入 LLM 微调/etcd/Docker 集群）。

## 二、T2 修复方案（自愈执行器修复）

### 2.1 verify_heal 验证真实化（D7）

- **改动前**：`verify_heal` 调 `assess()` 无参 → 返回默认满分 `HealthScore(overall=1.0)` → 无论自愈是否成功验证都通过（假成功）。
- **改动后**：
  - `verify_heal` 读取**最新持久化健康分**（T1 产出的 `data/health/history.jsonl`）；
  - 新增 `verify_action` 按动作类型分发验证器（`_verify_restart_service` / `_verify_restart_component` / `_verify_clear_cache` / `_verify_circuit_breaker` / `_verify_memory`）；
  - 健康分为 `None`（无数据）时返回 `False`，日志记录验证失败原因，不再假通过。

### 2.2 危险动作保护（D9）

| 动作 | 改动前 | 改动后 |
|------|--------|--------|
| `restart_service` | 无 `restart_command` 时仍返回 SUCCESS | 无命令 → **SKIPPED**；执行后强制验证 |
| `clear_cache` | 任意路径可清 | 白名单内可清；`pattern="*"` 或白名单外路径 → **SKIPPED** |
| `restart_component` | 不存在 | 新增（命令缺省 → SKIPPED） |

### 2.3 熔断恢复走公开 API（D11）

- **改动前**：`recover_circuit_breaker` 直接 `breaker._state = CLOSED` 等私有字段赋值。
- **改动后**：经 `circuit_breaker` 公开 API（`get_status()` / `manual_reset()` 等）恢复；T3 熔断统一后指向单一注册表接口。grep 校验无 `._state =` 直改残留。

### 2.4 恢复动作映射表（M4）

新建 `agent/self_healing/policy.py`：
- `RESTORE_MAP`：动作 → 恢复命令映射；
- `ACTION_STATUS`：动作 → 期望状态码；
- `DOMAIN_HINTS`：领域提示。
纯数据模块，供 `self_healer` 与 `alert_manager` 接线。

## 三、T4 修复方案（失败路径反思闭环）

### 3.1 失败触发反思（D12）

`planning/react.py` 原逻辑：

```python
if self.reflector and action_result.success:
    ...  # 仅成功反思
```

改动后新增失败分支（`elif self.reflector and not action_result.success:`）→ 调用 `_failure_reflect`：

```python
if self.reflector and action_result.success:
    ...  # 成功反思（不变）
elif self.reflector and not action_result.success:
    # 失败反思：结构化诊断 → failure_reflect → 注入下一轮
    await self._failure_reflect(thought, action_result, task, context)
```

**收敛保证**（D6）：独立反思轮数上限 `reflection_retries`（配置默认 2，`self._failure_reflection_count` 计数）；超限返回 `restore_eligible` → 触发快照还原重试（T5 能力，`restore_retry` 开关）或走升级路径（降级/人工）。

### 3.2 结构化诊断（M3，诊断引擎）

新建 `planning/diagnostics.py`：

```
FailureDiagnosis: error_type / error_message(≤300字符) / tool_name /
                  attempt / history(≤3轮) / project_context(≤8键) /
                  repair_hints
```

- `classify_error`：优先级 `YunshuError.category` > 工具缺失语义 > 文本特征匹配 > `unknown`；
- 修复提示表（`REPAIR_HINTS`）覆盖 16 类错误（含诊断层扩展 `TOOL_NOT_FOUND`）：

| error_type | 注入的修复约束 |
|-----------|----------------|
| network_timeout / network_temporary | 建议重试或换备用路径，**禁止无限重试** |
| permission_denied | 检查权限声明与工具白名单，勿重复尝试 |
| external_api / external_service | 校验参数与凭证，勿原样重发 |
| tool_not_found | 校验工具名与注册表，勿虚构工具 |
| data_invalid / data_missing / data_corrupt | 校验/补齐/重建数据 |
| resource_memory / disk / cpu | 降并发/清空间/降负载，勿同参重试 |
| config_error | 检查配置项与默认值 |
| security_alert | 停止尝试并上报 |

### 3.3 failure_reflect 与持久化

`planning/reflector.py` 新增 `failure_reflect`：
- LLM 可用：`FAILURE_REFLECTION_PROMPT`（原始任务 + 失败动作 + 诊断报告 + 修复历史）→ 输出 JSON `{root_cause, confidence, repair_actions, avoid}`；
- LLM 不可用/异常：规则兜底（基于 `repair_hints` + 历史重复检测），**不阻断主循环**（守不易）；
- 失败 lessons 写入 `lessons_db`，`get_advice_for_task` 可检索。

### 3.4 注入与换思路

- 修复建议注入 `context["_hints"]`（上限 20 条），下轮 `_think` 拼入"历史调整建议"段；
- 失败历史写入 `context["_failure_history"]`（保留最近 3 轮），第 2 轮起 prompt 显式声明：

```
【失败反思记录（前 N 次尝试及失败原因，请换思路）】
- 第1次失败: <action> → <error>（猜测根因: <root_cause>）
```

- 收敛/升级：反思超限或 LLM 连续 2 轮相同 `root_cause` → 终止反思并升级（降级/人工兜底）。
