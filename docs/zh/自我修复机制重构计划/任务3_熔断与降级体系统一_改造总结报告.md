# 任务 3：熔断与降级体系统一 — 改造总结报告

> 所属阶段：阶段二（恢复层修复）｜ 实施日期：2026-08-14
> 对应设计文档章节：第二层「即时恢复策略」（重试/降级/备用路由）
> 关联缺陷：D8、D10、D11、M6

---

## 一、改造目标

消除"两套熔断体系并存 + 降级伪造成功"两大问题，建立单一、诚实、可观测的即时恢复层：

1. 双熔断统一（修 D10）：`error_handler.py` 内部熔断注册表与 `circuit_breaker.py` 全局注册表合并为单一事实源；
2. 降级诚实化（修 D8）：`graceful_degrade` 模块降级方法不再伪造成功——降级路径返回结果携带 `degraded=True` 且不计入 success 指标；
3. 恢复路径规范（修 D11）：熔断恢复统一走公开 API，禁止私有字段直改；
4. 降级收益可量化（补 M6）：降级埋点补充"挽回损失"口径。

【不易】约束保全：`GracefulDegrade`/`CircuitBreaker`/`error_handler` 公开 API 签名不变；`DegradeModule` 枚举值不删；向后兼容别名（`RETRY`/`RELAXED`/`FALLBACK`/`DISABLED`）保留。

## 三、改造内容

### 步骤 1：熔断统一（单一事实源）— agent/error_handler.py

- `ErrorHandler.__init__`：`self._circuit_breakers = get_breaker_registry()`（与全局注册表共享同一 dict，双向同步）；
- `register_circuit_breaker`/`get_circuit_breaker`：签名不变，读写统一注册表；
- `get_circuit_breaker_status()`：委托 `get_all_circuit_breaker_status()`；
- 新增 `migrate_breakers()`：检测到非共享注册表时，将其中 OPEN 状态的熔断器迁入统一注册表（兼容两套 CircuitBreaker 类的 OPEN 判定），生产/测试环境防状态丢失。

### 步骤 2：降级诚实化 — agent/graceful_degrade.py

| 方法 | 改造前（伪造） | 改造后（诚实） |
|------|--------------|--------------|
| `critic_evaluate_with_degrade` | 硬编码 `overall_score=7` + 计 success | `{"degraded": True, "overall_score": None, "reason": "Critic 服务不可用..."}`，不计 success；`*args/**kwargs` 兼容 critic.py 三参数调用 |
| `memory_query_with_degrade` | 返回 `[]` + 计 success | 返回 `[]`（签名不变），不计 success，degraded 语义经埋点呈现 |
| `schema_validate_with_degrade` | dict 直接 `valid=True` | 可注入验证器真实校验（`set_schema_validator`/构造参数）；缺失或异常时 `valid=False + degraded=True` |
| `dashboard_data_with_degrade` | 返回 stub 数据无标记 | 返回对象带 `degraded=True`，缓存命中标记 `fallback_type="cache"` |

### 步骤 3：恢复路径统一 — agent/circuit_breaker.py

- 类方法 `CircuitBreaker.force_half_open()`：锁保护下置 HALF_OPEN 并清零半开计数；
- 模块级 `force_half_open(name)`：不存在则创建，经锁保护，作为恢复路径公开 API；
- 新增 `get_breaker_registry()` 共享注册表访问器。

### 步骤 4：降级收益可观测

- `_record_degrade` 新增收益口径参数 `fallback_used`/`avoided_calls`/`saved_latency_ms`/`fallback_type`；
- degrade_history 条目新增上述字段，`get_status()`/`get_metrics()` 输出 `degraded_fallbacks_used` 与 `degraded_calls_avoided`；
- 关键分支日志（本次补充）：`critic_degrade_enter`/`critic_degrade_fallback`/`memory_degrade_enter`/`memory_degrade_fallback`，携带输入规模、错误率级别、降级结果，供排查降级逻辑。

## 四、性能收益数据

> 测量方式：`scripts/measure_task3_degrade_benefit.py`，模拟 Critic 主路径 50ms，10 次成功建立基线后注入 40 次故障（禁用缓存排除干扰）。

| 指标 | 数值 |
|------|------|
| 降级短路线路计数（`degraded_calls_avoided`） | **39 次** |
| 实际使用 fallback（`degraded_fallbacks_used`） | 40 次 |
| 累计挽回延迟（Σ `saved_latency_ms`） | **1962.7 ms** |
| 平均单次挽回延迟 | 49.07 ms（≈ 主路径耗时） |
| 等价说明 | 若未降级，39 次主路径调用将耗时约 **1950 ms**；降级短路后每次降至 stub 开销（<1ms），**延迟节省约 98%** |

收益口径要点：
- `avoided_calls` 只统计**确实避免**的主路径调用（降级短路），重试耗尽场景（调用已实际发生）记 0，不虚报；
- `saved_latency_ms` 取自最近一次主路径实测耗时（`_main_latency_ms`），随负载自适应。

## 六、全库"伪造成功"排查结果与扩展修复

本次同步排查了全库"降级/熔断路径伪造成功"模式（`overall_score` 硬编码、`passed=True`、`record_success` 于异常路径），发现并**一并修复**了 `CriticEvaluator` 内与 D8 同类的两处残留：

| 位置 | 场景 | 修复前 | 修复后 |
|------|------|--------|--------|
| `agent/cognitive/critic.py` L138-155 | `should_skip(CRITIC)` 命中（错误率 ≥60% 降级跳过） | `overall_score=80, passed=True`（伪造成功） | `overall_score=None, passed=False`，reason 保留"Critic 服务不可用" |
| `agent/cognitive/critic.py` L157-179 | 熔断器打开（`allow_request()` False） | `overall_score=80, passed=True`（伪造成功） | `overall_score=None, passed=False` |

> 影响面评估：无既有测试固化这两处 80 分；`EvaluationResult` dataclass 无运行时校验；`CriticEvaluator` 无生产外部调用方（仅测试驱动），修改安全。新增 `test_evaluate_skips_when_degraded`/`test_evaluate_blocked_when_circuit_open` 验证（test_verification.py 33 passed）。

### 非缺陷（设计决策/空状态，仅说明）

| 位置 | 说明 |
|------|------|
| `agent/skills_mgmt/output_guard.py` L282 | `passed=True` 是显式设计（护栏不阻塞主流程，风险经 `severity` 传递给调用方），非伪造；调用方应依据 severity 而非 passed 决策 |
| `agent/tools/__init__.py` L508 | 无调用数据时的空状态默认评分（100），非降级语义 |
| `agent/guardrails/output_schema.py` L496 / `agent/error_handler.py` L323 | `record_success()` 均在真实成功路径，合理 |
