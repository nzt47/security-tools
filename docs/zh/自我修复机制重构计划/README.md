# 云枢自我修复机制重构计划（总纲）

> 依据设计文档：`docs/zh/设计思路/设计智能体自我修复机制-20260811065618.json`
> 审计时间：2026-08-12 ｜ 适用系统：云枢（Yunshu）v2.0.0
> 目标：将"理论上限"的设计思路裁剪落地为与云枢实际架构匹配的、可独立分发的重构任务集

---

## 一、审计结论摘要

设计文档提出了一套完整度很高的理想闭环：**分层隔离 → 五级健康探针 → 即时恢复 → ReAct+Reflexion 语义修正 → FATE 自我进化 → 安全护栏**。经对照云枢代码库逐层审计：

- **设计思路总体合理**（约 70% 可借鉴），核心哲学"先止血再治病""让 AI 从自己的错误中学习"与云枢"反思→经验沉淀"的既有方向一致；
- **但不可直接落地**：约 30% 内容依赖云枢不具备的基础设施（LLM 微调管线、etcd 分布式 KV、Docker 沙箱集群），且与云枢已实现的部分能力重复或冲突；
- **发现 12 项实质缺陷**，其中 3 项为"假成功"级硬伤（自愈验证永远通过、降级伪造成功、服务重启未验证），必须先修。

**一句话结论：架构思想可复用，工程实现必须按云枢单机进程 + 外部 LLM API + 无训练管线的现实裁剪。本计划即裁剪后的落地路线。**

## 二、设计文档合理性评估

### 2.1 合理且应借鉴的部分

| # | 设计点 | 评估 | 云枢落地建议 |
|---|--------|------|--------------|
| 1 | 分层隔离、故障不跨层传播 | ✅ 正确 | 云枢已有模块分层，落地为"故障域声明" |
| 2 | "先恢复服务，再排查根因" | ✅ 正确 | 与既有 GracefulDegrade 思路一致，保留 |
| 3 | 检测→诊断→恢复→验证→进化闭环 | ✅ 正确 | 补全缺失的"验证"与"进化"两环 |
| 4 | 代码场景用"可验证信号"做探针 | ✅ 正确 | 云枢语义层用 Critic 评分 + 工具调用结果代替 |
| 5 | 反思循环增量传递报错信息 | ✅ 正确省 token | 直接采纳进失败路径反思 |
| 6 | 结构化诊断报告 + 修复历史注入 | ✅ 正确 | 采纳，映射到工具调用失败场景 |
| 7 | 沙箱"一次性容器 + 天然回滚"思想 | ✅ 正确 | 云枢以进程级隔离代替（见任务 7） |
| 8 | 适配器层"多态输入→统一输出" | ✅ 正确 | 应用于错误归一化（error_handler 分类已有雏形） |

### 2.2 理论缺陷（概念层面不可行/不自洽）

| # | 缺陷 | 说明 |
|---|------|------|
| D1 | **FATE 训练闭环与云枢根本冲突** | FATE 要求监督微调 + PFPO 强化学习，云枢调用外部 API 模型，无本地权重、无训练管线，此层 100% 不可落地。需替换为"失败案例 → 结构化分析 → 修复策略库 → 运行时注入"的提示词/策略级轻量进化 |
| D2 | **L5 语义层无法客观量化** | "语义逻辑层健康评分 0-100"缺乏测量方法论——语义正确性无通用探针。仅代码场景可借测试通过率近似。云枢只能以 Critic 评分 + 用户反馈作为代理指标 |
| D3 | **动态权重调度可能掩盖真实故障** | "某层频繁出问题时自动降低该层权重"会导致故障层被"洗白"，健康向量失真。权重应来自业务重要性而非故障频率 |
| D4 | **"秒级回滚"前提未定义** | 每轮任务前快照到 etcd 假设：a) 有分布式 KV 基础设施（云枢单机没有）；b) 明确"哪一轮状态是好的"。LLM 任务上下文回滚的语义天然模糊 |
| D5 | **重试缺乏成本模型** | "LLM 超时重试 3 次"未考虑 token/延迟成本。云枢 ReAct 已有 deadline/token/cost 三层预算，文档反而缺失 |
| D6 | **反思循环无收敛保证** | "强制换一个思路"无法证明会收敛。需补充终止标准：最大轮数 + 重复失败模式检测（状态哈希） |

### 2.3 实践缺陷（落地时必然踩坑）

| # | 缺陷 | 说明 |
|---|------|------|
| D7 | 自愈验证假成功（**硬伤**） | `self_healer.verify_heal()` 调用 `health_assessor.assess()` 时未传 metrics，而 assess() 无参数时返回默认满分 1.0 → 自愈"验证"永远通过 |
| D8 | 降级模块伪造成功（**硬伤**） | `critic_evaluate_with_degrade` 返回硬编码 7 分、`memory_query_with_degrade` 返回空列表、`schema_validate_with_degrade` 对 dict 直接放行，均记为 success 污染指标 |
| D9 | 服务重启未验证（**硬伤**） | Windows 下 `Restart-Service 'yunshu'` 必然失败却返回 SUCCESS"指令已发送"，无实际验证 |
| D10 | 双熔断体系并存 | `error_handler.py` 自带熔断注册表 + `circuit_breaker.py` 全局注册表/三级熔断器，两套状态互不同步 |
| D11 | 恢复熔断器绕过公开 API | `_recover_circuit_breaker` 直改私有字段 `handler._circuit_breakers[name]._state`，耦合且脆弱 |
| D12 | 反思只在成功时触发 | `react.py` 中 `if self.reflector and action_result.success` —— 失败路径完全跳过反思，与设计文档"从错误中学习"背道而驰 |

### 2.4 需要补充完善的内容（设计文档未覆盖）

| # | 缺失项 | 说明 |
|---|--------|------|
| M1 | 健康数据持久化与历史趋势 | 现 assessor 仅内存 100 条，无法支撑"持续进化"与故障复盘 |
| M2 | 失败案例结构化回流 | defect_tracker 只收集不回流，无"修复策略→运行时"的闭环 |
| M3 | 决策链路循环检测 | "状态哈希重复 ≥3 次注入终止信号"未实现，仅有 max_iterations 兜底 |
| M4 | 工具/LLM/记忆分故障域的恢复动作表 | 文档有表但代码无映射实现 |
| M5 | 自动恢复失败后的升级告警与人工接管队列 | alert 有通知能力，但无"人工接管队列"状态机 |
| M6 | 降级动作的成本/收益记录 | 降级埋点有，但无"降级挽回的损失"口径，无法评估降级策略有效性 |

## 三、分阶段重构计划总览

依据内容逻辑（先修"假成功"、再补"检测与反思"、后建"进化与运营"）与工作量评估，拆分为 **4 个阶段、7 个独立任务**。

```
阶段一 地基：健康评估真实化          → 任务 1（健康评估体系重构）
阶段二 恢复层修复：让"止血"名副其实   → 任务 2（自愈执行器修复）
                                       任务 3（熔断与降级体系统一）
阶段三 认知层补强：让"反思"触达失败   → 任务 4（失败路径反思闭环）
                                       任务 5（状态快照与决策循环检测）
阶段四 进化与运营：轻量进化 + 安全    → 任务 6（轻量自我进化机制）
                                       任务 7（安全护栏与人工接管）
```

### 3.1 各任务速览

| 任务 | 名称 | 依赖 | 工作量 | 核心成果 |
|------|------|------|--------|----------|
| T1 | 健康评估体系重构 | 无 | 高 | 五层探针 + 真实评分 + 持久化 + Dashboard |
| T2 | 自愈执行器修复 | T1 | 中 | 验证真实化 + 动作补全 + 危险动作保护 |
| T3 | 熔断与降级体系统一 | 无 | 中 | 单熔断体系 + 降级诚实化 + 统一恢复路径 |
| T4 | 失败路径反思闭环 | 无 | 高 | 失败触发反思 + 结构化诊断 + 修复历史注入 |
| T5 | 状态快照与决策循环检测 | T4(弱) | 中 | 每轮快照 + 秒级回滚 + 状态哈希循环检测 |
| T6 | 轻量自我进化机制 | T1+T4 | 高 | 失败案例回流 + 修复策略库 + 参数联动 |
| T7 | 安全护栏与人工接管 | T2(弱) | 中 | 沙箱执行策略 + 升级告警 + 人工接管队列 |

> 工作量评级为相对复杂度（高/中/低），不含时间估算。T4 与 T5 均可独立执行；T6 依赖 T1/T4 的产物。

### 3.2 裁剪红线（易/变/简 三义约束）

以下为各任务必须遵守的【不易】约束，任何任务不得突破：

1. **不引入 LLM 微调/训练管线**（违【简易】+ 云枢无训练基础设施）——进化只能发生在提示词、策略、参数层；
2. **不引入 etcd / 分布式 KV**（违【简易】）——快照用本地 JSON 文件 + 已有 state_manager；
3. **不删除既有公开 API**（违【不易】）——所有重构向后兼容，新增接口优先于改动接口；
4. **所有自愈/降级动作必须诚实**（违【不易】= 假成功）——未执行、未验证的动作一律报 FAILED/SKIPPED，禁止伪造 SUCCESS；
5. **每个任务必须自带测试**（护城河）——新增/修改路径的单元测试 + 契约测试为强制验收项；
6. **安全操作须人工确认**（违【不易】= 越权）——清理缓存、重启服务等破坏性动作必须经策略白名单 + 冷却 + 频率三重校验。

## 五、执行建议

1. **按阶段串行执行**：T1 → T2/T3 → T4/T5 → T6/T7；同阶段任务可并行分发；
2. **每个任务独立验收**：执行方按任务文件内"评估标准"自测，提交自测报告（测试命令 + 通过数 + 关键日志样例）；
3. **回归门禁**：每任务完成后跑全量 `pytest`，确保测试收集错误为 0、新增用例通过；
4. **变更回滚**：任何任务若需改动 `agent/error_handler.py` / `agent/circuit_breaker.py` / `agent/graceful_degrade.py` 等被多处引用的模块，必须先跑 `tests/contract/` 契约测试并保留旧 API 别名。
