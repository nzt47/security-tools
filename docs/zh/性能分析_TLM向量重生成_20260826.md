# TLM 迁移向量重生成性能分析报告

> 关联：`scripts/benchmark_tlm_regen.py`（基准）、`scripts/migrate_to_tlm.py`（优化后默认配置）。
> 测试日期：2026-08-26
> 测试环境：Windows 10 / Python 3.12 / torch 2.13.0+cpu（6 线程）/ sentence-transformers 5.6.0

## 一、瓶颈定位

迁移脚本的向量重生成路径原实现：

```
ThreadPoolExecutor(max_workers=4) → 每个 worker 逐条调用 encoder.encode(text)
```

瓶颈假设（【不易】三义分析）：
1. **torch CPU 推理已自带多线程**（`torch.get_num_threads()=6`），Python 层再开 4 个 worker 并发调用 torch，
   会导致 4 个线程**争抢** torch 的 6 个底层计算线程，收益有限甚至为负。
2. **逐条 encode 有固定开销**（tokenize → padding → 模型前向 → 后处理），
   `SentenceTransformer.encode` 支持批量输入，批量推理能摊薄固定开销并利用 torch 内部并行。
3. 因此真正瓶颈是 **encode_batch（批量推理）**，而非 workers（并发度）。

## 二、基准方法

- 构造 100 条中文模拟记忆文本（与 mock 数据同构）
- 加载本地缓存 `BAAI/bge-m3`（1024 维，CPU 推理；与 bge-small-zh-v1.5 同架构，
  批量/多线程的**相对加速规律一致**，绝对耗时不同）
- 遍历 workers ∈ {1, 2, 4} × encode_batch ∈ {1, 16, 64} 共 9 组，每组预热后计时
- 指标：吞吐量（items/s）、相对加速比（基准 = workers=1, encode_batch=1）

## 三、实测数据

| workers | encode_batch | 耗时(s) | 吞吐(items/s) | 加速比 |
|---|---|---|---|---|
| 1 | 1 | 18.42 | 5.4 | 1.00x |
| 2 | 1 | 17.61 | 5.7 | 1.05x |
| 4 | 1 | 17.36 | 5.8 | 1.06x |
| 1 | 16 | 9.85 | 10.1 | 1.87x |
| 2 | 16 | 9.29 | 10.8 | 1.98x |
| 4 | 16 | 9.64 | 10.4 | 1.91x |
| **1** | **64** | **8.54** | **11.7** | **2.16x** |
| 2 | 64 | 8.80 | 11.4 | 2.09x |
| 4 | 64 | 10.90 | 9.2 | 1.69x |

## 四、结论

1. **encode_batch 是决定性因素**：batch=1 → 64 吞吐提升 **2.16x**（5.4 → 11.7 items/s）。
   批量推理利用 torch 内部并行（矩阵乘法批处理），摊薄固定开销。
2. **workers 几乎无增益**：encode_batch=1 时 workers 1/2/4 仅 5.4/5.7/5.8（≤1.06x），
   证实 torch 底层 6 线程已占满 CPU，Python 多 worker 争抢 GIL 无收益。
3. **workers=4 + encode_batch=64 反而下降**（9.2 vs 11.7，-21%）：多 worker 线程切换 +
   torch 线程争抢开销超过并行收益。
4. **最优配置：workers=1 + encode_batch=64**，吞吐 11.7 items/s（加速 2.16x）。

## 五、落地变更

[migrate_to_tlm.py](file:///c:/Users/Administrator/agent/scripts/migrate_to_tlm.py) 默认配置已更新：

```python
DEFAULT_WORKERS = 1       # ThreadPoolExecutor max_workers（torch 已并行，多 worker 无益）
DEFAULT_ENCODE_BATCH = 64  # 每次 encode 的批量大小（批量推理是主要提速点）
```

`regenerate_vectors` 实现同步升级：
- worker 内按 `encode_batch` 分片，调用 `encoder.encode_batch(sub)` 批量推理（替代逐条 encode）
- items 按 worker 数均分 chunks，避免 as_completed 拆散批次
- CLI 暴露 `--workers` / `--encode-batch` 便于环境差异调优

## 六、扩展建议（后续可选）

| 方向 | 预期收益 | 说明 |
|---|---|---|
| 增大 encode_batch（128/256） | 微增 | 受内存/单批序列化长度限制，需实测 |
| 量化模型（ONNX int8） | 2-4x | 需 `convert_bge_to_onnx.py` 流程，重生成单批瓶颈在推理 |
| GPU 迁移机 | 10-50x | bge-small 512 维在 GPU 上批量推理极快，多 worker 配置将重新有效 |
| 分批落盘降低峰值内存 | — | 万级数据时 encode_batch 攒批 + 写缓冲需关注峰值内存 |
