# 并行会话提交窗口协调机制建议（2026-08-15）

> 针对本次 EVO-T1~T6 收尾期间**并行会话反复 rebase 导致提交被剥离、推送被拒**的实战教训，提出提交窗口协调机制建议。
> 适用对象：主工作区 + 并行会话（TASK-06/07/08 等）所有操作 develop 分支的会话。
> 关联：[Git 提交摘要报告](进化机制重构计划/09_Git提交摘要报告_20260815.md) | [并行会话未提交文件清理建议](并行会话未提交文件清理建议_20260815.md)

## 一、问题背景（2026-08-15 实战记录）

| 事件 | 现象 | 根因 |
|---|---|---|
| 提交 `b8e43bd2` 被剥离 | update-ref 成功，但并行会话随后 rebase，提交成为孤儿对象 | 并行会话在本地 rebase 重写 develop，覆盖了我方 update-ref |
| 提交 `5d900313` 被剥离 | 本地/远程 develop 被并行会话重置到 `462e2675`，`5d900313` 移出历史 | 并行会话 `reset --hard origin/develop` 或等价操作 |
| push 被拒（non-fast-forward） | `git push` 提示远程有本地未包含的提交 | 并行会话在推送前又推进了远程（本地 ahead 2 / behind 1） |
| 契约文件改动丢失冲突 | 6 个 contract/pact JSON 工作区 M 状态随并行会话提交 `5b5f6933` 入库 | 并行会话批量 add/commit，吞并共享工作区改动 |
| 清理建议文档被触碰（MM） | 本会话已入库文档的 index 版本被并行会话改写 | 并行会话对 index 直接操作，未感知文档归属 |

**核心矛盾**：多个会话共享**同一本地仓库 index + develop 引用**，且并行会话偏好 rebase（重写 SHA），任何一方的本地提交都可能被另一方 reset/rebase 剥离。

---

## 二、根因分析

1. **共享 index**：主工作区 `git add` 会污染并行会话 staging 区；反之并行会话 `git add .` 会吞并他人 staged 文件（contract JSON 案例）。
2. **rebase 重写 SHA**：并行会话 rebase 后本地/远程 SHA 全部变化，基于旧 SHA 的 update-ref/commit 立即失效。
3. **无提交窗口约定**：任何会话随时可 push/rebase，无先后顺序，导致 non-fast-forward 频繁发生。
4. **detached worktree 提交后需 update-ref**：该模式（本会话采用）不产生 merge 冲突，但依赖 update-ref 时 develop 未被并发改写——当前无保护。

## 三、协调机制建议

### L0 基线规则（必备，即刻生效）

| 规则 | 内容 | 防患 |
|---|---|---|
| R1 专属分支 | 并行会话在主工作区之外，一律使用**专属 topic 分支**（如 `task06/*`、`task07/*`），禁止直接操作 develop | 消除 shared-index 污染 |
| R2 develop 只经 PR/MR 合入 | develop 的写入只允许通过 `git merge`（保持 SHA 不变），**禁止 rebase / reset --hard / update-ref 直接改 develop** | 防止历史重写剥离他人提交 |
| R3 提交前同步 | 任何会话 push 前先 `git fetch origin` + `git rebase origin/develop`（仅在自己 topic 分支上） | 消除 non-fast-forward |
| R4 不触碰他人文件 | `git add` 只加自己归属的文件路径；禁止 `git add .` / `git add -A` | 防止吞并他人 staged 改动 |

### L1 窗口协调（防 update-ref 竞态）

| 机制 | 说明 |
|---|---|
| 提交窗口令牌 | 通过共享文件（如 `docs/zh/并行会话提交窗口.md`）或会话间约定，同一时刻仅一个会话执行 update-ref/push develop |
| update-ref 后立即验证 | 执行 `git update-ref refs/heads/develop <hash>` 后**立即**检查 `git merge-base --is-ancestor <hash> develop`，失败则重试（本会话已在 `b8e43bd2`/`5d900313` 两次经历） |
| push 失败重试策略 | push 被拒后：fetch → 检查本地独有提交 → rebase 到远程之上 → 重新 update-ref → 再 push（本次 `6f8812fd..c5b6a908` 即按此流程成功） |
| 共享文件锁 | 涉及共享 docs 的写入前，先确认对方已完成（如检查 `git status` 该文件是否仍在 M/MM 状态） |

### L2 提交协议（规范化）

1. **提交前自查清单**：
   - [ ] 本地 develop 与 `origin/develop` 是否同步（`git rev-list --left-right --count`）
   - [ ] 本次提交文件是否全部归属本会话
   - [ ] 是否触碰了共享 docs（如 `已知问题清单`、`交付物清单`），若是先确认对方已提交
2. **提交时**：detached worktree 或 topic 分支 + `git add <明确文件>` + pre-commit 全绿。
3. **提交后**：update-ref develop（或 push topic 分支）→ **立即**验证 ancestor + 记录到提交窗口日志。
4. **检测到被剥离时**：保留对象引用（reflog / commit hash），基于最新 develop 重新重放，不强行 force push。
