## 2. 流式扫描 vs 分片扫描：架构差异对比

| 维度 | 流式扫描（`iter_cards()`） | 分片扫描（refs 按前缀/哈希分片） |
|---|---|---|
| 内存 | O(U)：refs 全量驻留（1000 万卡 ≈1.28 GB） | O(U/N)：单片驻留（16 片 ≈80 MB/片） |
| 时间 | O(N) 串行（1000 万卡 ≈37.5 分钟） | O(N/N + 合并)，可并行（16 片理论 ≈2.3 分钟 + 合并） |
| 增量写 | 单文件整读改写（`index_links.md` 每次全量读改写） | 只触达单片（写成本 ∝ 1/N） |
| 索引文件 | 单文件，读侧 O(1) 查表不变 | 多文件，读侧需合并查询（路由 + N 片读取） |
| 一致性 | 单文件原子写，简单 | 跨片无原子性，需补偿/重放机制 |
| 故障影响面 | 索引损坏 → 回退全扫 37.5 分钟 | 单片损坏 → 仅该片回退/重建 |
| 复杂度 | 低（新增 1 生成器 + 3 调用点） | 中高（路由、分片元数据、合并读、跨片一致性） |
| 适用范围 | ≤200 万卡（内存 <256 MB）；500 万为极限 | ≥500 万卡；1000 万卡为推荐线 |

**决策边界**：

```
≤200 万卡   → 流式扫描足够（refs ≤256 MB）
200–500 万  → 流式必须 + 索引健康监控（回退 7.5–18.75 分钟代价）
≥500 万卡   → 分片架构（流式收益耗尽，refs 本体成主导成本）
≥1000 万卡  → 分片 + 并行扫描 + 后台重建任务（同步回退已无工程意义）
```

## 5. 结论与建议

| 决策维度 | 1000 万节点评估 |
|---|---|
| 内存（现状） | ≈18.6 GB：单机完全不可行 |
| 内存（流式） | ≈1.28 GB（基线）～ 6.4 GB（高密度）：已超单机合理水位 |
| 内存（分片 16 片） | ≈80 MB/片（基线）：回到常态内存区间 |
| 耗时（全扫） | 流式 37.5 分钟 vs 分片并行理论 2.3 分钟 |
| 架构判定 | **分片架构强制线**（≥500 万即可启动评估） |

**建议**：

1. **1000 万节点 = 分片 + 并行 + 后台化三件套**：
   - refs 按 slug 哈希分片（16 片起），增量写只触达单片；
   - 全量重建改并行（分片独立扫描 + 结果合并）；
   - 回退/重建改后台任务，禁止同步阻塞（37.5 分钟无法同步等待）。
2. **落地顺序**：先流式（`iter_cards()`，是分片扫描的基础形态）→ 再分片路由与元数据 → 最后并行与后台化。每步独立可回滚。
3. **一致性设计**：分片引入跨片无原子性问题，需补偿/重放机制，与现有「增量叠加 == 全量重建」不变量对齐（分片后不变量改写为「各片叠加 == 对应片重建」）。
4. **阈值落地**：以本报告为参照建立容量监控——refs 超 512 MB（约 400 万卡）触发分片评估。

- 外推：线性；真实值可能随文件系统缓存、YAML 结构浮动 ±20%；分片并行时间为理想化下界，未计调度/合并开销
