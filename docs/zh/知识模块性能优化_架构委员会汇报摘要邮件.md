## 一、优化落地与实测成果（均已提交并回归验证）

| 优化项 | 内容 | 实测提升 |
|---|---|---|
| 入链索引（index_links.md） | 全量重建 + 增量叠加 + CRUD 挂接，一致性测试先行锁定「增量叠加 == 全量重建」不变量 | 入链判定 2249.3ms → 1.1ms（**≈2094x**） |
| 批量删除（delete_many） | 一次扫描 O(N) + O(K) 删除，复用入链索引 | 2342.9ms → 134.1ms（**17.5x**） |
| index.md 高频追加 | append 模式 O(1) 定位，内容集合不变式 + 重整收敛 | 单次写定位降阶 |

容错与降级：读路径索引缺失/损坏回退全库扫描（行为不退化）；写路径失败 warning 降级不阻断卡片主操作；配套 7 项降级单测，3 项关键分支 `--log-cli` 实证触发。完整回归 **70+ passed**。

## 二、容量扩展性评估结论（架构演进路线图）

从实测锚点（3000 卡 5.6MB）线性外推至 1 垓，形成分档决策边界：

```
≤200 万卡    → 流式扫描足够（当前执行线，充裕）
≥500 万卡    → 分片架构评估线
≥2000 万卡   → 分片执行线（64 片）
≥5000 万卡   → 分布式/对象存储线（256 片）
≥1 亿卡     → 分布式架构执行线（512 片）
≥100 亿卡   → 区域级多集群（32768 片，全球规模）
≥1 万亿卡   → 联邦式多租户（理论极限锚点）
≥1 垓卡     → 系列总终结（物理可行域外，模型闭合）
```

**核心启示**：分片不是万能解（2^20 片后边际收益被路由/对账成本吞没）；超大规模应切分业务域（联邦/多租户）。当前工程规模远低于所有分档线。

## 三、提请架构委员会关注的事项

1. **流式方案落地**：≤200 万卡执行线内落地 `iter_cards()` 流式扫描（分片的基础形态），内存 O(N)→O(U)；
2. **容量监控阈值落地**：refs > 512 MB（≈400 万卡）→ 触发分片评估；文件数 > 1000 万 → 存储层分层改造；
3. **分片架构前置设计**：≥500 万卡前完成分片 + 跨片一致性方案（路线图已含各档片数基线）；
4. **模型闭合声明**：容量预估系列已闭合（1 垓为终篇），后续不再外推；超出 10^16 的数值无决策价值。
