# BM25 优化技术复盘总结

> 归档位置：`docs/wiki/BM25_TECHNICAL_RETROSPECTIVE.md`
> 日期：2026-08-05
> 用途：团队内部分享——核心问题、解决方案、后续优化建议

---

## 1. 核心问题回顾

### 1.1 问题现象

VectorStore 的 InvertedIndex（BM25 算法）在英文关键词检索中出现**短文档排序虚高**：

- 查询 "machine learning" 时，2-token 短文档得分（1.35）反超 50-token 长文档（0.77）
- 短/长得分比高达 1.98x，排序结果与相关性直觉严重背离

### 1.2 根因分析

BM25 评分公式：

```
score = IDF * tf*(k1+1) / (tf + k1*(1 - b + b*dl/avgdl))
```

- `b` 是长度归一化参数（0~1）：b 越大，文档长度 `dl/avgdl` 对分母的影响越大
- 短文档（dl << avgdl）使 `b*dl/avgdl` 趋近 0 → 分母变小 → **得分虚高**
- 原默认 b=0.75 过度放大了这一效应

**数学验证**（b 值敏感性扫描）：

```
b=0.0  短/长比 = 1.00x（无虚高但无区分度）
b=0.25 短/长比 = 1.32x（轻微）
b=0.50 短/长比 = 1.77x（中等，折中）
b=0.75 短/长比 = 2.42x（偏高，原默认）
b=1.00 短/长比 = 3.48x（严重虚高）
```

**关键认知修正**：b 值越大虚高越严重——之前曾误判方向，通过极端场景脚本实证纠正。

## 2. 解决方案

### 2.1 核心变更

- `b` 默认值 0.75 → **0.5**（折中：缓解虚高 + 保留长短区分度）
- 支持 `BM25_K1`/`BM25_B` 环境变量动态配置
- InvertedIndex 构造函数接收 k1/b 参数（模块级默认值 fallback）

### 2.2 验证体系（3 层）

| 层 | 工具 | 覆盖 |
|----|------|------|
| 基础对照 | `verify_bm25_optimization.py`（3 用例） | 常规场景短/长得分比 |
| 极端场景 | `verify_bm25_extreme_cases.py`（5 场景） | 1-token/term_freq 极端/空文档/b 扫描 |
| 单元测试 | `test_vector_store_fallback.py`（TestBM25LengthNormalization） | 参数可配置性 + 得分比改善 |

### 2.3 CI 持续守护

每次提交自动运行两个 BM25 回归 step（基础 + 极端），失败时输出 `::error::` 标记 + 失败用例详情（旧/新比值 + Δ）。

## 3. 过程亮点

1. **对照实验法**：同一文档集 + 同一查询，仅 b 值不同，隔离变量
2. **诚实声明**：明确 b=0.5 缓解而非消除虚高，不夸大效果
3. **可回滚设计**：环境变量 `BM25_B=0.75` 一键回滚，零代码改动
4. **多实现验证**：InvertedIndex（已优化）与 BM25SkillSearcher（独立）正交验证，避免误伤
5. **认知纠错**：通过实证数据发现并修正 b 参数方向的错误认知

## 4. 后续优化建议

### P0（推荐，收益明确）

| 建议 | 说明 |
|------|------|
| **全参扫描（k1+b）** | 当前仅调整 b，建议对 k1∈[1.0,1.5,2.0] × b∈[0.3,0.5,0.7] 做网格扫描，用真实查询集评估（NDCG/Recall@k） |
| **多查询验证** | 当前验证用 3 组手工查询，建议扩展为 50-100 组真实技能检索查询，建立基准集 |

### P1（增强）

| 建议 | 说明 |
|------|------|
| **查询类型自适应** | 短查询（1-2 token）与长查询（5+ token）使用不同 b 值（短查询可下调 b，长查询可上调） |
| **TF 饱和曲线** | 引入 BM25+（t=1）避免长文档重复词惩罚，进一步平滑 |
| **缓存得分解释** | 检索结果附带得分构成（IDF/tf/长度项），便于调试排序异常 |

### P2（工程化）

| 建议 | 说明 |
|------|------|
| **验证基线入库** | 将 3 组基准查询 + 预期排序固化到 CI 测试夹具，防止漂移 |
| **性能回归守护** | 增加检索延迟基线（当前纯 Python 实现，数据量大时需关注） |
| **gitee CI 同步** | 当前 CI 仅 GitHub Actions，gitee 端如需同质守护需配置镜像流水线 |

## 5. 经验教训

1. **参数调优必须有实证**：仅凭直觉调参（曾误判 b 方向）风险高，极端场景扫描是必要工具
2. **验证脚本本身要进 CI**：一次性验证脚本价值有限，固化进流水线才能持续守护
3. **文档跟随代码演进**：b 方向修正后，技术文档（BM25_B_PARAMETER_RATIONALE.md）同步修正，避免文档与代码漂移
4. **双实现隔离**：项目存在两个 BM25 实现，优化时明确边界（InvertedIndex vs BM25SkillSearcher），避免耦合误伤
