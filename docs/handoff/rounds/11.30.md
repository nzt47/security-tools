**C. 本轮新增的坑**

1. **部署与看护竞态会变“双主”**（已修 #1363）：看护判死是 30s×3、冷启动实测 87s ⇒ 就绪可能刚好越过
   `ready_timeout=180s`（09:52 实测差 1 秒）。此时部署会再 spawn 一个后端：后起的抢不到 5678 却仍在后台
   加载 ChromaDB（pid 62184，需人工 kill）。**修法**：回退前再查一次 `listening_pids`，端口已占用就不再 spawn。
   判断依据：`Get-CimInstance Win32_Process -Filter "name='python.exe'"` 出现两个 `app_server.py`。
2. **审计落链有几秒异步延迟**：activity 的 `since_seq` 增量在写动作后立刻查可能为 0，等 3–5s 才出现
   （审计是「预留日志 + 队列 + 后台批量入库」）。排障时别据此判“没写审计”。
3. **慢分片是常态**：覆盖率 shard 3/6 单次 20–25 分钟（§11.10），两个 PR 并行时更久；别当挂死重跑。
4. **`data/window_config.json` 是 tracked 的运行期设置**：11:23 有人在界面开了「窗口感知」
   （审计 `ui.safety.api_window_consent.post`，文件 `enabled: false→true`）⇒ `git status` 出现 tracked 改动；
   11:59 服务重启后它又回到 `false`（应用启动时会重置）。**别 `git checkout` 掉、也别提交**，
   报告时按“运行期改动（用户 UI 动作）”说明；若重启后仍有残留 diff，以文件现状为准、先查审计再决定。
5. 本地 `test_skill_md_schema` 曾被 `autoresearch`/`pdf` 弄红（skill.md 缺必填 `enabled`）：这两个文件是 UI backfill
