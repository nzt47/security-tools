# 交接方式的对比与吸收（云枢 ↔ DeepSeek Harness）· 2026-11-05

> 结论先行：云枢的交接文档是**过程全记录**（可追溯，但越来越重）；DeepSeek Harness 把
> 会话状态交给**运行时派生**（session log / 压缩 / goal），文档只描述契约。两者不是谁替代谁，
> 而是「**契约**该短、**过程**该可检索、**数字**该机器生成」。本文给出可吸收的五条 + 已落地的一条。

## 1. 两边现在怎么做

### 云枢：单文件 append-only 的「会话转移」

- 载体：`yunshu_session_handoff_20261024.md`（3,500+ 行；每次会话末尾追加 §11.x）。
- 注入方式：人在新会话里粘贴「独立提示词」，要求先**完整读** §11.49/§11.48/§11.47/§11.46/§11.45/§11.42–44/§11.41/§11.40/§11.36 M 与 §7/§8。
- 内容结构（实际有效的那部分）：**A 快照 / B 本轮做了什么 / C 新口径（写代码前必读）/ D 未完成与判据 / E 独立提示词**。
- 优点：判据、踩坑、证据链完整；「新口径」那一节是真的省了很多重复试错；
  「期望值 + 自检命令」让新会话能**当场验证**交接是否成立。
- 代价：①读入成本线性增长（本次要求读 8 个 §，约 900 行）；②快照里的数字是**人手抄**的，
  几小时就漂（本轮实测审计 82,348 → 82,408、调度 15 → 16）；③旧轮次永不压缩，检索靠人肉扫。

### DeepSeek Harness：状态派生 + 三条机制

从它的包说明里能直接读到（`dsh-agent-instructions` / `dsh-compaction` / `dsh-goal`）：

1. **工作区指令（AGENTS.md 链）**：用户级 → 项目根 → 逐层目录，按「宽→窄」注入，
   有**字节预算**（默认 65,536），超预算先丢宽文件、最后才截断最窄的那个，并显式发一条
   「预算提示」告知被省略/截断的路径；文件改/删会在下一次请求里以「替换/移除通知」出现；
   换工作目录会重新加载。关键设计：**这些指令就是普通会话内容**，所以能回放、能压缩、能续接。
2. **压缩（compaction）**：把「一段旧历史」替换成**一条摘要消息**，近期历史不动；
   被遮蔽的内容**留在 session log 里**，因此回放能确定性复现同一段压缩后的对话；
   摘要消息带稳定标记，任何消费方都能识别「这是压缩过的历史」；自动（token 压力）与
   `/compact` 手动两种触发。
3. **目标（goal）**：一个跨轮次/重启存活的「完成目标」，支持 create/edit/pause/resume/complete/blocked，
   由独立的 round driver 推进（默认轮数上限），而不是靠人每轮复述。

## 2. 逐项对比

| 维度 | 云枢（当前） | Harness | 差距 |
|---|---|---|---|
| 契约/纪律的载体 | 交接文档里的「C 新口径」 | AGENTS.md 链（有预算、自动注入） | 云枢的契约没有独立、稳定、短小的家 |
| 过程记录 | append-only 全文 | session log（不可见，供回放/压缩） | 云枢把「过程」和「契约」混在一个文件 |
| 体积控制 | 无（只增不减） | 字节预算 + 压缩 + 标记 | 云枢读到后面会越来越慢 |
| 数字/快照 | 人手抄 | 运行时派生 | 云枢的快照会漂（已实测） |
| 可验证性 | 有（自检命令） | 有（log 可回放） | 云枢强在「当场自检」，弱在「历史可复现」 |
| 续接方式 | 人粘一段长提示词 | 服务自动带上（指令 + 目标 + 摘要） | 云枢依赖人，且提示词本身在变长 |

## 3. 可吸收的五条（按落地成本排序）

1. **数字不手抄：交接卡由脚本生成**（✅ 本次已落地）
   `python scripts/handoff_snapshot.py` → 写 `data/handoff_state.json`，并打印一段
   10 行「交接卡」（仓库 HEAD / 服务三处一致 / 技能与能力卡 / 调度 / 工具停用 / 单位看板 / 审计条数）。
   交接文档开头贴这张卡；正文只写**判据与决定**，不再抄数字。

2. **分两册：契约 vs 过程**
   - `docs/handoff/口径.md`：稳定契约，**≤150 行**，只放「写代码前必读」的纪律（真凭据、CodeQL 三种断链、
     派生必须在干净 worktree、双轨、异常回自定义属性、env 读取点进 registry…），改它要写理由。
   - `docs/handoff/轮次_<年月>.md`：append-only 过程记录（现在 §11.x 的内容），按轮次分节，
     每轮带「判据 / 结果 / 未完成」；只追加、不改写。
   - 交接提示词只要求读：**口径（全文）+ 最近 2 轮 + 交接卡**，其余按需检索。

3. **压缩旧轮次，而不是无限追加**
   每满 10 轮，把最早的轮次折叠成一段「摘要 + 索引」（保留：改了哪些文件、定了什么口径、
   被推翻的结论；不保留：逐条命令输出）。原文移到 `docs/handoff/archive/` 备查，
   并在摘要里写明「原文在哪」。**不给模型看全文**，但人能回查 —— 这是 Harness「摘要替换 + 原文留在 log」
   的低成本版本。

4. **next_actions 结构化**
   把「未完成」从散文表格改成机器可读的清单（`data/handoff_next.json`）：
   `{id, title, judge(验收判据), status, blocked_by, updated_at}`。
   交接时渲染成三行；每轮结束时由脚本/人把 status 推进。
   好处：不会再出现「上一轮说要做、这一轮没人记得」；也便于 `handoff_snapshot` 汇总。

5. **每轮固定自检，结果进快照**
   双轨 / validate / 审计链 / 分层基线 / 告警总数 —— 这些命令云枢已经有，
   但结果是「人抄进文档」。改成：跑完写进 `handoff_state.json` 的 `checks` 字段，
   交接卡直接列「上次自检：全绿（时间）」，红了就带出红项。**把可验证性也变成派生的。**

## 4. 不建议照搬的

- **自动压缩接进提示装配**：会改变模型每次看到的内容，属云枢的「改提示装配」，必须先有回归基线 + 灰度 + 回滚开关（C-8 的口径）。交接文档的压缩是**文档层**的，风险低得多。
- **session log 确定性回放**：Harness 是「一切皆事件」的架构；云枢是 Python 单体 + 审计链，
  真要做等价物，成本大于收益。云枢的审计链（82k 条、0 断点）已经承担了「可追溯」这一半。
