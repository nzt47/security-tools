## 1. 威胁模型（先写清楚防谁）

| # | 风险 | 处置 | 残余 |
|---|---|---|---|
| T1 | 脚本直接 import/调用工具（绕过授权、审批、限流） | 脚本**没有**工具句柄；只能发 RPC，由宿主执行并过全部闸门 | 无（协议层不可能绕过） |
| T2 | 脚本自我提权（读 .env、改 `agent/`、装包） | 不传密钥（env 白名单）；node `--permission` 只允许读运行目录+入口；写目录 = 运行目录；**禁止** `child_process` | node 引擎 0day（见 §7） |
| T3 | 资源耗尽（死循环/内存/输出洪泛/递归编排） | 墙钟 + 内存 + 输出字节 + 调用次数 + 嵌套深度=0 五道记账，超限即杀树 | 无 |
| T4 | 数据外泄（脚本把上下文发到公网） | 白名单不放网络工具；node `--permission` 默认拒绝网络（需 `--allow-net`，见 §2 的版本探测） | 旧版 node 没有该旗标 ⇒ 直接不跑（fail-closed） |
| T5 | 提示注入（工具结果里夹指令让脚本继续越权） | 工具结果只是数据；脚本动作仍受白名单与次数上限约束 | 语义层风险（模型自判） |
| T6 | 编排自激（脚本再编排、无限分身） | `spawn` 只允许深度 1 且计入 `max_subagents`；脚本工具**不在**自己的白名单里 | 无 |

## 2. 运行时：独立子进程（不是线程、不是 eval）

- **语言**：JavaScript（E4-1 明确要 JS 模板路径）。运行时 = 本机 `node`（实测 v25.8.1 可用），
  **可选依赖**：缺失时回可执行提示（`需要 Node.js（建议 ≥ 24）`），**绝不**降级成 `eval`/`exec` 在服务进程内跑。
  理由同 pywinpty（口径：不静默降级，管道/eval 不是同一能力）。
- **进程形态**：`node --permission --allow-fs-read=<run_dir>,<entry.js> --allow-fs-write=<run_dir>
  --no-warnings <runner.js>`，stdin/stdout 走 JSONL（每行一个消息），stderr 只做日志。
  入口先写 `data/orchestration/<run_id>/main.mjs`（常量目录 + fs_fence），再起进程。
- **权限模型实测（2026-11-27 本机 Node v25.8.1）**：`--permission` 下
  `fs.readFileSync('.env')`、`child_process.execSync`、`http.get(...)` **三者都是 ERR_ACCESS_DENIED**
  —— 即网络也在权限模型内（需显式 `--allow-net` 才放行）。**但 `--allow-net` 是较新版本才有的旗标**：
  启动时探测（`node --help` 是否含 `--allow-net`），缺失 ⇒ 视为**没有网络围栏**，默认拒绝运行
  （fail-closed，回 `no_net_fence`），要跑必须 Owner 显式打开 `CP_ORCH_ALLOW_NO_NET_FENCE`。
- **为什么独立进程**：① 崩溃/死循环不会拖死后端（配合 `proc_tree` 杀树）；② 内存上限可交给 OS
  （Windows Job Object / POSIX `RLIMIT_AS`）；③ 权限模型、cwd、env 是进程级设置，进程内做不到。
- **不做的**：不引入容器/VM；不把 node 装进 requirements（只在文档与启动报错里给安装命令）。

## 3. 工具白名单与调用协议（安全的核心）

- **谁执行工具**：宿主。脚本的 `tools.call(name, args)` 只写一行 JSON 到 stdout：
  `{"t":"call","id":7,"name":"read_file","args":{...}}`；宿主校验后执行，把结果作为一行回写 stdin。
  脚本侧 API 是 runner 提供的**冻结对象**（`Object.freeze`），没有 `require`、没有 `process`。
- **白名单 = 交集**（fail-closed，任一为空则该调用被拒）：
  1. 该 run 的 `line` 装配集（`agent.lines.assembler`，与 `fan_out` 同源）；
  2. E4 静态允许清单（只读为主；`write_file`/`shell` 默认不进）；
  3. 用户显式勾选（UI 未落地前 = 请求参数 `allow_tools`，且仍受 1∩2 约束）。
- **永远拒绝**：`govern` 平面（`ext_install`/`generate_tool`/`connect_mcp`/`schedule_*`）、
  编排工具自身、`terminal`（PTY 会绕过命令沙箱）。
- **每次调用仍过既有闸门**：权限预设 `is_confined()`、`needs_approval`（高危转审批挂单，脚本阻塞等结果
  或直接 `denied`，二选一由开关决定）、限流、审计（`usage_log.record_tool` 在真实执行点）。
- **结果上限**：单次结果 > `CP_ORCH_RESULT_CHARS`（默认 8k）截断并标记；总输出 > spill 阈值走 spill。

## 4. 资源上限（五道账 + 嵌套=0；默认值即上限，越界杀树）

| 维度 | 默认 | 上限 | 记账点 |
|---|---|---|---|
| 墙钟 | 120s | 600s | 宿主计时 → `proc_tree.kill_tree` |
| 内存 | 512MB | 2GB | Win Job Object / POSIX `RLIMIT_AS` |
| stdout+stderr | 1MiB | 8MiB | runner 侧 + 宿主侧双计（防绕过） |
| 工具调用次数 | 50 | 200 | 宿主逐次计数（不是脚本自己数） |
| 子代理 | 8 个 / 并发 4 | 16 / 8 | 复用 `fan_out` 的 clamp |
| 嵌套 | 0（脚本里不能再编排） | 0 | 白名单不含编排工具 |

另：cwd 固定 `run_dir`；env 只给 `PATH/TEMP/SystemRoot`（Windows）等最小集；`stdin` 只在协议内使用。

## 5. 状态保留（E4-2「PTC」的口径）

- **一次 run 内**：脚本变量天然保留（同一进程），这就是「程序化调工具保留状态」的实质；
  不要把"跨轮次保留"混进来。
- **跨轮次**：暂不做。若以后要做，只允许显式的 `state.json`（run_dir 内、fs_fence 保护、TTL 24h），
  **不**保留活进程 —— 活进程跨轮次 = 又一条绕过超时与回收的常驻通道。
- 会话级隔离：run 记录 `session_id`，结果面按会话过滤（同 `/api/background/tasks` 口径）。

## 6. 审计与可观测

- `orchestration_run`（run_id / line / 白名单大小 / 上限快照 / 结果 ok+退出码+耗时）；
- `orchestration_tool_call`（name / args 摘要长度 / 结果字节 / 耗时 / 是否被拒及原因码）；
- **不记**脚本源码与完整 stdout（只记 digest + 长度，同 PTY 口径）；stderr 尾部进结果（截断）。
- 失败码（回给模型与 UI 的稳定 code）：`disabled / no_node / denied_tool / cap_calls / cap_output /
  cap_memory / timeout / crashed / not_allowed_network`。

## 7. 失败姿态与「做不到的边界」（如实写）

- 开关 `CP_ORCH_SCRIPT_ENABLED` **默认 0**；`CP_ORCH_NODE_PATH` 可指定解释器；node 缺失 ⇒ `no_node`。
- 超时/取消/崩溃：杀整棵树 + 回收 run_dir 权限 + 保留 `stderr` 尾部证据。
- **不是安全沙箱**：node `--permission` 是**能力削减**，不防引擎 0day；网络是否被拦取决于运行时版本
  （见 §2 的 `--allow-net` 探测），**没有围栏时默认拒绝运行**。真要硬隔离仍只能靠 OS 级
  （防火墙/容器/低权限账户），本仓当前**没有**；实现时必须把这句写进工具说明与 UI。
- 回滚：关开关即回到「没有编排能力」；已产生的 run 记录留在 `data/orchestration/`（可清理，不影响对话）。

## 8. 判据（实现完成时逐条验）

1. 开关关：工具调用回 `disabled`，**不 spawn**、不写 run_dir（测试断言）。
2. 白名单：`shell_execute`/`write_file`/`ext_install` 在默认配置下一律 `denied_tool`；
   越权尝试计审计。
3. 上限：死循环 120s 内被杀（`timeout`）；输出洪泛触发 `cap_output` 且进程被收；
   调用第 51 次回 `cap_calls`；内存压力触发 Job Object/rlimit 终止（平台各一条）。
4. 协议：脚本拿不到 `require/process`；只能发 `call`；未知工具名回 `denied_tool`。
5. 审计：一次 run ≥3 条事件（run / tool_call / exit），工具台账不重复计数（真实执行点只记一次）。
6. 派生：新工具（若新增 `run_orchestration_script`）同批改 6 处计数契约 + 主线 boost + 干净 worktree 派生；
   新 env 全部登记 `registry.py`（`scan_settings --check` 零缺口）。
7. 前端：若暴露「编排运行」面板，路由同批有引用；否则**不建**路由（口径 §11）。

## 9. 分期与不做

- **第一期（E4-1）**：一次 run 内 `tools.call` + `spawn`（fan_out）+ 五道上限 + 审计 + 开关。
- **第二期（E4-2）**：run 内多步保留变量（同一进程）、`checkpoint` 只读投影、结果面。
- **不做**：跨轮次活进程、容器/VM、脚本内直接网络、脚本内 `require` 任意模块、嵌套编排。

## 10. 决策（2026-11-27，Owner 授权按推荐拍板）

| # | 决策 | 理由 |
|---|---|---|
| 1 | **接受 Node.js 作为可选运行时**；缺失回 `no_node`，不降级成 eval/exec | 与 pywinpty 同口径（不静默降级）；CI 不需要 node |
| 2 | **网络 fail-closed**：启动探测 `--allow-net`，缺失即拒跑；**不提供**绕过开关 | 旧版 node 没有网络围栏 = 数据外泄口子，宁可不跑 |
| 3 | **高危工具默认不进脚本白名单**；将来若要进，**整 run 一次性授权**（不做逐次弹窗） | 逐次弹窗会阻塞 JSONL 协议；整 run 授权与 fan_out 的"装配即授权"同源 |

→ 实现第一期（E4-1）可以直接按 §2–§4 开工，无需再等拍板；第二期（E4-2）在 E4-1 绿后按 §5 做。
