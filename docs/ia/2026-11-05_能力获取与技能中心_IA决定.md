## 1. 转化队列搬走、能力卡留下

**流水线视角**：摄取 → 生成草稿 → 评审 → 登记 → 启用。这是同一件事的 5 段，
目前被切在 3 个地方（能力获取页 / 技能中心弹窗 / 工具页·工作流页）。
第 3 段（登记）与第 4 段（启用技能）原本挂在技能中心的弹窗里 —— 也就是
"从外面拿进来的东西"的收尾动作跑到了"我已有的技能"的管理页去点，这违反单一入口。

⇒ **转化队列进「能力获取」**（同一组件 `embedded` 渲染，不复制实现），
技能中心只留一句去处说明 + 深链 `?panel=ingestion&tab=queue`。

**为什么能力卡不搬**：能力卡回答的是"我现在**有什么**能力"（46 条 LLM 技能 + 101 项元生功能，
按 L1 卡片列出触发/步骤/参数/示例）。它是**盘点与注入依据**，属管理面；
获取面回答的是"从外面**拿什么进来**"。两者同页会把"已有"和"新来"混在一张表里。

如果将来觉得能力卡的位置仍然别扭，正确的合并方向是
**「全景看板 → 平台能力」**（那里已经在做"功能单位 / 工具 / 调度"的盘点），
不是并入能力获取。这一条留作后续，不在本决定内。

## 2. 入轨助手：能整合，但要按"仓库化"语义收

现状（`SkillIntakeDialog`）：一个独立弹窗，列出 46 条技能的 tracked 状态，逐条"入轨 / 入轨并建 PR"。
46/46 已入轨 ⇒ 这个弹窗日常是**空转**的，只在新增技能后 1 次有用。

建议收敛（下一轮）：
1. 技能表加"未入轨"徽章（0 条时不渲染入口，避免空转）；
2. 行内"更多操作"里加「入轨 / 入轨并开 PR」（真正需要它的时刻就在那一行）；
3. 弹窗降级成"批量入轨"——只在有未入轨项时出现。

不并进能力获取：入轨是"把**已有**技能写进 git"，属仓库化，不属获取。

## 3. 批量获取：从来没有 batch 接口，是被收敛掉的旧入口

证据：`plugins/ingestion.py` 全历史没有 batch 端点（pickaxe `-S batch` 为空）；
真正的"批量"是 `claude_import.scan_claude_skills` 的一次性全量导入，
在 2026-10 的「单一获取入口」收敛（#1250）里随旧导入器一起下线；
S5 又把落库改成 `draft_only`，于是只剩"一条一条点"。

本轮恢复的批量**不是**老的全量导入，而是：
- 候选列表多选（上限 20）→ 逐条 `preview` + 逐条 `commit(draft_only=true)`；
- 需 LLM 重写的候选**跳过并记账**（批量不代跑 LLM，避免一次点出 20 次模型调用）；
- 不安装、不注册、不启用；登记与启用仍在转化队列；
- 不新增后端端点（避免第二个批量入口）。

## 4. 三种"生成草稿"入口：确实冗余，但冗余在**语义**不在按钮

现状三条路，落库语义各不相同（这是真问题）：

| 入口 | 产物 | 台账 | 是否可直接生效 |
|---|---|---|---|
| 能力获取（摄取） | 隔离区草稿 | `data/transforms/jobs.json` | 否 |
| 技能中心「从对话要求生成」 | 草稿 + 自动评审 | 部分 | 否 |
| 能力获取「从记忆生成技能草稿」(`MemorySkillAbstractor`) | **直接写技能库**（`auto_register`） | **无** | 是 |

⇒ 你的判断是对的：**应当统一成"学习 → 草稿队列（注明 source=learning）→ 转化"**。
但有两处必须收紧，否则会把"自动化"变成"自动污染"：

1. **生成端只准出草稿**：`memory_abstractor` 加 `to_queue=True`，草稿进同一台账
   （`source=learning:memory`），删掉面板上的"自动注册"勾选；
2. **转化端自动最多到 `registered`**：启用会改变模型每次看到的内容，必须保留人工确认
   （或灰度 + 回滚开关）。"自动启用"不做。

落地顺序（下一轮）：① 抽象器写台账 + 去掉直接注册；② 台账 UI 按 source 分组显示"来自学习"；
③ 定时学习任务（复用现有 learning scheduler）产出草稿，默认 dry_run。

## 5. 技能中心的"操作"逐项判

保留（这些动作离开这一页就没有等价物）：
- **启用/停用**（唯一双写点：文件轨 `enabled` + 主轨 `set_enabled`，带审计/回滚）；
- **版本与回滚**（升级小/中版本、回到任意版本）；
- **评审-评估 / 建议 / 再定义**（LLM 或规则起草中文说明，差异预览后应用）；
- **冲突自动处置、登记仅运行时技能为资产、删除、导出审计**；
- **能力卡**（见 §1）。

下掉或迁移：
- **从对话要求生成** → 与"能力获取 → 立即生成"重复，按 §4 统一到获取面；
- **新建技能（手写）** → 保留但降级为次要入口（真需要手写的人不会找不到）；
- 页面定位从"生成 + 管理"收成"**管理**"，所有"造东西"的动作指向能力获取。

## 6. software_search / install / list / uninstall：不恢复原样

证据（2026-09-17，`36e4a09b1`）：退役原因写得很清楚 ——
底层 `SoftwareManager` 是**空壳**，`install()` **恒返回 True**，会**谎报安装成功**。
这类工具比"没有这个工具"更糟：模型会据此认为软件已装好并继续下一步。

如果确实需要"装软件"（例如为了 nest CLI / 本机依赖），要做的是**新通道**，不是复活空壳：
1. 真实安装器（winget / choco），拿退出码；
2. 事后**探测**（命令是否存在 + 版本号），探测失败就如实报失败；
3. 白名单源 + 显式确认 + 审计（装软件是改机器状态，等同 medium 风险动作）；
4. 先以**工具草稿**入轨 → 审批 → 启用（走既有工具治理，不新开旁路）。
