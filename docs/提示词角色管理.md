## 0. 这份文档要解决什么

云枢的系统提示词此前是**一个模板 + 多处在外部裸拼字符串**：

    template.format(...)            # agent/orchestrator/orchestrator.py::_call_llm
    + "\n\n" + _ctx_extra           # ContextAssembler 旁路注入
    + "\n\n" + extra_material       # 工作流层工具执行素材

拼接顺序由**代码位置**决定，而不是由声明决定。于是三个问题没人答得上来：

| 问题 | 答不上来的后果 |
| --- | --- |
| 谁**拥有**这段文本？ | 改了不该改的段落，责任人查不出来 |
| 它**能不能被裁**？ | 预算一超限就"静默少一段"，没人知道少的是身份还是素材 |
| 它**为什么没进**最终提示词？ | 丢弃没有记录，无法审计 |

本次改动把这三问答成**数据**：角色词表（`PROMPT_ROLES`）+ 合并器（`compose_fragments`），
并把此前残留的**死字段** `LineProfile.prompt_note` 真正接到运行时（见 §4）。

## 1. 角色词表与职责

角色 = 片段的"拥有者"：**这段提示词归谁管、谁有权改**。
它和 [agent/prompt_manager/storage.py](../agent/prompt_manager/storage.py) 的 `PromptType`
（system/user/tool/skill/template/chat，"这段提示词**是什么**"）是**两个正交维度**：
一条记录可以同时是 `prompt_type=system` + `owner=line`（主线片段模板）。

词表顺序即默认输出顺序（= 前缀缓存顺序：越靠前越稳定）：

| # | 角色 | 语义 | 权威来源 | 谁有权写 | 可裁剪 |
| --- | --- | --- | --- | --- | --- |
| 1 | `system` | 系统骨架：本体身份与核心原则 | [agent/system_prompt_manager.py](../agent/system_prompt_manager.py) + [data/system_prompt.txt](../data/system_prompt.txt) | 仓库维护者 | ❌ 硬片段 |
| 2 | `persona` | 数字生命人格层：身份叙述与表达要求 | persona 包 + [agent/digital_life_persona.py](../agent/digital_life_persona.py) | 人格子系统 | ❌ 硬片段 |
| 3 | `line` | 主线片段：本 Agent 的身份边界与交付纪律 | [data/agent_lines/engineering.yaml](../data/agent_lines/engineering.yaml) 等 | 装线的人（UI / YAML） | ❌ 硬片段 |
| 4 | `skill` | 技能指令：本轮命中技能的操作指引 | agent/skills_mgmt | 技能子系统 | ✅ |
| 5 | `tool` | 工具/技能状态行：如实告诉模型看得见哪些工具 | 工具注册表 + 主线装配 | 工具子系统（编排器只决定暴露与否） | ✅ |
| 6 | `memory` | 记忆线索：历史摘要 / 长期检索 / 工作记忆 | memory 层 + [agent/context/assembler.py](../agent/context/assembler.py) | 记忆子系统 | ✅ |
| 7 | `task` | 本轮任务素材：旁路注入 + 工作流工具结果 | 编排器当轮调用点 | 编排器（每轮重建，不跨轮缓存） | ✅ |

**硬片段的判据不是"重要"，而是"丢了就不再是同一个 Agent"**：

- `system` 丢了 ⇒ 没有本体身份；
- `persona` 丢了 ⇒ 人格/表达要求断层；
- `line` 丢了 ⇒ 本线**自称**的身份边界与真实能力边界不一致（说一套做一套）。

> 新增角色：改 `roles.py::PROMPT_ROLES` / `ROLE_SEMANTICS` / `HARD_ROLES`，
> 并在本文档 §1 补一行、在 [tests/unit/test_prompt_roles.py](../tests/unit/test_prompt_roles.py) 补用例。
> 未在词表内的角色会被 `PromptFragment` **直接拒绝**（封闭词表，防止拼错静默生效）。

## 2. 片段、来源与优先级

片段是 `PromptFragment`（frozen dataclass）：

| 字段 | 含义 |
| --- | --- |
| `role` | 拥有者，必须是 `PROMPT_ROLES` 之一 |
| `content` | 正文。原样拼接（不 trim）；全空白会被丢弃 |
| `priority` | 排序键，**越小越靠前**，默认 `DEFAULT_PRIORITY = 50` |
| `source` | 人读来源，如 `line:engineering` / `context_assembler` / `workflow_material` |

### 排序规则（确定性）

按 `(priority, role 词表序号, 传入顺序)` 稳定排序，**绝不依赖 dict/set 迭代顺序**。

需要精确理解"确定"到什么程度：

- priority 或 role 不同的片段：**打乱输入顺序，输出逐字相同**；
- `(priority, role)` 完全相同的多个片段：按**传入顺序**排 —— 这是刻意契约
  （同一角色内保持调用点的因果顺序，例如两条 `task` 素材），
  此时打乱输入顺序输出会跟着变，不属于"不确定"。

判定标准只有一条：输出**只**由 `(priority, role, 传入顺序)` 决定。

### 当前生产来源

| 来源 | 角色 | 落点 | 实现 |
| --- | --- | --- | --- |
| 生效主线的 `prompt_note` | `line` | 模板之后（尾部） | `prompt_builder.line_prompt_fragment()` |
| ContextAssembler 旁路注入 | `task` | 模板之后（尾部） | `orchestrator._context_assembler_extra()` |
| 工作流层工具执行素材 | `task` | 模板之后（尾部） | `orchestrator._call_llm(extra_material=...)` |
| 工具状态文本 | `tool` | 模板槽位 `{tool_status}` | `_build_tool_status_text()` |
| 技能指令 | `skill` | 模板槽位 `{skill_instructions}` | `_build_skill_instructions()` |
| 记忆线索 | `memory` | 模板槽位 `{memory_context}` | memory / lifetrace |

有槽位的角色（tool/skill/memory）**不进尾部**（否则同一段文本会被注入两次）；
无槽位的角色（system/persona/line/task）只能追加在模板之后。
模板结构与槽位名**未改动**（`## 核心原则` / `## 记忆线索` / `【工具】` 等标记仍在）。

## 3. 预算与裁剪规则

### 3.1 系统提示词的预算权威只有一个

`build_system_prompt` / `_call_llm` 里既有的 **10000-token 检查**仍然是唯一权威，
口径**未放宽**：

- 超限 ⇒ `{tool_status}` 截到 300 字符 + `"...（已截断）"`，`{skill_instructions}` 置空；
- `_call_llm` 路径上，改动前被这条路径丢弃的"尾部素材"
  （`_ctx_extra` / `extra_material`）今天**同样被丢弃** —— 行为不变；
- **唯一新增**：`role=line` 属硬片段，在这条截断路径上仍然保留
  （丢掉它会让本线自称的身份边界与真实能力边界不一致）。
  未装线时该分支产出空串，因此**与改动前逐字一致**。

### 3.2 `compose_fragments` 的预算裁剪是给"自带预算的调用方"的能力

    compose_fragments(fragments, budget_tokens=..., counter=...)

- `budget_tokens is None`（**提示词主链路的选择**）⇒ 不做任何裁剪；
- 给了预算且超限 ⇒ 按**输出顺序的逆序**逐个丢弃**可裁剪片段**，每丢一个重新计数；
- 硬片段（`system` / `persona` / `line`）**绝不裁**；预算仍不够时
  `overflow=True` 如实上报，内容一个字符都不动；
- 不做**部分截断**：整片段进、整片段出。

**为什么主链路不用它**：两套预算会在同一段文本上互相打架（一个丢片段、一个截字段），
超限时到底少了什么将无法解释。所以 `prompt_builder` 调 `compose_fragments` 时
**一律不传 `budget_tokens`**。这条关系写在 `prompt_builder` 的模块 docstring 里。

### 3.3 丢弃必须可审计

`ComposedPrompt` 的字段：

| 字段 | 含义 |
| --- | --- |
| `text` | 最终文本 |
| `parts` | 进入 text 的片段（输出顺序） |
| `dropped` | 被丢弃的片段 + 原因（`empty` / `budget`），可审计 |
| `tokens` / `token_source` | token 数 + 是"真 counter"还是"粗估" |
| `overflow` | 硬片段本身就超预算（已无片段可裁） |

丢弃**不许静默消失**：空片段进 `dropped(reason=empty)`，预算裁剪进 `dropped(reason=budget)`。

## 4. `prompt_note` 接线语义（含"此前是死字段"的说明）

### 4.1 诚实记录：这个字段此前没有被任何一处消费

`LineProfile.prompt_note`（[agent/lines/models.py](../agent/lines/models.py)）此前的状态是：

- UI（[yunshu-ui/src/pages/hub/tools/lines.tsx](../yunshu-ui/src/pages/hub/tools/lines.tsx)）写着
  "随本线注入的系统提示词片段（可留空）"；
- [data/agent_lines/](../data/agent_lines/) 的档案里**每一条线都填了内容**；
- REST 层能存取它；
- **但运行时没有任何一处读它** —— 系统提示词里从来没有出现过这些片段。

也就是说：UI 的承诺与运行时不一致，用户填了却没有任何效果。本次改动把它接上，
UI 的承诺才成立。本节的接线语义即为该字段的**权威定义**。

### 4.2 取用链路（只读、惰性 import、绝不抛）

    prompt_builder.line_prompt_fragment(line_id=None)
      → agent.lines.resolve_line_id()             # 显式 > 全局激活指针 > None
      → agent.lines.get_line_registry().load(id)  # 读 data/agent_lines/<id>.yaml
      → profile.prompt_note.strip()
      → PromptFragment(role="line", content=note, source="line:<id>")

`agent.lines` 在**函数内**惰性 import（不在模块级建立依赖边）；
任何异常都被收口为"返回 None"并留一条 WARNING 结构化日志，
**绝不抛、绝不打断对话**。

### 4.3 注入位置与两条 LLM 路径

片段追加在"模板渲染（+ 工作记忆文本）"之后，用 `"\n\n"` 连接：

- `_call_llm`（标准路径）：`role=line` + `role=task`(旁路) +
  `role=task`(工作流素材) 一次合并；预算超限时按 §3.1 处理；
- `_call_llm_v2`：同样一次合并。persona 分支与模板分支共用这段尾部代码；
  该路径今天**没有** system prompt 的 token 预算检查，故**不新增**（保持原样）。

两处都留 `action=orchestrator.<方法>.line_prompt_note` 的 INFO 日志，
内容形如 `[主线] 已注入 prompt_note 片段: line:engineering（68 字符）`。

### 4.4 前端渲染口径（后端提供数据，前端不自己判）

装配预览要显示"本线会注入什么片段"时，**数据由后端给**，前端不要自己再判一遍 ——
前端判一遍就等于出现第二份"什么会被注入提示词"的口径，和系统提示词的真实组装
结果迟早分叉（与本仓库"装配结果由后端算"的既有纪律同源）。

两个端点（`POST /api/agent-lines/preview`、`POST /api/agent-lines/validate`）
在原有字段之外**新增**两个字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `prompt_fragments` | `list[dict]` | 该档案会注入系统提示词的片段（当前只有 role=line）。每项：`role` / `source`（`line:<id>`）/ `content`（片段原文）/ `chars` / `priority` / `croppable`（role=line 为 `false` = 硬片段） |
| `prompt_fragments_note` | `str` | 片段为空时的人读原因（"prompt_note 为空 ⇒ …与未装线时逐字一致" / "本线已停用…"）；有片段时为空串 |

两个端点给的是**同一份**判定（与 `skills` 字段同一纪律），判定实现即
`prompt_builder.line_fragment_for_profile` —— 与运行时装配共用同一个函数。

**是否真的会注入**还需两个前端已掌握的事实组合判断，故不塞进响应里：

- 这条线是不是当前激活线 ⇒ `GET /api/agent-lines` 的 `active` 字段；
- 保存内容是否与预览的草案一致 ⇒ 前端手里的 draft/`dirty` 状态。

片段信息本身取不到（判定实现抛异常）时**降级**：`prompt_fragments` 为空列表、
`prompt_fragments_note` 写明"已降级"，**预览本体照常返回**（HTTP 200）。

## 5. 未装线回退口径（未装线 = 没改过）

| 情形 | 行为 | 依据 |
| --- | --- | --- |
| 没有激活指针、也没显式指定 | `line_prompt_fragment()` 返回 `None` ⇒ 不注入 | `resolve_line_id()` → `None` |
| 档案不存在 | 同上 | `registry.load()` → `None` |
| 档案存在但 `enabled: false` | 同上（**停用线按未装线处理**） | 与 `assemble_for_line` 同口径 |
| `prompt_note` 为空 / 全空白 | 同上 | `note.strip()` 为空 |
| 档案损坏 / 读取异常 | 降级 + WARNING 日志 ⇒ 不注入 | `except Exception` 收口 |

上表每一情形都对应 [tests/unit/test_prompt_roles.py](../tests/unit/test_prompt_roles.py) 里一条用例，
其中"未装线"与"档案损坏"两条会断言**最终系统提示词与改动前逐字一致**。

## 6. 拥有者维度（registry / storage）

拥有者落在 `metadata["owner"]` 里 —— **零 schema 迁移**：
`metadata` 列本就是 `TEXT DEFAULT '{}'` 的 JSON 袋，加一个键不需要 `ALTER TABLE`。
回滚路径 = 不再读这个键，老库老行（无 `owner`）读出来就是"未声明拥有者"（空串），
**不默认归给任何角色**。[tests/unit/test_prompt_roles.py](../tests/unit/test_prompt_roles.py)
用 `PRAGMA table_info` 钉住"表里没有 owner 列"。

接口：

    PromptRegistry.register_prompt(..., owner: str = "")            # 写 metadata["owner"]
    PromptRegistry.update_prompt(prompt_id, owner=...)              # 换责任人；传 "" 撤销
    PromptRegistry.list_prompts(prompt_type=None, tags=None,
                                limit=100, offset=0, owner=None)    # 形状与既有口径一致
    PromptRegistry.list_prompts_by_owner(owner, prompt_type=None,
                                         tags=None, limit=100, offset=0)
    PromptMetadata.owner                                            # 元数据里也带出来
    PromptStorage.list_prompts(..., owner=...)                      # keyword-only

口径说明（诚实版）：`owner` 与 `tags` 一样在**存储返回的窗口内**做 Python 过滤
（JSON 袋在 SQLite 里没有索引），因此**不是精确分页**。提示词是小基数数据
（本仓 < 100 条），实践上等于全量过滤；条数涨上去时应调大 `limit`
或另立索引列（那是需要迁移的另一件事）。词表外的 `owner` 只**告警不拒绝**
（数据不因词表更迭而丢失）。

## 8. 边界与未做（避免过度承诺）

- **不改** [data/system_prompt.txt](../data/system_prompt.txt) 的槽位名与模板结构，
  也不放宽既有 token 预算；
- 合并器**不做部分截断**：要么整片段进，要么整片段出（"截到 300 字符"这类
  具体降级形态留在系统提示词自己的预算权威里）；
- 主线档案**每轮读取**（与工具装配同频），没有额外缓存层；
  档案是 ~1KB 的本地 YAML，若将来放大需要另做缓存；
- UI 的 role=line 区块**不由本变更实现**：后端只负责在
  `/preview`、`/validate` 的响应里给出 `prompt_fragments` /
  `prompt_fragments_note`（见 §4.4），渲染与前端用例归前端线；
  `yunshu-ui/` 下没有任何改动来自本变更；
- 其余角色（`system` / `persona` / `skill` / `tool` / `memory`）
  的**生产来源未改动**，本次只是把它们纳入同一套词表与合并入口。
