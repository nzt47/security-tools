# 技能转化器（Skill Transformer）设计草案

> 2026-11-01 · 起因：Owner 提「做一个技能转化器，对外来的技能进行去重合并优化合规安全审核，转化为 Agent 自身能力」。
> 本文是**方案**，不是已实现代码；P0 的前置（入轨一条龙）今天已落地。

## 0. 一句话

把「外来技能」（吞噬来的 md / 目录 / 压缩包 / 仓库）经过 **规范化 → 去重合并 → 优化 → 合规安全审核 → 能力化** 五段流水线，
变成**云枢自己的能力**（文件轨 + 主轨 + 能力清单 + 审计 + 可回滚），人只在三个决策点上拍板。

## 1. 现状与痛点（都有实测数字）

| 现象 | 实测 | 问题 |
|---|---|---|
| 同源技能散落 | 文件轨 46 条里 **15 条 pd-***（superpowers 系列） | 没有去重/合并，检索时互相抢召回 |
| 外文长文直接进库 | gstack 48.5 KB、gh-cli 39.9 KB | 一次检索塞进上下文，挤掉别的内容；没有能力卡提炼 |
| 来源字段五花八门 | external_agent / ingestion:trae / file_track_backfill / intake | 没有统一溯源，回滚时说不清「它是从哪来的」 |
| 审核全靠人眼 | 只有零散的凭据扫描（is_credential_path） | 没有危险指令 / 许可 / PII 的统一拦截 |
| 入轨曾靠命令行 | 今天之前要手工 6 步 | 已解决：intake_skill.py + UI 一条龙（#1388） |

## 2. 流水线（五段 + 一个决策闸）

```
外来技能 ──► S0 采集 ──► S1 规范化 ──► S2 去重/合并 ──► S3 优化(能力卡) ──► S4 合规安全 ──► S5 能力化 ──► PR
              │            │               │                 │                  │
           来源适配器    9 键补齐/裁剪    相似度+策略     引用原文的提炼      证据行号
```

| 段 | 做什么 | 关键约束 | 失败策略 |
|---|---|---|---|
| **S0 采集** | 适配 claude / trae / zip / URL / git；产出 artifact（原文 + 来源 + 内容 hash） | **同 hash 幂等**：重复导入直接返回既有 transform，不新建 | block |
| **S1 规范化** | 复用 intake_skill.fix_front_matter（9 个必填键）；标题层级、代码块语言、去 HTML 注释；超 N KB 走「原文存档 + 摘要卡」 | 只补**可确定性推导**的字段，不翻译不编造（与今天的入轨口径一致） | block |
| **S2 去重/合并** | 三层判定：① id/name 精确；② description 向量相似；③ 正文 MinHash/embedding 相似。产出 keep-separate / variant / merge / overlay 四选一 | **合并只允许逐段保留 + 冲突显式列出**，禁止「摘要式合并」（会吃掉独特内容） | 交人决策 |
| **S3 优化** | 提炼能力卡：触发条件 / 步骤 / 参数 / 示例 / 反例 | LLM 生成的每一条**必须引用原文片段**（行号 + 逐字），引用对不上即判失败 | 降级为「不提炼」，只登记原文 |
| **S4 合规安全** | 许可（license）、凭据/PII、危险指令（rm -rf / curl 管道执行 / 提权）、外部脚本 URL、内容政策 | 每条发现带**文件 + 行号 + 证据片段**，不许写「疑似」 | block / warn |
| **S5 能力化** | 写 data/skills_repo/<id>/ + 主轨登记 + 重派生清单 + 刷基线 + 审计 + 回滚凭据 | 复用今天的 intake_one + open_pr；H-3 两条仍然 409 | block |

## 3. 数据模型与幂等

```
data/ingestion/transforms/<transform_id>/
  manifest.json     # 源、内容 hash、各阶段产物路径、决策、审核结论、时间线
  raw.md            # 原文（不进 git）
  normalized.md     # S1 产物
  dedupe.json       # 相似候选、分数、选中策略与理由
  card.md           # S3 能力卡（含逐条引用锚点）
  review.json       # S4 发现（rule/file/line/evidence/verdict）
  diff.patch        # 与目标技能的合并 diff
```

- **幂等键** = sha256(raw)；同一 hash 二次导入直接复用 transform。
- **审计事件**：skill.transform.plan / .apply / .rollback，都带 transform_id。
- **回滚**：transform_id → 反向补丁 + 审计；不做「删目录」式回滚。

## 4. 只保留三个人工决策点

1. **合并冲突**（相似度 0.6–0.85）——自动只给建议，人选 merge / keep / variant；
2. **安全审核的 warn**（block 直接停，不需要人）；
3. **入轨 PR 的最终合并**（CI 绿了也由人点，这是最后一道闸）。

## 5. 接口

```bash
# 只读计划：相似候选 + 审核发现 + 能力卡草案，不写仓库
python scripts/skill_transform.py --plan data/ingestion/inbox/xxx.md
# 应用：落 transforms/、写技能目录、（可选）直接开 PR
python scripts/skill_transform.py --apply <artifact> [--merge-with <id>] --pr
```

| API | 用途 |
|---|---|
| POST /api/skills-mgmt/transform/plan | 只读分析，返回相似候选 + 审核发现 + 卡片草案 |
| POST /api/skills-mgmt/transform/apply | 落盘 + 能力化（open_pr 可选） |
| GET  /api/skills-mgmt/transform/status | 队列与逐阶段进度 |
| POST /api/skills-mgmt/transform/<id>/rollback | 按 transform 回滚 |

UI：吞噬页新增「转化队列」——每个 artifact 一张卡，左相似建议、右审核发现、下能力卡预览与 diff。

## 7. 分阶段（每阶段可独立上线）

| 阶段 | 内容 | 判据 |
|---|---|---|
| **P0 今天 ✅** | 入轨一条龙（自动补全 + git add + 派生 + 基线 + commit/push/PR） | 已上线并部署（#1388） |
| **P1（1 个 PR）** | skill_transform.py --plan：**只读**分析（去重候选 + 安全审核 + 卡片草案），不写仓库 | 跑 pd-* 15 条能聚成 1 组并给两两分数；gh-cli 能给出裁剪建议 |

| **P4** | LLM 能力卡（严格引用校验） | 卡片每条都能指回原文行号；引用对不上即降级 |

## 8. 风险与反例（提前写死，避免走偏）

1. **别用摘要替换原文**：合并/提炼的产物另存，原文永远留档（transforms/<id>/raw.md）——回滚与追溯都靠它；
2. **别让 LLM 决定「能不能进」**：审核用**规则 + 证据行号**，LLM 只在 S3 提炼阶段用，且必须逐条引用；
3. **别把大文件塞进 git**：raw.md 不进 git，git 只放能力卡 + 摘要 + sha256；
4. **别自动合并高相似但语义冲突的技能**（例如两条「代码审查」步骤相反）——相似度只用于**排序建议**，不是判决；
5. **别绕过 H-3**：global-core-principles / skill 一律只留主轨，转化器对它们直接 409。
