# 特性开关规范（Feature Flag Standard）

> **归属**：`TASK-03 第 6 步` 交付物 · **状态**：已定标准 + 已落地骨架 · **日期**：2026-09-18
> **适用**：`TASK-04` ~ `TASK-08` 全部阶段（v1.4 第 14 章"每阶段特性开关 + 一键回退"的落地口径）
> **实现**：`agent/settings/feature_flags.py` · **守卫**：`tests/unit/test_feature_flags.py`

---

## 1. 为什么需要这份规范（现状不是"没有开关"，而是"开关没有骨架"）

| 事实 | 证据 |
|---|---|
| 仓库里**唯一**的特性开关是 `YUNSHU_FEATURE_SANDBOX` | `agent/settings/registry.py:505` |
| 它被 **4 处**各自解析，口径是裸的 `os.getenv(...).lower() == "true"` | `app_server.py:1481`、`plugins/system_tools.py:232`、`agent/server_routes/routes_workspace.py:172` |
| `config.yaml` 已有 `features:` 节并在使用中 | `config.yaml:196-208`：`v2_lifetrace` / `verification_enabled` / `critic_evaluation_enabled` … |
| `verification.rollout_percentage: 10` 已存在灰度先例 | `config.yaml:216-217` |
| `scripts/feature_flags.py`（有 PERCENTAGE/USER_ID/SESSION/INTERNAL 策略的 CLI）**零生产引用** | 唯一消费者是 `tests/unit/test_release_engineering.py:17`；`data/feature_flags.json` 不存在 |

**结论**：缺的不是"存储"也不是"灰度算法"，缺的是 **①统一求值入口 ②运行时可切 ③审计 ④变更成本的机械化守卫**。
本规范把这四件事定死，并**不新建第二套配置系统**。

---

## 2. 术语分界（**最重要的一条**）

| | 配置项（setting） | 特性开关（feature flag） |
|---|---|---|
| 定义 | 系统参数：阈值 / 路径 / 等级 / 端点 | 行为灰度：某个功能开不开 |
| 例子 | `ROLLBACK_SUCCESS_DROP_PCT`、`SMOKE_BASE_URL` | `capability_registry`、`tool_confirm_levels` |
| 变更影响面 | 影响**参数取值** | 影响**代码路径是否存在** |
| 典型生命周期 | 长期存在 | 阶段性的，收口后应删除 |
| 默认生效方式 | 多半需要重启（`needs_restart`） | **必须**无需重启 |

⇒ **判据（一条就够）**：*"这个开关关掉之后，用户走的是另一条代码路径吗？"*
是 ⇒ 特性开关，进 `FEATURES` 表；否 ⇒ 配置项，进 `REGISTRY`。

### 2.1 禁止事项

* ❌ **禁止**新建特性开关的存储（不得新增 `data/feature_flags.json` 之类文件）。
* ❌ **禁止**在业务代码里直接 `os.getenv("YUNSHU_FEATURE_...")`。必须走 `feature_enabled()`。
* ❌ **禁止**复活死代码 `scripts/feature_flags.py`。它的策略枚举已被本规范的设计吸收；该文件应在 `TASK-04` 起作为**待删债务**处理（见 §6）。
* ❌ **禁止**把开关值缓存在模块级常量里（会让"一键回退"退化成"重启才回退"）。

## 3. 存储与求值口径（**沿用既有设施，不另建**）

```
优先级（高 → 低）        载体                                        变更生效
─────────────────────────────────────────────────────────────────────────────
1. 环境变量              YUNSHU_FEATURE_<NAME>                      立即（每次求值重读）
2. 开关中心覆盖层        data/ui_settings.json（agent/settings/overrides.py）  立即
3. config.yaml           features.<name>                            立即（mtime 缓存失效）
4. 代码默认值            FEATURES 表里的 default                      —
```

* 载体 2/3/4 全部复用 `agent/settings/`（`overrides.py` / `resolver._config_lookup`），
  **不新增任何文件格式**；载体 1 复用既有 `YUNSHU_FEATURE_` 前缀约定（与 `YUNSHU_FEATURE_SANDBOX` 同族）。
* 灰度比例：`YUNSHU_FEATURE_<NAME>_ROLLOUT`（0–100），等价于既有
  `verification.rollout_percentage` 的口径。
* 审计：变更/求值落 `agent/audit/facade.record("feature_flag.evaluated", ...)`。
  **best-effort**：审计不可用时降级为 debug 日志，**绝不阻塞读路径**（D4）。

### 3.1 灰度分桶

```
bucket = int(sha256(f"{name}:{subject}")[:4], "big") % 100
命中   = bucket < rollout_percentage
```
* **稳定**：同一 `(开关, 主体)` 永远同一个桶 —— 否则同一租户一会儿有、一会儿没有，
  造出无法复现的 bug 报告。
* **独立**：不同开关之间分桶不相关（`sha256` 的输入含开关名），避免"命中一个就命中全部"。
* 边界：`0%` 全不开、`100%` 全开（**已实测**，见 §5.3）。

## 4. 新增一个开关的**标准流程**（4 步）

| 步 | 动作 | 文件 | 行数量级 |
|---|---|---|---|
| 1 | 在 `FEATURES` 表加一条 `FeatureSpec` | `agent/settings/feature_flags.py` | ~7 行 |
| 2 | 在 `config.yaml` 的 `features:` 段加同名布尔键（默认 `false`） | `config.yaml` | 1 行 |
| 3 | 在**真实代码路径**调用 `feature_enabled("<name>")` 分流 | 功能归属模块 | 2~4 行 |
| 4 | 跑守卫 | — | 2 条命令 |

**不需要**做的事（这正是本规范的价值）：

* ❌ 不需要为每个开关在 `registry.py` 加一行 —— 环境变量按**动态前缀族**
  `YUNSHU_FEATURE_` 一次性登记（`registry.py` 的"特性开关族"段），N 个开关共享 1 条登记。
* ❌ 不需要改 UI —— 注册表的分类/风险/生效方式已经能让开关中心展示它。
* ❌ 不需要写新的解析函数 —— 求值统一走 `feature_enabled()`。

## 5. 成本量化（**实测，不是估算**）

### 5.1 正常路径的实测成本

```
改动文件数：2（agent/settings/feature_flags.py + config.yaml）
改动行数  ：约 8 行
需要跑的守卫：2 条
    python -m pytest tests/unit/test_feature_flags.py -q      → 21 passed  (2.15s)
    python -m pytest tests/unit/test_settings_registry.py -q  → 27 passed  (40.99s)
```

**结论：新增一个特性开关 ≈ 8 行 / 2 个文件 / 约 45 秒守卫时间。**
（对比：如果为每个开关在注册表里加一条字面量 `env_name` 行，则会同时踩 §5.2 的坑。）

### 5.3 已知陷阱（**实测踩过，写进规范避免重复付学费**）

`TASK-03 §2.8` 记录了 `agent/lines/models.py::_as_bool` 因"自定义读取助手不在
`KNOWN_READ_HELPERS` 内"导致 AST 漏检、零缺口守卫**假阴性**的先例。
本次新增特性开关族时又踩到同类坑，两种写法后果完全不同：

```python
# ❌ 实测后果：读取点落进 <unresolved> 兜底桶
#    check_gaps().unregistered_dynamic == ['<unresolved>', 'YUNSHU_FEATURE_']
raw = os.getenv(spec.rollout_env_name)          # 名字是**属性访问**，AST 解析不出

# ✅ 实测后果：正确归入 YUNSHU_FEATURE_ 家族，ok == True
raw = os.getenv(ENV_PREFIX + name.upper() + ROLLOUT_SUFFIX)   # 前缀 + 名字拼接
```

**纪律**：**永远不要登记 `<unresolved>` 兜底桶** —— 它是个黑洞，任何解析不出名字的
开关都能藏进去，登记它等于把"零缺口守卫"变成"零缺口摆设"。解析不出来就改写法。

## 6. 阶段开关族（供 `TASK-04`~`TASK-08` 使用）

| 开关 | 阶段 | 默认 | 灰度默认 | 用途 |
|---|---|---|---|---|
| `capability_spec_v2` | TASK-04 | `false` | 100 | 能力规格 v2 字段集读写路径 |
| `capability_registry` | TASK-05 | `false` | 100 | 统一 Registry 生效；关闭时回落现有 YAML 扫描 + 内存 `_registry` |
| `capability_non_llm_entry` | TASK-05 | `false` | **10** | 非 LLM 入口（service_account / human 触发） |
| `tool_confirm_levels` | TASK-06 | `false` | 100 | 工具侧 L0–L3 确认分级；关闭时回落"是否挂单"二值语义 |
| `sandbox_unified` | TASK-07 | `false` | 100 | SSRF / 注入隔离 / 沙箱统一收口 |
| `hot_path_load_tool_meta_cache` | TASK-08 | `false` | 100 | `load_tool_meta()` 的 `CSafeLoader` + 缓存（P0-1 一行可修项） |

**纪律**：
1. 每个阶段**只允许开自己的那一个**开关；跨阶段依赖必须显式写成"阶段 N 的开关隐含要求阶段 N-1 的开关打开"，并在代码里断言。
2. 阶段开关默认**必须**为 `false`（已由 `test_stage_switches_default_to_off` 钉死）——
   "重构代码合并"不等于"改变现网行为"。
3. 阶段收口后（功能稳定 + 观测无异常 + 一个发布周期），**删除**开关并清理 `config.yaml` 条目；
   不要留下"永远为 true 的开关"（那只是新的死配置）。

### 6.1 尚未收口的存量（**已知债务**）

| 项 | 现状 | 处置 |
|---|---|---|
| `YUNSHU_FEATURE_SANDBOX` | 3 处直读 `os.getenv`，未走 `feature_enabled()` | 收口属业务代码改动（TASK-03 E9 越界风险），登记为债务，建议随 `TASK-07` 沙箱统一收口时一并迁移 |
| `config.yaml` 的 8 个 legacy `features.*` 键（`v2_lifetrace` 等） | 由既有代码直接读 config，未进 `FEATURES` 表 | 由 `TASK-04` 起逐步迁移；`tests/unit/test_feature_flags.py::_LEGACY_FEATURE_KEYS` 显式列出它们（避免误红），迁移后应从该集合删除 |
| `scripts/feature_flags.py` | 零生产引用的死代码（唯一消费者是一个测试） | 建议 `TASK-04` 删除（本任务不删，避免与在飞切片冲突） |
| 灰度的 "INTERNAL / USER_ID / SESSION" 策略维度 | 本骨架只实现了 `subject`（调用方传租户/会话 ID）+ 百分比 | 需要多维策略时再扩展；当前以"调用方传什么就是什么"为最小可用口径 |

## 7. 变更与回退（SOP）

```
# 打开一个阶段开关（无需重启）
$env:YUNSHU_FEATURE_CAPABILITY_REGISTRY = "true"      # 或写 data/ui_settings.json 覆盖层

# 灰度 10%
$env:YUNSHU_FEATURE_CAPABILITY_NON_LLM_ENTRY = "true"
$env:YUNSHU_FEATURE_CAPABILITY_NON_LLM_ENTRY_ROLLOUT = "10"

# 一键回退（立即生效；不需要重启，故不承担 60–90s 冷启动代价）
$env:YUNSHU_FEATURE_CAPABILITY_NON_LLM_ENTRY = "false"
```

**回退代价**：`hot`（下次求值即生效，亚毫秒）。
**唯一的例外**：若某阶段开关的接线本身发生在**进程启动期**（例如在 `app_server.py`
的模块级初始化里分流），则该开关的实际生效方式是"需重启"，**必须**在 `FEATURES`
的 `description` 里写明，并在规范里登记为 `needs_restart`——不允许默默假设它是热的。
