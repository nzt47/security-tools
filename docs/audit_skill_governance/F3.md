## 0. 一句话裁决

**方案 A：保持现状（宣告行留在稳定节）。**

理由不是"感觉影响小"，而是三条**实测**事实：

1. **(a) 生产默认路径该行逐字恒定**——同一 session 连发 3 次相同请求，
   从**真实请求的 system prompt**（不是复算）里取出的宣告行**去重后只有 1 种**（§3）。
2. **(b) 工作台 SSE 路径的提示词里根本没有这一行**——它是 75 字符的字面量提示词，
   3 次不同表述下**逐字相同**、且不含 【工具】；变化的只是请求体里的 tools 选择结果，
   而本部署有激活主线（engineering），连 tools 都不变（26 个，名字集合逐字相同）（§4）。
   ⇒ F3 当初担心的"该行逐请求变"在**两条生产链路上都不成立**。
3. **(c) 命中率对比不支持改动**——"相同请求"与"同意图不同表述"两组实测命中率
   **5.735% vs 5.039%**（Σ口径），差异来自**易变尾簇**（首个差异字符落在
   「记忆线索/最近对话」区，字符 1698–1773），**不是**宣告行（字符 689）（§5）。
   而该行在**同前缀重复调用**（工具循环）里确实落在被命中的前缀内（热态 85%–99%），
   这正是"它必须恒定"的价值所在 —— 生产上它确实恒定。

反过来说：**拿不出"该行会变"的证据，方案 B（下移到易变尾簇）的收益实测为 0，
代价却落在 4 个生产渲染点 + 4 处已登记的测试/UI 契约上**（§6）。故不采纳 B，C 亦暂不必要。

## 2. 方法：怎么拿到"实际发给模型的那个 system prompt"

**不靠复算、不靠猜。** 证据链（全部只读）：

1. agent/llm_monitor.py:834-898 的 _wrap_get_client_for_tool_calling 把
   LLMService._get_client 返回的 client 的 chat.completions.create 包了一层，
   在 finally 里用**真请求的 kwargs** 构造记录：
   :873-878  sys_prompt = messages[0]["content"]（role 必须是 system）。
2. LLMInteraction 是 dataclass（:58-116），to_dict() = asdict(self) ⇒ **system_prompt 字段就在记录里**。
3. agent/server_routes/routes_llm_monitor.py:24-49 的 GET /api/llm-monitor/records
   返回 [r.to_dict() for r in page]。
   ⇒ 只要发**真实 HTTP 请求**，再读该端点，就拿到真请求里的真提示词、真 tools、真 usage。

探针（scripts/probe_prefix_cache_interaction.py）做的就是这件事；判定标记 【工具】
**硬编码**在探针里（不 import 生产模块），避免"用被测物自证被测物"。

> 一次 /api/chat 可能产生**多条**记录（工具循环每轮一条），而这正是本卡最有价值的一段数据（§5.3）。

## 4. (b) 工作台 SSE：该行**根本不存在**（不是"变化很小"）

工作台链路 = POST /api/chat/stream → plugins/chat.py::_workbench_real_stream。
3 次同意图不同表述（卡点原文给的例子）：列出当前目录 / 看看有哪些文件 / 当前文件夹里有什么。

**实测（12 条记录，组 W）**：

| 观测项 | 实测值 |
|---|---|
| system prompt 长度 | **75 字符**（字面量，见 plugins/chat.py:1146） |
| 其中是否有 【工具】 行 | **没有**（advert_present 全为 False） |
| 3 次不同表述下提示词 sha16 | **BB4566E990397314（全部逐字相同）** |
| tools（第 0 轮） | **26 个 / 名字集合 sha16 = 7B3660D62EE68B39（逐字相同）** |
| tools（第 ≥1 轮） | 0（循环只首轮带 tools） |
| prompt/hit/miss | **0 / 0 / 0 ⇒ 流式路径未上报 usage（拿不到命中率，不是 0% 命中）** |

**为什么 tools 也不变**：plugins/chat.py:1184-1189 **先**问主线装配器
（_line_whitelist），只有它返回空（无激活主线）才会走 :1198-1204 的
hybrid_select_tools(question)。本部署有激活主线，服务端日志三条请求逐字相同：

~~~text
22:31:10 [INFO] plugins.chat.stream : [workbench][SSE] 工具集: 主线:engineering(26) -> 26 个, 15726 字符, 6757 token(cl100k)
22:31:21 [INFO] plugins.chat.stream : [workbench][SSE] 工具集: 主线:engineering(26) -> 26 个, 15726 字符, 6757 token(cl100k)
22:31:50 [INFO] plugins.chat.stream : [workbench][SSE] 工具集: 主线:engineering(26) -> 26 个, 15726 字符, 6757 token(cl100k)
~~~

⇒ **F3 的假设「工作台 SSE 路径的 hybrid_select_tools(question) 会逐请求变 ⇒ 该行逐请求变」
在本部署不成立**：该分支被主线挡在前面，而且即便走到它，它改的也是 tools=，不是提示词
（plugins/chat.py:1208 tool_defs = _get_defs(whitelist=_whitelist)）。

### 4.1 反事实（把主线关掉会怎样）——**离线用生产选择链实测**

用生产函数直接跑（探针式调用，不改配置、不发请求）：

- **选择集确实逐请求变**（25/19/25 与 9/12/18/12）⇒ F3 的担忧在"无主线 + 智能选择"那条路上**是真的**。

## 5. (c) 真实缓存命中率对比

### 5.1 两组对照（控制变量：间隔、prompt 长度一并报告）

| 组 | n | Σhit/(Σhit+Σmiss) | prompt 均值 | **调用间隔 min/mean/max** | 宣告行种数 | tools 种数 |
|---|---|---|---|---|---|---|
| **A 相同请求**（主线 /api/chat，3 次） | 3 | **5.735%**（1664/29017） | 9672 | **11.0 / 12.6 / 14.1 s** | **1** | [26] |
| **B 同意图不同表述**（主线 /api/chat，3 次） | 3 | **5.039%**（1536/30481） | 10160 | **11.0 / 11.0 / 11.0 s** | **1** | [26] |
| W 工作台 SSE（3 次） | 11 | **n/a（流式未上报 usage）** | n/a | 0.7 / 4.3 / 17.4 s | 0（无该行） | [0, 26] |

- 间隔：A 组的两次间隔是 14.1s / 11.0s，B 组是 11.0s / 11.0s —— **量级相同**，可排除"间隔差造成命中率差"。
- prompt 长度：A 组 9360–10077，B 组 9853–10427 —— **同一量级**（差 <10%）。
- **差异只有 +0.70 个百分点（5.735% vs 5.039%），方向还是"相同请求略高"**，
  而两组的宣告行**都是恒定的**。⇒ **该行不是这两组命中率的解释变量。**

### 5.2 那 5% 的命中率从哪来？（原始源直读交叉校验）

对同组相邻记录的 **system prompt 做逐字符比对**（读同一份记录端点，非复算）：

~~~text
组 A（相同请求）：system prompt 首个差异字符偏移 = 1773 / 1859
  差异上下文（A#1 vs A#2）：
    prev: …要调用任何工具，请用一句话说明前缀缓存（prefix cache）的工作原理\n\n## 最近对话\n\nsystem: 云枢已觉醒！…
    cur : …要调用任何工具，请用一句话说明前缀缓存（prefix cache）的工作原理\n\n- 不要调用任何工具，…\n\n- 不要调用任何工具，…
组 B（不同表述）：system prompt 首个差异字符偏移 = 1698 / 1698
  差异上下文（B#1 vs B#2）：
    prev: …库检索更多相关内容。\n\n## 记忆线索\n## 相关记忆\n\n- 不要调用任何工具，请一句话说明前缀缓存（prefix cache）为什么能省钱\n…
    cur : …库检索更多相关内容。\n\n## 记忆线索\n## 相关记忆\n\n- 不要调用任何工具，一句话讲讲前缀缓存（prefix cache）省钱的道理\n…
（两组的宣告行偏移都恒为 689 ⇒ 差异**全部发生在该行之后**）
~~~

- 差异点（1698 / 1773）远在该行（689）之后，落在**易变尾簇**：
  「## 记忆线索 / ## 相关记忆」会注入**本轮用户问题原文**（B 组因此比 A 组早 75 字符分叉），
  「## 最近对话」每轮追加历史。
- ⇒ **跨请求只有 512–640 token 命中**，是因为前缀在 ~1700 字符处就分叉了，
  其后（system 尾簇 + 全部 messages，约 8,700–9,400 token）**每轮都要重算**。

### 5.3 关键反证：**热态下该行确实在缓存里**（同一次请求的工具循环）

同一次 /api/chat（问题=列出当前目录，22:29:19–22:29:26）产生 4 条记录，
**4 条的 system prompt sha16 完全相同（9CF19A15113862A1）**：

~~~text
22:29:19 src=tool_calling tools=26 prompt=  8092 hit=  512 miss= 7580 ratio= 6.33%
22:29:20 src=tool_calling tools=26 prompt=  9479 hit= 8064 miss= 1415 ratio=85.07%
22:29:21 src=tool_calling tools=26 prompt= 10022 hit= 9600 miss=  422 ratio=95.79%
22:29:26 src=tool_calling tools=26 prompt= 11389 hit= 9984 miss= 1405 ratio=87.66%
~~~

⇒ **当前缀真的重复时（同请求内的后续轮），命中率 85%–99%，且宣告行就在被命中的前缀里**
（system prompt 逐字相同、tools 逐字相同）。**这正是"该行必须恒定"的价值所在** ——
而生产上它确实恒定（§3、§4）。

### 5.4 该行一旦变化的**损失面**（数据支撑的上下界，不拍脑袋）

| 场景 | 现测命中 | 若该行逐请求变化，最多损失 |
|---|---|---|
| 跨请求（前缀已在 ~1700 字符处分叉） | 512–640 token（5.0%–6.4%） | ≤ 该头部（**≤ 640 token ≈ ≤6.8% of prompt**）—— 因为其后本来就没命中 |
| 同请求内热态（前缀逐字重复） | 8064–9984 token（85%–99%） | 从该行（字符 689）起全部失效 ⇒ **约 8,500–9,500 token ≈ 85–99%** |

- 该行自身规模：328 字符 / **94 cl100k token**（26 个工具名）；它之后的 system 内容
  约 2,500 字符 ≈ 1,568–1,694 cl100k token。
- 若该行变化，它**后面**的一切（尾簇 + 全部历史消息）都不再命中；本部署实测
  尾簇本就每轮在变，所以**跨请求**的边际损失被这 5% 头部封顶，
  而**同请求热态**的损失是灾难性的（所以"恒定"是必须保持的性质，不是可交易的余额）。

## 6. 最终裁决：**A 保持现状**（并列出重构触发条件）

### 6.1 三个方案的量化对照

| 方案 | 实测收益 | 实测代价/风险 | 结论 |
|---|---|---|---|
| **A 保持现状** | 该行在生产两条链路上都恒定 ⇒ 热态 85–99% 命中已被保住；跨请求那 5% 头部也保住 | 无 | **采纳** |
| **B 下移到易变尾簇** | **实测为 0**（该行不变，移不移动命中率都一样）；且在"无主线+智能选择"路径上，**tools= 同样逐请求变**，移了也不命中 | 生产 4 处渲染点（system_prompt_config.py:442-466 的 SECTION_REGISTRY、system_prompt_manager.py:36、digital_life.py:353、persona/persona_injector.py:53-55）+ 已在 CI 里的 4 处契约（test_prompt_cache_order.py:430,435 明文锁「技能指令 < 工具状态 < 当前状态」；test_system_prompt_emit_info.py:68 的 emit_order；UI 侧 identityPrompt.test.ts:50 的 emit_order=10003、promptLabRequirements.test.tsx:56 的键顺序）+ 3 处说明性注释 | **不采纳** |
| **C 域目录摘要（方案 3.5 的 B 思路）** | 行从 328 字符/94 token 缩到 ~49 字符/47 token（省 ~47 token/次 ≈ 0.5% of 9.5k），且"若该行变化"的方差面更小 | 宣告行不再列出**具体工具名**，模型对"我到底有哪些工具"的可读性下降（B1 的"宣告=下发"精神被削弱）；同样**不能**解决 tools= 逐请求变 | **暂不采纳**，仅在 §6.2 触发条件成立时重估 |

### 6.2 以下任一情况发生，请重开本卡（这就是"重构触发条件"）

1. **全局激活主线被关掉**（或改成按会话/按请求生效）⇒ 编排器与工作台的
   hybrid_select_tools 变成可达 ⇒ 宣告行**会**逐请求变（§4.1 已实测选择集变），
   此时"下移到尾簇"或"域目录摘要"才第一次有了真实收益，且**必须先解决 tools= 的变异性**。
2. **工作台改成渲染宣告行**（把 _build_tool_status_text 接进 plugins/chat.py）⇒
   本卡离线单测 test_工作台SSE的system_prompt不含工具宣告行 会**变红**，
   红灯含义正确：「这条不变量变了，请把 F3 的裁决重做一遍」。
3. B1 的"宣告=下发"不变量若被放宽（例如允许宣告注册表全量）⇒ 该行重新变成
   "进程内恒定"，风险反而更低，但 DSML 防线会被削弱 —— 那是另一张卡的事。

## 7. 混淆变量（**没控制住的，如实列出**）

| # | 混淆变量 | 影响方向 | 本卡处置 |
|---|---|---|---|
| 1 | **模型侧前缀缓存的 TTL / LRU 淘汰** | 未知 | 完全未控制。间隔 4–17s 属于"短"，理论上 TTL 不至于失效；但 DeepSeek 的具体 TTL/容量不公开，**不能排除** |
| 2 | **其它卡并发使用同一账号/同一 key**（本机同时有 audit_concurrency_probe、e1_worker2 等进程） | 污染命中率 | 未控制。前缀缓存按内容匹配，他人不同前缀不会直接命中我们的条目，但**可能挤占 LRU**；本卡无法隔离 |

## 11. 交给主控的旁路发现与建议

1. **真正的缓存损耗不在宣告行，在它门口的易变尾簇。** 本部署**跨请求**命中率只有 5%
   左右，首因是「记忆线索（含本轮问题原文）/最近对话」在 ~1700 字符处就分叉，
   而**同请求热态**能到 85–99%。若目标是省 token，收益更大的方向是
   **尾簇的稳定性/位置**（例如把"本轮问题原文"从记忆线索里去掉、或把最近对话改为消息数组承载），
   而不是把稳定的宣告行挪位置。**建议另开卡**用本卡探针做 A/B（改生产代码越界，本卡不做）。
2. **工作台 SSE 一次请求会打 3–4 次 LLM 调用**（3 次请求产生 11 条记录），且**流式不带 usage**
   ⇒ 工作台链路在成本/缓存可观测性上是**盲区**（B3 未验证项 2 的实例）。建议另开卡：
   给流式路径带 stream_options.include_usage（或在 chat_stream 里补 usage 解析）。
3. **探针可复用**：scripts/probe_prefix_cache_interaction.py 的输入只有"服务地址 + 间隔 + 组选择"，
   默认三组即本卡口径；加 --cases ident 单独跑只花 3 次出网预算，适合作为改尾簇前后的对照实验。
