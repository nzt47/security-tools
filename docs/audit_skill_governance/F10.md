## 2. 问题与复现（先复现，再修）

### 2.1 缺陷本体（直读源码）

`merge_with_backup` 写 sidecar 时**只写**这些键：

```python
rec = {"merge_id", "ts", "src_id", "dst_id",
       "src_snapshot": src.model_dump(),          # id 恒为 src_id
       "dst_before": {8 个字段，**不含 id**}}      # 保留方合并前的字段子集
```

而 `undo_merge` 在「保留方后来也被删除」时的重建判据是
`isinstance(snap, dict) and snap.get("id") == dst_id`，其中 `snap = rec.get("src_snapshot")`。
`src_snapshot["id"]` **恒等于 `src_id`**，而 `merge_duplicate_skills` 明确禁止
`src_id == dst_id`（`service.py:2016-2019`）⇒ 该条件**恒为假** ⇒ 分支不可达。

## 3. 修法

### 3.1 `merge_with_backup`：同批多写一份 `dst_snapshot`（保留方完整实体）

```python
"src_snapshot": src.model_dump(),
# [F10] 保留方的**完整实体**快照：undo_merge 在「dst 也被删除」时靠它整条重建。
# 旧记录没有这个字段（本卡之前写的 sidecar），undo_merge 对此**向前兼容**
# ——读不到就退回「不重建」，绝不抛异常（见 undo_merge 的 dst 重建分支）。
"dst_snapshot": dst.model_dump(),
"dst_before": { ... 8 个字段，原样保留 ... }
```

**为什么两种 dst 快照都留（不是冗余）**：`dst_before` 是**内容回滚的输入**
（情形一逐字段套回，且它**刻意不含**治理字段以外的 id/status/时间戳），
`dst_snapshot` 是**整条重建的输入**。混用一个必然有一边受伤：只有 `dst_before` ⇒ 无法重建
（缺主键）；只用 `dst_snapshot` ⇒ 情形一会把 `status`/`version`/`metrics` 等非内容字段
一起回滚，扩大 F9 刻意收窄过的口径。

### 3.2 `undo_merge` 的 dst 重建分支：改读 `dst_snapshot`

```python
snap = rec.get("dst_snapshot")
if isinstance(snap, dict) and snap.get("id") == dst_id:
    self.store.upsert(Skill.from_storage_dict(snap))
    restored.append(dst_id)
else:
    legacy = rec.get("src_snapshot")            # 旧格式记录：原样退回本卡之前的行为
    if isinstance(legacy, dict) and legacy.get("id") == dst_id:
        self.store.upsert(Skill.from_storage_dict(legacy))
        restored.append(dst_id)
    else:
        logger.warning(... 无可用快照 ⇒ 无法自动重建，需人工恢复 ...)
        dst_rebuild_skipped = True
```

### 3.3 向前兼容的降级口径（本卡要求论证）

卡上给了两个可选口径：「退回现有行为」或「明确报告无法重建，需人工」。
**本卡两个都做了，合起来才自洽**：

| 口径 | 本卡选择 | 理由（证据） |
|---|---|---|
| 读不到 `dst_snapshot` 时怎么办 | **原样退回本卡之前的行为**（保留旧判据作为兜底），且**不抛异常** | ① 与改动前**逐字等价**：旧判据在真实记录下恒为假（探针 `old_criterion_holds: false` 实测）⇒ 真实旧记录的行为一字不变；② 保留「按旧语义刻意构造的记录」的既有行为面 —— F9 单测用例 6（`f9-c2c-crafted`）就是这种记录，本卡**不改它的测试文件**也能让它继续绿（§5.2 实测）；③ 改动面因此收窄成「只让新记录的那一半从不可达变为可达」。 |
| 兜底也走不通时怎么办 | **不重建 + 明确留痕**（logger warning + 评估事件 summary 追加「未能自动重建…需人工用记录里的 dst_before 正文恢复」） | 卡上第二选项。之所以不静默：F10 的实质危害就是「静默少恢复」。事件与日志是本方法**既有的**报告通道（方法本来就用 `_emit_assessment_event` 报告撤销结果），故**不动返回结构**也能把话说到。 |
| 要不要拿 `dst_before` 硬拼一个技能 | **不要** | `dst_before` 只有 8 个字段，**不含 id/status/category/version/时间戳**，只能靠默认值猜补 ⇒ 会凭空造出一个**看起来真实**的技能（`status=draft`、`version=0.1.0`、`category=custom`）。这比「少恢复一个」更糟：操作员/前端无法区分它是「恢复出来的」还是「新造的」。与审计口径「宁可少记，不可记假」同源 —— **宁可少恢复，不可造假技能**。 |

补充（实测踩到的坑，已修）：warning 文案原本含 `⇒`(U+21D2)，Windows 控制台日志流是 **GBK**，
实测 `logging` 抛 `UnicodeEncodeError` 并把这条告警吞掉（原始输出见 §5.4）。现文案改为 ASCII `=>`，
并把这行实测结论写进代码注释，避免后人再踩。

## 4. 与 F9 的语义保持一致（本卡要求锁死）

F9 的 `_UNDO_MERGE_KEEP_FIELDS` 注释原文（`service.py:1120-1122`，本卡**未改**）：

> 生效范围仅限「dst 仍存在」的分支：技能已被删除、要靠快照重建时没有「现有
> 治理状态」可保护，快照里的 `enabled` 等照常恢复（见 `undo_merge` 两个分支）。

**两情形为什么不同**：情形一里 dst **还在**，操作员可能已经在合并之后改过它的启停/隔离状态
（那就是一份**真实存在的治理决策**），内容回滚不得把这份决策静默写回；情形二里 dst **已经不存在**，
**没有「现有治理状态」这个东西**，能依据的只有合并前快照 ⇒ 按快照整条重建，`enabled` 来自快照。

本卡新增的 dst 重建分支**属于后者**，故**刻意不做保留字段过滤**（注释已写明）。
锁定测试：`TestRebuildRestoresEnabledFromSnapshot::test_rebuilt_dst_takes_enabled_from_snapshot_not_from_default`，
构造方式是「快照停用（False）、删除前已被操作员启用（True）、`Skill.enabled` 模型默认值也是 True」
⇒ 重建结果断言 `False` **只可能来自快照**（不可能来自现值，也不可能来自默认值）；
同文件另有 `test_case_one_still_keeps_governance_state` 做反向对照（快照 True、现值 False ⇒ 保持 False）。

## 8. 结论

1. **缺陷已复现**：探针实测「合并 → 删 dst → undo」得到 `restored == ["…src"]`、`dst_rebuilt: false`，
   记录里 `has_dst_snapshot: false`、旧判据 `old_criterion_holds: false`。
2. **修复已落地且实测有效**：`merge_with_backup` 增写 `dst_snapshot`（保留方完整实体），
   `undo_merge` 的 dst 重建分支改以 `dst_snapshot["id"] == dst_id` 为判据；同一探针复跑得到
   `restored == ["…src", "…dst"]`、`dst_rebuilt: true`。
3. **向前兼容按卡面要求做到，且理由已论证**：旧记录**原样退回本卡之前的行为**（不抛异常、不造假技能），
   并在日志与评估事件里明确写「未能自动重建，需人工恢复」——「宁可少恢复，不可造假技能」。
4. **与 F9 语义一致且有测试锁死**：重建路径恢复快照里的 `enabled`（因为没有「现有治理状态」可保护），
   情形一仍**绝不**回滚治理字段；两情形差异在代码注释与测试里都写明了理由。
5. **签名与返回结构未变**；`dst_before` 的 8 字段逐字未变；D4/F9 的改动一行未动（§1.1 字节级证明）。
6. **唯一未闭环项**：F9 的单测文件里有一条「把缺陷写死」的断言（`test_rebuilt_skill_keeps_snapshot_enabled`），
   修好 F10 后它必然失败；最小补丁见 §5.2，因超出本卡允许修改范围**未实施**，需由其文件所有者合并。
