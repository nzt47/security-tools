## 0. 结论（先说三条最重要的）

1. **"零服务窗口"的风险成立，但审计 §1.4 给出的量级（58 s）不成立。** 实测旧代码的
   kill→bind 窗口约 **1 s**（§2），因为 55–85 s 冷启动几乎全部发生在旧清理语句**之前**
   （模块导入 + 引擎装配）。真正的风险不是"窗口有多长"，而是**清理是无条件的**：
   任何在旧清理语句之后失败的步骤（调度器、学习任务注册、`from waitress import serve` …）
   都会留下"旧实例已死、新实例没起来" = 完全无服务。本次修复针对的正是这个语义。
2. **零服务窗口已按"就绪门"消除**：清理旧实例只发生在 ①端口上确实有旧实例
   ②新实例**在进程内自证 /api/health == 200** 之后；新实例任何更早的失败都不再碰旧实例。
   本机实测交接窗口 **0.34 s**（旧代码同机推定约 1 s，见 §2.3）。
3. **子进程不再遗留**：本进程加入 `KILL_ON_JOB_CLOSE` 的 Windows Job Object，
   `taskkill /F`（TerminateProcess）、崩溃、正常退出三条路径通杀整棵进程树。
   已用**真进程实验**证明（§3.4）。另外为"修复之前启动的历史实例"补了一条显式补杀路径。

## 2. 问题 1：零服务窗口

### 2.1 旧行为 / 新行为 / 为什么安全

**旧行为（实测代码路径）**：`app_server.py` 在 `if __name__ == "__main__":` 的**前段**
（旧 1843-1847 行，紧跟健康采集线程启动之后）**无条件**执行
`cleanup_port_listeners(5678)` ⇒ `taskkill /F /PID <旧PID>`；之后才继续走
调度器启动（旧 1849-1895）、学习/清理定时任务注册、搜索引擎性能监控（旧 1897-1911）、
优雅关闭钩子注册（旧 1913-1918）、`from waitress import serve`（旧 1938），
最后 `serve(...)`（旧 1941）。

⇒ 上列**任何一步**抛错，进程直接退出，而旧实例**已经死了** ⇒ **完全无服务**，
且退出的是一条没有任何人监听的路径（审计 §1.4 记录的 2026-09-22 静默退出就是这样）。

**新行为**：
1. 旧 1843-1847 的清理调用**移走**，原位改为装 Job Object（§3），仍属"可失败初始化"的一部分；
2. 全部可失败初始化走完之后，最后一段变成：
   ```python
   _startup = guarded_startup(
       lambda: serve(app, host="127.0.0.1", port=5678, threads=16),
       5678,
       preflight=_startup_preflight,   # 进程内 app.test_client().get("/api/health") == 200
   )
   ```
3. `guarded_startup` 的**固定顺序**：只读探测端口 → （有旧实例才跑）就绪门 →
   **门通过才**清理旧实例 → bind。

**为什么安全**：
- 端口空闲时（没有旧实例可杀）**根本不跑探针**、不清理，零额外开销、零行为变化；
- 端口被占时，只有"新实例已经能在进程内把 `/api/health` 跑成 200"才允许清旧实例 ——
  这把"新实例能否服务"从**事后才发现**变成**事前已证明**；
- 探针自身抛异常按**失败关闭**处理（视为未就绪），不会因为探针坏掉而误杀；
- 放弃启动时写一条结构化留痕（`action=startup.gate.abort_before_cleanup`，
  `killed_any=false`，`old_instance_pids=[...]`），退出的是一条**可自证**的路径，
  不再是"日志戛然而止"。

### 2.2 未改的部分（避免"悄悄改变语义"）

- `cleanup_port_listeners` 的 kill 命令**逐字未改**（仍是 `taskkill /F /PID <pid>`，
  `timeout=3`）—— 回归锁 `tests/unit/test_server_port_guard.py:111` 对该 argv 是逐字断言，
  该文件不在本卡允许修改清单内，**本卡实测它 9 项全绿**（§6.2）。
- 端口探测仍走 `netstat -ano`，端口精确匹配逻辑未改。
- 不传 `preflight` 时**维持旧行为**（有旧实例就清理）—— 这条默认值**有意保留**并
  由 `test_no_preflight_configured_keeps_legacy_behaviour` 固定下来，避免被误当成"已修复"。
  `app_server.py` 的调用点**总是**传探针。

### 2.3 量级实测：审计 §1.4 的"58 s 窗口"不成立

审计 §1.4 写："`cleanup_port_listeners(5678)`（`:1845`）先 `taskkill /F` 旧实例，
`serve()`（`:1926`）在其后约 **58 s** 才就绪"。本次用 2026-09-22 那次运行的日志
按行定位了这两条语句各自**实际的**时间戳：

### 2.4 为什么做不到"严格原子"（如实登记）

单个监听端口无法原子交接：新实例**必须**等旧实例释放 socket 才能 bind，而 Windows 上
用 `SO_REUSEADDR` 让两个 socket 同时 bind 同一端口会得到**双监听的分裂脑**
（连接随机落到两个实例），比短暂无服务更糟。故本卡实现的是"**把窗口压到最小 + 保证
窗口只在确认新实例可用后才打开**"，残余的 <1 s 由看门狗（§4）兜底。

## 3. 问题 2：embedding / reranker 子进程不随父进程消失

### 3.1 机制

`agent/tool_router_hybrid.py:991` 的 embedding worker 与 `agent/skills_mgmt/reranker.py`
的精排进程都是 `subprocess.Popen` 起的独立 python 进程（审计实测各占 0.5–0.9 GB）。
`taskkill /F` == `TerminateProcess`：不投递信号、不跑 `atexit` ⇒ **父进程一死，
子进程被孤儿化**，继续占用内存与句柄。

### 3.2 选了哪个方案，为什么

**选 Windows Job Object（`KILL_ON_JOB_CLOSE`），不选 `taskkill /F /T`。**三条理由：

1. `/T` 只在**父进程还活着**时才有意义（它按当时快照枚举子进程）；而调用点拿到的是
   "正在监听 5678 的 PID"，无法保证覆盖已经 re-parent 的孙进程。
2. `/T` 必须经 `subprocess`，会**改变 `cleanup_port_listeners` 传给 `runner` 的 argv**，
   而 `tests/unit/test_server_port_guard.py:111` 对 argv 是**逐字断言**
   （`assert events[1][2] == "taskkill /F /PID 4321"`），并且**该测试文件不在本卡允许
   修改的清单内**（同一份 `runner` 还会把任何额外调用记成一条 `kill` 事件，
   连"补一条 `/T` 调用"都会破坏 `events == [log, kill]` 的顺序断言）。
3. Job Object 由内核保证，覆盖 `/F`、崩溃、正常退出**三条**路径，且不依赖
   "父进程来得及跑到清理代码"—— 而 `/F` 路径恰恰是"跑不到"的那条
   （`server_port_guard.py` 的 L23 注释自己承认了这点）。

### 3.3 实现

`agent/server_port_guard.py`：

- `install_child_process_reaper()`：`CreateJobObjectW` →
  `SetInformationJobObject(JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)` →
  `OpenProcess(self)` → `AssignProcessToJobObject`。
  句柄由模块级 `_REAPER_JOB_HANDLE` **长期持有**（句柄一旦被 GC 关闭，Job 立刻销毁
  并杀掉全部成员 —— 那会把"退出时清理"变成"启动时误杀自己"）。
  任一步失败都**只返回 `installed=False` + 原因，不抛异常**（降级不得阻断启动）。
- `app_server.py` 在 `__main__` 的启动前段（旧清理语句原位，健康采集线程之后、
  任何可能 spawn 子进程的初始化之前）调用它，成功记 INFO、失败记 WARNING。

**踩到的坑（实测，写进代码注释了）**：`GetCurrentProcess()` 返回的是伪句柄 `-1`，
**不能**用于 `AssignProcessToJobObject`：

```
CreateJobObject handle: 332 err 0
SetInformationJobObject: 1 err 0
AssignProcessToJobObject(self): 0 err 6      <- ERROR_INVALID_HANDLE
```

必须用 `OpenProcess(PROCESS_SET_QUOTA|PROCESS_TERMINATE, False, os.getpid())` 拿真句柄。
改真句柄后实测（子进程自动继承 Job）：

```
OpenProcess self: 156 err 0
AssignProcessToJobObject(self): 1 err 0
child pid: 1368
QueryInformationJobObject: 1 count: 2 pids: [2392, 1368]  self: 2392 child: 1368
RESULT child_in_job= True
```

### 3.4 真进程实验：父进程被 /F 后子进程确实消失

```
parent=13088 child=17492
child alive before kill: True
SUCCESS: The process with PID 13088 has been terminated.
child alive after parent taskkill /F: False
```

同一条不变量已固化进单测（`test_job_object_kills_children_on_parent_force_kill`，
本次实测通过，非 skip —— 见 §6.1 的 `15 passed, 0 skipped`）。
该用例只 taskkill **它自己 spawn 的**临时父/子进程，不碰任何既有服务。

### 3.5 历史实例的补救路径（`reap_children=True`）

Job Object 只对"**创建子进程之前**就加入 Job"的父进程有效。**修复之前启动的实例**
没有 Job，其后代要靠补杀。因此 `cleanup_port_listeners` 增加了**可选**
`reap_children=False`（默认关闭 ⇒ 默认调用路径逐字不变）：

- 强杀父进程**之前**先记下全部后代 PID（父进程一死，`psutil.Process(dead).children()`
  直接抛 `NoSuchProcess`，事后取必为空）；
- 强杀父进程；
- 再逐个补杀，且每个后代都要过**防 PID 复用闸**（`child_guard`：子进程的 PPID 仍须
  指向原目标父进程；父进程已死时 `ppid()` 读到的是残留值，判据依然成立）；
- 每条补杀写一条 `action=startup.port_cleanup.reap_child` 留痕。

**实测发现的噪声（已修）**：第一版没有过滤后代类型，A→B 交接时捕到一条
`parent_pid=17776 / target_pid=4080` 的记录，查下去 4080 是 **conhost.exe**（控制台宿主，
内核为被强杀的父进程托管，父进程一死自然消失）——把它记成"残留 embedding/reranker 子进程
并已补杀"是**误导性留痕**。现已显式排除 `conhost.exe / OpenConsole.exe`
（`_EXCLUDED_CHILD_NAMES`），复测后同一场景 `reaped_children=[]`（§5.4）。

## 4. 问题 3：看门狗

### 4.1 为什么用 Python 而不是 PowerShell（选型理由）

1. **执行策略**：`.ps1` 受 `ExecutionPolicy` 约束，默认 `Restricted` 的机器上直接拒绝运行
   （必须 `-ExecutionPolicy Bypass` 才起得来）；`.py` 没有这道门。
2. **解释器保证**：本仓库唯一被实测确认存在的解释器就是 python 3.12.0，且
   `start_yunshu.bat` 已经在用它拉后端；PowerShell 版本未做任何约束。
3. **同构性**：服务本身就是 python 进程，看门狗用同一个 `sys.executable`，
   不存在"看门狗能跑但服务跑不起来"的解释器分歧。

### 4.2 有意不复用 `agent/server_port_guard.py`

看门狗**只依赖 Python 标准库**，不 import 仓库内任何模块。理由：它必须在被看护对象
"坏掉"时仍然可用；一旦 `import agent.*`，任何一处导入期错误（依赖缺失、语法错误、
.env 解析失败）都会让看门狗与被看护对象**一起躺下**。代价是 netstat 解析重复实现了
约 15 行 —— 这是**有意**的（代码注释里写明了）。

### 4.3 行为

| 项 | 默认值 |
|---|---|
| 探活 URL / 间隔 | `http://127.0.0.1:5678/api/health` / **30 s** |
| 连续失败阈值 | 3 次（抗瞬时抖动） |
| 重启冷却 | 120 s（抗重启风暴 —— 审计 Q8 §5 实测过"9/22 5.5 小时内 7 次重启"） |
| 等就绪上限 | 180 s（冷启动实测 55–85 s） |
| 留痕 | `logs/watchdog_yunshu.jsonl`（JSON Lines，每条带 `ts/event/reason/old_pid/new_pid`） |
| 单实例 | `logs/watchdog_yunshu.lock` + 活体 PID 校验（防两个看门狗互相打架） |
| 拉起方式 | `subprocess.Popen([sys.executable, "app_server.py"], creationflags=DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP)`，stdout/stderr 落 `logs/watchdog_spawn_*.{out,err}.log` |

不使用 `msvcrt.locking` 做文件锁：进程被强杀时它不会自动释放，反而留下永久死锁。

### 4.4 接进 `start_yunshu.bat`

看门狗只在"**本次真的启动了后端**"的分支里拉起（后端已健康时走 `goto backend_up`，
不会多起一个看门狗）：

```bat
REM ---- 1.b Watchdog (A1): keeps the backend alive ----
start "Yunshu-Watchdog" /D "%ROOT%" cmd /k "python scripts\watchdog_yunshu.py"
:backend_up
```

同时修正了该文件里**已经失真**的注释（审计点名过"注释失真"，故不新增）：

- 旧第 22-24 行"app_server.py **在启动时**就 force-kill 5678 上的东西"——**已不成立**，
  改为准确描述"跑完全部可失败初始化 → 过就绪门 → 才替换"，并给出实测窗口 0.34 s；
- 旧第 8/58-59 行"关掉**两个**弹窗窗口即停服"——现在是**三个**（后端 / 看门狗 / 前端），
  且关掉看门狗窗口**不会**停后端（看门狗用 `DETACHED_PROCESS` 拉起后端）。已改。

## 9. 残余风险（交给后续卡片）

1. **清理→bind 之间仍有实测 0.34 s 的窗口**：单端口无法原子交接（§2.4）。
   兜底是看门狗：连续 3 次探活失败（默认 90 s）后重启，冷启动再 55–85 s
   ⇒ **最坏约 3 分钟**不可用窗口。若要把这段也压掉，需要引入端口级代理/双端口灰度，
   超出本卡"最小改动、不引入新依赖"的边界。
2. **Job Object 的适用范围**：只在"父进程创建子进程**之前**就加入 Job"时有效。
   **修复之前启动的历史实例**没有 Job —— 对它们要靠 `reap_children=True` 的补杀路径
   （已实现并单测覆盖），且补杀依赖 `psutil`（不可用时如实返回空，不臆测）。
   本机当前**没有**任何在跑的历史实例（5678 空闲）。
3. **被外部 Job 限制的场景**：若 `app_server` 由某个受限启动器放进一个不允许嵌套的
   Job，`AssignProcessToJobObject` 会失败（err=5）⇒ 降级为"不回收子进程"并记 WARNING。
   本机实测未触发（三次都 `installed: True`）。
4. **`cleanup_port_listeners` 的 kill 仍是 `/F`（无 `/T`）**：这是**有意保留**的
   （§3.2 第 2 条）。若后续允许修改 `tests/unit/test_server_port_guard.py`，可以考虑
   在**父进程存活时**先做一次 `/T` 快照式清理作为第三层护栏。
5. **看门狗只探 `/api/health`**：审计 §1.3 实测该端点 200/781 B/0.05 s。若服务
   "进程活着但业务不可用"（例如检索腿静默降级），看门狗不会发现 —— 那属于可观测性卡片的范围。

  **没有 try/except**；异常会穿出 `guarded_startup` → 穿出 `__main__` → 进程带栈退出；
- 而此刻**旧实例已经被杀**（异常发生在 kill 之后、bind 之前）⇒ **完全无服务**，
  正是本卡存在的理由本身。触发条件也容易满足：只要 `reap_children=True` 且**确实收到了
  一条后代记录**（例如历史实例留下的孤儿 embedding worker）。

**因此本轮做了两层修复**：

1. **点修**：汇总日志按 `action` 过滤（消灭该次 KeyError 的直接来源）；
2. **面修（更重要的不变量）**：在 `guarded_startup` 里把清理调用整段包起来 ——
   **"清理失败不阻断启动"是三处既有契约**（原 `app_server.py` 调用点的 try/except 注释
   "清理失败不阻断启动（与旧行为一致）"、本模块 docstring "调用方仍整体 try/except 兜底"、
   每个 kill 各自的 try/except），**新链路不得比旧链路更严**。现在清理抛任何异常都只记一条
   `action=startup.port_cleanup.failed` 的结构化留痕并**继续尝试 bind**；端口若未被释放，
   bind 会失败并以 `EXIT_SERVE_FAILED(4)` 退出，交给看门狗 —— 比在半途崩溃更可观测。

两条新回归钉死它（`tests/unit/test_startup_no_gap.py`）：

- `test_cleanup_exception_does_not_block_startup`：monkeypatch 让
  `cleanup_port_listeners` 抛 `KeyError("target_kind")`，断言
  `result["served"] is True`、`exit_code == 0`、留痕写出、`old_instance_pids` 完整；
- `test_cleanup_mixed_records_never_raise_keyerror`：直接对真实调用产出的
  `{kill_before, reap_child}` 混合记录断言两类 action 共存且不再抛异常。
