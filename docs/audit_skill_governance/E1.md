### 2.2 字段契约

每行形如（与卡点给定的字段一致，另加两个可追溯字段）：

~~~json
{"id":"rc-001","query":"帮我把这次改动的计划一条条写下来，我随时想看到进度",
 "expect_tools":["todo_write"],"forbid_tools":["schedule_task"],
 "note":"Q2 §3 组1（todo_write ↔ writing-plans）。边界=…",
 "source_groups":[1],"lang":"zh"}
~~~

- source_groups：锚定 Q2 §3 的组号（1..21），供「21 组全覆盖」守卫机器判；
- lang：zh = 全中文（无任何 ASCII 字母，单测逐字符判）；mixed = 含拉丁词。

### 2.3 全中文边界句的占比与理由

- **45/50 为全中文**（90%），5 条 mixed 分别是 rc-007（subagent / report.md）、
  rc-016（before merging / PR）、rc-020（ruff / mypy）、rc-032（LifeTrace）、rc-048（AI 写作）。
- 理由直接来自审计：中文在技能侧拿不到触发词、工具侧也有分词差异。本卡把这一点做成了**可对照的实验设计**：
  rc-011（表外口语）vs rc-012（表内关键词「单元测试」）、rc-019（全中文）vs rc-020（ruff/mypy 拉丁词）、
  rc-047（全中文口语）vs rc-048（词表入口 ai写作 的**大写加空格**写法）。
- 实测结论（§3.3）：**关键词兜底是子串匹配，中文口语与中英混排都会漏**
  （rc-008「并行处理」、rc-022「改动还没提交」、rc-048「AI 写作」三类漏法各有一例）。

### 2.4 两个层次的判据（本卡最关键的口径决定）

生产链路上「路由」其实有两个不同的产物，混为一谈会得出错误结论：

| 层次 | 定义 | 生产落点 |
|---|---|---|
| **决策层 · decision** | 融合排序的 **top1**（= 3.4 备通道「分差 >= τ 才执行」要门控的那个对象） | HybridRetriever.query() 的返回序 |
| **下发层 · payload** | 随请求发给模型的 tools[] 成员集合（默认上限 25） | hybrid_select_tools() 的返回值 |

- **主判据 = 决策层**：passed := top1 属于 expect_tools 且 top1 不属于 forbid_tools。
- **下发层只作诊断**：生产实现是「检索命中 ∪ 关键词类别命中」再截断，而 core 类 5 个工具
  （get_status / search_memory / remember / get_sensor_summary / todo_write）**恒在该集合内**
  ⇒ 下发层的 expected 命中对核心工具恒为真（实测 40/50 里有相当一部分是这个原因），
  forbidden 的「误扩」也只是关键词表撞词的读数（实测 25 条命中，例：rc-001 因「计划」把
  schedule 整类 5 个定时工具全拉进下发集）。
- 诚实声明：本卡度量的是**检索通道**，不是端到端答案质量——检索层选对不等于模型一定调对
  （L3 终审未落地，最终选择者仍是模型）。

### 3.1 「检索入口在没有服务时跑不起来」是怎么解决的 —— **不需要服务，直接 import 即可**

审计担忧的是「检索需要 app_server 引导注册表」。实测**不需要**：工具混合检索的索引源是
data/tool_index.json（由 91 个 YAML 生成，索引里 90 条），HybridRetriever 在构造时自己读文件建
BM25 + Embedding 双索引（agent/tool_router_hybrid.py:53 的 _INDEX_PATH、:1389-1414 的 _load_and_build_index），
**不依赖 app_server、不依赖 CapabilityRegistry、不读 skills 栈**。因此本卡的做法是：

~~~python
sys.path.insert(0, 仓库根); import agent.tool_router_hybrid as trh
trh.reset_hybrid_retriever()
retriever = trh.get_hybrid_retriever()      # 直接可用
trh.hybrid_select_tools(query, None)        # 生产入口本体
retriever.query(query, top_k=40)            # 生产入口内部用的同一份融合排序与分数
~~~

### 3.4 环境事实：本机工具检索的向量腿恒为降级态（**这是 τ 标定的前提，必须点名**）

输出里「检索模式: bm25_only / 向量腿可用=False」不是本卡的配置选择，而是**环境实测结论**。五条证据：

| # | 实验 | 原始结果 |
|---|---|---|
| 1 | 生产默认（不覆盖超时，_WORKER_READY_TIMEOUT=30s） | embedding.worker.ready_timeout timeout_sec=30.0 → degrade_to=bm25_only；degraded=True |
| 2 | 把就绪超时抬到 240s | embedding.worker.ready_timeout timeout_sec=**240.0**；embedding.preheat.failed elapsed_ms=**240208** |
| 3 | 把就绪超时再抬到 300s | embedding.worker.ready_timeout timeout_sec=**300.0**；embedding.preheat.failed elapsed_ms=**300146.78** |
| 4 | 直接跑 worker 源码同一段（外层 75s 上限） | {"type":"ready","load_time_sec":38.14}，整进程 55.6s，rc=0 |
| 5 | 直接调用 EmbeddingIndex._ensure_worker()（超时设 120s） | ok=True elapsed=**96.9s** available=True；随后 search 0.02s |
| 6 | **安静机器上复跑**（先等其它 python 进程退出，本次启动时机器只剩 2 个 python 进程），--worker-ready-timeout 300 --wait-embedding 420 | 仍然 embedding.worker.ready_timeout timeout_sec=300.0；preheat.failed elapsed_ms=**300230.55**；整次评测仍以 bm25_only 跑完（输出里「下限 : 27（BASELINE[bm25_only]）」即模式证据），结果与默认跑逐字一致（27/50、τ=0.0462） |

⇒ 两条结论：
1. **本机 BM25 索引与向量 worker 都是好的**，只是模型冷启动成本约 55–97s，远超生产硬编码的 30s
   ⇒ 服务冷启动后的一段时间内，工具检索**必然**是 BM25-only（与 C1 交付的 degrade_to 标记一致）。
2. **第 2/3/6 条与第 4/5 条相互矛盾**：把就绪超时抬到 240s/300s 后，**preheat 线程路径三次都没拿到 ready**
   （含第 6 条那次安静机器复跑），而同一台机器上直接调用却能成功。这两者不可能同时是"阈值太小"。
   第 6 条已**基本排除"机器争用"**这一解释（本次启动时机器只剩 2 个 python 进程，仍失败 300230.55ms）。
   ⇒ **未定位**：嫌疑落在 **preheat（后台线程）路径**本身——`_readline_with_timeout` 的 reader 线程 + join，
   或 preheat 内的锁/编码阶段。本卡不越界改代码，**建议 C1 线或单独卡复核**，
   并注意这与 F3 的「零召回静默点」「tool_retrieval 补 trace_id」同属检索链的可见性缺口。

**因此**：本卡的 τ 是在 **bm25_only** 配置下标定的；hybrid（向量腿可用、alpha=0.5 融合）配置的基线
标记为**未验证**（脚本里 BASELINE["hybrid"]=None，在该模式下不设下限并在输出里标注）。

| top1 **正确** | 27 | **0.2015** | 0.3304 |
| top1 **错误** | 23 | **0.0457** | 0.0821 |

⇒ 中位相差 **4.4 倍**、均值相差 **4.0 倍**。**分差在该通道上确实有判别力**（不是"无信号"），
但重叠区很大（如 rc-012 分差 0.0253 却是对的，rc-005 分差 0.1169 却是错的）。

**τ 建议值 = 0.0462**（判据：在 50 个候选 τ 上最大化 F1；并列取更保守者；候选集合 = 实测的 50 个分差取值
+ 0.0 + max+1e-6，**没有引入任何人为数值**）。该 τ 下（原始输出）：

| 指标 | 值 |
|---|---|
| 正确执行 TP | 25 |
| **误执行（假阳 FP）** | **11** |
| **不必要澄清（假阴 FN）** | **2** |
| 正确澄清 TN | 12 |
| precision / recall / F1 | 0.6944 / 0.9259 / **0.7937** |
| 执行率（分差 >= τ 的比例） | 72.00% |

**换口径的误召/漏召（卡点问的两个数）**：
- **误召**：τ=0.0462 时**把错误的 top1 直接执行 = 11 条**；另在检索层，forbidden 进入下发集 25 条、
  成为 top1 的 7 条（这 7 条与 τ 无关，是检索本身的错召）。
- **漏召**：τ=0.0462 时**本该直接执行却被要求澄清 = 2 条**；检索层 expected 未命中 = 23 条（决策层）/ 10 条（下发层）。

**第二个可操作点（供取舍）**：**τ = 0.2846** 是「FP = 0 的最小 τ」——零误执行，但假阴涨到 16 条、
执行率掉到 22%（precision 1.0、recall 0.4074、F1 0.5789）。
两个点构成一个显式的代价曲线：**要么 72% 执行率 / 11 条误执行，要么 0 误执行 / 22% 执行率**。

**必须与 τ 一起交付的三条限制（否则这个数值会被误用）**：
1. **只是标定值，没有消费点**：全仓 grep「分差」，agent/ 下唯一命中在
   agent/skills_mgmt/categorizer.py（讲技能分类的 0 分差平局），**没有任何生产代码读工具检索分差做门控**。
   与 B3 的 zero_recall_total 同处境（函数就绪、无调用方）。落地需要一个消费点 + 产品先定义"澄清"交互。
2. **只在 bm25_only 降级态标定**（§3.4）。向量腿可用时融合分是 0.5*bm25 + 0.5*cosine，量纲会变
   ⇒ **τ 必须在 hybrid 态重标**（本卡标为未验证）。
3. **τ 治不了"选错"**：它只能把"错并放行"变成"错并提问"。当前 precision 上限 0.69
   ⇒ **先修检索（描述边界 + 中文噪声），再启用 τ**；顺序反了只会把错答换成频繁打断。

### 4.4 分差分布的一个副作用发现

50 条里有 **8 条只有 1 个融合候选**（n_ranked=1，分差 = top1 分本身，如 rc-001/003/004/010/020/027/029/031）。
这些句子的"分差"其实是「有没有第二候选」的伪分差，不是真正的排序置信度。
本卡按「无第 2 名时 top2 记 0.0」的口径处理（这是**口径选择**，已在脚本注释里写明）。
若将来把 τ 用于生产门控，**必须先区分「单候选」与「多候选窄分差」两种情况**：
前者的分差大是因为没有竞争，不代表更可信。

## 6. CI 接入建议（**本卡不实施** .github/workflows/**）

建议加一个独立 job（或既有 job 的一步），两条命令，任一非 0 即阻断：

~~~yaml
# 建议片段（未实施）：仅在相关文件变更时触发
- name: 路由冲突回归集（E1）
  run: |
    python -m pytest tests/unit/test_route_conflict_cases.py -q
    python scripts/eval_route_conflict.py --no-embedding --min-pass 27
~~~

- **--no-embedding 是必须的**：这是 CI 的确定性口径（也正好等于生产里向量腿降级时的真实口径，§3.4）。
  不加它，同一次提交在不同机器上会因为向量腿是否就绪而给出不同数字。
- **--min-pass 27** = 本机实测基线（决策层通过数），语义是「**只许升不许降**」而不是"分数够高"。
  基线常量写在 scripts/eval_route_conflict.py 的 BASELINE 里 ⇒ 任何放水式调低都会出现在 diff 里，可被 review 拦住。
  不传 --min-pass 时脚本自动取 BASELINE[当前模式]。
- **触发条件（建议）**：data/tool_definitions/**、data/eval/**、agent/tool_router.py、
  agent/tool_router_hybrid.py、data/tool_index.json 任一变更 ⇒ 必跑（描述治理 G1 与互斥组 G2 落地时这是唯一的客观闸门）。
- **τ 不进 CI 判据**：τ 是标定输出，不是门槛（理由见 §4.3）。

## 7. 未验证项与局限（**显式列出，不冒充已验证**）

1. **hybrid 模式（向量腿可用）的基线未标定** —— 原因：本机 embedding worker 冷启动 55–97s 而生产就绪超时 30s，
   且把超时抬到 240s/300s 的 preheat 路径仍未就绪（§3.4）。脚本里 BASELINE["hybrid"]=None。
   **后果**：τ=0.0462 只对 bm25_only 有效，融合态必须重标。
2. **没有度量端到端答案质量** —— 本卡只度量检索通道（top1 / 下发集），不调用 LLM，因此无法回答
   「模型拿到这 25 个工具后会不会调对」。这也是"检索选对 ≠ 答对"的诚实声明。
3. **τ 未做在线验证** —— 无消费点（§4.3 限制 1），也没有澄清交互，因此 τ 只到"标定报告"这一层。
4. **未跑全量 pytest** —— 按铁律 3，只跑了本卡指定的 tests/unit/test_route_conflict_cases.py（31 条）。
5. **未启动服务** —— 全程零服务、零 LLM 调用、零费用；未验证服务内运行时的检索结果是否与本脚本逐字一致
   （差异来源可能有：服务内的白名单/主线收窄、smart_tool_selection 开关、planning/llm 双计等）。
6. **用例集的"期望"是本卡依据 Q2 §3 的重叠机制与工具描述做的判定**，其中 2 条（rc-026 rc-038）
   已标注为"期望可能过严、依赖产品口径"；若产品裁定反过来，通过率会变成 29/50（58%）。
   这类裁定应由 G1（描述三段式）/ G4（统一裁决点）落地时一并明确。
