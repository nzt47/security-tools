
# G1 实施前的产品决策分析（主审计，供决策用）

## 背景

G1-B0 确认 G1-B **可以开工**，但列出 **3 项未满足前置**，其中 **U-3 = 5 个产品决策**。
我先把它们逐个做出**有数据支撑的分析**，把「需要人类拍板的」与「我可以直接定的」分开。

## 决策 1：`description` 留英文还是留中文？

**我的建议：留英文。这不是偏好，是实测约束。**

| 事实 | 来源 |
|---|---|
| 技能侧「含典型触发句式」覆盖会从 **17/23（73.9%）掉到 13/23（56.5%）** | G1-A 实测，G1-B0 复现 |
| 掉的那 5 条具体是：`pd-executing-plans` / `pd-finishing-a-development-branch` / `pd-frontend-design` / `pd-requesting-code-review` / `pd-subagent-driven-development` | G1-B0 |
| 原因：`Use when ...` 这一族句式**正是这批英文描述的触发句式载体** | G1-A |

⇒ 把 `description` 换成中文 = **主动削掉 17% 的触发句式覆盖**，且这是**检索召回的主要信号之一**。
**中文另存 `description_zh`（S0 已打通写入链路），UI 读 zh，检索与模型读英文。**

## 决策 2：`description_zh` 谁执笔？

**我的建议：由我（AI）起草，人工抽检。理由是可量化的。**

- 待写条数：**15 条冲突 + 8 条文件轨独有 = 23 条**（真源是 23 个 `skill.md`）。
- 参考素材现成：主轨 `skills_mgmt.json` 里**已有中文描述**（15/15 与英文不同，可直接作为中文草稿的**起点**）。
- 所以我**不是从零翻译**，而是「以主轨已有中文为草稿，人工抽检 5 条」。
⇒ 这条**不需要人类逐条写**，但**需要人类抽检**。

## 决策 3：7 个主轨独有技能是否纳入？

**这条我给了一个比 G1-A 更精确的建议：把它们分成两类，而不是整体纳入或排除。**

我读了这 7 条的 description 与 content（共 13,725 字符）：

| 技能 | content | 描述性质 | 我的判断 |
|---|---|---|---|
| `global-core-principles` | 1421 | 「适用于**所有对话**…作为基础行为底线**始终生效**」 | **不是可路由技能，是常驻行为准则** ⇒ 应进 system prompt 常驻段，**不该进检索** |
| `skill` | 873 | 内容是 `1. 编码前必输出 <san_yi_analysis>...` | **描述字段被错填成指令内容**（不是描述）⇒ 无论纳不纳入，**都得先修字段** |
| `testing-anti-patterns` | 8220 | 「在以下情况请查阅这份参考指南：编写或修改测试…」 | **真正的可路由知识型技能** ⇒ 应纳入 |
| `code-observability` | 553 | 「生成功能模块代码或后端 API 时使用」 | 可路由（条件触发） ⇒ 应纳入 |
| `engineering-test-delivery` | 871 | 「在代码开发与生成的完整生命周期中…」 | 偏向常驻规范，但可条件触发 ⇒ 倾向纳入 |
| `frontend-state-sync` | 1304 | 「生成涉及前后端交互…的 Web 代码时使用」 | 可路由 ⇒ 应纳入 |
| `self-explanatory-ui` | 483 | 「进行界面设计或前端 UI 开发时使用」 | 可路由 ⇒ 应纳入 |

⇒ **建议**：
- **2 条不进检索**（`global-core-principles` 常驻；`skill` 先修字段再定），
- **5 条纳入检索**（迁移进 `skills_repo/<id>/skill.md`，从而真正可召回）。

**这条是我把「7 项不可召回」从「一个缺陷」重新解释为「两类不同问题」**：
其中至少 1~2 条**本来就不该被检索路由**（常驻准则），
所以审计里「7 项主轨技能不可召回」的说法需要**按技能性质细分**，不能整体当成缺陷。
这也是我建议 S2 门改为「双路径 + 明示性质」的原因。

## 决策 4：overlay / curated 删除还是留空？

**我的建议：删除数据条目，但先冻结写路径（G1-B0 的 M0 修正版），且删之前要证明没有活消费者。**

G1-B0 的关键修正是：**写路径是 3 条不是 1 条** —— 漏掉的是
`POST /api/skills/describe`（`plugins/skills.py:443-456`，**可写任意 id**）。
⇒ 只删数据不冻写路径，**下次调用就写回来了**。
顺序必须是：**冻结/关闭 3 条写路径 → 再删数据**。

## 决策 5：`compare_skills_legacy_vs_repo.py` 的 SKIP 语义

**我的建议：修掉（把「legacy 缺失即 SKIP 视为 ALL_MATCH」改为显式 FAIL 或显式 NOT_APPLICABLE 且在 CI 里可见）。**

理由（这条我在审计里已记为盲区）：Q3 实测该脚本**本地跑当前会报红**（only_legacy=7、字段差异=15），
**而 CI 是绿的** —— 因为「legacy 缺失即 SKIP 当作 ALL_MATCH」。
⇒ 这是与 S2 假绿**同族**的问题：**检查不通过时被当成通过**。
G1 做完后如果还留着这个语义，那么「描述一致性」这道门**永远可能是假的**。

# 决策 3 的一处关键事实补充（`skill` 技能的描述字段被错填）

`data/skills_mgmt.json` 里 `skill` 这个技能的 `description` 字段内容是：

```
1. 编码前必输出 <san_yi_analysis>: [不易]约束识别 → [变易]扩展性评估 → [简易]最简方案确认。
2. 原子推理，每步经三义校验。
3. 三义冲突时显式说明权衡取舍。
```

⇒ **这不是描述，是指令内容**（编号步骤 + 祈使句）。
它**无论纳入与否都必须先修** —— 否则任何路由/展示都会把指令当描述用。
这是 G1 实施时**必须单独处理的一处数据质量问题**，已登记。
