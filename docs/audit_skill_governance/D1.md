## 2. 读路径修复

### 2.1 `recent()`：limit 真正下推到 SQL

**缺陷**（`facade.py:402-408` 修复前）：签名有 `limit`，实现却 `chain.entries(**filters)` **不带 limit**，读出全表后 `rows[-int(limit):]` 切片。

**修复**：新增 `AuditChain.tail_entries(limit, **filters)`，内部 `ORDER BY seq DESC LIMIT n`（走 `seq` 的 UNIQUE 索引），返回前反转回 seq 升序。

**为什么不能直接"给 `entries()` 传 limit"**：`entries(limit=n)` 的 SQL 是 `ORDER BY seq ASC LIMIT n`，取的是**最老的 n 条**——语义正好相反。这是本卡最容易踩的坑，已单独写成用例
`test_recent_queries_desc_with_limit`。

**"读得到刚写的"必须保住**：`entries()` 会合并降级 ring buffer 与预留日志中尚未落库的记录。`tail_entries()` 沿用同一承诺：
DB 取最新 n 条 + **全部**额外记录 → 按 seq 排序 → 取尾部 n 条。
数学上等价于"合并全集的最新 n 条"（未落库记录的 seq 恒大于 DB 尾部，被截掉的只可能是更旧的 DB 行）。
实测见 §3.3（追加 30 条只在日志里的记录，`recent(5)` 正确返回它们是最后 5 条）。

### 2.2 `stats()` / `snapshot()`：三个方案的选择理由与代价

| 方案 | 收益 | 代价 / 为什么否掉 |
|---|---|---|
| **A. SQL 聚合（采用）** `COUNT(*)` + 两条 `GROUP BY` | 1751.93 → 32.48 ms，不再把 72,297 行物化成 `AuditEntry` | 仍是 DB 层一次扫描（`GROUP BY source` 10.96 ms、`GROUP BY actor` 7.62 ms）。**不含** `GROUP BY source,actor` 合并写法：实测 100.24 ms，比两条分开慢 6 倍（大临时 B-tree），故刻意分成两条 |
| B. 增量维护计数器表 | 理论上 O(1) | 需要**新增 DDL 写 live 库**（本卡明令不得改 `audit_chain.db` 内容），且崩溃恢复/回放后必须重算，恢复路径本身是"另一个真相源"⇒ 与审计链"重算即真相"的原则冲突。**否** |
| C. 加 TTL 缓存 | 面板轮询时最省 | 本进程不是唯一读者：`role="reader"` 实例与其它进程随时写入（单写者纪律只保证"每进程一个写者"，**不保证全局只有一个读者**）。缓存会让合规面板显示过期条数，而"面板数字与链头不一致"是审计最不能接受的失败模式。**否** |

**代价与口径**：`by_source` / `by_actor` / `total` 的数值与"逐行数"逐字一致（用例 `test_stats_distribution_matches_full_scan` 在已入库链上、`test_stats_counts_uncommitted` 在"只在预留日志里"的链上分别断言），未落库记录仍并入。

**顺带修掉的两个同性质全表**（都是被 `studio` 直接或间接调用的）：
- `count()` → `SELECT COUNT(*)` + `extra_entries()`（`seq IN (...)` 索引查询，避免"先全表取 seq 集合"）；带过滤条件时保留原实现（本卡不动，收益小、风险大）。
- `seq_range()` → `SELECT MIN(seq), MAX(seq)`；口径不变（仍然只并入 `_failed_snapshot()`，不含预留日志）。
- `chain_head()` 因调用上面两个而一并变快（753.35 → 16.53 ms）。

**屏障不能丢**：原来 `count()/seq_range()/stats()` 的第一步都会经由 `_query_rows(refresh=True)` 对 writer 角色先 `flush()`（"读得到刚写的"依赖它）。快路径绕开了 `_query_rows`，故在这三处**显式补回同一道 `flush(timeout=FLUSH_TIMEOUT)`**（队列空时立即返回）。这是刻意保留的行为，不是遗漏（§7 有独立说明）。

### 2.3 语义不变性：唯一的边界收紧

| 输入 | 修复前行为 | 修复后行为 | 判定 |
|---|---|---|---|
| `limit=50` 等正整数 | seq 升序取尾部 n 条 | **逐字相同** | 不变 |
| `limit=0` | `if limit` 假分支 ⇒ **返回全表**（签名叫 0、实际读 72,297 条，O(N) 陷阱） | `[]` | **刻意收紧**（已在 `facade.recent` docstring、用例 `test_limit_zero_returns_empty` 登记） |
| `limit=-3` | `rows[-(-3):]` ⇒ 丢掉最旧 3 条（无意义） | `[]` | 收紧（同上） |
| `limit=None` | 全表 | 全表（回落 `entries()`，docstring 明示 O(N)） | 不变 |
| 过滤条件 | 全表过滤后尾 n 条 | SQL 过滤 + LIMIT，结果相同 | 不变（§3.4 实测 8 场景） |

> **关于任务卡括号里的"最新的在前"**：修复前的真实语义是 **seq 升序、最新的一条在末尾**（`rows[-limit:]`），既有用例
> `tests/unit/test_audit_facade.py::test_recent_returns_tail_in_seq_order` 断言的正是 `["act3", "act4"]`（最新在**末尾**）。
> 本卡首要约束是"不因修复而改变返回值语义"，故**保持升序**，并把该事实固化为
> `test_newest_entry_is_at_the_tail_not_the_head`。若将来要"最新在前"，必须同时改 UI/调用方，属独立变更。

## 4. 保留 / 轮转策略（方案 + 实测）

### 4.1 为什么不能"到期就 DELETE 旧行"

审计链是**合规证据**。删链头的一段不会让剩余行"自身不自洽"，但：

1. **`verify_chain()` 的默认锚点必然失效**。`start_seq=None` 时它一律用 `GENESIS_PREV_HASH`（64 个 0）当锚；删掉 seq 1..K 之后的第一条保留记录，其 `prev_hash` 不等于创世哈希 ⇒ 必然报首个篡改位置。**这不是推测，是实测**（§4.4 的 A/B 对照：`ok=False, reason=prev_hash_mismatch, checked=0`）。
2. **按时间删"某一天"可能在链中留下空洞**。本仓实测日块与 seq **不同序**（2027-10-19 的块是 seq 928..2719，与 2026-09-14 的块 915..2782 交错）——按日区间删会连带删掉别的日的行，且剩下的 seq 不连续，任何验链器都无法解释。

### 4.2 设计（三层，全部可验证）

```
┌ 第 1 层：冷归档（安全，默认唯一推荐动作）
│  把某个 UTC 日的记录原样导出 → <archive-dir>/audit_<YYYYMMDD>.jsonl.gz
│  （逐行 JSON、字段与 DB 行一一对应；gzip mtime=0 ⇒ 同样输入产生同样字节与 sha256）
│
├ 第 2 层：锚点（让"归档"本身成为证据）
│  每个归档写一条锚点到 <archive-dir>/anchors.jsonl：
│    day / rows / first_seq / last_seq / first_ts / last_ts /
│    first_prev_hash / last_self_hash / archive_sha256 / archive_bytes /
│    prev_anchor_hash / anchor_hash
│  锚点**自身也是一条哈希链**（anchor_hash = sha256(规范化 JSON 去掉 anchor_hash)，
│  prev_anchor_hash 指向上一锚点的 anchor_hash）⇒ 事后删/改某天锚点可检出。
│
└ 第 3 层：删除（危险，默认关闭，且只允许"链头前缀"）
   可删上界 K = min( 窗口约束, 链头日保护 )：
     窗口约束 = （第一个"属于保留窗口内"的记录的 seq）- 1
     链头日保护 = （链头日最早一条的 seq）- 1        ← 防止"全库都旧"时一次删空
   只有 `seq ≤ K` 的**连续前缀**可删；前缀内出现任何**未归档**的日 ⇒ 拒绝执行。
   删除用单事务 `BEGIN IMMEDIATE`（拿不到写锁 = 服务在写 ⇒ 直接放弃）。
   删完打印**重新锚定**参数：
       chain.verify_chain(start_seq=K+1, anchor_prev_hash=<seq K 的 self_hash>)
```

**为什么"归档优先、删除可选"**：归档把冷数据搬走、留下证据锚点，是纯增量动作（只读库、只写冷文件），永不破坏链；磁盘回收则**必须**付"链断头"的代价，只有运维明示才做。二者解耦之后，"保留策略"不再等价于"删数据"。

### 4.3 本仓数据形态让"删除"通道被自动挡住（实测）

live 库用默认窗口（`--keep-days 90`，ref=今天 2026-09-25 ⇒ 截止日 2026-06-27）跑出来 **K=0**；把截止日放宽到 2026-09-20 也只有 **K=927**（3 个日块的部分行），因为：

- 2026-09-12 的块是 seq 1..553、2026-09-13 是 554..914 之后，**下一个 seq 段就属于 2026-09-14（915..2782）而它内部夹着 2027-10-19（928..2719）与 2025-08-10（976..1023）的行**；
- 于是"每行都属于早于截止日的日"的前缀在 seq 928 处就断了（那一行属于 2027-10-19，尚在窗口内）。

**这是脚本在拒绝做危险的事，不是缺陷**：本仓 ts 非单调（含回填与 2027 未来时间戳），按日删除**结构上**不可用。结论：**本卡交付的可用通道是"冷归档 + 锚点"，删除通道保留但在此数据形态下自动挡死。**

### 4.7 本脚本刻意不做的事（避免越界）

- **不重算、不写每日 Merkle 根**（`daily_roots.jsonl` 只读；卡面明令不得擅自重算）。
- **不向链上补"墓碑记录"**：追加必须走 `AuditChain.append` 的单写者 + 预留日志路径，直连 SQL 追加会破坏 `seq` 与 `prev_hash` 的纪律。
- **不做 `VACUUM`**（重写全库，风险与耗时都大；且会改库文件本身）。
- **不自动调度**（无 cron/scheduler 接线；按卡面只交付脚本）。
- **不重算两级哈希来"自证"归档**：归档的连续性由"相邻行 `prev_hash/self_hash` 链接 + 锚点的 `first_prev_hash/last_self_hash` + sha256"证明，避免复制 `chain.py` 的规范化逻辑（复制的东西会漂移）。要做"逐条重算"级别的复核，把归档回灌到一个 scratch 库后跑 `verify_chain(start_seq, end_seq, anchor_prev_hash)` 即可（脚本在 §4.5 已给出锚点参数格式）。

## 6. 数据完整性事实记录（**不属于本卡修复范围**，仅记录）

> 卡面要求：这些只记录、不修（修日根需重算，风险高）。本节数字均为本次只读实测，与 Q7 报告的口径差异已标注。

1. **DB 实况已变化**：Q7 报告时 53,948,416 B / **71,160 条**（seq 1..71160，journal 里有 71,161..72,260 待回放）；本卡实测已经是 **54,784,000 B / 72,297 条**（seq 1..72,297）。
   ⇒ 说明期间有进程启动过并把预留日志回放了（71,161..72,260），随后继续追加到 72,297。
   **本卡会话期间库还在被继续追加**（另一并行任务 D2 的 `skill.registry.set_enabled` 记录出现在链头）：72,289 → 72,297。这就是"修复前/后两次 benchmark 行数差 8 行"的原因，也是所有数字都标注了行号口径的原因。
2. **.seqjournal 回放机制正常**（当前 journal 2,049 行 / 1,342,128 B），**本卡未改动该机制**。
3. **日根缺陷（沿用 Q7，未重验）**：9 条日根 ed25519 验签全部通过，但 8 个有记录的 UTC 日无根（含占全链 71% 的 2026-09-23）；**2026-09-21 的根与当日实际不符**（`leaf_count=235` vs 实际 245）⇒ `verify_daily_root('2026-09-21')` 必然 FAIL。
   **本卡没有调用 `verify_daily_root`、也没有重算任何日根**（见 §7）。
4. **ts 含未来时间戳**：`ts_max = 2027-10-20T11:52:06`，`ts_min = 2025-08-10T12:14:03`；17 个不同 UTC 日。这条直接影响保留策略：**"按 ts 切窗口"必须与"按 seq 前缀删除"分开判定**（§4.3）。
5. 本卡新增发现（供后续卡参考）：**日块与 seq 不同序**（2027-10-19 的 seq 928..2719 夹在 2026-09-14 的 915..2782 里）。任何按 ts 做区间操作的代码都必须先验 seq 连续性。
