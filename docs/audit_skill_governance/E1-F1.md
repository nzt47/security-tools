## 2. 第 2 步：矛盾定位

### 2.1 生产就绪判定到底在等什么信号

\`EmbeddingIndex._ensure_worker()\`（\`agent/tool_router_hybrid.py:971\`）只等**一行 JSON**：
worker 脚本（\`:672\` 的 \`_WORKER_SCRIPT_EMBEDDING\`）在 \`SentenceTransformer(model_name)\` **返回之后**才 \`print(json.dumps({"type":"ready",...}), flush=True)\`（\`:685\`）。
读取点 \`:1008\` \`_readline_with_timeout(self._proc.stdout, self._WORKER_STARTUP_TIMEOUT)\`；超时 ⇒ \`:1016\` \`embedding.worker.ready_timeout\` + \`kill()\` + \`_init_failed = True\` ⇒ \`:839\` \`'degrade_to': 'bm25_only'\`。

**所以「ready 时间」= 「子进程解释器启动 + import torch/sentence_transformers + \`SentenceTransformer()\` 构造」的总时长。** 实测构成（§1.2 离线）：\`import_torch 1.91 + import_st 14.13 + ctor 2.03 = 18.11 s\`。**在线时 \`ctor\` 这一项从 2.03 s 膨胀到 >400 s。**

### 2.2 根因（可复现、可证伪）

\`_WORKER_SCRIPT_EMBEDDING\` 开头只设了两个变量（\`tool_router_hybrid.py:674-675\`）：

\`\`\`python
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
os.environ.setdefault("HF_HUB_DISABLE_XET", "1")
\`\`\`

**没有** \`HF_HUB_OFFLINE\`。于是 \`SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")\` 走**在线**解析路径：huggingface_hub 对仓库内**每个文件**发 \`HEAD\` 请求（含 \`adapter_config.json\`/\`processor_config.json\` 这类本地缓存里根本不存在的可选文件），每次握手 21 s 超时、**每次重试 5 遍并按 1s/2s/4s/8s/8s 退避**。文件数 × 5 次 × 21 s ⇒ **分钟级到十分钟级**。

证据链（每一环都可独立复现）：

| 环节 | 证据 | 位置 |
|---|---|---|
| 子进程卡在 HF 在线解析，不是 torch / 不是管道 | \`'...handshake operation timed out' thrown while requesting HEAD https://hf-mirror.com/.../adapter_config.json\` + \`Retrying in Ns [Retry k/5]\` | \`decomp_online.err.txt\`、用例 C 的 \`stderr_tail_after_kill\`、用例 E 的 16 行 stderr |

| 去掉网络后整条链就正常 | 同脚本 \`HF_HUB_OFFLINE=1\` ⇒ \`READY t=18.11\` | \`decomp_offline.out.txt\` |
| 生产路径也随之恢复 | \`_ensure_worker() ok=True elapsed=23199.96ms load_time_sec=4.0 available=True\`；\`retriever_degraded=False @25.03s\`；真实 hybrid 查询 \`embed_candidates=10\`、\`fused_candidates=15\` | \`fixprobe_offline.log\`（§3.2） |

### 2.3 「preheat / 线程路径竞态或死等」——**证伪**

任务点名的怀疑对象。反证是**三次非线程路径同样失败**：

- 用例 **A**：\`thread_name = "MainThread"\`，**完全不经过 preheat 线程**，Popen 参数与生产逐字相同 ⇒ 30 s 超时。
- 用例 **C/E/F**：同样 \`MainThread\`，抬到 300 s ⇒ **三次全超时**。
- 用例 **D**：甚至**不构造 \`EmbeddingIndex\`**，直接 \`subprocess.run([python, "-c", _WORKER_SCRIPT_EMBEDDING, model])\` ⇒ 600 s 超时、无输出。

⇒ **「直跑能成功 / 生产不能成功」不是路径属性**。E1 的 4 号（直跑 55.6 s 成功）与 5 号（直调 \`_ensure_worker()\` 96.9 s 成功）观测，是在一个**重尾分布**上抽到的两次偏快样本；本卡抽到了偏慢样本（D > 600 s）。E1 的 6 号「安静机器仍 300 s 失败」与 2/3 号则是偏慢样本。**两边都是同一个原因，不存在需要额外解释的第三种机制。**

### 2.4 「探针缓存把一次失败固化」——**证伪（但缓存本身确实是固化值）**

- 任务要求优先查这条，结论是**否定**，且用**运行时**证据而非仅靠 grep：
  磁盘上确实是固化负值：\`data/.embedding_probe\` = \`{"available": false, "probed_at": 1784737215.8083909}\`（写入时间 **2026-07-23 00:20:15**，早已超过 \`_PROBE_CACHE_TTL = 7 天\`）。
- **但它不在生产路径上。** \`probe_path_proof.py\` 把 \`_ensure_st_checked\` / \`_read_probe_cache\` / \`_write_probe_cache\` / \`_run_embedding_probe\` 全部换成「一旦被调用就抛异常并记录」的毒丸，然后跑真实的生产启动路径（\`EmbeddingIndex.preheat\`）：

\`\`\`json
{"probe_path_calls": [], "worker_spawned": true, "worker_pid": 13244,

  **探针链一次都没被调用，而 worker 照常被拉起。**

- 该结论与仓库既有审计文档 \`docs/audit_skill_governance/Q3_index_rebuild.md:25,334-335\` 独立一致。

⇒ 陈旧负缓存**无害**（因为整条链是死代码）；同时这也意味着当初为修「负结果永久固化」而加的 TTL 机制**从未生效过**。

### 2.5 「stdio 缓冲 / 命名管道」——**证伪**

- 用例 **F**（\`stderr=DEVNULL\`）：300 s 仍超时 ⇒ 与 stderr 背压无关。
- 用例 **E**（实时抽干 stderr）：300 s 仍超时，且抽到的 stderr 总计仅 16 行 ≈ 1.1 KB。
- 用例 **A** 失败时 \`stderr_len_after_kill = 0\`（30 s 时子进程连第一次 HEAD 都还没超时完）。
- 子进程用的是 \`print(..., flush=True)\`（\`:685\`），不存在 Python 层缓冲积压。
- 命名管道在本机**可用**：\`cwd=仓库根\` 下 \`python -c\` + 三根 \`PIPE\` 的 Popen **成功建立**（pid 正常、\`stdout\` 可读、\`stderr\` 可读，用例 E 收到了 16 行）。

### 2.6 为什么这个机制判定不受「机器不安静」影响

争用会让耗时变长，但**不可能**解释下列事实：
1. 端点在**任何**负载下都 21.0 s 连接超时（4/4），而本地缓存 0.84 s；
2. **同一台机器、同一时刻**，唯一差别是 \`HF_HUB_OFFLINE=1\`，结果 18.11 s vs >420 s（相差 >23×）；
3. 失败时 stderr **逐字指着** \`HEAD https://hf-mirror.com/...\` 的握手超时与 5 次重试；
4. 历史日志显示同一段代码在同一台机器上曾是 2.7 s。

### 3.1 先说**不是**修法的三个选项

| 选项 | 为什么不行 |
|---|---|
| **抬高 \`_WORKER_READY_TIMEOUT\`（30 → 240/300 s）** | **已被本卡证伪为无效**：C/E/F 三次 300 s 全超时、D 600 s 超时。就绪时间上限由「文件数 × 5 次重试 × 21 s」决定，不是常数能覆盖的。**E1 的三次实验已经证明了这一点，本卡把原因补上了。** |

### 3.2 推荐修法（**唯一有实测支撑的**）

**核心动作：把 worker 的模型解析从「在线」改成「缓存优先、缓存未命中才联网」。**

\`_WORKER_SCRIPT_EMBEDDING\`（\`tool_router_hybrid.py:672-689\`）里把
\`\`\`python

\`\`\`
替换为（示意，约 6 行；**留给 B3-W / 后续卡实施**）：
\`\`\`python
from huggingface_hub import snapshot_download
try:
    model_path = snapshot_download(model_name, local_files_only=True)   # 缓存命中：0.84s，零网络
except Exception:
    model_path = model_name                                             # 缓存未命中：退回原在线路径
model = SentenceTransformer(model_path)
\`\`\`
并配套（可选、同样小）：\`os.environ.setdefault("HF_HUB_ETAG_TIMEOUT", "3")\`、\`os.environ.setdefault("HF_HUB_DOWNLOAD_TIMEOUT", "3")\`，让「确实要联网」时快速失败而不是 5×21 s。

### 3.3 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **缓存未命中时行为变化** | \`local_files_only=True\` 失败会走 except 退回在线路径，与现状等价；但若实施成「无条件 offline」，则新机器/缓存被清后 worker 会直接 \`init_failed\` ⇒ 永久 \`bm25_only\`。 | 必须保留 fallback（上面的 \`try/except\` 形式），**不要**简单粗暴地全局设 \`HF_HUB_OFFLINE=1\`。 |

| **影响面越界** | 若把 \`HF_HUB_OFFLINE=1\` 放进进程级 \`.env\`，会连带影响 reranker / \`memory/vector_store\` 等所有 HF 使用者。 | 把改动**限制在 worker 脚本内部**（子进程 env 只影响该子进程）。 |
| **B3-W 冲突** | 该文件正在被别的卡修改。 | 本卡只出方案，不动代码。 |

### 3.4 不修的后果

1. **工具检索的向量腿在生产上继续恒为 \`bm25_only\`** —— 「靠混合检索提升召回」的全部收益当前为 0；\`alpha=0.5\` 的融合路在真实服务里从未生效过。

3. **\`/api/health\` 会持续报 \`degraded / degrade_to: bm25_only\`**，把一条**环境故障**长期呈现为「已知降级态」，掩盖真实可用性。
4. 每次服务冷启动都会**在后台白烧 30 s**（且每 5→10→20 s 退避重试至多 3 次）去拉一个**注定失败**的 worker，做无用功。

## 4. 是否复现 E1 的失败（如实）

**E1 的失败观测：复现。E1 的成功观测：未复现。因此 E1 表述的「矛盾」在本卡不成立。**

| E1 的条目 | E1 观测 | 本卡结果 | 判定 |
|---|---|---|---|
| 1 生产默认 30 s ⇒ 降级 | ready_timeout / bm25_only | 用例 A 30.01 s 超时；用例 B \`bm25_only\` | **复现** |
| 2 抬到 240 s | \`preheat.failed elapsed_ms=240208\` | （本卡取 300 s）用例 C 300.02 s 超时 | **复现**（同类） |
| 3 抬到 300 s | \`elapsed_ms=300146.78\` | 用例 C/E/F 三次 300.02 s 超时 | **复现** |
| 4 直跑 worker 源码 | 55.6 s ready，rc=0 | 用例 D **600 s 超时，stdout 空** | **未复现（反证）** |
| 5 直调 \`_ensure_worker()\` | 96.9 s 成功 | 等价形状 A/C/E/F 全部超时 | **未复现（反证）** |

## 5. 顺带发现（本卡不修，登记给后续卡）

1. **\`_ensure_worker\` 会在 worker 尚未就绪时就返回 \`True\`**（\`:987-988\` 只检查 \`_proc.poll() is None\`）。于是请求线程会在 worker 还在加载模型时向它写 \`encode\` 请求，然后 \`_readline_with_timeout\` 读到的**第一行是 \`{"type":"ready"\`** ⇒ \`embedding.encode.unexpected_msg\`（\`:1118\`）返回 \`None\`；而那行真正的 \`embeddings\` 响应留在管道里，会被**下一次**查询当成自己的答复读走 ⇒ **查询↔向量错位**。服务每次启动后约 30 s 内到达的请求都可能踩到。
2. **worker 进程泄漏（已实测）**：preheat 是 daemon 线程（\`:1382\`），父进程退出时线程随之消失，而**子进程不会被回收**（无 \`atexit\`、无 Job Object）。实测抓到 2 个孤儿：\`pid=11440\`（父 19944 已消失）、\`pid=14328\`（父 12240 已消失），各占 **451~454 MB** 且 CPU 增量为 0（即已 ready 后空转阻塞在 stdin）。\`EmbeddingIndex\` **没有公开的清理口**（只有只在错误路径上调用的私有 \`_cleanup_proc\`，\`:1157\`）。
3. **\`worker_health()["mode"]\` 会撒谎**：\`:932\` \`"bm25_only" if self._init_failed else "hybrid"\`。本卡在 spawn 后 6 s 采样得到 \`mode: "hybrid"\` 而 \`available: false\`。\`app_server.py:1479\` 用 \`retriever_degraded\` 并集兜住了，但裸字段仍是误导性的。
4. **同一模式可能同样命中 reranker**：\`agent/tool_router_reranker.py\` 有一模一样的「子进程 worker + ready 握手 + 加载 HF 模型」结构（历史日志 \`:58\` 显示其 \`load_time_sec=2.47\`）。**本卡未验证**它是否也在付同样的 21 s×5 代价。
