## 1. 先查触发源（硬伤 2）：**没有幽灵调用方，输入就是那一次请求自己的输入**

### 1.1 结论（一句话）

> `ping-21ec4378` 不是"服务内部某个非用户路径"写进去的：它是**会话 `b2ab_sink_OFF` 里一次真实
> `/api/chat` 请求**（`message="ping"`）学出来的，学习用的输入 = 该请求自己的输入，
> 工具步骤 = 该请求自己那一次 `search_memory` 调用。该会话里这样的 `ping` 请求共 **96 条**，
> 发送方是执行 B2「路由事件 sink A/B 对照」的**探针客户端**（不是服务内部、也不是别的会话）。

### 1.2 证据链 A（主证据）：会话消息流水里有 96 条 `ping`，且**唯一一次带工具调用的 ping** 与学习条目时间戳严丝合缝

1. 「一句 `ping` 也可能被 LLM 顺手调一次 `search_memory`」⇒ 旧代码会把它固化成一条工作流；
2. 旧代码**没有去重**：96 次同类请求会把垃圾一遍遍写进仓库（有 id 碰撞兜底，但换会话/换措辞就各成一条）。

## 2. 硬伤 1 修复：真签名口径 + 同任务去重

### 2.1 口径（可复算的规则；实现见 `agent/workflow_learning/learner.py`）

```
token      := 英文/标识符整词（小写化，长度 >= 2）
            | 中文：先按中文字停用字（复用既有 _STOP_WORDS）把汉字串切成"词段"，
              再对每段取 2 字滑窗（bigram）
签名        := tokens 去重 -> 字典序排序 -> 用 "|" 拼接；无 tokens -> "general"（SIGNATURE_FALLBACK）
tokens 上限 := 32（按首次出现序截断：句首承载任务意图；防止超长输入让签名线性膨胀）
```

**为什么这是"真签名"**：

- 旧口径产出的 `python|件|所|文|有|目|统|计|里|项` 里 9 个 token 是**单字**；新口径每个 token
  **至少 2 个字符**，正好等于仓库里唯一的"区分度"政策 `admission.MIN_TRIGGER_CHARS = 2`
  （admission 模块 §2 早已判定"中文单字无区分度"）⇒ 签名与准入政策同源，不引入第二套口径；
- 它是**输入的函数**（无状态、无时间、无随机）：同一输入恒得同一签名 ⇒ 可作去重键；
- 它同时被写进 `matcher` 的索引文本（`matcher.py:187`），语义化后不再往匹配面扩散单字特征。

### 2.2 实测对照（新旧签名）

| 输入（FINDINGS 里的原样数据） | 旧签名（实测/转储） | 新签名（本卡实测） |
|---|---|---|
| `统计项目里所有 Python 文件的行数并保存报告` | `python|件|所|文|有|目|统|计|里|项` | `python|保存|存报|并保|所有|报告|数并|文件|目里|统计|行数|计项|里所|项目` |
| `把代码仓库打包成 zip 压缩包` | `zip|仓|代|包|压|库|成|打|码|缩` | `zip|仓库|代码|包成|压缩|库打|打包|码仓|缩包` |
| `读取 JSON 配置文件并转换为 YAML 格式` | `json|件|取|并|换|文|置|读|转|配` | `json|yaml|件并|并转|换为|文件|格式|置文|读取|转换|配置` |
| `帮我列出当前工作目录下的文件` | `件|作|出|列|前|工|当|录|文|目` | `作目|出当|列出|前工|工作|当前|文件|目录` |

旧口径下这 4 条互不相同，但**同一输入学 3 次得到 3 条签名完全相同的条目**
（`wf-f19dc52c`/`wf-c7499f27`/`wf-28f2775d`）——新口径保留"不同任务不同签名"，
并用**去重**处理重复，而不是继续靠签名区分。

局限（如实登记）：仓库未依赖分词器（`jieba` 不在依赖里），2 字滑窗会含少量跨词噪声 bigram
（如 `目里`/`库打`/`数并`）。它们对**去重**与**区分**无害（同一输入恒得同一集合），
但作为"给人看的任务标识"不够干净 ⇒ §8 遗留 1。

### 2.3 去重语义（关键设计决策，均有单测固化）

实现位置：`agent/workflow_learning/service.py`（`learn_from_interaction` → `_find_same_task` → `_merge_observation`）。

1. **去重键 = 从 `entry.source_user_input` 重算的规范签名**，而不是库里存的 `task_signature`
   字符串。理由：存量 8 条的 `task_signature` 是旧"字符清单"口径，拿新签名比字符串**永远不相等**，
   那样既有的 `zip-d2968c59` 等条目会在下次学习时**再新生一条**（垃圾继续增长）。
   实测（§2.4 实测 B）：对 `把代码仓库打包成 zip 压缩包` 的一次学习**直接并入了既有的
   `zip-d2968c59`**（它库里的签名仍写着旧的 `zip|仓|代|…`）。
2. **同任务重复出现累加 `observed_count`**（新字段，默认 1），不新建条目；
3. **跨会话样本数不丢**：新增 `source_sessions` 累积来源会话，`repository.count_distinct_sessions`
   与 `signatures()` 都改为"`source_session_id` ∪ `source_sessions` 去重计数"。
   若不做这一步，去重会把 `admission.MIN_CROSS_SESSION_SUPPORT = 2`（自动升格门槛）**永久焊死在 1**；
4. **不复活、不覆盖**：合并只动 `observed_count` / `source_sessions` / `task_signature` / `updated_at`，
   `steps`、`name`、`status`、`success_count`、`confidence` 一律不动 ⇒ 归档条目不会被"学回来"；
5. **签名对齐**：合并时把条目 `task_signature` 对齐到规范签名（去重键就是它），存量脏签名在**被重新
   观察到之后**自然收敛；未被重新观察的条目保持原样（本卡**不**改存量数据，见 §6 清洗建议）；
6. **退化输入不落库**：`canonical_signature` 返回 `general`（无实词）时 `learn()` 直接抛
   `WorkflowLearningError(code=WF_LEARN_FAILED)`，仓库零写入（`""` / `"???"` / 单个汉字 / `"你好"`）。

## 4. 必答：准入规则是什么 / 谁消费 / 到底有没有意义

### 4.1 准入规则（唯一判定源 `agent/workflow_learning/admission.py`）

三条**结构性**门槛（`force=True` 也越不过，见 `admission.py:95-100`）：

| 门槛 | 常量/值 | 拒绝码 | 语义 |
|---|---|---|---|
| 步骤数下限 | `MIN_STEPS = 2` | `STEPS_TOO_FEW` | 1 步 = 一次工具调用，没有编排价值（且 `generator._compute_priority` 给"≤3 步" +20，制造优先级倒挂） |
| 触发词区分度 | `MIN_TRIGGER_CHARS = 2` | `NO_DISCRIMINATIVE_TRIGGER` / `IMPURE_TRIGGER_LIST` | 单字触发词（中文按字切分的产物）不得入库、不得混入 |
| 状态/启用 | `active` + `enabled` | `NOT_ACTIVE` / `DISABLED` | 草稿/归档不进候选池 |

**统计性**门槛（只作用于"自动升格为 Skill"，人 `force` 可越过）：`MIN_CROSS_SESSION_SUPPORT = 2`
（同签名 ≥2 个不同会话）、`success_count >= 5`、`confidence >= 0.7`、`priority` 达标。
三处复用同一份判定：`matcher.register/match`（候选准入）、`learner.learn`（不达标落草稿）、
`skill_converter` / `list_convertible_workflows`（转技能准入）。

F11 看到的 `【准入未通过 STEPS_TOO_FEW】`（`ping` 条目）就是第一张表第一行；
不达标条目**仍在仓库里**（`status=draft`，可按 ID 人工执行）——这是 S10-01 的既有政策，本卡不改。
