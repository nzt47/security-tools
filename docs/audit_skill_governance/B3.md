### 4.1 缺陷① planning 与 llm 对同一请求双重计数 —— **需另开卡**

- 位置：agent/orchestrator/orchestrator.py:1312（_record_intent_layer("llm")，无条件先执行）
  与 :1516（旧规划路 _record_intent_layer("planning")）。
- 触发条件（**读码结论，未实测复现**）：wire 规划**失败回退**时 _wire_planning_used=False ⇒ 走 1312 计 llm；
  而 _planning_mode 只在 wire **成功**时才被置 False（:1292）⇒ 旧规划段 :1506 仍会执行，
  :1516 再计一次 planning，且其响应**覆盖**了刚拿到的 LLM 响应 ⇒ 同请求计 2 层。
- 修法约束：prometheus 的 Counter 是**单调**的，无法"改判/回滚"，所以必须在**计数之前**判定。
  推荐（保行为不变、保 TD-1 的 llm/llm_error 配对不破）：
  把 1312 的计数改为**置位** _llm_layer_counted = True，在旧规划段判定完成后**只计最终生效的那一层**；
  若选择"直接禁掉 wire 失败后的旧规划段"，则同时消除了这一次**重复规划调用**（行为变更，需回归）。
- 本卡已做的替代：不动它；单测 §3.1 的「既有指标不回归」保证没有把它弄得更坏。

### 4.2 缺陷② tool_retrieval 与 route_decision 无法关联 —— **需另开卡 + 审计描述需更正**

**实测更正（重要）**：审计 T4 行写「tool_retrieval 只带 query_hash、**无 trace_id**」。
实测**该字段存在**，但它是 log_dict() **现场随机生成**的，与请求无关：

### 4.5 为什么 memory/llm_service.py 一行未改（而不是忘记）

卡点允许我在此文件「只加 usage 解析与计量」。**实测后决定不加**，理由是避免**同一个响应被计两次**：

- 生产三条出网路径最终都走 LLMService._get_client().chat.completions.create：
  orchestrator.py:3503 → :3597、tool_calling.py:684 → :710、memory/llm_service.py:296 → :304（_do_chat）。
- agent/llm_monitor.py:665-721 的 _patched_get_client 已经**包装了这个 create**，
  并调用 create_from_api_call(response_obj=...)，即**同一响应对象**已经到达我的计量点。
- 若再在 _do_chat 里计一次，就会对同一 token 双计（这正是缺陷①同一类错误的翻版）。
- 单测 test_字符串响应不产生usage指标_也不双计 固化了这个不变量：
  _patched_do_chat 拿到的是**字符串**（响应已被 _do_chat 转成 text）⇒ usage 不可用 ⇒ 不计数。
- 证据（该包装在生产确实生效）：data/llm_monitor_last.json 在**本卡改动之前**（20:46:58）
  的 source 就是 tool_calling，说明 create 包装一直在跑；本次 10 条记录 source 全部 tool_calling。
