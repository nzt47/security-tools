## 4. 流式 usage 的形状、到达时机、降级与中断处理

### 4.1 形状与到达时机（实测）

- **到达时机**：**最后一个 data chunk**，即模型生成完成之后（本端点与 `finish_reason=stop` 同块）。
- **本端点的形状**：`choices` **非空**（`[{"index":0,"delta":{"content":""},"finish_reason":"stop"}]`），
  `usage` 与之**同级**；之后再一行 `data: [DONE]` 哨兵。
- **OpenAI 规范形状**：可能补一个 `choices: []` 的**尾块**承载 usage。**两种形状都已覆盖**（§3.3 ①②），
  代理的取数逻辑写在 `choices` 判定**之前**，因此不依赖 `choices` 是否为空。
- 附带观察：带 `include_usage` 时，普通内容 chunk 会多一个 `"usage": null` 字段（对云枢不可见，因为 SDK 把它解析成 `None`）。

### 4.2 服务端不返回 usage 时的降级

- 代理里 `usage` 保持 `None` ⇒ 记录**照常落库**，字段维持既有语义 `usage_available=False`（不猜、不编、**不写 0 冒充命中率**）。
- `extract_usage` 本身对全 0 usage 也视作"未上报"，两层防线一致。
- **绝不因计量失败丢内容或抛异常**：代理只透传 chunk，计量在 `finally` 里 best-effort 完成（异常仅 `logger.debug`）。
- 请求侧：上游若**不认** `stream_options`（4xx），`memory/llm_service.py` 会**退回不带该参数的请求**，
  流式内容能力不受损，只回到"usage 未上报"的既有降级态。

### 4.3 客户端中断（用户关页面）

链路：Flask 关闭 SSE 生成器 → `GeneratorExit` 打进 `plugins/chat.py` 的 `for ... in llm.chat_stream(...)`
→ 打进 `chat_stream` 的 `for chunk in stream` → 关闭本代理的迭代器 → `except GeneratorExit` 置 `_ys_aborted`
→ `finally` 里 `_finalize()`。

- **usage 客观上会丢**：上游只在生成完成后才发 usage，中断时它**根本不存在**（不是云枢弄丢的）。
- **处理**：仍落**一条**记录（`usage_available=False`），记结构化日志
  `event=llm_stream_aborted source=… chunks=N usage_reported=False`；
  `error` 字段**保持空**——中断不是模型降级，若写成 error 会误触发 `model.degraded` 埋点。
- 同时**主动 `close()` 底层流**，不放任 HTTP 连接等 GC。
- 另有两道兜底：`close()` 与 `__del__`（消费方既没迭代完也没 close 时），`_finalize` 幂等、只落一条。

## 7. 未验证项与残留风险

1. **"不带 `stream_options` 也报 usage"只在 1 次冷请求上观测到**（787 prompt tokens、3 个 chunk）。
   是否对所有模型/所有长度/所有网关成立**未验证**；本卡因此仍显式开启 `include_usage`。
2. **`include_usage` 只在 `https://api.deepseek.com/v1` + `deepseek-flash` 上实测**。其他 OpenAI 兼容网关
   （自建代理、Azure、vLLM…）**未验证**；已加"不认该参数就无参重试"的降级，但该降级分支本身**没有真实触发过**。
3. **多轮工具循环（每轮一条记录）未做真实多轮实测** —— 本次工作台请求一轮即结束。
   逻辑上每轮的 `create` 各自产生一条记录，但**未实测**。
4. **真实"关页面"中断未实测**：中断路径只在离线打桩（`GeneratorExit`）下验证过。
5. **`duration_ms` 语义变化**：流式记录的时长由"create() 调用耗时"（改前 ≈290ms）变成"**整流耗时**"（改后 ≈954ms），
   与非流式语义对齐、更真实，但这是**行为变化**，依赖旧口径的下游需知悉。
6. **`response_full` 内容变化**：流式记录由 `str(Stream)` 变成 `{'usage': {...}}`（只有计量、没有正文）。
   流式正文仍**不入库**（保持既有隐私/体积口径），本卡未改。
7. **Prometheus 六指标**：端到端记录的 `call_cache_hit_ratio=0.8926 ≠ 0` 证明 `record_llm_usage` 已在流式路径被调用，
   但**累计计数器**（`llm_tokens_total{kind="cached"}` 等）未单独取数前后对照。
8. **`prompt_cache_hit_tokens` 的准确性依赖上游**：云枢只做透传与落库，不改写、不推算。
