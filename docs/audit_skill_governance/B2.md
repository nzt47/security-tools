## 2. 实现说明

### 2.1 复用了什么 —— 以及为什么不复用 setup_agent_logging

**复用的是 data/logs/<date>.jsonl 这个 sink 本身**：它由
agent/monitoring/loki.py:66-76 的 LokiClient._save_local_log 维护，行格式固定为
{"timestamp":…,"labels":{…},"message":"<json 字符串>"}，配置变更事件
（agent/monitoring/config_observability.py:230-234）走的就是它。
本卡只做「把路由事件接进这个既有通道」：LokiClient(enabled=False).push_log()，
即**同一个 writer、同一种行格式、同一个文件**，读侧 LokiClient.query_logs /
_get_local_labels 无需改动即可检索（message 保持字符串，因为读侧用的是
「query.lower() in message.lower()」这样的字符串包含匹配）。

**为什么不复用 setup_agent_logging(enable_file=True)**（Q5 建议的第一候选），读数依据：

| 读数 | 后果 |
|---|---|
| agent/logging_utils.py:479-481 先**清空 root 的全部 handler** | app_server.py:128 的 logging.basicConfig 控制台语义、:132-136 setup_readable_logging 的 formatter 会被一并拆掉 ⇒ 直接违反本卡要求 ③「不得破坏既有行为」 |
| :486-497 再自建一个 StreamHandler(sys.stdout) | 控制台输出渠道从 stderr 变成 stdout 且重复一份，既有 stderr 采集（logs/*.log，Q5 §6.3 那 114/110 条）会失配 |
| :504-513 的 file handler 用**纯文本 formatter** + 尺寸轮转 | 落下来的不是 JSONL，且文件名与轮转策略（size-based、.1 备份）与既有 data/logs/<date>.jsonl（按日期分文件）**不同源**，等于再造第二个 sink |
| handler 挂在 **root** 上（level INFO） | 会把**所有模块**的 INFO 全量落盘 —— 正是本卡明令避免的「无脑开全量」，与「只让路由决策类事件落盘」相悖 |
| :598-605 每次调用打 7 行 banner | 启动日志噪音，且与「复用既有 sink」无关 |

⇒ 结论：**复用既有 JSONL 通道（LokiClient），不复用 setup_agent_logging**。
没有新增任何日志框架、没有新增第二条写盘路径（全仓 data/logs 仍只有 1 个 writer）。

### 2.2 事件范围如何界定（不是无脑 DEBUG）

双重门 + 一个级别约束，均在 app_server.py L194-L203 常量区可见：

| 门 | 规则 | 效果（已实测） |
|---|---|---|
| ① logger 门 | handler 只挂 agent.orchestrator 与 agent.observability.tool_trace 两个 logger（**不挂 root**） | 其它模块的记录**根本不进入 handler**（单测断言：来自 agent.skills_mgmt.loader 的同名 action 事件既不落盘、也不计入 skipped） |
| ② action 门 | 记录 msg 为 dict（log_dict 产物），仅 action ∈ {orchestrator.process.route_decision, orchestrator.traffic.summary, tool_retrieval} 或前缀 ∈ {orchestrator.layer., orchestrator.intent_layer.} 才落盘 | 同一 logger 上的 orchestrator.llm.done / unknown 被丢弃（单测断言 written=0, skipped=2） |
| ③ 级别 | handler 级别固定 logging.INFO，全程不调 setLevel(DEBUG) | 层未命中（log_layer_result level=DEBUG）不落盘 —— **不影响分母**，理由见下 |

**为什么层未命中不落盘却不丢分母**：routing_observability.py:261 的 ctx.add_layer()
不区分级别地累积**所有**层（含 miss/DEBUG 那些），:291 又把整个 layer_results 全量写进
route_decision。所以**每条 route_decision 自带该请求的完整漏斗**。端到端实测正好抓到这一
点：请求 2 的 route_decision 里 layer_results = {input_guard: pass, workflow: **miss**,
template: hit} —— miss 作为分母留在同一行里（§4.2 原文）。这与 Q5 §3「110 条样本的
layer_results 键数即路由深度」的既有结论一致，无需新开 DEBUG 通道。

### 2.3 目标文件与行格式（与既有 sink 完全一致）

- 目标：data/logs/<date>.jsonl（date 取记录时间戳 record.created 的本地日期；
  LokiClient._save_local_log 内部同款算法），可用 CP_ROUTE_EVENT_SINK_DIR 覆盖目录（默认不覆盖）。
- 行：{"timestamp": <float>, "labels": {"app": "yunshu-route", "event": <action>,
  "level": <INFO/WARNING>, "logger": <record.name>}, "message": "<事件的完整 JSON>"}
- labels.app 固定为 yunshu-route，因此**筛选路由事件不需要解析 message**，
  且与既有配置变更事件（labels.app=agent-config）在同一文件内天然可区分。

### 2.4 装配时序（与 A1 的关系）

装配点写在 __main__ 内 **install_child_process_reaper()（A1 的 Job Object）之后、
guarded_startup(...) 之前**（app_server.py L2148-2172），三个理由已写进代码注释：
① 必须在 serve() 前（请求到来前）；② 必须在 Job Object 之后，以保持 A1 在那一行写下的
「本行以上只有模块导入与横幅打印，不 spawn 任何子进程」不变量逐字成立（本段会
os.makedirs + 打开文件，但不 spawn 子进程）；③ 与就绪门/看门狗零耦合（不调用
guarded_startup / cleanup_port_listeners，见 §5 静态核对）。

### 2.5 开关、幂等与失败姿态

- 开关：CP_ROUTE_EVENT_SINK_ENABLED（默认开启；0/false/no/off 关闭，大小写/空白不敏感）。
  关闭时**不装配**，并且会**摘掉已装的 handler**（单测覆盖「先开再关」）。
- 幂等：install_route_event_sink() 重复调用先 _detach 再装配，绝不叠加 handler
  （叠加会导致同一事件写多行；单测断言重复装配后 handler 数 = 1、1 次事件只写 1 行）。
- 失败姿态：装配异常（如 loki 模块缺失）只 warning 不阻断启动；单条写盘异常只累加
  failed 计数，绝不向业务线程抛出（单测用抛 OSError 的 stub client 验证）。
- 既有语义保留：不碰 root handler、不碰 formatter、不改 propagate、不改任何
  logging.basicConfig / LOG_REQUEST_PRINT 代码路径。

## 3. 不拖慢请求路径（同步写的论证 + 微基准原始输出）

**设计**：同步追加写（1 条事件 = 1 次 open+write+close），**不用** QueueHandler /
后台线程 / 缓冲区。理由：进程被 taskkill /F 时（本仓常见退出方式，见 app_server.py
的 A1/优雅关闭注释）异步队列里未刷盘的事件会丢，而「服务一重启路由决策就丢」
正是本卡要消灭的问题；用异步反而把问题从「重启丢」变成「重启和被杀都丢」。

**实测量级**（抽取同一份生产代码后跑微基准：2000 次写盘 × 2 轮，预热 50 次）：

~~~text

bytes per event line: 866.0 (total file 1775300 bytes)
json.dumps only us: mean=9.0

--- second run ---
events emitted: warmup=50 + measured=2000, written=2050, failed=0
per-emit us: mean=267.1 median=245.9 p95=339.5 p99=486.4 max=4117.0
~~~

读数：单次写盘 **中位 226–246 us、p95 289–340 us、最坏 2.5–4.1 ms**（最坏值出现在
被抢占的调度片）。成本几乎全在 open/close（对照：保持句柄的纯 append 只要 3 us），
JSON 序列化仅 9–10 us/条。按端到端实测的 **2 条/请求**算，请求路径新增
**约 0.45–0.54 ms（中位）**，相对实测请求耗时（0.5 s 起、LLM 路径可到秒级）
占比 < 0.1%，且发生在请求**收尾**（路由决策已定）而非关键等待路径上 —— 可接受。
（本段数字是微基准实测，不是估算；文件位于本地 NTFS 盘；微基准脚本写在
系统临时目录，不在仓库内。）
