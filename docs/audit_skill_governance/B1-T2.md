## 3. 修法：采用 B1 的改法 A（上移定稿，而不是事后改写）

卡内指定的顺序是「优先改法 A；副作用超出预期再退到改法 B」。**实测副作用为零**，
故采用改法 A。之所以不去走改法 B：B 需要新增一个幂等改写函数
（B1 建议放在 `agent/tools_prompt_guard.py`），而该文件是 **B1 的已交付成果、本卡明令禁改**
（任务卡【边界】），改法 B 在本卡约束下不可用；改法 A 不需要任何新函数，只用 B1 已经
交付并单测覆盖的 `tool_defs=` 入参。

### 3.1 "上移是安全的"——我自己复核（不只引用 B1 的结论）

再与"提示词侧名字"求交。脚本（仓库外 `%TEMP%\b1t2_dep_check.py`）与原始输出：

2. `:3385-3389` 渲染：

### 3.3 V2（`_call_llm_v2`）具体改动

V2 没有本地 `_tool_defs`（真正下发在 `ToolCallingService.chat_with_steps` 内部
——`agent/tool_calling.py:277 tool_defs = tools.get_tool_defs(whitelist=tools_whitelist)`），

1. `:4063` 起：`tools_whitelist = None` / `_v2_dispatch_defs = None` +

### 3.4 一处刻意的结构选择（如实披露）

`_tool_defs is None` 的**回退分支**除了上面 3.2 说的真实用途外，还同时满足
`tests/unit/test_tools_prompt_alignment.py:428` 的源码级断言：

```python
assert "_build_tool_status_text(expose_tools=allow_tools)" in src
```

那是**子串**断言，一旦三处调用点全部写成 `(expose_tools=allow_tools, tool_defs=…)`，
这个子串就消失了 —— 而该测试文件**不在本卡可改清单内**，我不会为了让它变绿去改测试。
所以这里保留了一个**真实可达**的未定稿分支（而不是为过测试硬塞一行）：
`self._llm` 为空、或定稿失败时，渲染确实回到默认口径，此时这行代码就是正确实现。
`allow_tools=False` 的语义由 `expose_tools=allow_tools` 继续承担（两条分支都传了它）。

### 3.5 降级路径的行为变更声明（唯一一处非等价改动）

被上移的 40 行原先位于「`if self._llm:` → `try:`」内，抛异常时由该 `try` 的
`except` 记 `orchestrator._call_llm.llm` 并以 `（抱歉，处理时遇到了问题: …）` 优雅返回。
上移后为避免"异常穿出 `_call_llm`"（`_call_llm` 的调用方不保证捕获），我在定稿块外
加了一层 `try/except`：**记 `orchestrator._call_llm.dispatch_defs_failed` 警告 →
`_tool_defs = None` → 按修复前口径继续本轮**。即：

* 触发条件：`_get_enabled_tools_whitelist` / `get_tool_defs` / `prune_tool_defs` 等抛异常（生产未观测到）；
* 行为变化：**由"整轮返回错误文案"变为"降级为默认渲染口径继续本轮"**（工具侧不因此少下发，
  `prune_tool_defs` 那段本来就有自己的 `try`）；
* 依据：不变量优先 —— 宁可让渲染回退到修复前口径，也不让主链路因为"统计工具数"而中断；
  该分支在 ``2.3` 与 `5` 的实测中均未触发（日志无 `dispatch_defs_failed`）。

V2 同理（`_v2_dispatch_defs = None`），且 V2 出网块仍是原来的大 `try`。
