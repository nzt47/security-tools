def sha256_file(p):
    h = hashlib.sha256()
    with open(p, "rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()


def stat_line(p):
    st = os.stat(p)
    return f"size={st.st_size} mtime_ns={st.st_mtime_ns} sha256={sha256_file(p)[:32]}"

## 3. 核心技术障碍与方案

### 3.1 障碍的准确定性

`daily_roots.jsonl` 是**只追加**的封印日志（外层根链 `prev_entry_hash → entry_hash` 保证
**任何一行都不被删改**）。同一天可以有多条记录，于是"哪一条是有效日根"必须被**显式定义**。
D5 之前的实现把这件事交给了"文件里第一条"，而**写侧**（`daily_merkle_root(force=True)`）
只会**追加**。写侧追加、读侧读第一条 ⇒ 重封写下的新根永远读不到。
⇒ **这是读侧的取用语义缺陷，不是写侧缺陷**，所以"再写一条"这条路本身修不好它。

### 3.2 三条候选路线与取舍（本卡选 (a)）

| 路线 | 说明 | 判定 |
|---|---|---|
| **(a) 明确取用语义：默认取"该日最后一条"，并支持 `seal=k` 取指定序号** | 改 `get_daily_root/verify_daily_root` 的解析规则；文件保持只追加 | **采用**。它是唯一"不需要改写任何历史字节"就能让重封生效的方案；且把隐式行为变成显式契约 |
| (b) 重封时"同时写入一个能被现有读取逻辑取到的位置"（先写占位再覆盖） | 例如把新根塞到旧根**前面**，或原地改写旧行 | **否决（两条都不可行/不合规）**：<br>① 把新行插到旧行**前面**在只追加文件里做不到（会破坏外层根链，等于重写整个文件）；<br>② 原地**改写**旧行 = 修改合规证据，本卡明令禁止（也正是"删除/修改历史链行"的事故形态） |
| (c) 其他 | 例如"验签时遍历该日全部记录、任一条通过即算通过" | **否决**：那是**降低**篡改检出能力（一条伪造根 + 一条真根就能让该日"通过"），也会让"该日有几条根、哪条生效"变得不可判定 |

选 (a) 的直接理由：**它把"后发现的事实应当取代先前的记录"这条语义写进代码**，
而这正是"只追加封印日志"这种结构的常规读法（后写覆盖先写）；同时它**不删除任何字节**，
外层根链与逐条 ed25519 签名仍然完整保护每一条历史记录。

### 3.3 取用语义的最终定义（`resolve_daily_root`，三处共用）

- `seal is None`（默认）：该日**最后一条**记录 —— 最新封存生效；
- `seal=k`：该日第 k 条（1 起、按文件行序）—— 取证 / 历史回放用，`k=1` 即"最早那次封存"；
- `k` 越界或该日无记录 → `None`（保持 `get_daily_root` 的 Optional 契约，不抛异常）；
- 该规则**只定义取用**，不校验、不写盘；"这条记录可不可信"仍由
  `verify_daily_root`（重放 + 签名 + 外层根链）回答。
- `verify_daily_root` 的**判定逻辑一字未改**，只在结果里回填 `seal_index/seal_total`，
  让"验的是第几条、一共有几条"可被脚本直接断言。

### 3.4 向后兼容论证（既有 9 条有效根的验签行为不变）

**生产实测**：9 个有日根的 UTC 日里，只有 `2026-09-14` 有**两条**记录（第 2、7 行），
两条的 `root_hash / leaf_count / first_seq / last_seq / first_self_hash / last_self_hash`
**逐字相同**（只有 `created_at / prev_entry_hash / entry_hash` 不同 —— 那是重封时必然变化的字段）。
⇒ 解析规则从"取第一条"变成"取最后一条"，对这 9 条根**没有任何可观测差别**：

- **D3 的巡检脚本**（`scripts/audit_governance_check.py`，只读）在修复前后**输出逐字相同**：
  G3 仍然是 `OK 2026-09-14 叶子=82（根记录 82） 签名=True 根链=True`，G1~G4 结论不变
  （`FAIL=0 WARN=2`），见 §6.6。它正是通过 `verify_daily_root` 读取日根的消费者。
- **单测锁定**：`test_existing_valid_roots_verification_unchanged` 用"同日两条内容相同的记录"
  （生产 09-14 的同形构造）断言：单条记录的日子"默认取用 == 显式 `seal=1`"逐字段相同；
  两条记录的日子 `seal=1` 与 `seal=2` 的 `ok/recorded_root` 相同。
- **未改磁盘格式**：`DailyRoot` **没有新增字段**，所以既有 10 行日根的 `entry_hash`
  重算口径完全不变（`core_dict()` 一字未动）；副本 `--apply` 前后的不变量核对里
  `root_chain=True` 也反复确认了这一点。

### 3.5 安全权衡与两条"护栏"（不隐瞒代价）

**代价（必须说清）**：取"最后一条"意味着"**能追加写 `daily_roots.jsonl` 的一方可以取代该日
既有根**"。修复前，"第一条生效"让追加者无法改变已生效的根。这是本卡引入的**真实能力变化**。

**为什么仍然接受**：
- 能追加该文件的一方，本来就能**整文件删除/截断**（那样 `verify_daily_root` 直接
  `root_not_found` / `root_chain_broken`，同样是失败），"只追加"从来不是针对
  写权限攻击者的屏障，而是针对**证据留存**的要求；
- 追加一条**伪造**根不会让篡改"通过"：`verify_daily_root` 会重算该日叶子并比对
  `root_hash`、校验签名、校验外层根链 —— 伪造根只会让该日**验签失败**（DoS 面，不是伪造面）；
- 真正防伪造的是**逐条 ed25519 签名 + 外层根链 + 台账链**，它们本卡一字未动。

**护栏 1（工具层）**：重封工具**拒绝**去重封"失败原因属**篡改类**"（`entry_hash_mismatch` /
`root_chain_broken` / `signature_invalid`）的日期 —— 因为那种情况下"追加一条新根"会把这条
发现从默认读路径上**抹掉**（该日立刻重新显示为通过），那是掩盖而不是修复。
必须由人显式加 `--allow-tamper-reseal` 才继续。实测见 `test_tamper_class_failure_is_refused_by_default`。

**护栏 2（取证层）**：被取代的记录**永不消失**，且可**显式取回**：
`get_daily_root(day, seal=1)` 拿旧根、`daily_root_records(day)` 列出全部（带文件行号）、
`verify_daily_root(day, seal=1)` 对历史记录**照旧如实报不符**
（副本实测：`verify(seal=1)=False root_hash_mismatch`）。

## 4. 不变量：**只允许新增日根记录**（合规证据的安全边界）

### 4.1 声明（逐条写死）

1. 本卡的所有写动作**只发生在** `<roots>`（默认 `data/audit/daily_roots.jsonl`），
   且**只以追加一行**的形式发生；
2. **绝不删除、绝不修改** `daily_roots.jsonl` 里的任何既有字节；
3. **绝不新增、删除、修改** 审计链台账 `audit_chain` 的任何一行（含任何 `DELETE/UPDATE/INSERT`）；
4. **绝不生成**签名私钥（私钥缺失时拒绝 `--apply`，因为 `RootsSigner` 在密钥缺失且允许
   生成时会**现场生成并落盘**，那会改变日根的签名身份）；
5. 若某处**必须改写历史**才能修 ⇒ **停下来报告并等**（本卡实测未遇到这种情形：09-21 只需追加）。

### 4.2 代码保证（不是口头承诺）

| 层 | 机制 | 位置 |
|---|---|---|
| ① 框架层：不具备写台账的能力 | 台账实例一律以 `AuditChain.reader(...)` 打开（`role="reader"`），框架在 `append()` 入口直接 `raise ReadOnlyChainError` | 脚本 `main()` |
| ② 运行期断言：日根文件只追加 | 写前把文件读成 `roots_bytes0`，写后断言 `roots_bytes1.startswith(roots_bytes0)` 且行数不减；违反 ⇒ 退出码 4 | 脚本「不变量核对」段 |
| ③ 运行期断言：台账零写入 | 写前/写后比对台账**结构指纹**（行数、min/max seq、链头 `self_hash`）与**文件 sha256**；结构变化 ⇒ 退出码 4 | 脚本「不变量核对」段 |
| ④ 静态自检：源码里不许出现写台账的 SQL | `_self_check_no_destructive_sql()` 在 `main()` **第一步**扫描本脚本源码，命中任何写台账的 SQL 关键字即拒绝运行（退出码 4）。关键字在本函数里**拆成两段拼接**，否则这条自检会命中它自己 | 脚本 `_self_check_no_destructive_sql` |

第 ④ 层还配了**负向探针**（`test_destructive_sql_self_check_is_not_vacuous`）：
把一段含写语句的文本写成临时文件，断言自检**真的会红** —— 否则这条自检就只是恒绿的空断言。

单测另有两层数据级保证：
- `test_apply_never_calls_chain_append`：把 `AuditChain.append` 换成抛异常的桩，
  `--apply` 全流程**仍必须跑通**（证明流程一次都没碰写路径）；
- `test_apply_only_appends_roots_and_leaves_chain_rows_untouched`：`--apply` 前后
  台账 **13 列 × 全部行**逐行比对相同，且 `audit_chain.db` **整个文件的 sha256 不变**。

## 5. 工具：`scripts/audit_reseal_daily_root.py`

### 5.1 用法

`@text
python scripts/audit_reseal_daily_root.py                      # dry-run：列出全部缺根日（默认）
python scripts/audit_reseal_daily_root.py --date 2026-09-21    # dry-run：只看某日
python scripts/audit_reseal_daily_root.py --all-missing        # dry-run：只看缺根日
python scripts/audit_reseal_daily_root.py --date 2026-09-21 --apply
python scripts/audit_reseal_daily_root.py --all-missing --apply
`@

| 参数 | 语义 |
|---|---|
| `--apply` | **只有加它才会写**；缺省 dry-run（只打印将要做什么 + 将要写什么根 + 写完会长什么样） |
| `--date YYYY-MM-DD`（可重复） | 限定某日（补封或重封都走它；已正确的日会**幂等跳过**） |
| `--all-missing` | 补齐所有"有记录但没有日根"的日 |
| `--exclude` / `--include-future` / `--allow-degraded-signing` / `--allow-tamper-reseal` | 安全阀（见 §5.2） |
| `--db` / `--roots` / `--key-path` | 路径覆盖（副本演练用） |

**重封后立即自验**：每个日期写完都调 `verify_daily_root(date)` 并打印
`ok / reason / 叶子数 / 记录数 / seal=i/n / sig / root_chain`；任一不通过 ⇒ 打印 detail 并**退出码 3**。

### 5.2 行为边界（每条都有单测）

1. **`--all-missing` 是窄口径**：只补"**没有任何日根**"的日，**刻意不**顺手重封"已有根但验签不过"的日
   —— 后者必须 `--date` 点名。理由：批量动作最容易把"发现问题"变成"掩盖问题"（见 §3.5 护栏 1）。
2. **未来日期默认跳过**：`2027-10-19/20` 这类（晚于 UTC 今日）的日期默认**只报告不处理**，
   必须显式 `--include-future` 才封根（本卡未处理它们，见 §8）。
3. **无记录的日期拒绝服务**：`--date` 一个台账里没有任何记录的日期 ⇒ 退出码 2；
   `reseal_daily_root` 亦返回 `reason="day_not_found"` 且零写入
   （空日根是"该日无新增"的**绝对断言**，不给没有记录的日期凭空下这种结论）。
4. **篡改类失败默认拒绝**（§3.5 护栏 1）⇒ 退出码 2。
5. **私钥缺失拒绝 `--apply`**（退出码 2），dry-run 不需要私钥；实测未生成私钥文件。
6. **`--apply` 必须带目标选择器**（`--date` 或 `--all-missing`），不给"猜目标"留口子。
7. **幂等**：当前有效根已通过验签 ⇒ `applied=False reason="already_ok"`，**一个字节都不写**。
