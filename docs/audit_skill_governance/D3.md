## 2. 四道门的口径（以及为什么这么定）

### G1 豁免漂移（对应主报告 §1.5 **S1**、§3 风险预案表「确认门豁免漂移」一行）

- **读什么**：覆盖层 `data/ui_settings.json` 的 `overrides[CP_TOOL_CONFIRM_LEVEL_EXEMPT]`
  （经 `agent.settings.overrides.OverrideStore`，覆盖层的唯一读写入口；不可用时退回直读同一文件的同一键）。
- **同时读生效值**：`agent.tool_exemptions.effective_value()`（开关中心解析：`env > ui_override > config > default`）。
  两个来源都看——覆盖层回答"谁在什么时候改的"，**生效值才是闸门真正读的那份**
  （`tool_gate._exempt_tools()` 读的是进程 env，覆盖层变更会被热写进 env）。
- **查级别**：`agent.lines.load_tool_meta()` —— 与闸门/能力清单**同一个唯一真相源**，
  取 `ToolMeta.effective_confirm_level`；名单项按"原名 / 小写 / 末段"三种候选解析，
  与闸门 `_query_keys()` 的宽容口径对齐（写 `delegate` 还是 `cp.builtin.delegate` 都要认出同一个工具，
  否则会出现"闸门豁免了、巡检说查不到"的**假绿**）。
- **判定**：含 L2/L3 ⇒ **FAIL** 并列出「哪个工具 / 什么级别 / 为什么危险」；仅 L0/L1 ⇒ WARN；
  空/缺失 ⇒ PASS；解析不出的名字 ⇒ WARN（它对闸门无实际效果，不 FAIL——FAIL 必须建立在"确实放宽了拦截"之上）。
- **为什么 L2/L3 才 FAIL**：L2 = 逐次确认（单次有效），L3 = 默认禁止（仅显式预授权）；
  被豁免 = 这一级要求**整条取消**。Q1 §5.1 的 `fan_out`（L2 / effect=execute / risk=high）
  正是这个形态——它被豁免时，模型可不经任何人工确认自动并发分派。

### G2 链完整性（Q7 §4.2 的只读复核）

调 `AuditChain.reader(db, roots_path=..., signing_enabled=False).verify_chain()`：
`role='reader'`（不占单写者登记、不启 writer 线程、不写预留日志、不取跨进程锁），
`signing_enabled=False` 是硬要求——`RootsSigner` 在 enabled 且密钥缺失时会**现场生成并落盘**
（`chain.py:722-731`），巡检绝不能写盘。台账不存在 ⇒ **FAIL 且不创建**（reader 的 `_init_db` 仍会建库文件，故这层守卫只能由脚本自己做）。

### G3 日根覆盖（Q7 §4.4 的两类缺陷）

- 差集：各 UTC 日记录数（`substr(ts,1,10)`，与 `chain.day_of_ts` **恒等**：后者就是 `str(ts)[:10]`）− 有日根的日；缺失 ⇒ **WARN**（已知历史事实，不 FAIL）。
- 重放：**最近 N（默认 2）个有根日**逐个 `verify_daily_root`，失败 ⇒ **FAIL**。
- **额外**：其余历史日根也全部重放（实测一天 0.03–3.2 s，9 个日根总耗时 ~4.5 s），因为
  "窗口只覆盖最近两天"会漏掉"重封历史日把根改坏"这类问题。判定分三层，避免造出**恒红**的门：
  1. 窗口内失败 ⇒ FAIL（封印路径正在产出错误日根）；
  2. 窗口外但**失败原因属篡改类**（`entry_hash_mismatch` / `root_chain_broken` /
     `signature_invalid` / `seal_metadata_mismatch` / `root_not_found`）⇒ FAIL（此刻的完整性问题）；
  3. 窗口外、非篡改类（`root_hash_mismatch` / `leaf_count_mismatch`）⇒ 允许至多
     `--max-known-bad-roots`（默认 1）天，**WARN**；越界即 FAIL。
  用**数量**而不是"日期白名单"作界是有意的：白名单会腐烂成第二份豁免清单（正是本卡要治的病），
  而数量界在**新增**一天失败时立刻越界报警。零容忍用 `--max-known-bad-roots 0`（当前仓库会红，直到 09-21 重封，见 §9）。

### G4 统计口径卫生（对应 §1.5 **S7**）

- 模式可配置 `--junk-pattern`，默认 `(?i)(?:^|[._-])(?:test|tests|probe)(?:[._-]|$)|^x\.y$|global_test`。
- **实测零误报**：对当前链上 **122 个不同 action** 全量匹配，只命中 Q7 §1.3 点名的那 3 个
  （`global_test_action` 50 / `x.y` 13 / `ssrf_probe_test` 1），没有误伤
  `escape`（131，真实事件镜像）、`ui.*`（真实 UI 操作）等业务 action。
- 占比超阈值 ⇒ **只 WARN 不 FAIL**：链是**只追加**的，历史污染无法删除（Q7 §6 定性为"永久化"）；
  把历史遗留做成红灯等于造一个恒红的门。本门的价值在**增量**（有新的测试/探针往生产链写）。

## 7. G1 反事实探针：证明这道门**不是假绿**

只读卡最容易犯的错是"门永远绿"。故用**临时目录里的假覆盖层**（不碰 `data/`）跑 5 个反事实：

| 假覆盖层的值 | 期望 | 实测 |
|---|---|---|
| 键缺失 | PASS | **PASS**，`exit_code=0` |
| `fan_out,delegate`（**S1 的历史原值**） | FAIL | **FAIL**，`exit_code=1`，点名：`工具 fan_out 级别=L2（plane=act effect=execute risk=high）来源=覆盖层 ⇒ L2 = 逐次确认…被整条取消 ⇒ 该工具不再进审批收件箱，模型可自动路由执行；且 effect=execute（会改变世界，不只是读）；risk=high` |
| `notify`（L1） | WARN | **WARN**，`exit_code=0` |
| `read_file`（L0） | WARN | **WARN**，`exit_code=0` |
| `cp.builtin.fan_out`（能力 id 写法） | FAIL | **FAIL**，解析到同一个工具（`out["names"][0]["tool"]=="fan_out"`） |

关键点：**历史原值 `fan_out,delegate` 被精确判成 1 项危险（fan_out=L2）+ 1 项 WARN（delegate=L1）**
—— 说明这道门真的会在 S1 复发的那一刻变红，并且顺便纠正了"delegate 也是高危"的直觉（它实测是 L1/medium）。
（假覆盖层放在 `%TEMP%\d3_probe_settings\`，运行后已删除，实测 `cleaned=True`。）

## 8. 巡检过程中发现的其它事实（**只报告，本卡不修**）

### 8.1 本卡运行期间**有其它进程在写生产审计链**（观察，非缺陷结论）

- 链头在本卡工作期间持续增长：`72300 → 72302 → 72304 → 72305`；新增记录形如
  `seq=72303/72304/72305 action=ui.chat.api_chat.post actor=ui:127.0.0.1`（12:15–12:18 UTC）。
- `seq=72302` 是一条 `action=lock.degraded`：
  `{"lock_name":"audit_chain","reason":"seq_conflict: UNIQUE constraint failed: audit_chain.seq","pid":18800}`
  —— 即**另一个进程**（pid 18800，与本卡任何进程都不同）在分配 seq 时撞了 UNIQUE 约束并留痕。
- **本卡不下结论**：链的完整性校验（72,305 条）通过、seq 连续无空洞，说明该冲突被既有恢复机制吸收了；
  但"跨进程 seq 协调是否有真实丢行风险"需要审计链**写路径**的卡去判（见 §9.3）。
- 影响：本报告引用的条数/哈希都是**某一时刻的快照**；复跑时数字会更大（这本身也说明巡检必须容忍并发写者）。

### 8.2 链上存在**未来日期**与**一年前日期**的记录（数据卫生，成因未验证）

`2027-10-19`（1738 条）、`2027-10-20`（58 条）与 `2025-08-10/11`（48+58 条）
都在"正常业务窗口"之外，且**都没有日根**（§4.3）。它们的 ts 形态正常（`+00:00`），
故不是"日期前缀口径"问题。**成因未验证**（时钟前跳 / 回填 / 测试造数皆可能），登记在 §11。

### 8.3 对"重封日根"的一个实测陷阱（给后续卡的硬约束）

在**临时链**上实测（不碰生产）：

```text
封印后回填一条同日记录（seq 更大）: verify ok=True（封印点的 seq 上界把它挡住了 ⇒ 不误报）
默认重封（force=False）: leaf_count=3 —— 幂等，直接返回旧根，**没有重算**
force=True 重封: 新根 leaf_count=4、root_hash 与重算一致（**自洽**），根文件变成两行
但 get_daily_root() 仍返回 leaf_count=3（**第一条**）⇒ verify_daily_root 读的还是旧根
```

⇒ **"追加一条新根"这种修法对 `verify_daily_root` 无效**：`get_daily_root()` 按日期取**第一条**
（`chain.py:2955-2960`），"后一条生效"这个直觉在实现里不成立。
（2026-09-14 那对重复根之所以看起来无害，正是因为两条内容完全相同。）

## 9. 发现项的处置建议与**责任卡**

### 9.1 2026-09-21 日根不符 + 8 天缺根 —— **不属于 D3，建议新开一张卡**

- 本卡是**只读巡检卡**（卡面明令：不改 `data/`、不写审计链）；重算/重封日根是**写** `daily_roots.jsonl` 的高风险动作，超出本卡范围。

  它至少要先回答三件事：
  1. 09-21 这段的 10 条差异到底怎么来的（§4.4 的两种候选机制，需要查预留日志 / DB 文件史）；
  2. 重封语义怎么定 —— §8.3 实测表明**追加式重封对验签无效**，要么改 `get_daily_root` 的取用语义
     （取最后一条 / 取"最新有效"条），要么承认该日永久不符并把它登记为已知缺陷；

⇒ D1 管的是"前缀删除 + 冷归档"，**不管日根重封**。不要把它当成 09-21 的归宿。

### 9.3 并发写者 / `lock.degraded(seq_conflict)` —— 归审计链写路径的卡

### 9.4 链本身 —— **无需任何卡介入**

## 10. 「这个巡检该怎么接入 CI / 定时任务」（**只给建议，未改任何 CI 配置**）
