## ② 逐键裁定与理由

| # | 键 | 裁定 | 理由 |
|---|---|---|---|
| 1 | `enabled` | **删除** | 无读取点，且**语义重复**：「拦截执行」已由 `orchestrator.workflow_learning_layer.enabled`（活键 + env 逃生）把守，「自动学习」已由 `learn_from_interaction.enabled`（活键 + env 逃生）把守。硬接线一个「服务级总开关」得先裁定它到底关什么（学习？执行？两者？），那是**语义决策 + 新增能力**，不是机械接线 |
| 2 | `repo_path` | **删除** | 无读取点，且**接线反而更危险**：配置写的是**相对路径** `./data/...`，代码用的是**模块相对的绝对路径**（`repository.py:16`）。接线后存储位置会绑到**进程 CWD** —— 换个目录启动就等于换一份空仓库（已学工作流「凭空消失」），正是 `tests/unit/test_config_yaml_anchor.py`（L8）在防的缺陷族。而且两者本来指向同一个文件 ⇒ 删除**零能力损失** |
| 3 | `matcher.min_similarity` | **接线** | 真实旋钮（TF-IDF 相似度下限），配置值 `0.3` == 改前生效值 ⇒ **零行为变更**；接上之后改配置才真的有用 |
| 4 | `matcher.min_confidence` | **接线** | 同上（`0.4` == 改前生效值）。**已在配置注释里标注耦合风险**：learner 的初始置信度硬编码 `0.4`，本键若 > 0.4 会复现冷启动死锁（新学条目永不进候选） |
| 5 | `matcher.top_k` | **接线**（配置值保持 5） | 真实旋钮。改前执行器**硬编码 3**，配置写 5 从未被读。接线后池深 3→5，但 `try_execute` **只消费候选池 top1**（`wf, score = candidates[0]`）⇒ 命中/不命中判定**结构上不可能改变**，只有 `ctx["candidates"]` 与 `[Matcher] … → N 候选` 日志变化（纯观测）。§6 有 3 vs 5 的差分实测 |
| 6 | `executor.min_score` | **删除**（不接线） | **接线 = 行为变更**：服务级默认门槛 0.3 → 0.25 ⇒ 对**不带 `min_score` 的调用方**（HTTP `/api/.../try-execute`）**更多工作流会被自动执行**。而**生产拦截路径根本不走这个默认值**（`orchestrator.py:2030` 每次显式传 0.25）⇒ 接线只影响旁路调用方，收益为零、风险非零；更糟的是让**同一个数有两处真相源**（正是本卡要消灭的东西）。真门槛在 `workflow_learning_layer.min_score`，已活且带 env 逃生 |
| 7 | `executor.step_timeout_ms` | **删除** | 执行器**没有**单步超时机制（0 命中）。接线 = **新增能力**：给每步套超时会中断长步骤、改变执行语义与失败面，属独立立项 |
| 8 | `executor.max_steps` | **删除** | 执行器**没有**步数上限（现存的「分支 > 3 / 步骤 > 10 转 Agent 模式」不是截断）。新增上限会**减少**可执行工作流（行为变更），独立立项 |
| 9 | `learner.min_tool_calls` | **删除** | 唯一可接线的位置在 `orchestrator._learn_workflow_from_interaction`（本卡**只读**，且正被并发卡修改）。接线 = 跳过单工具交互的学习 ⇒ **减少学习产出**（行为变更）。附带：1 步交互学到的条目本就落草稿（`admission.MIN_STEPS=2`）、不可匹配、不可升格，价值极低 —— 但「少学东西」仍是行为变更，留给下一张卡配逃生开关一起做 |
| 10 | `learner.max_keywords` | **删除** | 学习器里**不存在**这个概念：唯一实现是 `learner.py` 的模块常量，而 `learner.py` **本卡禁改**（并发卡在改）。（`orchestrator._extract_keywords(max_keywords=3)` 同名不同物，属另一条 prompt 链路） |
| 11 | `learner.dedup_window_days` | **删除** | F11 的去重是**同签名无限期去重**（与时间无关）。加「7 天窗口」会改变去重语义（7 天前的老条目重新变成「新任务」而重复建条），与 F11 卡既定契约冲突，属行为变更 |
| 12 | `learn_from_interaction.enabled` | **保持** | 活键，优先级链 env > config.yaml > 硬编码默认，且已在 `agent/settings/registry.py:1371-1374` 登记 |

**裁定小结**：接线 3 键（#3/#4/#5，全部**零行为变更**）、删除 8 键（#1/#2/#6/#7/#8/#9/#10/#11）、
保持 1 键（#12）。**凡是会改变「自动执行面」或「学习产出面」的键，一律不接线。**

## ④ 行为变更声明

> ### 结论：本卡**没有**改变「多少工作流会被自动执行」，也**没有**改变「多少交互会被学习」。

| 面 | 改前 | 改后 | 是否变更 |
|---|---|---|---|
| **拦截层自动执行门槛** | `workflow_learning_layer.min_score = 0.25`（`orchestrator.py:2030` 显式传入，压过执行器默认） | **同左，一字未动** | **否** |
| 服务级执行门槛 `executor.min_score` | 构造默认 `0.3`（影响旁路调用方：HTTP try-execute 路由） | `0.3`（**故意不读配置**） | **否** |
| `matcher.min_similarity` / `min_confidence` | `0.3` / `0.4` | 配置里也是 `0.3` / `0.4` ⇒ 同值 | **否** |
| `matcher.top_k`（候选池深度） | 硬编码 `3` | 读配置 = `5` | **值变了，判定不变**：`try_execute` 只消费 `candidates[0]`（§6 实测 3 vs 5 的 top1 与 `try_execute` 结果**逐字段相同**）；唯一可观测差异是候选计数与日志 |
| 学习触发面 | `tool_calls` 非空 | **同左**（`min_tool_calls` 删除而非接线） | **否** |
| 去重语义 | 同签名无限期去重 | **同左**（`dedup_window_days` 删除而非接线） | **否** |

**明确不做的高风险项（留给下一张卡，须带已登记的 env 逃生开关）**：

1. 让服务级 `min_score` 读 `config.yaml`（0.3 → 0.25）⇒ **更多工作流会被自动执行**
   （影响 HTTP `/api/.../try-execute` 等不带 `min_score` 的调用方）。建议同时新增 env
   `WF_LEARNING_MIN_SCORE`，并按 `agent/settings/registry.py` 的**零缺口**纪律登记
   （`tests/unit/test_settings_registry.py` 用 AST 机械提取，未登记即红）。
2. 让 `learner.min_tool_calls` 真正生效（在 `orchestrator._learn_workflow_from_interaction`
   或服务层加闸门）⇒ **更少交互会被学习**；需同步修正 `orchestrator.py:2184` 那句过时 docstring。
3. 新增 `step_timeout_ms` / `max_steps` 能力（**新增**而非接线）⇒ 会中断长步骤 /
   **减少**可执行工作流。
