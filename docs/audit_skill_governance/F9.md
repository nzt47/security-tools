## 2. 问题（读码复核，与被修前的 `HEAD` 实现做真机差分）

### 2.1 快照字段清单（直读源码，非推测）

```
service.py:968-972（merge_with_backup）
    "dst_before": {
        k: getattr(dst, k) for k in (
            "name", "description", "content", "content_type",
            "enabled", "default_params", "config_schema", "tags")
    },
```

⇒ `dst_before` 是 **8 个字段**（不是 `model_dump()` 全字段），其中 **`enabled` 是唯一的治理类字段**。

### 2.2 被修前的行为（`HEAD` 版实现，真机跑出来的，不是"应该"）

撤销时的循环是逐字段无条件套回：

```
HEAD: agent/skills_mgmt/service.py
        for k, v in before.items():
            data[k] = v          # k 可以是 enabled
```

差分探针（把 `git show HEAD:agent/skills_mgmt/service.py` 载入为探针模块，与修后实现跑**同一场景**；
审计/事件路径按 `tests/conftest.py` 同口径隔离到临时目录，sidecar 落在探针临时目录）：

场景：创建 dst/src → `merge_with_backup(src, dst, keep_dst)` → `update(dst, content)` →
`set_enabled(dst, False)` → `undo_merge(merge_id)`。

```json
{"impl": "old_HEAD", "sidecar_is_tmp": true, "snapshot_enabled": true, "enabled_before_undo": false, "enabled_after_undo": true,  "content_after_undo": "# 保留方正文（合并前）"}
{"impl": "new_fixed", "sidecar_is_tmp": true, "snapshot_enabled": true, "enabled_before_undo": false, "enabled_after_undo": false, "content_after_undo": "# 保留方正文（合并前）"}
```

⇒ **旧实现：`enabled` 由 False 被静默改回 True（B 被静默重新启用），内容同时被回滚；
新实现：`enabled` 保持 False，内容照常回滚。** 两边内容恢复结果逐字相同。

这条差分同时证明新单测**不是恒真**：`snapshot_enabled=true` 前提下旧实现必然给出 `True`，
所以单测里那句 `assert dst.enabled is False` 在改动前必然失败。

## 3. 修法（两种情形分开处理，不搞一刀切）

### 3.1 情形一：`dst` 仍存在（覆盖已有技能）⇒ 只回滚内容

```python
for k, v in before.items():
    if k in self._UNDO_MERGE_KEEP_FIELDS:
        continue
    data[k] = v
```

新增的私有类常量（放在 `undo_merge` 正上方，属"该函数需要的邻近私有辅助"）：

```python
_UNDO_MERGE_KEEP_FIELDS = frozenset(
    {"enabled", "is_sensitive", "isolation_strategy"})
```

### 3.2 情形二：技能已不存在（用快照重建）⇒ `enabled` 照常恢复

- `src` 缺失走 `:1150-1159` 的 `src_snapshot` 重建；
- `dst` 缺失走 `except SkillNotFoundError` 里的快照重建分支；
- 两处**都没有**加保留过滤（注释已写明"与上面的情形一相反，这里刻意不做保留字段过滤"），
  因为**没有「现有治理状态」可保护**。

### 3.3 治理类字段清单的取舍与理由（本卡要求说明）

| 字段 | 是否列入 | 理由（证据直读） |
|---|---|---|
| `enabled` | **列入（必列）** | `dst_before` 的 8 个字段里唯一的治理类字段；也是本仓**唯一有启停审计动作族**的字段（`enhancer.AUDIT_ACTION_ENABLED_SET = "skill.registry.set_enabled"`，`enhancer.py:77,105`）。它的静默变更正是 F9 的实质危害（技能被静默重新启用）。 |
| `is_sensitive` / `isolation_strategy` | **列入** | `update()` 白名单把这两个字段**单独**标注为「[变易] 敏感技能隔离字段透传」（`service.py:1580-1581`），`models.py:249-255` 定义为"是否为敏感技能（独立上下文隔离）/隔离策略"⇒ 决定技能**如何运行/注入**，不是正文内容，与 `enabled` 同属"决定技能是否/如何运行"的治理决策。**但要说清代价**：这两个字段**当前不在** `dst_before` 的字段清单内 ⇒ 本集合对今天的快照**零可观测影响**，属前瞻性防护（快照将来若扩到全字段，不会退化出同一类静默治理变更）。为免"写了却测不到"，单测用**构造记录**把这条口径固化（见 §5.4）。 |
| `status` | **不列入** | 它是评审工作流状态（draft/approved/published…），不是启用/隔离治理决策；且不在 `dst_before` 内。 |
| `category` / `tags` / `version` | **不列入** | 不是治理决策；`tags` 在快照里且属于内容性元数据（合并时会并集、撤销时应回滚），`category`/`version` 不在快照内。 |

**刻意不走"恢复但留痕"路线（卡上的方案 3）**，理由：
1. 语义上，撤销合并是**内容回滚**；让它具备改治理的能力，等于把 F9 的结论（"要恢复启用态应由操作员显式再启停一次"）反过来做；
2. 若恢复 `enabled` 并补写 `skill.registry.set_enabled`，链上会出现一条**并非真实治理决策**的启停记录 ——
   按启停动作名检索的复核者会把"撤销合并带来的副作用"读成"有人改了启停"，是**误导性留痕**；
3. 反向条件已写进代码注释：若将来产品要求"撤销合并必须完整还原（含启停）"，那时应当走方案 3（恢复 + 留痕），
   而不是把保留口径悄悄去掉。

### 3.4 接口契约

- **签名不变**：`undo_merge(self, merge_id: str) -> Dict[str, Any]`；
- **返回结构不变**：`{"ok", "merge_id", "restored", "note"}`（`restored` 顺序仍为 src → dst）；
- `note` **文案**有更新（同一 key，非结构变化）：补充"治理状态（enabled 等）不随内容回滚，
  如需恢复启用态请重新启停（该次启停会写入启停审计）"。全仓 grep 该旧文案只有 `service.py` 自身引用，
  无任何测试断言旧文案（`grep -rn "建议重新评审-评估后决定去向"` 实测）。
- 评估事件 summary 同步补一句"（内容快照回滚，不回滚已有技能的治理状态）"；
  用"已有技能"限定词保证情形二（整条重建）下这句话依然成立。

## 6. 顺带发现（**已实测，未改**：超出本卡允许范围）

**情形二的 dst 重建分支在真实合并记录下不可达**：

```python
except SkillNotFoundError:
    snap = rec.get("src_snapshot")
    if isinstance(snap, dict) and snap.get("id") == dst_id:   # ← 判据
        self.store.upsert(Skill.from_storage_dict(snap))
```

`merge_with_backup` 只写 `src_snapshot`（= `src.model_dump()`，其 `id` 恒为 `src_id`），
而 `merge_duplicate_skills` 明确禁止 `src_id == dst_id` ⇒ 判据 `snap["id"] == dst_id` **恒为假**。
实测佐证：§5 用例 5 里删掉 dst 后 undo，`restored == ["f9-c2-src"]`，**dst 没有被重建**
（`svc.get("f9-c2-dst")` 仍抛 `SkillNotFoundError`）。

⇒ 修它需要让 `merge_with_backup` 额外写一份 `dst_snapshot`，而该函数**不在本卡允许修改的文件行区间内**，
故本卡只把语义用构造记录固化（用例 6），**不动实现**。建议单开一张卡。

## 8. 结论

F9 已闭环：**情形一（覆盖已有技能）不再回滚任何治理字段**（至少 `enabled`），
**情形二（快照重建）仍然从快照恢复 `enabled`**，签名与返回结构未变，
内容恢复行为在不涉及治理字段时与改动前**逐字段一致**（单测差分 + `HEAD` 真机差分双重佐证），
且撤销过程不再可能产生"改治理却没痕"的路径。
