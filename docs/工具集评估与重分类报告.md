## 0. 执行摘要

### 0.1 核心结论

云枢的工具集**不是"70 余个工具有点重复"，而是"十三处互不同步的工具真相表 + 一条只发 10 个工具的模糊召回路由 + 一个拦不住任何工具的治理闸门"**。

| # | 结论 | 证据强度 |
|---|---|---|

**一句话**：当前工具集**不可组装、不可治理、不可扩展，且有多处静默失效**；而这三条正是多 Agent 多主线的前提。精简的收益主要不来自"少几个工具"，而来自**把十三处真相表收敛成一套**，并让路由从"固定 top-k 模糊召回"改成"域内选取"。

### 0.2 对第一稿的更正（务请优先阅读）

本报告首稿曾据**代码静态分析**得出两条结论，经**运行时实测**后被更正。两条更正都指向同一个教训：**静态读代码会高估"不可达"，也会误判"哪条路径是主路径"。**

| 原结论 | 更正后 | 依据 |
|---|---|---|
| "6 个 `uncategorized` 工具**永远不可达**" | **只对关键词路由不可达**。hybrid 路由从 `data/tool_index.json`（含全部 74 条）取候选、**不做分类过滤**，实测确实返回它们：`'连接 MCP 服务'` → `[... 'disconnect_mcp','scan_mcp','connect_mcp']` | 实测 `hybrid_select_tools()` |
| "路由饥饿（25 上限）是主瓶颈" | 饥饿只在**关键词兜底路径**上发生。**主路径 hybrid 只发 ≤10 个**，`max_tools=25` 的截断分支从不触发——所以真正的瓶颈是 **10 个名额的模糊召回**，而不是 25 个名额的优先级截断 | `_DEFAULT_TOP_K = 10` + 实测返回 8–10 |
| "`process_distill_run` 取消注册" | **不能注销，只能隐藏**。`distill_process_async` 以 `tool_name="process_distill_run"` 提交异步任务，`async_executor.py:224` 经 `call()` 调用，而 `call()` **要求名字在 `_registry` 中**（`tools/__init__.py:230/244`，否则抛 `未知工具`）。注销它会**直接打断 `distill_process_async`**。正确做法是保留注册、从 `get_tool_defs()` 可见集排除（`internal: true`） | 调用链实测 |

**同一更正方向还带来一个新发现**：既然 hybrid 认识 `uncategorized`，那么"把这 6 个工具归入 `extension`"**不是**让它们可达的必要条件——但**仍是必要的**，因为 `uncategorized` 没有关键词、没有 priority、不参与 `PINNED_TOOLS` 补回，在关键词兜底下完全缺席。两条路径的行为差异本身就是缺陷。

> **三条更正指向同一个教训**：**静态读代码会既高估"不可达"、又误判"哪条路径是主路径"、还容易开出一个会打断功能的"清理"建议。** 本报告中凡标"实测"的结论都已在本仓库跑过；标"代码对照"的属于静态分析，实施前应再验一次运行时行为。

## 1. 评估范围与权威名单

### 1.1 五个自相矛盾的工具计数

"云枢有多少个工具"在这个仓库里有**五个都正确但都不相等的答案**：

| 口径 | 数量 | 来源 |
|---|---|---|
| YAML 定义 | **74** | `data/tool_definitions/*.yaml` |
| 实际注册进 `_registry` | **77** | `lifecycle_manager.py:1057-1067` 的 11 个 `register_all()` + `:1052` 的 `register_distill_tools()` = 74 + 3 |
| 检索索引 `tool_index.json` | **74** | = YAML 集合，**不含** 3 个 `distill_*` |
| 路由分类全集 `TOOL_CATEGORIES` | **68** | 74 − 6 个 `uncategorized` |
| 白名单过滤后 | **74** | 77 − 3 个被 `tools_config.json` 禁用 |
| **且另有 6 个 `kb_*` 从未注册** | — | 见 §1.3-D |

实测：11 个 `register_all()` 执行后 `len(_registry) == 74`，与 YAML 文件数**恰好 1:1**。

```
TOTAL REGISTERED: 74
ALL-SCHEMA: 74 tools, 29231 chars (raw) / 26571 chars (pruned=+9.1%)
uncategorized (registered, not in TOOL_CATEGORIES):
  ['connect_mcp','disconnect_mcp','generate_tool','install_tool','market_search','scan_mcp']
```

**"注册了"不等于"能用"**：`software_*` 4 个是空壳（§4.7a），`kb_*` 6 个未注册，`distill_*` 3 个无 schema 暴露面。**77 个注册工具里，真正可用的约 70 个。**

### 1.2 YAML 里两个"留了位却从没用过"的字段

读完 74 个 YAML 定义后，两个结构性事实：

1. **74 个定义全部 `deprecated: false`** ⇒ **弃用机制形同虚设**，**没有任何工具被标记退役**。`tool_schema_pruner.py` 里那套"移除工具级 `deprecated: true`"的逻辑（`SCHEMA_PRUNE_DEPRECATED`）**从未有过输入**。
2. **0 个文件含 `aliases:` 字段** ⇒ schema 留了位置，实际从未使用，别名只能**硬编码在 `tool_router.py:243-247`**。这正是 §3.3 三条错误映射无处可审的成因：别名不是数据，是代码。

> 这两点对 §7 的方案有直接影响：新增 `domain`/`effect`/`risk` 字段之所以可行，是因为 YAML 已经是 source of truth 且**已有"加字段但不填"的先例**——但必须同时把**守门测试**做上（`sync_tool_index.py` 已在，见 §7.6），否则新字段会重蹈 `deprecated`/`aliases` 的覆辙。

### 1.3 第二套注册表：`dl._planning_tools`

除全局 `agent.tools._registry` 外，`lifecycle_manager.py:521` 另建了一个 `ToolRegistry()` 挂在 `dl._planning_tools`（供规划引擎用），由 `core_tools.py:51 register_planning_tools(dl)` 注册 5 个：`check_health` / `get_status` / `search_memory` / `get_sensor_summary` / `llm_chat`。

**其中 3 个名字与全局工具重名**，且 handler 体在同一个文件里**逐行复制**：

- `core_tools.py:20-38`（planning 版，注册到 `dl._planning_tools`）
- `core_tools.py:65-135`（全局版，注册到 `agent.tools`）

⇒ 同一能力两处实现、两处维护。这也解释了 `data/tools_config.json` 里 `check_health: true` 这条**幽灵条目**——它是 planning 工具，不在全局注册表，白名单永远匹配不到它。

### 1.5 四条"看不见"的路径

#### A. `uncategorized` 6 个 —— 关键词路由不可达，hybrid 可达

`tool_router._load_tool_categories_from_yaml()` 只接受 `_DEFAULT_TOOL_CATEGORIES` 的 11 个键，`uncategorized` 不是键 ⇒ 被**静默丢弃**（不报错、不告警）。

| 工具 | 功能 | 关键词路由 | hybrid 路由 |
|---|---|---|---|
| `generate_tool` | **让 LLM 自己写 Python 并注册为工具** | ❌ | ✅ |
| `install_tool` | 从市场安装工具 | ❌ | ✅ |
| `market_search` | 搜索扩展市场 | ❌ | ✅ |
| `connect_mcp` | 连 MCP（`transport=stdio` + `command`/`args`）⇒ **可拉起任意本地进程** | ❌ | ✅ |
| `scan_mcp` | 扫描 MCP 服务 | ❌ | ✅ |
| `disconnect_mcp` | 断开 MCP | ❌ | ✅ |

实测 hybrid：`'帮我生成一个新的工具'` → `[...'install_tool','market_search','disconnect_mcp','connect_mcp','generate_tool']`。

**注意资源影响**：这 6 个的 schema 合计约 2410 字符（≈800 token），在主路径 hybrid 下**会随召回进入每轮请求**，是 token 大户之一。

#### B. `v2` 4 个 —— 关键词路由**永久**不可达（新发现）

`data/tool_router_keywords.json` 实测顶层键：

```
['web','file','code','system','extension','pdf','software','async','schedule','lifetrace','memory']
```

**没有 `v2`**。而 `classify_user_input`（`tool_router.py:418-424`）会跳过不在 `TOOL_CATEGORIES` 里的分类 — `lifetrace` 与 `memory` 在此被丢弃。后果：

- `v2` 的 4 个工具（`search_lifetrace`/`get_persona_info`/`get_preferences`/`trigger_distillation`）**没有任何关键词能命中**，关键词路由永不返回。
- `lifetrace`(16 词) + `memory`(15 词) = **31 个关键词是死配置**。
- 正确的 `v2` 关键词段其实写在 `data/tool_router_default_config.json` 里，但 `agent/tool_router.py` **完全不读那个文件**——它只读 `tool_router_keywords.json`。**两份关键词配置，一份生效一份是死的。**

实测：`"触发一次人格蒸馏"` → 关键词路由只给 `{core}`。

#### C. `distill_*` 3 个 —— **两条路由都不可达**

`register_distill_tools()` 确实在生产链路执行（`lifecycle_manager.py:1052-1053`），但这 3 个**既无 YAML 也无 `tool_index.json` 条目** ⇒ 无 category、无索引 ⇒ **LLM 看不到它们的 schema**（`tools.call("distill_process_async")` 仍可用，但模型不知道它存在）。

其中 `process_distill_run` 按自身描述即"内部执行体，通常不直接使用"——**它不该对模型可见**。但注意它**不能注销**：`distill_process_async` 以它为 `tool_name` 提交异步任务，而 `call()` 要求名字在 `_registry` 中（详见 §6.3）。

#### D. `kb_*` 6 个 —— 未注册 + 无 YAML（双重不可达）

`agent/knowledge/tools.py` 完整定义了 `kb_capture`/`kb_distill`/`kb_discuss`/`kb_card`/`kb_lint`/`kb_search`（含 schema 与 handler，约 310 行），但 `register_knowledge_tools()` 的调用点**只有测试与开发校验脚本**（`tests/unit/test_knowledge_workflow.py:279`、`scripts/dev/verify_knowledge_workflow.py:427`）。`lifecycle_manager._register_builtin_tools()` **没有调用它**。

⇒ **知识库的 6 个能力已实现、已测试、在生产中不存在。** 知识工作流（wiki 卡片 / 健康巡检 / 语义检索）目前是纯离线/CLI 能力。

## 2. 现状架构：十三处并存的"工具真相"

**"哪些工具存在、属于什么、风险多高、谁能用"这个问题，代码里有十三处各自回答了一遍，彼此不同步。** 这是本次评估最重要的结构性发现。

| # | 位置 | 形态 | 覆盖 | 问题 |
|---|---|---|---|---|
| V1 | `data/tool_definitions/*.yaml` | `name` + `category` | 74 | 6 个为 `uncategorized`；无 `risk`/`effect` 字段 |
| V2 | `agent/tool_router.py` `_DEFAULT_TOOL_CATEGORIES` | 硬编码工具名列表 | 68 | 与 V1 内容重复，靠派生函数覆盖；两处需同步维护 |

| V4 | `data/tool_router_keywords.json` | 运行时关键词 | 11 键 | **缺 `v2`**；多出 `lifetrace`/`memory` 两个无效键（31 词死配置） |
| V5 | `data/descriptors.json` | `cp.builtin.*`/`cp.skill.*` | **3/74 工具** | 承载 `risk_level`/`requires_approval`/`timeout_ms`/`idempotent`/`audit_level`，几乎为空 |

## 3. 重复度分析

### 3.1 规模与判定

对运行期注册的 **77 个工具**做全量两两语义比对，得到 **28 组重叠**：

- **10 组是真重复**（同一实现或同一能力，合并不损失任何能力）
- **18 组是分层/正交**（如"按名找文件"`search_files` vs "按内容检索"`grep`；"后台任务"`submit_task` vs "子代理委派"`delegate`）——**不应合并**

### 3.2 工具级重叠分组

实现层判定按"是否同一 handler 函数"；能力层判定按"是否同一件事"。已实测：**大多数已注册工具只是 12–43 行的薄封装壳**，实现委托给另一模块。

| 组 | 工具 | 实现层 | 能力层判定 | 处置建议 |
|---|---|---|---|---|
| **HTTP 获取** | `web_get` `web_post` `web_download` | 3 个独立实现（`_web_get`/`_web_post`/`_web_download`），注册层各 ~16–20 行 | 同一件事：发 HTTP 请求取回内容 | **合并**为 `web_fetch(method, url, …)` |
| **网页抽取** | `web_xpath` `web_css` `web_clean_data` | 3 个独立实现，各 ~16–27 行 | 同一件事：从 HTML 抽结构化内容 | **合并**为 `web_extract(mode, …)` |
| **批量** | `web_batch` | 15 行壳，委托 `batch_request` | `web_fetch` 的循环 | **合并**进 `web_fetch(batch=[…])` |
| **新闻** | `fetch_news` | 76 行，但**无独立业务逻辑**：`:350-367` 循环 3 条硬编码英文 query 全走 `dl._get_web_search().search()` | **真重复**（`web_search` 的高层封装） | **合并**为 `web_search(preset="news")` |
| **数据格式** | `json_query` `json_validate` `data_format_detect` `json_to_yaml` `yaml_to_json` | 各自独立 | 同一件事：识别/校验/查询/转换结构化数据 | **合并**为 `data_transform(op, …)` |

### 3.3 别名机制：设计意图是去重，实际效果是删能力

```python
TOOL_ALIASES: dict[str, list[str]] = {
    "shell_execute": ["run_program"],      # 两者都是命令执行,保留 code 分类的高优先级工具
    "read_file": ["read_pdf"],             # 读取 PDF 时优先通用 read_file
    "list_directory": ["list_processes"],  # "列出"语义歧义,目录列出优先于进程列出
}
```

合并逻辑：**主工具在结果中 ⇒ 从结果中移除别名**。

**`read_file → read_pdf` 是硬功能缺陷**，且**两条路由都中招**：

```
关键词路由：输入='读取pdf文件的内容'
  -> read_pdf 在结果中: False | read_file 在结果中: True
  结果(19): [... 'read_file', 'edit', ... 'merge_pdf', 'split_pdf', 'get_pdf_info']

hybrid 路由：hybrid_select_tools('读取pdf文件的内容')
  -> ['web_get','decompress','edit','grep','write_file','read_file','merge_pdf','get_pdf_info','split_pdf']
     read_pdf 同样缺失
```

而 `read_file` 的实现明确对二进制返回失败：

```python
is_binary = _is_probably_binary(raw_data, encoding)
if encoding is None or is_binary:
    ...  "binary": True,
```

⇒ **用户要求读 PDF，拿到的是读不了 PDF 的 `read_file`，唯一能读的 `read_pdf` 被别名机制删掉。** 更糟的是 `"合并pdf文件"` 会给出 `merge_pdf` 却不给 `read_pdf`。`list_directory → list_processes` 同理（说"列出进程"时进程工具被目录工具挤掉）。

`shell_execute → run_program` 方向大体正确，但注释理由是"保留 code 分类的高优先级工具"——而 `code` 优先级为 3，在 §4.2 的饥饿场景下**根本进不了结果**，等于把两者**双双删掉**。

> **结论**：`TOOL_ALIASES` 这套"主/别名"机制应当**整体废弃**。正确做法是合并**实现**（一个工具、一个 `mode` 参数），而不是在候选集上做减法——减法会删掉真正可用的那个。

**并且：这个缺陷长期未被发现，是因为守门脚本本身是假的。**

`scripts/scan_tool_aliases.py` 把结论**硬编码**为字面量：

```python
"current_status": "已合并 ✅",   # 行 95、102、109、116、123 —— 共 5 条硬编码
status_icon = "✅" if "已合并" in rule["current_status"] else "⚠️"   # 行 157
```

它输出的 5 组"已合并 ✅"完全不读真实代码；同一文件行 232 又去读真实的 `TOOL_ALIASES`（只有 3 条）。**"已合并 5 组"的叙事与代码之间没有任何真实校验。**

## 4. 能力缺口评估

### 4.1 三条并存的 LLM 调用路径，工具暴露完全不同

这是"换入口就换一套工具集"的根源。实测确认三条路径：

| 入口 | 实现 | 工具暴露 | 路由 | Schema 裁剪 | 闸门 |
|---|---|---|---|---|---|
| **Web UI**（`/api/chat/stream`） | `plugins/chat.py:968 _workbench_real_stream()` | `get_tool_defs()` **无白名单 → 全量 74 个 ≈ 11.2k token/轮** | ❌ 绕过 | ❌ 绕过 | ✅ 经 `tools.call()` |
| **编排器 V2**（主路径） | `orchestrator.py:1300 _call_llm_v2` → `tool_calling.py:277` | `hybrid_select_tools()` → **≤10 个** | ✅ hybrid 主路由 | ❌ **`prune_tool_defs` 不在 v2 路径上** | ✅ |

证据：
- `plugins/chat.py:1090` 的 `get_tool_defs()` 位于 `_workbench_real_stream()`（L968），该函数是 `@bp.route("/api/chat/stream")`（L1189-1190）的实现；打包产物 `static/assets/index-*.js` 对 `/api/chat/stream` 有 **53 处引用**，对 `"/api/chat"` 仅 4 处 ⇒ **Web UI 走的是全量那条**。

**结论**：
- 本项目投入最大的两块基础设施——**关键词分类路由 + BM25/Embedding 混合检索**——在 **Web UI 路径上完全没有生效**；

### 4.4 【严重】静默失效：工具"报成功"而"什么都没做"

对自主 Agent 而言，最危险的不是"工具报错"，而是"工具报成功但没做"。发现三处：

**a) `software_*` 四件套全是空壳**

注册链（`agent/tools/software_tools.py:20-62`）调 `dl._software_mgr.register_backend(...)` 五次，而 `agent/software_manager.py`（全文 43 行）只定义：

```python
class SoftwareManager:
    def __init__(self): self._installed_software = {}
    def check_updates(self): return []
    def install(self, software_name): return True      # ← 什么都不做
    def uninstall(self, software_name): return True    # ← 什么都不做

```

- **没有 `register_backend`** → 5 次注册全部 `AttributeError` → 被 `except Exception` 吞掉 → 只留 warning → **0 个后端**。
- **没有 `search`** → `software_search` 无实现可依。
- `install()`/`uninstall()` 恒 `return True`；`_installed_software` 永远是空 dict → `software_list` 恒返回空。
- `agent/software_backends.py` 同样是空壳：`ChocolateyBackend.install()` 只打日志然后 `return True`；`WebDownloadBackend` **没有 `__init__`** 而 `software_tools.py:50-53` 却传 `http_client=`/`search_engine=` 两个 kwarg → `TypeError`；`GitHubBackend` 只有 `clone()`，没有 `install()`/`uninstall()`。

⇒ **`software_install` 会返回成功，但什么都没装**，Agent 会把"已为你安装 X"报给用户。这 4 个工具占 600 token 的 schema 额度。

**b) 定时任务分脑：0 vs 41**

两套独立调度子系统，**持久化文件不同**：

| | 工具路径（Agent 用） | REST 路径（UI 用） |
|---|---|---|
| 实现 | `agent/scheduling.py` `Scheduler` 单例 | `agent/tools/task_tools.py` |
| 存储 | `data/schedules.json` | `data/scheduled_tasks.json` |
| 实测内容 | `{"updated_at":"…","tasks":[]}` → **0 个** | **41 个任务**（含 `echo_task`: `echo hello`/30s） |
| 入口 | `code_tools.py` 的 5 个 schedule 工具 | REST 路由 + `agent/system_tools.py` 再导出 |

⇒ Agent 调 `list_scheduled_tasks` 得到"无定时任务"，而系统里实际有 41 个在跑；Agent 新建的任务写进 `schedules.json`，UI 看不到；UI 建的任务 Agent 更看不到。**两个调度器各跑各的任务集。**

**c) 动态工具持久化断裂**

`lifecycle_manager.py:1001-1012` 调 `init_dynamic_tools_persistence(...)` 与 `load_dynamic_tools()`，但实测 **`agent/tools/__init__.py`（550 行）这两个函数都不存在**（`def` 计数 = 0）；同文件 `:1024-1028` 调 `tool_router.set_discovery_service(...)`，而实测 **`agent/tool_router.py`（611 行）也没有这个函数**（`def` 计数 = 0）。

三处 `AttributeError` 均被 `except Exception` 吞成一条 warning。⇒ **`generate_tool` 生成的工具重启即丢失**（尽管 `generate_persistent` 会写文件到 `agent/tools/custom/`）。

> **通用教训**：`except Exception: logger.warning(...)` 在**注册期/初始化期**吞掉错误，会让"工具存在但无后端"、"能力宣称存在但未接线"这类状态完全隐形。建议把注册期异常升级为**注册失败即不注册**（fail-closed），而不是注册一个空壳或静默跳过。

### 4.5 【严重】治理真空：闸门对 77 个工具零拦截

**a) `tool_gate` 实测放行一切**

```

check_tool_call('generate_tool', {})                          -> None
check_tool_call('ext_install', {})                            -> None
check_tool_call('connect_mcp', {})                            -> None
check_tool_call('write_file', {})                             -> None
check_tool_call('remember', {})                               -> None
```

`tool_gate` 是 `agent/tools/call()` 里的**唯一汇聚点**（`tools/__init__.py:217-223`），语义设计为 **fail-open + 显式拒绝**——只有策略文件或描述符明确返回 `allowed=False` 才拒绝。而：

- `data/permission_policies.json` 四个角色（admin/developer/guest/owner）的 **`denied_tools` 全为空列表**；
- `data/descriptors.json` 的 `requires_approval` **32 条中 0 条为 true**；
- 严格模式需显式设 `CP_TOOL_GATE_STRICT`，**当前未设**；
- `default_role` 仍是 `guest`，故 `owner` 角色无影响。

⇒ **闸门目前是一个纯空转的钩子。**这是一处**设计意图与部署现实之间的缺口**，不是"没写治理"——治理框架齐全，但没有一条规则被启用。

### 4.6 组装机制：已实现，但对真实工具名不设防

**好消息**：`agent/subagent/toolset.py` 的 `SubAgentToolset` 是一个设计良好的**最小暴露**原语：

- `build(requested, authorized_capabilities)` = 申请 ∩ 授权 − 矩阵拒绝（三重交集，**不存在"申请即获得"路径**）

**且 fail-closed 前缀网确实有效**：实测 `memory.dream`（未登记的受保护前缀）被正确拒绝。

**但它只认带点号的抽象名**，而真实工具名没有一个含 `memory.`/`approval.` 前缀。**实测**：

## 5. 性能瓶颈

### 5.1 每轮 token 成本（按 3 字符/token 估，中文 schema 实际更高）

| 路径 | 工具数 | schema 字符 | ≈token |
|---|---|---|---|
| **Web UI**（`/api/chat/stream`） | **74（全量）** | **29231** | **≈9743** |
| 编排器 V2（hybrid 主路径） | **≤10** | ~2810–5960 | **≈940–1990** |
| 编排器标准（关键词兜底，上限） | 25 | ~10034–10284 | **≈3345–3428** |
| 编排器标准（仅命中 core） | 6 | 2126 | 817 |
| **有效常驻**（`tools_config.json` 已禁用 3 个） | 3 | 1403–1528 | ≈467–509 |

- **Web UI 路径每轮固定约 9.7k token 的 schema 开销**，与用户说什么无关。这是最大的单点浪费。
- **Schema 裁剪收益极小**：全量 29231 → 26571 字符，**仅省 9.1%**。因为 schema 的 token 主要来自 `properties` 结构与 `required`，而非 description（`tool_schema_pruner.py` 也自述"保守，不做激进字段移除"）。
- **且裁剪在主路径上不生效**：`prune_tool_defs` 唯一生产调用点 `orchestrator.py:3411` 位于 `_call_llm`；主路径 `_call_llm_v2` → `chat_with_steps`（`tool_calling.py:277`）直接 `get_tool_defs(whitelist=…)`，**完全不走 pruner**。生产上真实付出的是 raw 数字。
- `get_tool_defs` 的缓存**对白名单调用无效**（`tools/__init__.py:375-397` 只在 `whitelist is None` 时用缓存）；智能路由下**永远传 list** ⇒ 每轮重建 74→N 条 def。**`_get_tool_defs_cache` 在生产中从未命中。**
- `_get_enabled_tools_whitelist()` **每次 LLM 调用读一次磁盘**（`open()+json.load()`，无缓存、无 mtime 判断）。
- `data/tools_config.json` 禁用了 3 个 core 工具（`get_status`/`get_sensor_summary`/`expand_context`），直接削弱"始终可见"的常驻能力集；其中 `expand_context` 又是语义扩召回的**唯一**入口（且它在向量记忆未启用时本就返回失败）⇒ **语义扩召回生产中双重失效**。
- 该文件还留了一条 `check_health: true` **幽灵条目**——`check_health` 只注册进 `dl._planning_tools`（规划引擎专用），**不是全局工具**。

### 5.2 无工具级超时（重要）

`tool_calling.py:147, 160-161, 167-168, 173` 给 `self._tool_timeout` 赋值，但**全仓再无任何读取点**。`lifecycle_manager.py:407, 1176` 传入的 `tool_timeout=60` **从未被使用**。

⇒ **单次工具执行没有超时保护。** 唯一的时间约束是**任务级 600s Timer**（`tool_calling.py:290-296, 309-315`），而它只在**轮次之间**被检查，回调只 `set()` 一个 Event，**不能中断正在执行的工具**。

工具在调用线程内同步执行（`tool_calling.py:811-822` → `tools.call(...)`），无 `ThreadPoolExecutor`、无 `asyncio`、无进程隔离。`shell_execute` 的 120s 上限与 `web_get` 的 30s 默认超时是**唯一**的实际护栏。⇒ **一个卡住的工具会挂住整轮对话。**

### 5.3 选择链路的实际形态

```
编排器 V2（主）：
  _get_enabled_tools_whitelist()          # 读 data/tools_config.json（每轮一次磁盘 IO）
  → hybrid_select_tools(user_input, wl)   # BM25 + Embedding 双路融合
       ├─ BM25Index（name + parameter_names + description）
       └─ EmbeddingIndex（paraphrase-multilingual-MiniLM-L12-v2）
            └─ 独立子进程 + JSON-Lines IPC + query LRU 缓存(128) + 预热线程
       └─ top_k=10 ⇒ 返回 ≤10 个  ← 真正的瓶颈在这
  → get_tool_defs(whitelist=…)            # 无裁剪、无缓存命中
  → tools.call() → tool_gate(空转) → rate_limiter(错配) → handler
```

对 **74 个候选**做 BM25 + 语义双路融合，是为"上千工具"规模设计的机制——**在 74 个工具的场景下，用一个子进程 + 一个 embedding 模型 + IPC 换 10 个模糊候选，性价比很低**；而 `top_k=10` 这个数字本身就构成了能力上限。

### 5.4 命名/归置误导：`tool_router_reranker.py`

## 7. 重新分类：三层可组装架构

> 目标（用户明示）：**不同 Agent 各管一条线；要全方面能力；可以单独给 Agent 组装；以后能自主新增主线。**

现状的 11 个类别是**学科轴**（web/file/code/system/pdf/software…），它无法支撑组装——因为"一个 Agent 需要哪些学科"没有边界（每个 Agent 都可能要读写文件）。组装需要一个**有治理含义**的轴。

### 7.1 三层结构

```
L1  能力原子 Tool          ← data/tool_definitions/*.yaml（唯一权威）
      声明：domain / effect / risk / grants / idempotent / timeout_ms
L2  能力域   Domain        ← data/tool_domains/*.yaml（新，9 个域）
      声明：域内核心工具、默认效应上限、是否只读
L3  主线档案 Line Profile  ← data/agent_lines/*.yaml（新）
      声明：domains + 工具增删 + 授权 + 人格/技能包
```

**关键约束**：L1 是唯一权威，L2/L3 由 L1 派生；`tool_router`、`tool_router_hybrid`、`SubAgentToolset`、`HITL`、`rate_limiter`、`descriptors`、`tool_gate` **全部改为读 L1/L2**，消灭 §2 的十三处真相。

### 7.2 新增字段（在现有 YAML 上追加，不破坏兼容）

```yaml
name: shell_execute
category: code          # 保留，向后兼容
domain: execute         # 新增：归属能力域（组装轴）
effect: execute         # 新增：read | write | execute | extend（治理轴）
risk: high              # 新增：low | medium | high | critical
requires_approval: true # 新增
grants: [execute.shell] # 新增：SubAgentToolset 的授权点名（真实工具名 → grants 的映射由本字段派生）
idempotent: false       # 新增
timeout_ms: 120000      # 新增（直接解决 §5.2 的无超时问题）
```

**两根轴的分工**：
- `domain` 服务**组装**（"这个 Agent 管哪条线"）
- `effect` 服务**治理**（"这个 Agent 最多能造成什么后果"）

一个只读的研究 Agent = `domains: [sense, seek, recall]`，**不需要逐工具列举**。这就是"可单独组装"。

### 7.3 九个能力域（覆盖全部 83 个工具）

| 域 | 含义 | 含工具（重组后） | effect |
|---|---|---|---|
| **sense** 感知 | 从外部世界取信息 | `web_search`（含 `preset="news"`）`web_fetch` `web_extract` `get_weather` | read |
| **seek** 检索 | 从本地取信息 | `read_file` `list_objects(file)` `get_file_info` `search_files` `grep` `read_pdf` | read |
| **recall** 忆取 | 从自有记忆/知识取 | `recall(memory)` `recall(lifetrace)` `recall(kb)` `get_status` `get_sensor_summary` `get_persona_info` `get_preferences` `expand_context` | read |
| **remember** 记忆 | 写入自有记忆/知识 | `memorize` `todo_write` `kb_capture` `kb_distill` `kb_discuss` `kb_card` `kb_lint` | write |
| **mutate** 变更 | 改动本地文件/数据 | `write_file` `edit` `data_transform` `compress` `decompress` `diff_files` `edit_pdf` `humanize_zh` `arch_diagram` | write |
| **execute** 执行 | 任意代码/进程/软件 | `shell_execute` `manage_process` `software` `code_review` `run_sandbox` `run_tests`（新） | execute |
| **orchestrate** 编排 | 时间与并行 | `submit_task` `task_status` `task_result` `manage_task` `schedule_task` `manage_schedule` `delegate` `distill` | execute |
| **evolve** 进化 | 改写自身能力集 | `ext_search` `ext_install` `ext_manage` `ext_list` `generate_tool` | extend |
| **channel** 通道 | 对外发言 | `ext_send_channel`（+ 未来 `notify`/`mail`/`report`） | execute |

**为什么这样切**：域边界 = **权限边界**。`seek` 全只读、`remember` 只写自己的记忆、`mutate` 写文件、`execute` 能造成任意后果、`evolve` 能改变未来的能力集。组装 = 选域；治理 = 按 effect 设阈值。这使"给一个 Agent 组装工具集"变成一句声明，而不是一张 74 行的白名单。

### 7.5 路由与组装如何共存

**前提：修好 §4.2 的 `top_k=10`**（这一步比修饥饿更重要）：

```
旧：hybrid top_k=10 全局召回 → （最坏情况）关键词路由按 priority 截断 25 → 补回 delegate
新：① 按会话/Agent 的主线档案，限定候选域
    ② 每个命中域先给出"域内核心工具"（L2 声明，约 2-4 个/域）
    ③ 剩余名额按域内相关度（BM25 分数）分配，总名额 = 每域下限之和（而非固定 10/25）
    ④ 未命中域不进入；未命中域的 pinned 核心工具不补回（不绕过路由）
```

这样：
- `top_k=10` 的硬上限消失，命中 `execute` 域就**一定**能拿到 `shell_execute`；
- 关键词兜底的 `core+web+file=25` 饥饿消失；
- 路由的候选集从"74 个按文本相似度排序"变成"若干个域内小集合"——**BM25 在 5–10 个候选上比在 74 个上可靠得多**，这同时缓解 §4.2 的召回噪声问题。

**组装如何接入**：

```
会话/Agent 创建时 →  载入 L3 主线档案
  → 展开为 {domain 集合, effect 上限, grants}
  → tool_router / hybrid 只用这些 domain 做候选（解决问题 ①②③）
  → SubAgentToolset 用 grants 做 fail-closed 判定（真实工具名 ↔ grants 由 L1 派生，解决 §4.6）
  → HITL / tool_gate 用 L1 的 risk 字段（解决 §4.5a/b）
  → rate_limiter 用 L1 的 domain 分桶（解决 §4.5d）
  → descriptors 由 L1 自动补齐（解决 C5，3/74 → 83/83）
  → 工具超时由 L1 的 timeout_ms 提供（解决 §5.2）
```

**六处历史问题一次收敛**，因为它们本来就都是"缺一份权威的工具声明表"。
