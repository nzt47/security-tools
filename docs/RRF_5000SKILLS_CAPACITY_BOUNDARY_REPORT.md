# 5000 技能规模性能验证报告 — 倒排索引实时性边界评估

> 生成时间：2026-07-30
> 评估脚本：`scripts/demo_rrf_1000skills_scaling.py`（scale_levels 扩展至 5000）
> 数据规模：100 / 500 / 1000 / 2000 / **5000** 技能五档对比
> 测试 query：18 个（与 100 技能 demo 同源）
> 核心问题：5000 技能量级下，倒排索引是否还能维持 < 50ms 实时性？

---

## 1. 执行摘要

### 1.1 核心结论

**5000 技能在倒排索引开启时仍满足实时性要求，但余量仅 10%，已接近容量边界。**

| 指标 | OFF（O(n)） | ON（O(k)） | 加速 | 实时性 |
|---|---|---|---|---|
| **RRF avg** | 66.15ms | 25.24ms | **2.62x** | - |
| **RRF P99** | **94.07ms ✗** | **44.78ms ✓** | **2.10x** | ON 达标 / OFF 超标 |

**关键发现**：
- ON 模式 P99=44.78ms，仍在 50ms 阈值内，但余量仅 5.22ms（10.4%）
- OFF 模式 P99=94.07ms，接近阈值 2 倍，严重超标
- 倒排索引是 5000 技能规模下维持实时性的**必要条件**

### 1.2 容量边界评估

| 数据规模 | RRF P99 (ON) | 余量 | 评估 |
|---|---|---|---|
| 1000 技能 | 10.01ms | 80% | ✅ 安全 |
| 2000 技能 | 18.89ms | 62% | ✅ 安全 |
| **5000 技能** | **44.78ms** | **10%** | ⚠️ 临界 |
| 10000 技能* | ~90ms | -80% | ❌ 超标（外推） |

*10000 技能基于 5000→10000 线性外推，预计 P99 约 90ms，将严重超标。

## 2. 实测数据详析

### 2.1 五档规模延迟对比（ON vs OFF）

| 规模 | TF-IDF OFF | TF-IDF ON | TF-IDF 加速 | RRF OFF | RRF ON | RRF 加速 |
|---|---|---|---|---|---|---|
| 100 | 0.24ms | 0.13ms | 1.85x | 0.90ms | 0.76ms | 1.18x |
| 500 | 6.55ms | 2.44ms | 2.68x | 8.39ms | 3.52ms | 2.38x |
| 1000 | 12.23ms | 4.87ms | 2.51x | 14.96ms | 5.72ms | 2.62x |
| 2000 | 24.85ms | 9.11ms | 2.73x | 28.02ms | 9.88ms | 2.84x |
| **5000** | **58.70ms** | **26.65ms** | **2.20x** | **66.15ms** | **25.24ms** | **2.62x** |

**分析**：
- 倒排索引加速倍率稳定在 2.2-2.8x（5000 技能档 2.62x，与 1000 技能档 2.62x 完全一致）
- TF-IDF 路绝对延迟随数据量线性增长（即使开启倒排索引）

### 2.2 P99 延迟达标验证（核心指标）

| 规模 | RRF P99 OFF | RRF P99 ON | P99 加速 | OFF 达标 | ON 达标 |
|---|---|---|---|---|---|
| 100 | 1.30ms | 1.21ms | 1.07x | ✓ | ✓ |
| 500 | 15.67ms | 8.80ms | 1.78x | ✓ | ✓ |
| 1000 | 20.90ms | 10.01ms | 2.09x | ✓ | ✓ |
| 2000 | 43.57ms | 18.89ms | 2.31x | ✓ | ✓ |
| **5000** | **94.07ms** | **44.78ms** | **2.10x** | **✗ 超标** | **✓ 达标** |

**关键结论**：
- 5000 技能是 OFF 模式的**崩溃点**（P99=94.07ms，接近阈值 2 倍）
- 5000 技能是 ON 模式的**临界点**（P99=44.78ms，余量仅 10%）
- 倒排索引将 5000 技能从"不可用"拯救为"勉强可用"

### 2.3 TF-IDF 路增长趋势（ON 模式）

```
500 → 1000 → 2000 → 5000
2.44 → 4.87 → 9.11 → 26.65 ms
```

| 数据量变化 | 延迟变化 | 增长系数 |
|---|---|---|
| 500 → 1000 (2x) | 2.44 → 4.87 (2.0x) | 1.00（线性） |
| 1000 → 2000 (2x) | 4.87 → 9.11 (1.87x) | 0.94（亚线性） |
| 2000 → 5000 (2.5x) | 9.11 → 26.65 (2.92x) | 1.17（超线性） |

**分析**：
- 500→2000 技能阶段，倒排索引受益明显（亚线性增长）
- 2000→5000 技能阶段，候选集规模增长更快（同领域技能变多），出现超线性增长
- **根因**：倒排索引 O(k) 中的 k = 候选集大小，随数据量增长而增长（每领域技能数从 200 增至 500）

### 2.4 延迟组成分析（5000 技能档，ON 模式）

```
RRF 总延迟: 25.24ms
  ├─ TF-IDF 路: 26.65ms (105.6%)  ← 绝对瓶颈
  ├─ 向量路:    1.89ms (7.5%)
  └─ 融合+门禁: ~0ms (可忽略)
```

*TF-IDF 占比 >100% 是因为 RRF avg（25.24ms）与 TF-IDF avg（26.65ms）测量独立，存在正常波动。

**对比 1000 技能档**：
- TF-IDF 路占比从 85.3% 升至 105.6%（绝对值 4.87ms → 26.65ms，增长 5.5x）
- 向量路占比从 18.5% 降至 7.5%（FakeModel O(n) 增长平缓）

## 3. 生产环境外推

### 3.1 生产环境 5000 技能延迟估算

生产环境与 FakeModel 的关键差异：向量路从 O(n) numpy 矩阵乘法变为 O(log n) sqlite-vec KNN。

| 场景 | TF-IDF 路 | 向量路 | 融合+门禁 | 合计 |
|---|---|---|---|---|
| FakeModel ON（实测） | 26.65ms | 1.89ms | ~0ms | 25.24ms |
| **生产估算 ON** | ~26.65ms | ~3.0ms | ~0.5ms | **~30.2ms** |
| FakeModel OFF（实测） | 58.70ms | 9.35ms | ~0ms | 66.15ms |
| **生产估算 OFF** | ~58.70ms | ~3.0ms | ~0.5ms | **~62.2ms** |

**注**：生产环境 TF-IDF 路延迟与 FakeModel 一致（均为 O(n)/O(k) 纯 Python 实现），向量路因 sqlite-vec O(log n) 而更优。

### 3.2 生产环境 P99 估算

| 场景 | avg 估算 | P99 估算（avg × 1.8） | 达标(<50ms) |
|---|---|---|---|
| 生产 ON | ~30.2ms | ~54.4ms | ⚠️ **临界超标** |
| 生产 OFF | ~62.2ms | ~112ms | ❌ 严重超标 |

**风险提示**：
- 生产环境 5000 技能 P99 估算约 54ms，**可能略微超标**
- FakeModel 实测 P99=44.78ms 达标，但生产环境 P99/avg 比值可能更高（因 sqlite-vec 有偶发延迟）
- 建议：5000 技能规模下监控 P99 趋势，准备降级方案

## 5. 优化建议

### 5.1 当前状态（5000 技能）

| 维度 | 状态 | 说明 |
|---|---|---|
| 实时性 (P99 < 50ms) | ⚠️ 临界 | ON 模式 P99=44.78ms，余量仅 10% |
| 加速效果 | ✅ 稳定 | 倒排索引 2.62x 加速，与 1000 技能一致 |
| 语义不变 | ✅ 验证 | 117 个单元测试全部通过 |
| 数据生成 | ✅ 可行 | 5000 技能构建 ~14 秒 |

### 5.2 短期建议（5000 技能维持实时性）

1. **query embedding LRU 缓存**（最高优先级）
   - 生产环境 BGE-m3 推理 5-10ms/query
   - 高频重复 query 可缓存 embedding，省 5-10ms
   - 预期：P99 从 44.78ms 降至 ~35ms，余量提升至 30%

2. **TF-IDF 路候选集上限**
   - 当前倒排索引返回所有候选，无上限
   - 可设 candidate_limit=200，超出按 TF-IDF 分截断
   - 预期：5000 技能 TF-IDF 路从 26.65ms 降至 ~15ms

### 5.3 中期建议（10000+ 技能扩展）

1. **BM25 替代 TF-IDF**
   - BM25 有 IDF 权重，对常见词降权，候选集更精准
   - 预期：候选集规模减少 50%，TF-IDF 路延迟减半

2. **倒排索引持久化**
   - 当前每次进程启动都需重建（O(n)）
   - 持久化后启动直接加载，省首次 query 构建开销

3. **分片检索**
   - 10000+ 技能按领域分片，每片独立倒排索引
   - 查询时只检索相关分片，候选集大幅缩小

### 5.4 容量规划建议

| 目标规模 | 当前方案 | 建议方案 | 预期 P99 |
|---|---|---|---|
| ≤ 2000 技能 | 倒排索引 ON | 当前方案足够 | < 20ms |
| 5000 技能 | 倒排索引 ON | + query embedding 缓存 | < 35ms |
| 10000 技能 | 倒排索引 ON | + BM25 + 候选集上限 | < 40ms |
| 20000+ 技能 | - | + 分片检索 | < 50ms |

## 7. 结论

### 7.1 核心结论

1. **5000 技能 ON 模式 P99=44.78ms，勉强达标**（余量仅 10%）
2. **倒排索引是 5000 技能维持实时性的必要条件**（OFF 模式 P99=94.07ms 严重超标）
3. **加速效果稳定**：5000 技能倒排索引加速 2.62x，与 1000 技能一致
4. **5000 技能是当前方案的容量边界**，10000+ 技能需进一步优化

### 7.2 风险提示

- 5000 技能 ON 模式 P99 余量仅 10%，生产环境可能因 sqlite-vec 偶发延迟而超标
- 建议在 5000 技能规模下部署 P99 监控告警，阈值设为 45ms
- 准备降级方案：P99 持续超标时自动启用候选集上限（candidate_limit=200）

### 7.3 三义校验

- **【不易】**：数据生成逻辑不改，复用现有 `generate_n_skills`；测试 query 不变；语义不变（117 测试通过）
- **【变易】**：scale_levels 扩展至 5000，结论部分动态计算加速倍率；容量边界外推至 10000 技能
- **【简易】**：仅扩展 scale_levels 列表 + 动态化结论输出，无新增复杂逻辑
