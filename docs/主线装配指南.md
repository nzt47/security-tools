# 云枢主线装配指南

> 面向"多 Agent 各管一条线、能力可单独组装、以后能自主新增主线"。
> 配套评估依据见 `docs/工具集评估与重分类报告.md`。

---

## 1. 一句话模型

```
工具原子（决定能力与风险）  →  主线档案（决定权重与边界）  →  本轮工具集
data/tool_definitions/*.yaml    data/agent_lines/*.yaml
   plane / effect / risk           平面权重 / 保底 / boost / mute / 策略
```

**核心设计判断：主线是"权重"，不是"分区"。** 同一个工具可以同时被多条主线使用；
主线只决定"它排多前、要不要被排除、哪些动作需要确认"，不争夺归属权。
这样"不预设单一主线、按能力平面分层"才成立。

---

## 2. 四能力平面

| 平面 | 含义 | 判定标准 | 治理含义 |
|---|---|---|---|
| `resident` 常驻 | 每轮必发的高频低 token 工具 | 与"是谁、要干什么"无关都要有 | 常驻成本，越少越好 |
| `perceive` 感知 | 只读取信息，不改变世界 | 无副作用 | 默认可放行 |
| `act` 行动 | 会改变世界 | 写文件 / 执行命令 / 进程 / 出网 | 按 risk 决定是否确认 |
| `govern` 治理 | **会改变云枢自身的能力集** | 装扩展 / 生成工具 / 接 MCP | **就是审批边界**，必须确认 |

> `govern` 平面不是"又一个分类"，而是把"能改自己"的工具单独圈出来当闸门。
> 当前 9 个：`ext_install` `ext_uninstall` `ext_toggle` `ext_configure`
> `install_tool` `generate_tool` `scan_mcp` `connect_mcp` `disconnect_mcp`。

## 3. 效果与风险两根正交轴

**effect 是偏序**：`read` < `write` < `execute` < `extend`

- `read` 无副作用 → risk 通常 low
- `write` 本地可逆变更 → low / medium / high
- `execute` 任意代码、进程、出网 → medium / high（不受限的代码执行用 critical）
- `extend` **改变自身能力集** → high / critical，**必须审批**

`effect_allow` 是**上限**：写了 `[read, write]` 就永远拿不到 `shell_execute`。
`requires_approval` 是**确认清单**（不授予权限，只标记需确认）。
`allow_govern: true` 会自动把 `extend` 加进 `effect_allow`（否则"允许治理"是个静默失效的开关）。

|---|---|---|---|---|

| `dev` | 通用研发 Agent | 感知 1.0 / 行动 1.0 | ❌ | 纯研发，**永不动自身能力集** |

| 主线 | 工具数 | 上限 | govern 数 | 需确认 |
|---|---|---|---|---|
| assistant | 18 | 18 | 0 | 0 |
| dev | 22 | 22 | 0 | 2 |
| digital_life | 18 | 18 | 1 | 1 |
| engineering | 26 | 26 | 0 | 2 |
| harness | 26 | 26 | 5 | 6 |
| knowledge | 20 | 20 | 0 | 0 |
| recon | 22 | 22 | 0 | 0 |

> **engineering 由 24→26 的原因（2026-09-18）**：工具集扩容后（新增 `git`/`run_tests`/
> `apply_patch`/`run_lint`/`workspace_*`/`browser_*` 等），该线 24 个名额被挤掉的是
> **`run_tests`（该线 prompt_note 明令的"改完必须跑验证"）**与 `arch_diagram`。
> 实测：`max_tools=25` 恰好恢复 `run_tests`，`26` 再恢复 `arch_diagram`，两者**均零丢失**；

> 故取"放宽名额 +2"这一条无副作用的修法。dev 的"需确认"由 1→2 亦是同一次工具集扩容所致。
> 复现：`assemble(profile, sorted(load_tool_meta()), meta=…)` 逐线打印。

## 5. 装配算法（为什么它修掉了"饥饿"）

旧口径是"按 category.priority 全局排序 → 截断 25"，而
`core(6) + web(9) + file(10) = 25` **恰好等于上限** ⇒ 只要同时命中 web 与 file，
`code/system/extension/pdf/software/schedule/v2` **全部返回 0 个工具**，含 `shell_execute`。

新口径（`agent/lines/assembler.py`）：

```
① 治理过滤：effect 上限 / mute / 平面启用；无声明的工具 fail-closed 拒绝
② 打分：plane_weight×100 + 核心工具60 + 标签命中12 + 常驻加成40
③ 平面保底：每个启用的平面先各取 plane_floors 个（默认 2）
④ 打分补足剩余名额
⑤ 截断：只裁"打分入选"的部分，**全部保底一律保留**（允许略超 max_tools）
```

⇒ **任何已启用平面都不会归零。**这是与旧行为最重要的差别。

三条不变量（`tests/unit/test_agent_lines.py` 已锁）：

1. `test_plane_floor_prevents_starvation` —— 保底平面不许被吃光
2. `test_unknown_tools_are_fail_closed` —— 无 plane/effect 声明的工具一律拒绝
3. `test_line_whitelist_returns_none_when_no_line_active` —— 未装线必须回退旧路径

## 6. 技能包（skills）

主线档案的 `skills:` 决定**本线允许注入哪些技能**。减法落在**注入侧**，因为技能
不是模型发起的工具调用 —— 提示词型技能由 `ContextInjector` 按意图注入、带脚本技能
由 `SkillExecutor` 显式执行（口径见 `data/skill_callability.yaml` 开头）。

| 声明的 `skills` | 运行时语义 | `source` |
|---|---|---|
| 未装线 / 档案缺失 / 主线停用 | **不限制**（全局启用的技能都可注入） | `no-line` / `profile-missing` / `line-disabled` |
| 空（不写 / 只写空白串） | **不限制** | `empty-declaration` |
| 非空 | **白名单**：只有列出的技能可注入 | `whitelist` |

判定实现：`agent/lines/skillpack.py`（纯数据、只读探测；接线入口
`agent/lines/integration.py::line_skill_pack()`，**永不抛**：档案坏了就回退不限制）。

三条必须记住的语义：

1. **空 = 不限制，不是「一个都不给」。** 工具侧是 fail-closed（没有 plane/effect 声明
   一律拒绝），技能侧**不能照抄**：技能内容由系统按意图注入，空声明只是「本线没表态」。
   照抄的后果是所有装线场景的技能段瞬间清空，且是静默的。
2. **unknown 如实报告。** 声明了但技能目录里查不到的 id（既无实体、也无声明）**不注入**，但会出现在
   `SkillPack.unknown`、装配预览的「技能」区块，以及 `POST /api/agent-lines/validate`
   的 `issues`（`引用了未注册的技能: [...]`）里；保存时也会被 `LineRegistry.save` 拦下。
   写错一个技能 id 不再静默失效。
3. **缓存按线分键。** 技能段的系统提示词缓存键是 `(line_id, mode, allowed)`。技能段是
   身份相关的：单槽位缓存会让「切换主线后的第一次调用」拿到上一条线的技能段（命中即
   返回，连启用状态都不再查），而且只错这一次 —— 典型的一次性幽灵缺陷。

生效链路（每一步都可在 `/api/agent-lines/preview` 的 `skills` 段里看到结论）：

```
data/agent_lines/<id>.yaml 的 skills
  → agent/lines/skillpack.py::resolve_skill_pack    判定：白名单 / 不限制 + unknown
  → agent/lines/integration.py::line_skill_pack     取生效主线（未装线/异常 ⇒ 不限制）
  → DigitalLifePersonaMixin._build_skill_instructions
      注入集 = 本线技能包 ∩ SkillRegistry().list_enabled_ids() ∩ _SKILL_PROMPTS
```

> **接线前后的行为等价（本次落定的口径）**：`_SKILL_PROMPTS` 里的 7 个 persona 技能
> （`self_reflection` / `memory_summary` / `emotion_expression` / `proactive_suggestion` /
> `context_aware` / `safety_guard` / `voice_interaction`）在接线前**全部 known 且全部
> enabled ⇒ 每轮都注入，与是哪条线无关**。而 7 条主线原先声明的都是指令型 id
> （`global-core-principles` / `engineering-test-delivery` / `code-observability` /
> `testing-anti-patterns`），**没有一个声明 persona 技能**。
>
> 于是：若只接线、不补数据，按「非空声明 = 白名单」的语义，装线后**每条线的 persona 段
> 都会变成空的** —— 那是 7 段提示词的能力回退，**不是「如实结果」**。故本次把 7 个 persona
> id 补进每条主线的 `skills:` 声明（顺序：原有 id 之后按 id 字典序），实测 7 条线均为
> `whitelist`、persona 段 7/7、声明无重复、`validate(known_skills=…)` 无问题 ——
> **与接线前逐字一致**（与工具侧「未装线 = 旧行为」同一纪律）。
>
> 逐线收窄 persona 段属于**产品口径调整**，另行立项（见交付结案报告的遗留台账），
> 不由本次接线顺手决定。守门用例：
> `tests/unit/test_line_skillpack.py::TestValidateSkills::test_每条内置主线都必须声明全部_persona_技能`
> —— 它让「静默收窄」不可能发生：要让某条线放弃某个 persona 段，必须显式删 id，
> 并同步改那条用例与本节。
>
> 历史说明：`skills:` 此前**只有 UI 与存储、没有运行时消费方**（7 条线都写了它，
> 但没有任何代码读它，写错一个 id 也只是静默失效）；本次把它接到注入侧，
> 并在保存/校验时对拍真实技能目录。这条链**只做减法**：装了线之后，
> 注入的技能段 = 本线 `skills:` 声明 ∩ 全局启用 —— 声明里没写的一律不注入。

> **两条进模型提示词的路径都已受本线 `skills:` 约束**（2026-09-23 收口）：
>
> | 路径 | 入口 | 闸门 |
> |---|---|---|
> | ① 系统提示词的技能段（persona 7 项） | `DigitalLifePersonaMixin._build_skill_instructions()` | 本线技能包 ∩ 全局启用 ∩ `_SKILL_PROMPTS` |
> | ② 按意图命中注入 | `Orchestrator._context_assembler_procedural()`（ContextAssembler 旁路，`learning.context_assembler.enabled: true`） | `agent/lines/integration.py::filter_skill_entries()` |
>
> ② 是**生产链路**（旁路开关自 2026-08-12 起为 true），此前未被白名单约束 —— 只堵①会让它
> 成为绕开本线 `skills:` 的第二条注入通道。
>
> **这是治理口径变更，不是接线**，因此把后果写明：7 条内置主线目前**都没有声明文件轨技能**
> （`pd-*-skill` 等 15 条），故过滤生效后**旁路不再注入它们**。要让某条线在旁路里拿到某个技能，
> 把 id 写进该线 `skills:` 即生效（`/api/agent-lines/preview` 的 `skills.allowed` 会如实显示本线允许集）。
>
> **仍不受本线约束的**：技能子系统自身的接口（`ContextInjector` / `SkillsMgmtService` /
> `SkillManager.build_context`）—— 它们的调用方是技能管理 UI、过程蒸馏、工作流学习等**内部流程**，
> 不构成"给模型看的技能面"。若将来它们也要按线收口，判据仍是同一条：**这段内容会不会进模型提示词**。

> **known 的唯一权威**：`SkillRegistry.list_skill_ids()`（主轨 `data/skills_mgmt.json` ∪
> 文件轨 `data/skills_repo/<id>/skill.md`）。它不可用时退回磁盘事实
> （`data/skills_repo/` 目录名 / `data/skills_mgmt.json` 键 / `data/skills.json` 的 id），
> 任何异常都只丢掉对应来源，**不抛出**。
>
> 另外并上 **tracked** 的技能声明表 `data/skill_callability.yaml` 的 `skills:` 键。为什么
> 需要这第二处来源：`data/skills_mgmt.json` 被 `.gitignore` 忽略，干净 checkout 里不存在，
> 而内置主线声明的指令型技能恰只活在那份台账里 —— 只认运行时目录会让同一份档案在开发机
> 与 CI 得到不同的 unknown 判定。声明表只补「这个 id 有出处」，不改变「实际装了哪些」
> （真正注入什么仍由运行时启用集合决定）。

## 7. 怎么新建一条主线

### 方式 A：UI（推荐）
「工具调用 → 主线管理」→ 新建 → 调权重 → 看实时预览（工具数 / 分平面清单 / 需确认项 /
被 effect 拦下的）→ 保存 → 设为当前。

### 方式 B：直接写 YAML
在 `data/agent_lines/<id>.yaml` 建文件即可，**零代码改动**：

```yaml
id: my_line
name: 我的主线
description: 干什么用
enabled: true

plane_weights:      # 0 = 该平面不参与
  resident: 0.8
  perceive: 1.0
  act: 0.9
  govern: 0.0

plane_floors:       # 每个平面的保底名额（防饥饿）
  resident: 4
  perceive: 4
  act: 3

boost:              # 主线核心工具（权重加成，可跨平面）
  - read_file
  - grep
  - write_file
mute:               # 明确排除
  - shell_execute

tags: [code]        # 命中标签的工具获得小幅加成

max_tools: 20       # 单轮最多给模型看几个

effect_allow: [read, write, execute]   # 效果上限
requires_approval: [execute, extend]   # 需人工确认
allow_govern: false                    # 是否允许改自身能力集

skills: [global-core-principles]
prompt_note: 这条线的行为约束（会注入系统提示词）
```

**校验规则**（保存时自动执行，UI 会显示问题）：
- `id` 小写字母开头，2–41 字符，含小写字母/数字/`_`/`-`
- `boost`/`mute` 只能引用**真实存在**的工具（typo 会静默失效，故必须拦住）
- `skills` 只能引用**真实存在**的技能 id，且不得重复 / 留空（同上理由，见 §6）
- `plane_weights`/`plane_floors` 的键必须是四个平面之一
- `effect_allow`/`requires_approval` 的值必须是四个效果之一
- `allow_govern: true` 会自动补 `extend` 进 `effect_allow`

## 8. 怎么新增一个工具（含治理声明）

1. 在 `agent/tools/` 写注册模块（照 `file_tools_reg.py` 的形状），或加进已有的。
2. **必须**建 `data/tool_definitions/<name>.yaml`，字段顺序照 `grep.yaml`：

```yaml
name: my_tool
category: code        # 必须在 KNOWN_CATEGORIES 内（scripts/sync_tool_index.py）
description: 中文一句话，可带英文关键词（BM25 会索引它）
deprecated: false
version: 1.0.0
plane: act            # resident | perceive | act | govern
effect: write         # read | write | execute | extend
risk: medium          # low | medium | high | critical
tool_type: tool          # ── 以下六项是「可被 LLM 调用」声明 ──
llm_callable: true       #    见 docs/工具与技能可调用性标注规范.md
callable_mode: auto      #    auto | required | manual（manual = 仅人工/系统调用）
permission_level: public #    必须与 plane/effect/risk 的派生值一致（--check 对拍）
sandbox_allowed: false   #    写/执行/出网 ⇒ false（只读且不出网才 true）
tags: [code]
schema: { ... }       # 与注册时传入的 schema 完全一致
examples: []
```

> 可调用性声明也可由 `python scripts/backfill_tool_callability.py` 按治理轴自动补齐
> （幂等、只补缺失）：`--check` 除查缺失外还会对拍 `permission_level` 与派生值，
> 防止"同一件事两份口径"。补齐后由 `scripts/sync_capability_manifest.py` 派生统一清单
> `data/capability_manifest.json`（✅/⚠️/❌ 三档标识），`get_tool_defs()` 会据此把
> 声明判否的工具挡在模型可见集之外。

3. 把工具名加进 `agent/tool_router.py` 的 `_DEFAULT_TOOL_CATEGORIES` 对应分类列表
   （顺序即优先级顺序）。**漏了这步它就不会被关键词路由选中。**
4. 跑守门：
   ```powershell
   python scripts/backfill_tool_planes.py --check       # 每个工具都有 plane/effect/risk
   python scripts/backfill_tool_callability.py --check  # 每个工具都有可调用性声明且与治理轴一致
   python scripts/sync_tool_index.py                    # 生成 data/tool_index.json
   python scripts/sync_capability_manifest.py           # 生成 data/capability_manifest.json（✅/⚠️/❌ 清单）
   python -m pytest tests/unit/test_agent_lines.py tests/unit/test_tool_definitions_yaml.py tests/unit/test_tool_callability.py -q
   ```

### 内部工具（不该被模型看见）
加 `internal: true`。它会：保留注册（`call()` 仍可按名调用，供 AsyncExecutor 等内部链路）、
从 `get_tool_defs()` 隐藏、**从路由分类表排除**。
例子：`process_distill_run`（`distill_process_async` 以它为 `tool_name` 提交异步任务，
所以**不能注销**，只能这样隐藏）。

## 9. 装配器怎么接进对话

`agent/lines/integration.py` → 编排器两个 LLM 路径（`_call_llm` / `_call_llm_v2`）：

```
有激活主线  → line_whitelist() 装配结果作为工具集
无激活主线  → 返回 (None, None) ⇒ 完全回退旧行为（hybrid 智能选择 → 关键词兜底）
装配异常    → 同样回退，绝不打断对话
```

⇒ **不装线 = 等于没改过**。可以逐线灰度、随时用「设为当前 → 空」回退。

激活指针存在 `data/agent_lines/_active.json`（`{"active": "<id>"|null}`）；
环境变量 `YUNSHU_AGENT_LINES_DIR` 可覆盖档案目录（测试隔离用）。
