# 工具 / 技能「可被 LLM 调用」标注规范

> 一句话：**每个能力都必须能回答"模型能不能自己发起调用它；不能的话，缺什么"。**
> 输入是权威数据（工具 YAML + 技能覆盖表），输出是统一清单
> `data/capability_manifest.json`，判定口径只有一处：`agent/lines/callability.py`。

配套：`docs/主线装配指南.md`（工具原子与主线装配）、`docs/工具集评估与重分类报告.md`
（为什么要有治理轴）。守门测试：`tests/unit/test_tool_callability.py`。

---

## 1. 为什么需要这份标注

在它之前，"模型能调什么"是由**四处分散事实隐式决定**的，谁也一眼看不出来：

| 事实 | 位置 | 它单独决定什么 |
|---|---|---|
| `internal: true` | `data/tool_definitions/*.yaml` | 保留注册但不给模型看（如 `process_distill_run`） |
| 有没有 handler | `agent/tools/__init__.py::_registry` | 没注册 ⇒ 调不动 |
| 有没有 JSON Schema | 同上（缺 schema 时 `get_tool_defs` **静默**补空壳） | 无 schema ⇒ 模型不知道参数名，等于半残 |
| 权限策略 / 审批边界 | `data/permission_policies.json` + `agent/tool_gate.py` | 被拒 / 需人工确认 |

后果是三个具体问题：**看不出来**（UI 与文档只能靠人脑记）、**解析不了**（没有机器可读的
清单，自动化/评测/网关各写一份口径）、**控不住**（高风险或未注册能力可能被顺手暴露）。

本规范把这件事收敛成**一组统一字段 + 一条判定规则 + 一份派生清单**。

## 2. 统一字段（工具与技能同构）

| 字段 | 类型 | 说明 |
|---|---|---|
| `tool_name` | string | 能力名（工具名 / 技能 id）——两个清单**共用同一主键名**，便于合并解析 |
| `tool_type` | enum | `tool` / `skill` / `api` / `script` |
| `llm_callable` | boolean | **生效值**：是否允许 LLM 发起调用（声明 + 事实 + 权限共同决定） |
| `callable_mode` | enum | `auto`（模型自主判断）/ `required`（必须调用）/ `manual`（仅人工/系统调用） |
| `schema_registered` | boolean | 是否已注册**可用**的 JSON Schema（技能侧：是否有参数契约） |
| `host_executor` | string | 宿主执行器 ID 或执行入口，形如 `agent.tools.system_tools:_shell_execute` |
| `permission_level` | enum | `public` / `internal` / `restricted` |
| `sandbox_allowed` | boolean | 是否允许在沙箱（受限会话/分身沙箱，默认只读）中执行 |
| `reason` | string | 不可调用原因（`llm_callable=false` 时**必填**，不允许空） |

随行诊断字段（不属八项，供 UI 与排障）：
`mark`、`reachable`（是否可达）、`trigger`（真实触发者）、`reason_kind`（标识成因类别）、
`blockers`/`blocker_codes`（硬阻断：不可达）、`soft_blockers`/`soft_codes`（软阻断：可达但不经模型发起）、
`conditions`、`notes`、`declared_llm_callable`、`declared_permission_level`、
`derived_permission_level`、`declared_in`、`category`/`plane`/`effect`/`risk`/
`needs_approval`/`internal`/`enabled`。

### 判定（两组阻断，`llm_callable` 与 `mark` 各答一个问题）

**硬阻断 ⇒ 不可达 ⇒ ❌**：无执行器 / 无内容实体 / 已停用（enabled=false 或未发布）/
权限策略拒绝 / **内部专用**（`internal: true`：设计上不对模型开放，也不进检索索引）。

**软阻断 ⇒ 可达但不经模型发起 ⇒ ⚠️**：声明 `llm_callable: false` /
`callable_mode: manual`（由系统或人工触发）/ 缺 JSON Schema（需人补参数）。

```
llm_callable = 无硬阻断 且 无软阻断     # 只回答：模型能不能发起这次调用（manual 恒 false）
mark                                                # 回答：这项能力可用吗
    ✅ 可调用        llm_callable 且不在审批边界
    ⚠️ 条件可调用    可达，但需人工确认（审批边界）或不经模型发起（manual/声明 false：
                     由系统·人工触发）或缺参数契约
    ❌ 不可调用      不可达（硬阻断）
```

> **⚠️ 与 ❌ 的分界是"能不能被执行"，不是"模型能不能发起"。** 这条界是刻意的：
> 技能（提示词型由 `ContextInjector` 按意图注入、脚本型由 `SkillExecutor` 显式执行）
> 属于"可达但不经模型发起"，标 ⚠️；而"注册点里找不到执行器""已停用"这类才是真的不可用，标 ❌。
> 在此之前两者都算 ❌ ⇒ 全部技能都被标成 ❌，看上去像"技能全坏了" —— 标识因此失去分辨力。
> `trigger` 与 `reason_kind` 把这件事说全：
> `trigger ∈ {model, system, human, none}`，`reason_kind ∈ {unreachable, not_model_initiated, needs_approval, ""}`。

> **`sandbox_allowed=false` 只进 `notes`，不改变标识。** 沙箱适用性是与"能否被模型发起"
> **正交**的一条轴：实测把它算成条件会让 58/91 个工具齐刷刷变 ⚠️，标识随即失去分辨力。

### `permission_level` 怎么来

    needs_approval（govern / extend / critical）或被策略拒绝 → restricted
    effect == read 且 risk == low                            → public
    其余（写 / 执行）                                        → internal

声明必须与派生值一致（`scripts/backfill_tool_callability.py --check` 会对拍）；
要改等级就改 `plane`/`effect`/`risk`，**不要**只改 `permission_level` —— 否则同一件事
就有了两份口径。

## 3. 三层归属（谁说了算）

```
声明层（人定的策略，L1 权威）
  工具 → data/tool_definitions/<name>.yaml
         tool_type / llm_callable / callable_mode / permission_level / sandbox_allowed / reason
  技能 → data/skill_callability.yaml（defaults + 个别覆盖）
         ↑ 技能为什么不用 skill.md front matter：那里由安装器与 meta_editor 管辖，
           未知键可能被重写；技能侧用单一覆盖表，集中审计、集中回滚。

事实层（可证的事实，不由人填）
  schema_registered ← 工具 YAML/注册表的 schema；技能 ← config_schema / output_schema / 脚本参数契约
  host_executor     ← 运行时注册表（agent.tools.registry_facts()）
                      → 静态注册点扫描（AST，默认口径，确定性）
                      → 技能侧声明的执行器

派生层（代码算出，写进清单）
  llm_callable（生效值）、mark、blockers、conditions、notes、统计
```

## 4. 清单长什么样（真实条目）

```json
{
  "tool_name": "web_search", "tool_type": "tool",
  "llm_callable": true, "callable_mode": "auto", "schema_registered": true,
  "host_executor": "agent.tools.web_tools:_web_search",
  "permission_level": "public", "sandbox_allowed": false, "reason": "",
  "mark": "✅ 可调用",
  "notes": ["sandbox_allowed=false：不允许在沙箱（受限会话）中执行"]
}
```

```json
{
  "tool_name": "shell_execute", "tool_type": "tool",
  "llm_callable": true, "callable_mode": "auto", "schema_registered": true,
  "host_executor": "agent.tools.system_tools:_shell_execute",
  "permission_level": "restricted", "sandbox_allowed": false, "reason": "",
  "mark": "⚠️ 条件可调用",
  "conditions": ["属审批边界（govern 平面 / extend 效果 / critical 风险）：调用会挂审批单，需人工确认后原样重试"]
}
```

```json
{
  "tool_name": "process_distill_run", "tool_type": "tool",
  "llm_callable": false, "callable_mode": "manual", "schema_registered": true,
  "host_executor": "agent.process_distill.tools:_run_handler",
  "permission_level": "internal", "sandbox_allowed": false,
  "reason": "内部执行体：仅由 AsyncDistill 后台链路按名调用（保留注册、不进模型可见集）",
  "mark": "❌ 不可调用", "reachable": false, "trigger": "none",
  "reason_kind": "unreachable", "blocker_codes": ["internal_only"]
}
```

```json
{
  "tool_name": "context_aware", "tool_type": "skill",
  "llm_callable": false, "callable_mode": "manual", "schema_registered": false,
  "host_executor": "agent.skills_mgmt.context_injector:ContextInjector",
  "permission_level": "public", "sandbox_allowed": true,
  "reason": "纯提示词技能：由 ContextInjector 按意图注入，模型不发起调用；无 JSON Schema（缺参数契约，模型无法按 schema 填参）",
  "mark": "⚠️ 条件可调用", "reachable": true, "trigger": "system",
  "reason_kind": "not_model_initiated", "soft_codes": ["declared_false", "no_schema"]
}
```

> `llm_callable=false` **不等于不能用**：`process_distill_run` 依旧可被后台链路按名调用
> （`agent.tools.call()` 不拦它），只是模型看不见；技能则照常由语义层命中后注入 ——
> 前者**谁都不能**从模型侧触发且设计上不对外开放（❌），后者**能生效但不由模型发起**（⚠️）。

当前统计（**仓库可复现口径**：91 工具 + 23 技能实体 = 114 条）：**✅ 80 / ⚠️ 33 / ❌ 1**，
其中 `llm_callable=true` 的 90 条。按触发者：`model 90 / system 23 / none 1`。
23 条 system 触发的全部是技能（提示词型由 `ContextInjector` 按意图注入、脚本型由
`SkillExecutor` 显式执行 —— 模型手里没有"调用技能"的工具）；唯一的 ❌ 是内部专用执行体
`process_distill_run`。

> **清单口径 = 仓库可复现的能力面**（这条是 CI 教出来的，勿放宽）：输入只取**入库**数据 ——
> `data/tool_definitions/*.yaml`、`data/skill_callability.yaml`、`data/skills_repo/*/skill.md`、
> `data/permission_policies.json` 与注册点静态扫描。
> `data/skills.json`、`data/skills_mgmt.json` 被 .gitignore 忽略（应用运行时写的状态），
> 干净 checkout / CI 里不存在 ⇒ 一旦清单依赖它们，CI 重算必然与提交产物不一致
> （实测 23 处差异，`--check` 红灯）。清单文件里每条都带 `"scope": "repo"`。
>
> **只在运行时存在的技能走"请求期补标注"**（不进清单文件）：`GET /api/capability-manifest`
> 在响应里另附 `runtime_skills`（每条 `"scope": "runtime"`），由
> `agent/lines/callability.py::runtime_only_skill_entries()` 就地补算 ——
> 例如 id=`skill`（易之三义）：内容内联在 `data/skills_mgmt.json`、仓库里没有
> `data/skills_repo/skill/skill.md` 实体。不补这一层，界面那几行就没有徽章（实测如此）。
> 界面把两批合并（`indexCallability(runtime_skills, manifest.skills)`：**仓库口径覆盖运行时口径**），
> 并在图例里提示"其中 N 条由运行时目录/台账补算"。
> 要在本机看运行时全貌：`python scripts/sync_capability_manifest.py --runtime --summary`
> （**该产物不提交**）。

## 5. 怎么用

| 目的 | 做法 |
|---|---|
| 看清单 | `python scripts/sync_capability_manifest.py --summary`（含 ✅/⚠️/❌ 计数、按触发者、两侧成因分布、明细） |
| 界面看标识 | 「工具调用 → 主线管理」页：每行工具带 ✅/⚠️/❌ 徽章（悬浮显示触发方式/原因/条件/执行器）；**装配预览的工具 chip 同样带标识**（压成单字形，完整说明在悬浮里） |
| 取数据 | `GET /api/capability-manifest`（整份清单 + `runtime_skills` 运行时补标注）或 `GET /api/agent-lines/planes`（每行工具带 `callability`）；装配预览 `POST /api/agent-lines/preview` 的 `tools_meta` 每行同样带 `callability`，并以 `callability_source` 标明出处 |
| 代码里判 | `from agent.lines.callability import build_manifest, non_callable_tool_names`；按触发者分流读 `trigger`，按"模型能不能发起"读 `llm_callable` |
| CI 守门 | `python scripts/backfill_tool_callability.py --check` + `python scripts/sync_capability_manifest.py --check` |

> **同一份清单，多个视图**：目录端点、预览端点与界面三处**读的都是**
> `data/capability_manifest.json`（`routes_agent_lines.py::_callability_index` 一份缓存），
> 任何一处都不重算判定 —— 这正是本仓"十三处工具真相"病史的对症纪律，
> 由 `tests/unit/test_tool_callability.py::test_装配预览与目录的标注同源` 锁死。

**模型可见集过滤**：`agent/tools/__init__.py::get_tool_defs` 会隐藏
`internal` ∪ 声明判否的工具；检索索引 `data/tool_index.json` 同步排除
（否则 hybrid 召回会把隐藏绕开）。开关 `CP_TOOL_CALLABILITY_ENFORCE=0` 可回滚为
"只隐藏 internal"（登记在 `agent/settings/registry.py`）。

## 6. 怎么给新能力加标注

### 新增工具（三步，与主线装配指南 §7 同一批动作）

1. 写注册模块 + `data/tool_definitions/<name>.yaml`；
2. 补可调用性声明（照 `grep.yaml` 的字段顺序）：
   ```yaml
   tool_type: tool          # 恒为 tool
   llm_callable: true       # 不允许模型调用时置 false，并在 reason 写明原因
   callable_mode: auto      # 仅人工/系统调用 ⇒ manual
   permission_level: public # 与 plane/effect/risk 的派生值一致（--check 会对拍）
   sandbox_allowed: true    # 只读且不出网 ⇒ true；写/执行/出网 ⇒ false
   ```
   或直接跑 `python scripts/backfill_tool_callability.py`（按治理轴派生，幂等，只补缺失）；
3. 跑守门：
   ```powershell
   python scripts/backfill_tool_callability.py --check
   python scripts/sync_tool_index.py
   python scripts/sync_capability_manifest.py
   python -m pytest tests/unit/test_tool_callability.py -q
   ```

### 新增技能

在 `data/skill_callability.yaml` 的 `skills:` 下加条目：默认口径已覆盖"技能不是模型可
发起调用"的情形，只有当该技能**特例**（带脚本、状态未发布、涉及敏感内容、或将来真能被
模型调用）时才写字段，并在 `reason` 里写清机制。
