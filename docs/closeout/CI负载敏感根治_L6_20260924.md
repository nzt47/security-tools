- **日期**：2026-09-24　**分支**：`fix/ci-load-sensitivity-l6`
- **台账**：[`遗留问题立项_20260922.md`](遗留问题立项_20260922.md) 的 **L6**（本条即其根治交付）
- **第一手现场**：[`工具审批链路修复与逐工具豁免开关_20260922.md`](工具审批链路修复与逐工具豁免开关_20260922.md) 的 §10.6 / §10.7
- **取向**：走 L6 的 **(b) 路线（根治）**；**不做 (a)**（不把用例移出 PR 期、不加 `slow` 标记、因此不涉及 Nightly 必跑清单变更）；**不做 (c)**（不换/不加 runner）。
- **纪律**：**断言一字未改**，未放宽任何上界；只有"怎么算得更便宜"变了，"算什么"逐字节相同（证据见 §4）。

## 1. 结论

L6 现象表里的**两条红**（单元分片 Shard 1 的 capregistry 全仓扫描、全项目覆盖率 Shard 2/6 的
技能流程用例）各有各的放大器，本轮**两条都做了根因定位并各自根治**（后者是 2026-09-24 复核 CI 时新拿到的
第一手证据，见 §2.4）。

单元分片那条：**不是**某个用例"本来就很慢"，而是三个放大器叠在一起：

1. **同一份全仓 AST 扫描被反复重做**（进程内：缓存被清 / 被超时打断；跨进程：xdist 的
   `loadscope` 把**同一个测试文件的各个类**分到不同 worker）；
2. **单次扫描本身太贵**（每文件 3 次整树遍历 + 全仓 1406 个文件全部 `ast.parse`）；
3. **热路径也要起子进程**（每次 `scan()` 6 个 `git grep`，而 `main(["--check"])` 在一个文件里要跑 5 次）。

本轮把三条同时按掉：**冷扫描 14.33s → 4.65s（3.1×）**，**每个仓库状态只需一份扫描产物**
（同一进程内"清缓存/被超时打断后重扫"不再冷扫；跨进程共享同一份产物，
最坏情形只退化为"两个 worker 同时冷启、各扫一次"，见 §7.2），**热路径 0.80s → 0.24s**；
出问题的那个测试文件在**命令完全一致**的
对拍下 **48.7s → 18.1s（12 核）/ 61.6s → 10.5s（2 核亲和）**，且用例数从 33 涨到 45（新增守护用例，全部通过）。

## 2. 根因（**第一手 CI 日志**，不是推断）

证据来源：GitHub Actions job **106915652550**（run 35773694230，"单元测试 (Python 3.12 / Shard 1)"，
`37m45s`；同一 commit 的另一轮同 job 是 `17m43s` **通过**）。
下载命令：`gh run view --job 106915652550 --log`（日志 12MB，本地复查用）。

### 2.1 两个 worker **同时**卡在全仓扫描里被超时打断

```
______ ERROR at setup of TestScanCache.test_重复_scan_命中缓存且结论一致 ______
[gw1] ... tests/unit/test_capregistry_callpaths_routes.py:67: in findings
    return audit.scan()
scripts/audit_call_paths.py:876: in scan
    raw = _collect_findings(root, files)
scripts/audit_call_paths.py:758: in _collect_findings
E   Failed: Timeout (>300.0s) from pytest-timeout.

______ ERROR at setup of TestCallPathInventory.test_清单非空且四类都在 ______
[gw0] ... scripts/audit_call_paths.py:751: in _collect_findings
    sym.visit(tree)
E   Failed: Timeout (>300.0s) from pytest-timeout.
```

**`gw0` 与 `gw1` 各自都在 `_collect_findings` 里跑满 300s**（栈分别停在主循环与 `_SymbolIndex.visit`）。
原因是 xdist 的 `--dist=loadscope` 对**带类的测试模块**是**按类分组**的 ——
本文件有 6 个类 ⇒ 各类落到不同 worker 进程，**每个进程各自付一次全仓扫描**。

### 2.2 被超时打断的扫描**不留缓存** ⇒ 后面的用例各自从零重扫

```
20:13:58 [gw1] ERROR TestScanCache::test_重复_scan_命中缓存且结论一致     ← 300s 被打断
20:14:53 [gw0] ERROR TestCallPathInventory::test_清单非空且四类都在      ← 300s 被打断
20:20:38 → 20:25:38 [gw0] FAILED TestCheckMode::test_正例_当前仓库通过_check ← 又是 300s
（另 3 条 TestCheckMode 用例同样各自 300s：它们每个都调一次 `main(["--check"])`）
```

**单进程 6 次全仓 AST** 由此而来：`findings` 夹具的 1 次 + `main(["--check"])` 的 4 次 +
另一个类的 1 次。仅 `TestCheckMode` 一个类就吃掉约 20 分钟（4 × 300s），
正好解释了该 job 的 `pytest 35m05s`。

### 2.3 本机对拍（同一 commit、同一命令）

- 固定顺序（与 CI 的 `-p no:randomly` 同口径）：`48.7s` / `33 passed`；
- 模块级夹具（`audit.scan()`）单次 `16.08s`；`TestCheckMode` 的 4 条热扫 `0.86–1.05s`/条；
- `TestParseCache` 里有用例会 `scan_cache_clear()` ⇒ 之后那次真实扫描**又冷扫一遍**（`17.65s`）。

即：**超时之所以致命，是因为"打断"把这个文件里本来可以复用的唯一一份昂贵计算扔掉了，
而它本来要付 2–6 次。**

### 2.4 第二条红（全项目覆盖率 Shard 2/6）的根因：**每读一个开关就重解析一遍 config.yaml**

同一 commit 的 `可观测性质量保障` run **35953984262** 里，job **107488274312**
（"全项目测试覆盖率 (Shard 2/6)"，04:03:07 → 05:01:08 = **58 分钟**）又一次红在
**与 L6 现象表完全相同的那条用例**上（重试一次后仍红）：

```
04:34:01  E   Failed: Timeout (>300.0s) from pytest-timeout.
05:01:02  E   Failed: Timeout (>300.0s) from pytest-timeout.     ← 重试一次仍超时
FAILED tests/integration/test_skills_workflow_flow.py::TestSkillsEndToEnd::test_search_after_multiple_creates
===== 1 failed, 4074 passed, 20 skipped in 1615.81s (0:26:55) =====
```

**超时栈（pytest-timeout 在信号处理里 dump 的现场）指向一处真实的重复计算**：

```
tests/integration/test_skills_workflow_flow.py:115: in test_search_after_multiple_creates
    skills_svc.create_manual(_skill_data(
agent/skills_mgmt/service.py:198: in create_manual
    self._advisory_assess(skill.id)
agent/skills_mgmt/assessor.py:697: in assess
    blocked = any(f.severity in blocking_severities() for f in findings)
agent/skills_mgmt/assessor.py:163: in blocking_severities → assess_list → _cfg_value
agent/skills_mgmt/assessor.py:100: in _cfg_value
    cfg = _config_yaml()
agent/skills_mgmt/assessor.py:83: in _config_yaml
    return _yaml.safe_load(f)      ← 40KB YAML、纯 Python SafeLoader
```

即：`_cfg_value()` **每次调用都重新读盘并完整解析一遍 config.yaml**（本机实测 40.1KB / **26ms**），
而 `blocking_severities()` / `assess_flag/int/list()` 是**按 finding、按技能**反复调的。
本机实测（探针统计）：

| 观测 | 值 |
|---|---|
| `tests/integration/test_skills_workflow_flow.py` 整文件 | **160 次** `yaml.safe_load` |
| 其中 `test_search_after_multiple_creates` 一条 | **85 次** |
| 该条用例耗时 | 2.50s，其中约 **2.2s（88%）** 花在重复解析上 |

**如实说明（不夸大）**：本机 85 次 × 26ms = 2.2s，即便按"慢 10 倍"的 runner 估也只有 ~22s，
**"单条 >300s"不可能只由这份 CPU 成本解释**（那需要 ~135 倍）；栈里是一次正常的 CPU 调用，
所以更可能是"进程被严重饿死/换页"叠加在一个**本来就贵**的用例上。可以确定的是：
这份重复解析是**真实且可消除**的放大器（本机实测该条 **10.9 倍**加速）。
**CI 轮次给出的结论（§8）**：改造后同一 job 由 `58m01s`（重试一次仍超时）变为 **`11m00s × 3 轮全通过**
⇒ ⑤ 打掉的正是该 job 的主要成本；但"本机 2.2s 的算术推不出 300s"这一点仍如实保留在 §7.4。

## 3. 改了什么（五处，全部只降成本、不改判据）

| # | 改动 | 位置 | 为什么判据不变 |
|---|---|---|---|
| ① | **跨进程扫描产物**（按仓库状态指纹命名的临时目录 JSON，原子写、只读原始 Findings） | `scripts/audit_call_paths.py`（`_load_raw_from_disk` / `_store_raw_to_disk`） | 指纹 = 进程内缓存**同一个** `signature`（`_heuristic_signature()` + 逐文件 `(rel, mtime_ns, size)`）+ root + include_scripts + **扫描器自身源码指纹** + 格式版本 ⇒ 任一输入变了就换键；**例外表/死模块/违规范围一律不进产物**，照旧每次在 `_apply_policy` 重算（否则负例会静默失效） |
| ② | **字节预筛**：不可能出现"参与判据的调用点标识符"的文件直接不 `ast.parse` | 同上（`_source_may_contain_call_site`） | 判据论证：三类分支只可能由 `Name.id`/`Attribute.attr` ∈ {`call`} ∪ `_FUNNEL_ALIASES` ∪ `_REMOTE_PRIMITIVES` ∪ `handler_names` 触发，这些**都是标识符**、在源码里必然逐字出现且两侧不是标识符字符 ⇒ `\b名\b` 必定命中，跳过不可能丢 Finding。标识集**由判据常量派生**（不是手抄），并有守护用例 |
| ③ | **单次遍历**：import 绑定表 + 符号锚点 + 调用点主循环共用一次 BFS（与 `ast.walk` 同序） | 同上（`_TreeIndex` / `module_bindings_from_nodes`） | 旧 `_SymbolIndex` 的锚点 = "该 call 被访问时符号栈内容"，父链上溯反转后**逐字符相同**；绑定表的"同名重复 import 后者覆盖"依赖遍历顺序，两次遍历**同为 BFS 同序**⇒ 逐字节相同。两条都有对拍用例（含内联的旧递归口径 oracle） |
| ④ | **`git grep` 进程内 memo**（键含仓库状态 digest） | 同上（`_module_importers`） | 它只查"谁 import 了这个模块"，与仓库状态一一对应；键里带同一套指纹 ⇒ 仓库变了必不命中 |
| ⑤ | **`config.yaml` 解析结果按文件指纹缓存**（第二条红的根因） | `agent/skills_mgmt/assessor.py`（`_config_yaml`） | 键 = `(绝对路径, mtime_ns, size)`，config.yaml 被改写必然改 mtime_ns 或 size ⇒ 不会读到过期配置；**只缓存 yaml 解析结果**，`SKILLS_ASSESS_*` 环境变量优先级仍每次照跑（有守护用例） |

**未做的事（有意）**：不动任何断言语义与上界；不改 `pytest.ini`；不改 CI 的分片/超时参数
（`--timeout=60` 保持原样）；不把用例移出 PR 期。

### 3.1 产物落在哪里、怎么关

- 默认：`<tempfile.gettempdir()>/cp_audit_call_paths/`（CI 是 `/tmp`；测试期
  `tests/conftest.py` 会把 `tempfile.tempdir` 重定向到仓库内 `.pytest_tmp/`，那是 pytest
  的临时区、且已在 `.gitignore` 第 40 行）——**绝不写 `data/`、绝不写被跟踪的路径**；
- 关掉：`CP_AUDIT_SCAN_DISK_CACHE=0`；换目录：`CP_AUDIT_SCAN_CACHE_DIR=/path`；
- 写盘失败 / 产物损坏 / 目录不可写 ⇒ **一律按未命中退回重扫**（有守护用例）；
- 只保留最近 32 份产物（自动清理）。

### 5.1 同种子对拍（分片级唯一结论）

固定 `--randomly-seed=2427474863`，两个工作区（`origin/master` 未改动 / 本分支）跑**同一命令**：

| | master（未改动） | 本分支（改后） |
|---|---|---|
| pytest 计时 | **786.29s**（13m06s） | **755.66s**（12m35s） |
| 用例 | 2777 passed / 6 skipped / 0 failed | **2789** passed / 6 skipped / 0 failed（+12 条新守护用例） |
| wall（含解释器启动） | 791.4s | 760.1s |

⇒ 分片净省 **30.6s**（−3.9%），**且这个数正好等于出问题那个文件自身的净省**
（48.7s → 18.1s = −30.6s，见 §5 表）—— 分片里另外 106 个文件不碰扫描器，所以分片级收益
本该就等于这一个文件的收益；两者对上，说明分片这 30.6s 的差不是噪声带来的。

**如实说明两点**：① 分片里这一个文件只占约 4%，所以"分片总耗时"不是本改造的主指标 ——
主指标是**该文件在 CI 上不再有时而 300s 超时**（§2 的 6 次全仓扫描 → 1 次 + 单次便宜 3.1 倍）；
② 同种子两次运行里，master 那次期间本机还并行跑了提交钩子等杂项负载，方向上只会让 master
偏慢，故 30.6s 这个差值**不宜外推**（文件级那两个数才是命令完全一致、无并行的干净值）。

## 7. 没有做到的 / 剩余风险（如实）

1. **单次冷扫描仍有 4.65s（2 核 CI 上约 ×2–4）**：本改造把"次数"降到 1、把"单次"降 3 倍，
   但**没有**把全仓 AST 分析变成常数级。若 runner 慢到"单次扫描 > 300s"（2026-09-22 那轮
   实测量级），本文件仍会红 —— 只是从"6 次 × 300s"变成"1 次 × 300s"。**真正兜底的仍是 (c) 加核**，
   或把该文件的扫描型用例移入 Nightly（(a)，本轮**未做**）。
2. **跨进程产物只在"状态相同"时共享**：两个 worker 若**同时**冷启（都未命中产物），仍会各扫一次
   （未做"谁先写谁广播、另一个等待"的互斥）。实测最坏情形是 2 次而非 6 次；若要彻底 1 次，
   需要加锁等待（本轮评估为收益小、复杂度与死锁风险高，未做）。
3. **预筛的"全仓等价性"是一次性对拍**（§4 的 sha256），不是每次 CI 都跑的常驻用例
   （常驻只跑合成语料 + 标识集派生守卫）：跑一次全仓双扫要 +5s 左右。若日后有人再改
   `_collect_findings` 的判据分支，**应当重跑 §4 那条对拍命令**。
4. **第二条红已在 CI 上得到验证（但本机算术仍解释不了倍数）**：改造后同一 job
   （全项目覆盖率 Shard 2/6）**3 轮全为 `11m00s` 且全通过**，改造前是 `58m01s` 且重试一次仍超时
   ⇒ ⑤ 打掉的正是该 job 的主要成本。**如实保留**：本机口径（85 次解析 × 26ms ≈ 2.2s）本身
   推不出 300s，说明 CI 上该放大器的倍数远大于本机（覆盖率追踪 + 更慢的 CPU 叠加），
   我没有单独测出那个倍数 —— 结论只建立在"同一 job 改造前后 58m 超时 → 11m 通过"的实测对比上。
5. **仍未做结构性改造的其它负载敏感项**（仅登记）：`test_load_tool_meta_cache.py` 的 5ms 性能预算、
   `test_skills_digest_assessor` / `test_process_distill` 的等待上界 —— 仍是"预算校准 + 重跑"的既有处置。
6. **本地分片级数据不可比**：两次本地分片尝试被套件既有的偶发卡死打断（真实外连 HTTPS 卡在 `SynSent`；
   懒加载 `torch` 导入超 120s 预算），故分片级只报 CI 的 job 耗时（§8）。
