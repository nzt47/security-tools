## 2. 唯一的产品缺陷：vec0 KNN 约束写法跨平台失效

### 2.1 现象

CI 日志（Linux / Python 3.12.14）：

```
ERROR memory.vector_store.sqlite_vec_backend:sqlite_vec_backend.py:259
  [SqliteVecBackend] search 失败:
  A LIMIT or 'k = ?' constraint is required on vec0 knn queries.
```

连续出现 **5 次**，全部紧跟在
`[SqliteVecBackend] 初始化完成: db=…/sqlite_vec_test_*/test_vec.db, dim=4, table=vec_test`
之后 ⇒ 触发者就是**该测试文件自己的用例**，不是并发问题。

### 2.2 根因

原实现（`ORDER BY distance LIMIT ?` 的子查询再 JOIN metadata）**依赖
"LIMIT 被下推进 vec0"**。该前提在 Windows 上成立、在 Linux 上不成立。

**实测排除"扩展版本"这个可能**（避免误修）：

| sqlite-vec 版本 | Windows 上旧写法 | Windows 上新写法 |
|---|---|---|
| 0.1.9 | ✅ 放行 | ✅ 放行 |
| 0.1.10a2 | ✅ 放行 | ✅ 放行 |
| 0.1.10a4 | ✅ 放行 | ✅ 放行 |

⇒ 与扩展版本无关，是**平台查询计划器差异**。

### 2.3 修法

改为 sqlite-vec 文档给出的**规范 KNN 约束写法** `AND k = ?`（不依赖 LIMIT 下推）：

```sql
SELECT k.id, m.content, m.metadata, m.timestamp, k.distance
FROM (
    SELECT id, distance FROM vec_test
    WHERE embedding MATCH ?
      AND k = ?            -- ← 规范写法；此处不再需要 ORDER BY
) k
JOIN meta_test m ON k.id = m.id
```

语义等价、代价为零（仍走 KNN 索引路径，返回行数与 `top_k` 一致）。

### 2.4 顺带揭开：一个被测试掩盖的静默失效（**比上面 4 个用例更重要**）

`search()` 的 `except` 把异常吞成 `return []`：

```python
except Exception as e:
    logger.error("[SqliteVecBackend] search 失败: %s", e)
    return []          # ← "查询失败" 与 "查无结果" 返回值完全相同
```

而上层 `VectorStore.search` 与 Chroma 分支**同样** `except → []`。

**这解释了一件反常的事**：既有 4 个用例在 Linux 上真实失效时**依然全绿** ——
因为 `test_empty_search` 断言的 `results == []` 与"查询炸了"的返回值**一模一样**。

**处置（刻意保守）**：**不改返回语义**（上层"不传播"是既有契约，
`test_backend_field_not_modified_by_add_failure` 也依赖它），只把降级写进 ERROR 日志，
并把该契约用测试锁死。

### 2.5 回归保护（原用例锁不住这个 bug，故新增）

新增 `TestKnnQueryFormIsPlatformStable`，用 SQLite 官方 `set_trace_callback`
抓**实际下发的 SQL**，断言：① 含规范 `k =` 约束；② 不含 LIMIT。

> **实现踩坑记录**（两处，供后人省时间）：
> 1. `sqlite3.Connection.execute` 在 CPython 3.12 上是 **C 实现的只读属性**，
>    `monkeypatch.setattr` 会报 `object attribute 'execute' is read-only` ⇒ 必须用
>    `set_trace_callback`。
> 2. `search()` 内部 `finally: conn.close()` 会关掉连接，而测试还要读抓到的轨迹
>    ⇒ 需一个把 `close()` 变成 no-op 的代理顶替。
> 3. `set_trace_callback` 抓到的是**参数展开后**的 SQL（`k = 3` 而非 `k = ?`）
>    ⇒ 断言不能用字面量 `"k = ?" in sql`。

**变异探针实测**（证明新用例真的锁得住）：

| 操作 | 结果 |
|---|---|
| 把生产代码改回旧 `ORDER BY … LIMIT ?` 写法 | 新增 **2 例立即变红**；而**原有 4 例在 Windows 上仍全绿** |
| 还原 | 全文件 **30 passed** |

⇒ 直接验证了"旧测试对该缺陷**零覆盖**"。

## 3. 其余 5 个用例：都是测试/环境的自身缺陷

| 用例 | 真相 | 修法 |
|---|---|---|
| `::ffff:127.0.0.1` 归一化 | `str()` 对该地址的渲染**随 CPython 补丁级变化**（3.12.0 → `::ffff:7f00:1`；3.12.14 → `::ffff:127.0.0.1`）。原断言把解释器实现细节钉死在字符串等价表里 | 移出等价表，改为独立用例断言**语义**（`ipv4_mapped` == 内嵌 IPv4、`check_host` 的 `allowed/category/is_internal` 与裸 IPv4 **逐项相等**） |
| `test_reading_matches_init_positional_order` | 两次独立 `reading()` 构造各取当前时间，相差 **25µs** 即红；本用例契约其实是"位置参数映射顺序" | 剔除 `timestamp` 后比较，并单独断言两条都是合法 ISO-8601 UTC；`metadata/tags/severity/category` 断言**全部保留** |
| `test_100KB提示词对齐耗时小于50ms` | CI 实测 **56.7ms**，纯负载抖动（单次采样测的是"当时机器有多闲"） | 预热 + **min-of-5**；阈值 `×3` 有界余量。实测退化倍率：本地 +100ms(15×) 红、CI 余量下 +300ms(43×) 红 ⇒ 回归保护未失效 |
| `test_confirm_level`（2 例） | **测试依赖未入库的运行期文件**（见 §4） | 给测试**自备**最小描述符台账 |

**契约文件污染（顺带查出）**：`tests/contract/contract_framework.py::save_contract()`
既被测试调用、又无条件 `write_text` 到**入库**文件，而导出内容含每次新取的
`generated_at` ⇒ **每跑一次契约测试就改写 6 个入库文件**（差异只有这一行）。
后果不只是"看着脏"：它让 `git status` 失去"工作区是否被污染"这一信号。
改为**无实质变更不落盘**（忽略 `generated_at` 后比较）。

**`tests/perf/` 的 4 处单次采样阈值（顺带查出）**：`可观测性质量保障` 的 Shard 4
报 `assert 56.23216800000819 < 50`，而本地连跑 5/5 通过、整个 `tests/perf` 目录
总耗时仅 0.83s。统一改为重复测量取最优（每轮**重建初态**）+ 有界余量。

## 4. ⚠️ 我的错误定性更正（**本文最值得留存的部分**）

### 4.1 我最初的定性

复查 `test_confirm_level` 时，我把失败归因为：
> 「策略台账缺失 ⇒ 闸门 fail-open ⇒ **把高危工具的审批边界放行了**」（即一条安全降级缺陷）

并且我**差点据此去改闸门的安全语义**。本地"复现"似乎也支持它：
把 `data/descriptors.json` 移开，本地就**恰好复现 CI 的 2 failed / 100 passed**。

### 4.2 为什么这个定性是错的

动手改代码前我验证了两个事实：

```powershell
# ① YAML 里到底有没有这个字段？
Select-String -Path data\tool_definitions\*.yaml -Pattern 'requires_approval|trust:'
#   → 命中行数: 0        ← YAML 根本没有 trust.requires_approval
```

```powershell
# ② descriptors.json 是入库文件还是运行期产物？
git check-ignore -v data/descriptors.json
#   → .gitignore:223:data/descriptors.json
#   → （并注释写明：ToolDescriptor Registry 持久化，运行期台账，同 skills_mgmt.json 不入库）
```

⇒ `data/descriptors.json` 是**运行期派生台账**（由
`scripts/backfill_tool_descriptors.py` 生成、被 gitignore），**CI runner 上不存在**。

⇒ 真相是：**测试依赖了一个未入库的运行期文件** —— 开发者机必然通过、CI 必然失败。
闸门第 2 步"描述符审批边界"读到空索引后走 fail-open，是**本模块文档化的既定语义**
（`tool_gate.py` 注释明写"策略/台账文件缺了 ⇒ 那条规则读不到依据 ⇒ fail-open 放行是对的"），
**不是缺陷**。

### 4.3 正确修法与"断言是否有牙齿"的验证

新增 `real_descriptor_boundary` fixture：`tmp_path` 下自备最小台账并
`monkeypatch` 到 `G.DESCRIPTORS_PATH`（写法与 `tests/unit/test_tool_gate.py`
的 `GateFiles` 同构）。

> **一处刻意的设计选择**：台账里**只列 `shell_execute`，不列 `write_file`**。
> 因为这两条用例的语义是"关掉**新的**分级层时**旧的**边界仍拦住"，
> 而 `write_file` 正是"新加的那部分"；若它也列入就会**被旧边界拦住**，
> 两条断言立刻自相矛盾。**首版实现正是踩了这个坑**（本地 2 failed），已修正。

| 验证场景 | 结果 |
|---|---|
| 开发者机（`descriptors.json` 存在） | **102 passed** |
| 模拟 CI（移开 `descriptors.json`，try/finally 还原） | **102 passed** |
| **变异探针**：把 fixture 台账的 `requires_approval` 改成 `False`（＝旧边界消失） | **恰好那 2 条 FAILED**，其余 100 passed；还原后 102 passed |

⇒ 修的是**环境依赖**，**fail-open 语义一字未动**，断言**仍有牙齿**。

### 4.4 教训

> **定性一个失败之前，必须先把"它所依赖的数据从哪来"查清。**
> 我差点因为一个错误的定性去改**安全语义** —— 而正确的处置只是修测试的环境依赖。
>
> 具体到本案：如果当时"顺手"把 fail-open 改成 fail-closed，会**凭空发明一条
> YAML 里根本不存在的安全规则**，并把一条文档化的既定语义破坏掉。

## 5. CI 配置缺陷：可观测性质量门禁**永远**拿不到集成测试报告

### 5.1 现象

`可观测性质量保障` 的门禁 job 恒报**退出码 2**：

```
⚠️  整体状态: 不确定（inconclusive）- **不得视为通过**
未跑成的检查项（缺报告/缺工具，不代表达标）:
  - integration_tests: 未找到集成测试报告
[quality_gate] 退出码 2：检查未能全部跑成（inconclusive），不得视为通过
```

而其余 5 项检查**全部 ✅ 通过**。

### 5.2 定性：门禁的逻辑是对的，缺的是报告确实没产出

门禁脚本（`scripts/observability_quality_gate.py`）把"找不到报告"记为 `skipped`，
并**刻意**让 `all_passed=False` —— 源码注释写明"**「跳过」不等于「通过」——
不要在这里放宽门禁来让报告变绿**"。这个判定**正确，不应放松**。

真因在 workflow：

```yaml
- name: 上传集成测试结果
  uses: actions/upload-artifact@v7
  with:
    name: observability-integration-test-results
    path: test-results/          # ← 该目录从未被创建
```

该 job 的 pytest 命令**没有任何 `--junitxml`**，仓库 pytest 配置也无 junitxml/addopts 兜底
⇒ 目录不存在 ⇒ `upload-artifact` 上传 **0 个文件** ⇒ 门禁的
`check_integration_tests`（判据是报告路径含 `integration`）永远匹配不到 ⇒ 记为 `skipped`。

⇒ **该 job 的失败与覆盖率、与测试真实结果都无关**：即使 6 个 shard 全绿，
工作流仍会红。（历史上前几次 success 的 run 之所以通过，是因为当时另有其它含
`integration` 字样的报告混在合并目录里。）

### 5.3 修法（不放松任何判定）

1. pytest 增加 `--junitxml=test-results/integration-junit.xml`，运行前 `mkdir -p test-results`；
2. 新增"生成集成测试报告"步骤（`if: always()`），从 junit 解析
   tests/failures/errors/skipped，产出 `test-results/integration-test-report.json`；
   `overall_status` **仅在 failures==0 且 errors==0 且 total>0 时为 `passed`**；
   **报告缺失时写 `failed` 并带 error 说明 —— 绝不写成 passed**。

### 5.4 验证

| 项 | 结果 |
|---|---|
| `yaml.safe_load` 解析 | ✅ 通过；集成 job 步骤序列正确（7 步），含 junitxml 与报告写入 |
| 报告脚本（真实 junit） | `{"total": 102, "failures": 0, "errors": 0, "overall_status": "passed"}` |
| 报告脚本（文件缺失分支） | `{"total": 0, "overall_status": "failed", "error": "未找到 …"}` ⇒ **不会静默通过** |
| 端到端（CI 实测） | 门禁 **6/6 通过、跳过 0、失败 0 → "整体状态: 通过 - 允许部署"**，其中 `集成测试` 由 `skipped` 转 `passed` |

### 6.1 一处必须自己先纠正的表述错误

我在本文与交付报告的**初版**里写了：

> `可观测性质量保障` | run 35539615539 | ✅ 质量门禁 6/6 通过 → 允许部署

**这个写法不准确。** 复查 run 元数据后发现：该 run 的整体 `conclusion` 是 **`cancelled`**：

```
run 35539615539  sha=3990bd57  status=completed  conclusion=cancelled
```

**根因**：该工作流**自带** `concurrency` 取消策略（源码注释原文：
"密集 push 时旧 run 结果已过时，取消仅保留最新可显著降低排队长度；
本 workflow 是全项目 6-shard 最贵 job（30-45min/run）"）。
我在它收尾阶段又推了一次提交 ⇒ **它被新 run 按设计取消**。
同一原因也取消了 `35538236909` 与 `35539102814` 两个观测 run
（三个 run 的 `conclusion` 均为 `cancelled`）。

⇒ **正确口径（两个都报，不含糊）**：
- **门禁检查项**：**6/6 实测通过**（有 job 日志为证），`集成测试` 由 `skipped` 转 `passed`；
- **整轮 run**：**`cancelled`，不是 `success`**。

> **为什么必须自我纠正**：这正是本项目整轮在消除的那类失真 ——
> **把"部分成功"写成"全绿"**。我要求子代理不这么做，就必须对自己同样严格。
> 我最初写出那个表述，是因为**只看了 job 状态而没查 run 的整体结论**；
> 检查一个 run 是否真的通过，必须**同时**看 `run.conclusion`
> 与关键 job 的 `conclusion`，二者可能不一致。

### 6.2 无干扰验证

为取得一份**不会被后续推送取消**的完整结论，已用 `workflow_dispatch` 触发：

该触发方式不依赖 push、不会被新推送取消 ⇒ 其收尾结果可作为该工作流的最终结论。
**在它收尾之前，本工作流只有"门禁 6/6 通过 / 整轮 run cancelled"这一条结论。**
主 CI（`云枢系统测试流程`）的 success **不受影响** —— 它那一轮未被取消。
