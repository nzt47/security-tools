## 2. 逐项：根因 / 修法 / 证据

### 2.1 台账 #2 —— 伦理规则把**参数名**当内容匹配

**根因**：`agent/human_in_the_loop/ethics.py` 的规则是 `"format" in str(params)` —— 把整个参数字典（**含键名**）转成字符串做裸子串匹配。
delegate 的必填参数 `artifact_format` 让**每一次**委派都命中 E002「禁止格式化磁盘」；`git log --format=%H`、`"{}".format(x)`、`grep shutdown` 同样误报。

**修法**（`agent/human_in_the_loop/ethics.py`）：
- 规则只对**参数值**判定（递归摊平；映射键名永不产出）；
- E002/E003 要求命令动词落在**命令位**（串首，或紧跟 shell 分隔符/引号/括号/换行，容许 sudo/doas/cmd /c/powershell -c 前缀）。

**真命中一条没放宽**：`format C:`、`shutdown -h now`、`bash -c "shutdown -h now"`、`sudo shutdown -h now`、`rm -rf /`、`del /f`、E004/E005/E006 全部照旧（tests/unit/test_ethics_engine.py 钉住）。

**实测**：改前 `delegate → E002`；改后 `delegate → confirm_level=L1（plane=act, effect=execute, risk=medium）`，理由里再无伦理规则。

### 2.2 台账 #1 —— 裁定为设计内 + 挖出其中真缺陷

**裁定（有证据）**：
- `run_sandbox` / `shell_execute`：YAML `risk: critical` ⇒ 派生 **L3**，且 `data/descriptors.json` 也标 `trust.requires_approval=true`；**两个来源逐条一致**（全部 10 条描述符与 YAML 对拍通过）。⇒ 拦截正确。
- `delegate`：YAML `effect: execute` ⇒ **L1（摘要确认，可批量）**，由 `tests/unit/test_confirm_level.py` 明确钉住"L1 也要确认"。
- 放行路径实测可用：挂单 → 人工批准 → 原样重发 → 执行（且 L1 批准在会话+TTL 内可复用）。

**其中真缺陷（已修）**：因为 #2 的误报，`delegate` 在**两个书面承诺会放行的配置下仍被拦**：
- `CP_TOOL_CONFIRM_LEVEL_ENFORCE=0`（文档化的窄回滚）；
- `CP_TOOL_CONFIRM_LEVEL_SHADOW=1`（"只告警、不拦截"）。
改后两者都实测 ALLOWED，而**真命中**（run_program + shutdown）在影子态下仍被拦。

### 2.3 台账 #3

`submit_task → get_task_status → get_task_result` 畅通，无改动。

### 2.4 控制台页不可达（人点不到）

- `GET /api/approval/console` 挂 `@require_token`，而**浏览器地址栏导航无法携带 Authorization 头** ⇒ 打开即 401（实测）。
- 修法：新增 `GET /approval-console`，**只返回静态外壳**（模板里仅一个挂载点，不含任何数据）；`/api/**` 的令牌纪律不动。
- 去重：两条路由共用 `_render_console_shell()`。
- 测试：人工入口无令牌可开（200）、外壳里**不得出现任何审批记录**（外壳 ≠ 数据）。

### 2.5 控制台 JS 不带令牌

`static/js/approval_console.js::request()` 只发 Accept/Content-Type/X-CSRF-Token，**从不注入 API 令牌**。
修法：注入 localStorage 的 `yunshu_api_token`（与 React 侧 `apiToken.ts` **同键**），缺令牌时面板内可直接粘贴，并把 401 与 403 分开提示。
配套测试：两处令牌键**必须同键**（防"主界面登录过了、控制台还说没令牌"的第二真相源）。

### 2.6 工作台审批收件箱 401 unknown_session（你可复现的那条）

- **根因**：`yunshu-ui/src` 里**没有任何地方调用** `POST /api/approval/session`，也从不带 `X-CSRF-Token`；
  而批量裁决 `/api/cp/approvals/batch/link` → `/batch` 逐条复用单条审批链（会话 → CSRF → 一次性链接 → 二次认证 → 矩阵）⇒ 每次裁决必然 401。
- **修法**：新增 `yunshu-ui/src/lib/approvalChain.ts`：
  - 无会话标记时先开会话（用 JS 可读的 `cp_approval_csrf` 当标记；`cp_approval_session` 是 HttpOnly，JS 读不到，这是对的）；
  - 审批请求带 CSRF 头；`apiClient` 增加 headers 选项（Authorization 仍由客户端后合并）；
  - 命中 `unknown_session` / `session_expired` / `csrf_mismatch` 时**重开会话并重试一次**（后端会话只在进程内、重启即失效）；`session_mismatch` 等真实冲突**不重试**。
- **线上实测**（干净 curl 会话，复刻面板调用序列）：

```
① 开会话                  → 200，csrf cookie 32 字符且 JS 可读
② 不带 CSRF 头 batch/link → 403 csrf_mismatch   ← 校验没被绕过
③ 带 CSRF 头 batch/link   → 200，batch_id 已签发  ← 修复前这里是 401 unknown_session
④ 完全不开会话            → 401 unknown_session   ← 复现你看到的那条
```

### 2.7 新增 CLI 通道（代码承诺过、但一直不存在）

`agent/capregistry/invoke.py` 与 `agent/tool_gate.py` 都写着"改由人工身份（**CLI 交互** / 审批收件箱）执行一次"，而全仓没有任何脚本实现它。
新增 `scripts/approve_tool_call.ps1`：列单 / 批准 / 驳回 / `-DryRun`，走**同一条安全链**（会话 → CSRF → 一次性链接 → 二次认证 → 矩阵），令牌永不打印；不合法记录、非待审记录都有明确回执。

## 3. 安全姿态变化（**请重点复核这一节**）

### 3.1 新增的豁免开关

| 项 | 值 |
|---|---|
| 开关键 | `CP_TOOL_CONFIRM_LEVEL_EXEMPT`（逗号分隔工具名/能力 id） |
| 登记级别 | **A 级（可直接切）**，热生效 |
| 落值 | UI 改动写 `data/ui_settings.json` 覆盖层（**绝不改 .env/config.yaml**） |
| 谁能改 | `settings.change`：Actor 矩阵里**只有 human 放行**，auto / sub_agent / service_account 一律拒 ⇒ **云枢无法给自己松绑** |
| 留痕 | 每次改动进审计链（settings.change），闸门命中时另记 decision=exempted |

**为什么是 A 而不是 B**：B 级要求**两位不同的人工**（`second_approver_must_differ`）。本机是单操作者部署，登记成 B 只会得到一个"永远批不过"的死按钮——那比 A 更坏（人会以为坏了，转头手改 .env，绕过全部留痕）。**最粗的两根杠杆（CP_TOOL_GATE_APPROVAL_ENFORCE / CP_TOOL_CONFIRM_LEVEL_ENFORCE）仍是 B 级**，未被降级。

### 3.2 豁免**够不着**的 10 个工具（仍然要人工确认）

`shell_execute`、`run_sandbox`、`generate_tool`、`ext_install`、`ext_uninstall`、`ext_toggle`、`ext_configure`、`connect_mcp`、`disconnect_mcp`、`scan_mcp`

它们的审批要求来自**能力描述符**（`trust.requires_approval`），判定排在分级层**之前**。界面上这些行显示为**锁定徽章 + 原因**（点了不发请求），而不是给一个点了没反应的开关。
⇒ 若要让它们也免确认，只能改 `data/descriptors.json` 或关闭审批边界总开关（B 级；**代价是伦理硬规则一并降级为仅告警**）。

### 3.3 豁免**不放宽**的东西（由测试钉住）

- 权限策略黑名单、描述符硬要求、受限会话 sandbox_allowed（都判在更前面）；
- **伦理硬规则**（禁 rm -rf /、格式化、关机、读 /etc/passwd…）——判在更后一步，不依赖审批开关；
- RBAC/ABAC 严格模式（判在更后面）；
- **子代理自己发出的工具调用仍各自过闸门**（`agent/tools/__init__.py::call` 是唯一汇聚点）。

## 8. 附：本次踩到的坑（供后续参考）

- **"批准绑定参数摘要"**：批准绑定 `(工具, 参数摘要)`；参数差一个字就算另一次调用。云枢前几次重试各挂了不同的单，**批其中一张放行不了另一次重试**。
- **审计单次有效**：L1 的批准在会话+TTL 内**可复用**，L2/L3 **单次消费**。
- **审批会话只在进程内**（`approval_session.py`："重启即失效，fail-closed"）⇒ 后端一重启，浏览器手里的 Cookie 就指向不存在的会话。
- **开关中心的 env 锁定**：只要 env 里有值（**哪怕是空串**，实测过）该键就被判"运维注入 ⇒ UI 不可改"。
