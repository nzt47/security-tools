## 0. 一句话结论

在**应用启动路径**（组合根 `app_server.py`）上补了一次**无条件**的熔断器状态发布：
`_publish_circuit_breaker_states()` → `business_metrics.publish_deployed_circuit_breaker_states()`
→ `agent.circuit_breaker.get_circuit_breaker(<真实名字>)`（访问点内即 `_notify_state_observer`）。
实测 `python -c "import app_server"` 后，`export_prometheus()` 里熔断器相关行由 **4 行（只有 HELP/TYPE、0 条样本）
变成 8 行（多出 4 条真实样本行）**；分层、既有空族契约、幂等性均由新增测试守住。

## 1. 发布点：选了什么、为什么是它、分层依据

### 1.1 先查清楚"本部署到底有哪些熔断器"

按指定命令枚举生产调用点（`agent/`、`app_server.py`、`plugins/`），并用 AST 级别的正则把
`get_circuit_breaker(...)` / `CircuitBreaker(...)` / `CircuitBreakerConfig(name=...)` 的字面名全部列出：

| 名字 | 出处（生产代码） | 是否经**全局注册表** | 本次是否发布 |
|---|---|---|---|
| `guardrails.egress_chain` | `agent/guardrails/egress_chain.py:381`（常量定义 `CHAIN_BREAKER_NAME` 于 `:57`） | ✅ `get_circuit_breaker` | ✅ 发布 |
| `learning_budget` | `agent/learning_budget.py:182`（默认名定义于 `:153`） | ✅ `get_circuit_breaker` | ✅ 发布 |
| `critic` | `agent/cognitive/critic.py:114` | ✅ `get_circuit_breaker` | ✅ 发布 |
| `schema_validation` | `agent/guardrails/output_schema.py:202` | ✅ `get_circuit_breaker` | ✅ 发布 |
| `capregistry.{kind}` | `agent/capregistry/loader.py:181` | ❌ **直接构造**实例 | ❌ 刻意不发布 |
| `prometheus-exporter` | `agent/monitoring/prometheus.py:75` | ❌ **直接构造**实例 | ❌ 刻意不发布 |
| `session` / `user` / `global`（三级） | `agent/circuit_breaker.py:891/903/914` | ❌ `ThreeLevelCircuitBreaker` 内部实例 | ❌ 不发布 |
| `tool_calling` | `agent/tool_calling.py:26` 只 import 不使用（`:220` 注明旧字段已删） | — 无调用点 | ❌ 不发布 |

**两条筛选原则（都可一句话检验）**：

1. **只发布"经全局注册表 `get_circuit_breaker(<字面名>)` 取用"的名字。**
   只有这类名字，发布出去的状态才与真实业务路径**拿到的是同一个对象**。
   直接 `CircuitBreaker(...)` 构造的实例（`capregistry.remote` 等、`prometheus-exporter`）
   **不在 `_breakers` 注册表里**，若用同名去注册表取，会新建**另一个对象**
   ⇒ 那条序列会是**假的**（永远 closed、永远不反映真实熔断），比"没有序列"更难发现。
2. **只发布本仓生产代码里出现过的字面量**（新增测试
   `test_发布的名字都取自生产源码的真实字面量` 做静态守卫，禁止编造名字）。

### 1.3 发布方式：复用**已有的**访问点，不新增埋点通路

`agent/circuit_breaker.py:659 get_circuit_breaker()` 在第 `686` 行本就有
`_notify_state_observer(name, None, state)`（`None` = "仅发布当前状态"），
经 `business_metrics.py:2395 _on_circuit_breaker_state` 落到
`update_circuit_breaker_state()` → `_set_gauge("yunshu_circuit_breaker_state", ...)`（**幂等**）。
本次**没有新增任何埋点通路**，只是补上"谁来无条件触发它"：

```
app_server.py::_publish_circuit_breaker_states()          # 模块级调用，启动即执行
  -> agent/monitoring/business_metrics.py::publish_deployed_circuit_breaker_states()
     -> agent.circuit_breaker.get_circuit_breaker(name)   # 访问点内 _notify_state_observer(name, None, state)
        -> business_metrics._on_circuit_breaker_state()
           -> BusinessMetricsCollector.update_circuit_breaker_state()
              -> _set_gauge("yunshu_circuit_breaker_state", {breaker_name, state}, 1.0)
```

**没有伪造数据**：写进去的值是熔断器对象的**真实状态**（`breaker.state.value`，实测均为 `closed`），
不是给空族补的常量；`export_prometheus()` 的"空族只输出 # HELP/# TYPE"契约**一行未动**
（并由新增测试的对照断言守住）。

### 1.4 分层依据（为什么放在这两个文件）

- 契约：`.importlinter` + `tests/unit/test_circuit_breaker_layering.py` 规定
  `agent/circuit_breaker.py` **不得**导入 `agent.monitoring.*`——因为
  `agent/error_handler.py` 会导入 `agent.circuit_breaker`，反向 import 会让**底层间接依赖上层**。
- 本次选择的方向与仓内既有做法（`_install_circuit_breaker_observer` 的"上层注入"）完全一致：

```
app_server.py  (组合根/最上层)
   -> agent.monitoring.business_metrics   (monitoring = 上层)   # 发布函数写在这里，紧邻既有注入点
      -> agent.circuit_breaker             (底层，被 error_handler 依赖)
```

- 发布函数刻意**不放在 `business_metrics` 的导入期自动执行**：该模块被大量单测/脚本导入，
  导入期写全局采集器会污染每一个"只读导出"的调用方断言。
  "发布"是一次**部署动作**，属于组合根职责，因此由 `app_server.py` 显式调用。
- 名字清单放在 `business_metrics.DEPLOYED_CIRCUIT_BREAKER_NAMES`（monitoring 层），
  `app_server.py` 只负责"启动时驱动一次"，不复制清单 ⇒ 单一事实源。

## 5. 剩余边界（什么情况下这条规则**仍会** firing）

1. **应用根本没起来 / 端点抓不到**：进程未启动、`up{job="yunshu-business"}=0`、
   `/api/business/prometheus` 不可达 ⇒ 两条序列都不存在 ⇒ `absent(...) and absent(...)` 为真 ⇒ **firing**。
   **这是本规则的本意（真阳性）**：C-2 那次窗口的第一段就是这种情况（T+89.7s 起 `up=0`）。
   此时该修的是"应用为什么没起来"，不是压制这条规则。
2. **应用起来了、但埋点管道坏了**：`business_metrics` 导入失败、采集器单例被替换、
   `_state_observer` 被卸载、`get_circuit_breaker` 抛异常等 ⇒ 发布为空 ⇒ 仍然 firing。
   这正是这条规则**应当**给出的信号（"配置可能被移除或模块未加载"）。
3. **只覆盖本次登记的 4 个熔断器**：将来新增熔断器却漏登记，
   **新熔断器不会有自己的序列**（但已有熔断器的序列仍在 ⇒ 本式不会触发，也不会发现漏登记）。
   这是"漏登记"的可见性缺口，需要靠登记表守卫那一族测试补，不能靠这条规则兜。
   另外，`capregistry.{kind}`、`prometheus-exporter`、三级熔断器的 `session/user/global`
   **本就不在这套业务指标里**（它们不走 `get_circuit_breaker` 注册表），本次也**刻意不发布**。
4. **本次改动尚未在活体上生效**：正在运行的 :5678 实例是旧进程（§4.5 实测仍是 0 条样本）。
   在它被重启/重新部署之前，C-2 那种场景**依然不会 resolved**。
5. **`state` 序列的"陈旧分面"问题（既有行为，本次未改）**：
   `_on_circuit_breaker_state` 只把**新状态**写成 1，不把**旧状态**写成 0。
   所以一个熔断器从 closed 转 open 后，导出里会同时存在
   `{state="closed"} 1.0` 与 `{state="open"} 1.0`。
   本次启动发布会保证 `{state="closed"} 1.0` 一定先存在，使这种并存**更容易出现**（此前也可能出现，
   只是要等到发生过一次状态转换）。对依赖 `state="open"` 的那几条规则（`CircuitBreakerStuckOpen`、
   `CircuitBreakerGlobalTriggered`）**无影响**，但对"按 `state` 分面求和"的看板是个已知噪声源。
   **本次刻意不动它**（改它等于改既有埋点语义与看板口径，超出本任务范围）——见 §6。
