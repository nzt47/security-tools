## 2. 取证明细

### 2.1 15 条缺失 seq —— **曾存在，且可逐字还原**

**判据（决定性）**：`data/audit/audit_chain.db.seqjournal` 是设计上的**预写日志**
（`agent/audit/seq_journal.py` 模块 docstring：整条记录在锁内先写日志、再由后台批量入库）。
逐行解析该日志（20,090 行，0 损坏行）：

| seq | 结论 | 日志中的 `prev_hash` 是否 == DB 中 seq-1 的 `self_hash` |
|---|---|---|
| 19220 | 在日志中（1 次） | ✅ 是（`f2167db2…` == seq 19219 self_hash） |
| 19768 | 在日志中 | ✅ 是（`7cfe571e…` == seq 19767 self_hash） |
| 20077 | 在日志中 | ✅ 是（`a3dd4ace…` == seq 20076 self_hash） |
| 20078–20085 | 在日志中 | 链条内部互相衔接（依次 prev==前一条 self） |
| 20092–20095 | 在日志中 | ✅ 首条 prev == 20091 self_hash；末条 self == 20096 的 prev_hash |

**日志与本库的差集恰好是且仅是这 15 条**（`journal-only seqs = 15`，`db-only seqs = 14`）；
日志内部空洞**也只有 2 处**（477、552，见 §2.3）。

**「是否被删」的直接否证 —— 表从未发生删除**：

```
rows = 20089            id 范围 = 1..20089（span 20089，gap = 0）
sqlite_sequence['audit_chain'] = 20089     PRAGMA freelist_count = 0
```

`id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`，`sqlite_sequence` 记录**历史分配过的最大 id**。
若曾有 15 行被插入后删除，则 `sqlite_sequence` 必为 20104 而现存 20089 行。
实测 `sqlite_sequence == count == max(id) == 20089`、且 id 集合是**无空洞的 1..20089**
⇒ **该表一生只插过 20,089 行、从未删过任何行**。

**旁证（每日根）**：2026-09-17 的日根封印区间 `seq 8437..19228`（10792 个槽位）而
`leaf_count = 10791`，且**按序区间重放 Merkle 根与记录一致**（`L1_evidence/root_semantics.log`
“BY-RANGE MATCHES_RECORD=True”）⇒ 封印那一刻 **19220 就已经不在库里**——不是封印后被删。

**为什么 20077–20085 是 9 条连续**：这 9 条不是"删除"，而是**同一进程在一次终止中丢掉的
在途批次**。其时间戳显示它们由**突发批量**产生、跨约 5 分钟、随后进程消失：

```
20077..20083  2026-09-20T11:31:46.0x  guardrails.ssrf_guard / egress_blocked  (同一毫秒 7 条 = 一次 SSRF 测试突发)
20084         2026-09-20T11:33:51     diag / ssrf_probe_test
20085         2026-09-20T11:36:38     auto / approval.submit (web_get)
--- 此处进程终止 ---
20086         2026-09-20T11:59:53     system / global_test_action   ← 新进程从日志链头续接
```
同理 20092–20095 是 `guardrails.foreign_taint` 在 `14:23:43.30x` 同一毫秒的 4 条突发；
19220 落在 `17:38:48` → `23:38:13`（**近 6 小时的关机边界**）。
四条空洞的**两侧边界都恰好是进程空闲/终止边界**，这是"队列未提交即随进程消失"的典型特征，
与"批量 DELETE"不符（`DELETE` 会留下 `sqlite_sequence` 与 freelist 痕迹，实测均为零）。

### 2.2 6 处断点的成因（**两类，成因不同**）

| # | 断点 | 缺口 | 成因 | 证据 |
|---|---|---|---|---|
| 1 | 476→**477** | 无 | **UI 写路径绕过预写日志 + 取到外来 prev_hash** | 见 §2.3 |
| 2 | 551→**552** | 无 | 同上 | 见 §2.3 |
| 3 | 19219→**19221** | 1 | **丢失写**（日志有、库无） | 日志中 19220 的 prev/self 与两侧严丝合缝 |
| 4 | 19767→**19769** | 1 | 丢失写 | 同上 |
| 5 | 20076→**20086** | 9 | 丢失写（一次终止丢掉同一在途批次） | 9 条在日志中连续且哈希自洽 |
| 6 | 20091→**20096** | 4 | 丢失写（同毫秒 4 条突发） | 同上 |

**为什么这 4 处"丢失写"必然造成"断点"而不是"空洞"**：`_resolve_head()` 的权威链头取
`max(内存, 日志末行, DB 最大行)`，而**日志优先于 DB**。进程终止后新进程从日志读到
"链头 = 那条未入库的记录"，于是**下一条记录以它的 self_hash 作为 prev_hash**。
结果：库里少一行，但下一行的 `prev_hash` 指向"不存在于库中的哈希"——正是实测形态。

**根因（为什么从未被自愈）**：`AuditChain._drain_journal()` 用
`self._journal.read_since(0, limit=5000)` 取候选，而 `read_since` 按 seq **升序**返回并
截断到前 5000 条。日志覆盖 seq 13..20104，故它永远只看得到 **seq 13..~5013**；
19220 及之后的空洞**不在窗口内**，`_drain_journal` 判定"前 5000 条全在库"后即
`_journal_needs_drain = False` 收敛退出。设计意图（"精确判定哪些 seq 不在库"）正确，
但**扫描窗口有界，导致高序号空洞永久不可达**。

### 2.3 seq 477 的来源判定 —— **用户后端写入，不是测试写入**

`seq=477` 与 `seq=552` 的完整 payload：

```json
{"actor_ip_hash_status":"degraded_no_key","actor_ip_masked":"127.0.xxx.xxx",
 "actor_ip_present":true,"actor_source":"explicit","actor_type":"human",
 "audit_scope":"ui_write_route","body_bytes":0,"body_hash":"","duration_ms":17.823,
 "endpoint":"admin.api_apply_network_config","identity_degraded":true,
 "identity_source":"remote_addr","identity_tier":"degraded","method":"POST",
 "path":"/api/apply-network-config","query_keys":[],"schema":"audit.chain.v1",
 "status":"ok","status_code":200}
```

**结论：这是真实生产 UI 写路由（管理控制台"应用网络配置"）的成功请求，非测试写入。** 判据：

1. `source='ui'`、`actor='ui:127.0.0.1'`、`audit_scope='ui_write_route'`、
   `endpoint='admin.api_apply_network_config'`、`method=POST`、`path='/api/apply-network-config'`，
   且带**实测往返时延** `duration_ms=17.823 / 26.14` —— 这是真实 HTTP 中间件的产物形态。
2. **它不在预写日志里**，而**全部 874 条 `source='ui'` 记录中，只有 477 与 552 这两条不在日志里**
   （其余 872 条都在）。这两条正是**唯一两处"无缺口断点"**。⇒ 它们走了一条**绕过
   `SeqJournal` 的独立写库路径**，即 2026-09-12 当时尚存的旧 UI 直写缺陷；后来（seq 851 起）
   该路径已改为经日志，故 `link_ok=True`。
3. 它们的 `prev_hash`（`5aab0bf0…` / `856ab3ec…`）**在整库与整份日志中都不存在任何
   `self_hash` 等于它** —— 是**外部/历史链系的悬空哈希**，而非本链成员。
4. **与 TASK-07 的两条 401 不是同一条**：这两条的 `status_code = 200`、`status = "ok"`。
   即 TASK-07 报告中"两条 401 / identity_tier degraded"若确指此端点，则其状态码记错了；
   本报告只对**实际记录的内容**负责：本端点在链上共 224 条 `ui:127.0.0.1` 记录，
   `status_code=200` 的成对成功请求出现在 09-12/13/14/15/16/17/20 多天，
   呈"人工点击 Apply"形态（成对、间隔数秒、间隔天级分布）。

**为何这两处无法零改写修复**：`self_hash = sha256(seq|ts|actor|action|subject|payload_hash|prev_hash)`
含 `prev_hash`。把 477 的 `prev_hash` 改成 476 的 `self_hash` 后，477 的 `self_hash` 必然改变，
而 478 的 `prev_hash` 又引用了 477 的旧 `self_hash`——**哈希前向传播不可回避**
（数学性质，非实现选择）。故修 477/552 必然要求**从 477 起重算到 20104**，共 19,628 行（97.7%）。

## 3. 方案对比与推荐

| 路线 | 说明 | 对 `daily_roots.jsonl`（含 ed25519 签名）的影响 | 结论 |
|---|---|---|---|
| **A 归档 + 重建** | 归档现库，重建只含合法记录的新链，seq 重编号 | 全部 6 个日根的 `first_seq/last_seq` 与叶子集合全变 ⇒ **6/6 不可验**；历史 attestation 与数据彻底脱钩 | ❌ 不推荐 |
| **B 保号修复** | 保留 `seq/ts/subject`，只重算 `prev_hash`/`self_hash`，并清理污染 | 重算使所有 `self_hash` 变 ⇒ 6 个日根的 Merkle 叶子全变 ⇒ **6/6 失效**；若再删 5,130 条污染，**再添 5,130 个空洞**，须二次重链接 | ⚠️ 仅取"保号 + 重链接"部分 |
| **C 只修断裂** | 不删记录，只在断点补齐链接并重算后续 | 与 B 的哈希后果**完全相同**（477 之前无断点，故重算范围 = 477..20104）→ **6/6 失效** | ⚠️ 与 D 合并执行 |
| **D 日志回放（本报告采用）** | 把日志中 15 条**从未入库**的记录**原样原哈希**插回 | **不触碰任何现有行**；09-17 日根的封印区间内新增 1 片叶子 ⇒ 该根 `root_hash`/`leaf_count` 需重生成 | ✅ **推荐** |

**推荐路线：D（零改写的 WAL 恢复）→ 残余 2 处断点按 C 重链接 → 日根重生成。**

对 `daily_roots.jsonl` 的最终处置（**必须显式决策，本报告已执行"重生成"**）：

- 重链接后，6 个历史日根记录的 `root_hash` 对应的 `self_hash` 集合**已不存在**，
  它们**无法再通过 `--roots-check all`**（不是"被篡改"，而是"所炼之链已被修订"）。
- 本次执行**重生成**：按重链接后的 `self_hash` 重算 6 个日根的
  `root_hash / leaf_count / first_seq / last_seq / first_self_hash / last_self_hash`，
  用**同一把 `audit_signing_key.pem` 重新 ed25519 签名**，并按原顺序重算外层根链
  `prev_entry_hash → entry_hash`（`get_daily_root()` 返回**首个**匹配项，故必须原地重写而非追加）。
- **原始 6 条日根已完整留档**：`L1_evidence/daily_roots.ORIGINAL.jsonl`
  （sha256 `3A776CB928D6875EBF64F7019345EEEB28F56CD7DB39AF92AE45F92BE5718181`）。
- ⚖️ **合规提示（须由仓库负责人确认）**：重签名意味着"用同一把私钥对修订后的链重新出证"。
  若合规口径要求"原始出证不得覆盖"，则应改为**保留原始 6 条、并在报告/外部存证中标注
  "该链经 L1 修复后与原始日根不再对应"**——回滚命令与原始日根均已就位，可随时切换该口径。
