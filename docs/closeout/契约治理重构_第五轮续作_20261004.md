## 2. P1-front（删 `pickObj` 启发式 / K4）的前置 —— 已量出**真实缺口**

### 2.1 四轮交接的表述与实测的差别

四轮 §4 写：「那些端点开始返回 `X-Envelope: v2`。即先做**后端 `ok()` 的灰度铺开**」。
**方向没错，但缺了一个关键量**：`ok()` 目前**一个调用点都没有**。实测：

```powershell
# 全仓真正 import 信封模块的文件，以及 ok() 的调用点数
Select-String -Path app_server.py -Pattern "api_envelope"
#   → 只 import 了 install_error_handlers / problem，**没有 ok**
```

- `agent/api_envelope.py` 同时导出 `ok()` / `problem()`；
- `ok()` 写入 `X-Envelope`（第 119 行），`problem()` 也写入（第 156 行）；
- 但**只有错误路径被接上**：`app_server.py` 引的是 `install_error_handlers` 与 `problem`。

⇒ 今天 `X-Envelope: v2` 只出现在**错误响应**上，**成功响应一个都没有**。
这也解释了为什么在无令牌下探测时「22 个端点全部带 v2」——那是 401 的头，不是成功体的头。
**这类误读会直接得出「前置已完成」的错误结论**，故新脚本把成功/非 200 分开统计。

**这些约定是逐端点长的，不能靠一条规则归一。**

### 2.3 为什么**不能只改后端**（这条决定了实施形态）

当前消费方是逐端点**特判**的（`pickObj<T>(r) ?? (r as unknown as T)` 这类写法遍地），
不是「统一解包一层」。因此若先把 `ok()` 铺到某个端点上，成功体会从
`{ok, overview}` 变成 `{code, data, message}` —— **现有页面立刻读到错形状**。

⇒ 必须**按端点原子化**走扩展-收缩（同一提交里改完两端），不能「先整个后端铺开、再整片改前端」。
这条正是四轮 §4 里「删掉启发式只会把『猜』换成『错』」的**机械原因**。

### 2.4 建议的第一批（工具已就位）

**选择标准**（不写死端点清单 —— 它会随收口与后端变化，写死等于把今天的数值当契约）：

1. **消费面已明确**：该端点的调用点只有一两处，且代码/注释里已写明真实形状
   （例如 `pages/hub/engine/heartbeat.tsx` 的注释直接写了 `{history, limit, offset, total}`），
   改写时无需语义猜测；
2. **裸数组优先**：今天要靠 `pickList` 猜键名的（如 91 项的 `/api/tools/config`），
   改完收益最大；
3. **单端点单提交**：见 §2.3 —— 两端必须原子化，不能"先铺后端"。

**每个端点一条提交**，做完重跑 §2.2 的命令，以「成功且带 `X-Envelope`」**单调上升**为准。
端点清单直接从该命令的表格里挑，不要另外维护一份（本仓对"两清单同步"已有记录）。

## 3. 一个此前未记录的结构性隐患：commit 的 `templates/yunshu.html` 指向**不入库**的产物

### 3.1 事实

- `.gitignore:448` **刻意**忽略 `static/assets/`（注释写明「部署/开发时执行 build:flask 重新生成」）；
- 但 `templates/yunshu.html` **入库**，且内容是一条带内容哈希的引用：
  `<script type="module" crossorigin src="/static/assets/index-<hash>.js">`；
- CI（`.github/workflows/yunshui-ui-tests.yml:171`）只跑 `npm run build`，
  **没有任何作业校验「入库的模板引用是否存在」**。

⇒ 新克隆者拿到仓库时，`templates/yunshu.html` 引用的入口 chunk **不在工作树里**；
任何一次 `git checkout`（例如合入一个改了前端的 PR）之后，
工作树里的模板会指向一个**已不存在**的哈希，直到有人重跑 `npm run build:flask`。

本机现场即是这个状态：服务实际在跑，而

```
GET /static/assets/index-9nAcc5Ou.js   → 404   （origin/master 模板所引）
GET /static/assets/index-CYZIa2TX.js   → 404   （PR #1006 模板所引）
GET /static/assets/index-CYkfufYv.js   → 200   （在飞 tail 分支模板所引）
```

### 3.2 Vite 内容哈希**不可复现** —— 所以「比哈希判断是否陈旧」是无效方法

同一个工作树、同一份源码，连续构建两次，得到**两个不同的入口哈希**：

```powershell
cd <worktree>\yunshu-ui
npm run build    # → dist/assets/index-BjzRX7wB.js  (489.93 kB)
npm run build    # → dist/assets/index-BBmuKbKf.js  (489.93 kB)   ← 同字节数、不同哈希
```

⇒ **不要**用「入库模板的哈希 == 本地重建的哈希」来判陈旧（会假红）；
也**不要**因为哈希不同就断定构建是陈旧的（会假绿地放行真陈旧）。
真要守这条，判据只能是「**模板所引用的入口 chunk 在构建后确实存在**」，
而不是字节相等。

### 3.3 本轮的处理：**只记录，不改**

- 为什么推迟：它同时牵动 `.gitignore` 语义、CI 作业（要装 Node 并重跑全量前端构建）、
  以及「模板到底算不算源文件」的产品判断；四轮 §5.2 明确要求**新增 CI 作业自己装最小依赖**，
  在前端 job 里加全量构建会显著拉长门禁。
- 什么条件下能做：先由维护者定「`templates/yunshu.html` 是生成物还是源文件」。
  若定为**生成物** ⇒ 从版本控制移除它（与 `static/assets/` 一致），CI 只跑构建；
  若定为**源文件** ⇒ 加一条作业：构建后断言模板引用的入口 chunk 存在于 `static/assets/`。

## 6. 本轮新增的坑（补进四轮 §6 的清单）

15. **「有令牌」和「有结论」是两件事**：无令牌探测时 22 个端点**全部**带 `X-Envelope: v2`，
    看起来「前置已完成」；真相是那 22 个都是 **401**，头来自错误路径。
    **盘点覆盖面必须把「成功」与「非 200」分开统计**，否则会把鉴权层的头当成业务契约。
16. **`ok()` 存在 ≠ `ok()` 被用**：`agent/api_envelope.py` 导出 `ok()` 且它有 23 条单测，
    但**全仓 0 个调用点**。「模块已实现 + 单测全绿」完全不足以证明「机制已生效」——
    要问的是**调用点**，而这只能靠运行期响应头或调用点计数回答。
17. **构建产物的内容哈希不可复现，所以它不能当「陈旧判据」**：同源连构两次得到不同哈希。
    用哈希比对判陈旧会**假红**，用「哈希不同所以没问题」会**假绿**。
    能守的命题只有「引用的文件在构建后存在」（§3.2）。
18. **同一批文件里「形状种类」比「端点数」更能说明工作量**：60 个成功端点 53 种形状，
    意味着这是**逐端点**的活，不是「加一个统一解包」。先量形状数，再决定要不要排期。
19. **「本机绿、CI 超时」要先把差异归到工作树，而不是代码**：
    同一个 `strip_comments`，本机 0.5s、CI >60s。原因不在代码而在**工作树的形状** ——
    CI 有巨大 `node_modules` 子树，而扫描器用 `rglob` 会把它**走完**。
    ⇒ 遇到这类分歧，先问「两边看到的东西一样吗」，再问「代码哪里慢」。
20. **把「优化」做在错误的层上会变慢**：我先用「对 6 个 token 各做一次 `find`」替换逐字符循环，
    语义正确但实测 **1.1s→8.4s**（每轮 6 次调用开销 > 省下的字节码）。
    合成**一条**交替正则后才降到 0.5s。**改完必须量**，否则会把「优化」提交成退化。
21. **既有实现的怪癖要先复刻、不要顺手修**：`strip_comments` 在 `/*` 未闭合时会多补一个换行
    （其循环守卫 `i + 1 < n` 永不检查最后一字符，本仓 4 个文件命中）。
    我第一版"顺手修好"了它，于是「逐字节对照」这条最强证据立刻失效 ——
    只能改用逐例解释差异，说服力掉一个档次。**要修应另开一条并单独立据。**
22. **验证方法的有效性取决于对照物选得对不对**：本次差分验证连错两次 ——
    ① 备份模块放在 `scripts/` 下，它的 `ROOT = parents[2]` 指向了**另一个目录**，
    于是"文件集合不一致"完全是假象；② 备份文件本身躺在被扫描的树里，
    于是"产物字典不相等"也是假象。**对照实验要先证明两边看的是同一个世界。**
23. **同一路径有两份实现时，改动可能落在死代码上**：`/api/heartbeat*` 在
    `plugins/status.py`（活体）与 `agent/server_routes/routes_monitoring.py`（未接线）里
    各有一份。改错那个**不生效、也不报错** —— 是"看起来改完了"的最坏形态。
    本仓已有 `test_server_routes_registration_inventory.py::KNOWN_UNREGISTERED` 记录了
    **模块级**的未接线状态，但**没有**记录"某条具体路径由谁提供"。
    ⇒ 动任何端点前，先问运行期 `url_map`：
    `python -c "import sys;sys.path.insert(0,'.');import app_server;
    print([ (str(r.rule), r.endpoint) for r in app_server.app.url_map.iter_rules() if '<路径片段>' in str(r.rule)])"`。
    本次实测运行期只有 1 条重复路径（`/metrics`），故"重复即遮蔽"是**低频但高杀伤**的一类。

## 7. 本轮最重的一处修复：契约扫描器的**规模爆炸**（Shard 5 超时）

### 7.1 现象与归因

PR #1012（tail）的 `单元测试 (Python 3.12 / Shard 5)` **红**。
按四轮 §6 第 3 条**先读失败原因**：5 条 `Failed: Timeout (>60.0s) from pytest-timeout`，
全部落在 `tests/unit/test_frontend_stray_baseline.py` 的模块级 fixture `current`，
traceback 停在 `collect_stray_frontend_literals` → `count_frontend_literals` → `strip_comments`。
同 run 另有 **3817 passed** —— **断言一条都没失败**。
（这正是四轮 §3 里「Shard 5 的红是超时不是断言」的**同一个形态在同一个分片上第二次出现**。）

### 7.2 根因：两处成本都「随规模」而不是「随需要」增长

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| ① | `_iter_source_files` | `rglob("*")` **先把整棵树走完**，`continue` 只是「走完之后不 yield」，**省不到走树的钱** —— `EXCLUDE_DIRS` 里的 `node_modules` 照样被逐条 stat | 改 `os.walk` 并**就地改写 `dirnames`** 剪枝（`EXCLUDE_DIRS` 成员 + 点开头目录）。点开头前缀是「锚在机制上」，避免逐条列举永远漏 |
| ② | `strip_comments` | **逐字符**过循环，成本与**文件体积**成正比而非与「注释/引号个数」成正比；一次全量扫描要剥 5.8 MB，大头是几乎无注释的 minified 产物 | 普通字符分支先用**一条合成正则**定位「下一个可能改变状态的位置」，中间整段一次切片取出 |

⇒ 本机 0.5s、CI >60s，差别**不在代码而在工作树形状**（CI 有巨大 `node_modules`）。
本仓 #1008 已把修法固化（预筛 + `os.walk` 剪枝 + 记忆化）并解决了另外两处，
**`_iter_source_files` 是最初出现该形态的地方，当时被漏掉了**。

### 7.3 语义不变的证据（本提交最该被复核的部分）

```
模糊测试   随机字符 30,000 例 + 结构化片段 30,000 例   逐字节相同，0 分歧
真实语料   384 个前端文件 / 5,829,335 字符             逐文件对照 0 分歧
文件集合   剪枝版 vs rglob 版（320 + 64 个）           逐条相同
产物面     collect_* 返回的字典                         相同；react stray 0 / legacy stray 2
```

**刻意保留了一个既有怪癖**：`/*` 未闭合时旧实现会多 append 一个换行
（其循环守卫 `i + 1 < n` 永不检查最后一字符；本仓 4 个文件命中）。
不顺手修的理由见 §6 第 21 条。

### 7.4 实测提速

| 指标 | 改前 | 改后 |
|---|---|---|
| 一次全量 `collect_stray_frontend_literals` | 0.488s | **0.174s** |
| 1.4 MB 无注释文件 `strip_comments` | 0.344s | **0.016s**（21×） |
| 同一目录遍历（`rglob` → `os.walk` 剪枝） | 0.059s | **0.013s** |

### 7.5 新增守卫 `tests/unit/test_contract_scan_scale.py`（5 条，**锚机制不锚耗时**）

· 合成树里断言 `node_modules`/`dist`/`.venv` **根本没被下降**（旧实现会走完）；
· 断言剪枝**没把合格文件也剪掉**（防「为快而漏报」）；
· 断言剪枝产物与不剪枝遍历**逐条一致**；
· 用**状态机轮数**（而非秒数）度量剥离成本：无注释大文件应≈1 轮。

> **为什么不用「耗时 < N 秒」**：耗时随 runner 漂移，会假红假绿 —— 而本缺陷**本身**
> 就是「数值随环境漂移」造成的。轮数与机器速度无关，正是「是否随规模爆炸」的直接度量。
