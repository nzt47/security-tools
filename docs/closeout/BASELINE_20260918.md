## 4. 全量测试失败集合（TASK-03 第 3 步第 2、3 项 / **E3 / E6**）

### 4.1 运行口径（**为什么用一个与 TASK-03 略有差异的命令**）

TASK-03 §3 第 1 项给的命令是：

```
python -m pytest tests/unit -q --cov=agent --cov-report=term-missing --timeout=300
```

本次实际使用：

```
python -m pytest tests/unit -q --no-header -p no:cacheprovider -p no:randomly --timeout=300
```

两处有意的差异，理由如下：

| 差异 | 理由 |
|---|---|
| 加 `-p no:randomly` | **pytest-randomly 在本仓默认开启**（`pytest.ini` 未禁，实测日志出现 `Using --randomly-seed=<随机数>`）。基线是**集合比较**，随机顺序会让"本地跑一遍"与"CI 跑一遍"的失败集合漂移，无法区分"回归"与"顺序污染"。仓库自己的全量入口（`ci.yml` 分片、`coverage-ci.yml`）同样固定该参数，`pytest.ini:93` 也把 `-p no:randomly` 记为已知基线的口径（"2026-08-13 全量 `-p no:randomly`：68 failed / 14359 passed / 10 errors"）。 |
| 去掉 `--cov` | 覆盖率与失败集合**不共用一次运行**：`--cov` 在本仓会让耗时型测试（`test_perf_monitor` 单例跑 16.7 万 / 43.9 万次操作）**慢约一个数量级**。串行 + 无 cov 的失败集合才与旧基线可比。 |

### 4.2 集合差异（对照 `failures_baseline.txt`）—— **实测结果**

> "从零干净环境真装成功"未验证。** TASK-03 §3 第 2 步第 6 项的那句
> "在一个干净环境里 `pip install -e .` 能装上"**只完成了前一半**。

### 5.5 `pip check` 的诚实报告（**§4 交付物 3 说"`pip check` 干净"—— 实测不是**）

```
$ python -m pip check
mootdx 0.11.7 has requirement httpx<0.26.0,>=0.25.0, but you have httpx 0.28.1.
gtts 2.5.4 has requirement click<8.2,>=7.1, but you have click 8.4.2.
hermes-agent 0.14.0 has requirement tenacity==9.1.4, but you have tenacity 8.5.0.
langchain 0.2.17 has requirement numpy<2.0.0,>=1.26.0 ... but you have numpy 2.4.6.
langchain-openai 0.1.23 has requirement openai<2.0.0,>=1.40.0 ...
langgraph-prebuilt 1.1.0 has requirement langchain-core>=1.3.1 ...
opentelemetry-instrumentation 0.63b1 has requirement opentelemetry-semantic-conventions==0.63b1 ...
opentelemetry-instrumentation-flask 0.63b1 ...
opentelemetry-instrumentation-wsgi 0.63b1 ...
（共 9 条）
```

**根因**：本机的 `python` 是一个**全局共享解释器**，不是项目 venv。实测：

```
$ python -c "import importlib.metadata as md; print(md.version('mootdx'), md.version('gtts'), md.version('langchain'))"
0.11.7 2.5.4 0.2.17         # ← 这三个都不在任何 requirements*.txt 里
```

**判定**：9 条冲突**全部**来自**其它项目**装进同一个解释器的包
（`mootdx` / `gtts` / `hermes-agent` / `langchain*` / `langgraph-prebuilt` /
`opentelemetry-instrumentation*`）。**落在本项目依赖闭包内的是 0 条**。

**处置**：`scripts/audit_dependency_drift.py --pip-check` **按"是否落在本项目闭包内"分组**，
只对 `in_project_closure` 计数做阻断断言。
**为什么不直接把 `pip check` 挂成门禁**：那会得到一条**永远红、且与本项目无关**的断言，
最后必然被改回 `|| true` —— 这正是本任务要消除的模式。**分组是为了让它不必被放宽。**
