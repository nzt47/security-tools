### 2.4 双路径键的残余偏差：**已根治**（扩展登记模型，2026-09-23 拍板）

`LEARNING_LIFECYCLE_UPGRADE_THRESHOLD` 是**双路径**读取：`skills_mgmt.scale.upgrade_threshold` 为主、
`learning.lifecycle.upgrade_threshold` 为**备用**（`agent/skills_mgmt/lifecycle.py:164-168`：前者为 None 才读后者）。
首版只登主路径 ⇒ **若运维只写备用路径**，`resolve()` 显示 `default` 而模块实际用备用值 —— **残余谎报**（当时如实声明、未修）。

**本轮根治**（用户拍板「扩展」）：`SettingSpec` 新增 `config_path_aliases: Tuple[str, ...]`，
`resolver` 按**模块真实读取次序**（主 → 备用）取值，并新增 `config_path_used` 如实透出**实际命中**的那条路径。

| 场景 | 修前 | 修后 |
|---|---|---|
| 两条都没写 | default / None | default / None（`absent`） |
| **只写备用路径** | default / None ← **谎报** | **config / 备用值**，`config_path_used` = 备用路径 |
| 只写主路径 | config / 主值 | config / 主值（`config_path_used` = 主路径） |
| 两条都写 | config / 主值 | config / **主值**（主优先，与模块同序） |

守护：备用路径**必须非空、不得等于主路径、必须写进 description**，且该键必须有主路径
（`test_alias_paths_are_declared_and_documented`）；双路径键另有**定点**判据
（`test_dual_path_key_is_declared_with_alias`，含「必须写明取值次序」）；对拍工具新增
「只写备用路径」场景（`scripts/audit_settings_config_path_parity.py` 第三段输出，实测命中备用路径 OK）。

**为什么后 13 个键不留 config_path**：它们的归属模块里**没有** config.yaml 读取（逐条核实），
补上路径就是**新的假来源**（UI 会声称值来自 config.yaml，而代码从不读它）——与 L1 反向守护同一条纪律。

## 六、L4：显示口径 —— 让 UI 分得清「未提供」与「显式 false/空」

**问题**：源只有四个 token（env / ui_override / config / default），于是这两种处境在 UI 上都显示「代码默认值」：
- 该键**没有** config.yaml 口径（登记表 `config_path` 为空）；
- 该键**有** config 口径，但 config.yaml 里**没写**这一行。

而运维的动作完全不同（后者写一行就能改）。反向也有盲点：ObservabilityConfig 运行态的值**恰好等于登记默认值**时，
旧口径把 `config_present` 判成 False —— "配置层提供了但与默认相同"被折叠进"未提供"。

**改法（纯显示口径，不改任何生效值）**：

- `resolver` 新增 `config_state` ∈ `provided | absent | no_path` 与 `config_layer` ∈
  `file | runtime | 空`，并透出到 `to_public_dict()`（`config_state` / `config_state_label` /
  `config_layer`）。★ `config_present` 与**全部取值分支一字未改**；三态由既有的
  `config_present` + 「有没有 `config_path`」派生，**不引入第二套"提供"定义**。
- **按层给文案**（`CONFIG_STATE_LABELS` / `CONFIG_STATE_LABELS_RUNTIME`）：两层的"提供"能力不同 ——
  file 层可区分「写了 false」与「没写」；**runtime 层不能**，因为 `observability_config` 初始化时
  用**登记默认值把运行态铺满**（`agent/monitoring/observability_config.py:624`）。
- 前端 `settings.tsx` 的来源行：**仅当 source=default** 时多一枚说明芯片，文案**逐字用后端**
  `config_state_label`（前端不另造说法）；source=config 时不重复（来源本身已说明），
  source=env/ui_override 时由 `shadowed_by` 说明。
- 契约类型 `cpPanelsTypes.ts` 同步补齐字段。

### 6.1 一次**真实缺陷**：运行态层差点把 48 个键全标成「config.yaml 已提供」（独立复核发现，已修）

首版实现把"配置层提供了"写成 `config_source_is_file or obs_value is not _SENTINEL` ——
对 observability 口径的键，"运行态对象里有这个键"**恒为真**（运行态被默认值铺满），于是
**48 个键里 47 个**会显示「config.yaml 已提供该键」，而 config.yaml 里根本没有这些行 ——
**正是本次要消灭的那类谎报**。这是**独立子代理对抗性复核**在交付前抓出来的（见 §十一.2）。

**修法**：运行态层的"提供"取 `config_present` 的既有语义 = **取值与登记默认值不同**（= 真有人设过它），
文案也改成「运行态配置已提供该键（与代码默认值不同）／运行态配置未覆盖该键（当前取代码默认值）」。
**已知局限（如实声明）**：运行态层无法区分「显式设成默认值」与「从未设置」（该对象初值就是默认值）；
文件层没有这个盲区 —— 这是两层能力的差异，不是权宜之计。

**用例**：resolver 侧 10 条（no_path / absent / 显式 false / 显式空串 / C 级空值 / 运行态默认值**不得**报成
provided / 运行态非默认值报 provided 且文案含「运行态」 / **全量** 48 个 observability 键逐一断言
「层标 runtime 且文案不含 config.yaml」 / 参数化三键断言三态只跟配置层走且 source+value 不变）；
前端 3 条（default 上屏且两态文案必须不同、config 不上屏、env 不上屏）。
