## 2. #1020 的红：**断言测的不是它声称的那件事**（本会话最该被复核的部分）

### 2.1 先量：那条断言冤枉了它指向的对象

红的是 `tests/unit/test_network_config_demo_no_side_effect.py::
test_importing_demo_script_does_not_touch_real_files`，报
「导入 `tests/test_network_config_integration.py` 改写了真实配置文件：
[`agent/data/network_config.json`]」。

实测（推进 §4.4bis 已做过一次，本会话复算）：

- 演示脚本连续 3 次以**同样的子进程方式**导入，两个目标文件的指纹**逐字节不变**
  （该脚本导入期会 `pytest.skip(allow_module_level=True)`，根本不执行写操作）；
- 单独跑这条用例**通过**。

⇒ 它红/绿取决于「同一分片里还有谁动过那个文件」。**它测的不是它声称的那件事。**

### 2.2 根因是**测量窗口的边界**，不是断言太严

旧判据是「父进程先取指纹 → 起子进程导入 → 父进程再取指纹」。
CI 的单元测试分片是 `-n 2`（两个 xdist worker **共用同一个工作树**），
于是窗口里包含**别的进程**的动作 —— 别人的写入被算到了演示脚本头上。

### 2.3 改法：换成因果正确的判据（审计钩子），不是放宽断言

新判据：子进程装 `sys.addaudithook`，只记录**本进程**针对那两个目标文件的
`open`（写模式）/ `os.remove|rename|replace|truncate` 事件；报告经 argv[3] 指定的
JSON 文件回传（不解析 stdout，避免与被测模块自己的输出耦合）。

- **别的进程不在观测范围内** ⇒ 病根被去掉，而不是被容忍；
- 顺带修掉旧判据的一个**盲区**：旧实现有 `before[p] is not None` 过滤，
  于是「文件本来不存在、导入期被创建」这一最危险的形态（**正是 2026-09-20 事故的形态**）
  **看不见**；写模式 `open` 天然覆盖创建；
- 同时断言「导入演示脚本不起子进程」（起子进程能绕开进程内观测）；
- 去掉原来的 `skip`：旧实现要「目标文件已存在」才跑，纯 CI 检出下等于不守。

### 2.4 守卫的守卫（5 条，两个方向都能失败）

| # | 合成输入 | 期望 |
|---|---|---|
| ① | 模块真的**改写**已有文件 | 必须报红 |
| ② | 模块**新建**本来不存在的文件 | 必须报红 |
| ③ | **事故的原始写法**（`NetworkConfigManager(...).update(...)`） | 必须报红 |
| ④ | 模块只读不写 | 必须报绿（否则守卫会被当噪声关掉） |
| ⑤ | **父进程另起写入者**持续改写目标文件 | 必须仍为绿（§2.3 要解决的问题本身） |

③ 是刻意单钉的：前两条用的是 `Path.write_text`，而真实事故走的是
`NetworkConfigManager._save()` 内部的 `open(..., 'w')` —— **判据要钉在真实机制上**。

## 3. 一条过程订正：上一轮那句「地板在 CI 没生效」，证据是什么

推进 §4.4bis 记的是「`NETCFG-FLOOR` 在 CI 上没有生效，我关掉了 PR #1022」。
本会话把证据钉死（上一轮没写清是哪一条红）：

  **Shard 1 通过**、**Shard 6 红**；
- Shard 6 红的是**地板自己的守卫**（`tests/unit/test_network_config_test_floor.py`）3 条，
  断言消息里实测值是**仓库路径**：
  `NetworkConfigManager() 的落盘路径不在地板临时目录
  （实测 /home/runner/.../agent/data/network_config.json）`；
- 同一次运行里**没有** `[NETCFG-FLOOR] 未能重定向...` 告警 ⇒ conftest 导入期那段
  patch 没抛异常，却也没留下效果。

⇒ 结论可以确定的是：**在 CI 的某些 worker 里，导入期写下的模块级常量在用例执行时已经不在**。
**根因仍未确定**：至少有两种候选机制，且本次无法把二者分开（第 ①② 条对修法是等价的）：

    ① 地板那次 `import agent.network_config` 当场失败，被 `except Exception` 吞成一条

       这一点上一轮的推理有漏洞：那个 `_warning` 是在 pytest 的日志捕获配置生效**之前**发出的）；
    ② 地板装上了，但之后模块被重载/重新执行 ⇒ 模块级常量退回默认值。

⇒ **不要再用「导入期改进程级模块属性」做地板**。
   **2026-10-06 已按「环境变量 + 调用期解析」重做，见 §4.10** —— 该修法对 ①② **同时免疫**

### 4.11 一条 CI flake 的根治：**把「等 600ms 防抖」改成假定时器推进**（2026-10-06）

**现象与定性**（本会话实测）：`src/pages/prompt-lab/promptLabRequirements.test.tsx` 里那条
「技能指令停用 → 提示词区域不再显示 `{skill_instructions}`」的用例：

- 在 PR #1020 的**纯文档提交**上也红过（那次唯一改动是一个 .md）⇒ **与被测代码无关**；
- 本机同一文件连跑 13 次里红过 1 次（首次运行、Vite 缓存还冷）。

被测链路本身是对的：`onToggle` → 600ms 防抖（`identityPrompt.ts::PREVIEW_DEBOUNCE_MS`）
→ 重建模板 → `setTemplate`。原来的写法是「`fireEvent.click` + `waitFor(..., { timeout: 4000 })`」，
于是这条断言实际在说**「这台机器能在 4 秒内跑完 600ms 防抖」** —— 与续作 §7.5 里
「为什么不用『耗时 < N 秒』」是同一条纪律的反面（时间预算随 runner 漂移，会假红假绿）。

**改法：时间由测试自己推进**（假定时器），真实时钟不参与：

    vi.useFakeTimers()
    try {
      fireEvent.click(toggle)
      await act(async () => { await vi.advanceTimersByTimeAsync(2000) })   // ≥ 600ms 防抖，余量而已
    } finally {
      vi.useRealTimers()
    }
    expect(promptArea()?.textContent ?? '').not.toContain('{skill_instructions}')

**实测读数**：

| 判据 | 结果 |
|---|---|
| 改后连跑 10 次 | **10/10 通过**（改前 13 次里红过 1 次） |
| 全套（92 文件 / 810 用例） | 全绿 |
| **可证伪**：把 `onToggle` 里的 `schedulePreview(next)` 注掉（制造「防抖后不重建」的缺陷） | 该用例**立刻红**，且**只用 349ms**（不再烧 4 秒超时）——失败形态从「超时」变回「断言失败」，这正是本仓要求的区分 |

> 附带收益：这条用例的失败信息现在会**直接指出**「模板没被重建」，而不是让人去猜
> 「是机器慢还是真的坏了」。

**还剩什么没迁（不是漏，是口径）**：本系列迁的是**被前端消费的端点**（`envelope_coverage.py`
的那 108 条）。未被消费的端点、以及消费方尚未迁移的写端点（如 `/api/skills/toggle`、
`/api/skills-mgmt/*`、`/api/context/config` 等）仍返回既有形态 —— 它们不再阻塞任何事：
**没迁移的端点继续用 hubGet/hubPost（拿到原始体），迁移过的用 getEnvelope/postEnvelope（拿到 data）**，
两条路各自显式，不再有任何「猜」。

> **一条实测到的价值**：那条 AST 断言当场抓到了我自己的漏改 —— `api_panorama` 的 docstring
> 改了、`return jsonify(` 没改。行为用例**覆盖不到**它（该载荷要拉十几个 `_Yunshu` 子系统，
> 执行等于把 app_server 导入拉回来），只有结构断言能拦。
> ⇒ 「行为测不到的地方，用 AST 钉结构」在这类守卫里是必要补充，不是洁癖。

**其余消费方也扫过了（结论写下来，免得下一个人重扫）**：`health_check.py` 与
`tests/test_observability_e2e.py` 只断言**状态码 200**、不读响应体；
`_provider_sensors/_provider_status` 调的是 `_Yunshu` 的内部方法而不是视图；
`agent/modules_api.py` 的 `/api/health/dashboard` provider 走纯函数 `get_probe_overview()`；
全仓 `tests/` 与 `yunshu-ui/` 对这四个端点的**顶层键访问实测 0 处**；
`agent/server_routes/routes_panorama.py` 是同名**死副本**（守卫单钉「活体在 `plugins/status.py`」）。
