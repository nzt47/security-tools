## 1. 证据由三层构成

| 层 | 机制 | 存储 | 校验入口 |
|---|---|---|---|
| **① 哈希链** | 每条记录两级 sha256（`payload_hash` + `self_hash`），`prev_hash` 串起前后 | `data/audit/audit_chain.db` 表 `audit_chain`（WAL + `synchronous=FULL`） | `scripts/verify_audit_chain.py`（全链重算） |
| **② Merkle 日根** | 每个 UTC 日的 `self_hash` 建 Merkle 树，根哈希 + 派生元数据写入受保护文件 | `data/audit/daily_roots.jsonl`（默认只读） | `--roots-check all`（重放 + 签名 + 外层根链） |
| **③ ed25519 签名** | 用 `data/audit/audit_signing_key.pem` 对日根签名消息签名，公钥随记录同行 | 同上（`signature` / `signer_public_key`） | 同上（`RootsSigner.verify`） |

---

## 2. **可用**：这套证据能证明什么

1. **链的完整性与连续性（可自证、可复算）**
   `verify_audit_chain.py` 逐条重算两级哈希 + `prev_hash`。2026-09-21 实测：
   **exit 0，20,105 条，seq 1..20,105 连续，`bad_seqs` 为空，链头 `self_hash=3e4ca5f5a356e5c9…`**
   （`_ci_logs/audit_pollution/T04_final.txt`）。
2. **单条记录未被事后篡改**
   任何字段改动都会让该条 `self_hash` 重算不一致（`entry_hash_mismatch`），并沿链前向传播。
3. **每日集合未被删改（在封印口径内）**
   日根把"该 UTC 日、封印点之前的记录集合"钉死；`leaf_count` / `first_seq` / `last_seq` /
   首尾 `self_hash` 同在签名消息内，改任一项必然 FAIL（`seal_metadata_mismatch`）。
4. **日根文件自身未被删改**
   外层根链 `prev_entry_hash → entry_hash` 连续（`_verify_root_chain`），整行删除/改写可检出。
5. **出证方的不可否认性（在密钥可信的前提下）**
   日根签名可用公钥 `b73dd748ad340a2fa87a4646b6846965bc8fb544e7a8951bb9c22b877d98ae6f` 独立验签。

## 3. **边界**：这套证据**不能**证明什么（必须随证据一起交付）

| # | 边界 | 事实与证据 |
|---|---|---|
| B1 | **链上约两成记录不是生产业务行为** | 测试污染：`strict`(S1∪S2) = **4,127 / 20,105 = 20.53%**；采纳口径 `strict_gray`(∪S3∪S4∪S5) = **4,420 = 21.98%**；另有一族 X2「名字像测试、身份像生产」**201 条**；上界 `strict_gray_x2` = **4,621 = 22.98%**。证据：`_ci_logs/audit_pollution/L16_gray_inclusive/` |
| B2 | **2026-09-21 的链**经过**就地前向重算**，不是"从未被改动过"的原始链 | 修复为补 6 处断点 / 15 个 seq 空洞，对 **19,628 行（seq 477..20104）**的 `prev_hash` + `self_hash` 两列做了**前向重算**（`PRODUCTION_receipt.json`：`relink_first_affected=477`、`relink_rows=19628`）。`payload` 等其余列未改，但**哈希列已非当初写入时的值** |
| B3 | **6 个 ed25519 日根是重签的**，不是原始出证 | 用**同一密钥**（公钥 `b73dd748…` 未变、`audit_signing_key.pem` sha256 `CA751F36…` 修复前后一致）对新 `self_hash` 重签。原始日根存档于 `docs/closeout/L1_evidence/daily_roots.ORIGINAL.jsonl`（sha256 `3A776CB9…`，**未被改动**），二者 **6/6 root_hash + signature 全部不同**。见 `ATTESTATION_原始日根说明.md` |
| B4 | **"未被重算的原始链"在本机只存在于独立备份** | `_ci_logs/audit_backup_20260921_035434/audit_chain.db`（sha256 `FDAC9BFA60874E6F065BBC533CB31A58922D9C5FE5FC3706B5BABD11F719E294`）。生产路径上**不存在**原始链的第二份 |
| B5 | **日根的"治理根"取同日首条记录**，`force` 追加的新根不改变判定依据 | `get_daily_root()` 返回首条匹配（`agent/audit/chain.py:2752-2757`），`verify_daily_root()` 用它（`chain.py:2798`）。2026-09-21 实测：追加 09-14 新根后共 7 条根记录、`--roots-check all` 报 7 条（**6 个不同日期**，09-14 出现两次）、7/7 OK，但 `get_daily_root('2026-09-14')` 仍返回**旧的首条**（`entry_hash=ded4a103…`）。**即"追加新根"留痕有效、"变更治理根"当前 API 做不到** |
| B6 | **无第三方时间戳 / 无外部锚定** | 签名是**本机单密钥**自签，没有 TSA、没有区块链/外部日志锚定，也**没有把链头对外公示**。因此"这些记录不晚于某时刻存在"**无法**用本机证据向第三方证明 |
| B7 | **封印区间内可混有异日记录** | 09-14 的封印区间 `915..2782`（1,868 条）里，**1,786 条**的 `ts` 不属于 09-14（`2027-10-19` 1,738 条 + `2025-08-10` 48 条）。成因是 seq 顺序与 ts 顺序不一致（回填/污染），**不是链损坏**；现行口径按"日 ∩ 前缀上界"取叶，故该日判 OK |
| B8 | **链上存在合成时钟记录** | `S6`（`ts` 在真实运行窗口之外）**1,902 条**。因此**不可**直接用链上 `ts` 做业务时序统计 |
| B9 | **判定语义在 2026-09-21 变更过** | 每日根叶子口径由"只按 seq 区间"改为"日 ∩ `seq ≤ last_seq`"（`chain.py:2762-2796`）。**跨该日期的"历史 FAIL/OK"结论不可直接比较** |
