## L1 · 开关登记表与 config.yaml 的口径脱节（**部分已修复**，2026-09-22）

### 现象
`agent/settings/registry.py` 登记的部分键，其 `config_path` 为空 ⇒ `agent/settings/resolver.py`
**不会**去 `config.yaml` 取值，于是「开关中心」的 `source` 永远只显示 `default`／`env`。
若 `config.yaml` 里显式写了某个值（例：`evolution.enabled: false`），UI **仍会显示**代码默认值。

### 证据
- 本轮修掉的 5 个键（`SCHEMA_PRUNE_*` / `FEWSHOT_ENABLED` / `EVOLUTION_*`）`config_path` 均为 `""`；
- `agent/evolution/injector.py` 读的是 config.yaml **顶层** `evolution:` 段，而 `registry` 没有登记该路径；
- 实测 `yaml.safe_load(config.yaml)` 的顶层键里没有 `evolution`（现存的 `learning.evolution` 段**无读取方**）。

### 影响
**只影响"显示与来源标注"**（不改变真实生效值）—— 但它是**谎报类**问题：人会以为
"UI 显示的就是生效值"。本仓库对"面板显示的不是真实生效值"有明确纪律（resolver 的设计初衷）。

### 拟议方案（待细化）
给相关登记项补 `config_path`（指向真实的 config.yaml 路径），并让 `_config_lookup` 的
取值为空的语义与 `default` 的关系在 UI 上一并如实标注（"config 层未提供" vs "config 提供 false"）。

### 风险
改 `config_path` 会让本来"只读 default"的键**开始受 config.yaml 影响** ⇒ 可能改变生效值。
必须逐键核实"该模块到底读不读 config.yaml、读哪个路径"，禁止批量补。

### 验收判据
- 对每个受影响的键：**代码真实读取点**、`registry` 登记、UI 显示三者一致（可用一条从源码
  机械提取读取路径的守护测试钉住，参照本轮 `TestRegisteredDefaultsMatchCodeFacts` 的做法）；
- 生效值不因本次改动而改变（改前/改后逐键对拍）。

## L2 · 跨进程**并发**消费同一张批准的窗口（**已修复**，2026-09-22）

### 现象
`agent/tool_approval.py` 的"单次有效"依靠消费台账（append-only JSONL）。
本轮已修掉**陈旧缓存**造成的绕过（`a6a27f96`：缓存按文件指纹失效）。
但**两个进程在同一窗口各自"查台账 → 追加"**时，仍可能都判"没用过" ⇒ 同一张批准被放行两次。

### 证据
- 本层不提供跨进程锁；`consume()` 的语义是"查已消费集合 → 判断 → 追加"，分两步（非原子）；
- 修复只保证"下一次问能看见**已落盘**的事实"，不保证**并发互斥**；
- 触发场景真实存在：人在 UI/CLI 进程裁决、模型在服务进程消费 —— 两个进程都在动这本台账。

### 影响
治理面：一张**单次有效**的批准可能被执行两次。影响面小于"陈旧缓存"（需要精确的并发窗口），
但它违反的是同一条不可重放承诺。

### 拟议方案（待细化，二选一）
1. **文件锁**：对台账文件加 OS 级互斥（Windows `msvcrt.locking` / POSIX `fcntl.flock`），
   把"查 + 追加"放进临界区；
2. **单点写者**：把台账的唯一写者收敛到审批流进程，消费方走一次带幂等键的请求（改动更大）。

### 风险
- 引入锁 ⇒ 需要考虑**死锁/超时/跨平台**差异（本仓 CI 在 Linux、开发机在 Windows，两边语义必须一致）；
- 锁粒度若按"整本台账"会给高频消费带来串行化；必须实测热路径开销。

### 验收判据
- 一条**可确定复现**的并发用例（两个进程/线程在同一窗口消费同一 approval_id）**恰好放行一次**；
- 单进程顺序消费、跨进程顺序消费、以及"台账不存在/不可读"三种既有语义保持不变；
- 锁的失败路径（拿不到锁 / 超时）**不得**静默放行 —— 与审批边界的 fail-closed 口径一致。

## L2 · 实现结果（2026-09-22 回填）

采用**方案 1（文件锁）**，并复用仓内**唯一**锁实现 `agent/utils/cross_process_lock.py`
（Windows `msvcrt` 字节区间锁 / POSIX `flock` 的平台分支在锁模块内部；另有一条「不许抄第二套锁」
的守护用例）。要点：

- **临界区**：`consume()` 的「查台账 → 判重 → 追加」整段进入以 `<台账>.lock` 为名的 OS 文件锁；
  判重在临界区内**直接读台账真值**（不信任 `(mtime_ns, size)` 指纹缓存——它不覆盖"等长重写 + 同 tick"）。
- **fail-closed**：拿不到锁 / 等锁超时 / 临界区异常 ⇒ `consume` 返回 `False` 并给出可读原因，
  **绝不**静默降级成"当作没消费过"；闸门那侧据此**重新挂单**（不放行）。
- **有限等待**：等锁上限 `CP_TOOL_APPROVAL_LOCK_TIMEOUT_SEC`（默认 5s，`0` 合法＝不等），
  已登记进 `agent/settings/registry.py`（A 级 / 热生效）。
- **热路径不进临界区**：`find_permission`（每次工具调用都问一次）只读、不取锁、不建锁文件。
- 锁文件**独立于台账本体且永不删除**（删除＝inode 替换竞态）；已被 `.gitignore` 的 `data/*.lock` 覆盖。

验收判据的满足情况：
- **确定性复现**：两个 `spawn` 子进程在「查完台账、尚未追加」处用 `arrived`/`go` 精确对齐窗口
  （对齐失败由 `peer_on_lock` 归因，拒绝假绿）⇒ 还原成 HEAD 版本时 `4 failed`，其中
  `AssertionError: 同一张批准被放行 2 次（必须恰好 1 次）`；修复后同一条命令 `7 passed`。
- 既有语义原样通过：单进程顺序消费、跨进程顺序消费、台账缺失/不可读按未消费、`reset_cache()` 后不可重放；
  连同 e2e / confirm_level / tool_gate / tool_exemptions 一起 `249 passed`。
- 生产数据核对：`data/approval_records.jsonl` 25119B 前后一致；`data/tool_approval_uses.jsonl` 仍未被测试创建。

## L2 · 如实标注的**不覆盖**面（未修复，交付时点口径）

1. **NFS / SMB 等网络盘**上的锁语义可能退化成"各自有效"⇒ 台账放共享盘时互斥**不保证**；
2. **锁文件被外部删除/替换**：本层永不删除，但外部删除会让锁落到新 inode，该窗口互斥退化；
3. `find_permission` 与 `consume` 之间的 **TOCTOU**：本层保证"**恰好一次消费**"，
   不是"判定与消费原子"；调用方的纪律必须是 **consume 成功之后才执行**；
4. **外部直接改写台账**（人工手改 / 外部工具重排 / 等长重写）绕过本层；
5. **超时后不自动重试、不降级**（要不要重试是调用方的决定，且必须重新走一次判定）；
6. **POSIX 仅静态审查**：本层零平台分支，Linux 侧语义由锁模块的 `fcntl.flock` 分支承担（本机为 Windows，未在 Linux 实跑）。

## L3 · `record_id` 时间段在同一时钟刻度内**不单调** ⇒ "最新裁决"可能判反（**已修复**，2026-09-22）

### 现象
`agent/tool_approval.py::_decision_key` 在"审批记录时间戳只到秒"的并列上用 `record_id` 的
**字典序**兜底裁决先后；其成立前提是"`strftime('%f')` 的微秒段真能区分先后"——
**在 Windows 上不成立**（`datetime.now()` 的时钟粒度约 15.6ms）。

### 证据（确定性，不靠概率）
- 两次失败样本的 20 位时间段**逐字相同**：
  `appr-20260922231458496757-7f1b2d6c` / `appr-20260922231458496757-1d7acd21`（日志相隔 17ms）；
- 把 `agent/tool_approval.py` **与** `tests/unit/test_tool_approval.py` 都逐字节还原成 HEAD（零改动）后
  整文件连跑 25 轮 → **2 次失败**（`test_驳回_*` 两条，≈8%）；带本修复跑 20 轮 → 1 次（同族）；
  单独跑该用例 40 次 → 0 次（与执行序/上下文有关）。
- 新增**冻结时钟**用例后，在逐字节 HEAD 上**确定性失败**（连"相隔 1 微秒"都不成立）。

### 影响
安全性方向：同一秒内"先批准、后驳回"时，**老批准可能压过新驳回**（被否决的调用照旧放行）；
反方向则让"人工重新批准"被老驳回吞掉（审批人的操作被静默忽略）。CI 侧表现为 `test_驳回_*` 偶发红。

### 实现
`agent/skills_mgmt/approval.py`：`_generate_id` 的时间段在**同一进程内严格单调**
（撞上同刻度 / 时钟回拨 ⇒ 抬到上一个 +1µs；`_ID_TS_LOCK` 保证并发生成不撕裂）。
**格式一字未变**（定宽 20 位 + 8 位 hex）⇒ 既有解析 / 掩码 / 日志链路不受影响；
时间段最多比真实时钟超前几微秒（它只用于排序，真实时刻另有 `created_at`）。

### 验收判据（已满足）
- `test_record_id时间段_同一时钟刻度内仍严格单调`：同一刻度内连发 3 个 id，时间段必须递增且不重复；
- `test_同一秒内的两次相反裁决_新裁决必胜`：时钟冻结 ⇒ 两条记录 `updated_at` 逐字相同，
  仍必须"新驳回压过老批准"，且先钉住 id 先后可判；
- 两条新用例在**逐字节 HEAD** 上确定性红（实测 `2 failed`，断言即 `先后不可判`），修复后恒绿；
- 既有语义不变：`test_驳回_*` / `test_最新裁决以决定时刻为准_后决定的旧单胜出` 等原样通过。

### 仍不覆盖
**跨进程**同一刻度内生成的两个 id，先后仍由随机 hex 段决定。要为此引入全局序号必须改 id 格式
（会让既有按 id 解析的链路失效），而"人对同一事项的两次相反裁决落进同一 15.6ms 刻度"并不现实 ⇒
本层不承担该语义，**如实标注而不宣称彻底解决**。
