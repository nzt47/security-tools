# 会话任务区「子代理 / 后台任务」下拉：从"永远为空"到"说清为什么空"

**日期**: 2026-10-02
**触发**: 线上提问 ——"UI 上的「子代理」和「后台任务」下拉有没有接通后台？怎么有业务发生时没见过它们显示过？"

---

## 1. 先回答"有没有接通"

接通了。三条独立证据：

1. **代码接线**：`WorkbenchChatPage.tsx:438/440` 常驻渲染两个组件 → `hubGet('/api/subagent/list')`、
   `hubGet('/api/background/tasks?limit=50')`（相对路径 → vite `/api` 代理 → `127.0.0.1:5678`）；
   后端 `routes_subagent.py:92` / `routes_background.py:60` 均在 `app_server.py` 显式注册。
2. **实测**：带令牌 GET 两条端点均 **HTTP 200**，只是返回空集
   （`{"tasks":[],"total":0}` / `{"subagents":[],"count":0,"channel":{"llm":true,"ok":true}}`）。
3. **浏览器确实在打**：`logs/watchdog_spawn_20261001_125244.err.log` 里当日有 92 条
   `BackgroundTasks.background.tasks` 的 START/END trace（`trace_route` 在视图函数上，
   401 会在 before_request 被挡下、根本走不到这里 ⇒ 也反证了令牌是带上的）。

**所以问题不是"没接线"，而是"没有东西可显示"。**

---

## 2. 根因（为什么"有业务发生也看不到"）

### 2.1 「子代理」列的是**存活容器**，而委派是"用完即弃"

- `/api/subagent/list` → `SubagentManager.list()` → `SubagentLifecycleManager.list()`，
  读的是**内存里还活着的分身容器**（`lifecycle.py:245`）。
- 而所有委派都传 `destroy_after=True`（`tools/subagent_tools.py:300`），
  生命周期管理器在 `finally` 里销毁（`lifecycle.py:363`）⇒ 委派一结束，容器就没了。
- UI 的「委托执行」还要求**先存在**一个分身（`routes_subagent.py:264` `mgr.get(name)` 否则 404）。
- ⇒ 正常业务里这个列表**几乎恒为空**；唯一能看到条目的方式是去「装配车间 → 分身创建与组装」
  手工创建分身（且 TTL 到期也会消失）。

### 2.2 「后台任务」读的是**内存注册表**，且只有三条路径会写

- `AsyncExecutor` 是进程内单例：完成的任务超过 `result_ttl`（缺省 3600s）被清理，进程重启即清空。
- 生产者只有 `submit_task`、`process_distill_run(async_=true)`、MCP 调度器（`plugins/mcp_scheduler.py`）
  三类；**普通对话轮次不产生任何后台任务**。
- 另有 `data/async_tasks.jsonl` 追加写，但**代码从不回读** ⇒ "跑过"这件事在界面上会彻底消失。

### 2.3 两处附带缺陷（用户感知为"功能坏了"）

- **陈旧选择**：`localStorage` 里的分身名随容器回收而失效，但 `delegate` 仍为真值
  ⇒ 按钮可用 → POST → **404「分身不存在」**，且提示与真实原因无关。
- **空态无解释**：无活跃分身时按钮禁用、空列表点击静默 `return`，用户既点不动也看不到原因。

## 3. 改法

### 3.1 后端

| 文件 | 变更 |
| --- | --- |
| `agent/jsonl_history.py`（新增） | JSONL 尾部窗口读 / 计数 / 追加。两条消费方共用一份实现（本仓"同一口径写两遍"是老毛病） |
| `agent/subagent/delegation_history.py`（新增） | **委派记录**：每次委派一条轻量 JSONL（`<仓库根>/data/subagent_delegations.jsonl`），**不含交付物正文** |
| `agent/subagent/container.py` | `run_delegation` 增 `source` 形参；在**咽喉处**落记录（单发路径） |
| `agent/subagent/lifecycle.py` | `delegate`/`delegate_many` 透传 `source`；`_record_batch` 为批量落记录（批量走 `execute_many`，**不经过容器**） |
| `agent/server_routes/routes_subagent.py` | 新增 `GET /api/subagent/history?limit=`（最新在前，limit 收敛 [1,100]）；新增 **`POST /api/subagent/delegate`（临时分身委派：不要求先存在分身）**；八要素缺省补齐与结果回显抽成模块级 helper（两条委派入口共用一份，避免漂移） |
| `agent/server_routes/routes_background.py` | `GET /api/background/tasks` 响应增 `history:{total, records, path}`（读**执行器自己的** `_tasks_file`） |

`source` 取值：`ui`（界面）/ `tool`（模型工具）/ `fan_out`（批量）/ `lifecycle`（未标注），
界面按此显示中文来源。

### 3.2 临时分身委派（本轮追加：把"死路"打通）

**问题**：具名端点 `/api/subagent/<name>/delegate` 要求 `mgr.get(name)` 命中一个**存活容器**，
而容器 `destroy_after=True` 跑完即回收 ⇒ 界面上"列表为空 ⇒ 无法委托"，用户唯一出路是先去装配车间
手工造分身。这正是"面板看着是死的"的最后一块。

**做法**：新增 `POST /api/subagent/delegate`（URL 上不带 `name`），直接走
`SubagentLifecycleManager.delegate(config, ctx, destroy_after=True, source="ui")` ——
与模型侧 `delegate` 工具、`fan_out` **完全同一条执行链路**（八要素 / 隔离 / Trace / 成本 / 回收三件套），
只是把"容器从哪来"从"用户先建"换成"现建现回收"。

- **回收纪律硬编码 `destroy_after=True`**：临时分身不是资源，用完必须走（否则撞 `max_subagents`，
  且"临时"二字就成谎话）。
- **规则同一份**：八要素缺省补齐（`_build_context`）、目标过短/无通道的拒绝（`_short_goal_response` /
  `_no_channel_response`）、工具白名单（`_granted_tools`）、八要素回显（`_elements_view`）全部抽成
  模块级 helper，两条入口共用 —— 缺省规则写两份必然漂移。
- **命名与 TTL 不重复实现**：容器名用固定前缀 `ui-delegate`，重名消歧与 TTL（取契约⑦）仍由
  `lifecycle._prepare_config` 统一负责。
- **静态路由不被动态吃掉**：`/api/subagent/delegate` 与 `/api/subagent/<name>/delegate` 是两条规则，
  有用例断言二者各自可达（并进真实入口 url_map 守门）。
- **具名端点 404 给出路**：返回体新增 `hint` 指向临时分身入口，404 不再是死路。

**前端**：没有活跃分身时提交到 `/api/subagent/delegate`，按钮文案区分「委托执行（用所选分身）」
与「委托执行（临时分身）」；委托完成后**立即刷新委派记录**，让"刚刚这一下"马上出现在历史里。
### 3.3 前端

- **SubagentMenu**：新增「📜 委派记录」区（成功/失败、来源、耗时、tier、产物数、目标、错误，
  支持「复用目标」回填输入框）；**陈旧选择**显式提示 + 「清除选择」，且委托目标只取**活跃**分身
  （陈旧名字不再被发出去）；无活跃分身时按钮转琥珀色并在标签上直说
  「委托执行（当前没有活跃分身）」，点击给出**指名下一步**的原因；空态补一句
  "委派跑完即回收，常年为空属正常，发生过什么见委派记录"。
- **BackgroundTasksMenu**：空态展示历史提交摘要（总数 + 最近 5 条：时间 / 名称 / 状态）；
  头部统计追加 `· 历史 N`。`total=null`（文件过大未统计）显示为"条数未统计"而不是 0。

## 4. 不变量与取舍

1. **fail-soft 三处**：JSONL 追加、尾部读取、计数失败一律降级（空结果/False）并告警，
   绝不让"记历史/读历史"打挂委派与列表（历史永远是附带信息）。
2. **只记元信息**：不落 `output_text`（外来文本 §5.7 机制 1 + 体量不可控），正文的权威位置仍是 trace/产物。
3. **`total=null ≠ 0`**：超大文件宁可"未统计"，也不给一个截断后看着精确的数字。
4. **静态路由优先**：`/api/subagent/history` 必须命中历史处理器，不能被 `/api/subagent/<name>` 抢走
   （否则表现为 404「分身不存在: history」）—— 有用例钉死。
5. **测试不得写仓库 data**：见 §5 的污染回归。

## 7. 一句话总结

两个下拉**一直是接通的**，问题是它们读的集合在现实业务里恒为空、且空得没有解释。
本次把「子代理」补上**委派记录**（发生过什么）、把「后台任务」补上**历史摘要**（跑没跑过），
并让"为什么现在没有东西"这件事在界面上直说；再补上**临时分身委派**，
把"一个分身都没有时界面无从下手"这条死路打通 —— 同时把两条新数据源的 fail-soft 契约、
"测试不得写仓库 data"、"两条委派路由互不遮蔽"都钉进用例。
