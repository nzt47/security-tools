# 上下文三旋钮：默认值、值域与"真正生效"的口径对齐

**日期**: 2026-10-02
**触发**: 线上提问 ——「上下文最大 Token / 单次发送 / 单次回复的默认值是不是太小？没几下就用完」

---

## 1. 先回答"是不是太小"：是，而且比"小"更严重

**实测 provider（不是我猜的）**：`GET https://api.deepseek.com/v1/models` 直答 ——

```
id: deepseek-flash   (DeepSeek-V4.1-Flash)
  context_window:    1048576      ← 1M
  max_output_tokens:  393216      ← 384K
  effort: low/high/max（默认 high）
```

并实测 `max_tokens: 200000` 的请求被**接受**（HTTP 200）⇒ 模型侧几乎不构成限制。

而云枢这边（修复前）：

| 旋钮 | 代码默认 | 真机实际 | 模型能力 | 修复前是否生效 |
| --- | --- | --- | --- | --- |
| 上下文最大 Token | `4096`（`config.py:89`） | 面板分母 `19968`／真正组装窗口 `32768`（`config.yaml`） | 1048576 | ✅ 生效，但**三份数值互相打架** |
| 单次发送 | `2048` | `3456` | — | ❌ **全仓零强制点** |
| 单次回复 | `4096` | `3968` | 393216 | ❌ **全仓零强制点**；真正上限是 `orchestrator.py` 按模型名硬编码的 **8192** |

「没几下就用完」的体感来自三件事叠加：

1. **读数吓人**：`plugins/memory.py` 把「累计压缩次数 ≥ 5」直接判 `critical` ⇒ 占用 22% 也常年报红
   （真机 `compress_rounds=23`，它是摘要版本号、**累计值**，与当前占用无关）；
2. **真窗口只有模型的 1/32**（32768 vs 1048576），而校验器 `le=32768` 让想调大也调不动；
3. **回复被硬编码卡在 8192**（模型的 1/48），旋钮调了没用。

## 2. 改法（按 Owner 选定档位）

| 项 | 决定 | 落点 |
| --- | --- | --- |
| 组装窗口 | **32768 → 131072**（模型的 1/8，成本折中） | `config.yaml:memory.token_limit` + `config.py` 默认值与 `le` 上限 512..1048576 |
| 单次回复 | **16384**，且**真正接上 max_tokens**；可调上限放宽到 131072 | `orchestrator._resolve_max_output_tokens` |
| 单次发送 | **只告警、不截断** | `plugins/chat.py` 响应 `context.send_limit` + WARNING 日志 |
| 面板读数 | 分母 = 真实编排窗口并披露来源；档位按占用判；摘要退化单列 | `plugins/memory.py` `/api/context/status` |

### 2.1 `_resolve_max_output_tokens`（回复上限为什么这样定）

```
want = 配置值(per_message_recv_limit) 若 > 0，否则按模型名分档(8192 / 16384)
final = max(档位下限, min(want, CP_CHAT_MAX_OUTPUT_CEILING(缺省 131072)))
```

- **配置优先** ⇒ 界面旋钮真的决定 `max_tokens`；
- **启发式只当下限** ⇒ 未配置时与改动前**逐字一致**，且配置缺失永远不会让回复比以前更短（单调不减）；
- **硬上限收敛** ⇒ 一个手滑的大数字不会把 provider 打回 400；`ceiling < floor` 时以 floor 为准（不许把回复顶成 0）。

### 2.2 窗口滑块为什么必须"推给运行中的编排器"

`_memory_token_limit` 是**启动时**从 config.yaml 写死的，而 `POST /api/context/config` 此前只改 `_cfg`
这个运行时副本 ⇒ 面板数字变了、真正"超限丢弃最旧消息"的边界一动不动（同一个旋钮两套账）。
现在 `_push_runtime_window()` 同时推两处：`_Yunshu._memory_token_limit`（组装窗口）与
`_Yunshu._memory._token_limit`（压缩触发阈值），并在响应里回报 `runtime_applied`。

### 2.4 顺带挖出的"第四、第五层口径"：调大窗口会被**静默改回 4096**

第一次重启后线上读数仍是 `4096`，而来源却写着 `config.yaml:memory.token_limit` —— 追下去发现
`config.py` 里其实有**两套校验**，各自带一份硬编码的默认值与值域：

| 层 | 位置 | 修复前 |
| --- | --- | --- |
| ① pydantic 字段 | `MemoryConfig.token_limit` | `default=4096, ge=512, le=32768` |
| ② 聚合默认 | `Config.DEFAULT["memory"]` | `4096 / 2048 / 4096` |
| ③ 字典校验器 | `validate_config()`（config.py:460-468） | `512..32768`，否则记 error |
| ④ 修正器 | `validate_and_fix_config()`（config.py:552-554） | 非法即 **`= 4096`** |

实测后果：把 `config.yaml` 写成 `131072`，③ 判非法、④ **静默改回 4096**，
于是一次"把窗口调大"的改动在两层里各失败一次，而现场只有一条 WARNING，面板照旧显示 4096。

**修法**：把六个数（三档默认值 + 三个上限）收口成 `config.py` 顶部的模块常量
（`MEMORY_TOKEN_LIMIT_DEFAULT/MIN/MAX`、`PER_MESSAGE_SEND_LIMIT_*`、`PER_MESSAGE_RECV_LIMIT_*`），
①②③④ 全部引用同一份常量；④ 的修正目标改为**默认常量**而不是写死的 4096。
并用测试锁死"四处定义同口径"与"131072 必须穿过全部校验层"，另加一条**回归锚**：
`32769` 曾因旧上限被判非法，现在必须原样通过。

### 2.3 面板读数口径

- 分母取 `context_limit_info()`（与 `/api/chat` 的 `context.token_limit` **同一个单一事实源**），
  并披露 `token_limit_source`；取不到时如实报 `None`（**不拿 4096 之类冒充分母**）；
- `status_level` 只跟**占用**走；「摘要退化」用独立的 `compress_degraded` / `status_reasons` 表达；
- 删掉死代码 `pct_warn = pct >= 80 or pct >= 60`；
- UI（工作台 + legacy 页）值域、文案、来源一并更新，"单次发送"提示改为**超限只告警不截断**。

## 4. 线上实测（后端重启后现场采集，pid 22436 → 23320）

```
GET /api/context/status
  token_limit        = 131072          ← 修复前 4096（被字典校验器改回过一次）
  token_limit_source = config.yaml:memory.token_limit
  configured_limit   = 131072
  percentage         = 0.6   (semantics=current_window_usage)
  status_level       = ok              ← 修复前同样占用下报 critical
  status_reasons     = [summary_degraded]   ← 红色成因被单列，不再冒充"占用高"
  compress_rounds    = 23   compress_degraded = True
  send/recv limit    = 8192 / 16384   send_semantics=warn_only

POST /api/context/config  {"token_limit": 262144}
  changed=[token_limit]  runtime_applied=True   ← 当场推给运行中的编排器
  改后 status: token_limit=262144  source=runtime_override(api)  pct 重算

POST /api/context/config  {"token_limit": 131072}      ← 复位到 config.yaml 的值
POST /api/context/config  {"per_message_recv_limit": 999999, "per_message_send_limit": 999999}
```

**验证到的三件事**：① 窗口值真的从 config.yaml 生效（131072）；
② 面板分母 = 真实组装窗口 + 来源可查；③ 滑块改窗口**当场生效**（`runtime_applied=True`，
来源切到 `runtime_override(api)`），不再只改一个没人读的副本。

## 5. 追加发现（同日晚）：**主 UI（工作台流式）根本不吃这两个旋钮**

在按 §2 改完并上线之后，我顺手核对"用户天天在用的那条路"到底走哪个端点 —— 结果是：

- 工作台 = `POST /api/chat/stream`（SSE，`yunshu-ui/src/lib/sse.ts`）；
- `/api/chat`（我们刚改的那条）只被**旧的 hub 会话页**用。

而 `plugins/chat.py::_workbench_real_stream` 里：

| 项 | 修复前 | 后果 |
| --- | --- | --- |
| 单次回复上限 | `max_tokens=2048` **写死**在请求体里 | 面板调到 16384 对主 UI 零作用；回复被卡在模型的 **1/192** |
| 上下文 | `hist[-8:]` —— **写死最近 8 条** | 窗口从 32768 调到 131072 对主 UI 零作用；反过来 8 条里的长工具输出没人管 |
| 预算可见性 | 完全没有 | 用户只能猜"为什么它忘了我刚说的话" |

⇒ 也就是说：**§2 的那些数字修正，对用户日常那条路一度是无效的**。
同一份对话换个入口换一套口径，正是本仓反复出现的病。

### 5.1 修法

1. **单一口径模块 `agent/chat_limits.py`**（新增）：`resolve_max_output_tokens()`（配置优先 / 模型档位下限 / 硬上限收敛）与 `resolve_context_budget()`（窗口 − 系统提示 − 工具 schema − 回复上限 − 余量）。编排层原来的 `_resolve_max_output_tokens` 改为**委托**它（保持既有属性与方法名不变），工作台直接调它。
2. **工作台取本会话全部历史**（软上限 400 条防内存失控），再按 token 预算从后往前裁 —— `_select_within_budget()`，至少保留 2 条（否则"接上上一句话"都做不到）。
3. **`max_tokens` 改为解析值**（优先问编排器，取不到按同一规则自算）。
4. **装配可见**：新增 `thinking` 事件 `id=context-budget`，把"窗口 / 系统提示 / 工具 / 回复上限 / 历史预算 / 带入条数"直接推给界面；单条超「单次发送」阈值时推 `id=send-limit` 告警事件（**只告警不截断**）。
5. **不触发重量级导入**：新增 `_app_server_or_none()` 用 `sys.modules.get("app_server")` 取**已加载**的模块，而不是 `import app_server` —— 后者会执行整套装配（注册全部工具），生产里免费、测试里是副作用。

### 5.2 线上实测（重启后 pid 12344）

```
POST /api/chat/stream  {"message": "只回复两个字：收到"}
  [thinking] context-budget | 上下文装配 |
    窗口 131072 · 系统提示 67 tok · 工具 6757 tok · 回复上限 16384
    ⇒ 历史预算 107352；带入 5 条（丢弃 0 条，753 tok）
  → chunk=18, done=1（正文正常流出）
```

对照：回复上限 **2048 → 16384**（模型的 1/192 → 1/24），上下文由"固定 8 条"变为"按 107k token 预算"，
且这两个数字**现在与面板上的旋钮同源**。

### 5.3 新增用例（`tests/unit/test_workbench_sse_thinking.py`，+7 条）

`max_tokens` 来自配置而非 2048 / 未配置时按档位兜底 / 历史不再固定 8 条 / 窗口小时按预算裁到最少 2 条 /
`context-budget` 事件可见 / 超阈值只告警且**原文完整**送出 / 未超阈值不发告警。

## 6. 遗留

1. **工具结果未从压缩触发口径里单独计量** —— "一次大工具输出 = 一次压缩"的行为不变（原立项保留）；
2. provider 还支持 `effort: low/high/max`（默认 high），云枢未使用；需要"更快/更省"时可作为独立开关立项；
3. 面板与 `/api/chat` 仍各自算一个百分比（前者=当前窗口占用，后者=会话累计占比），两者**语义不同**，
   已在两处都写进 `percentage_semantics` 字段；若将来要合并口径，需先决定"累计占比"是否还有用。
