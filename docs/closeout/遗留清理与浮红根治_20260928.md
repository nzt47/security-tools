## 1. 浮红根治：`sleep` 打桩的**作用域**

### 1.1 现象与根因（实测，两步）

`tests/unit/test_retry_budget.py::TestEndToEndRetryAmplification::test_http_calls_are_truncated_by_budget`
的断言 `all(0.8 <= s <= 1.2 for s in slept)` 在 CI 上偶发红（L6 记载的原文：「slept 序列里出现越界值」），
而本机同文件同款命令全绿。**根因不是被测代码**：

1. **打的是进程全局的 `time.sleep`**：`monkeypatch.setattr(tc.time, "sleep", ...)` 里 `tc.time` 就是 `time`
   模块本身 —— 实测 `import agent.tool_calling as tc; tc.time is time` → **True**。于是同进程里**任何**
   其它代码的 sleep 都会落进记录器。
2. **同进程里确实有别人的 sleep，而且会活到后面的用例**：生产代码里有 **60 处** `time.sleep`，其中多处在
   **daemon 轮询循环**里（`agent/log_system/optimized_storage.py:130` 的 0.05s、`agent/audit/chain.py:2483`
   的 0.005s、`agent/monitoring/*` 等）；而 CI 的 6 个 shard 用 `-n 2 --dist=loadscope`，**同一个 worker 顺序**
   跑很多文件 ⇒ 先前用例启动却没 `stop()` 的线程会一直活到后面。

**确定性复现（都跑出来了，不是推的）**：

```
① 无关线程注入：打桩后让一个与 tool_calling 无关的线程 time.sleep(5.0)
   记录器 = [5.0, 1.03]   ⇒ all(0.8 <= s <= 1.2) = False      ← 判据被判红
② 真实生产线程：BatchLogWriter(...).start()（daemon，0.05s 轮询，故意不 stop）
   再跑 _run(budget_max_retries=1)  ⇒ 记录器里混进 0.05 ⇒ 同一条断言假红
```

### 1.2 修法（只动"测量"，不动"判据"）

`tests/unit/conftest.py` 新增两个夹具（`scoped_sleep` / `scoped_async_sleep`）：打桩 `time.sleep` /
`asyncio.sleep`，但**只把被监视源文件发出的调用记进 `recorded`**（被测层照旧不真等）；其它来源记进
`foreign` 并**透传给真 sleep**（不改变无关代码的行为）。判定用**调用点的 `f_code.co_filename` 后缀**匹配，
兼容相对导入路径。

改造的三处（**都是"记录器作用域"问题，不是断言问题**）：

| 文件 | 旧写法 | 为什么它也会浮红 |
|---|---|---|
| `test_retry_budget.py::_run` | `setattr(tc.time, "sleep", ...)` | 上面那条 ±10% 断言 |
| `test_retry_budget.py::test_mcp_retry_delay_is_jittered` | `setattr(mc.asyncio, "sleep", ...)` | **计数**断言 `len(slept) == 2`；`asyncio.sleep` 同样是模块全局属性 |
| `test_wait_index_retry.py::test_immediately_clean_no_sleep` | `patch.object(wtr.time, "sleep")` + `assert_not_called()` | 对**全局** mock 断言"一次都没调用" ⇒ 别人 sleep 一次就假红 |

### 1.3 验证

- 改造后：`test_retry_budget.py` + `test_wait_index_retry.py` 合计 **28 passed / 0 failed**；
- 新增**回归锁** `test_retry_budget.py::TestEndToEndRetryAmplification::test_泄漏线程的sleep不混进判据`：
  启动**真实生产组件** `BatchLogWriter`（故意不 `stop()`）后再跑一次 `_run`，
  要求 `foreign` **非空**（前置非空转）且 `recorded` 全部落在 ±10% 带内；
- **单变量反证**：把 `watched()` 从"只认 `agent/tool_calling.py`"换成"恒 True"（= 旧机制的等价物）、
  其余一字不改 ⇒ 同一条断言**确定性变红**。

### 1.4 如实标注的边界

- 只认"直接调用 `time.sleep` / `asyncio.sleep`"的形态；用 `from time import sleep` 的模块**本来**就不受任何
  monkeypatch 影响，改前改后在这一点上完全一致；
- 本夹具解决的是**测量被污染**，**不是**"泄漏线程"本身。泄漏侧（哪个用例启动了线程却没 `stop()`）仍是
  `NEXT_SESSION_BACKLOG.md` P2-4 登记未修的条目，见 §6。

## 2. `test_skill_h3_migration.py` 的 3 条常红（两种红、两个根因）

### 2.1 现场

```
python -m pytest tests/unit/test_skill_h3_migration.py -q -p no:randomly
→ 22 passed, 3 failed
FAILED TestNoNewDualDescriptionConflict::test_main_track_only_set_is_exactly_two[real]
FAILED TestActuallyRecallable::test_runtime_only_set_shrinks_to_the_two[fixture]   ← 注意是 fixture！
FAILED TestActuallyRecallable::test_runtime_only_set_shrinks_to_the_two[real]
```

### 2.2 根因 A（**真 bug**）：`[fixture]` 这一半并不密闭

该文件的 `[fixture]` 参数号称"CI 冷启动也真跑"（把冻结快照写进 `tmp_path`、把生产读路径 monkeypatch 过去）。
但它只隔离了 **`callability.SKILLS_MGMT_PATH`**；而它调用的 `_skill_sources(include_runtime_catalog=True)`
读的是**两份**运行期文件（`callability.py:1027/1037`）：② `SKILLS_JSON_PATH`（`data/skills.json`）与
③ `SKILLS_MGMT_PATH`（`data/skills_mgmt.json`）。②**没有被隔离**，仍指向仓库里那份 gitignore 的真实
运行期目录 ⇒ 本机实测该目录含 **8 条**无仓库实体的技能，于是"runtime_only 恰好 2 条"在**本机恒红**、
而在 CI 冷启动（两份文件都不存在）上是**绿** —— 同一个用例两副面孔。

**单变量反证**：只把新增的那一行 `monkeypatch.setattr(callability, "SKILLS_JSON_PATH", ...)` 停掉 →
`test_runtime_only_set_shrinks_to_the_two[fixture]` **立刻复现失败**（1 failed / 25 passed / 2 skipped）；
加回来即绿。

### 2.3 根因 B（**运行期数据正当漂移**，不是缺陷）：`[real]` 在断言一份**历史快照**

`[real]` 读仓库里那份运行期台账，而这两条断言的是"**主轨独有恰好 2 条**"——那是 **2026-09-27 迁移时刻**
那份台账的具体内容。实测该台账已漂移：

```
data/skills_mgmt.json  243008 B（迁移时刻登记的 sha256 = bcda9ecf…，现已不是）
新增 6 条：adaptation / agent / boundaries / skill-card / templates / voice
  created_at = 2026-09-28T19:49:51~52（同一批 0.6 秒内）  source = external_agent
  owner = unknown   tags = ["external","imported","markdown"]   category = custom
data/skills.json（运行时技能目录）同样含这 8 条，mtime 19:49:52
```

⇒ 这是**经生产导入通道写入的运行期技能**（不是测试污染：`data/learned_workflows.json` 为空、标签与来源字段
都是导入通道的形态），**H-3 的"恰好 2 条"作为"对实时台账"的断言已经过期**。继续判它，就是把"运行期有人
导入了技能"判成红 —— 正是 `D3.md:91` 说的**造一个恒红的门**。

### 2.4 修法：把判据拆成「契约本体」与「快照精确性」两半（断言一条没删）

- **契约本体**（`fixture` / `real` **都判**，与漂移无关）：H-3 裁定"不纳入"的那 2 条
  （`global-core-principles` / `skill`）**必须仍在"主轨独有"集合里**。谁给它们补了 `skill.md`（偷偷纳入）
  ⇒ 立刻红；
- **快照精确性**（**只有 `fixture` 判**）："恰好等于那 2 条"仍是**精确相等**断言，只是钉在冻结快照上；
- **`real` 在漂移时显式 `pytest.skip`** 并**贴出实测集合与哈希口径**（不是静默通过），理由与本文件既有约定
  （`CI3.md` §3.4：真实台账内容类断言显式 skip，同不变量由 `[fixture]` 版在 CI 上照跑）一致；
- 新增 `TestContractHalvesAreNotVacuous` **3 条非空转自证**：手工构造"偷偷纳入"/"夹具多出一条"两个输入
  直接调被测函数，证明 ① 契约本体真会红 ② `fixture` 口径仍判精确相等 ③ `real` 漂移走的是
  `pytest.skip.Exception` 而不是静默通过。

### 2.5 验证

```
修前：collected 25 → 22 passed / 3 failed
修后：collected 28 → 26 passed / 0 failed / 2 skipped（2 条 skip = 上面那个显式漂移说明）
```

## 3. P2-2：`generate_persistent` 的落盘路径未净化（任意路径写文件）

### 3.1 现象

`agent/tools/tool_generator.py::generate_persistent` 把 `category` / `name` **直接拼接**进落盘路径
（`os.path.join(_CUSTOM_TOOLS_DIR, category)` 与 `{name}.py`）。台账把它记为「静态推断、未利用、未复现」，
本轮**复现了**：

```
停用两级净化（= 修复前行为）后：
  generate_persistent("my_tool", …, category="../..")  → 返回 True
  实际落盘 = C:\Windows\TEMP\my_tool.py   （相对 _CUSTOM_TOOLS_DIR = ..\..\my_tool.py）
  ⇒ 写到 agent/tools/custom/ 之外，属"任意路径写文件"
```

补充一条**只有看代码才知道**的坑：`generate_simple` 在 `namespace.get(name)` 落空时会**回退到"第一个可调用
对象"并照旧返回 True** ⇒ 非标识符的工具名能一路走到落盘那一步（生成出的模块还会是语法坏文件）。

### 3.2 修法

- 新增 `_is_safe_path_segment()`：拒绝空/首尾空白、`.` 与 `..`、绝对路径、任何目录分隔符、冒号（盘符 / NTFS
  ADS）、NUL 与控制字符、结尾点或空格（Windows 会归一）、Windows 保留设备名（`CON`/`NUL`/`COM1`…）；
- 新增 `_is_safe_tool_module_name()`：要求合法标识符且**不是关键字**（`name` 同时是模块文件名与生成代码里
  的函数名）；
- 两道净化放在**任何副作用之前**（原来是"先注册到内存、再拼路径"）⇒ 非法入参**不注册、不建目录、不落盘**，
  返回 `False` 并在日志里给出拒绝原因。

**行为变更声明**：被拒的只有"本来就写不出可用工具"的入参；既有合法调用（`category="custom"`、合法标识符
工具名）行为一字未变 —— 全仓唯一的生产调用点 `agent/tools/ext_tools.py:370` 走的就是默认 `category`。

### 3.3 验证

`tests/unit/test_tool_generator_security.py` 新增 **31 条**（18 条分类 + 12 条工具名 + 1 条"合法入参不受影响"
反证），每条判据三条：返回 `False`、**不再进入注册路径**（`generate_simple` 零调用）、连 `custom/` 目录都不建。

```
python -m pytest tests/unit/test_tool_generator_security.py -q -p no:randomly
→ 59 passed in 2.40s
```

## 5. 失败基线收缩（`failures_baseline.txt`）

### 5.1 做了什么

`failures_baseline.txt` 上一版（2026-09-18 重建）固化 **7 条**，其头部自己写明它们全部归属**并行任务的在飞改动**
（TASK-01 的 `agent/tool_calling.py`、P0-1 的 `test_load_tool_meta_cache.py`），并要求「对应任务清零后，**必须**
用 `--update` 把它们从基线删除（只许收缩）」。本轮履行该条并把基线**收缩到 0 条**。

**证据（三个文件整文件跑）**：

```
python -m pytest tests/unit/test_date_shift_blindspots_guard.py \
                 tests/unit/test_llm_response_parsing.py \
                 tests/unit/test_tool_calling_comprehensive.py \
     -q -p no:randomly --timeout=120 --no-header -p no:cacheprovider
⇒ 156 passed, 1 skipped（0 failed）
```

7 条 nodeid 全部落在这三个文件里，逐条复现为绿 ⇒ 可移出基线。

### 5.2 ⚠️ 一处**没能完成**的复核（如实标注）

本轮尝试用**一轮整跑**复核全量 `tests/unit`（`-p no:randomly --timeout=300`），结果是：

```
跑到 76% 被 pytest-timeout 打断；栈：
  tests/unit/test_settings_registry.py:159 scan → _production_scan()
  → scripts/scan_settings.py:396 _assign_targets → for node in ast.walk(tree)
  → +++++ Timeout +++++
无结束摘要、无 junitxml（pytest-timeout 在 Windows 上默认用 thread 方法，dump 栈后 os._exit）
```

这就是 L6 / L10 记载的「全仓 AST 扫描」类负载敏感问题的**又一次一手复现**（这次它直接把整轮跑杀掉，
而不只是让某一分片红）。两个后果都写进了基线文件头部：

1. 本轮**不能**声称「全量单测当前零失败」，只能说「这 7 条已逐条复核为绿」；
2. 若全量里还有别的失败，它们会在 CI 的 `baseline-regression` job 里以**新增失败**出现 —— 那是**预期信号**
   （旧基线也没记过它们），不是清空引入的假警报。

### 5.3 顺带修掉的一道**假绿**闸（本轮实测踩到）

上面的「被打断」暴露了消费方 `scripts/check_baseline_regression.py` 的一个**静默假绿**路径：

```
pytest 被 timeout/OOM 打断 ⇒ 日志里既没有结束摘要、也没有短摘要行
  ⇒ parse_results 得到**空集合** ⇒ 与基线差集为空 ⇒ 脚本**退出码 0（全绿）**
```

修法：**输出里没有 pytest 结束摘要就直接拒绝判定**（退出码 2），并打印是不是被 timeout 打断、该怎么重跑。
新增契约测试 `tests/unit/test_check_baseline_regression.py`（**5 条**）：没摘要时拒绝（含 `--update` 也必须拒绝、
且不得改写基线文件）、新失败 ⇒ 1、基线内失败 ⇒ 0、`--update` 拒绝把新失败写进基线。

**端到端验证（用本轮那条真实被杀掉的日志）**：

```
python scripts/check_baseline_regression.py --pytest-log _ci_logs/now/pytest.txt
→ 失败基线回归检查 —— 拒绝判定 / ✗ 本次 pytest 输出里**没有结束摘要** / exit=2
```

### 6.6 顺带修正：一处**平台相关**的事实（免得留下未经验证的说法）

## 8. P0-1：`min_score` 判据**重设计**（中文召回 4/8 → 8/8）

> 设计依据与实测数据：`docs/audit_skill_governance/MINSCORE1.md`（那张卡判"不修"并给出三条硬理由；
> 本轮把其中的**第二条**（跨文件阻塞）与**第三条**（Pareto 支配）一起解决）。

### 8.1 问题（三条，全部实测）

1. **职责混用**：`min_score` 的语义是「调用方的验收阈值」，却被当成**两条检索腿的候选过滤器**
   （`loader.py` 的 tfidf/vector 两处）。而它比的量是 `tfidf_score = H/N_q`（query token 命中率，
   **不是相似度**，与 query 长度**严格反比**）⇒ 中文 bigram 下长 query 的正解在**进闸之前**就被删。
2. **连带把补偿判据打成永久失效**：闸的 BM25 补偿通道要求 `bounded_score is not None`；腿被清空 ⇒
   该条件恒假 ⇒ 即使 BM25 rank1 就是正解、裕度 8.09，整单照样 reject。
3. **编排层再犯一次同样的量纲错误**：`_bounded_relevance < min_score` 用**同一个 0.3** 比**同一个 H/N**
   ⇒ 只在 loader 里修 = 端到端零收益（MINSCORE1 §4.5 实测：被救回的 3 条 100% 被拦）。

### 8.2 为什么"再调一个阈值"无解（Pareto 支配，本轮复核并扩到 15 个特征）

把真阳性 `zh01` 与 S10-03 噪声并排（同配置）—— 噪声在**其余每一个坐标上都不劣**：

| 特征 | zh01（正） | 噪声 | 结论 |
|---|---|---|---|
| cov = H/N_q | 0.0909 | **0.1000** | 噪声更优 |
| H（命中 token 数） | 1 | 1 | 平 |
| bm25_t1 | 2.5441 | **4.6614** | 噪声更优 |
| BM25 裕度 | 1.3359 | **1.5433** | 噪声更优 |
| IDF 加权覆盖 | 0.0594 | **0.0869** | 噪声更优 |
| doc_cov / cosine / 相邻连跑 / ascii 命中 / id 命中 / 字段归属 | 0 | 0 | 逐项实测：噪声不劣 |

⇒ 任何对这组特征单调的判据**要么同时收下、要么同时拒绝**。本轮把候选特征从 5 个扩到 **15 个**
（`_scratch/probe_p0_feature_battery.py`），找出**唯一**能让正样本严格占优的新坐标：

| 新坐标 | zh01 | 噪声 |
|---|---|---|
| **命中 token 在语料里的邻域规模 `reach`** | **4**（「测试」覆盖 4 条技能） | **1**（「回答」只覆盖 1 条） |

语义：**域外查询最多与语料发生一次孤立碰撞**；真查询的主题词会在相关技能之间反复出现。

### 8.3 判据重设计的四条（形态变了，尺子没松）

| # | 改动 | 位置 |
|---|---|---|
| ① | **腿级地板与调用方阈值解耦**：两条腿改用召回地板 `_RRF_LEG_MIN_SCORE=0.01`（只管"有没有命中"，不做质量判断） | `loader.py::_try_rrf_match` |
| ② | **补偿通道加"证据非单点偶然"**：`命中 ≥2 处` **或** `命中处在语料里非孤立（reach ≥2）`；**只**加在"用 BM25 补偿弱有界相似度"这条路上 | `loader.py` 质量闸 ⑤ |
| ③ | **编排层不再复判**：loader 的闸判过（`MatchResult.quality_gate` 非空）⇒ 不再用同一个 0.3 比同一个 H/N；**没跑闸的路径**（非 RRF / 旧 loader / 闸门被关）原判据不变 | `orchestrator.py::_semantic_layer_match` |
| ④ | 观测透出：`quality_gate`（靠哪条判据过的）+ 闸日志新增 `evidence_reach / evidence_tokens / in_domain / gate_passed_via` | `loader.py` |

### 8.7 本轮踩到并修掉的一个实现缺陷（**既有守卫抓到的**）

新增常量 `_LOADER_QUALITY_GATE_VALUES`。

> 这条值得记下来：**"新增一个可选标记字段 + getattr 真值判断"是一个反模式**，在满是 mock/替身的测试仓里
> 会静默把守卫变成摆设。要么严格白名单，要么显式 `isinstance` 契约类型。

### 14.6 因此做的根因修复：整仓扫描「每收集器各遍历一次」→ **一次 BFS**

这是台账里挂着的 **L6 残留项**（`scan_paths` 重复 `ast.walk`），本轮由上面这条红正面暴露，于是直接修掉。

**先量化（本机实测，不是估计）**：

| 口径 | 改前 | 改后 |
|---|---|---|
| 整仓扫描（765 文件）耗时 | **15.8s** | **9.3s（-41%）** |
| cProfile 累计 | 81.8s | 37.2s |
| `ast.walk` 访问的 AST 节点总数 | **15,900,014**（≈ 每文件整体遍历 6~7 次） | **1,830,110** |
| `ast.walk` 占累计耗时 | **73.7%** | — |
| 调用计数（`ast.walk` 调用次数） | 97,407 | 77,907 |

**根因**：`_extract` 让 6 个收集器（`_assign_targets` / `collect_constants` /
`_enclosing_environ_params` / `_collect_function_scopes` / `classify_local_helpers` / `collect_loop_literals`）
**各自** `ast.walk(tree)` 一次；其中两个还对**每个函数**各做一次子树遍历求最大行号（且**各算一遍**）。

**修法（只动"遍历几次"，不动任何判据与输出）**：

1. 新增 `_walk_nodes_and_ends()`：一次 BFS 同时产出「节点表（与 `ast.walk` **逐元素同序**）」与父指针，
   再由一次逆序汇总出「子树内最大行号」备忘表；
2. 6 个收集器都接受 `nodes` / `ends`（**缺省时仍自行遍历**，仓外直接调用不受影响），
   `_extract` 与 `scan_paths` 里每个文件的树只遍历一次；
3. **不**用 `node.end_lineno` 走捷径 —— 那是**源码跨度末行**（多行调用会落在闭合括号那一行），
   比"子树内最大 lineno"更大 ⇒ 函数体区间变宽 ⇒ `_is_pass_through` 会漂移；本函数要的是与改前逐值相同的量。
