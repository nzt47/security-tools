## 2. 本轮实测推翻的一处任务书表述（重要）

任务书写：

> `/api/diagnostics/metrics` 仍在 `CP_API_AUTH_ALLOW` 里，**因为** `templates/observability_dashboard.html`
> （路由 `/dashboard`）仍以 **tokenless** 方式消费它。收敛该页即可摘掉最后一个豁免。

**该因果不成立。** 两条独立方法得同一结论：

```powershell
# ① 活体（enforce_all 档，无令牌）
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:5678/api/diagnostics/metrics   # 401
# ② 静态：该视图带 @require_token
#    agent/server_routes/routes_logging.py:828  @require_token
```

⇒ 豁免条目**被装饰器遮蔽**（"影子豁免"）：闸门放行与否都拦不住视图内部的装饰器，
所以该条目**从不产生任何效果**。页面其实**从来没能** tokenless 消费它 ——
`/dashboard` 的 5 条端点在该部署下**全部 401**，页面本身就是个空壳。

**代价不是"少做一件事"，而是规划建立在假前提上**：把"摘掉一个无效条目"当成
"关掉一个开放面"，从而低估剩余开放面、并高估那次收敛的安全收益。

**机制化处置**：新增 `agent.server_auth.find_shadowed_exemptions` +
`app_server.audit_shadowed_exemptions`（启动期点名）。它与既有的
`find_allowed_write_endpoints` 是互补的两半：

| 函数 | 查什么 | 性质 |
|---|---|---|
| `find_allowed_write_endpoints` | 豁免**多**放开了本该受保护的写端点 | 安全洞（H-5） |
| `find_shadowed_exemptions` | 豁免**什么也没放开**，却宣称放开了 | 认知洞（H-7 同族） |

本机清理后启动自检：`豁免清单无影子条目（12 项豁免均真实生效或为页面）`。

## 3. P1 的 live 实测（真实 app，不是单测夹具）

按本仓纪律「机制是否真正生效类判断必须主会话实测」，用 `app_server.app.test_client()`
在真实装配上跑：

| 请求 | 结果 |
|---|---|
| `GET /api/definitely-missing`（带令牌） | **404** `application/problem+json`，`X-Envelope: v2` |
| `POST /api/health`（带令牌） | **405** `application/problem+json`，`X-Envelope: v2` |
| `GET /api/health` | 200（形状不变） |
| `GET /definitely-missing-page` | **404 text/html**（浏览器语义保持不变） |
| 无令牌 `GET /api/<任意>` | **401** `application/problem+json`（闸门出口） |

404/405/500 的字段集合**逐一相同**（`type/title/status/detail/instance`）——
这就是 K3「错误结构种数 = 1」的可执行形式。

**一处必须说明的偏差**：审计验收 A6 的字面判据是
`grep -rc "@app.errorhandler" app_server.py >= 1`。本实现**不满足该字面判据** ——
错误形状集中在 `agent/api_envelope.py`，`app_server` 只调用 installer（为的是
①形状只有一处实现 ②可纯单测 ③可整段开关）。A6 的**意图**由更强的断言保证
（源码级"确实装载了" + 行为级"字段集合唯一"）。**如实记录，不以改 grep 蒙混。**

- **为什么推迟**：`scripts/audit/contract_diff.py` 的
  `manifest_route_undeclared`（插件真实注册了但 manifest 未声明）与
  `manifest_route_not_real` 是**当前 CI 门禁的核心判据之一**。
  routes 一旦变成派生物，这两条**在数学上恒真** —— 门禁会从"能查出漏声明"
  退化成"永远绿"。先做半截 = **主动把一把会漏报的尺子装进 CI**，

- **能做的前置条件**：先改 `contract_diff`，把 manifest 侧判据从
  "声明 vs 现实"换成"**派生完整性**"（每个插件蓝图下的真实规则都必须出现在派生结果里，
  且蓝图未注册/插件未注册要报），并同步改 `tests/unit/test_contract_diff_matcher.py`
  的锁死用例。两块必须**同一个提交**落地，否则中间态门禁是弱的。

### 4.2 P1 前端：删除 `pickObj` 启发式 —— **推迟**

- **实测阻塞点**：`pickObj/pickList/unwrap` 共 **39 处调用、16 个文件**，

## 6. 本轮的方法学教训（写给下一轮）

1. **扫描器的"输入清单"必须覆盖全集**：本轮做静态扫描时把文件集写成
   `app_server.py + plugins/*.py + agent/server_routes/*.py`，于是
   `/logs/dashboard` 被判为"豁免清单里的陈旧条目"—— 而它其实是
   `agent/log_system/dashboard.py` 里的真实路由。**差一点就写进结论。**
   运行期 `app.url_map` 才是权威输入（这也是 `audit_modules_registry` 用它的原因）。
2. **别把实现细节当契约**：一个守卫断言"必须出现 `return jsonify`"，
   把 401 改走 `_problem(...)` 后立刻假红 —— 它守的是"用哪个 helper"，
   而它想守的是"必须拒绝"。**守卫要按意图写，且结构边界要用 AST 表达**
   （用文本切片时会误把相邻分支算进来）。
3. **行号不能进基线键**：给 `admin_api._require_admin` 加了 5 行，
   基线里的 `/api/auth/login` 从 `:360` 变 `:365`，守卫随即报出
   **一条形状与"安全洞"完全相同的假警报**（"新增 N 条无鉴权变更型路由"），
   而一条路由都没变。
4. **先跑再下结论**：本轮两次归因错误都发生在"没读失败原因就动手"之前
   （探针把 `{"methods": [...]}` 当成了方法集合，得出"53 条全不命中"的假结论）。

## 7. 第三轮追加（2026-10-03/04 · 承接 PR #1000 #1001 #1002 #1004 #1005）

> 本节只追加**事实与决策数据**，不改动上面的结论。

### 7.1 H-8（依赖三源分裂）：**不能**用"在 Linux 上重新 pip-compile"解决 —— 已实测

本机 Docker 可用，于是按 `requirements.txt` **文件头自带的规范命令**
（`pip-compile --output-file=requirements.txt pyproject.toml`）在 `python:3.12-slim`
（与 ci.yml 的 `PYTHON_VERSION: '3.12'` 一致）里重新生成到临时路径。结果：

| 项 | 旧锁 | Linux 容器新生成的锁 |
|---|---|---|
| 行数 | 476 | 554 |
| 带 `sys_platform` 标记的行 | **3** | **0** |
| `comtypes` / `pypiwin32` / `pywin32` / `wmi` | 全在 | **全部消失** |

根因：**pip-compile 按"当前平台"求值环境标记**，在 Linux 上把
`sys_platform == 'win32'` 的直接依赖解析掉了。而**生产运行环境是 Windows**
（本机 `pip list` 实测这 4 个包都在装）⇒ 采纳那份锁 = 生产丢掉 WMI 感知能力。

**决策：不采纳 Linux 生成的锁。**
正确做法是**按目标平台分别生成**（或先明确本仓的锁文件到底服务哪个平台）——
本仓同时存在 Windows 生产服务与 Linux CI，**单一锁文件装不下两种平台的求值结果**，
这是设计决策而非一次命令。**前置条件**：定下锁文件的平台归属。

### 7.2 顺带关掉一个"全绿也能合入"的漏报口（PR #1005）

用上面那份 Linux 锁替换后跑**现有**门禁，实测：

### 7.4 方法学教训（第三轮新增，都是我自己踩的）

5. **守卫要锚在机制上，不要锚在"今天的数值"上**：
   我为"注释里的端点描述不算调用"写的守卫断言
   `stray[callability.ts] == 1`，而下一个 PR 恰好把该文件迁进常量层 ⇒
   这个数**合法地**变成 0，于是 CI 上**三条作业同时红**（契约门禁 + 两个分片），
   功能却完全正确。改法：抽出纯函数对**合成输入**判定 + 全仓**单调性**命题
   （"剥注释后计数 ≤ 不剥"）——后者不会随进度失效。
6. **断言消息必须覆盖它实际能失败的所有方向**：上面那条消息只写了
   "大于 1 说明注释又被算进来了"，而实际失败是 **0 == 1**（往下偏）。
   排查者会顺着"注释没剥干净"去找，而真相是"文件被迁走了"。
7. **批量改写脚本在找不到锚点时必须"整文件不写回"**：
   迁移 10 个文件时，首版正则要求 import 行以分号结尾（本仓多数不带），
   6 个文件报 `NO IMPORT ANCHOR`。若当时选择"先替换再想办法补 import"，
   就会产出 6 个引用未导入标识符的坏文件，而 `tsc` 要到下一步才告诉你。
8. **"看起来在报警、其实在说谎"比不报警更贵**：本轮又一次印证 ——
   门禁**有信息但不拦**（§7.2）与门禁**报警报错方向**（教训 6）都会让人不再信任它。
