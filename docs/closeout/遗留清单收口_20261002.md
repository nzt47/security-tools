## 1. flaky 测试：OPEN 状态下的并发断言被"冷却期"抢跑

- **现象**：全量/边界套件偶发红，单跑 100% 通过。
- **根因**：用例用的是为"观察状态转换"造的夹具 `fast_breaker`（`cooldown_seconds=0.1`），
  而 `allow_request()` 会在冷却期到期时**惰性**把 OPEN 转成 HALF_OPEN 并放行探测
  （`agent/circuit_breaker.py:308-318`）。机器一忙，从打开熔断到 20 个线程各调一次之间就可能 >100ms
  ⇒ 状态已是 HALF_OPEN ⇒ 前 3 个探测返回 True ⇒ `assert all(r is False ...)` 失败。
- **修法**：该用例要验的是"**处于 OPEN 时**全部拒绝"，与冷却期无关 ⇒ 改用长冷却期（3600s）的熔断器，
  把时间窗口消掉；并加一条反向锚 `assert breaker.state == OPEN`（若有人把语义改回去，这里会说话）。
- **验证**：单文件连跑 5 次全绿；整个 `tests/boundary` 连跑 2 次全绿。

## 2. `effort`（low/high/max）：核实**不做**

模型卡（`GET /v1/models`）写着 `"effort":{"supported_levels":["low","high","max"],"default_level":"high"}`，
但**在 OpenAI 兼容面（`/v1/chat/completions`）上传它没有可观测效果**：

| 变体 | reasoning 长度（三次） | 均值 |
| --- | --- | --- |
| 不传（默认 high） | 139 / 338 / 386 | 288 |
| `effort=low` | 327 / 253 / 426 | 335 |
| `effort=max` | 163 / 370 / 154 | 229 |

- 三者**没有单调性**（low 反而比默认长），差异落在采样噪声内；`reasoning_effort=low` 同样无效；
- 三个变体都返回 HTTP 200（该端点对未知字段**不报错**，所以"能发出去"不等于"被采纳"）；
- 模型卡的 `api_capabilities` 只声明了 `anthropic_messages`，该旋钮很可能只在 Anthropic Messages 面生效。

**结论**：不实现。加一个"界面能调、后端收下、实际无效"的旋钮，正是本次交付一路在消灭的东西。
（若将来要"更快/更省"，应先在 Anthropic 面上验证该参数确有系统差异，再立项。）

## 3. 压缩触发口径：工具结果单独计量

**立项前提是"一次大工具输出 = 一次压缩"**（2026-09-13，实测 `list_directory` 返回 195 项 ≈14k token）。
**核实结果：该前提在当前架构下已不成立** —— 真实记忆文件 `memory_data/messages.jsonl`（1481 条）
里**只有 user/assistant**（tool / tool_call_id 计数为 **0**）：编排器只把这两类写进记忆，
工具结果留在**请求内**的 `_working`（`orchestrator.py:3744-3753`）。

即便如此仍然落地，理由是把它从"碰巧没人写进去"变成**构造性事实**：

- 新增 `MemoryManager._compress_accounting()`：把待压缩窗口切成 (正文, 工具结果) 两笔；
- 新增 `MemoryManager._should_compress_now()`：**正文**按阈值触发；工具结果**只有在自身撑爆窗口时**才兜底触发
  （否则"只产工具输出"的记忆会无界增长）；
- 两处触发点（`add_message` / `score_and_save_message`）统一走它 —— 口径只有一份；
- 有工具结果时打一行 INFO（正文 N tok / 工具结果 M tok 单独计量），让"为什么没压缩"可复核。

**用例**（`tests/unit/test_memory_compress_accounting.py`，10 条）：切分正确性（含 `tool_call_id` 形态）、
14k 工具输出在 131072 窗口下**不再触发**、正文超阈值仍触发、小窗口下兜底触发、混合时按正文判定。

## 4. 两条对话路径的统一（工作台 vs 编排器）

上一轮已统一：**回复上限**、**上下文预算**、工具选择链、工具执行治理（都过 `agent.tools.call` → `tool_gate`）。
本轮补三处：

### 4.1 全局记忆（此前工作台完全不写）

工作台是**主 UI**，却只写会话存储：长期记忆 / 压缩 / 召回只反映另一半对话 ——
这也是"上下文面板量到的"与"实际被记住的"对不上的原因。
现在工作台在**正常收尾**时按与 `/api/chat` 同口径写入 `_memory`（user → assistant）。

**只在正常收尾时写**：客户端中途断开时回复是残缺的，写进长期记忆会污染召回；
会话存储仍保留部分回复（既有行为，便于用户查看已生成内容）。

### 4.2 本轮状态（turn_state）

`/api/chat` 会记本轮 `tool_steps` / `reasoning`，工作台此前只在会话消息里留 steps
⇒ 同一会话换个入口读到的东西不一样。现在工作台也写 `_set_turn_state(session_id, ...)`，
且 `tool_steps` **只收真实工具事件**（`tool-real-*`），`reasoning` 取真实推理事件。

### 4.3 删掉四条**拟态**阶段事件

原实现依次外发"意图识别 / 知识检索 / 规划分解 / 工具调用"四条**总是显示完成**的事件，
而本路径**并没有**跑这些引擎（源码自称"轻量拟态"）—— 用户看到一个"知识检索 ✓"却什么都没检索。
这与"假分母""死旋钮"是同一类病：**界面声称的与实际执行的对不上**。
现在只保留真实阶段（对话准备 / 上下文装配 / 工具调用：<name> / 思考过程 / 生成回复）。

**遗留（明确登记，非本轮范围）**：意图 / 检索 / 规划仍只在编排器路径上跑；
让工作台也跑它们属**行为与成本变更**（会改变回复内容、增加延迟与花费），需 Owner 决策后再做。

## 8. 最后一项遗留已被"做成菜单"关闭（同日追加）

§4.3 登记的遗留是：**意图 / 知识检索 / 规划仍只在编排器路径上跑**，要不要给工作台接上 ——
我当时判断它是"行为与成本变更，需 Owner 决策"。Owner 的决定是：**三档都要，做成菜单让用户自己选**。

### 8.1 三档（工具栏「输出格式」右侧的「对话模式」）

| 档位 | 后端行为 | 模型调用次数 | 流式 | 单轮增量 |
| --- | --- | --- | --- | --- |
| ⚡ 轻量 `plain`（默认） | 只用本会话历史 | 1 | ✅ 真流式 | —（与引入开关前**逐字一致**） |
| 🔎 检索 `retrieval` | 轻量 + 注入检索片段 | 1 | ✅ 真流式 | +≤3000 token 注入（实测 1433） |
| 🧠 完整 `full` | 委托编排器全链路（意图分层 + 检索 + 规划 + 工具） | 1 ~ 10+ | ❌ **非流式**（整段返回再分段外发） | 视任务，最坏 10 步 |

### 8.2 实现要点（口径与不变量）

- **检索口径只有一份**：工作台直接调编排器的 `_context_assembler_extra(question, mode="workbench")`，
  不另写检索 —— 否则就是"两套命中结果、两套预算"。
- **注入计入预算**：检索片段的 token 计入固定开销 ⇒ 历史预算自适应（实测 107352 → 104486），
  不会因为注入而把请求顶出窗口。
- **完整模式委托而非复刻**：编排器链路是 async 且步骤多，复刻=第二套实现；
  代价是非流式，这一点**写在 UI 选项说明里**，不隐瞒。
- **记忆不重复写**：完整模式下编排器自己写 `_memory`，工作台侧 `write_memory=False`；
  实测记忆条数 18 → 20（**恰好 +2**）。会话存储仍由工作台写（编排器不碰会话）。
- **非法模式回落 `plain` 并记日志**：前端传错不该让对话失败，但也不该静默变成别的模式。
- **失败可见**：编排器不可用 / 抛异常 / 检索异常都**明确回显原因**（不返回空回答）；
  检索失败按轻量继续。
