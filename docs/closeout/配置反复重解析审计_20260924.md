# config.yaml 反复重解析审计（L6 同族，2026-09-24）

> 来源：PR #968（分支 `fix/ci-load-sensitivity-l6`，**尚未合并**）根治了台账 L6 的负载敏感问题。
> 其中一条根因是 `agent/skills_mgmt/assessor.py` 的 `_cfg_value()` **每次调用都重新读盘并完整
> 解析一遍 config.yaml**（40KB，SafeLoader 本机实测 ≈ 28ms），而它是按 finding、按技能反复调的

>

> 的读取点，逐点**实测**调用次数，**只**修有实测证据的热点。修法与 `assessor.py` 那一处
> **完全同构**：按 `(绝对路径, mtime_ns, size)` 缓存 **yaml 解析结果**。

## 3. 改了什么（唯一一处：`agent/monitoring/cost_brake.py`）

```python
_budget_yaml_cache: Dict[Tuple[str, int, int], Dict[str, Any]] = {}   # (绝对路径, mtime_ns, size) → budget 段
def _config_yaml_budget() -> Dict[str, Any]:   # 命中即返回浅拷贝；未命中才 open + safe_load
```

**为什么它是真热点（而不是「测试凑出来的」）**：`load_config()` 不是「只跑一次」的装配函数 ——
`theta_limit()` / `shadow_overhead_audit()` / `daily_cost_view()` 的
`config if config is not None else load_config()` 分支就是**现读现解析**，属生产路径。

四条纪律与 `assessor.py` 逐条对齐：

1. **缓存键** = `(绝对路径, mtime_ns, size)`；**只缓存 yaml 解析结果**（本函数只取 `budget` 段）；
2. **env 优先级照跑**：`CP_BUDGET_*` 在 `load_config()` 里**独立于本函数**解析，缓存命中不影响
   `env > config.yaml > 默认` 的判定顺序；
3. **文件缺失 / 解析失败**仍返回 `{}`（原来的降级语义一字未改；`os.path.exists` 换成 `os.stat` 的
   `OSError` 分支，等价）；
4. **只留一份条目**：未命中时 `clear()` 再写入，长驻进程里不会无界增长。

守护用例（`tests/unit/test_s5_03_cost_brake.py::TestConfigYamlParseCache`，4 条）：

| 用例 | 守什么 |
|---|---|
| `test_same_file_parsed_once` | ① 同一指纹连读 5 次，`yaml.safe_load` 只被调用 **1** 次 |
| `test_content_change_invalidates` | ② size 变 ⇒ 失效；**同长度改写**只动 mtime ⇒ 也必须失效 |
| `test_missing_file_still_degrades` | ③ 文件缺失 ⇒ `{}` + 默认关（不抛、不误开刹车） |
| `test_env_priority_not_frozen_by_cache` | ④ **缓存命中之后**才 `setenv`，仍须 `enabled=True` 且 `source=="env"`，且**零次**重解析 |

## 4. 为什么没改其它模块

- **`agent/autonomy.py`（11 + 2 次）**：它的两个读取点**本来就是进程级缓存**
  （`_AUTONOMY_CFG_CACHE` / `AutonomyPolicy._overrides_loaded`），生产路径**不存在**「每次调用重解析」。
  那 13 次全部来自 `tests/unit/test_autonomy.py` 的 autouse fixture 逐用例调用
  `reset_config_cache()`（「重置配置缓存（仅测试用）」是**公开 API**）。套用指纹缓存后，只要仍尊重
  该 API「强制重载」的语义，次数**一次也降不下来**（测得 0 收益）；要降下来就必须改这个公开 API 的
  语义 ⇒ **不值得动**，如实记录。
- **`agent/evolution/injector.py`（7）、`agent/learning_budget.py`（6）、
  `agent/learning/novelty_hooks.py`（2）**：三者都在任务书给的「已知候选」里，但**实测都远低于 10 次/文件**。
  `learning_budget` 与 `novelty_hooks` 还有第二重理由：调用方（`get_learning_budget()` 单例、
  `novelty_hooks` 的开关函数）本身已保证低频，加缓存只是徒增状态与失效面。
- **`agent/skills_mgmt/loader.py` / `agent/orchestrator/orchestrator.py` /
  `agent/settings/resolver.py`**：`git grep` 命中了它们，但**已经是 mtime 缓存**（前两者还带
  命中/失效计数器），无重复工作。
- **`agent/tool_router.py`（91 次）**：见 §2 表下注释，是 import 期一次性扫描 91 个工具定义 YAML，
  非热点。

| | 用例数 | 轮次耗时 | 均值 | 该文件内 config.yaml 解析次数 |
|---|---|---|---|---|
| 改前（`origin/master` 928d2e17） | 107 | 9.09 / 8.87 / 8.74 / 8.62 s | **8.83 s** | **81** |

解析次数 81 → 6：其中 **2 次**是真实 config.yaml（缓存被守护用例清空后各重建一次），
另 4 次由守护用例**刻意制造**（3 次写 tmp 配置验失效 + 1 次预热）。
实测净省 ≈ **1.45 s**（8.83 → 7.38 s，≈16%）：75 次真实解析 × ≈28ms ≈ 2.1 s 是毛收益，
其中 ≈0.15 s 被新增守护用例自身吃掉，余下差额在轮次噪声内（改前 4 轮的极差就有 0.47 s）。

## 6. 剩余风险

- **缓存失效面**：指纹只覆盖 `mtime_ns` + `size`。极端场景（改写后**长度不变**且 mtime 被系统
  复位到原值）理论上会读到旧值 —— 与 `assessor.py`（PR #968）承担**同一风险**，且需要文件系统
  层面的时钟回拨才能触发；刻意**不引入 TTL**（宁可不命中重算，也不给「过期但看起来正常」的结论）。
- **返回浅拷贝**：`budget` 段里的嵌套对象（如 `theta` 子表）在缓存命中的多次调用间**共享引用**；
  与「每次现解析」相比，若某调用方**原地改写**嵌套值，改动会对后续调用可见。已核对现有唯一调用方
  `load_config()` 全程只读（`.get` / 传给 `_parse_theta_table` 只读），故当前无影响；
  将来若有调用方改写，须改为深拷贝或返回不可变视图。
- **未覆盖面**：本审计只扫了 `agent/` 下「自己读 config.yaml」的读取点与 27 个相关测试文件，
  **没有**做全量 CI 分片对拍；CI 总时长是否随之下降，需在本 PR 的 CI 上复核。
