> **裁定人**：主会话（用户已授权"可代为决定"）。

## 决策 1：SSRF 用独立守卫 vs 改 `data/policies/policies.json` —— **接受独立守卫**

**子代理做法**：通过新增 `agent/guardrails/ssrf_guard.py` 实现"默认拒绝"，
**策略文件 `data/policies/policies.json` 一字未改**，并说明这与 TASK-07 §3 第 2 步第 4 项的
"把策略文件改成显式 deny 私有网段"是**实现路径分歧**。

**裁定：接受它的做法。** 依据三条：

1. **更可靠**：独立守卫在**策略文件缺失/损坏时仍然生效**（这正是 fail-closed 要求，E3 已实测）；
   若把默认拒绝塞进策略文件，文件一坏就回到零防护 —— 而本仓恰恰有"策略文件缺失 ⇒ fail-open"
   的既有语义（`tool_gate` 的 fail-open 路径）。
2. **职责更清**：SSRF 判据是**网络层事实**（IP 字面量归一、DNS 后校验、重定向逐跳复检），
   不是"策略配置"。塞进策略文件会让它变成可被改配置绕过的开关。
3. **不冲突**：它没有删/改任何既有策略，故两层并存时以更严者为准，无矛盾。

**要求（已满足）**：它给了 `scripts/audit_egress_points.py` 作为**白名单外直连为零**的守门脚本（E2 实测 violation 0）。

## 决策 2：保留 `bash -c` 语义 vs 改白名单 argv —— **接受保留，但要求登记为高风险**

**子代理做法**：`argv = [shell, "-c", command]`，整串先过 `validate_command`；
并说明"会话里的管道/重定向/`&&` 是 LLM 的正常用法，直接换 argv 会让它全线失效"。

**裁定：接受保留。** 依据：

1. **一换就废**：本仓 shell 工具的核心用途就是 LLM 编排命令（管道/重定向/串联），
   改成白名单 argv 会**当场打断主要使用场景** —— 那是"为了安全把功能删掉"。
2. **有纵深防御**：命令串已过 `validate_command`（黑名单 + 危险模式），
   且**执行器已换成 `run_sandboxed`**（子进程 + 超时 kill + 输出截断），
   另有 `CP_SANDBOX_SHELL_MODE` 三档（`off`/`shadow`/`enforce`）可收紧到拒绝。
3. **诚实标注已做**：它在代码注释与审计字段 `shell_semantics: true` 里标为高风险。

**遗留（登记）**：`data/process_whitelist_custom.json` 的白名单机制**未接**。
⇒ 登记为待办；若将来要收严，正确路径是"在白名单模式下逐步迁移调用方"，而不是一次性切换。

## 决策 3：边界词无 token 通路 ⇒ 命中即硬拒绝 —— **接受硬拒绝（从严），但登记词面过宽**

**子代理做法**：`guard_tool_execution` 的机制 5（边界词）在 `call()` 里留了保留参数
`__boundary_token__`，但**没有任何地方签发它** ⇒ 命中"永不自动化五类"
（`转账|付款|支付|汇款|打款`）的调用**在当前实现下是硬拒绝**。它担心"偏严"。

**裁定：接受硬拒绝。** 依据：

1. **fail-closed 是这类词的正确默认**：这五类词对应的是**不可逆的对外资金动作**。
   "没有 token 通路"的现实含义是"当前没有任何授权路径"，那就**应该拒绝**，
   而不是"因为没有通路所以放行" —— 后者才是危险的（把缺失基础设施当默认许可）。
2. 与 TASK-06 的方向一致：闸门自身故障时**治理动作 fail-closed**。

**遗留（登记）**：词面 `转账|付款|支付|汇款|打款` **较宽**，可能误伤"解释一下支付流程"这类
纯文本讨论。⇒ 要求后续在**影子模式**下采集一轮误报率（记录"本会拒绝"的调用），
按数据决定是否收窄词面或改为"拒绝 + 提示走 UI 签发"。
**在此之前不上宽词面，因为它偏严的方向是安全侧。**

## 决策 4：每轮 2 条 401 的 `ui.admin.api_apply_network_config.post` 归属 —— **判为后端，不是测试**

**子代理做法**：它**不断言**，把举证责任交上来。它给的反证很关键：
唯一两个涉及该路径的测试文件都**不产生 401**（一个断言 200/500 且用 Flask test client；
另一个是手工脚本、pytest 收集 **0 条**）。

**裁定：判为"用户正在运行的后端收到未鉴权 UI 写请求"，不计入测试污染。** 依据：

1. **反证成立**：既然涉及该路径的测试都不产生 401，把它归给测试就与证据冲突；
   而"后端收到未鉴权请求"与 `status_code 401` + `identity_tier degraded` 完全自洽。
2. **与 D13 的既有警告一致**：「不要把后端写入算作测试残留」——本会话已有一次同类误判
   （我曾把 `approval_records.jsonl` 的性质判断错）。
3. **不阻塞**：该判定不影响 TASK-07 的验收（它已如实报告，未掩盖）。

**可选的后续（不属本任务）**：若确认无人手动访问，则可能是某个自动化/探针在轮询该端点
⇒ 值得看一眼 `data/audit/audit_20260920.jsonl` 里这几条的 `actor_ip_hash` 来源。

## 决策 5：chunk_0 超时杀进程是否可接受 —— **接受，但登记为未完全归因项**

**子代理做法**：两轮都在**同一处**超时（`test_tool_callability.py:273` →
`callability.build_manifest` → `location.py::_walk_chain`），但单跑该文件 **43 秒通过**，
冷进程全量走链 **6.7 秒**（最慢单工具 558 ms）。它**明确说"我无法证明它与我的改动完全无关"**。

**裁定：接受（判定为规模/争用现象），但保留为未完全归因项。** 依据：

1. **它自己给了对照数据**：单跑 43s（预算 120s）、冷进程全量走链 6.7s
   ⇒ 单次走链成本远未到超时线；而 chunk 进程 RSS 1.2–1.5 GB 且与另 3 个 chunk 抢机器。
2. **与本会话已记录的同一族问题一致**：D14 记的就是"裸单进程/并行负载下本仓全量会退化"
   （我们实测过 7.5 分钟/1% 的边际退化）。
3. **它做了正确的自我约束**：中途因自己改代码而**主动作废了一轮结果**（D13），
   并未把不可比的数据混进来。

**要求（已完成）**：它给出了可复现命令与日志定位方法。
**遗留**：`location.py::_walk_chain` 在全量规模下的走链成本值得**单独观测**（不属 TASK-07）——
它同时被 `build_manifest` 调用，而 `--check` 已进 CI，若未来工具数增长到数百，
这里可能成为新的超时源。⇒ 登记为 TASK-08（性能）的候选观测点。
