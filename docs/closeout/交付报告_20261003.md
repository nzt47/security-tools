**49 个用例在 setup 阶段全部 ERROR** ⇒ `NameError: name 'BaseModel' is not defined`（`config.py:53`）。

**完整触发链（逐环核实，不是推断）**：

1. 该作业的 `Install test dependencies` 只装 pytest/pytest-timeout/pytest-asyncio ⇒ 环境里**没有 pydantic**（日志实证：`No module named 'pydantic'`）；

4. `config.py` 的 `except ImportError` 分支**只置标志、没给占位**，模块继续执行 `class LLMConfig(BaseModel)` ⇒ NameError。

**为什么首个提交是绿的**：`6005f6f6` 时 `lifecycle_manager` 还不 import config，同一条链没被触发（该作业在当时确实 49 passed）。
换言之：这条红是本次改动**真实引入**的，不是历史包袱，也不是 flaky。

**修复（提交 `fdc41237`）**：

| 层 | 改动 | 理由 |
| --- | --- | --- |
| 根因 | `config.py` 在 pydantic 缺失分支给出**结构性占位**（`BaseModel`/`ConfigDict`/`Field`/`validator`/`ValidationError`），降级校验按 `_PYDANTIC_AVAILABLE` 显式门控；占位基类**一旦实例化立刻 RuntimeError** | 文件头写的是「Pydantic 模型支持（可选）」，但**可选分支从来没被实现**——只要 pydantic 不在，模块导入期就炸，`_basic_validation` 永远走不到。这是比 CI 红更早的隐性缺陷 |
| 环境 | CI 该作业 `Install test dependencies` 追加 `pydantic>=2.0.0` 并注记原因 | **防御性、不是本红的修复点**：真正修好的是 config.py。补依赖只是让该作业的配置模型与生产一致；即便不加，本作业也已转绿（见下方「机制澄清」） |
| 守门 | 新增 `tests/unit/test_config_optional_pydantic.py`（5 条）：**子进程**用 `sys.meta_path` 屏蔽 pydantic 后 `import config` | 本机装了 pydantic，进程内屏蔽验证不了「模块级导入期」行为；只有真 import 不到 pydantic 的独立解释器才能复现 CI 现场 |

**机制澄清（独立核验后更正的一处夸大）**：在与该作业同构的裸环境里加探针复现可见，
`agent.orchestrator.lifecycle_manager` **其实从未被真正导入** —— `tests/unit/conftest.py::_safe_patch` 会吞掉 `ImportError`

修复前 `import config` 在导入期抛 **NameError**（不在被吞之列）⇒ fixture 直接中断、49 个用例 ERROR；
修复后 config 可导入，即便后续因 `watchdog` 缺失抛 `ImportError`，也回到 `_safe_patch` 既有的兜底路径。
结论：**真正的修复点是 config.py**；给该作业补 `pydantic` 属**防御性一致性**（让配置模型与生产一致），
