### 9.7 CI 在 Linux 上抓到的一个跨平台回归（已修，并记入常设约束）

**现象**：`可观测性质量保障 / 全项目测试覆盖率 (Shard 2/6)` 失败：

    FAILED tests/unit/test_system_tools_platform.py::TestErrorHandling::test_invalid_path_characters

**根因**：我给 `safe_resolve_path` 加的 symlink 加固在 realpath 抛错时 `raise` 了自己的
ValueError，改掉了「畸形输入返回字符串」这一既有契约。而该差异**只在 Linux 暴露**：
Linux 的 `os.path.realpath` 对含 NUL 的路径抛错，**Windows 不抛** ⇒
本地 `test_system_tools_platform.py` 是 **125 passed**，此回归在本地完全不可见。

**修法**：realpath 失败时**跳过本项检查、保持改动前行为**（返回字符串），不再新增异常与拒绝。
取舍理由：本加固的目标是「符号链接绕过」而非「畸形输入」；畸形输入自有下游 `open()` 处理，
其错误契约不该被本函数顺手改掉，且原实现同样不做这一检查 ⇒ 安全性不受影响。
验证：monkeypatch `os.path.realpath` 令其抛 Linux 同款异常，确认 `safe_resolve_path`
**返回 str 且不抛**；本地全量重跑后该失败消失。提交 `24080e0d`。

**由此确立的常设约束（本项目应长期遵守）**：

> **本仓的 CI 是 Linux，而开发/验证环境是 Windows。凡涉及路径语义（大小写、分隔符、

> 对这类改动，必须：① 用 monkeypatch 显式模拟 Linux 语义做一次反证；

### 9.12 **管理后台加固 + `enforce_all` 下管理后台不可用**（业主决定 #5「做」，2026-10-01 实测）

#### 9.12.1 修复的漏洞：管理令牌**可伪造**（完全绕过认证）

`plugins/admin_api.py` 原实现把用户名**明文写在 token 里且不做任何校验**：

```python
token = f"mock-token-{username}-{int(time.time() * 1000)}"          # 签发：名字直接拼进去
m = re.match(r"^mock-token-(.+)-(\d+)$", token); return m.group(1)  # 校验：只做正则，无签名
```

⇒ 任何人手写 `Authorization: Bearer mock-token-admin-1` 即成为 admin，可调用 `/api/user/info`、
`/api/auth/menus`、用户增删改等**全部管理端点**。原 docstring 自述「Web 演示态不做强校验」，
但这不是「弱校验」的量级问题，而是**认证可被完全绕过**。

**修法**：改为 **HMAC-SHA256 签名 + 12 小时有效期**。用户名以 hex 编码进 token，但**必须**带正确签名才算数；
签名密钥取自既有的 `FLASK_API_TOKEN`（已在 `settings/registry` 登记，不新增环境变量），
未配置时回退**进程内随机密钥** —— 只会让重启后旧 token 失效（更严格），绝不放宽。
对外契约不变（仍返回 `{"token": ..., "user": ...}`、仍走 `Authorization: Bearer`），前端零改动。

顺带两条：口令改从 `YUNSHU_ADMIN_PASSWORD` 读取（**未配置即 fail-closed**，见 §9.12.4）；
登录失败的「用户不存在」与「口令错误」返回**同一句文案** + 常量时间比较（防用户枚举）。

#### 9.12.2 修复的结构性缺陷：`enforce_all` 让**整个管理后台 401 不可用**

这是在验证 9.12.1 时实测发现的**既有**缺陷（非本次改动引入），根因是两个子系统把**不同的**令牌
放进**同一个** `Authorization` 头：

| 子系统 | 令牌 | 写入位置 |
|---|---|---|
| 全局鉴权网关 | `FLASK_API_TOKEN` / token_map | `Authorization: Bearer`（`@/lib/apiToken`） |
| 管理后台会话 | `mock-token-<签名>` | `Authorization: Bearer`（`utils/request.ts:86`） |

而旧 `_bearer_or_header_token()` 是「**Authorization 存在就只看它**，没有才看 X-API-Token」⇒
网关把管理会话令牌当成「无效的 API 令牌」拒掉。前端**无解**：管理端只读 `Authorization`，网关又只认它，
两层在同一个头上互斥 ⇒ 必须在网关侧允许回退。

**修法**（两处小改，安全语义不变）：
1. `agent/server_auth.py` 新增 `authorize_request()`：按 `Authorization` → `X-API-Token` **逐个**试，任一通过即放行。
   两个头携带的是**同一份**共享密钥 / **同一张** token_map，比较逻辑一字未动；无候选令牌时仍走
   `authorize_token("")`，保留「完全未配置令牌 ⇒ 不校验」的既有语义。
2. `yunshu-ui/src/utils/request.ts` 在请求拦截器里**同时**带上 `X-API-Token`（不覆盖 `Authorization`，
   否则会把管理会话令牌冲掉）。

**线上实测**（`http://127.0.0.1:5678`，`CP_API_AUTH_MODE=enforce_all`）：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 管理令牌放 `Authorization` + API 令牌放 `X-API-Token` → `/api/user/info` | **401**（管理后台不可用） | **200** |
| 同上 → `/api/auth/menus` | 401 | **200** |
| 伪造 `mock-token-admin-1` | 200 + `{"code":200,...}`（**admin 身份**） | `{"code":401,...}` 拒绝 |
| 篡改合法令牌的用户名段（`user`→`admin` 自我提权） | 通过 | `{"code":401,...}` 拒绝 |
| 令牌放错头 / 两个头都是垃圾 / 都缺失 | 401 | 401（不回退成放行） |
| 仅 `Authorization`=API 令牌（工作台原有方式） | 200 | 200（无回归） |

#### 9.12.3 已知偏差（**有意保留**，不是遗漏）

`_fail(code, message)` 对 `401` 仍返回 **HTTP 200** + body `code:401`（管理后台前端按 `body.code` 分支）。
这**不是**安全边界（真正的边界是 token 签名 + 全局网关），改成真状态码会让「用户名或密码错误」这类精确提示
被前端 HTTP-4xx 分支的通用文案顶掉 ⇒ 属 UI 契约变更。故契约保持，但补了**鉴权失败日志**
（`code in (401,403)` 记 warning），避免「HTTP 200 掩盖 401」落到完全不可观测。

#### 9.12.4 口令来源与 CI 门禁的冲突（**一次被 CI 纠正的设计取舍**）

**我最初的做法**：口令取 `YUNSHU_ADMIN_PASSWORD`，**缺省回落到演示值 `123456`**，
并在使用默认值时首次登录告警一次。理由写的是"删掉会让本机管理后台登不进去，
属把可用性换成安全性"。

**CI 直接否掉了它**：`硬编码密码扫描（全分支）` 用 gitleaks 规则 `hardcoded-password-assignment`
命中 `_DEMO_PASSWORD = ...`（变量名含 `PASSWORD` 且赋字面量）⇒ 该 workflow 失败。
这条门禁的存在意义正是"**源码里不许出现口令**"，而我的"告警一次"只是在给一个字面量找借口。

**改后的做法（正确做法）**：源码里**不留任何口令字面量**，未配置环境变量时
**fail-closed** —— 登录一律拒绝，并在文案里**点名**要配置哪个变量（同时打一条 ERROR 日志）。
这同时满足 INV-08「不静默降级」：默认值就是安全值，且"为什么登不进去"是自解释的。

**必须记下的一点**：正确的修法**不是给变量改名躲开扫描**（那是在骗自家的安全门禁），
而是真的不留字面量。同理我把测试里用作"旧口令"的字面量也换成了无意义的假值，
并在 `tests/unit/test_admin_api_token_hardening.py` 里加了一条**镜像该 gitleaks 规则**的源码守卫，
避免同一个人（本次就是我）在下一个改动里再写回去。

`.env` 中 `YUNSHU_ADMIN_PASSWORD=123456` 现在是管理后台口令的**唯一来源**（源码里已无默认值）。

且管理后台现在能在 `enforce_all` 下正常工作 ⇒ 建议改成强口令：


**若要留给全新部署者**：`.env.example` 已补上 `# YUNSHU_ADMIN_PASSWORD=` 条目并写明

### 9.13 【严重】鉴权闸门的 fail-open 可被**远程触发** ⇒ 完整鉴权绕过（已修，2026-10-01 实测）

§3 表格里原本把「闸门自身异常一律放行」记为「可用性 vs 安全性的**显式设计取舍**，改动需产品判断」。
**这个判断是错的**：该 fail-open 有一个**可远程触发**的入口，构成**完整的鉴权绕过**。

#### 9.13.1 根因链（三个环节缺一不可）

1. `secrets.compare_digest(str, str)` 对**含非 ASCII 字符**的 str 抛
   `TypeError: comparing strings with non-ASCII characters is not supported`；
2. `authorize_token()` 把该异常抛给调用方；
3. 闸门 `_api_auth_gate()` 的 `except Exception: return None` 是 **fail-open**
   （原 docstring 自述「任何异常都放行并记 ERROR（可用性优先）」）⇒ 异常被吞，**请求直接放行**。

于是：**只要在令牌头里塞一个非 ASCII 字节（`é` 即可），整站 API 全部无认证可达。**

#### 9.13.2 实测（`CP_API_AUTH_MODE=enforce_all`，`http://127.0.0.1:5678`）

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `GET /api/status`（无令牌） | 401（对照） | 401 |
| `GET /api/status`（合法 `FLASK_API_TOKEN`） | 200（对照） | 200 |
| `GET /api/status` + `Authorization: Bearer <含 é 的任意串>` | **200 + 完整响应体** ❌ | **401** |
| `GET /api/status` + `X-API-Token: <含 é 的任意串>` | **200 + 完整响应体** ❌ | **401** |
| 非 ASCII `Authorization` + 垃圾 `X-API-Token` | **200** ❌ | **401** |
| 非 ASCII `Authorization` + 合法 `X-API-Token` | —（回退尚未引入） | **200**（回退正常，不受影响） |

**影响面**：`enforce_all` 是本次已切换的运行档位 —— 换句话说，**切换本身的效果被这个洞抵消**。
任何人（含本机以外的、能连到 5678 的进程）在任意 `/api/*` 请求上加一个字节即可绕过全部鉴权。
本机绑定 `127.0.0.1` 使其**当前**不可远程利用，但只要端口被转发/容器映射/反代暴露，即为**全站沦陷**。

#### 9.13.3 修法（三处，缺一不可）

1. **`agent/server_auth.py` 新增 `token_equal()`**：按 **bytes** 比较，且自身**绝不抛异常**
   （任何异常一律返回 `False` = 不通过）。
2. **`authorize_token()` 改用 `token_equal()`**；同时 `app_server.require_token`、
   `plugins/status.py` 的本地 `_require_token`、`plugins/admin_api.py` 的口令比较也都改为按字节比较
   （这几处会抛 `TypeError` ⇒ 把「无效凭证」变成 500，同样是缺陷）。
3. **闸门的 `except` 在 `enforce`/`enforce_all` 下改为返回 401**（fail-closed）；
   `shadow`/`off` 仍放行 —— 那两种模式的语义本就是「只记不拦」。
   理由：放行等于把「闸门坏了」降级成「谁都能进」，这是 **INV-08（不静默降级）** 在安全面上的一等公民。

`agent/security/identity.py::TokenMap.lookup` 的 `compare_digest` **经核实不在此列**：
它比较的是 `_hash_token()` 产出的 sha256 **hex 串**（恒为 ASCII），不会触发该 `TypeError` ——
故**未**改动（避免无谓改动；这条也是"看起来像同一个 bug、实际不是"的例子）。

#### 9.13.4 教训（值得写进本仓规则）

- **「可用性优先的 fail-open」在鉴权主防线上不是取舍，是漏洞**：它把异常路径从「拒绝」变成「放行」，
  而异常路径恰恰是攻击者最容易构造的路径。
- **docstring 写了「fail-closed」（`app_server.py:664`）但实现是 fail-open** —— 注释与实现相反，
  与本次审计中反复出现的「单测绿、线上 404」「注释称未配令牌、实测已配」是**同一类问题**：
  **文档不是证据，运行期实测才是**。
- 常量时间比较是安全纪律（值得保留），但 `secrets.compare_digest` 的**非 ASCII `TypeError`** 是本仓
  反复出现的比较点上的共同坑 —— 故把它收敛成**唯一入口** `token_equal()`，并用源码级守卫
  （`test_授权路径不再直接用_compare_digest_比较原始字符串`）防止再各自写回。

**复核命令**：`python -m pytest tests/unit/test_auth_gate_failopen_bypass.py -q`（13 passed）。

### 9.18 真机验证暴露的**系统性缺口**：业务指标整层没接线（2026-10-02 实测）

#### 9.18.1 现象与证据链

| 环节 | 实测 |
|---|---|
| `GET /api/business/prometheus` | **200**，`text/plain`，74 行 = 37 个 `# HELP` + 37 个 `# TYPE`，**样本行 0 条** |
| `app_server.py` 对 `business_metrics` 的引用 | **0 处**（grep 全文件无匹配） |
| `business_metrics.py` 提供的写入 API | `record_interaction` / `record_tool_call` / `record_circuit_breaker_trigger` … **20+ 个**，**无人调用** |
| `monitoring/prometheus.yml` 是否抓该端点 | **没有**（但这不是根因，见下） |

**它连自己的注释都写着该被依赖**：`app_server.py:1623` ——
「T3：业务仪表盘（**Prometheus 告警依赖** `/api/business/prometheus`）」。

#### 9.18.2 后果（两种相反方向的失效，都比"名字写错"严重）

1. **引用业务指标的告警 = 死规则**：相关序列不存在 ⇒ 表达式恒空 ⇒ **永不触发**。
2. **用 `absent()` 写的告警 = 永久 firing**：实测 `CircuitBreakerMetricsMissing`
   （`circuit_breaker_alerts.yml:148-150`，`for: 5m`，severity=warning）因为
   `absent(yunshu_circuit_breaker_state)` 恒为 1 ⇒ **该告警长期挂着**。
   这不是"静默"，而是**告警疲劳**：一条永远亮的 warning 会把真信号淹掉。

#### 9.18.3 **我刻意没有做的一个"看起来像修复"的动作**

最直觉的修法是给 `prometheus.yml` 加一个抓 `/api/business/prometheus` 的 job。
**但实测表明它救不了**：该端点当前**只有 `# HELP`/`# TYPE`、没有任何样本行**，
Prometheus 摄入后**不会产生任何序列** ⇒ `absent(...)` 仍然为 1，那条告警**照样永久 firing**。
真正的缺口是**写入侧**（20+ 个 `record_*` 无人调用），不是采集侧。

⇒ 故本轮**不加**该 scrape job：它是一个"改了但没效果"的改动，会制造"已经修好了"的错觉。
正确顺序应是：**先补写入点**（让指标真的有数据）→ 再补 scrape job → 那时加 job 才有意义。

#### 9.18.4 与前几轮发现的关系

不是个别名字写错。**归因到"名字"上会一直修不好。**
