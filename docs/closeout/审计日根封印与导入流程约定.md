# 审计日根封印与导入流程约定

> 裁定来源：主会话 **D-20260921-04 / L17** —— 定为「**先导入后封印**」**单轨**（**纯流程，不改代码**）。
> 执行者：TASK-09 子代理（独占窗口），2026-09-21。本文件为**新增文件**。
> 适用对象：任何会向审计链写入 `ts ≠ now` 记录的人/脚本（回填、导入、迁移、演练数据、修复补洞）。

---

## 0. 一句话铁律

> **要回填，就先把回填做完，再对当日封印。**
> 已经封印之后才发生的回填，**不得删除或改写已封日根**，只能按 §4 用
> `daily_merkle_root(day, force=True)` **追加**一条新根。

---

## 1. 失效的是哪一种封印（先把语义说清）

现行封印语义（`agent/audit/chain.py:2762-2796`）：

> **封印 = 「该 UTC 日」∩「在封印点（`last_seq`）之前已入链」的记录集合。**

两条约束各管一半（`chain.py:2776-2779`）：

| 约束 | 作用 | 代码 |
|---|---|---|
| `seq ≤ recorded.last_seq`（前缀上界） | **不误报**：封印之后新写入的记录 seq 更大，天然落在集合之外 | `chain.py:2802-2804` |
| `day_of_ts(ts) == day`（按日过滤） | **不误判**：封印区间里混进的**其它日**记录不参与该日根（L18 的 09-14 就是这种形态） | `chain.py:2807-2808` |

---

## 2. 为什么**正常写入（`ts = now`）不触发**该 FAIL

正常写入时 `append()` 在跨进程锁内取**权威链头 + 1** 分配 seq
（`chain.py:1598-1604`），因此：

- 对**任何已封日** D：D 的封印早已完成，其 `last_seq` 是当时的链头；
  之后写入的记录 seq **严格更大** ⇒ `seq ≤ last_seq` 对它们不成立 ⇒ **不进叶子集合**
  ⇒ 叶子集合恒定 ⇒ 该日根**恒 OK**（这正是 §1 前缀上界给出的保护）。
- 对**当日**：D = 今天时，`_maybe_auto_seal()` 只封 `d < today` 的日
  （`chain.py:2228-2231`）⇒ **今天不会被封**，今天的记录不会与"已封"冲突。

⇒ **正常业务运行时不会看到该 FAIL。** 我们在 TASK-09 的实测也印证了这一点：
2026-09-21 当天链上有新写入（`audit_chain.db` mtime 19:17），而
`verify_audit_chain.py --roots-check all` 依旧 **exit 0**。

---

## 3. 什么会**真的**触发 FAIL（三种机制，全部有实证）

### 机制 ①：记录**晚到**，但占据了 `seq ≤ last_seq` 的位置（回填/导入/补洞）

这是 L17 的本体。前缀上界只挡"seq 更大的后来者"，**挡不住"后来才写、却落在旧 seq 上"的记录**。
一旦该记录的 `ts` 归属某**已封日** D 且 `seq ≤ D.last_seq`：

```
叶子集合 = entries(day=D, end_seq=D.last_seq)   # 多出这一条
```
⇒ 重算 `root_hash` 变化 ⇒ `root_hash_mismatch`（`chain.py:2859-2863`）；
若仅条数变化而根恰好相同（概率可忽略），也会被 `leaf_count_mismatch` 拦下
（`chain.py:2864-2868`）。

**实证（就在本仓库里发生过）**：2026-09-21 的链修复为补 15 个 seq 空洞，
`INSERTED 15` 条**零改写**地补回库中（`docs/closeout/L1_evidence/PRODUCTION_receipt.json`
→ `before.holes` / `recovered_seqs`）。其中 **`seq=19220`**：

| 项 | 值 | 来源 |
|---|---|---|
| `seq=19220` 的 `ts` | `2026-09-17T17:38:48.104732+00:00` | 只读查询 `audit_chain` 表 |
| 归属日 | **2026-09-17** | `day_of_ts(ts)` |
| 09-17 的封印区间 | `8437..19228` ⇒ **19220 落在区间内** | `daily_roots.jsonl` 现行 09-17 行 |
| 09-17 根叶子数 | **10791（原始）→ 10792（现行）** | `daily_roots.ORIGINAL.jsonl` vs `data/audit/daily_roots.jsonl` |

⇒ 一条**在封印之后才被补回、却落在封印区间内**的记录，直接把 09-17 的叶子数从
10791 顶到 10792。若当时不重签 09-17 的根，该日就会 **FAIL**。
**这就是"封印后再入链 FAIL"的完整机制，且它是必然结果。**

### 机制 ②：**空日根**之后回填该日

`last_seq == 0` 的空日根不含前缀上界，走**全量按日**核对
（`chain.py:2789-2791`、`2805-2806`）：空日根断言的是"该日无新增"这一**绝对命题**，
之后回填任何一条该日记录 ⇒ 叶子数变化 ⇒ FAIL。这是**故意**的（不静默放过）。

### 机制 ③：封印元数据被改

`first_seq` / `last_seq` / 首尾 `self_hash` 同在签名消息内，被改必然 FAIL
（`seal_metadata_mismatch`，`chain.py:2815-2826`、`2869-2875`）。

## 4. 流程约定（**铁律**）

### 4.1 唯一推荐顺序：先导入、后封印

```
[1] 完成全部回填/导入写入（ts 可任意历史时刻）
[2] 确认写入已 flush 落库
[3] 再对受影响的每一个"已过完的 UTC 日"执行封印
[4] 跑 verify_audit_chain.py --roots-check all 对拍（应 exit 0）
```

**禁止**：先封印、后导入（这正是机制 ① 的触发条件）。
**禁止**：封当日之后再往当日回填（封当日 = 给"今天"建前缀上界，
后续"今天"的正常写入 seq 更大、不受影响；但任何**落在旧 seq** 的当日补写都会打破它）。

### 4.2 已经封印后才发生的回填 —— 走 `force=True` **追加**路径

```python
# 只追加，不改历史；同一天会出现两条根记录（旧 + 新）
chain.daily_merkle_root("<YYYY-MM-DD>", force=True)
```

代码依据：

| 行为 | 代码 |
|---|---|
| `force=False`（默认）同日已有根 ⇒ 直接返回旧根，**幂等** | `chain.py:2683-2686` |
| `force=True` ⇒ 跳过幂等检查，走 `_append_daily_root` **追加一行** | `chain.py:2687` |
| 追加时 `prev_entry_hash` = 文件**末行**的 `entry_hash`（外层根链续接） | `chain.py:2697-2699` |
| 只 `open(path, "a")` 追加，**不截断、不重写既有行** | `chain.py:2700-2707`、`_appending()` `chain.py:815-831` |

**绝对禁止**：删除或改写 `daily_roots.jsonl` 里已封日的**历史行**。
它们参与外层根链（`prev_entry_hash → entry_hash`）连续性校验
（`chain.py:2898-2919`），删除/改写会让 **全部** 日根报 `root_chain_broken`。

### 4.3 ⚠️ `force=True` 的**能力边界**（TASK-09 实测，必须知道）

`get_daily_root(day)` 遍历 `read_daily_roots()` 返回**首条**匹配
（`chain.py:2752-2757`），而 `verify_daily_root()` 正是用它取"治理根"
（`chain.py:2798`）。因此：

| 事实 | 实测证据（2026-09-21，TASK-09） |
|---|---|
| 追加新根后，**同日出现 2 条根记录** | `daily_roots.jsonl` 行数 **6 → 7**；记录序列：09-13, 09-14(旧), 09-16, 09-17, 09-18, 09-19, 09-14(新) |
| `get_daily_root('2026-09-14')` 仍返回 **旧（首条）**记录 | 返回 `entry_hash=ded4a103…`、`created_at=2026-09-15T00:00:00.298169+00:00`（**不是**新追加的 `3853628d…` / `2026-09-21T11:32:08`） |
| 新增行**参与**外层根链校验 | `verify_daily_root(...).root_chain_checked == 7` |
| `--roots-check all` 报告数 = 行数 | **7 条报告，7/7 OK，6 个不同日期**（09-14 出现两次，两次都描述首条记录） |

⇒ **结论**：`force=True` 追加的是**一条"再出证"记录**（新 `created_at`、新
`entry_hash`、续接外层根链、由同一密钥 ed25519 重新签名），
**但它不会成为该日的"治理根"**——治理根仍是首条。
若**确实需要**让一条新根成为治理根（即改变该日的判定依据），
**当前 API 做不到**，必须由人类裁定后另行改动 `get_daily_root` 的取值口径
（**属于判定语义变更，不在本任务权限内**）。

> 另注：本次实测中，09-14 的新根 `root_hash` 与旧根**完全相同**
> （都是 `1fb4fe20f5a3155a…`），因为叶子集合没有变化——所以这条追加是
> "**在同一条链上把该日重新出证一次**"，而不是"修正一个错的根"。
> 这一点必须如实引用，不得表述为"根被修正了"。

### 4.4 每次导入/封印前后的强制对拍

```powershell
python scripts\verify_audit_chain.py --roots-check all --stats
```

判据是 **exit 0 且 seq 连续**（`bad_seqs` 为空），**不是"条数不变"**：
条数是 append-only，只应**单调不减**。

---

## 5. 为什么这不是 bug

1. **是新口径的直接推论**：把封印定义为"封印点**之前**的该日集合"，
   就必然意味着"**封印点之前**的集合是签名的对象"；而"后来补写、却落在封印点之前"
   恰恰改变了签名的对象。旧口径（只按 seq 区间取叶）看不到这类变化，
   代价是**对 09-14 那类异日记录恒定误报 FAIL**——两者不可兼得。
2. **它检出的是真实变化**，不是噪声：机制 ①/②/③ 全部对应"签名的那个集合被改动了"。
3. **它是可处置的**：按 §4.2 追加新根即可留痕处置，无需删改历史。
4. **代码不需要改**：本约定**纯流程**，不改 `agent/audit/**` 任何一行
   （任务裁定明确"不改代码"）。
