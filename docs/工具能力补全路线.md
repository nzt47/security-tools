### B+ 档 —— 治理网/质量门的五个洞（2026-09-17 收口）

| 洞 | 后果 | 处置 |
|---|---|---|
| **审批边界"看得见、拦不住"**：`tool_gate` 的审批步骤默认只告警；唯一 fail-closed 的审批权威 `HITLManager.assess` **在生产代码里零调用方**（只有测试引用） | 91 个工具里 10 个 `needs_approval`（govern 8 + act 2，含 `shell_execute` / `generate_tool` / `run_sandbox` 三个 `critical`）在默认配置下**无人确认即可执行** —— 治理框架齐全却一条都没生效 | ✅ 接通**审批闭环**：闸门命中 ⇒ `agent/tool_approval.py` 向既有审批流挂单（`object_type=tool_call`，与审批收件箱同库同源）⇒ 返回 `APPROVAL_REQUIRED` + `approval_id` + 恢复指引 ⇒ 人工在「治理 → 审批收件箱」批准 ⇒ 模型**原样重试**即放行（**单次有效**，参数与会话绑定）⇒ 驳回则返回 `APPROVAL_REJECTED` 且带否决理由。闭环接通后 `CP_TOOL_GATE_APPROVAL_ENFORCE` **默认改为开启**，回滚＝置 0。端到端证据：`tests/unit/test_tool_approval_e2e.py` |

#### 审批闭环的操作口径（怎么用 / 怎么回滚）

| 环节 | 口径 |
|---|---|
| 触发 | 模型调用 `needs_approval` 的工具（`plane=govern` / `effect=extend` / `risk=critical`，当前 **10/91** 个）。参数级致命检测（如 `rm -rf /`）不依赖本层 |
| 模型收到什么 | `{"ok": false, "blocked": true, "error_code": "APPROVAL_REQUIRED", "approval_id": "...", "guidance": "..."}`；被驳回则是 `APPROVAL_REJECTED` + 否决理由（模型不该重试） |
| 人工在哪批 | 「治理 → 审批收件箱」（`GET /api/cp/panels/approvals/inbox`，数据源 `agent/ui_panels/data.py::approval_inbox`）。**注意**：收件箱有硬规则「缺 `undo_hint` 不出气泡」，故工具审批单的 payload 必须带 `undo_hint`——已实现，别删 |
| 怎么恢复执行 | **原样重试同一次调用**（同一工具 + 同一参数摘要 + 同一会话）。批准**单次有效**，且有 TTL（`CP_TOOL_APPROVAL_TTL_SEC`，默认 900s，与审批会话 ≤15min 同口径）；单据按参数绑定 ⇒ 换参数＝另一次审批 |
| 落盘位置 | 决策：`data/approval_records.jsonl`（审批流，本层只读不写）；消费事实：`data/tool_approval_uses.jsonl`（append-only，只做"不可重放"的减法，不制造第二真相） |
| 回滚 | `CP_TOOL_GATE_APPROVAL_ENFORCE=0` ⇒ 回到"只告警、照常放行"，不写任何文件。总开关 `CP_TOOL_GATE_ENABLED=0` 仍然压过一切 |
| 隐性路径 | 自动安装（模型调了不存在的工具名 ⇒ 市场搜索 ⇒ 安装）**同样受本边界约束**：`agent/tools/discovery_service.py` 取闸门判定，未获批准不安装 |
| 无人值守场景 | 定时/后台任务命中边界工具时不再静默执行，而是挂单等人批准（这正是审批边界对"无人值守"的意义） |

## 二、云枢会自己生成新工具吗？

**会，但此前整条链路是断的。本轮修好了三处断点。**

`generate_tool` 工具的实现是真实的、不弱的：
- 有 AST **顶层**语句白名单（`tool_generator.py:25-61`）
- 生成后跑独立子进程验证，**5s 超时强杀**
- 支持 `generate_simple`（内存）与 `generate_persistent`（落盘到 `agent/tools/custom/`）

但三处断裂让它实际上不可用：

| # | 断点 | 后果 | 本轮处置 |
|---|---|---|---|
| 1 | `category: uncategorized` ⇒ 被 `tool_router` 的分类表**静默丢弃**，关键词路由永不返回 | 用户说"你自己生成个新工具"，模型**根本看不到** `generate_tool` | ✅ 归档到 `extension` 类 + 补 10 个关键词；实测 `'你自己生成一个新工具'` 已能召回 |
| 2 | `lifecycle_manager` 调用的 `init_dynamic_tools_persistence` / `load_dynamic_tools` **在 `agent/tools/__init__.py` 里根本不存在**（550 行 0 个 def） | 每次启动 AttributeError 被吞成 warning ⇒ **自生成的工具重启即失** | ✅ 新建 `agent/tools/persistence.py` 实现真实持久化：扫 `agent/tools/custom/**`、导入、调 `register_all()`、维护台账 |
| 3 | 生成的工具**没有 `plane/effect/risk` 声明** ⇒ 被主线装配器 **fail-closed 拒绝** | 即使注册成功也永远轮不到它 | ✅ 加载时用**注册表差值**反推"这个模块注册了哪些工具"，自动补写 `data/tool_definitions/<name>.yaml`，默认 `plane=act / effect=execute / risk=critical` |

### 为什么默认定 `risk: critical`
AST 白名单**只校验顶层语句，函数体不受限**（`tool_generator.py:29` 自述）——
生成即拥有完整 Python 能力。这与 `generate_tool` 自身的定级一致，也因此自动
落入 `needs_approval` ⇒ **自生成工具必须经过人工确认才能被调用**。

### 完整的自主进化闭环（现在通了）

```
云枢发现缺能力
  → generate_tool（govern 平面，需确认）写代码并落盘
  → 重启/热加载时 load_dynamic_tools() 扫到并注册
  → 自动补 plane/effect/risk 声明
  → 进入主线装配的候选池（govern 平面，默认需确认）
  → 可被 harness / digital_life 这类开启治理的主线调用
```

### 自生成工具的验证门（已补上，2026-09-17）

原先"一旦写入就生效，中间没有门"，现已实现 `agent/tools/persistence.py::verify_generated_tool()`，
写入注册表前依次过三道：

1. **语法与函数存在性**（最先跑——放在安全校验之后会让 `SyntaxError` 自己先抛出来，把语法问题误报成安全问题）
2. **安全校验**（顶层语句白名单）
3. **调用探针**（真的调一次，确认能返回）

未过闸的条目不落注册表，并记入台账 `rejected` 段（可审计"生成过什么、为什么被拒"）。

> **边界说明**：这是**质量门**，不是安全边界。它拦的是"生成的工具是坏的/跑不起来的"；
> 而对"能跑但危险"的函数体，靠的是 `plane=govern` + `risk=critical` ⇒ `needs_approval`
> 进人工确认。两者不能互相替代。

### 完整的自主进化闭环（现在通了）

```
云枢发现缺能力
  → generate_tool（govern 平面，需确认）写代码并落盘
  → verify_generated_tool 三道门（语法 → 安全 → 调用探针）
  → 重启/热加载时 load_dynamic_tools() 扫到并注册
  → 自动补 plane/effect/risk 声明
  → 进入主线装配的候选池（govern 平面，默认需确认）
  → 可被 harness / digital_life 这类开启治理的主线调用
```
