# 云枢工具能力补全路线

> 回答两个问题：**① 全方位的 Agent 还缺什么工具？② 云枢会自己生成新工具吗？**
> 依据：`docs/工具集评估与重分类报告.md` 的全量核验。

---

## 一、还缺什么工具（按"卡不卡住事"排序）

### A 档 —— 缺了就没法当"能自己干活的 Agent"（本轮已补大半）

| 工具 | 状态 | 为什么必需 |
|---|---|---|
| `git` | ✅ 本轮新增 | 全仓有 `.git`/`.github`/hooks/发布流程，却**没有一个 git 工具**——只能裸跑 `shell_execute`，而 shell 桶限流 0.2/s 且在多域请求里会被饿死 |
| `run_tests` | ✅ 本轮新增 | 有 `pytest.ini`/`run_tests.py`/pre-commit，没有可调用的测试工具。"改完并验证"这个闭环缺一半 |
| `apply_patch` | ✅ 本轮新增 | 只有 `edit`（定点替换）+ `diff_files`（只比较）。**能读 diff 不能应用 diff** |
| `run_sandbox` | ✅ 本轮注册 | 实现质量高（独立 spawn + 超时强杀 + 逃逸预检）却从未注册为工具 |
| `browser_navigate` / `browser_screenshot` | ✅ 本轮注册 | 实现完整、被大量单测覆盖，却从未注册——只是缺一行注册 |
| `look_at_screen`（OCR/视觉） | ✅ 本轮注册 | 同上，`VoiceVision` 已实现 |
| `get_clipboard` / `set_clipboard` | ✅ 本轮注册 | 同上 |
| `workspace_*`（4 个） | ✅ 本轮注册 | 同上 |
| `read_pdf_tables` | ✅ 本轮注册 | PDF 表格抽取器已实现未注册——而"从 PDF 提数据"是高频需求 |
| `list_mcp_connections` | ✅ 本轮注册 | `mcp_connector.list_connections()` 已实现，但没有工具暴露它 ⇒ **Agent 看不到哪些 MCP 连接是活的** |
| `weekly_report` | ✅ 本轮注册 | 报表生成器已实现未注册 |

### B 档 —— 不缺就"能用但笨"

| 工具 | 建议 | 理由 |
|---|---|---|
| `sqlite_query` | **建议尽快补** | 仓库里到处是 sqlite（`data/*.db`、`tool_fewshot.db`、`tool_trace.db`），Agent **无法查自己的运行数据**。只读模式 + `PRAGMA query_only` + 表白名单即可，风险低收益高 |
| `notify`（通知/提醒） | 建议补 | `schedule_task` 语义是"周期重复执行"，**不是"到点提醒我"**。缺一个能主动触达用户的通知原语，自主运行就没人知道结果 |
| `lint` / `typecheck` | 建议补 | 有 ruff/mypy 配置（`.ruff_cache`/`.mypy_cache`）却无工具；`humanize_zh` 是文风检测，不是代码检查 |
| `todo_write` 落盘 | **建议改** | 现描述直言"状态仅保存在当前会话内存中，不落盘"⇒ 会话一结束计划就没了。跨会话任务需要有持久化 |
| `fan_out`（并行多 Agent 编排） | **建议补，且优先级高** | `delegate` 是**串行单发**。要做"不同 Agent 各管一条线并同时干活"，缺一个按主线并行派发的原语。底层 `DelegationExecutor.execute_many(max_concurrency)` 已存在，是接线工作而非新建 |

### C 档 —— 到了再说

RSS/Atom 订阅、容器/K8s 工具、日历/日程、通用带凭据的第三方 API 调用工具、符号级重构（LSP/AST）。

### 已补的"不是缺实现，而是缺注册"
本轮把 9 项已实现却未接线的能力接了线（见 A 档后 6 行）。这类问题的修复成本≈0，
但此前一直躺在代码里——**"已实现未注册"和"未实现"在用户体验上没区别**。

## 二、云枢会自己生成新工具吗？

**会，但此前整条链路是断的。本轮修好了三处断点。**

`generate_tool` 工具的实现是真实的、不弱的：
- 有 AST **顶层**语句白名单（`tool_generator.py:25-61`）
- 生成后跑独立子进程验证，**5s 超时强杀**
- 支持 `generate_simple`（内存）与 `generate_persistent`（落盘到 `agent/tools/custom/`）

但三处断裂让它实际上不可用：

| # | 断点 | 后果 | 本轮处置 |
|---|---|---|---|
| 1 | `category: uncategorized` ⇒ 被 `tool_router` 的分类表**静默丢弃**，关键词路由永不返回 | 用户说"你自己生成个新工具"，模型**根本看不到** `generate_tool` | ✅ 归档到 `extension` 类 + 补 10 个关键词；实测 `'你自己生成一个新工具'` 已能召回 |
| 2 | `lifecycle_manager` 调用的 `init_dynamic_tools_persistence` / `load_dynamic_tools` **在 `agent/tools/__init__.py` 里根本不存在**（550 行 0 个 def） | 每次启动 AttributeError 被吞成 warning ⇒ **自生成的工具重启即失** | ✅ 新建 `agent/tools/persistence.py` 实现真实持久化：扫 `agent/tools/custom/**`、导入、调 `register_all()`、维护台账 |
| 3 | 生成的工具**没有 `plane/effect/risk` 声明** ⇒ 被主线装配器 **fail-closed 拒绝** | 即使注册成功也永远轮不到它 | ✅ 加载时用**注册表差值**反推"这个模块注册了哪些工具"，自动补写 `data/tool_definitions/<name>.yaml`，默认 `plane=act / effect=execute / risk=critical` |

### 为什么默认定 `risk: critical`
AST 白名单**只校验顶层语句，函数体不受限**（`tool_generator.py:29` 自述）——
生成即拥有完整 Python 能力。这与 `generate_tool` 自身的定级一致，也因此自动
落入 `needs_approval` ⇒ **自生成工具必须经过人工确认才能被调用**。

### 完整的自主进化闭环（现在通了）

```
云枢发现缺能力
  → generate_tool（govern 平面，需确认）写代码并落盘
  → 重启/热加载时 load_dynamic_tools() 扫到并注册
  → 自动补 plane/effect/risk 声明
  → 进入主线装配的候选池（govern 平面，默认需确认）
  → 可被 harness / digital_life 这类开启治理的主线调用
```

**仍缺一环（建议下一步）**：生成后没有"自我验证"步骤——应该先跑
`run_sandbox` 里的探针用例确认新工具真的可用，再写入正式注册表。
现在是一旦写入就生效，中间没有门。

## 三、优先级建议

1. **`fan_out` 并行多 Agent** —— 让"多 Agent 各管一条线"从概念变成能同时干活
2. **`sqlite_query`** —— 让 Agent 能查自己的运行数据（低风险高收益）
3. **`todo_write` 落盘 + `notify`** —— 让长任务能跨会话、能主动汇报
4. **自生成工具的验证门** —— 生成 → 沙箱验证 → 才入注册表
5. `lint`/`typecheck`、RSS、日历等按需补
