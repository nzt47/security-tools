# 云枢分身装配单

> 一句话：**派一个分身之前，它到底拿到什么** —— 工具集、技能面、提示词片段，
> 全部收敛在**一份只读装配单**里，由唯一入口 `resolve_subagent_assembly()` 产出。
>
> 唯一实现：`agent/subagent/assembly.py`；
> 唯一入口：`agent/tools/fan_out_tools.py`（并行多线委派）；
> 只读投影（UI 上的「分身面」）：`agent/server_routes/routes_agent_lines.py`
> 的 `_subagent_assembly_payload()` —— 与派发路径调**同一个** `resolve_subagent_assembly()`，
> 只加 `available` / `reason` / `semantics` / `semantics_note` 四个说明字段，不另立口径；
> **它用哪个模型 / 多热**（装配单之外的第二件事）：`agent/subagent/llm_factory.py::resolve_subagent_llm()`
> —— 空=跟随母体、指定=经 `LLMService.with_model()` 派生**独立实例**、失败=回退母体并如实记 `source`；
> `llm_temperature` 由 `TemperaturePinnedLLM` 在**调用面**钉住（`None` = 不干预，不是 0.0）；
> 安全边界：provider / api_key / base_url 恒取部署配置，分身只能选同 provider 下的模型名与温度；
> **它以什么身份做**（装配单之外的第三件事）：`agent/subagent/role_templates.py` 的**受控角色模板**
> —— 默认档只用词表正文，自由文本必须显式开启 `template+text`（只进 ②约束）或 `full-system`
> （进 system prompt：红档 + 审计），见 §10；
> 工具侧主线装配见 `docs/主线装配指南.md`（本文只讲"分身"这一侧的后半程）。

---

## 1. 一句话模型

```
主线档案（身份/权重/技能包/提示词片段）  →  分身装配单（只读）  →  委派契约 + 逐任务信封
data/agent_lines/<id>.yaml                  SubagentAssembly        DelegationContext / results[*]
```

装配单回答四个问题，**一个都不多**：

1. 这个分身能调用哪些工具？（`tools` / `needs_approval`）
2. 这个分身被允许使用哪些技能？（`skills` / `skills_mode`）
3. 这个分身该带着哪段本线交付纪律走？它是谁的？（`prompt_note` / `prompt_source`）
4. 上面三条**凭什么**？（`note` / `skills_note`，人读、如实、可审计）

**本模块不做判定，只做收敛**：装配算法在 `agent/lines/assembler.py`，
权限矩阵在 `agent/security/actor_matrix.py`（经 `agent/subagent/toolset.py`），
技能包在 `agent/lines/skillpack.py`，提示词角色在 `agent/prompt_manager/roles.py`。
抄一份判定 = 造第二份口径，两份迟早分叉。

## 2. 装配单字段表

| 字段 | 类型 | 含义 | 权威来源 |
|---|---|---|---|
| `line_id` | str | 生效主线 id；空串 = **未点名** | 调用方解析（`task.line` → 全局激活指针 → 空） |
| `mode` | str | `line` / `default-readonly` | 本模块 |
| `tools` | tuple[str, ...] | 授权工具名（已去 govern、已去 §5.7 机制 3 硬禁） | `assemble()` + `SubAgentToolset.hard_denied()` |
| `needs_approval` | tuple[str, ...] | 其中需人工确认的（⊆ `tools`） | `data/tool_definitions/*.yaml` 的 plane/effect/risk |
| `note` | str | 工具面的人读说明（剔除了谁、为什么） | 本模块 |
| `skills` | tuple[str, ...] | 本线技能包里允许下发给分身的技能 id = **授权面** | `line_skill_pack()` → `SkillPack.filter()`，再去私人记忆类 |
| `skills_mode` | str | `unrestricted`（本线未收紧）/ `whitelist`（按本线 `skills:` 声明做减法） | `SkillPack.mode`（不另立词表） |
| `skills_note` | str | 技能面人读说明（含"未收紧"/"取不到标签"等**事实**） | 本模块 |
| `prompt_note` | str | 本线 `prompt_note` 经提示词角色层合成的**正文** | `PromptFragment(role="line")` + `compose_fragments()` |
| `prompt_source` | str | 该片段的来源标识（如 `line:engineering`）；无片段时为空串 | 同上（`ComposedPrompt.sources()`） |
| `to_dict()` / `__len__()` | — | 面板/日志投影；`len()` = 授权工具数 | 本模块 |

约束：字段只增不改（既有 5 个字段的语义与顺序不动），新增字段全部有默认值，
因此旧的构造点与 `to_dict()` 消费方逐字兼容。

## 3. 两条失败语义（与主智能体**相反**）

| 情形 | 主智能体侧 | 分身侧（本模块） |
|---|---|---|
| **没点名** line | 等于没装线（旧行为） | 只读默认集 `mode="default-readonly"`：`_default_subagent_tools` 去掉 govern 平面、再去掉 §5.7 机制 3 硬禁项 |
| **点了名却装不上**（不存在 / 停用 / 档案损坏） | 回退旧路径 | **抛 `LineUnavailable`**，该任务就地失败，**绝不回退成全量授权** |

为什么不冲突：主智能体那条纪律管的是"**没点名**"；分身侧要防的是
"**点了名却装不上**"被当成"没点名"——那等于用一个坏档案把子代理的权限面悄悄
放到最大，正是这套治理要防的事。取证：

- 未点名 ⇒ 工具集 == `subagent_tools._DEFAULT_SUBAGENT_TOOLS` 且不含 `write_file` / `edit` / `shell_execute`；
- 三种不可用 ⇒ 逐个 `pytest.raises(LineUnavailable)`，一个装配单都不返回。

对应用例：`tests/unit/test_subagent_assembly.py::TestDefaultReadOnly` 与
`TestLineUnavailable`（`tests/unit/test_fan_out.py` 的
`TestLineUnavailable` 从工具侧锁同一条语义）。

**【技能面不随工具面回退】** 未点名时技能面走 `resolve_skill_pack(None)`
（"未装线 ⇒ 不限制"，技能侧自己的纪律），**不**再去读一次全局激活指针：
否则会出现"工具走只读默认集、技能面却按某条线收紧/放行"的错配。

## 4. 技能为什么只作"授权面"随契约下发，而不注入正文

下发的只有**技能 id 集合**（`skills`）+ 模式（`skills_mode`），
随 `DelegationContext.metadata` 物化进 task_file；**技能指令正文一个字符都不进提示词**。

三条理由（按强度排序）：

1. **§5.7 机制 1/2**：子代理的 system prompt 是云枢自有固定文本
   （`agent/subagent/executor.py` 的 `DELEGATE_SYSTEM_PROMPT`），
   不得拼接外来内容。技能正文由技能子系统在**主智能体**侧按意图注入
   （`agent/skills_mgmt/context_injector.py`），分身不是它的旁路。
2. **谁注入谁负责**：技能有独立的可调用性口径（`data/skill_callability.yaml`）与
   注入时机；装配单把正文搬过来，等于在委派链上开第二条注入通道，
   两条通道的预算/裁剪/审计各算一份。
3. **授权面 ≠ 内容面**：分身需要知道的是"我被允许用什么"（可自检、可回给上游），
   不是"这些技能的操作指引长什么样"。真要用时，走既有的技能执行/注入链路。

**分身专属收紧（与 §5.7 机制 3 同源）**：子代理不含私人记忆读写，因此本线技能包里带
**私人记忆 / 人格 / 生命轨迹**性质的技能不下发给分身。判据**数据驱动**（看技能标签，
不看 id 黑名单）：

- 标签来源：`agent/skills_mgmt/loader.py` 的 `SkillLoader.list_all_metadata()`
  （= `data/skills_repo/<id>/skill.md` 的 front matter，人工声明处，官方读取入口带缓存与逐技能容错）；
- 判定：`标签 ∩ {memory, persona, lifetrace, life_trace, 记忆, 人格, 生命轨迹} ≠ ∅`
  **且** `标签 ∩ {knowledge} = ∅`（后者与 `agent/subagent/toolset.py` 的
  「`memory` 且非 `knowledge`」同源：`kb_*` 那类**共享知识库**不是私人记忆，
  一并剔除会掐掉 knowledge 线子代理的检索/入库能力——那是过度收紧，不是最小暴露）；
- 不选主轨 `data/skills_mgmt.json` 的理由：那里的标签是
  `SkillsMgmtService._derive_tags` 从 content_type/category **自动派生**的检索词，
  不是人工语义声明；拿它当安全判据等于把"检索得像不像"当成"是不是私人记忆"。
- **取不到标签 ⇒ 不收紧**（`tag_index is None` 或该 id 无标签），
  但在 `skills_note` 里如实写"未收紧（取不到标签）"并点名是哪几项。
  判据是"声明出来的事实"：默认收紧会变成静默的能力剥夺，默认不收紧至少可审计。

【当前数据现状（如实）】主轨独有的 7 个技能（如 `engineering-test-delivery`）
在文件轨没有 front matter，因此拿不到标签 ⇒ 不收紧并在 note 里逐项点名；
`data/skills_repo` 里 `context_aware` / `emotion_expression` /
`proactive_suggestion` / `safety_guard` / `voice_interaction`
的 tags 为空 ⇒ 同样不收紧。**补标签即生效，不需要改代码**（这正是"数据驱动"的意义）。

> ⚠️ **这条局限的实测覆盖面（当前只有 memory_summary 一条真的被挡住）与两条收严路径，
> 见 §8.1 的独立登记**——不要把它读成"人格类已经挡住"。

## 5. prompt_note 为什么进 constraints（②约束）

`fan_out_tools._prompt_constraint()` 在本线 `prompt_note` 非空时，
往该任务的 ②约束里追加**一条**带来源标注的文本：

```
constraints = ["只读仓库，不得修改任何文件"]           # 调用方原样
            + ["[主线 engineering] 本线的交付标准是"改完并验证"：…"]   # 本线片段 + 来源
```

为什么是 constraints：

1. **不能进子代理的 system prompt**：那是云枢自有固定文本（§5.7 机制 1/2 不得拼接外来内容），
   主线档案是**配置**，不是云枢本体；
2. **constraints 是父体自撰的内部文本**，本来就随 task_file 物化给子代理
   （`DelegationContext.to_dict()` → task_file），子代理**真能读到**；
3. "应该怎么交付"在本工具里正是 ②约束（`ELEMENT_CONSTRAINTS`）的位置，
   塞进别的要素会与八要素契约的语义打架（八要素的必填项与 JSON Schema 一个字都没动）。

实现纪律：

- **先复制再追加**（`constraints = list(elements["constraints"])`）：elements 里的列表
  就是调用方入参的同一个对象，就地 append 会改写调用方参数，并让复用的第 2 个任务
  看到第 1 个追加过的内容（重复追加 + 串线）；
- **未装线 / 字段为空 ⇒ 行为与今天逐字一致**：不追加任何东西，`metadata["prompt_source"]`
  给空串（键始终在，消费方不必写 `.get` 分支），信封 `prompt_note_applied=False`；
- 来源标注形如 `[主线 engineering]`，取自装配单的 `prompt_source`
  （由提示词角色层合成），本模块不自己拼一个形似的来源串。

## 6. 决策记录：为什么不给 `SubagentConfig` 加 `line` 字段

**背景**：`agent/subagent/container.py` 的 `SubagentConfig` 现在带
`name` / `model_id` 等字段，而"这个分身是哪条线的"只出现在
`DelegationContext.metadata["line"]`（以及 `authorized_capabilities` 等溯源字段）里。
自然会被问：为什么不给配置对象也加一个 `line`？

**决定：不加。装配溯源统一走委派契约。**

理由：

1. **一处记着线，就不会只更新一处**：`SubagentConfig` 是"分身怎么跑"（名字/模型/容量），
   `DelegationContext` 是"这一次委派是什么"（八要素 + 溯源）。线属于**这一次委派**，
   不属于"分身进程本身"——同一个分身进程模型可以服务不同线，把线写进配置就把它钉死了。
2. **两份记录必然分叉**：一旦 `SubagentConfig.line` 与
   `ctx.metadata["line"]` 同时存在，总有一天只更新其中一处，
   于是"日志说 dev、授权集是 engineering"，而这种 bug 在评审里看不出来
   （两处都是"看起来对"的字符串）。溯源字段必须**单点**。
3. **权威方向明确**：授权集与技能面的**权威来源**是逐任务工厂
   （`execute_many(tools_for=…, authorized_for=… )`，见 `agent/subagent/executor.py`），
   `metadata` 只是"随 task_file 物化给子代理"的那一份投影。
   再往 `SubagentConfig` 里加一份，等于引入第三个来源，而它既不是权威也不是投影。
4. **容器委派/单发 delegate 等其它分身入口复用同一条规矩**：它们各自构造
   `SubagentConfig`（形态不同），但都产出 `DelegationContext`；
   把溯源放契约里，等于对所有入口一次性成立。

**代价（如实）**：看一个"正在跑的分身"时，配置对象本身答不出它是哪条线，必须看它手里那份契约。
接受这个代价：可观测性靠日志/信封（`results[*].line` /
`results[*].prompt_source`）补齐，而不是靠复制一份状态。

## 7. 逐任务信封（如实回报）

`fan_out` 的 `results[*]` 逐条新增四个字段（八要素 Schema 未改）：

| 字段 | 含义 | 主线不可用时 |
|---|---|---|
| `skills_granted` | 该任务被允许的技能 id（授权面） | `[]` |
| `skills_mode` | `unrestricted` / `whitelist` | `""` |
| `prompt_source` | ②约束里那条本线片段的来源 | `""` |
| `prompt_note_applied` | 是否**真的**追加了约束（布尔） | `False` |

"空"与"没查"是两件事：失败任务给的是**明确的空值**，而不是缺字段。

## 8. 已知边界与局限（未做/未验）

### 8.1 【局限·未覆盖】按标签收紧的实际覆盖面目前只有 1 条 ← 后续工作

**这不是"已覆盖"，是"机制到位、数据没到位"。** 2026-09-23 实测（engineering 线声明了
11 个技能 = 4 个指令型 + 7 个 persona）文件轨 front matter 的标签现状是：

| 技能 | front matter tags | 装配结果 |
|---|---|---|
| `memory_summary` | `(memory_summary, summary, compression, memory, 记忆摘要, …)` | **剔除**（命中 memory） |
| `self_reflection` | `(self_reflection, reflection, review, self_check, 自我反思, …)` | 保留（有标签但不含私人语义） |
| `context_aware` / `emotion_expression` / `proactive_suggestion` / `safety_guard` / `voice_interaction` | **空** | 保留 + 在 `skills_note` 里点名"未收紧（取不到标签）" |
| 4 个指令型（`engineering-test-delivery` 等，主轨独有） | 无 front matter | 保留 + 同上（见下一条） |

⇒ 也就是说：**"私人记忆/人格类技能不下发给分身"这句话，当前实际只对 `memory_summary` 成立**；
另外 5 个 persona 技能（以及主轨独有技能）目前是"按纪律不收紧 + 如实记账"，**没有被挡住**。
覆盖率低的根因是标签本身：7 个 persona 技能里 5 个的 `tags` 为空。

要真正收严，两条路（都属后续工作，二选一或并用）：

1. **补数据**：给 `data/skills_repo/<id>/skill.md` 的 front matter 补 `persona` /
   `lifetrace` 等标签 —— 判据是数据驱动的，**补完即生效，不需要改代码**
   （`tests/unit/test_subagent_assembly.py::TestSkills::test_真实数据上收紧判据的两侧`
   的数据事实锁会因此变红，需要同步更新那份清单）；
2. **改判据形态**：放弃数据驱动、改用显式清单（例如档案里的 `no_subagent: true`）——
   代价是新增技能要人工登记，漏登记就静默不下发/误下发，本模块当初选标签正是为了避开这个。

**为什么现在不选"默认收紧"**：标签取不到时默认收紧会变成静默的能力剥夺（使用者只看到
"某个技能莫名其妙不生效"），而默认不收紧至少是**可审计**的：`skills_note` 里点名了
是哪几项、为什么没判。这个取舍是刻意的，见 §4。

### 8.2 其它边界

- **技能标签覆盖面**：只覆盖文件轨（见 §4）。主轨独有技能（如 `engineering-test-delivery`）
  拿不到标签 ⇒ 不收紧 + 记账。
- **技能正文不注入**：分身"被允许用某技能"与"它真的用了某技能"之间，
  仍隔着既有的技能执行链路（本装配单不参与）。
- **`SubagentConfig` 无 line 字段**：是有意为之（§6），不是漏做。
- **未跑全量测试**：本文档的取证只覆盖 `tests/unit/test_subagent_assembly.py` /
  `tests/unit/test_fan_out.py` / `tests/unit/test_subagent_toolset.py` 与
  `-k 'subagent or delegation'` 这一档（未跑全量 tests/unit）。

## 10. 角色（受控模板）与三档显式开启（2026-10-08 交付）

> **"每个分身独立角色"在本仓只有一条合法做法**：角色正文必须是云枢自有的**受控模板**
> （`agent/subagent/role_templates.py::ROLE_TEMPLATES`，进仓可审），经提示词角色层
> `PromptFragment(role="delegate_role")` 合成。因为 §5.7 机制 1/2 定死：**外来文本永不进
> system prompt**（分身的 system prompt 是 `executor.DELEGATE_SYSTEM_PROMPT` 这段自有固定文本）。
>
> 反面做法（也是一种"很省事"的做法）是在创建契约里加一个 `system_prompt` 字段直通执行器 ——
> 那会在一条 HTTP 路径上静默绕开机制 1/2，而所有既有守卫测试仍会全绿（它们查的是"已知注入点"，
> 不是"有没有新增注入点"）。本模块存在的意义就是让那条路根本不存在。

### 10.1 三档（默认最小权限 → 高等级需显式开启 → 开关进审计与 UI 徽章）

| `role_mode` | 语义 | 默认 | 审计 | UI 徽章 |
|---|---|---|---|---|
| `template` | 只用词表里的模板正文 | ✅ | 否 | 灰（受控模板） |
| `template+text` | 模板正文进 system prompt；自由文本**只进 ②约束**（子代理在 task_file 里读到） | 显式开启 | 是（`subagent.role.tier`） | 琥珀（模板+文本） |
| `full-system` | 自由文本**进 system prompt**（打破机制 1/2） | 显式开启 | 是 | **红档** |

`full-system` 不是"更高级所以更好"：它取消了机制 1/2 对这条路径的保护，因此必须
**显式开启 + 审计留痕 + 红档徽章**（沿用主线档案 `allow_govern` 的三缺一不可纪律）。

### 10.2 三条失败语义（fail-closed，不静默降级）

| 情形 | 行为 | 为什么 |
|---|---|---|
| `role_template` 为空 | 返回 `None`（无片段），执行器 system prompt **与改动前逐字相同** | 未装角色 = 旧行为；不造"默认通用角色"这种看不见的注入 |
| 点名了但不在词表 | `UnknownRoleTemplate`（创建/委派端点 400） | 不回退默认模板 —— 那是"用错身份也照跑"，与主线档案"点名装不上就失败"同源 |
| `role_text` 非空但档位是默认 `template` | `RoleTextNotEnabled`（400） | **不静默忽略** —— 静默忽略会让使用者以为这段文本生效了 |
| 有 `role_text` 但没 `role_template` | 400（自由文本没有受控来源可依附） | 自由文本独自进分身提示词正是机制 1/2 禁止的形态 |

### 10.3 自由文本的去处（唯一的两个合法槽位）

* `template+text` ⇒ ②约束，且带来源标注（形如 `[角色模板 code_review] …`，
  与 `fan_out_tools._prompt_constraint` 的标注纪律同款）；
* `full-system` ⇒ system prompt 正文（模板正文在前、自由文本在后），**不重复**进 ②约束
  （同一段文本在两个槽位各出现一次，使用者无从判断哪份算数）。

### 10.4 守卫（可证伪，回退产品逻辑立刻红）

| 不变量 | 用例 |
|---|---|
| 词表正文无占位符、无自由文本直通 system prompt 的路径（对每一条模板 × 每一档穷举） | `test_subagent_role_templates.py::TestNoFreeTextPath` |
| 未显式开启时 `role_text` 绝不出现在 `executor.execute` 的 `system_prompt` **实参**里 | `test_subagent_role_wiring.py::TestDelegateRouteRole` |
| 显式开启后执行器写 `subagent.role.tier`，并把"记上了没有"放进 `outcome.role_audit.recorded` | `test_subagent_role_wiring.py::TestExecutorWiring` |
| 角色片段真的到达 LLM 调用面（基座在前、片段在后） | `test_subagent_role_wiring.py::test_内部LLM执行器_基座与角色片段都交给LLM` |
| 热更新不得把已有 `role_text` 静默清空 | `test_subagent_role_wiring.py::TestCreateAndReloadRole` |

前端（`yunshu-ui/src/pages/hub/workshop/agents.tsx`）只渲染后端给的 `role` 投影
（模板标题 / 档位 / 红档），**不自己维护第二份模板清单**；用例见 `agents.test.tsx`。

### 10.5 未做（避免"以为做了"）

* **跨 provider / 自带密钥**：不在本轮。角色模板只决定"是谁"，不碰 provider / api_key / base_url
  （那三项恒取部署配置，见 §1 抬头与 `llm_factory` 的模块 docstring）；
* **`scoped` 记忆档**（分身自带私人记忆域）：不在本轮，见设计文档 §3 与 P3；
* **外部 CLI 通道的角色**：`system_prompt` 由对端进程决定，`ChannelInvocation.system_prompt`
  只被内部 LLM 执行器消费（外部 CLI 忽略它）—— 这是如实的现状，不是"忘了接"。
