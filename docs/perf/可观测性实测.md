**归因判定（来自探测详情原文，非推测）**：

- **L3 长期 `null` 的直接原因是"无调用计数"** —— 与本文第 2 节实测**完全互证**：
  `yunshu_tool_calls_total` 与 `yunshu_llm_calls_total` 在 `/metrics` 上

  但全仓无任何 `.inc()` 写入点）。⇒ **L3 的 `null` 是埋点缺失导致的，不是 Loki 导致的。**

  但 L3/L4 的探测详情明确指向**指标侧无数据**。

> 因此：**L3/L4 长期 `null` 不能归因于 Loki**；根因是 `yunshu_tool_calls_total` /
> `yunshu_llm_calls_total` 无写入点 + 业务指标端点零样本。修 Loki 不会让 L3/L4 变绿。

阅读被遮蔽 handler 的实现（`routes_logging.py:1142-1157`）发现**两处独立缺陷**：


## 11. 方法学局限（如实声明）

1. **未做到端到端告警触发**：Prometheus `:9090` 未运行，因此 E10 的"人为触发 → 告警生效"
   以**手工 PromQL 求值**替代。该替代证明的是**可求值性**，不是链路可用性。
2. **`histogram_quantile` 用静态近似**：无 `rate(...[5m])` 时间窗，故 P95/P99 数值为
   **累积快照分位**，非滚动窗口分位。流量平稳时接近，但**不能等同于 Prometheus 结果**。
3. **`/metrics` 为单次抓取快照**：指标为累加型 Counter，本文数值是**该时刻的累计值**，
   不同时刻抓取会得到不同数字；结构性结论（哪个族存在/缺失）稳定，具体数值不稳定。
4. **`_metrics` 单例统计基于静态 grep**：判据是 `_metrics = BusinessMetricsCollector()` 字面量；
   若存在其他等价写法（如别名导入后实例化）可能漏计。已用 `observability.py` 文件全量清点交叉核对
   （27 个文件 / 25 个命中 / 2 个例外，加总吻合）。
5. **看板无源指标判定依赖"实测指标名集合"**：若某指标由未运行的组件（如 kube-state-metrics）
   在目标环境提供，则它在**本机**判为无源，但在**目标 K8s 环境**可能有源。
   已在 7.2 中按"旧命名 / K8s 组件 / 未加载录制规则"分类说明，便于区分。
