## 0. 口径与纪律（**先读这一节再看数字**）

| 项 | 本报告的做法 |
|---|---|
| 合成 vs 生产 | 所有扩容数字都是**合成负载**（`scripts/bench_capregistry.py::_synthesize`，与 TASK-05 同一套）。合成只能回答"数据结构在 N 量级的行为"，**不能**回答"真实 N 条能力下的表现" |

| 应用级日志 | 压测前把 `agent.tool_router_hybrid` 等 logger 压到 `CRITICAL`。`HybridRetriever._query_locked` 每次查询写 4 条 `logger.info`，开着会把日志格式化成本算进"查询耗时"。**生产若开 INFO 会另有开销** |
| 机器状态 | 本机**同时运行着用户的真实后端**（`python app_server.py`，PID 980，已连续运行 20 小时）。此外并行会话也在跑自己的基准脚本 ⇒ 采集于**并发负载**下 |

## 1. BM25 索引构建 O(n²)：验证 → 实测 → 修复（E1p）

### 1.1 缺陷位置（已核实，行号为修复后）

| 文件:行 | 原代码 | 复杂度 |
|---|---|---|
| `agent/tool_router_hybrid.py:436`（原 370） | `total_length = sum(self._doc_lengths.values())`（在 `add_document` 内） | **单次插入 O(n)** |
| `agent/tool_router_hybrid.py:456`（原 384） | 同款全表重算（在 `_remove_document_locked` 内，覆盖写路径每次都会走到） | 同上 |
| `agent/tool_router_hybrid.py:647`（原 573，**第二处**） | `self._pending = [(d, c) for d, c in self._pending if d != doc_id]`（`EmbeddingIndex.add_document` 的 pending 去重） | **单次插入 O(pending)** |

三处都在 `HybridRetriever.rebuild()`（索引构建的唯一生产路径，`agent/tool_router_hybrid.py:1013` 起）
的循环体内，所以"构建 n 个工具的索引"= O(n²)。第一处是任务点名的；第二、三处是本次实测中
**发现的同类项**（不修则 build 曲线仍不线性）。

### 1.2 修复方式（对外行为不变）

* 新增累加字段 `_total_doc_len`：`add_document` 用 `+=`，`_remove_document_locked` **先减后删**
  （顺序反了会取不到长度、总长永久偏大），`clear()` 一并归零（否则下一轮 `_avg_doc_length` 带历史残留）；
  新增只读属性 `total_doc_length`（`agent/tool_router_hybrid.py:509`）作为运行时观测口。
* `EmbeddingIndex` 增加与 `_pending` 同步维护的 `_pending_ids` 集合：**不存在就直接 append（O(1)）**，
  只有真出现重复 doc_id 时才走原来的过滤分支 ⇒ 语义逐字等价、复杂度降为 O(1)。
  三处（append / filter / 两个 `clear()`）都必须成对更新，代码里逐处写了 why。
* **未改动**：BM25 打分公式、`_avg_doc_length` 的取值口径、分词器、检索排序、`_total_docs` 语义。
  没有任何新环境变量/开关 ⇒ 不涉及 `agent/settings/registry.py` 登记（D5 不适用）。

### 1.3 退化曲线（前 / 后）

负载：由 `data/tool_index.json` 的**真实 90 条工具定义循环扩增**（token 长度分布与真实一致，语义高度重复）。
进程模型：每规模一个**冷子进程**；每规模重复 3 次取**中位数**；两种实现**按规模交错测量**、
并逐规模交替先后顺序（否则"后测的那一组"会把机器负载漂移吃进差值——首轮分块测量就出现了约 14% 的系统性偏差）。

| n | 修复前 总耗时 | 修复后 总耗时 | 差值 | 占修复前 | 加速比 | 修复后 单次均摊 |
|---|---|---|---|---|---|---|
| **90**（真实规模） | 2.47 ms | 2.92 ms | −0.45 ms | 噪声带 | 0.84× | 0.033 ms |
| 1,000 | 36.72 ms | 30.15 ms | 6.57 ms | 17.9% | 1.22× | 0.030 ms |
| 5,000 | 278.69 ms | 181.92 ms | 96.77 ms | 34.7% | 1.53× | 0.036 ms |
| 10,000 | **731.41 ms** | **342.23 ms** | 389.19 ms | **53.2%** | **2.14×** | 0.034 ms |

**曲线形状（比总耗时更有信息量）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| log-log 拟合指数（1.0=线性，2.0=二次） | **1.202** | **1.020** |
| 两项拟合 `t(n)=a·n+b·n²` | a=37.64 µs/条，**b=+3.554 ns/条²** | a=37.47 µs/条，**b=−0.319 ns/条²**（≈0，无二次项） |
| 二次项超过线性项的规模 `n*` | **≈ 10,592 条** | ∞（无二次项） |
| n=10,000 时"末 10% 单次插入 p50 / 首 10%" | **3.01×**（单次插入随索引变长而变贵） | **0.95×**（与已插入条数无关） |
| n=10,000 单次插入 p50 | 0.0579 ms | 0.0239 ms |

**结论（本次实测的口径）**

1. O(n²) 真实存在，但**在真实 90 条规模上完全看不见**：90 条时前/后都在 ~3 ms，
   修复的收益为负值（噪声）。这与 TASK-05"真实 114 条最差 p99 = 33.60 ms 达标"并不矛盾——
   那是**查询**侧的信封延迟，与本处**构建**侧无关。
2. 二次项在 **≈1 万条**（拟合交叉点 10,592）开始与线性项等量；10,000 条时它占修复前总耗时的 **53.2%**。
   ⇒ **"114 条达标"与"10,000 条达标"之间的真实断点就在 1 万条附近**，"114 条达标"不能外推到 1 万条。
3. 修复后指数回到 **1.020**、末/首比 ≈0.95、10,000 条从 731 ms 降到 342 ms（2.14×），
   且**与 n 的二次关系消失**。

### 1.4 测试与"对外行为不变"的证据

### 2.2 破线点（**两种口径分开判定**）

| 指标 | 目标 | 16 并发口径的最差 p99 | 结论 | 单线程口径的最差 p99 | 结论 |
|---|---|---|---|---|---|
| Registry 主键查询 | < 100 ms | 0.003 ms | 永不破线 | 0.002 ms | 永不破线 |
| Registry 过滤查询 | < 100 ms | 257.922 ms | **5,000 条起破线** | 4.123 ms | 永不破线 |
| Registry 分页信封 | < 100 ms | 731.180 ms | **500 条起破线** | 22.782 ms | 永不破线 |
| Registry 全量信封 | < 100 ms | 1555.607 ms | **1,000 条起破线** | **105.695 ms** | **10,000 条起破线** |

**必须说清楚的一点**：上表两列的破线点不同，是因为它们量的**不是同一件事**。

* **单线程列是结构成本**（算法/数据结构代价）：除"无条件全量信封"之外，其余指标在 10k 条时全部
  **< 23 ms**，**不破 100 ms**；Router 组装 **< 0.7 ms**，不破 50 ms。
  **唯一真正因条数而破线的是无条件全量信封**：单线程 p50 从 1.66 ms 涨到 **61.24 ms**、
  p99 从 8.34 ms 涨到 **105.70 ms**（10,000 条时越过 100 ms）。它与 N 近线性增长
  （"一次序列化 N 条"的固有成本），与 TASK-05 标定的"已知未达标项"一致。
  ⇒ **从数据结构看，10,000 条的破线点只有一个：`list_envelope()` 的无条件全量信封。**
* **16 并发列是部署形态下的尾**：分页信封在 **500 条**（本次最小规模）就已 p99 = 314 ms。
  这不是"500 条太多"，而是 **GIL 串行吞吐上限**造成的排队（见 §2.3）。

**注意分页信封在单线程口径下的非单调**（9.17 / 8.96 / 22.78 / 8.31 ms）：它在 5,000 条时数值最高，
10,000 条反而更低。这类单点抖动来自本机并发负载（每档只有 n=200 个样本），
**不足以支撑"5,000 比 10,000 更慢"的结论** —— 可用的判断只有"分页信封的单线程 p99 在 10k 以内始终 < 25 ms"。

### 2.3 尾延迟归因：不是算法退化，是 GIL 串行 + CPU 超订

三个独立探针（探针 1/2 出自 `_ci_logs/t08_cap_full3.txt` 第 ③ 节与 `_ci_logs/t08_cap_scaling.json`；
探针 3 出自 `_ci_logs/t08_cs_probe.txt` 第 ⑦ 节。1/2 的规模是 500/1k/5k/10k，3 的规模是 10,000）：

1. **关掉分代 GC**（诊断口径）：分页信封 p99 731.18 → **501.66 ms（1.46×）**、过滤查询 257.92 → 300.60 ms（0.86×）。
   ⇒ GC 对**信封**那条路有可观贡献（每次请求构造 500 个 dict），但两个数量级里只解释了一半不到，
   且对过滤查询无解释力。
2. **把 `sys.setswitchinterval` 压到 0.5 ms**（诊断口径）：**全面恶化** ——
   分页信封 p99 731.18 → **1446.19 ms**，过滤查询 257.92 → 587.00 ms，而单线程 p50 也从 1.9 ms 级
   抬到数百 ms 级（n=500 时 418.9 ms）。⇒ 切换更频繁只是加剧线程抖动，说明**争用已经饱和**。
3. **并发度扫描**（决定性判据，同一 Registry 实例，只改线程数）：

| 线程数 | 过滤查询 p50 | 过滤查询 p99 | 分页信封 p50 | 分页信封 p99 | **分页信封 qps** |
|---|---|---|---|---|---|
| 1 | 2.111 | 4.328 | 4.384 | 10.719 | **202.0** |
| 2 | 2.066 | 19.078 | 4.888 | 45.195 | **199.1** |
| 4 | 2.058 | 109.993 | 4.833 | 147.130 | **194.0** |
| 8 | 2.300 | 240.042 | 4.912 | 373.240 | **193.5** |
| 16 | 2.231 | 237.601 | 4.643 | **637.379** | **198.3** |
| 32 | 2.171 | 194.082 | 5.265 | 605.688 | **178.5** |

⇒ **p50 几乎不动（1.06×），p99 涨 59×，而吞吐恒定在 ~200 qps、与线程数无关**。
线程从 1 加到 32，吞吐一点没涨，只是把等待时间堆到了尾部。
这是 **GIL 串行（单进程内只有一条 Python 字节码流水线）+ 12 逻辑核上跑 16 个 CPU 密集线程**的典型指纹。

**因此本报告对"破线点"的最终回答**：

* **数据结构口径（可归因于代码）**：Registry 的唯一破线项是 **`list_envelope()` 无条件全量信封**，
  在 **10,000 条**时单线程 p99 = 105.70 ms（p50 61.24 ms）越过 100 ms 目标，且随 N 线性增长；
  过滤查询（4.12 ms）、分页信封（22.78 ms）、主键查询（0.002 ms）在 10k 以内**都不破线**；
  Router 组装（真实配置）最差 0.649 ms，距 50 ms 目标有两个数量级余量。
* **部署口径（v1.4 §6 的 p99 目标就是按并发定义的）**：**单进程 16 线程的 waitress 形态下，
  分页信封的 p99 目标在 500 条就已经不达标**，而根因是"每请求约 5 ms 的串行 Python 工作量 × 16 线程"
  ⇒ 这条目标**不是靠限制能力条数就能满足的**，必须从吞吐模型入手（见下）。
  1. 降低每请求的 Python 工作量（`list_envelope` 现已强制分页 500，但**仍先做一次全表 `query()` 扫描**，
     10k 时单线程 2.38 ms 全花在这；把 `limit` 下推进 `query()` 只能省序列化、省不了扫描）；
  2. 多进程 worker（waitress 单进程 → gunicorn/waitress 多实例），把 GIL 换成进程级并行；
  3. 对 `/capabilities/tools` 做**服务端缓存或游标流式**，把"一次处理 N 条"从请求路径上摘掉。

### 2.4 语义召回的 p99 由"查询词频"决定，不只是 N

语义召回口径说明：复用仓库既有检索栈的 **BM25 腿**（`HybridRetriever`，`AGENT_HYBRID_EMBEDDING=0`
⇒ `EmbeddingIndex.available=False`，代码本来就走纯 BM25 降级路；**没有**拉起句子向量模型）。
`/capabilities/skills/search` 这个真实端点是**复用** `agent/skills_mgmt/loader.py`（chroma + BM25 + RRF）
的，它检索的是**技能实体**而非能力条目，本脚本不注入合成技能实体，故**没有**按 500/1k/5k/10k 缩放它。

单线程 p50 恒为 0.013–0.015 ms（与 N 无关），但单线程 p99 从 2.79 ms（500 条）涨到 **36.93 ms**（10,000 条）。
逐查询拆解（n=10,000，单线程，每串 20 次，取自 `_ci_logs/t08_cap_full3.txt`）给出了原因：

| 查询串 | 单线程 p50 | 单线程 p99 | 命中返回 | 性质 |
|---|---|---|---|---|
| `'合成能力 1234 描述'` | **33.62 ms** | 42.32 ms | 25 | **高频词**：合成描述模板里每个文档都含这些字 ⇒ postings ≈ 全表 |
| `'压缩目录'` | 10.21 ms | 15.76 ms | 25 | 单字命中面很宽（"压"/"测"类字在描述模板里） |
| `'运行测试'` | 9.29 ms | 11.36 ms | 25 | 同上 |
| `'搜索互联网信息'` 等 6 串 | 0.006 ms | 0.008–0.022 ms | **0** | 词汇表里根本没有这些字 ⇒ 一次查表即返回 |
| `'synthetic 000123 search web fetch'` | 0.006 ms | 0.022 ms | **0** | 分词器把 `synthetic_000123` 当**一个** token（`[a-zA-Z0-9_]+`），查询里两个词因此都命不中 |

⇒ BM25 的单次成本 = Σ(命中 term 的 postings 长度)，**"命中面"而不是"条数"决定单次延迟**：
命中 25 条时 9–34 ms，一次不命中时 0.006 ms。

> ⚠ **本项的合成语料偏向"乐观"**：合成能力的 `description` 只有一句固定模板
> （`合成能力 {i}（压测用，非真实能力）`）＋ 合成名，**词汇表极小**，因此 10 条查询里有 6 条**完全不命中**
> （0.006 ms）——它们把 p50 拉到了 0.013 ms。**真实语料的描述丰富得多、绝大多数查询都会命中**，
> 分布会整体向"命中面宽"的那一端移动。
> ⇒ **不要**把这里的 p50 = 0.013 ms 当成"语义召回很快"的证据；可用的结论只有两条：
> ① 索引结构本身在 10k 条不退化（查表与排序的成本与 N 无关）；
> ② 单次召回的真实成本由**查询词的文档频率**决定，最坏的形态是 O(N)（本口径下 10k 约 34 ms 单线程），
> 这类查询在 16 并发下会随 GIL 队列一起放大（10k 时 16 并发 p99 = 33.5 ms）。
> 若要对这类查询兜底，应做**查询侧**限制（截断 postings / 对超高频 term 降权或跳过），
> 而不是继续优化索引结构。

### 2.6 **超限行为：当前无强制点**（必须写死的一句话）

2. **代码口径**（换一个检索口径复测，避免假阴性）：

⇒ **因此不能声称『单租户 ≤500 / 全局 ≤10,000』这条目标已受控**。它目前只是一句写在设计里的

## 3. 内存基线重测（E1r，**HEAD 版本**）

### 3.1 方法（可复现）

* 工具：`psutil.Process().memory_info()`，取 `rss`（驻留，取样瞬时）、`vms`（虚拟）、
  `peak_wset`（**内核记录的进程生命周期工作集峰值**——"压力峰值"必须用它，用取样 rss 会系统性低估）。
* **冷进程**：每个读数都在**新起的子进程**里取（`python -c` 只 import + 执行被测动作），
  避免分配器 arena 复用把前一次实验的驻留算进后一次。
* **空载基线采样 7 次**（间隔 0.25 s），报 min / 中位 / max；压力峰值取进程结束前的 `peak_wset`。
* 全部读数都在**应用级日志压到 CRITICAL**、`AGENT_HYBRID_EMBEDDING=0`（不拉句子向量模型）下采集。
* ⚠ **明确排除**：用户正在跑的后端 **PID 980** 的 WS **不是**本节的测量值（只在 §3.5 作为"非基准"的参考读数出现）。

### 3.2 HEAD 空载基线（冷进程，只 import TASK-08 热路径栈）

| 读数点 | RSS / WS | 备注 |
|---|---|---|
| 仅解释器 + psutil（import 前） | **22.84 MB** | 冷进程地板 |
| `import` capregistry + tool_router + tool_router_hybrid + tools 之后 | **39.14 MB**（7 次采样 min/中位/max 全为 39.14） | import 耗时 **401 ms**；类别数 11；工具注册表为空（`register_all` 由 app_server 装配时才调用） |
| 同进程 VMS | 381.16 MB | 虚拟地址空间（含保留区），**不要**当占用用 |
| 同进程 `peak_wset` | 39.14 MB | 空载阶段没有更高峰 |

> ⚠ **为什么这不是"app_server 整机空载占用"**：`import app_server` 在 **import 期**就会

### 3.3 压力峰值（合成负载，冷子进程逐规模）

| n | 建 Registry 后 RSS | 峰值 WS | 建检索索引后 RSS | 边际 MB/条 |
|---|---|---|---|---|
| 500 | 24.64 MB | 39.10 MB | 39.10 MB | 0.004 |
| 1,000 | 26.92 MB | 43.17 MB | 43.17 MB | 0.004 |
| 5,000 | 45.12 MB | 72.89 MB | 72.88 MB | 0.005 |
| **10,000** | **68.19 MB** | **109.19 MB** | 108.18 MB | 0.005 |

* 空载地板 22.4 MB（同一次运行内各规模一致）。逐段拆开看 10,000 条的边际占用：
  * Registry（10,000 条能力）：68.19 − 22.42 = **45.8 MB** ⇒ **≈4.6 KB/条**；
  * 检索索引（10,000 篇文档，BM25 倒排 + doc 长度表）：108.18 − 68.19 = **40.0 MB** ⇒ **≈4.0 KB/条**；
  * 两项合计 **≈86 MB / 8.6 KB/条**，进程峰值 WS **109.19 MB**。
* 构建耗时（同口径）：Registry 10k = **17.4 ms**；检索索引 10k = **213.2 ms**（修复后，见 §1）。
* **口径警告**：这些是**合成**能力（schema 刻意带 6 个参数，见 `_synthesize`），
  真实能力的 `input_schema`/AST 证据更重 ⇒ 真实 1 万条的占用**会更高**，本表不得外推为真实容量承诺。

### 3.4 旧读数（≈61–78 MB / ≈610–627 MB）的时效性与**来源更正**

* **来源**（两个检索口径都查了）：`_ci_logs/audit_20260919/云枢性能容量与可观测性审计报告.md` §7.6 与 §9

## 4. 局限与未测项（不得当成已覆盖）

1. **合成 ≠ 生产**：全部扩容数字来自 `_synthesize` 的合成能力，不得用于声称"真实 1 万条达标"。

   （属检索栈，见 `docs/RRF_5000SKILLS_CAPACITY_BOUNDARY_REPORT.md`）。

   该列的绝对值只说明"单进程 16 线程形态的尾很脆弱"，换机器/换负载会变；**结构成本（单线程）列才是可迁移的**。

   285.8 / 314.0 ms）⇒ 报告只对**量级与曲线形状**下结论，不引用单点之间的几毫秒差异。
7. **同文件并行改动**：`agent/tool_router_hybrid.py` 同时被并行会话改动（新增 `_WORKER_ENCODE_TIMEOUT` 等，
   见 `git diff`）。那些改动与 BM25 构建路径无关，本报告数字采集于该合并后的工作区。
   本子工作流**只提交自己的新增文件**，该共享文件保持未暂存，以免替并行会话预提交半成品。
