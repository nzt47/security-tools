## 1. Axios 封装（src/utils/request.ts）

### 1.1 契约（不易，勿随意改动）

后端统一返回结构，所有接口遵守：

```json
{ "code": 200, "data": null, "message": "success" }
```

| 场景 | 判定 | 行为 |
|---|---|---|
| 业务成功 | HTTP 200 且 `code === 200` | 返回 `response.data.data`（解包），调用方无 `.data` 嵌套 |
| 业务错误 | HTTP 200 且 `code !== 200` | `toast.error(message)` + Reject，**不跳转** |
| HTTP 401 | 网络层状态码 401 | 清除 token → `window.location.hash = '#/login'`（HashRouter，免整页刷新）→ toast |
| HTTP 403/404/500 | 网络层状态码 | 对应 toast 文案 + Reject |

### 1.2 拦截器职责

- **请求拦截**：从 `localStorage('token')` 读 Token，注入 `Authorization: Bearer <token>`；同时记录 `performance.now()` 起点（`WeakMap` 以 config 为 key，支持并发）。
- **响应拦截**：输出耗时日志 → 业务判定 → 错误提示 → 解包。

### 1.3 耗时统计日志（[perf]）

每个请求输出一行 `console.info`，格式：

```
[perf] POST /auth/login 200 510ms
[perf] GET /user/info 401 13ms     ← HTTP 状态码 401 走错误分支
```

- 实现：`logPerf()`（request.ts）；起点在请求拦截器，终点在响应成功/失败两个分支。
- 排查性能：关注耗时突增的接口（>1s 需查 mock 延迟/后端慢查询/网络）。

### 1.4 类型化请求方法

```ts
export function request<T = unknown>(config: AxiosRequestConfig): Promise<T>
```

- 泛型 `T` 即业务数据类型（已解包）。
- 注意：axios `^1.19` 的 `request<T, R>` 返回条件类型 `AxiosResponseResult`，无法直接得到 `Promise<T>`，故此处用 `as unknown as Promise<T>` 断言（见 request.ts 内注释，勿改回泛型写法）。

### 1.5 API 模块约定

业务接口统一放在 `src/api/`，按模块分文件（如 `user.ts`），导出：
- 类型定义（`LoginParams` / `LoginResult` / `UserInfo`）
- 接口函数（`login()` / `getUserInfo()`），内部用 `request<T>({ url, method, data })`

## 2. Toast 组件（src/components/Toaster.tsx + toast.css）

### 2.1 用法

```ts
import { toast } from '@/components/Toaster'

toast.success('保存成功') // 绿色
toast.error('出错了')     // 红色
toast.info('提示')        // 蓝色
```

- **模块级单例**：非 React 模块（如 request.ts 拦截器）也可直接调用。
- **挂载点**：`main.tsx` 中 `<Toaster />` 全局唯一（勿重复挂载，否则出现双 Toast）。

### 2.2 行为

| 项 | 值 |
|---|---|
| 位置 | 右上角 `fixed right-4 top-4 z-[9999]`，宽度 320px |
| 动画 | 淡入 `toast-in 0.3s` + 淡出 `toast-out 0.3s`（2.7s 后开始） |
| 生命周期 | 3 秒自动移除 |
| 样式 | Tailwind 类：success=绿、error=红、info=蓝（`TYPE_STYLE` 映射） |

### 2.3 修改注意（【不易】约束）

- `DURATION`（Toaster.tsx）与 `toast-out` 动画的 `2.7s` 延迟（toast.css）**必须同步调整**，否则会出现"未淡出即消失"或"淡出后残留透明元素"。
- 如需改样式/位置，只改 `TYPE_STYLE` 与容器 className。
- **去重逻辑**：`push()` 对同一 `type+message` 的已在展示 Toast 直接跳过（防弱网/StrictMode 并发重复请求导致多次弹窗，已实测：双请求 → 单弹窗）。改文案/提示策略时勿移除该去重。

## 3. 登录流程与跳转逻辑

### 3.1 路由结构（HashRouter，src/router/index.tsx）

```
/login            → LoginLayout → LoginPage（公开）
/                  → RequireAuth（守卫）→ MainLayout → Dashboard
/system/user       → 受保护，AuthRoute 权限守卫（仅 admin）
/profile           → 公开测试页（挂载时自动 GET /user/info）
/403               → 无权限页
/detached/:panelId → Electron 独立窗口
```

### 3.2 登录跳转规则（【变易】演进点）

- **路由守卫**（RequireAuth）：localStorage 无 token 访问受保护路由 → `<Navigate to="/login" state={{ from: location }}>`。
- **登录页**（src/pages/Login/index.tsx）：成功后 `navigate(from ?? '/', { replace: true })` —— 有来源路径跳回来源，否则直达仪表盘 `/`。
  - **历史教训**：曾写死 `/dashboard`，但路由表无该路径，依赖兜底重定向造成一次多余跳转；已改为 `/`。
- **HTTP 401 拦截**（request.ts）：清 token + 跳 `#/login`。因是 HashRouter，用 `window.location.hash` 而非 `pathname`，避免整页刷新；已在登录页时不重复跳转（防死循环）。

### 3.3 Token 生命周期

```
登录成功 → setToken() 写 localStorage('token') + useUserStore 同步
业务请求 → 请求拦截器自动注入 Authorization: Bearer <token>
HTTP 401 → clearToken() 清除 + 跳转 /login
退出登录 → clearToken() + 路由跳转
```

## 4. Mock 机制（src/mocks/devMock.ts）

### 4.1 开关

`.env.development` → `VITE_MOCK_API=true/false`（仅 dev server 生效，改后 Vite 自动重启）。

### 4.2 已实现的场景

| 接口 | 场景 | 返回 |
|---|---|---|
| `POST /api/auth/login` | 任意非空用户名/密码 | `{ code:200, data:{ token:'mock-token-xxx', user } }` |
| `GET /api/user/info` | 无 Token | HTTP 200 + `code:401`（**业务错误** → 弹 Toast，不跳转） |
| `GET /api/user/info` | Token 以 `expired-` 开头 | **HTTP 401**（→ 清 token + 跳转 `#/login`） |
| `GET /api/user/info` | 正常 Token | 返回用户信息 |
| `GET /api/user/list` | 分页/关键字 | 26 条 mock 用户 |
| `DELETE /api/user/:id` | — | 成功 |

### 4.3 手动复现两个关键场景

1. **业务 401 Toast**：清空 token 访问 `#/profile` → 红色 Toast「未登录或登录已过期」，页面不跳转。
2. **HTTP 401 跳转**：`localStorage.setItem('token', 'expired-mock-token')` 后访问 `#/profile` → 跳转 `#/login`、token 被清除。

### 4.4 扩展 mock

在 `configureServer` 中间件中按 `req.method + url` 追加分支，`sendJson(res, status, body)` 返回统一结构；注意中间件先于 vite proxy 执行（命中即不转发后端）。

## 5. 环境变量与后端联调

### 5.1 前端相关变量（yunshu-ui/.env.development）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `VITE_MOCK_API` | false | true 时启用本地 mock（无后端开发） |
| `VITE_API_PROXY_TARGET` | `http://127.0.0.1:5678` | Vite dev 代理目标（后端换端口/远程时覆盖） |
| `VITE_API_BASE` | 空 | 直连后端地址（需后端开 CORS）；留空走相对 `/api` + 代理 |
| `VITE_DEV_SERVER_PORT` | 5173 | dev server 端口 |

### 5.2 500 错误的根因与排查

- **根因**：Vite 把 `/api` 代理到 `VITE_API_PROXY_TARGET`，但目标后端未启动 → 代理失败返回 500。
- **排查顺序**：① 后端是否监听（`Invoke-RestMethod http://127.0.0.1:5678/api/health`）→ ② 端口是否与 `VITE_API_PROXY_TARGET` 一致 → ③ 是否误开了 mock 之外的转发。

### 5.3 后端启动方式（真实后端）

```powershell
# 项目根目录（venv 缺依赖时用系统 Python，需 Python 3.12 + flask）
python app_server.py        # 监听 127.0.0.1:5678
```

- 依赖根目录 `.env`（LLM key 等）；缺失时以降级模式启动（有 WARNING，服务可用）。
- **启动耗时**：约 1-2 分钟（加载 8+ 模块：规划引擎/工作流/分身等），期间端口未绑定，属正常。

### 5.4 真实后端现状（重要维护信息）

`app_server.py` 已实现管理模板全部核心接口，实测：

| 接口 | 真实后端 | mock |
|---|---|---|
| `/api/auth/login` | ✅ 200（admin/admin123） | ✅ |
| `/api/user/info` | ✅ 200（Bearer token） | ✅ |
| `/api/user/list` | ✅ 200（分页 + keyword 搜索） | ✅ |
| `DELETE /api/user/:id` | ✅ 200（内置管理员 400 / 不存在 404） | ✅ |
| `/api/auth/token-check` | ✅ 200 | — |
| `/api/health` / `/api/status` | ✅ 200 | — |

> 结论：管理模板全部接口已可真实联调（`VITE_MOCK_API=false`）；mock 作为无后端时的兜底保留。

### 5.5 管理后台认证实现（app_server.py「管理后台用户认证」段）

- 契约与前端 mock 完全一致（见 §4.2），前端无需任何改动即可在 mock / 真实后端间切换。
- 账号：单管理员。凭据经根目录 `.env` 的 `YUNSHU_ADMIN_USERNAME` / `YUNSHU_ADMIN_PASSWORD` 配置（**当前环境实测为 admin/123456**；未配置时代码默认 admin/admin123，启动日志会在使用默认密码时告警）。前端/脚本联调用同一凭据。
- 令牌：`secrets.token_hex(32)`，存储 **Redis 优先**（`REDIS_URL`，默认 `redis://127.0.0.1:6379/0`；SET EX 由 Redis TTL 自动清理，**后端重启不失效**）；Redis 不可用时自动降级内存（启动有 WARNING，重启后令牌失效）。有效期环境变量 `YUNSHU_USER_TOKEN_TTL`（默认 86400 = 24h）。
- 本地无 Redis 时的验证方式：`pip install fakeredis --target .devtools/pylibs` 后用 `TcpFakeServer(('127.0.0.1', 6379))` 起一个 Redis 协议兼容服务即可全链路验证（本仓库已实测：重启后端后旧 Token 仍有效）。
- 鉴权语义（与前端拦截器对应）：
  - 登录失败 → HTTP 200 + `code:401`（业务错误，前端弹 Toast，停留登录页）
  - 无 Token 访问受保护接口（user/info、user/list、DELETE）→ HTTP 200 + `code:401`（业务错误，前端弹 Toast，停留当前页）
  - Token 无效/过期 → **HTTP 401**（前端清 token + 跳转 `/login`）
- 用户管理数据：进程内种子列表（26 条，`_seed_manager_users`），后端重启恢复初始数据；内置管理员(id=1)不可删除。
- 安全注意：登录接口 `@log_request(show_body=False)`，请求体不落日志（避免密码泄露）；密码比对用 `secrets.compare_digest`（防时序攻击）。

## 6. 故障排查与测试指引

### 6.1 令牌存储的 Redis 降级逻辑

行为（`app_server.py` `_UserTokenStore`）：

| 场景 | 表现 | 影响 |
|---|---|---|
| 启动时 `REDIS_URL` 不可达 | 日志 WARNING「Redis 不可用…降级为内存存储」 | 令牌存内存，**后端重启后失效**（需重新登录） |
| 运行中 Redis 断连 | 单次读写异常被捕获，日志 WARNING「Redis 写入/读取失败，降级内存存储」 | 该次操作走内存，不影响请求；Redis 恢复后连接池自动重连 |

排查与恢复：
1. **判断当前用哪个**：看后端启动日志——`用户令牌存储：Redis（…）` = Redis 模式；`Redis 不可用…降级` = 内存模式。
2. **恢复 Redis**：启动 Redis（本仓库无真实 Redis 时可用 fakeredis 起兼容服务：`pip install fakeredis --target .devtools/pylibs` 后 `TcpFakeServer(('127.0.0.1', 6379)).serve_forever()`），**后端无需重启**（redis-py 连接池自动重连）；但内存模式期间签发的令牌不会自动迁入 Redis。
3. **常见坑**：`REDIS_URL` 用 `localhost` 时可能优先解析 IPv6 `::1` 而实际服务监听 IPv4 `127.0.0.1`，建议统一用 `127.0.0.1`；改 `REDIS_URL`/`YUNSHU_USER_TOKEN_TTL` 后需重启后端生效。
4. **历史教训**：改造令牌存储时曾残留旧版 `_issue_user_token`/`_resolve_user_token`（引用已删除的 `_USER_TOKENS`）导致登录 500（`NameError`）。改动此类模块级函数后，务必 grep 旧引用确认无残留再重启验证。

方式一（Postman GUI）：导入 `postman/云枢管理后台接口.postman_collection.json` → 按文件夹顺序执行 → 登录成功后 token 自动写入集合变量，其余接口自动带 `Authorization: Bearer {{token}}`。

### 6.3 令牌过期 / 401 跳转排查

- **现象**：前端页面突然跳转 `#/login`、token 被清、弹红色 Toast「登录已过期，请重新登录」。
- **链路**：Redis 中 `yunshu:user_token:<token>` 过期或被删 → 后端 `GET` 返回空 → 判定 `invalid` → 返回 **HTTP 401** → 前端拦截器 `clearToken()` + 跳转。
- **排查命令**：
  ```powershell
  python -c "import redis; r=redis.Redis.from_url('redis://127.0.0.1:6379/0'); print('exists:', r.exists('yunshu:user_token:<token>'), '| ttl:', r.ttl('yunshu:user_token:<token>'))"
  ```
- **模拟过期**（复现验证）：登录取 token 后删除 Redis key（`r.delete('yunshu:user_token:<token>')`），再请求任一受保护接口即返回 401；前端加载该 token 访问 `#/profile` 即可观察完整跳转链路（已实测通过）。

### 6.4 自动化故障排查脚本

文件：`scripts/dev/backend_auth_smoke.py`（后端接口故障排查的完整可执行版本，含 PASS/FAIL 汇总与退出码）

```powershell
python scripts/dev/backend_auth_smoke.py                                    # 默认直连 127.0.0.1:5678
python scripts/dev/backend_auth_smoke.py --base-url http://localhost:5173   # 经 Vite 代理联调
```

覆盖 20 项断言：
- 登录：成功/错误密码（code 401）/空参数（code 400）
- 用户信息：有效 Token / 无 Token（业务 401）/无效 Token（HTTP 401）
- 用户列表：分页 / 关键字搜索
- 删除：成功 / 内置管理员（400）/不存在（404）
- 新增：成功 / 重复用户名（400）/空用户名（400）；编辑：邮箱/角色/状态；清理测试用户
- Redis：令牌写入 Redis、删除 key 模拟过期 → HTTP 401；Redis 不可达时自动降级检测（内存签发令牌仍可用、无 500）

> 凭据默认读根目录 `.env`（`YUNSHU_ADMIN_USERNAME/PASSWORD`），与后端行为一致；复现 Redis 断连降级：停止 Redis 后重跑本脚本即可（脚本自动检测存储模式）。

### 6.5 实测记录（2026-08-18）

**Redis 断连降级日志时间线**（真实断连一次事件，日志原文摘录）：

| 时间 | 日志（节选） | 触发与含义 |
|---|---|---|
| 12:58:36 | `[INFO] 用户令牌存储：Redis（redis://localhost:6379/0），TTL=86400s` | Redis 模式启动 |
| 12:58:42 | `[WARNING] Redis 读取失败，降级内存存储：Protocol Error: b'_'` | `GET /user/info`（旧 Redis 令牌）→ 残留连接被截断 → 降级内存 → 内存无该令牌 → 返回 401 |
| 12:58:44 | `[WARNING] Redis 读取失败，降级内存存储：Protocol Error: b'_'` | 同上，二次读取降级 |
| 12:59:00 | `[WARNING] Redis 写入失败，降级内存存储：Timeout connecting to server` | `POST /auth/login` → 新连接被拒超时 → 降级内存写入 → 登录成功（内存签发） |

**结论**：断连瞬间残留连接报 `Protocol Error`，随后新连接报 `Timeout connecting`；读写两条降级路径均按预期触发，服务全程不 500。

**自动化测试通过报告**：`python scripts/dev/backend_auth_smoke.py` 实测 **PASS=20 FAIL=0**（退出码 0）：
- Redis 正常模式：20/20（含「新增/编辑/清理用户」「登录令牌写入 Redis」「令牌过期（key 删除）→ HTTP 401」）
- Redis 断连模式：20/20（过期模拟两项断言自动替换为「内存签发登录/用户信息可用、无 500」降级检测）

## 7. 常见改动 checklist

- [ ] 改了 Toast 时长 → 同步 `DURATION` 与 `toast.css` 动画延迟
- [ ] 新增业务接口 → `src/api/` 新建模块 + 完整类型定义
- [ ] 后端接口路径调整 → 同步 mock（devMock.ts）与 `src/api/` URL
- [ ] 改了 401 跳转 → 确认 HashRouter 下用 `window.location.hash`，并测试防死循环
- [ ] 回归验证 → 登录、业务 401 Toast、HTTP 401 跳转三个场景（见 §4.3），或直接跑 `scripts/dev/backend_auth_smoke.py`
- [ ] 改了 Toast 提示逻辑 → 确认去重（同文案只弹一次）仍生效（见 §2.3）
