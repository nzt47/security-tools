# requesting-code-review

> LLM 整理，逐条经**原文引用校验**：verified 30 / 30（未通过的已丢弃）。

## 何时使用

- 完成任务、实现核心功能时，或合并代码前，用它确认工作是否符合要求。
- 在子代理驱动开发中，每个任务完成后进行审查。
- 完成重大功能后进行审查。
- 合并到主分支前进行审查。
- 卡住时借助新视角进行审查。
- 重构前做基线检查。
- 修复复杂 bug 后进行审查。

## 步骤

- 立即修复 Critical 问题。
- 继续之前修复 Important 问题。
- 记录 Minor 问题留待后续处理。
- 如果审查者有误，带理由进行反驳。
- 每个任务后都进行审查。
- 在问题累积前发现它们。
- 进入下一个任务前先修复。
- 每个任务后或自然检查点进行审查。
- 获取反馈、应用、继续。
- 合并前进行审查。
- 卡住时进行审查。
- 用技术理由进行反驳。
- 展示能证明其有效的代码或测试。
- 请求澄清。

## 参数

- 提供所做工作的简要说明。
- 提供计划或需求，说明它应该做什么。
- 提供起始提交 SHA。
- 提供结束提交 SHA。

## 约束 / 反例

- 不要因为“很简单”就跳过审查。
- 不要忽略 Critical 问题。
- 不要在 Important 问题未修复时继续推进。
- 不要与有效的技术反馈争辩。
