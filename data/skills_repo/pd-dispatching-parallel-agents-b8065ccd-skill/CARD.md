# dispatching-parallel-agents

> LLM 整理，逐条经**原文引用校验**：verified 27 / 27（未通过的已丢弃）。

## 何时使用

- 面对 2 个以上可独立开展、无需共享状态或先后依赖的任务时使用。
- 适用于多个测试文件因不同根因失败的情况。
- 适用于多个子系统各自独立损坏的情况。
- 每个问题都能在不依赖其他问题上下文的情况下被理解。
- 各调查之间没有共享状态。

## 步骤

- 为每个 agent 指定具体范围：一个测试文件或子系统。
- 为每个 agent 设定清晰目标：让这些测试通过。
- 给 agent 加约束：不要改动其他代码。
- 要求 agent 输出预期结果：所发现与修复内容的摘要。
- 阅读每个 agent 的摘要。
- 验证各修复之间不冲突。
- 运行完整测试套件。
- 整合所有改动。
- 阅读测试文件并理解每个测试验证什么。
- 识别根因：是时序问题还是真实缺陷。
- 用基于事件的等待替换任意超时。
- 若发现中止实现中的缺陷则修复。
- 若测试的是已变更的行为，则调整测试预期。

## 参数

- 任务应聚焦于单一明确的问题域。
- 任务应自包含，包含理解问题所需的全部上下文。
- 应明确说明 agent 需要返回什么输出。

## 约束 / 反例

- 若失败彼此相关（修一个可能修好其他），则不应并行分派。
- 若需要理解完整系统状态，则不应并行分派。
- 若多个 agent 会互相干扰，则不应并行分派。

## 示例

- 示例测试：应中止工具并捕获部分输出，期望消息中出现 'interrupted at'。
- 示例测试：应处理已完成与已中止工具混合的情况，快速工具被中止而非完成。
- 示例测试：应正确跟踪 pendingToolCount，期望 3 个结果却得到 0。
