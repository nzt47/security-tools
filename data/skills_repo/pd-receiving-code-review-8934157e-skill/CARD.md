## 何时使用

- 在收到代码审查反馈时、着手实现建议之前使用，尤其当反馈不清晰或技术上存疑时。
- 需要技术严谨与验证，而不是表演式附和或盲目实现。

## 步骤

- 第一步：完整阅读反馈，不做反应。
- 第二步：用自己的话复述需求，或提问。
- 第三步：对照代码库实际情况进行核实。
- 第四步：评估该建议对当前这个代码库在技术上是否合理。
- 第五步：给出技术性确认或有理有据的反驳。
- 第六步：逐项实现，每项都测试。
- 回应时复述技术需求。
- 提出澄清性问题。
- 如果反馈有误，用技术理由反驳。
- 直接开始工作，行动胜于言辞。
- 对可信来源的反馈，理解后再实现。
- 范围不清晰时仍要提问。
- 先澄清所有不清楚之处，再按顺序实现。
- 实现顺序：先处理阻塞性问题（破坏、安全）。
- 实现顺序：再处理简单修复（拼写、导入）。
- 实现顺序：最后处理复杂修复（重构、逻辑）。
- 逐个测试每个修复。
- 验证没有引入回归。

## 约束 / 反例

- 避免说“You're absolutely right!”，这是明确违反 CLAUDE.md 的行为。
- 避免“Great point!”/“Excellent feedback!”这类表演式回应。
- 避免在验证之前就说“Let me implement that now”。
- 不做表演式附和。
- 跳过空话，直接行动或做技术性确认。
- 核实：该建议对当前这个代码库在技术上是否正确？
- 核实：是否会破坏现有功能？
- 核实：当前实现的原因是什么？
- 核实：是否在所有平台/版本上都能工作？
- 核实：审查者是否了解完整上下文？
- 当建议会破坏现有功能时，作为需要警惕的情形。
