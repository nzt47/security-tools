# test-driven-development

> LLM 整理，逐条经**原文引用校验**：verified 32 / 32（未通过的已丢弃）。

## 何时使用

- 在实现任何新功能或修复 Bug 时，应在编写实现代码之前使用。
- 触发条件包括 test、driven、development。

## 步骤

- 步骤清单中的一项：New features。
- 步骤清单中的一项：Bug fixes。
- 步骤清单中的一项：Refactoring。
- 步骤清单中的一项：Behavior changes。
- 步骤清单中的一项：Throwaway prototypes。
- 步骤清单中的一项：Generated code。
- 步骤清单中的一项：Configuration files。
- 测试应只覆盖一个行为。
- 测试应有清晰的名称。
- 使用真实代码，除非不可避免否则不使用 mock。
- 测试通过。
- 移除重复。
- 改进名称。
- 提取辅助函数。

## 约束 / 反例

- 不要把它保留为“参考”。
- 不要在编写测试时“改编”它。
- 不要看它。
- 删除就是删除。
- 测试应失败而不是报错。
- 失败信息应符合预期。
- 失败应是因为功能缺失，而不是拼写错误。
- 其他测试仍然通过。
- 输出应干净，没有错误和警告。
- 可能测试了错误的东西。
- 可能测试了实现而非行为。
- 可能遗漏了你忘记的边界情况。
- 你从未看到它捕获该 Bug。
- 没有记录你测试了什么。
- 代码变化时无法重新运行。
- 在压力下容易忘记用例。
