# testing-anti-patterns

## 何时使用

- 在编写或修改测试、添加 Mock（测试替身），或者想往生产代码里加仅供测试使用的方法时，应加载这份参考指南。
- 这份指南列出那些让测试通过却证明不了任何东西的反模式，并给出能防止它们的 TDD 纪律。

## 步骤

- TDD 循环：先写失败的测试，再实现使其通过，然后重构，最后才声称完成。
- 修复测试 Mock 行为的做法：不 Mock 该组件并断言真实组件，或者若必须为隔离而 Mock，就不要对 Mock 断言，而是测试页面在侧边栏存在时的行为。
- 修复生产代码中仅供测试方法的方式：把清理逻辑放到测试工具中（如 cleanupSession），生产类不提供 destroy()。
- 修复过度 Mock 的方式：在正确层级 Mock，只 Mock 慢的部分并保留测试所需的行为。
- 修复不完整 Mock 的方式：让 Mock 响应镜像真实 API 的完整性，包含真实 API 返回的所有字段。

## 约束 / 反例

- 核心原则：测试代码做了什么，而不是测试 Mock 做了什么；Mock 只是隔离手段，不是被测对象。
- 三条铁律：绝不测试 Mock 行为；绝不往生产类加仅供测试的方法；绝不在不理解依赖的情况下 Mock。
- 若不确定测试依赖什么，先用真实实现跑一遍测试，观察实际需要发生什么，再在正确层级加最小 Mock。
- Mock 的规则是：按现实中完整的数据结构来 Mock，而不只是当前测试用到的字段。
- 若不确定，就包含所有有文档记录的字段。
- 测试是实现的一部分，不是可选的后续工作；没有测试就不能声称完成。
- 出现这些警示信号时应警惕：断言检查 *-mock 测试 ID、方法只在测试文件中被调用、Mock 搭建占测试 50% 以上、移除 Mock 后测试失败、说不清为何需要 Mock、为求保险而 Mock。
- Mock 过于复杂时（搭建比测试逻辑还长、为让测试通过而 Mock 一切、Mock 缺少真实组件的方法、Mock 一变测试就坏），应考虑用真实组件做集成测试。
- 底线：Mock 是隔离的工具，不是被测对象；如果 TDD 发现你在测 Mock 行为，说明已经走错，应改为测真实行为或质疑为何要 Mock。

## 示例

- 反模式一示例：测试只验证 Mock 是否存在，属于坏做法。
- 反模式二示例：生产类 Session 中的 destroy() 只在测试里使用，却看起来像生产 API。
- 反模式三示例：Mock 掉的方法带有测试所依赖的副作用（写配置），导致重复服务器检测失效。
- 反模式四示例：只 Mock 自己认为需要的字段，缺少下游代码会用到的 metadata，后续访问时出错。
- 反模式五示例：实现完成但没有写测试，却声称已准备好测试。
