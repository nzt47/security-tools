# code-refactor

> LLM 整理，逐条经**原文引用校验**：verified 16 / 16（未通过的已丢弃）。

## 何时使用

- 用户要求重命名标识符、替换过时代码模式、更新方法调用或在多个位置做一致更改时使用。
- 触发场景包括：把某标识符重命名为新名称、替换所有某模式、重构为使用新模式、更新所有对某函数/API 的调用、把旧模式转换为新模式。

## 步骤

- 按文件数量选择模式：1-9 个文件用原生工具（Grep + Edit 配合 replace_all），10+ 个文件自动使用 code-execution 技能。
- 原生模式核心流程第一步：用 Grep 找出所有出现位置，先列出文件，再带上下文核对。
- 第二步：用 Edit 并设置 replace_all=true 替换所有实例。
- 第三步：再次用 Grep 验证，旧模式应无匹配结果。
- 重命名函数示例流程：查找、统计出现次数、逐文件 replace_all 替换、重新 Grep 验证、建议运行测试。
- 替换过时模式示例：先 Grep 定位 var 声明，分析应改为 let 还是 const，再 Edit 替换，最后运行 lint 验证。
- 更新 API 调用示例：Grep 定位旧路径，用 replace_all 替换为新路径，并建议做集成测试。
- 安全流程：搜索全部、分析是否合适、告知用户范围、执行更改、验证已应用、建议运行测试。

## 参数

- Edit 的 replace_all=true 表示替换所有出现；false 表示只替换第一个（多个匹配时会失败）；匹配必须完全一致，包括空白和引号。
- Grep 参数：-n=true 显示行号，-B=N/-A=N 显示上下文行，-i=true 忽略大小写，type="py" 按文件类型过滤。

## 约束 / 反例

- 规划阶段：先找出所有实例、审查每个匹配的上下文、告知用户范围、考虑字符串和注释等边界情况。
- 边界情况：字符串/注释中的匹配需询问是否更新；导出的 API 要警告破坏性变更；注意大小写敏感性并明确说明。

## 示例

- 10+ 文件时自动切换到执行模式，可用 code_transform 的 rename_identifier 批量重命名，显著节省 token。
- 可与 test-fixing、code-transfer、feature-planning 技能配合：重构后修复测试、迁移重构后的代码、规划大型重构。
