# writing-plans

> LLM 整理，逐条经**原文引用校验**：verified 27 / 27（未通过的已丢弃）。

## 何时使用

- 在动手写代码之前，当你手头有规格说明或多步骤任务的需求时使用。

## 步骤

- 设计边界清晰、接口明确的单元，每个文件只承担一项明确职责。
- 优先使用更小、更聚焦的文件，而不是承担过多职责的大文件。
- 一起变更的文件应放在一起，按职责而非技术分层来拆分。
- 先写会失败的测试。
- 运行测试确认它失败。
- 实现让测试通过的最小代码。
- 运行测试并确认通过。
- 提交。
- 在计划中标注要创建的文件的确切路径。
- 在计划中标注要修改的既有文件及其确切行号范围。
- 在计划中标注测试文件的确切路径。
- 必需子技能：使用 superpowers:subagent-driven-development。
- 每个任务使用全新的子代理，并进行两阶段审查。
- 必需子技能：使用 superpowers:executing-plans。
- 批量执行并设置检查点以供审查。

## 参数

- 始终给出确切的文件路径。
- 每个步骤都给出完整代码；若某步骤改动代码，就展示该代码。
- 给出确切的命令及预期输出。
- 遵循 DRY、YAGNI、TDD 与频繁提交。

## 约束 / 反例

- 在既有代码库中遵循既有模式；不要单方面重构大文件，但若正在修改的文件已变得难以驾驭，可在计划中包含拆分。
- 避免使用“TBD”“TODO”“implement later”“fill in details”这类占位表述。
- 避免“添加适当的错误处理”“添加校验”“处理边界情况”这类笼统表述。
- 避免只写“为上述内容写测试”而不给出实际测试代码。
- 避免“与任务 N 类似”的写法，应重复给出代码，因为工程师可能不按顺序阅读任务。
- 避免只描述做什么而不展示怎么做的步骤；代码步骤必须包含代码块。
- 避免引用任何任务中都未定义的类型、函数或方法。
